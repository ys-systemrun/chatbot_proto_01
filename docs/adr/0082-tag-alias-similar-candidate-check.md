# ADR-0082: タグエイリアス追加・編集時の重複・類似候補チェック適用（ADR-0071の適用範囲拡張）

- ステータス: Accepted
- 日付: 2026-09-09
- 関連: `docs/requirement/202609091119_タグエイリアス管理機能要件定義書.md`, ADR-0071

## コンテキスト

ADR-0071は、`TagTreePage`の新規タグ作成フォームに、入力中の名前と既存タグ名・エイリアスとの類似候補を非ブロッキングで提示する機能（`findSimilarTags`、`front_dev/src/feature/tag_admin/tagFilter.ts`）を追加した。この機能は、タグ運用ガイドライン（202609021050）5章が定める「新規タグ作成前に既存タグ・エイリアスを確認する」手順を、担当者の記憶・手作業に頼らず支援するものだった。

ADR-0080により、`TagTreePage`からエイリアス自体を追加・編集できるようになったが、この入力に対しては類似候補チェックが適用されない。しかし、エイリアスの追加も「既存の別概念の名前・エイリアスと紛らわしい文字列を登録してしまう」リスクという点では、タグの新規作成と本質的に同じ性質の操作である（例: あるタグに「ネット認証」というエイリアスを追加しようとしたが、実は別タグ「ネットワーク認証」のエイリアスと紛らわしい、といったケース）。ADR-0071の要件定義書（202609021102）12章Open Issue #4も、「重複・類似名チェックを新規作成時以外にも適用するか」を別途確認すべき論点として残していた。

## 決定

**ADR-0071で実装済みの`findSimilarTags`を、タグ新規作成の入力欄に加えて、エイリアスの追加・編集の入力欄にも適用する。対象タグ自身の名前・他のエイリアスとの一致は候補から除外する。**

- `findSimilarTags(tree, input, threshold)`はタグの木構造全体を走査する純粋関数であり、呼び出し側で対象を絞ることができる。エイリアス追加・編集時は、返された候補から「操作対象のタグ自身（`node.id`が一致するもの）」を除外してから表示する。これは、同じタグに複数のエイリアス（表記ゆれ）を登録すること自体は正常な操作であり、警告する必要がないためである。
- 候補が見つかった場合の表示・挙動（非ブロッキング、候補の名前・説明文・所属階層を表示）は、ADR-0071のタグ新規作成時と同じ実装を再利用する。
- 完全一致の重複（別のエイリアスと文字列が完全に一致する場合）は、従来通り`add_tag_alias`/`update_tag_alias`の`TagError`（`tag_alias.alias`のUNIQUE制約由来）で拒否する。本ADRはこれに加えて近似一致を検知する非ブロッキングの警告を追加するものであり、既存の重複防止機構を置き換えるものではない（ADR-0071と同じ位置付け）。

## 検討した代替案

- **エイリアス追加・編集には類似候補チェックを適用しない（現状維持）**: 実装コストは最小だが、タグ新規作成と同種のリスク（紛らわしい表記の混入）がエイリアス側にも存在するにもかかわらず放置することになり、タグ運用ガイドラインが目指す「タグという統制されたボキャブラリーを一貫して育てる」という目的と整合しない。発注者確認の結果、適用範囲を広げることとした。
- **対象タグ自身の名前・エイリアスとの一致も候補から除外せず表示する**: 実装は単純だが、エイリアス追加のたびに「自分自身のタグ名と一致しています」といった無意味な警告が常に表示されることになり、UXを損なう。対象タグ自身は候補から除外する方式を採用した。
- **エイリアス側は`rename_tag`と同様、当面チェック対象に含めない（ADR-0071要件定義書202609021102 Open Issue #4の未決事項に合わせて保留する）**: `rename_tag`（タグ名自体の変更）は既存タグへの参照（`qa_tag`等）が既にある分、別タグとの類似が発覚した場合の対処（統合・リネーム）がより重い操作になるため、慎重な検討が必要という事情がある。一方エイリアス追加は新規登録であり、`rename_tag`ほど後戻りのコストが高くないため、本ADRでは先行してエイリアス側にのみ適用することとし、`rename_tag`への適用可否は202609021102 Open Issue #4の検討を待つ、と整理した。

## 結果・影響

- `front_dev`の`tagFilter.ts`（`findSimilarTags`）自体には変更を加えない。`TagTreePage.tsx`のエイリアス追加・編集フォームから、既存の新規タグ作成フォームと同じ関数を呼び出す形で再利用する（対象タグ自身を除外するフィルタ処理のみ呼び出し側に追加）。
- 類似候補チェックの閾値・正規化ルールはADR-0071と共有され、個別に調整することはしない（要件定義書202609021102 Open Issue #5の対象範囲に含まれる）。
- `rename_tag`への適用要否は引き続き未決（202609021102 Open Issue #4）。
