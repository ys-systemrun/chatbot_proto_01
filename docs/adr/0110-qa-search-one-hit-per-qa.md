# ADR-0110: QA の検索結果を QA ごとに 1 件にまとめる

- ステータス: Proposed（実装済み。AWS へ反映して評価 v3 を実行し、出典の一致率と記事が出典に出るかを確かめたら Accepted にする）
- 日付: 2026-11-04
- 関連: ADR-0058 / ADR-0059（タグ類似度によるスコア）, ADR-0078（トラブルシューティング記事の検索統合）, ADR-0105（Redmine のエラー対応）

## コンテキスト

`QARepository.search` は、言い換え質問文（`hiroba_question_altered`）の行ごとに埋め込み距離で候補を取り、
スコア順に上位 `top_k` 件を返していた。同じ QA に属する言い換えが複数ヒットすると、**同じ QA が上位の枠を
何件も占める**。

チャットの検索は `top_k=3`（agent_invitro）で、`SearchService` は QA と記事の結果をスコア順に並べて上位
`top_k` 件にする。そのため、よく当たる QA が 3 枠を埋め、**トラブルシューティング記事が出典に入れなかった**。
2026-11-02 の評価（v3, pipeline / agentic の 50 回答）と、それ以前のすべての評価結果で、出典が記事になったことは
一度もなかった。例えば `h004`（ContainerNotFound）の出典は、同じ QA `a8582b80…` が 3 件並んでいた。
agentic 方式は結果を `id` で重複排除する（F-6.3.7）が、それは上位 3 件を受け取った後なので、枠は増えない。

ADR-0105 で Redmine のエラー対応 29 件を加え、ADR-0109 で本番で欠けていた記事 52 件の埋め込みも入れたが、
このままではそれらが回答に使われない。

## 決定

**`QARepository.search` は、QA ごとに最もスコアの高い 1 件だけを残してから上位 `top_k` 件を返す。**

- スコアは、その QA の言い換えのうち最も近いもの（タグ類似度を合成したもの）を使う。
- 候補の取り方（候補プール `pool_size`、検索対象フラグ、カテゴリ・タグ）は変えない。
- `TroubleshootingRepository`（記事ごとに埋め込み 1 件）と `SearchService` は変えない。

## 影響

- 上位 `top_k` 件が別々の QA・記事になるため、2 番目以降の候補（別の QA や記事）が出典に入りやすくなる。
  逆に、1 つの QA だけが正解の質問では、2・3 番目の出典が関係の薄い QA・記事になりうる（回答生成が関係の
  薄い出典に引きずられないかを評価で確かめる）。
- 出典の一致率（`source_hit_at_1` など）は、正解の QA が 1 位にあれば変わらない。
- 候補プールの中で QA が少数に偏っていると、返す件数が `top_k` より少なくなることがある（プールは
  `max(top_k * 10, 50)` 行）。
