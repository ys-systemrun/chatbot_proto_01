# ADR-0068: 管理画面一覧ページ（QA一覧・言い換え質問文一覧）の検索条件・ページ位置のURL同期方式

- ステータス: Accepted
- 日付: 2026-08-31
- 関連: `docs/requirement/202608311600_QA一覧・言い換え質問文一覧ページ検索条件URL保持機能要件定義書.md`, ADR-0015, ADR-0064, ADR-0067

## コンテキスト

QA一覧ページ（`QaListPage.tsx`）・言い換え質問文一覧ページ（`QuestionAlteredListPage.tsx`）は、検索条件（`keyword` / `category` / `tag_id`、`keyword` / `qa_id`）とページ位置（`offset`）を`useState`によるコンポーネントローカルなstateのみで保持しており、URL（`/admin/qa`, `/admin/question_altered`固定パス）には一切反映していない。`react-router-dom`（6.26系、ADR-0015で`/admin`サブツリー限定に導入済み）のルーティングにより、一覧ページから編集ページ（`/admin/qa/:id`等）へ遷移すると一覧側のコンポーネントはアンマウントされ、ローカルstateは破棄される。編集ページ（`QaFormPage.tsx` / `QuestionAlteredFormPage.tsx`）は、保存・削除成功後に`navigate("/admin/qa")` / `navigate("/admin/question_altered")`という固定パスへ遷移し、「一覧へ戻る」リンクも同じ固定パスの`Link`である。この結果、検索条件・ページ位置を指定した状態から1件編集して戻ると、一覧は毎回初期状態（検索条件なし・1ページ目）にリセットされる。

発注者から、(a) 検索条件・ページネーションをURLクエリから注入できるようにすること、(b) 編集後に検索条件・ページ位置を保持したまま一覧へ戻れるようにすること、の2点が要望として示された（要件定義書202608311600）。本ADRはこれを実現する実装方式を決定する。

検討にあたり、発注者へ以下4点を確認済みである。

1. 検索条件・ページ変更時のブラウザ履歴の扱い: **replace**（履歴を積み上げない）を採用する。
2. 編集ページから一覧ページへ戻る際の検索条件・ページ位置の引き継ぎ方式: **明示的にURLを引き継ぐ**方式（ブラウザの`戻る`操作 = History APIの`back`には委ねない）を採用する。
3. ページネーションのURL表現: **`page`（1始まり）**を採用する。
4. QA一覧のタグ複数選択（`tag_id`）のURLエンコード方式: **繰り返しパラメータ**（`tag_id=3&tag_id=7`）を採用する。

## 決定

**一覧ページの検索条件・ページ位置を`useSearchParams`（`react-router-dom`）でURLクエリパラメータへ同期し（履歴はreplace）、編集・新規作成ページへの遷移リンクには遷移元一覧の現在のURLを`back`クエリパラメータとして明示的に付与する。編集・新規作成ページは、この`back`パラメータ（ホワイトリスト検証済みの場合）を「一覧へ戻る」リンクおよび保存/削除成功後の遷移先として使用する。**

1. **一覧ページ側のURL同期（`useSearchParams`、単一箇所への集約）**: `QaListPage` / `QuestionAlteredListPage`は、マウント時に`useSearchParams()`でURLから初期state（`keyword` / `category` / `tagIds` / `qaId`、および`page`から導出した`offset`）を復元してから`load(初期offset)`を呼ぶ。既存の`load(nextOffset)`関数（初期表示・「検索」ボタン押下・ページ送り・削除後の再読込・CSVインポート後の再読込のすべてが通る唯一の箇所）の末尾に、現在の検索条件と`nextOffset`から導出した`page`を用いた`setSearchParams({ ...条件, page }, { replace: true })`の呼び出しを追加する。URL同期のロジックをこの1箇所に集約することで、検索条件・ページ位置とURLの不整合が生じる経路を作らない。既定値（空文字列・空配列・`page=1`）に該当するパラメータはURLから省略する。
2. **`page`（1始まり）と内部`offset`（0始まり、`PAGE_SIZE=20`固定）の相互変換**: URL上は`page`のみを露出し、`offset = (page - 1) * PAGE_SIZE`への変換をフロントエンド内で完結させる。既存API（`GET /api/qa`, `GET /api/question_altered`）の`limit` / `offset`パラメータ仕様は変更しない。
3. **タグ複数選択は繰り返しパラメータ**: `tag_id`は`URLSearchParams`の`append` / `getAll`をそのまま利用し、カンマ区切り等の独自エンコード・パース処理を追加しない。既存の`api.ts`の`listQa`が`tag_id`配列を同じ繰り返しパラメータ形式でAPIへ送信していることとも自然に整合する。
4. **履歴操作はすべてreplace**: 一覧ページ内でのURL更新（検索条件変更・ページ送り・削除後再読込・CSVインポート後再読込）は`{ replace: true }`を指定し、新しい履歴エントリを積まない。一覧ページへの遷移そのもの、および一覧⇔編集ページ間の`Link` / `navigate`（通常のページ遷移）は、`react-router-dom`の標準動作（push相当）のまま変更しない。
5. **`back`クエリパラメータによる戻り先の明示的な引き継ぎ**: 一覧ページの「編集」「＋ 新規」リンクに、`back=${encodeURIComponent(location.pathname + location.search)}`を付与する（例: `/admin/qa/{id}?back=%2Fadmin%2Fqa%3Fcategory%3D...%26page%3D2`）。編集・新規作成ページ（`QaFormPage` / `QuestionAlteredFormPage`）は、自身の`useSearchParams()`から`back`を読み取り、「一覧へ戻る」リンクの遷移先、および保存成功後・削除成功後の`navigate()`遷移先として使用する。
6. **`back`値のホワイトリスト検証（オープンリダイレクト対策）**: `back`は利用者が自由に書き換え可能なURL値であるため、`QaFormPage`側は`/admin/qa`で始まる相対パスのみ、`QuestionAlteredFormPage`側は`/admin/question_altered`で始まる相対パスのみを有効な戻り先として受理する。それ以外（未指定、他ホストを指す値、想定外のパス）は無視し、既存の固定パス（`/admin/qa`, `/admin/question_altered`）にフォールバックする。これにより、`back`パラメータ追加前の既存URL（`/admin/qa/{id}`のみ等）との後方互換性も自動的に確保される。

## 検討した代替案

- **ブラウザの`戻る`操作（`navigate(-1)`相当）に委ねる方式**: 追加のURL構築ロジックが不要でシンプルだが、一覧ページを経由せず編集ページURLを直接開いた場合（ブックマーク、新規タブでのURL入力）や、一覧ページで複数回検索条件を変更したあとに戻ると想定と異なる履歴エントリに着地する可能性がある。発注者からも「明示的にURLを引き継ぐ」方式が指定されたため不採用とした。
- **`react-router-dom`の`location.state`でURLを渡す方式**: `<Link state={{ back: ... }}>`のようにHistory APIのstateへ格納する方式。追加のクエリパラメータが不要でURLが短く保てる利点があるが、`state`はブラウザの操作履歴エントリに紐づく値であり、一覧ページを経由しない直接URL入力・新規タブでの編集ページオープンでは`state`が存在せず、要件定義書が求める「編集後に検索条件・ページ位置を保持したまま戻れる」ことをあらゆる遷移経路で安定して満たせない。決定5に示したクエリパラメータ方式（`back`）は、編集ページのURL自体に戻り先情報を含むため、直接URL入力・リロード・別タブでの共有のいずれでも同じ戻り先が再現され、より頑健である。
- **検索条件をURLではなくReact Context等のグローバルなクライアント側状態で保持する方式**: URLに表れないためブックマーク・URL共有ができず、要件定義書の「URLのクエリから注入できるようにする」を満たさないため不採用とした。
- **履歴をpushする方式（検索条件変更のたびに新しい履歴エントリを積む）**: ブラウザの「戻る」で検索条件の変更を1操作ずつ辿れる利点があるが、一覧に入る前のページへ戻るために何度も「戻る」を押す必要が生じ、利用者体験として煩雑になる。発注者確認によりreplace方式を採用した（決定4）。
- **ページネーションのURL表現を内部実装と同じ`offset`（0始まり）にする方式**: 変換ロジックが不要になる利点があるが、URLとして直感的でなく（例: `?offset=40`は何ページ目か即座に分からない）、将来`PAGE_SIZE`を変更した場合に既存URLの指す内容が意図せずずれる懸念もある。発注者確認により`page`（1始まり）を採用した（決定2）。

## 結果・影響

- 変更対象は`front_dev`の`QaListPage.tsx` / `QuestionAlteredListPage.tsx` / `QaFormPage.tsx` / `QuestionAlteredFormPage.tsx`のみ。`knowledge_mcp` / `web_backend` / DBスキーマへの変更は一切ない。既存の`GET /api/qa` / `GET /api/question_altered`のリクエスト・レスポンス仕様も変更しない。
- `routes.tsx`のルート定義（パスパターン）は変更不要（クエリパラメータの追加はReact Routerのルートマッチングに影響しない）。新規の依存パッケージ追加も不要（`react-router-dom`はADR-0015で導入済み）。
- `QuestionAlteredListPage.tsx`は、`qa_id`がURLに含まれる場合、既存の`getQa`（`api.ts`、現在`QaFormPage.tsx`が利用）をマウント時に追加で1回呼び出すようになる。
- QAレコード削除機能（ADR-0067）との相互作用として、言い換え質問文一覧の`qa_id`フィルタが削除済みQAを指すURLで開かれるケース（ブックマーク・共有URL経由）が新たに起こりうる。本ADRは`getQa`失敗時のラベルフォールバック表示で対応し、一覧自体は（実データを反映した）0件表示として正しく機能させる。
- 一覧ページ内での検索条件変更・ページ送りはブラウザ履歴を積まなくなる（replace）。一覧⇔編集ページ間の遷移は従来通り履歴に積まれるため、ブラウザの「戻る」ボタンの基本的な使用感（1つ前のページへ戻る）は変わらない。
- `back`パラメータは利用者が書き換え可能なURL値であるため、ホワイトリスト検証（決定6）を経ない実装をした場合オープンリダイレクトの懸念が生じる点に留意し、実装時は必ずこの検証を含める。
- 将来、他の一覧ページ（タグ階層ページ、検証機能一覧ページ等）に同様のURL永続化を適用する場合、本ADRのパラメータ命名規則（`page`基準、既存API名との一致、`back`パラメータ）をそのまま踏襲できる。
