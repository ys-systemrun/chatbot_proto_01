# ADR-0060: 検証機能への既存タグ入力パラメータ追加と新規タグのみの記録方針

- ステータス: Accepted
- 日付: 2026-08-26
- 関連: `docs/requirement/202608261510_検証機能既存タグ入力・新規タグ記録機能要件定義書.md`, ADR-0048, ADR-0049, ADR-0050, ADR-0051, ADR-0057, ADR-0058, ADR-0059

## コンテキスト

既存の検証機能（202608260909、ADR-0048〜0050、実装済み）は、検証質問（質問文のみ）を入力に`select_tags`を実行し、返された選択タグをそのまま`verification_run_tag`へ保存していた。

発注者から、「ブラウザ側から渡されたタグ群（既存タグ）をパラメータとして設定可能にし、実行結果として保存するのは`select_tags`で取得された新規のタグ（既存タグは保存する必要がない）としたい」との要望が示された。これを実現するには、次の3点を決定する必要があった。

1. 「既存タグ」をどこで・どう設定するか（検証実行のたびに都度指定するか、検証質問マスタに恒常的に持たせるか）。
2. `select_tags`の結果から「新規タグ」（既存タグに含まれないもの）をどう特定し、何を保存するか。
3. `search_knowledge`へ既存タグ・新規タグをどう渡すか（`tags`引数はAND完全一致であり、タグ数が増えるほど0件化しやすいという既知の制約、ADR-0057）。

発注者への確認の結果、（1）既存タグは検証質問マスタに恒常フィールドとして保持する、（3）`search_knowledge`へのタグの渡し方は`docs/requirement/202608261450_タグ階層展開・タグ構成類似度スコアリング機能要件定義書.md`（ADR-0058・ADR-0059）による`knowledge_mcp`側の方式変更を前提に単一の`tags`引数にまとめる、既存タグの入力値自体は実行結果に再現性のためのスナップショットとして保存する、との回答を得た。

## 決定

**`verification_question`に恒常フィールド`existing_tags`（タグ名の配列、JSON文字列で保持）を追加する。検証実行時、`select_tags`が返したタグのうち`existing_tags`に含まれない（`name`が一致しない）ものを「新規タグ」として特定し、`verification_run_tag`には新規タグのみを保存する。既存タグ自体は、その実行で使用した値を`verification_run.existing_tags_snapshot`としてスナップショット保存する（個々のタグとして`verification_run_tag`には書かない）。`search_knowledge`は、既存タグと新規タグを1つの`tags`引数にまとめて1回だけ呼び出す。**

- **`select_tags`の呼び出しは変更しない**: `select_tags`は`query`のみを引数に取るインターフェース（ADR-0049）のままとし、既存タグを`select_tags`側の入力として渡すことはしない。既存タグとの比較（差分計算）は`web_backend`（`verification_controller`）側で行う、アプリケーション層の集合演算とする。
- **既存タグの保持場所を質問マスタとする**: 検証実行APIのリクエストボディに毎回タグを含める設計（都度パラメータ方式）ではなく、`verification_question.existing_tags`に持たせる。これにより、同じ既存タグ設定で何度も再実行する（`select_tags`の結果が実行のたびに変わりうるかを確認する等の）運用に対して、担当者が毎回タグを入力し直す必要がない。
- **`verification_run_tag`には新規タグのみを保存する**: 既存タグは担当者が既に把握している情報であり、実行結果として重複して記録する意味が薄いという発注者の判断（コンテキスト参照）に従う。
- **既存タグ入力値はスナップショットとして保存する**: `verification_question.existing_tags`は後から編集されうるため、「その実行が実際にどの既存タグを前提に行われたか」を追跡できるよう、`verification_run.existing_tags_snapshot`に実行時点の値をコピーする。これは既存の`question_text_snapshot`（ADR-0050）と同じ設計思想である。
- **`search_knowledge`への渡し方**: 既存タグと新規タグを重複除去した上で1つの配列にまとめ、`tags`引数として1回だけ`search_knowledge`を呼び出す。ADR-0057が`agent_invitro`で採用した「タグ別複数回呼び出し＋結果統合」は採用しない。これは、ADR-0058・ADR-0059により`search_knowledge`の`tags`引数がAND完全一致のハードフィルタからJaccard類似度ベースのソフトなランキングシグナルへ変わり、タグ数増加による0件化のリスクが実質的に解消されるためである。

## 検討した代替案

- **既存タグを検証実行APIの都度パラメータとする（質問マスタに持たせない）**: 「その場でタグを変えて何度も試したい」という探索的な使い方には柔軟に対応できる。しかし、発注者の回答は「質問マスタに恒常フィールドとして保持する」であり、また同じ既存タグ設定を使い回す運用（再実行のたびに同じタグを入力し直す手間を省く）を優先し、不採用とした。将来、都度パラメータでの上書き実行が必要になった場合、APIのオプション引数として既存タグを追加で受け付け、指定時のみマスタ値を上書きする拡張は可能である（本ADRの範囲では設計しない）。
- **既存タグも`verification_run_tag`に保存する（新規タグと区別するフラグ列を追加する）**: 実行結果を1つのテーブルで完結して確認でき、SQL上の扱いも単純になる利点がある。しかし、発注者が明示的に「既存タグは保存する必要がない」と回答しており、この方針に従わない理由がない。また、既存タグは`verification_run.existing_tags_snapshot`で別途保存されるため、情報が失われるわけではない（1テーブルにまとめるか、質問の性質が異なる2つの列に分けるかという表現上の違いにとどまる）。
- **`search_knowledge`をADR-0057と同じ「タグ別複数回呼び出し＋統合」方式で呼び出す**: `docs/requirement/202608261450_...`（ADR-0058・0059）のリリースを待たずに本機能を先行実装できる利点がある。しかし、（1）両機能は同日に並行して要件整理されており、実装順序の調整で対応可能と見込まれること、（2）1回呼び出し方式の方がコード・レイテンシの両面で単純であること、（3）202608261450が採用されれば早晩不要になるワークアラウンドを新たに追加するのは二重投資になること、から不採用とした。ただし、リリース順序に関する依存関係は要件定義書12章Open Issue #2として明記し、実装フェーズで確認する。

## 結果・影響

- `conversation`データベースに、`verification_question.existing_tags`・`verification_run.existing_tags_snapshot`の2列が追加される（`db_hiroba_qa_init/migrations_conversation/0003_add_verification_existing_tags.sql`、ADR-0051の方式に従う新規マイグレーションファイル）。既存の4テーブルの他の列・既存データには影響しない。
- `web_backend/src/main/controllers/verification_controller.py`の検証実行オーケストレーションロジックに、既存タグとの差分計算（新規タグの特定）が追加される。`web_backend/src/mcp_client/tag_selector_mcp_client.py`（`TagSelectorMcpClient`）自体には変更を加えない。
- `front_dev/src/feature/verification/`（`VerificationFormPage`・`VerificationListPage`・`VerificationDetailPage`）に、既存タグの入力・表示が追加される。既存のタグ管理API（`GET /api/tags`）を、既存タグ選択時のタグ一覧取得に再利用する。
- 本ADRは`docs/requirement/202608261450_タグ階層展開・タグ構成類似度スコアリング機能要件定義書.md`（ADR-0058・ADR-0059）の実装完了を前提とする。実装順序が入れ替わる場合、`search_knowledge`の呼び出し方式（単一呼び出しかADR-0057方式の複数回呼び出しか）を暫定的に切り替える必要が生じる可能性がある（要件定義書12章 Open Issue #2）。
- 既存タグを設定しない検証質問（`existing_tags`が`NULL`）は、`select_tags`の結果全件が新規タグとして扱われ、既存（202608260909）と完全に同じ動作になる。既存の検証データ・運用フローへの後方互換性が保たれる。
