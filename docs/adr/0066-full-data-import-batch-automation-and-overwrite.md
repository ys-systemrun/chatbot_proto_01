# ADR-0066: 全データインポート機能のバッチ自動化と全消去上書き方式への変更

- ステータス: Accepted
- 日付: 2026-08-31
- 関連: ADR-0055（本ADRが一部を上書き）, ADR-0046, ADR-0047, ADR-0040, ADR-0052, ADR-0018, `docs/requirement/202608261002_DBマイグレーション・データインポート機能要件定義書.md`（2.4節で追加確認した内容を反映）

## コンテキスト

ADR-0055は、全データインポートの実行手段として「ブラウザUIとしては実装せず、運用者が実行する専用の手段」を採用し、AWS環境については「ECS Execによる一時タスクを起動し、タスク内で運用者が`aws s3 cp`・`psql -f`を手動実行する」という、対話的なECS Execセッションを前提とした手順を定めた。また要件定義書202608261002 2.3節#5・#6では、「投入先データベースは常に空の状態であることを前提とする」「実行方式はブラウザUIではなくCLI／一時タスク実行とする」ことが発注者確認済みの前提として定められていた。

その後の運用検討で、次の2点についてADR-0055・2.3節#5の前提を見直す必要が生じ、発注者に追加確認した（要件定義書2.4節に反映）。

1. **対話的なECS Execセッションではなく、1回のコマンド実行（バッチファイル実行）のみで完結させたい。** ただしECS Exec手順そのものは、バッチ処理が失敗した場合の障害切り分け・手動リカバリ手段として残したい（併存）。
2. **投入先データベースが常に空であるという前提を撤回し、既存データがある環境に対しても、既存データを全消去した上でインポートデータによる上書きを行いたい。**

1.は、ADR-0055が「検討した代替案」の中で将来の発展先として言及していた「`db_hiroba_qa_init`を拡張し、環境変数で『インポートモード』を切り替えて実行する」方式の採用を意味する。この方式は、`terraform/deploy`の`cmd_seed`（ECS一時タスクをrun-task起動→`STOPPED`までポーリング→`exitCode`確認、という完全自動パターン）と同型であり、既存コードに前例がある。

2.は、「常に空のDBへの投入のみを想定する」という要件定義書2.3節#5の前提を覆す、より広い運用（同一環境への再投入・ロールバック的な使い方を含む）を許容する変更である。

## 決定

**全データインポート機能に、`db_hiroba_qa_init`拡張によるバッチ自動実行方式を追加する。ECS Exec手順（ADR-0055）は障害時の手動対応手段として残し、両方式を併存させる。バッチ方式は、投入先の既存データを全消去した上でインポートデータによる上書きを行う。**

1. **実行方式**: `db_hiroba_qa_init`イメージに、環境変数（例: `IMPORT_MODE=true`、名称は実装フェーズで確定）による分岐を追加する。ONの場合、通常のマイグレーション・シード処理の代わりに、S3から取得したSQLダンプの投入処理を実行し、終了コードで結果を返す。`terraform/deploy`に、`cmd_seed`と同型の新規サブコマンド（例: `import-data`）を追加し、対象DBのECS一時タスクをrun-task起動→`STOPPED`まで待機→`exitCode`確認、という完全自動（バッチ）パターンで実行する。対応する`.bat`（例: `terraform/import-data.bat`）を新設し、ADR-0040のUX（`.bat`ダブルクリック→コンテナ内Pythonオーケストレータ）を踏襲する。
2. **ECS Exec手順の併存**: ADR-0055が定めたECS Exec手順は撤回せず、バッチ処理が異常終了した場合の障害切り分け・手動リカバリ手段としてREADMEに残す。通常運用はバッチ方式を第一手段とする。
3. **対象範囲の選択**: 新規サブコマンドに対象選択パラメータ（`chatbot` / `conversation` / `both`）を設け、1回の実行で両データベースを処理する場合と、いずれか一方のみを処理する場合とを使い分けられるようにする。
4. **全消去した上での上書き**: 実行対象（3.の選択に従う）について、全データエクスポート機能が対象とする全テーブル（要件定義書7.2節記載の、`chatbot`データベース6テーブル・`conversation`データベース6テーブル）を`TRUNCATE ... RESTART IDENTITY CASCADE`でデータのみ消去した後、S3から取得したSQLダンプの`INSERT`文を適用する。ダンプの`CREATE TABLE IF NOT EXISTS`は既存スキーマに対して素通りするため、テーブル定義自体は変更しない。**本方式は、エクスポート元と投入先が同一のマイグレーション適用状態（スキーマバージョン）であることを前提とする。** スキーマに差異がある場合の扱いは本ADRの対象外とし、必要になった時点で別途要件化する。
5. **事前自動バックアップ**: 全消去の直前に、既存の全データエクスポート機能（ADR-0046/0047）を同一バッチ内から自動的に呼び出し、消去対象データの退避SQLを生成してS3の専用プレフィックス（例: `rollback/<実行対象>/<実行時刻>/`）へ保存する。誤操作・想定外のインポートによるデータ喪失に対する復旧手段として位置づける。
6. **破壊的操作の実行確認**: 全消去→上書きという不可逆的な操作であるため、実行前に対象環境名（例: 環境識別子や接続先クラスタ名）のタイプ確認を必須とする。既存の`cmd_destroy_app`等が用いる`prompts.confirm_typed`と同様のパターンを踏襲する。
7. **S3アップロードの内包**: ローカルで生成済みのSQLダンプ（`chatbot.sql`・`conversation.sql`）をS3へアップロードする操作も、同一バッチコマンド内に含める。ADR-0055が前提としていた「運用者が事前に`aws s3 cp`で手動アップロードする」手順は、バッチ方式では不要になる。
8. **対象サービスの停止・再開の内包**: バッチ実行時、実行対象（3.の選択）に応じて、`chatbot`/`conversation`データベースに接続する全アプリケーションサービス（`web_backend`・`knowledge_mcp`・`tag_selector_mcp`）を停止（ECSサービスの`desired_count`を0に変更し、タスク停止を待機）してからインポート処理を実行し、完了後に停止前の`desired_count`へ戻して安定化（`services_stable`ウェイター）を待つ、という一連の処理を同一バッチに含める。運用者による個別のサービス停止・再開手順は不要になる。

## 検討した代替案

- **全消去をテーブルごとDROPし、マイグレーションから再構築（`yoyo migrate`）した上でINSERTする方式**: エクスポート元と投入先でマイグレーション適用状態が異なる場合の差異も吸収できる利点があるが、処理時間・実装複雑性が増す。本ADRが前提とする「エクスポート元と投入先が同一の環境間コピー」という主要ユースケースでは、テーブル定義自体を作り直す必要性が薄いため、まずTRUNCATE方式を採用し、スキーマ差異への対応が必要になった時点で見直すこととした。
- **事前自動バックアップを組み込まない（運用者の手動エクスポートに委ねる）**: バッチ処理の実装がシンプルになるが、全消去という不可逆的操作の直前に安全策なしで進めることになり、誤操作時の被害が大きい。既存の全データエクスポート機能をそのまま呼び出すだけで実現できるコストの低さも踏まえ、自動バックアップを組み込むこととした。
- **確認方式を単純なy/n確認（`confirm_or_exit`）とする**: 既存の`apply-all`等と同様の軽量な確認だが、破壊的操作に対する誤操作防止効果は、対象環境名のタイプ確認（`confirm_typed`）に劣る。全消去という影響範囲の大きさを踏まえ、より強い確認方式を採用した。
- **停止対象サービスを`web_backend`のみとする**: 要求時の表現（「web_backend等」）を字義通りに解釈する案だが、`knowledge_mcp`・`tag_selector_mcp`も`chatbot`データベースへ直接接続するため、データ全消去中にこれらのサービスが稼働していると、接続エラーや不整合なクエリ結果が生じうる。データベースに直接接続する全サービスを停止対象とすることとした。
- **バッチ方式に一本化し、ECS Exec手順を廃止する**: 運用手順がシンプルになるが、バッチ処理自体が想定外の状態（S3上のファイル不備、権限不足等）で失敗した場合に、手動で状況を確認・復旧する手段が失われる。バッチ処理を主、ECS Execを障害時の副手段とする併存構成を採用した。

## 結果・影響

- 要件定義書202608261002の以下の箇所が本ADRの内容に合わせた改訂を要する（2.4節に追加確認内容を反映済み）。2.3節#5・#6（本ADRにより前提を撤回・置換）、4.1(e)・4.2（全データインポートのスコープ記述）、6.5節（機能要件、バッチ自動実行方式の追記）、7.2節（インポート対象データ、TRUNCATE後の再投入である旨）、8章（非機能要件、可用性・部分失敗時の扱い）、11章（受け入れ基準、「常に空のDBへの投入」を前提とした基準の置換）、14章（ADR一覧、本ADRの追加）。
- IAM: `db-init-task`のtask roleに、SQLダンプ取得用の`s3:GetObject`に加え、バックアップアップロード用の`s3:PutObject`が新たに必要になる。またサービス停止・再開のための`ecs:UpdateService`・`ecs:DescribeServices`が、`terraform/deploy`実行主体（運用者のAWS認証情報）に必要になる。
- `db_hiroba_qa_init`の責務が、ADR-0016が定めた「マイグレーション・シード専用のワンショットコンテナ」から、「初期化（冪等シード）」と「全消去インポート（破壊的上書き）」の二役に拡張される。両者は排他的な起動モードとして分離されるが、同一イメージ・同一サービスに破壊的操作のロジックを持ち込むことの是非（誤ってインポートモードで通常起動してしまうリスクの排除方法を含む）は、実装フェーズで安全設計（例: 環境変数の誤設定を検知して起動時に警告・追加確認を挟む等）を詰める必要がある。
- ADR-0018が定めた「シードは冪等・データを破壊しない」という既存方針とは明確に異なる性質の処理（全消去）を同じコンポーネントに追加することになるため、README・運用手順書では、通常のシード起動（冪等・安全）とインポートモード（破壊的・要確認）の違いを明確に区別して記載する必要がある。
- TRUNCATEの実行権限は、ADR-0052で新設するマイグレーターロール（DDL実行権限を持つロール）を用いる想定とする。アプリケーションロール（DML専用）にはTRUNCATE権限を付与しない。
- 全消去バックアップの保存先（S3プレフィックス）・保持期間・世代管理ルールは、実装フェーズで運用ルールとして別途定める必要がある。
