# ADR-0050: 検証対象質問の管理方式と実行履行の保持方針

- ステータス: Accepted
- 日付: 2026-08-26
- 関連: `docs/requirement/202608260909_質問タグ情報源検索精度検証機能要件定義書.md`, ADR-0048, ADR-0049

## コンテキスト

検証機能の要件として、「質問、質問から取得したタグ（最終実行の際の結果）、質問・タグから取得した情報源（最終実行の際の結果）を一覧で見られるようにしたい」「検証結果についてはDBに保存したい」という要望があった。これを実現するにあたり、次の3点を設計する必要がある。

1. 検証対象の質問をどう管理するか（都度入力の単発実行か、登録制の再実行可能な質問セットか）。発注者への確認の結果、「登録済みの質問セットを再実行可能に管理する」との回答を得た（要件定義書2章 回答1）。
2. 実行結果（タグ・情報源）の正誤判定の要否。発注者への確認の結果、「人が目視で評価を入力する」との回答を得た（要件定義書2章 回答2）。
3. 「一覧には最終実行結果を表示する」という要望と、「結果をDBに保存したい」という要望をどう両立するか。前者は最新1件のみの表示を求めているように読めるが、後者は実行のたびに結果を残すことを示唆しており、両立するには「質問（マスタ）」と「実行（履行）」を分離するデータモデルが必要になる。

これらを踏まえ、質問マスタと実行履行の関係、削除時の扱い、評価をどの単位（質問単位か実行単位か）で記録するかを決定する必要がある。

## 決定

**検証対象の質問は`verification_question`（マスタ、再実行可能）として管理し、実行するたびに`verification_run`（履行、`question_id`に対してN行）を新規追加する。一覧画面は各質問について`executed_at`が最新の`verification_run`のみを表示し、詳細画面で全履行を参照できるようにする。評価（適切／不適切＋コメント）は`verification_run`単位（実行単位）に記録する。**

- **質問マスタと実行履行の分離**: `verification_question`（`id`/`question_text`/`memo`/`created_at`/`updated_at`）と`verification_run`（`id`/`question_id`/`question_text_snapshot`/`executed_at`/`status`/選択タグ・情報源への参照/評価列）を分離する（要件定義書7.2節）。`verification_run`は`question_text_snapshot`として実行時点の質問文を保持する。これは、質問マスタを編集（`question_text`を更新）した後も、過去の実行結果が「実行当時どの質問文に対する結果だったか」を正しく表示できるようにするためである（既存の`ConversationDB`が`message.content`を不変に保つ方針と同じ考え方）。
- **一覧表示は最新実行のみ**: 一覧APIは、各`verification_question`について`executed_at DESC`で1件のみを取得するクエリ（例: `DISTINCT ON (question_id)`または相関サブクエリ）で最新の`verification_run`を結合する。これにより「一覧には最終実行の際の結果を表示する」という要望に応える。
- **履行はすべて保持**: 実行するたびに新規`verification_run`行を追加し、既存行を上書きしない（成功・失敗にかかわらず）。これにより「検証結果をDBに保存したい」という要望（履行の蓄積）に応える。詳細画面（要件定義書6.1.3節）で全履行を参照できる。
- **評価は実行単位**: `evaluation`/`evaluation_comment`/`evaluated_at`は`verification_run`に持たせる（質問単位（`verification_question`）には持たせない）。再実行すると新しい`verification_run`が作られ、その評価は未設定の状態から始まる。過去の実行に対する評価は、その実行行に残ったまま変更されない。
- **削除時の扱い**: `verification_question`を削除すると、`ON DELETE CASCADE`により関連する`verification_run`（およびその`verification_run_tag`/`verification_run_source`）もすべて削除される。履行を保持したまま質問だけを一覧から外したい場合の論理削除は、本フェーズでは実装しない（要件定義書12章Open Issue #2として引き継ぐ）。

## 検討した代替案

- **質問ごとに1行upsert（最新結果のみ保持、履行を残さない）**: 「一覧には最終実行の際の結果を表示する」という要望の文言には最も単純に合致し、既存の`ConversationDB.upsert`（`message`テーブルへの`ON CONFLICT ... DO UPDATE`）と似た実装で済む利点がある。しかし、「検証結果についてはDBに保存したい」という要望、および発注者への確認で「登録済みの質問セットを再実行可能に管理する」という回答（1回だけでなく繰り返し実行し、その都度の結果を比較・追跡したいという意図が読み取れる）を踏まえると、過去の実行結果を上書きで消してしまう設計は要望を弱く解釈しすぎであると判断し、不採用とした。将来、履行テーブルの行数が運用上問題になった場合は、古い履行を別途アーカイブ・削除する仕組み（要件定義書12章Open Issue #5と関連）を検討する。
- **評価を質問単位（`verification_question`）に記録する**: 質問ごとに1つの評価状態を持たせる方式で、UI上の状態管理はやや単純になる。しかし、再実行によってタグ・情報源の内容が変わった場合、古い評価が新しい実行結果に対してそのまま残り続け、「この評価はどの実行結果に対するものか」が曖昧になる（評価内容と実行結果の対応が取れなくなるリスク）。実行単位に評価を持たせる方式は、既存の会話評価（`message.evaluation`、メッセージという不変の単位に対して評価を持たせる設計）と考え方が一致するため、こちらを採用した。
- **論理削除（`is_active`列等）をMVPから採用する**: 履行を保持したまま質問を一覧から外せる利点があるが、削除・復元・一覧フィルタ（有効/無効）等のUI・API仕様が増え、MVPの範囲としては過剰と判断した。CASCADE削除（シンプルだが履行も消える）を採用し、運用開始後に論理削除への変更が必要と判明した場合に再検討する方針とした（要件定義書12章Open Issue #2）。

## 結果・影響

- `conversation`データベースに4テーブル（`verification_question`/`verification_run`/`verification_run_tag`/`verification_run_source`）が追加される（ADR-0048、DDLは要件定義書7.2節）。
- 一覧APIの実装には、質問ごとの最新実行を1回のクエリで取得するSQL（`DISTINCT ON`等）が必要になる。件数が多い場合の性能は実装フェーズで確認する（要件定義書8章）。
- 詳細画面（`VerificationDetailPage`）は、1質問に対して複数件の実行履行・評価をリスト表示する必要があり、一覧画面（最新1件のみ）よりも表示ロジックが複雑になる。
- 「検証対象の質問を都度その場で入力して単発実行したい」という将来的なニーズ（要件定義書4.1節で採用しなかった案）が生じた場合、`verification_question`を作らずに`verification_run`だけを作る経路を別途追加することで対応できる余地はあるが、本ADRの範囲では設計しない。
