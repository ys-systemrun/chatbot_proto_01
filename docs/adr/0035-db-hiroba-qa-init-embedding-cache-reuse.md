# ADR-0035: db_hiroba_qa_initにembeddingキャッシュ再利用オプションを追加する（destroy→再apply時のBedrock再計算回避）

- ステータス: Accepted
- 日付: 2026-08-12
- 関連: `docs/requirement/202608100910_MCPサーバークライアントAWSデプロイ要件定義書.md`（8章コスト、14章 Open Issue #7）, ADR-0016, ADR-0017, ADR-0018, ADR-0030, ADR-0031, ADR-0034

## コンテキスト

`db_hiroba_qa_init`は、テーブル単位の存在チェックによる冪等なシード処理を持ち（ADR-0018）、既にデータが投入済みのテーブルへの再投入をスキップする。この冪等性は、同一のRDSインスタンスに対して`deploy.bat`（`deploy.ps1`）を複数回実行するケース（例: イメージ更新のみの再デプロイ）では有効に機能する。

一方、`envs/verify`は検証用途の最小構成であり（要件定義書8章コスト、14章 Open Issue #7）、`database`モジュール（ADR-0026）は`skip_final_snapshot = true`・`deletion_protection = false`で構成されている。運用上、コスト管理のために使用しない期間は`destroy.bat`で環境全体（VPC/RDS/ECS等）を破棄し、必要なときに`deploy.bat`で作り直す運用が想定されている（`destroy.ps1`の確認メッセージにも「RDSのデータも失われます」と明記されている）。この運用サイクルでは、RDSが毎回新規作成され`question_altered`テーブルが空の状態から始まるため、ADR-0018の存在チェックは実質的に機能せず、`deploy.ps1`のPhase 4（db_init run-task）が毎回、約1,150件相当の`question_altered`全件に対してBedrock（`BEDROCK_EMBEDDING_MODEL_ID`, ADR-0031）への埋め込みAPI呼び出しを行う。これは、環境の作り直しのたびに発生する時間（Bedrock呼び出しのレイテンシ×件数）とAPIコストの両面で無視できないオーバーヘッドであり、検証環境をこまめに作り直して使う運用（コスト管理、Open Issue #7）を阻害する要因になっている。

ADR-0034では、シード元データ（`category.csv`/`exportjson_withguid.json`/`question_altered.csv`）をイメージに同梱する方式を決定した際、`question_altered`についてはテキストのSQL化ではなく「投入時に埋め込みAPIを呼び出す現行方式を維持する」ことを明記していた。当時の検討は「テキストからベクトルへの変換処理をどこで行うか」が論点であり、「一度計算したベクトル自体を保存し、条件が変わらない限り再計算を避ける」という観点は対象にしていなかった。本ADRは、ADR-0034が現行方式維持と決めた部分について、再計算コストの観点から見直しの余地があるかを検討する。

## 決定

**`db_hiroba_qa_init`に、`question_altered`の埋め込みベクトルを事前計算済みキャッシュファイルから読み込み、Bedrock/LM Studioへの埋め込みAPI呼び出しをスキップする「キャッシュ再利用モード」をオプションとして追加する。**（ユーザー確認済み: 「計算済みembeddingを再利用できるようにする」方向を採用）

- 新規環境変数（例: `EMBEDDING_CACHE_MODE`、既定値は現行方式維持の`off`）により、キャッシュ再利用を明示的に有効化できるようにする。既定で無効のため、既存のローカル開発環境（LM Studio）・AWS環境の動作は変更されない。
- キャッシュファイルは、`qa_id`（または`question_altered`の行キー）とベクトルの組に加え、そのベクトルを計算した際の`EMBEDDING_PROVIDER`・埋め込みモデルID（`BEDROCK_EMBEDDING_MODEL_ID`等）・`EMBEDDING_VECTOR_DIM`をメタデータとして保持する。シード実行時、現在の環境変数（プロバイダ・モデルID・次元）とキャッシュのメタデータが完全一致する場合のみキャッシュを使用し、不一致の場合は現行方式（API呼び出し）に自動的にフォールバックする（ADR-0031が指摘したモデル切り替え時の次元不一致リスクに対し、キャッシュ機構自体が安全側に倒れる設計とする）。
- キャッシュファイルの生成は、シード処理本体とは別の一度限り（またはソースデータ変更時）の運用手順として扱う。具体的には、対象環境（AWS Bedrock、選定モデル固定）に対して1回だけ通常モード（API呼び出し）でシードを実行し、その結果生成された`question_altered`のベクトルをエクスポートしてキャッシュファイル化し、`db_hiroba_qa_init`のビルドコンテキストに同梱する（ADR-0034と同じ「イメージ同梱」の考え方を、シード元テキストだけでなく計算済みベクトルにも拡張する）。
- 既存のADR-0018（テーブル単位の存在チェックによる冪等性）・ADR-0034（シード元データのイメージ同梱）の決定内容自体は変更しない。本ADRが変えるのは「ベクトルをどこから取得するか（API呼び出し or キャッシュ）」のみであり、「いつ投入するか（存在チェック）」「テキストデータをどこから読むか（イメージ同梱）」には影響しない。

## 検討した代替案

- **RDSのデータをdestroy/recreateで消さないようにする（最終スナップショットの保持、または`database`モジュールを他リソースと別ライフサイクルに分離する）**: RDS自体が生き残ればADR-0018の冪等性がそのまま機能し、追加のキャッシュ機構も不要になる利点がある。しかし、（1）検証環境全体をディスポーザブルに保つという既存の設計方針（ADR-0026・ADR-0030、および`destroy.ps1`が前提とする「壊して作り直す」運用）と矛盾する、（2）スナップショットの保存コスト・復元時のエンジンバージョン/パラメータグループ互換性という新たなリスクを抱える、（3）VPC/ECS等、RDS以外のリソースも作り直したい（クリーンな検証をしたい）ケースでは解決にならない、という理由から本ADRでは不採用とした。将来的に「RDSだけは常時起動を許容する」という運用コスト方針に変わった場合の代替案として記録は残す。
- **`deploy.ps1`にPhase 4（run-task）自体をスキップする手動フラグのみ追加する**: 実装コストは最小だが、「RDSにデータが本当に残っているか」の判断を運用者の記憶・目視確認に依存することになり、スキップ判定を誤るとサービスがデータ欠損状態で起動するリスクがある。また、destroy→再apply運用（本ADRが対象とするシナリオ）では、RDSは必ず空になるため、このフラグは前提となるシナリオそのものを解決しない。運用上の応急措置としては将来的に併用を検討できるが、本ADRの主たる解決策としては不採用とした。
- **何もしない（現行方式を維持）**: `question_altered`のシード元テキスト自体（CSV）は変更頻度が低く、埋め込みモデル・プロバイダも本検証（MVP）の間は固定される見込みが高いため、キャッシュ導入コストに対して再計算コストがどこまで問題になるかは運用回数に依存する。ただし、ユーザーへのヒアリングにより「destroy→再apply運用を今後も継続し、そのたびの再計算を避けたい」という明確な要望が確認できたため、本ADRでは対応する方針を決定した。

## 結果・影響

- `db_hiroba_qa_init`側の実装変更が必要になる（キャッシュファイルの読み込み・メタデータ照合・フォールバック処理、環境変数`EMBEDDING_CACHE_MODE`等の追加）。これは本ADR（要件・方針レベルの決定）のスコープ外であり、別途実装指示書（IMPL）で詳細化する。
- キャッシュファイルの生成・更新（初回生成、`question_altered.csv`の内容変更時の再生成、埋め込みモデル変更時の再生成）を行う運用手順を新たに定義する必要がある。この手順自体もコーディングを伴う可能性があり、実装フェーズでの確定事項とする。
- キャッシュファイルの保存場所は、ADR-0034と同様にDockerイメージへの同梱を基本方針とするが、キャッシュファイルのサイズ（1,150件×次元数の浮動小数点数、次元によっては数MB程度）・更新頻度によっては、イメージ同梱以外の配布方式（例: イメージタグ更新のたびに再生成する運用ルールにする等）を実装フェーズで検討する。
- 本オプションはBedrockモデル切り替え時に自動的に無効化（フォールバック）される設計とするため、ADR-0031が指摘した次元不一致のリスクを新たに悪化させることはない。
- 以下は実装フェーズで確定すべき残課題（Open Issue）として明示する。
  1. キャッシュファイルの具体的な形式（CSV/JSON/npy等）とファイル名・配置パス。
  2. `question_altered.csv`側の内容変更をキャッシュの陳腐化として検出する方法（例: ソースファイルのハッシュ値をキャッシュのメタデータに含め、シード時に比較する）。
  3. キャッシュファイルの生成・更新を誰が・どの手順で行うか（手動スクリプト、`deploy.ps1`への専用サブコマンド追加、CI等）。
  4. ローカル開発環境（LM Studio、`db_nomic`/`db_multilingual`）向けにも同様のキャッシュ再利用オプションを提供するか（本ADRはAWS環境のdestroy→再apply運用を主眼としているが、ローカルでも`docker compose down -v`等でボリュームを消した場合には同様の課題が生じる）。
- `docs/adr/README.md`のADR一覧に本ADRを追記する。
