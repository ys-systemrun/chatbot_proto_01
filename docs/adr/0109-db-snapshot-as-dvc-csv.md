# ADR-0109: DB の現状を CSV スナップショットとして DVC で管理し、SQL ダンプの長期保管をやめる

- ステータス: Proposed（方針の決定。実装は「進め方」の段階ごとに行う）
- 日付: 2026-10-30
- 関連: ADR-0046 / ADR-0047（全データエクスポート）, ADR-0066（全データインポート）, ADR-0097（ナレッジデータの DVC 管理）, ADR-0103（退避付き一括破棄・export-data）, ADR-0106（記事の uuid）, ADR-0108（シード元データの CSV 統一）

## コンテキスト

DB の中身を残す手段は、いま SQL ダンプ（`knowledge.sql` / `conversation.sql`）だけである。

- `export-data.bat` / `destroy-all.bat`（ADR-0103）が `terraform/backup/` に書き出し、`import-data.bat`（ADR-0066）が全消去→上書きで戻す。管理画面の全データエクスポート（ADR-0047）も同じ形式を ZIP で返す。
- `terraform/backup/` は git の管理外で、書き出すたびに上書きされる。版の履歴が無く、何が変わったかも追えない。
- SQL は 1 ファイルに全テーブルが入り（`knowledge.sql` は埋め込みを含めて約 67MB）、差分が読めない。

一方、シード元データ（`db_init/data/`, DVC 管理, ADR-0108）は初期投入用の元データで、管理画面での編集（QA の削除、言い換えの追加、タグ・同義語・フォルダ、QA と記事のタグ付け）を含まない。
2026-10-26 時点の AWS の件数と比べると、QA 824（シード 825）、言い換え 5,126（同 5,033）、タグ 80・同義語 120・フォルダ 15・QA タグ付け 1,175・記事タグ付け 21（シード用ファイル無し）とずれている。
DB を作り直してシードすると、これらの編集は失われる。

DB の現状を、DVC で版管理できる CSV として書き出し、そこから DB を戻せるようにしたい。

## 決定

### 1. 正本は DB とし、CSV はその版（スナップショット）とする

- 編集はこれまでどおり管理画面で行う。CSV を直接編集して DB に戻す運用はしない。
- 定期的に（大きな編集の後・リリースの前・環境を破棄する前に）DB を CSV に書き出し、DVC に版として残す。
- 別の環境の構築・復旧は、スナップショットから取り込んで行う。

### 2. 対象と置き場所

| DB | 置き場所（DVC 管理） | 用途 |
|---|---|---|
| knowledge（9 テーブル） | `db_init/data/knowledge/`（`<テーブル名>.csv` と `manifest.json`） | **シード元データを兼ねる**（空の DB への初回投入もここから）。イメージに同梱される |
| conversation（7 テーブル） | `snapshots/conversation/`（同上） | 復旧専用。シードには使わない。イメージに同梱しない |

- テーブルの集合と順序は、既存の `import_data.KNOWLEDGE_TABLES` / `CONVERSATION_TABLES` と同じにする。
- conversation には利用者の質問文が含まれる。DVC リモート（非公開の S3）にのみ置き、git には `.dvc` だけを入れる。保管期間は別に定める。

### 3. 書式は PostgreSQL の `COPY ... CSV` に従い、DB の値をそのまま往復させる

- 書き出しは `COPY (SELECT <列> FROM <テーブル> ORDER BY <主キー>) TO STDOUT WITH (FORMAT csv, HEADER, FORCE_QUOTE *)`、取り込みは `COPY <テーブル> (<列>) FROM STDIN WITH (FORMAT csv, HEADER)` を使う。
  - **NULL は引用符なしの空欄、空文字列は `""`** として区別される（Python の `csv` では区別できないため、変換は PostgreSQL に任せる）。
  - 真偽値・日時・数値の表現も PostgreSQL のもの（`t` / `f`、タイムゾーン付きの日時など）になり、型の変換で値が変わらない。
  - UTF-8・LF。NULL 以外の値はすべて引用符で囲まれる。
- 行は主キーの順に並べる（`dvc diff` / 差分ツールで変更が読めるようにする）。
- **列は DB の全列。ただし埋め込み（`embedding`）は除く**（モデルに依存し、サイズが大きいため。下の 5）。
- この書式は ADR-0108 の書式と、NULL・真偽値の表し方だけが違う。スナップショットのファイルについては本 ADR を優先する。

### 4. DB の ID（通し番号）をそのまま持つ

- 取り込みは「全消去→全行投入」なので、`id SERIAL` の値も CSV のとおりに入れ、最後に各シーケンスを最大値に合わせる（`setval`）。外部キー（`tag_id`・`folder_id` など）も ID のまま往復できる。
- そのため、タグフォルダや言い換え質問に uuid を追加する必要はない。ADR-0108 で例外とした言い換え質問も、`id` を持つ形になる。
- 人が読む助けになる列（タグ名など）は CSV に足さない（DB の列と 1 対 1 にし、往復を単純に保つ）。

### 5. 埋め込みはキャッシュから引き、無いものだけ計算する

- 取り込んだ後、`embedding` が NULL の行を、埋め込みキャッシュから埋める。キャッシュに無い行だけ埋め込み API を呼ぶ。
- キャッシュは「埋め込みモデル ID × 埋め込み元テキストの SHA-256 → ベクトル」で、DVC で別に管理する（`db_init/data/embedding_cache/<モデル ID>/`）。書き出しの際に、DB にあるベクトルでキャッシュを更新する。
- これにより、5,000 件超の言い換え質問を取り込みのたびに計算し直さずに済む（ADR-0035 の考え方）。

### 6. `manifest.json` と取り込み前の照合

- 書き出しのたびに `manifest.json` を作る: 書き出し元（環境名）・日時・スキーマの版（yoyo の適用済み ID）・テーブルごとの件数と CSV の SHA-256・スナップショット全体のハッシュ。
- 取り込みの前に次を照合し、合わなければ中止する（明示の `--force` でのみ続行）。
  - **スキーマの版が投入先と同じ**（ADR-0103 の `import-data` と同じ照合）。
  - **投入先 DB が、最後に取り込んだ・書き出したスナップショットから変わっていない**。投入先を同じ方法で一時的に書き出してハッシュを比べ、記録（下記）と一致することを確かめる。管理画面での未保存の編集を黙って上書きしないため。
- knowledge / conversation の各 DB に、最後に取り込んだ・書き出したスナップショットのハッシュを 1 行記録する（小さな管理テーブルを追加する）。

### 7. 取り込み・書き出しの仕組みは db_init に置き、既存の流れを使う

- db_init に、スナップショットの書き出しモード・取り込みモードを追加する。AWS では、既存の `export-data` / `import-data` と同じく S3 の import バケットを経由して手元と受け渡す。
- 取り込みは既存の `import_data` と同じく、事前の自動退避→1 トランザクションで全消去と投入。失敗したら全体が元に戻る。
- バッチ: `kb-export.bat`（DB → 手元の CSV → `dvc add`）、`kb-import.bat`（手元の CSV → DB）。ローカルの docker compose 環境でも同じモードを使う。
- **シードは「空の DB へのスナップショットの取り込み」に一本化する**。

### 8. SQL ダンプは一時的な退避だけに使う

- 取り込み前の自動退避（S3 の `rollback/`）は SQL のまま残し、S3 のライフサイクルで短期間（例: 30 日）で消す。
- `terraform/backup/` への SQL の書き出しと、`destroy-all` の退避は、スナップショットの書き出しに置き換える。
- 管理画面の全データエクスポート（ADR-0047）の CSV も、スナップショットと同じ書式にそろえる（CSV の形式を 2 種類にしない）。

### 9. 新しい情報源の取り込み（Redmine など）はスナップショットと分ける

- `redmine_error_taiou.csv` のような「新しく追加するデータ」は、これまでどおり追加用の取り込み（未投入の行だけ入れる冪等シード）で DB に入れ、次の書き出しでスナップショットに含める。
- 追加用の元データは、スナップショットとは別の場所（例: `db_init/sources/`）に置く。スナップショットに取り込まれた後は、DB とスナップショットが正本になる。

## 進め方

| 段階 | 内容 | 確認 |
|---|---|---|
| 1 | 書き出しモード（DB → CSV と `manifest.json`）と `kb-export.bat` | 書き出した CSV を空の DB に `COPY` で戻し、全テーブルの全列が元の DB と一致すること（往復テスト） |
| 2 | 取り込みモード（CSV → DB、シーケンスの調整、事前退避、照合）と `kb-import.bat` | 往復テストを自動テストにする |
| 3 | 埋め込みキャッシュ（書き出し時の更新・取り込み後の補完） | 取り込み後に埋め込み API の呼び出しが 0 件になること（変更が無い場合） |
| 4 | 最初のスナップショット: `terraform/backup/knowledge.sql`（2026-10-26 の AWS）をローカル DB に入れて書き出し、`db_init/data/knowledge/` に置く。シードをスナップショットの取り込みに切り替え、現在のシード用 CSV は `db_init/sources/` に移すか廃止する | シードで作った DB が AWS の 10/26 時点と一致すること |
| 5 | conversation のスナップショットと保管期間 | 同上 |
| 6 | SQL の長期保管をやめる: `terraform/backup/` の SQL 書き出し・`destroy-all` の退避を置き換え、`rollback/` に期限を付け、全データエクスポートの CSV をそろえる | `destroy-all` → `apply-all` → `kb-import` で環境が戻ること |

## 影響

- `db_init/data/` は「元データ」から「DB の版」に意味が変わる。KB の版（`KB_DATA_VERSION`）はスナップショットの版になる。
- マイグレーションで列を追加したら、次の書き出しから CSV にも列が増える（列は DB から読む）。古い版のスナップショットは、そのスキーマの版の DB にしか取り込めない（照合で止まる）。古い版を新しいスキーマに取り込む手順（マイグレーションを当ててから書き出し直す）は段階 2 で用意する。
- 管理画面での編集の後に書き出しを忘れると、その編集は版に残らない。リリースや環境の破棄の手順に書き出しを組み込む（段階 6）。
- 取り込みは全消去を伴う。照合（上の 6）と事前退避で、誤操作の影響を抑える。
