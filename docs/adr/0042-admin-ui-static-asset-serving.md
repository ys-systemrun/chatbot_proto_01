# ADR-0042: front_dev本番ビルド資産の配信方式

- ステータス: Accepted
- 日付: 2026-08-21
- 関連: `docs/requirement/202608211014_AWS環境向けQAタグ管理UI要件定義書.md`, ADR-0015, ADR-0041

## コンテキスト

`front_dev`は現状、`vite dev server`（`npm run dev`、Dockerfileの`CMD`）をコンテナ内で常時起動し、開発用のホットリロードとViteのプロキシ機能（`/api`等を`web_backend`へ転送、`vite.config.ts`）に依存する構成になっている。AWS上の`admin_ui`サービス（ADR-0041）では、この開発用サーバーではなく、本番相当のビルド済み静的資産（`npm run build`の出力、`front_dev/package.json`の`build`スクリプト）を配信する必要がある。

配信方式として次の3案を検討した。

1. **`web_backend`（FastAPI）コンテナから静的資産を配信する**: `front_dev`をビルドした`dist/`を`web_backend`のコンテナイメージに含め、FastAPIの静的ファイル配信機能（例: `StaticFiles`）でルート（`/`）配下を配信し、既存の`/api/*`エンドポイントと同一コンテナ・同一ECSサービスで共存させる。
2. **`front_dev`専用の軽量Webサーバー（nginx等）コンテナを別サービスとして新設し、ALBのパスベースルーティングで`/api/*`は`web_backend`、それ以外は`front_dev`サービスへ振り分ける**。
3. **S3の静的ウェブサイトホスティング＋CloudFrontで配信し、`/api/*`のみALB経由で`web_backend`へ転送する**。

## 決定

**案1（`web_backend`コンテナから静的資産を配信する）を採用する。**

- `front_dev`のビルド成果物（`npm run build`の出力）を、`web_backend`のコンテナイメージのビルド手順に含める（マルチステージビルド等、具体的なDockerfileの記述は実装フェーズで確定する）。
- `web_backend`（FastAPI）に、ビルド済み静的資産を配信するルートを追加し、既存の`/api/*`エンドポイント（既存UI要件定義書6.4節、ADR-0013）とは名前空間を分離したまま同一プロセス・同一コンテナで提供する。
- 管理画面のページパス（`/admin`配下、ADR-0015）へのブラウザからの直接アクセス（リロード、URL直接入力）に対応するため、`/api`にマッチしないパスはSPAのエントリーポイント（`index.html`）を返すフォールバックを設ける（既存の`/evaluated_messages`と同様の考え方、既存UI要件定義書9.2節を踏襲）。
- ALB・ECS Fargateサービス（ADR-0041）は、`admin_ui`という単一サービス・単一ターゲットグループで構成する。`front_dev`用の別サービス・別ターゲットグループは新設しない。

## 検討した代替案

- **案2（別コンテナ＋パスベースルーティング）**: `web_backend`と`front_dev`の責務が分離され、将来的なスケールやデプロイ独立性の観点では有利だが、ECS Fargateサービス・ターゲットグループ・タスク定義が2倍になり、本フェーズの利用規模（社内の運用担当者数名程度、既存UI要件定義書8章）に対しては構成の複雑さ・コストが正当化できないため見送った。
- **案3（S3＋CloudFront）**: 静的資産配信としては一般的な構成だが、CloudFrontの追加（ディストリビューション、オリジンアクセス制御）、およびALBの社内IPアドレス限定（ADR-0041）とCloudFront側のアクセス制御をどう整合させるかという追加の検討が必要になり、本フェーズの規模に対しては過大と判断し見送った。

## 結果・影響

- `web_backend`のコンテナイメージビルド手順に、Node.js環境でのビルドステージが追加される（現状の`web_backend/Dockerfile`は`python:3.11`ベースのみ）。マルチステージビルドの具体的な記述は実装フェーズで確定する。
- ローカルの`docker-compose`環境（開発用、`front_dev`は`vite dev server`のまま）には影響しない。本番ビルド配信用のDockerfile・設定は、AWSデプロイ用として別途追加し、既存の開発フローとは分離する。
- 将来、`front_dev`と`web_backend`のデプロイ独立性やスケールの必要性が高まった場合は、本ADRを見直し、案2（別サービス化）を再検討する余地を残す。
- 本ADRは配信方式（どのコンテナ・サービスが静的資産を返すか）のみを対象とし、ネットワーク境界・アクセス制御（社内IPアドレス限定等）はADR-0041の範囲であり、本ADRでは変更しない。
