# ADR-0027: Terraform state管理方式（S3バックエンド採用）

- ステータス: Accepted
- 日付: 2026-08-10
- 関連: `docs/requirement/202608100910_MCPサーバークライアントAWSデプロイ要件定義書.md`, ADR-0024, ADR-0026

## コンテキスト

Terraformで管理するAWSインフラ（VPC、ECS Fargate、RDS等、ADR-0024, 0026）の適用にあたり、Terraform stateの管理方式を決める必要がある（要件定義書 Open Issue #6）。ローカルファイルとしてstateを保持する方式は、複数人での運用や再実行時の一貫性確保に適さない。

検討した選択肢は次の3案。

1. **S3バックエンド**: Terraform stateをAmazon S3バケットに保存する。AWS標準の構成であり、既存のAWSアカウント内で完結する。
2. **HCP Terraform（Terraform Cloud）等のSaaS**: HashiCorpが提供するマネージドのstate管理・実行環境。
3. **ローカルstate（各実行者の端末に保持）**: 追加のAWSリソースを必要としないが、複数人・複数環境での運用には適さない。

## 決定

**S3バックエンドを採用する。**（発注者確認済み）

Terraform stateは、本検証用に用意するAmazon S3バケットに保存する。ロック方式は、利用するTerraformのバージョンに応じて次のいずれかとする（実装フェーズで確定）。

- Terraform 1.10以降を利用する場合: S3バックエンドのネイティブロック機能（`use_lockfile = true`）を用い、追加のDynamoDBテーブルを用意しない。
- それ以外の場合: 従来方式であるDynamoDBロックテーブルを別途用意する。

state用S3バケットは、バージョニングおよびサーバーサイド暗号化（SSE-S3またはSSE-KMS）を有効化する。

## 検討した代替案

- **HCP Terraform等のSaaS**: state管理・実行ログ・チーム管理機能等が充実しているが、外部SaaSへのAWS認証情報連携や利用契約等の検討が新たに必要になり、本検証（MVP）のスコープに対して過大と判断し見送った。
- **ローカルstate**: 追加リソースが不要な点はシンプルだが、複数人での実行や再実行時にstateの不整合が発生するリスクが高く、本番運用を見据えた検証という目的にも適さないため不採用とした。

## 結果・影響

- state用S3バケット（および必要であればDynamoDBロックテーブル）は、Terraformの管理対象そのものには含めず、事前に用意する「ブートストラップ」用のリソースとして扱う（Terraform自身が参照するバックエンドを、同じTerraformで管理する循環を避けるため）。ブートストラップの具体的な手順（手動作成か、最小限の別Terraform構成で作成するか）は実装フェーズで確定する。
- stateバケットへの書き込み権限は、Terraformを実行する主体（開発者のIAMユーザー/ロール、または将来のCI/CD実行ロール）に限定する。
- なお、本ADRはTerraform CLIの実行環境（開発者端末やCI）からAWSのコントロールプレーン（S3・Terraform実行）へのアクセスに関する決定であり、ADR-0023が定めるアプリケーションランタイムのネットワーク境界（AWS内部限定）とは別の関心事である。Terraform実行自体はインターネット経由のAWS API呼び出しを前提とし、ADR-0023の制約対象ではない。
- AWSアカウント・リージョンの選定自体は本ADRの対象外であり、要件定義書のOpen Issueとして引き続き残る。
