# ADR-0065: タグ階層データのCSVエクスポート機能の実装方式（Knowledge MCP新規ツールによるフラット化、既存インポート列構成との統一）

- ステータス: Accepted
- 日付: 2026-08-28
- 関連: `docs/requirement/202608281421_タグデータCSVエクスポート機能要件定義書.md`, ADR-0005, ADR-0006, ADR-0008, ADR-0013, ADR-0046, ADR-0047, ADR-0061, ADR-0064

## コンテキスト

タグ単体の一括インポート機能（ADR-0061）の実装時、要件定義書（202608261600）はOpen Issue #3として「既存のタグ一覧（`list_tags`）をCSV形式でエクスポートする機能が別途必要かどうかは、本書のスコープ外とし、必要になった場合に別途要件化する」としていた。

その後、言い換え質問文（`question_altered`）管理機能（ADR-0064）が、一覧ページに対する「そのまま再インポートできる形式」のCSVエクスポート機能を実装し、（1）CSVの列構成をインポートと完全に一致させることで再インポート可能にする、（2）既存の全データエクスポート（ADR-0046/0047）とは独立した別機能として、Knowledge MCP経由の同一経路（ADR-0013の原則をエクスポートにも適用）で実装する、という設計パターンを確立した。

発注者より、タグ階層ページ（`TagTreePage`）にも、言い換え質問文一覧ページと同様のCSVエクスポート機能を追加したいという要望が示された。既存の全データエクスポート（ADR-0047）は既に`tag.csv`（`id`/`name`/`parent_tag_id`/`description`）を出力しているが、`parent_tag_id`は数値IDであり、タグ一括インポート（`parent_name`による名前解決、ADR-0061）へそのまま再投入できる形式ではない。

タグの一覧取得ツール（`list_tags`）は、ページングや`is_primary`絞り込みへの対応が必要だった言い換え質問文一覧（`list_question_altered`）とは異なり、元々全タグを一度にツリー構造（`TagNode`、`children`を含む）で返す設計になっている（`knowledge_mcp/src/knowledge_mcp/repository/tag_repository.py`）。このため、「既存の読み取りツールをそのまま再利用するか、専用のエクスポートツールを新設するか」という、言い換え質問文の場合とは異なる実装上の論点があった。

## 決定

**Knowledge MCPに新規ツール`export_tags`を追加する。引数なしで全タグ（親子関係を含む全件）を、既存のタグ一括インポート（ADR-0061）と同一の列に対応する形式（`id`/`name`/`parent_name`/`description`）でフラットな配列として返す。`web_backend`はこの配列を`name`/`parent_name`/`description`の3列でCSV化する薄いエンドポイント（`GET /api/tags/export`）を追加する。`front_dev`のタグ階層ページ（`TagTreePage`）に「CSVエクスポート」ボタンを追加する。**

1. **新規ツールとして追加する（`list_tags`を`web_backend`側でフラット化しない）**: `list_tags`は既存の`TagNode`ツリー構造（`children`・`aliases`を含む）を返す設計であり、フラット化（親ノード名の解決）ロジックをここに実装すると、`web_backend`側にツリー走査ロジックが新設されることになる。`web_backend`は既存の各コントローラ（`qa_controller`/`tag_controller`/`question_altered_controller`）を通じて「MCPツール呼び出し＋レスポンス変換のみ」という薄いBFFの役割に一貫して留められており（ADR-0013）、この役割分担を崩さないよう、変換ロジックはKnowledge MCP側（既存ツリー構築ロジックのすぐそば）に置く。実装は、既存`TagRepository.list_tags()`が構築するツリーをそのまま深さ優先で走査し、各ノードの親ノードの`name`を`parent_name`として子ノードに持ち回るだけであり、新たなSQL・新たな循環参照チェック等の業務ロジック追加は不要な薄いラッパーである。
2. **列構成をタグ一括インポート（ADR-0061）と完全一致させる**: CSVの出力列は`name`/`parent_name`/`description`の3列とし、`id`は出力しない。タグのupsertキーは（`question_altered`の`id`列とは異なり）`name`であるため、`id`列を出力するとインポート時の一致条件として誤解されるおそれがある。既存のタグ一括インポートUI（`TagTreePage`のCSV一括インポート説明文）が案内する列構成とそのまま揃え、エクスポート結果を再インポートしても内容が変化しない（往復整合性）ことを優先する。
3. **エイリアス（`tag_alias`）は対象外とする**: タグ一括インポート（ADR-0061）が`name`/`parent_name`/`description`の3列のみでエイリアスに対応していないため、エクスポートに含めると「そのまま再インポートしても情報が失われない」という前提が崩れる。エイリアスは引き続き既存の個別操作（`add_tag_alias`/`remove_tag_alias`、`TagTreePage`の個別編集）でのみ管理する。
4. **全タグを常に対象とする（絞り込みなし）**: 現状の`TagTreePage`には絞り込みUIがなく、`list_tags`自体も常に全件を返す設計であるため、部分エクスポート（特定の親タグ配下のみ等）は本書のMVPでは提供しない。将来要望が出た場合に別途要件化する。
5. **出力順序**: `export_tags`は既存ツリーを深さ優先で走査し、親タグが子タグより先に出現する階層順で返す。タグ一括インポートの`parent_name`解決は行の並び順に依存しない（ADR-0061の複数パス反復解決）ため、出力順序は再インポートの正しさには影響しないが、人が内容を確認する際の可読性のために階層順とする。
6. **既存の全データエクスポート（ADR-0046/0047）との関係**: 本ツールは、ADR-0046が新設した読み取り専用ロール（`CHATBOT_EXPORT_DB_URL`）を経由せず、Knowledge MCP経由（ADR-0013の原則をエクスポートにも適用、ADR-0064で先例化）で実装する。既存の全データエクスポート（8テーブルのZIP、`tag.csv`は`id`/`name`/`parent_tag_id`/`description`の数値ID形式）は変更せず、独立した別機能として併存させる。両者の`tag.csv`は列構成・用途が異なるため、画面上の説明・ファイル名で混同を避ける（詳細設計フェーズで確定）。

## 検討した代替案

- **既存`list_tags`をそのまま`web_backend`側で呼び出し、レスポンスのツリーを`web_backend`側でフラット化してCSVを組み立てる（新規ツールを追加しない）**: 実装コストが最小で済む利点がある。しかし、`web_backend`の各コントローラは一貫して「MCPツール呼び出し＋レスポンス変換のみ」の薄いBFFという役割に留められており、ツリー→フラット変換という（軽微とはいえ）データ構造の組み替えロジックをここに新設すると、この役割分担の一貫性が崩れる。発注者確認の結果、Knowledge MCP側に専用ツールを追加する方針を優先し、不採用とした。
- **既存の全データエクスポート機構（`web_backend/src/export/tables.py`、ADR-0046の読み取り専用ロール）の`tag.csv`をそのまま流用・拡張する**: 列定義（`id`/`name`/`parent_tag_id`/`description`）が既に存在し実装コストは最小だが、`parent_tag_id`が数値IDであるためタグ一括インポート（`parent_name`による名前解決）へそのまま再投入できず、「そのまま再インポートできる形式」という本書の目的を満たさない。また、この機構は`chatbot`データベースへの読み取り専用ロール経由の直接SQLであり、Knowledge MCP経由に統一するADR-0013・ADR-0064の方針とも整合しない。既存の全データエクスポートは、バックアップ・移行目的の別機能として変更せず併存させる。
- **CSVエクスポートにエイリアス（`tag_alias`）列を含める（例: 区切り文字で複数エイリアスを1セルにまとめる等）**: タグ一括インポート側がエイリアス列に対応していないため、エクスポート→インポートの往復でエイリアス情報が失われ、利用者が気づかないままエイリアスを喪失するリスクがある。発注者確認の結果、往復整合性を優先し、エイリアスは対象外とした。
- **タグ階層の一部（特定の親タグ配下）のみをエクスポートする機能もあわせて提供する**: 現状の`TagTreePage`には絞り込みUIがなく、運用上のニーズも明確でない。範囲を広げず、まず全件エクスポートのみで運用を開始し、必要になった時点で別途要件化する方が安全と判断した。

## 結果・影響

- `knowledge_mcp`に新規ツール`export_tags`とその実装（既存`TagRepository.list_tags()`のツリー構築ロジックを再利用したフラット化処理、`TagRepository`への新規メソッド追加）が追加される。既存の`list_tags`/`create_tag`/`rename_tag`/`set_tag_description`/`move_tag`/`delete_tag`/`import_tag_batch`の実装・シグネチャには変更を加えない。
- `web_backend`の`tag_controller.py`に新規エンドポイント`GET /api/tags/export`（CSV組み立てのみ）が追加される。既存の`/api/tags/*`・全データエクスポート（`/api/export`）には変更を加えない。
- `front_dev`の`TagTreePage`に「CSVエクスポート」ボタンが追加される。既存の個別CRUD・CSV一括インポートUIには変更を加えない。
- タグ一括インポート（ADR-0061）とCSVエクスポートの列構成が完全一致するため、エクスポート→（必要な修正）→再インポートという運用が可能になる。
- エイリアス（`tag_alias`）、部分エクスポートは本ADRの対象外のまま維持される。将来、これらの要望が出た場合は別途ADRが必要になる。
- ファイルサイズ・件数上限、ファイル名の詳細は、要件定義書のOpen Issueとして引き継ぐ。
