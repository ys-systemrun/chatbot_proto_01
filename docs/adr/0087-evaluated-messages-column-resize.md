# ADR-0087: 評価済みメッセージページの列幅ドラッグ変更機能の実装方式

- ステータス: Accepted
- 日付: 2026-09-14
- 関連: `docs/requirement/202609141030_評価済みメッセージページ列幅ドラッグ変更機能要件定義書.md`、ADR-0015、ADR-0044、ADR-0045

## コンテキスト

評価済みメッセージページ（`EvaluatedMessagesPage.tsx`）は、会話（`EvaluatedConversation`）ごとに`<details>`で開閉可能な会話カードを並べ、各カードが独立した`<table className="ev-table">`を持つ構造である。列（#・役割・評価・モデル・本文・LLM入力・登録日時の7列）の幅は`style.css`のクラス指定（一部のみ固定px、残りはブラウザの自動幅）で決まっており、`<colgroup>`は存在せず、利用者が変更する手段もない。「本文」「LLM入力」列は長文になりやすく、固定幅では折り返しが多くなり閲覧しづらいという課題が要件定義書（202609141030）で示された。

`front_dev`は`react`（18.3系）・`react-router-dom`（6.26系、`/admin`サブツリー限定、ADR-0015）のみに依存を絞る方針を採っており、テーブル系UIはすべて素の`<table>`要素の自前実装である（DataGrid等のUIライブラリは未導入）。

検討にあたり、発注者へ以下3点を確認済みである。

1. 画面内に並ぶ複数の会話テーブル間での列幅の扱い: **全テーブルに同期**（いずれか1箇所でのドラッグ変更を、画面内の他の全会話テーブルの対応する列へ即時反映する）を採用する。
2. 列幅の永続化: **ブラウザ（`localStorage`）に保存し永続化**（サーバー側・DBでの保存は行わない）を採用する。
3. 今回の対象範囲: **評価済みメッセージページのみ**（他の管理一覧ページ`admin-table`系への展開は対象外）とする。

## 決定

**列幅の可変化は外部ライブラリを追加せず、`<colgroup>`とネイティブの`mousedown`/`mousemove`/`mouseup`イベントによる自前実装のドラッグリサイズとする。列幅stateは`EvaluatedMessagesPage`側で一元管理し、全ての`ConversationCard`（`<table>`）へ共通のpropsとして渡すことで、画面内の全テーブル間での同期を実現する。確定した列幅はバージョン付きキーで`localStorage`に永続化する。**

1. **列幅stateの一元管理と全テーブルへの共有**: 列幅（7要素、px単位の数値配列）を`EvaluatedMessagesPage`のトップレベルstateとして保持し、`ConversationCard`にはprops（現在の列幅配列、更新用コールバック）としてのみ渡す。`ConversationCard`自身はローカルの列幅stateを持たない。ドラッグ操作自体は個々のテーブルの`th`上で発生するが、更新は共通の親stateに対して行われるため、結果としてどのテーブルでドラッグしても画面内の全テーブルに同時反映される（発注者確認事項1）。
2. **`<colgroup>` + `table-layout: fixed`への変更**: 現状`ev-table`は`<colgroup>`を持たず`table-layout`も既定（auto）であるため、列幅を数値で厳密に制御できない。各`<table>`直下に`<colgroup><col style={{ width: `${widths[i]}px` }} /> …</colgroup>`を追加し、`.ev-table`に`table-layout: fixed`を指定する。既存の`ev-td-num`・`ev-td-model`・`ev-td-content`・`ev-td-date`等のクラスは、幅指定を`<col>`側に一本化するため、`width`/`max-width`指定を削除し、文字揃え・色等の非幅指定用途に限定する。
3. **ドラッグハンドル・操作方式**: 各`th`の右端に幅約8pxの透明な操作領域を設け、ホバー時は`cursor: col-resize`とする。`onMouseDown`でドラッグを開始し、開始X座標・開始幅を記録したうえで`window`に`mousemove`/`mouseup`リスナーを登録する（`th`個別ではなく`window`に登録することで、マウスがハンドル領域から外れてもドラッグを継続できるようにする）。`mousemove`では移動量を開始幅に加算し、列ごとの最小幅でクランプしたうえで列幅stateをリアルタイム更新する。最大幅の上限は設けない（既存の`.ev-table-wrap { overflow-x: auto }`により、合計幅が画面幅を超えても横スクロールで閲覧可能なため）。`mouseup`でドラッグを終了し、リスナーを解除したうえで`localStorage`へ保存する。ドラッグ中は`user-select: none`相当のクラスを`document.body`等へ付与し、テキストの誤選択を防ぐ。
4. **列ごとの最小幅の定数化**: 要件定義書6.4節の表に対応する既定幅・最小幅を、`EvaluatedMessagesPage.tsx`内に列インデックスに対応する定数配列として定義する。
5. **リセット機能**: ドラッグハンドルのダブルクリックで対象列のみ既定幅に戻す。加えて、画面上部に「列幅をリセット」ボタンを設け、全列を既定幅に戻すとともに`localStorage`の保存値も既定値で上書きする。
6. **`localStorage`への永続化とフォールバック**: 列幅の確定時（`mouseup`、リセット操作）にのみ、`localStorage.setItem("ev_column_widths_v1", JSON.stringify(widths))`で保存する（`mousemove`のたびには書き込まない）。マウント時に`localStorage.getItem("ev_column_widths_v1")`を読み取り、要素数が7かつ全要素が対応する列の最小幅以上の有限数値である場合のみ初期stateとして採用し、それ以外（未保存・パース失敗・要素数不一致・範囲外の値）は既定幅にフォールバックする。キー名に`_v1`を付与し、将来列構成（列数・順序）を変更する際はバージョンを上げることで、古い保存値との不整合（列のずれ）を防ぐ（発注者確認事項2）。
7. **対象範囲を評価済みメッセージページのみに限定**: 他の管理一覧ページ（`QaListPage`等`admin-table`系）は本ADRの対象外とする（発注者確認事項3）。将来的に同様の機能を他ページへ展開する場合、本ADRの列幅state一元管理パターン・`localStorage`キー命名規則・ドラッグ実装方式を流用できるが、共通フック（例: `useResizableColumns`）への切り出しは本ADRの対象外とし、実際に展開する要望が出た時点で別途検討する。

## 検討した代替案

- **列幅stateを各`ConversationCard`（テーブル単位）でローカルに保持する方式**: 親コンポーネントへのprops引き回しが不要で実装がやや単純になるが、画面内の複数会話テーブル間で列幅が独立して変化しうるため、同じ列見出しであるにもかかわらず視覚的に列幅が揃わなくなる。発注者確認事項1（全テーブルに同期）と矛盾するため不採用とした。
- **React製の汎用テーブル・グリッドライブラリ（例: TanStack Table、react-resizable、react-data-grid等）を新規導入する方式**: 列リサイズに加えソート・仮想化・列の表示/非表示切替等の機能が標準で揃う利点があるが、`front_dev`は現状`react` / `react-router-dom`のみに依存を絞る方針（ADR-0015）を採っており、`EvaluatedMessagesPage`は`<details>`によるカード型レイアウト・`ExpandableCell`による展開セル等、素の`<table>`を前提とした独自UIを既に持つ。列幅ドラッグという単一機能のためにライブラリを導入すると、学習コスト・依存追加・既存UIとの統合コストが要件の規模に見合わないと判断し、既存方針を踏襲した自前実装を採用した。
- **列幅設定をサーバー側（DBまたは利用者プロファイル）に永続化する方式**: 利用者・端末をまたいで設定を共有できる利点があるが、`conversation`データベース・関連APIへの新規スキーマ・エンドポイント追加が必要になる。単純な表示上の好みの保存にそこまでのコストをかける必要はないと判断し、`localStorage`によるブラウザ単位の保存で十分とした（発注者確認事項2）。
- **列幅に最大値の上限を設ける方式**: 列を極端に広げる誤操作を防止できる利点があるが、「本文」「LLM入力」等の長文列を大きく広げたいという本要件の主目的（背景セクション参照）を制約しうる。上限は設けず、既存の横スクロール機構（`.ev-table-wrap`）で対応する方式とした。
- **`ConversationCard`ごとに列幅を独立させたうえで、あるカードでの変更を他カードへ`useEffect`等で同期反映するイベント伝播方式**: 状態を親で一元管理する方式（決定1）と最終的な見た目は同じになりうるが、複数箇所に列幅stateが分散し、同期漏れ・競合状態のバグを生みやすい。親コンポーネントでの単一の状態管理（Single Source of Truth）の方がシンプルで堅牢と判断した。

## 結果・影響

- 変更対象は`front_dev`の`EvaluatedMessagesPage.tsx`・`style.css`のみ。`web_backend` / `knowledge_mcp` / `agent_invitro` / DBスキーマへの変更は一切ない。新規npm依存パッケージの追加もない。
- `table-layout: fixed`への変更に伴い、列幅は`<col>`側の指定が優先されるようになる。既存の`ev-td-content`の`max-width: 300px`等、幅に関する既存CSS指定は削除し`<col>`側に一本化する必要がある（実装時、二重指定によるスタイル競合・意図しない折り返し崩れに注意する）。
- `localStorage`に保存された列幅は当該ブラウザ・オリジンに閉じる。利用者が別端末・別ブラウザ・シークレットウィンドウで開いた場合は既定幅から開始する（発注者確認済みの既知の制約）。
- 将来、他の管理一覧ページ（`QaListPage`等の`admin-table`系）へ同様の列幅ドラッグ機能を展開する要望が出た場合、本ADRの列幅state一元管理パターン・`localStorage`キー命名規則（画面ごとにバージョン付きキーを個別に持つ）を踏襲しつつ、共通フックへの切り出しを別途ADRとして検討する。
- 列構成（列数・列の意味・順序）を将来変更する場合、`localStorage`キーの`_v1`サフィックスを上げる形で移行する想定である。実際に列構成変更が発生した時点で、具体的な移行手順（旧バージョンキーの扱い等）を別途定める必要がある（要件定義書11章 Open Issue参照）。
