# ADR-0103: デプロイ環境のデータをローカルの SQL ファイルへ退避してから一括破棄する `destroy-all` を新設する

- ステータス: Proposed（実装済み。AWS 上で export-data・destroy-all・import-data による復旧を確認したら Accepted にする）
- 日付: 2026-10-20（実装 2026-10-21）
- 関連: `docs/requirement/202610201030_デプロイ環境データ退避付き一括破棄機能要件定義書.md`, ADR-0039（破棄順序 app → database）, ADR-0040（`.bat` → コンテナ内 Python）, ADR-0046 / ADR-0047（全データエクスポート）, ADR-0066（全データインポート・事前自動バックアップ。本 ADR で `import-data` に照合を追加）, ADR-0075（MIGRATE_ONLY）, ADR-0083（QUERY_MODE）, ADR-0095（常駐 4 サービスの 1 タスク集約）

## コンテキスト

デプロイ環境の撤去は `destroy-app.bat` → `destroy-database.bat` の 2 段で行っている。`destroy-database` は RDS を `skip_final_snapshot=true` で削除し、import バケット（`force_destroy=true`）も一緒に消すため、実行した時点で RDS 上のデータは AWS 上に残らない。

RDS には、DVC 管理のシード元データ（ADR-0097）から再現できないデータがある。管理 UI で追加・編集した QA・タグ・トラブルシューティング記事（`knowledge`）と、会話ログ・評価・リリース記録・検証結果（`conversation`）である。今は破棄の前に管理 UI の全データエクスポート（ADR-0047）を手で実行するしかなく、忘れると取り返せない。

ユーザーから「① データを SQL ファイルとしてエクスポート ② destroy-app 相当 ③ destroy-database 相当」を 1 つのバッチで行いたいという要求があった（2026-10-20）。追加確認で次の方針も決まった（要件定義書 2.4 節）。

- 退避ファイルは運用者の PC（ローカル）以外には保存しない。
- 途中で失敗したときに、続きから再実行できるオプション引数を設ける。
- app 構成が既に無い場合は、`destroy-database.bat` を実行するか `apply-app.bat` の後に再実行するよう案内して終える。
- 復旧時にスキーマ版が違うときは、そのまま SQL を実行するか終了するかをコンソールで確認する。
- 会話ログを含む `conversation.sql` は、次回のエクスポートで上書きされる形で消えるようにする。`knowledge.sql`・`manifest.json` も同じ固定フォルダで毎回まとめて上書きする。

既存のデータ取り出し手段は 3 つある。

- **管理 UI のエクスポート（`GET /api/export`）**: ブラウザ操作が前提。バッチから呼ぶには ALB への到達経路と認証をデプロイコンテナに持ち込む必要がある。
- **`import-data` の事前自動バックアップ（ADR-0066 §5）**: `db_init` の run-task が `TRUNCATE` + `INSERT` 形式の SQL を作り、import バケットの `rollback/` に置く。生成ロジック（`build_backup_sql`）は対象テーブルを実 DB から introspection するため、列の追加に追従する。
- **`query.bat`（ADR-0083）**: 結果を CloudWatch Logs 経由で表示する。全件ダンプには向かない。

## 決定

**`db_init` に退避エクスポート専用の起動モード `EXPORT_MODE` を追加し、ADR-0066 の退避 SQL 生成を流用して両データベースを import バケット経由で運用者の PC の固定フォルダ（`terraform/backup/`）へ退避し、毎回上書きする。退避の成功をローカルで確かめてから、`destroy-app` → `destroy-database` と同じ処理を順に行う `destroy-all` サブコマンドと `destroy-all.bat` を新設する。失敗した段から続ける `--resume-from` を設け、`import-data` には退避時と投入先のスキーマ版の照合を加える。退避だけを行う `export-data` サブコマンドと `export-data.bat` も新設する。**

1. **退避の実行場所**: `db_init` の既存タスク定義（`db_init_task_family`）を、run-task の環境変数オーバーライドで `EXPORT_MODE=true` にして起動する（IMPORT_MODE・QUERY_MODE・MIGRATE_ONLY と同じ方式）。新しいタスク定義・イメージ・IAM は作らない。他のモードとの同時指定はエラーにする。
2. **SQL の形式**: ADR-0066 の `build_backup_sql` と同じ形式（先頭に `TRUNCATE ... RESTART IDENTITY CASCADE`、親→子順の 500 行単位マルチ行 `INSERT`、DDL なし）にする。この形式は `import-data` の投入ダンプとしてそのまま使え、`psql -f` で直接適用しても退避時点の状態に戻る。対象テーブルも `import_data.py` の `KNOWLEDGE_TABLES`・`CONVERSATION_TABLES` をそのまま使い、退避・全消去・再投入で同じ集合にする。
3. **対象漏れの検出**: 各データベースの `public` スキーマに、対象テーブルにも yoyo の管理テーブルにも入っていないテーブルがあれば、退避を失敗させる。リストの更新漏れのまま破棄してデータを失うことを防ぐ。
4. **一貫性**: 退避の前に集約サービス（ADR-0095）を `desired_count=0` にして書き込みを止める。さらに 1 データベースの読み出しを 1 つの `REPEATABLE READ READ ONLY` トランザクションで行う。`export-data` は成功・失敗にかかわらずサービスを元に戻す。`destroy-all` は退避が失敗したときだけ戻す（成功したら続けて破棄するため）。
5. **受け渡しと検証**: タスクは `export/<ts>/knowledge.sql`・`conversation.sql`・`manifest.json`（バイト数・SHA-256・テーブルごとの行数・スキーマ版＝yoyo の適用済みマイグレーション ID の集合）を import バケットに置く。`<ts>` はオーケストレータが環境変数 `EXPORT_TIMESTAMP` で渡す。`<ts>` は S3 上で実行ごとの成果物を区別するためだけに使い、ローカルのファイル名には付けない。オーケストレータはこれを一時フォルダ `terraform/backup/.incoming/` にダウンロードし、SHA-256 を照合する。照合に失敗したら、前回の退避ファイルには手を付けずに終え、破棄にも進まない。ローカルのマニフェストには AWS アカウント・リージョン・クラスタ名・git コミットを書き足す。
6. **破棄の順序と停止条件**: `[0]` 前提確認 → `[1]` 退避 → `[2]` `destroy-app` 相当 → `[3]` `destroy-database` 相当 の順に実行する。どの段も、失敗したら後ろの段は実行しない。② ③ で失敗したときは、再開コマンドを表示する。
7. **app 構成が無いとき**: 退避用の run-task は app 構成の ECS クラスタで動くため、app 構成が無い（state が無い・リソースが空・クラスタ名が取れない）と退避できない。このときは「退避が不要なら `destroy-database.bat` を実行、退避が必要なら `apply-app.bat` を実行してから再実行」と表示し、何もせずに終える（`export-data` も同じ）。退避なしで破棄へ進む経路は `destroy-all` には作らない。
8. **確認方式**: 実行前に、退避先と、`destroy-app`・`destroy-database` が出しているのと同じ破棄内容の警告を表示する。そのうえで `'destroy-all'` のタイプ確認を 1 回だけ行う。`--yes` による省略は設けない（`destroy-app`・`destroy-database` と同じ）。②③ では個別の確認を出さない。既存の `cmd_destroy_app`・`cmd_destroy_database` にタイプ確認を省略する引数（既定は現行どおり確認する）を追加し、その引数を付けて呼び出す。
9. **再開実行**: `destroy-all --resume-from {destroy-app,destroy-database}` で、指定した段から最後までを実行する。退避は取り直さず、`terraform/backup/` を変更しない。
   - 再開の根拠は `terraform/backup/` の現在の内容（直前の退避）とする。フォルダを指定するオプションは設けない。
   - 破棄の前に、`terraform/backup/` の 3 ファイルがそろっていること、SHA-256 がマニフェストと一致すること、マニフェストの AWS アカウント・リージョンが現在の `.env` と一致することを確かめる。満たさなければ何も破棄しない。
   - 再開段と state が食い違う場合は、正しい再開段を案内して終える（`destroy-app` から再開しようとして app が破棄済みなら `destroy-database` から、`destroy-database` から再開しようとして app が残っていれば `destroy-app` から）。
   - 再開実行でも `'destroy-all'` のタイプ確認を 1 回行い、退避ファイルの取得日時・クラスタ名・行数を表示する。
10. **復旧時のスキーマ版照合（`import-data`）**: 投入ダンプと同じディレクトリに `manifest.json` があれば、そこに書かれたスキーマ版を退避時の版とする。投入先の版は、`db_init` を `EXPORT_MODE` + `EXPORT_MANIFEST_ONLY=true`（SQL を作らずマニフェストだけ作る）で run-task 起動して取る。
    - データベースごとに比べ、一致すれば何も聞かずに進む。
    - 異なれば、片方にしか無いマイグレーション ID を表示し、「このまま SQL を実行するか」を `y/N` で確認する。`N` なら何も変更せずに終える。
    - マニフェストが無いダンプ（管理 UI のエクスポート等）は「スキーマ版を確認できない」と表示して同じ確認を行う。
    - この照合は既存のクラスタ名タイプ確認・S3 アップロード・サービス停止より前に行い、`--yes` で省略できないものとする。
11. **ローカル保存と上書き**: 退避ファイルの保存先は運用者の PC の固定フォルダ `terraform/backup/` のみとし、中身は `knowledge.sql`・`conversation.sql`・`manifest.json` の 3 ファイルにする。取得日時はファイル名ではなくマニフェストに記録する。
    - 次回の退避（`export-data`・`destroy-all` の ①）が照合まで成功した時点で、3 ファイルをまとめて一時フォルダの内容で置き換える。会話ログを含む `conversation.sql` は、次回の退避までの間だけ PC に残る。世代管理はしない。
    - 3 ファイルは常に同じ回の退避でそろえる。次回の退避が途中で失敗したときは、前回分をそのまま残す。
    - 退避以外のコマンド（`import-data`・再開実行など）は `terraform/backup/` を変更しない。
    - 退避の確認画面では、上書きされる前回分の取得日時・クラスタ名・行数を示す。
    - `terraform/backup/` は `.gitignore` に入れる（`conversation.sql` が会話ログを含むため）。S3 上の `export/<ts>/` は ③ で import バケットごと消えるので、退避の正本はローカルだけになる。
    - 完了時に、退避先と復旧手順（`apply-all` → `import-data --knowledge-sql backup\knowledge.sql --conversation-sql backup\conversation.sql`）と、「復旧が済むまで退避を実行しないこと（上書きされるため）」を表示する。

## 検討した代替案

- **管理 UI のエクスポート API をバッチから呼ぶ**: 出力形式が管理 UI のダウンロードと同じになる利点がある。しかし ALB への到達経路（接続元 IP の許可）と認証をデプロイコンテナに持たせる必要がある。さらに `web_backend` のスキーマ定義はハードコードのため、列追加への追従が `db_init` の introspection 方式より弱い。同期配信のため ALB のタイムアウトも受ける（ADR-0047 の Open Issue）。採らない。
- **RDS の最終スナップショットを残す（`skip_final_snapshot=false`）**: 手間なく完全な状態が残る。しかしスナップショットは AWS 上で課金され続け、破棄の目的（コスト停止）と矛盾する。また「SQL ファイルとして手元に残す」という要求を満たさない。採らない。
- **退避ファイルを長寿命バケット（datastore 構成の DVC バケット等）にも置く**: PC の故障や誤削除に強くなる。発注者の判断（ローカル PC 以外には保存しない）により採らない。
- **実行ごとに日時付きフォルダ（`terraform/backup/<ts>/`）を作り、世代で残す**: 過去の時点に戻せる。しかし会話ログを含む `conversation.sql` が際限なく PC に溜まる。発注者の判断（次回のエクスポートで上書きされる形で消える）により採らない。
- **`conversation.sql` だけを上書きし、`knowledge.sql` は世代で残す**: ナレッジの過去分は残せる。しかし古い回の `knowledge.sql` には対になる `conversation.sql` とマニフェストが無くなり、再開実行や復旧のときにどの組を使うかが曖昧になる。3 ファイルをまとめて上書きする方式を、発注者の確認のうえで選んだ。
- **ダウンロード先に直接上書きする（一時フォルダを使わない）**: 実装は単純になる。しかしダウンロードや照合が途中で失敗すると、前回分が消えたうえに今回分も不完全という状態になりうる。一時フォルダで照合してから置き換える。
- **`destroy-app.bat` と `destroy-database.bat` を順に呼ぶだけの `.bat` を作り、その前に退避を挟む**: 実装は最小になる。しかし確認が 3 回（退避・`destroy-app`・`destroy-database`）になり、`.bat` の中で前段の失敗を見て止める処理を書くことになる（`cmd /k` 再起動やエラーレベルの扱いが複雑）。段の制御は Python のオーケストレータに集める（ADR-0040 の方針）。
- **退避中もサービスを止めず、`REPEATABLE READ` のスナップショットだけで済ませる**: サービスを止めずに済む。しかしスナップショットの取得から破棄までの数分間の書き込み（チャットや評価）が失われる。直後に破棄するので止めても困らないため、停止を選ぶ。
- **`pg_dump` を `db_init` イメージに入れて使う**: 標準的な形式が得られる。しかし `import-data` の投入ダンプ形式（`INSERT` を 1 トランザクションで適用し、後でシーケンスを同期する）と合わず、復旧経路が別になる。既にある `build_backup_sql` を流用すれば、退避と復旧が同じ形式でつながる。採らない。
- **再開段を state から自動で判定する（オプションなしの再実行で続きから進む）**: 運用者がオプションを覚えなくてよい。しかし「退避からやり直したい」のか「破棄だけ続けたい」のかは state からは分からず、古い退避ファイルのまま破棄へ進む事故につながる。破棄段の再開は、運用者が `--resume-from` で明示したときだけにする。代わりに、失敗時に打つべき再開コマンドをそのまま表示し、指定した段と state が食い違えば正しい段を案内する。
- **再開実行で退避ファイルを検証しない**: 処理は単純になる。しかし退避ファイルが壊れていたり、別アカウント・別環境のものだったりしても破棄が進んでしまう。SHA-256 とアカウント・リージョンの照合は安価なので行う。
- **スキーマ版の照合で、投入先の版をリポジトリのマイグレーションファイルから推定する**: run-task が不要で速い。しかし投入先 DB に実際に適用されている版と、手元のコードの版が一致する保証がない（古いイメージのまま、`migrate` 未実行など）。実 DB の `_yoyo_migration` を読む方が確実なため、run-task で取得する。
- **スキーマ版が違うときは常に中止する**: 安全側だが、列追加だけのマイグレーションのように投入できる場合まで止まる。投入は 1 トランザクションで、列が合わなければ失敗して投入前に戻るため、発注者の判断どおり確認のうえで実行できるようにする。

## 結果・影響

- 破棄の前に退避を確実に挟めるようになる。退避に失敗したときは、破棄が一切始まらない。
- 退避ファイルは `import-data` の投入ダンプとして使えるため、`apply-all` → `import-data` で同じデータの環境を作り直せる。スキーマ版が違うときは、`import-data` が差分を示してから実行するかを聞く。実行を選んで列が合わなければ、投入は失敗して投入前の状態に戻る（ADR-0066 の 1 トランザクション）。
- `import-data` は、照合用の run-task が 1 回増えるため、数十秒〜1 分程度長くなる。
- PC 上の退避ファイルは常に最新 1 回分になる。会話ログを含む `conversation.sql` が溜まり続けることはない。一方で、復旧前に誤って `export-data`・`destroy-all` を実行すると、復旧したいデータが上書きされる（例: `apply-all` で作り直した直後の空に近い環境を退避してしまう）。確認画面で上書きされる前回分の取得日時・クラスタ名・行数を示し、完了時にも「復旧が済むまで退避を実行しない」よう案内して防ぐ。前回分を残したい場合は、運用者が退避の前に別の場所へ手でコピーする。
- ② ③ が途中で失敗しても、表示された再開コマンドで続きから実行できる。退避は取り直さないため、退避後〜失敗までの間のデータは、集約サービスを止めているので増えない。ただし ② の失敗後に運用者が手で app を戻して使った場合は、その間のデータは退避ファイルに含まれない（確認画面で注意を出す）。
- `db_init` の起動モードが 4 つ（通常・MIGRATE_ONLY・IMPORT_MODE・QUERY_MODE）から 5 つになる。EXPORT_MODE は読み取りのみだが、他モードとの同時指定は起動時にエラーとする。
- 新しい対象外テーブルの検出（決定 3）は、`import-data`・`export-data`・`destroy-all` に共通する「対象テーブルの更新漏れ」を表に出す。マイグレーションでテーブルを足したときに `KNOWLEDGE_TABLES`・`CONVERSATION_TABLES`（と `web_backend/src/export/tables.py`）を更新しないと、`destroy-all` が止まる。
- 運用者の AWS 認証情報に、import バケットの `s3:GetObject`・`s3:ListBucket` が必要になる。`db_init` のタスクロールは既に必要な権限を持つため、Terraform の変更はない。
- app 構成が既に破棄され、database 構成だけが残っている環境では退避できない。決定 7 の案内に従い、`apply-app` で戻してから実行するか、退避なしで `destroy-database.bat` を使う。
