# ADR-0023: MCPサーバー・クライアント群をAWSへデプロイする際のアクセス範囲・ネットワーク境界方針

- ステータス: Accepted
- 日付: 2026-08-10
- 関連: `docs/requirement/202608100910_MCPサーバークライアントAWSデプロイ要件定義書.md`, ADR-0002, ADR-0007, ADR-0019

## コンテキスト

Knowledge MCP サーバ・Tag Selector MCP サーバは、独立Dockerコンテナ + Streamable HTTP方式（ADR-0002, ADR-0007）でdocker-compose上に構築済みであり、README.mdには「本フェーズでは追加認証を実装していません。社内ネットワーク外へポートを公開しないでください」という運用上の制約が明記されている。これらMCPサーバー・クライアント（agent_invitro）をAWS上にTerraformでデプロイし、動作検証を行うにあたり、AWS上のどこからの到達性を許可する構成にするかを決める必要がある。

検討した選択肢は次の3案。

1. **AWS内部限定**: MCPサーバー・クライアントへ到達できるのは、同一AWSアカウント/VPC内で動く他コンポーネント（agent_invitroなど）のみとし、AWS外（オンプレ社内LAN・インターネット）からの直接アクセスは一切許可しない。
2. **オンプレ社内LANからの直接アクセスも許可**: 拠点間VPN（Site-to-Site VPN等）を新規に構築し、社内LAN上のPCや別システムからMCPエンドポイントへ直接到達できるようにする。
3. **上記の併用**: 通常はAWS内部限定としつつ、運用者の動作確認・デバッグ用途に限りAWS Client VPN等を追加する。

発注者へ確認した結果、**AWS内部限定（案1）**を採用する方針が確定した。オンプレ社内LANとAWS VPC間の接続手段は現時点で用意されておらず、本デプロイの目的（AWS上での動作検証）に対して新規構築するコストは正当化されないと判断した。

## 決定

MCPサーバー・クライアント群（knowledge_mcp, tag_selector_mcp, agent_invitro）は、**AWSアカウント内のVPCに閉じたプライベートサブネットに配置し、インターネットゲートウェイを経由した外部公開を行わない**。また、**オンプレ社内LANとAWS VPC間の新規接続（VPN/専用線等）も本フェーズでは構築しない**。

- 各コンポーネントへの到達は、同一VPC（または将来的にPeering・Transit Gateway等で接続された他のAWS内部ネットワーク）内からのみに限定する。
- ネットワーク到達性の制御は、セキュリティグループにより「agent_invitro → tag_selector_mcp」「agent_invitro → knowledge_mcp」の通信のみを明示的に許可する形で行う。
- 開発者・運用者が動作確認のためにMCPエンドポイントへ個別にアクセスする必要がある場合は、AWS標準の踏み台手段（ECS Exec、SSMポートフォワーディング等）を用いる。専用のVPN基盤は本フェーズでは追加しない。

## 検討した代替案

- **案2（拠点間VPN構築）**: 社内の別システムや開発者PCから直接MCPエンドポイントへ到達できる利点があるが、本デプロイの目的はagent_invitroからの呼び出しによる動作検証であり、agent_invitro以外にMCPサーバーを直接叩くクライアントは現時点で想定されていない。新規のVPN基盤構築（Customer Gateway・VPN Gateway・ルーティング設定等）はこの目的に対して過大であるため見送った。
- **案3（AWS Client VPNの併用）**: 運用者個人の動作確認用途としては有用だが、案1の範囲でもECS Exec等のAWS標準機能で同等の目的（コンテナ内部への接続・ログ確認）を代替できるため、MVPフェーズでは見送った。将来、運用担当者からの直接デバッグアクセスが恒常的に必要になった場合は、別ADRで再検討する。

## 結果・影響

- インターネットゲートウェイ・パブリックサブネット・パブリックALBは本構成には含まれない。外部LLM API（OpenAI等）を利用する場合は、NATゲートウェイまたはVPCエンドポイント経由でのアウトバウンド通信のみを許可する（インバウンドの外部公開とは区別する）。
- AWS内部限定であることを前提に、**アプリケーションレベルの認証（OAuth等）は本フェーズでは実装しない**。これはADR-0019がagent_invitro実験フェーズにおいて「ホスト側へポートを公開しないため追加の認証検討は不要」と判断した考え方を、AWS内部限定構成にも同様に適用するものである。ADR-0002が残していた「認証・アクセス制御の設計が新たに必要」という課題は、本ADRの範囲（AWS内部限定）では、ネットワークレベルの制御（VPC・セキュリティグループ）で当面代替する、という位置づけになる。
- 将来、社外のMCPクライアントや他部門からのアクセスなど、外部公開・オンプレ直接アクセスが必要になった場合は、本ADRを見直し、MCP仕様のAuthorization機能（OAuth 2.1ベース）やAWS Client VPN／拠点間VPNの追加を含めて別途ADRを起票する。
- コンピュート基盤（ECS Fargate等）・agent_invitroの実行形態変更・既存DBの配置方針など、本ADRの範囲外の論点は要件定義書のOpen Issuesとして別途整理する。

**（追記, 2026-08-10）** 「アプリケーションレベルの認証を本フェーズでは実装しない」という本ADRの結論について、要件定義書 Open Issue #2として改めて発注者に確認を依頼していたが、差し当たり本ADRの方針どおり実装しないことで確定した。将来、外部公開や他部門からの利用が必要になった場合に再検討するという位置づけ（上記）に変更はない。
