# ADR-0055: 全データインポート機能の実装方式とアクセス経路

- ステータス: Accepted
- 日付: 2026-08-26
- 関連: `docs/requirement/202608261002_DBマイグレーション・データインポート機能要件定義書.md`, ADR-0013, ADR-0045, ADR-0046, ADR-0047

## コンテキスト

全データエクスポート機能要件定義書（202608241530）4.2節は、「インポート機能（エクスポートしたSQL/CSVを別環境に取り込む操作自体は本書の対象外とし、生成するSQLファイルが`psql -f`等で再投入可能な形式であることの確認にとどめる）」として、実際の取り込み機能自体を対象外としていた。エクスポート機能が生成するSQLダンプ（`chatbot.sql`・`conversation.sql`）は、`CREATE TABLE IF NOT EXISTS`と`INSERT INTO`文で構成され、`psql -f`でそのまま再投入可能な形式であることは、エクスポート機能の受け入れ基準として既に確認済みである（ADR-0047）。

本ADRは、この「再投入可能なファイル」を実際に別環境へ取り込むための、公式な実行手段を決定する。

全データエクスポートは、`admin_ui`（`web_backend`）にブラウザボタンから実行できる機能として実装されている。インポートについても対称的なUI（ブラウザからのアップロード）を用意することが考えられるが、これには次の固有のリスクがある。

- **書き込み権限の付与**: エクスポートは読み取り専用ロール（`chatbot_export_reader`、ADR-0046）で完結する。一方インポートは`INSERT`・`CREATE TABLE`（スキーマも含めて再現するため）を実行する必要があり、`admin_ui`に`chatbot`データベースへの書き込み権限を新たに付与することになる。これは、ADR-0013（QA・タグの書き込みはKnowledge MCP経由に統一する）・ADR-0045（`admin_ui`への`chatbot`データベース資格情報の不付与）という既存の2つの制約を、いずれも上書きする変更になる。
- **任意のSQL実行のリスク**: アップロードされたSQLファイルをサーバー側でそのまま実行する機能は、ファイルの出どころ（正規のエクスポート機能が生成したものか、改変されたものか、全く別のSQLか）を厳密に検証しない限り、悪意ある・誤ったSQLを本番データベースに対して実行してしまうリスクを構造的に抱える。ブラウザ経由（ネットワークレベルの制限のみ、追加のログイン認証なし、ADR-0041）でこの操作を許可することは、既存の読み取り系操作（エクスポート、QA閲覧等）と比べてリスクの質が大きく異なる。

## 決定

**全データインポートは、ブラウザUIからのアップロード機能としては実装せず、運用者が実行する専用の手段（ローカル: `docker compose exec`によるコンテナ内`psql`実行、AWS: ECS Execによる一時タスク実行）を公式の実行手順として整備する。`admin_ui`（`web_backend`）に新たな書き込み権限は付与しない。**

- **ローカル環境**: 運用者が`docker compose exec -T <db_service> psql -U <role> -d <database> < chatbot.sql`（`conversation.sql`も同様）を実行する手順を、READMEに明文化する。実行に使う資格情報は、既存の`chatbot`データベースの管理者権限（ローカル環境は元々`postgres`公式イメージのデフォルト権限を保持、ADR-0046参照）、またはADR-0052で新設するマイグレーターロールを用いる。
- **AWS環境**: 既存のMCP Inspector検証（ADR-0029）と同様、ECS Execによる一時タスクを起動し、タスク内から対象RDSインスタンスへ`psql`で接続してSQLファイルを適用する。実装フェーズにおいて、次のとおり確定した（手順の全文は`README.md`「全データインポート（別環境への投入）> AWS 環境（ECS Exec）」に整備した）。
  - **一時タスクは専用モジュールを新設せず、既存の`db_hiroba_qa_init`タスク定義を流用する**（新規の常駐サービス・ALBエンドポイントを増やさないという方針に沿う）。`aws ecs run-task`で`--enable-execute-command`と、既定CMD（マイグレーション＋シード）を`sleep`で上書きするコンテナオーバーライドを付けて一時起動し、`aws ecs execute-command`で接続する。
  - **SQLファイルの受け渡しはS3経由に確定する**（要件定義書12章 Open Issue #4）。運用者が用意した投入用バケットへエクスポート成果物をアップロードし、コンテナ内から`aws s3 cp`で取得して`psql -f`を適用する。
  - 上記を実行可能にするための前提として、(1) `db_hiroba_qa_init`イメージへの`postgresql-client`・`awscli`の同梱、(2) `db-init-task`のtask roleへの対象バケットの`s3:GetObject`付与、の2点が別途必要になる（本ADRの手順整備の範囲外。イメージ・IAMのコード変更として別途反映する）。
- **将来のUI化への含み**: 本ADRはブラウザUIでの即時実行を否定するものではなく、運用実績を踏まえて「頻繁に必要とされ、かつ安全に自動化できる」と判断された場合に、別途ADRを起こしてUI化を検討する余地を残す（対象外、要件定義書4.2節）。
- **投入対象はSQL形式のダンプに限定する**: CSV形式は`embedding`列を含まず、`chatbot`データベースの完全な再構築ができないため、インポート対象としてはSQL形式のみを正式にサポートする（ADR-0047の設計判断を踏襲）。

## 検討した代替案

- **エクスポートと対称的なブラウザUI（アップロード・実行ボタン）を実装する**: エクスポートと一貫したUXが得られる利点があるが、コンテキストで述べた「`admin_ui`への書き込み権限付与」「任意のSQL実行リスク」が、既存のセキュリティ設計方針（ADR-0013、ADR-0041、ADR-0045、ADR-0046が積み重ねてきた最小権限・経路分離の原則）と正面から矛盾する。エクスポート機能が「読み取り専用ロールの新設」という比較的小さな見直し（ADR-0046）で実現できたのに対し、インポート機能を同水準のUXで実現しようとすると、はるかに大きなセキュリティ上のトレードオフを伴う。本フェーズでは、これを許容してまでUI化する明確な利用頻度・緊急性が確認できていないため、まず運用者向けの手順整備を優先することとした。
- **Knowledge MCPに「ダンプ投入」用の新規ツールを追加する**: ADR-0047が「Knowledge MCPへの全テーブルダンプ用ツール追加」を、エクスポート方向についてすでに「業務ロジックのレイヤーという位置付け（ADR-0006）にそぐわない」として不採用としている。インポート（書き込み）方向はなおのこと、Knowledge MCPに「渡されたSQLをそのまま実行する」という汎用プロキシ機能を持ち込むことになり、同様の理由で不採用とした。
- **`db_hiroba_qa_init`を拡張し、環境変数で「インポートモード」を切り替えて実行する**: `db_hiroba_qa_init`が既にマイグレーション・シード実行の専用ワンショットサービスとして確立していることを踏まえると、一定の合理性はある。ローカル・AWSいずれの案（ECS Exec一時タスク、`docker compose exec`）とも実行形態としては近く、将来的に本ADRの手順をよりコード化・自動化したくなった場合の発展先として有力である。本ADRでは「まず手順として確立する」ことを優先し、`db_hiroba_qa_init`への統合は実装フェーズまたは将来のADR見直しで検討する余地を残す。

## 結果・影響

- `admin_ui`（`web_backend`）には、`chatbot`データベースへの書き込み権限・新規APIエンドポイントを追加しない。既存のADR-0013・ADR-0045の制約はそのまま維持される。
- READMEに、ローカル環境向けのインポート手順（`docker compose exec` + `psql`）を追記済み（`README.md`「全データインポート（別環境への投入）> ローカル環境」）。
- AWS環境向けのECS Execによる一時タスク実行手順（SQLファイルのS3経由受け渡しを含む）をREADMEに整備済み（「同 > AWS 環境（ECS Exec）」）。実際に手順を実行可能にするには、上記「決定」に記した2点の前提（`db_hiroba_qa_init`イメージへの`psql`・`awscli`同梱、`db-init-task` task roleへの`s3:GetObject`付与）を、イメージ・IAMのコード変更として別途反映する必要がある。
- 発注者確認（2026-08-26）により、投入先データベースは常に空の状態であることを前提とし、実行中は対象サービスを停止するメンテナンス時間帯を設けることが決定した（要件定義書2.3節#5・#10）。既存データがある状態への投入は本ADRのスコープ外とする。
