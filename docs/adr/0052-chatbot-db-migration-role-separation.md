# ADR-0052: chatbotデータベースのマイグレーション実行ロールの権限分離

- ステータス: Accepted
- 日付: 2026-08-26
- 関連: `docs/requirement/202608261002_DBマイグレーション・データインポート機能要件定義書.md`, ADR-0016, ADR-0017, ADR-0018, ADR-0046, ADR-0051

## コンテキスト

既存要件定義書（202608061016）13章Open Issue #4は、「現行は`postgres`スーパーユーザーで全処理を行う前提だが、将来的に本番運用を見据えた際、マイグレーション専用ユーザーとアプリケーション用ユーザーを分離すべきかは別途検討課題とする」として、判断を先送りしていた。

現状、`db_hiroba_qa_init`（DDL実行）と`web_backend`/`knowledge_mcp`/`tag_selector_mcp`（DML実行のみで足りるはずのアプリケーション）は、いずれも同一の`DATABASE_URL`（`postgres`スーパーユーザー、または少なくとも同一の高権限ロール）を使って`chatbot`データベースへ接続している（要件定義書202608061016 9.2節）。

一方、直近のADR-0046では、`chatbot`データベースへの「エクスポート専用の読み取り専用ロール」（`chatbot_export_reader`、`SELECT`のみ）を新設し、用途別に最小権限のロールを分離するという先例が既にできている。ADR-0046の理由づけ（最小権限の原則、`admin_ui`が技術的にDDL・書き込みまで実行できてしまう状態を避ける）は、マイグレーション実行ロールとアプリケーションロールの分離にもそのまま当てはまる。

`conversation`データベースについても、ADR-0051によりyoyo-migrationsでの管理に移行するため、同様のロール分離が可能になる。

## 決定

**`chatbot`データベース・`conversation`データベースのそれぞれに、DDL実行権限を持つ「マイグレーター」ロールと、DML（`SELECT`/`INSERT`/`UPDATE`/`DELETE`）のみを実行できる「アプリケーション」ロールを新設し、用途ごとに分離する。**

- **マイグレーターロール**（`chatbot_migrator`・`conversation_migrator`、仮称）: `db_hiroba_qa_init`のみが使用する。`CREATE TABLE`/`ALTER TABLE`/`CREATE EXTENSION`等のDDL権限、および対象データベースの全テーブルへの読み書き権限（シード投入のため）を持つ。
- **アプリケーションロール**（`chatbot_app`・`conversation_app`、仮称）: `web_backend`/`knowledge_mcp`/`tag_selector_mcp`が使用する。対象データベースの全テーブルへの`SELECT`/`INSERT`/`UPDATE`/`DELETE`権限のみを持ち、DDL権限（`CREATE`/`ALTER`/`DROP`等）は付与しない。`ALTER DEFAULT PRIVILEGES`により、マイグレーターロールが将来追加するテーブルにも自動的にこれらの権限が及ぶようにする（ADR-0046の`chatbot_export_reader`と同じ考え方）。
- **既存の`chatbot_export_reader`との関係**: 本ADRが新設する2ロールとは別に、既存の読み取り専用ロールをそのまま維持する。用途（マイグレーション実行／アプリケーションDML／エクスポート読み取り）ごとに3系統のロールを最小権限で使い分ける方針を、`chatbot`・`conversation`両データベースで統一する。
- **ロール作成の実行主体**: 既存の`db_hiroba_qa_init`の起動シーケンスに、ロール作成・権限付与ステップを追加する（`CREATE ROLE IF NOT EXISTS`相当の存在チェックを行い、既存の冪等性方針、ADR-0018を維持する）。
- **ローカル`docker-compose`環境への適用**: ADR-0046がローカル環境ではエクスポート専用ロールの新設を見送った（コストに対して必要性が薄いと判断した）のとは異なり、本ADRのロール分離は、開発時点からアプリケーションコードが「DDL権限がない状態」で正しく動作することを検証できるという開発上の利点があるため、ローカル環境にも適用する。

## 検討した代替案

- **現状維持（単一の`postgres`スーパーユーザーを共用）**: 実装コストがゼロだが、`web_backend`等のアプリケーションコードにSQLインジェクション等の脆弱性が仮に存在した場合、DDL実行（テーブル削除・スキーマ破壊）まで到達可能な状態が残り続ける。本書がマイグレーション・インポート機能を新たに整備する機会に、既存Open Issueとして積み残されていたこの課題も併せて解消することとした。
- **`postgres`スーパーユーザーはマイグレーション専用のまま残し、アプリケーション用ロールのみを新設する（マイグレーター用の新規ロールは作らない）**: 実装範囲を小さくできるが、「スーパーユーザー」という最大権限のロールを`db_hiroba_qa_init`が使い続けることになり、最小権限の原則からは外れる。`db_hiroba_qa_init`はワンショットサービスであり常時稼働しないため攻撃面は限定的だが、統一的なロール設計（3系統に分離する）の一貫性を優先し、マイグレーション専用ロールも新設することとした。
- **ロール分離を`chatbot`データベースのみに適用し、`conversation`データベースは対象外とする**: ADR-0051で`conversation`データベースがyoyo管理下に入るタイミングと合わせて実施する方が、2度手間（先に`chatbot`のみ対応し、後日`conversation`にも同様の変更を行う）を避けられるため、両データベース同時対応とした。

## 結果・影響

- `db_hiroba_qa_init`に、ロール作成・権限付与ステップの追加実装が発生する。
- `docker-compose.yml`・`.env.example`・Terraform（Secrets Manager）の接続文字列が、用途別（マイグレーター用／アプリケーション用）に分かれる。既存の単一の`DATABASE_URL`／`CONVERSATION_DB_URL`という環境変数構成の見直しが必要になる（実装フェーズで確定）。
- `web_backend`/`knowledge_mcp`/`tag_selector_mcp`が誤ってDDLを実行しようとした場合、権限エラーとして早期に検出できるようになる。
- 既存の`chatbot_export_reader`（ADR-0046）には変更を加えない。
- 本ADRを含む本書の方針は、発注者確認（2026-08-26）により承認された。ロール作成対象を将来のデータベース・サービスにどこまで拡張するかは、要件定義書12章Open Issue #1として引き継ぐ。
