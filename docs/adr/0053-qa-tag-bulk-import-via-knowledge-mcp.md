# ADR-0053: QA・タグデータの一括インポート機能の実装方式（Knowledge MCP経由のバッチツール新設）

- ステータス: Accepted
- 日付: 2026-08-26
- 関連: `docs/requirement/202608261002_DBマイグレーション・データインポート機能要件定義書.md`, ADR-0006, ADR-0013, ADR-0014

## コンテキスト

QAタグ管理UI要件定義書（202608060826）4.2節は、「タグ・QAデータの一括インポート/エクスポート（CSV等）」を対象外としていた。現状、QA・タグの登録・更新は、`front_dev`のQA登録・編集フォームから1件ずつ行うほかなく、既存のシードデータ（`db_hiroba_qa_init`が読み込む`CSV_DATA_DIR`配下のファイル）以外の方法でまとまった件数のQAを登録する手段がない。

QA・タグへの書き込みは、ADR-0013により`web_backend`から`chatbot`データベースへ直接行わず、必ずKnowledge MCPサーバのMCPツール（`create_qa`/`update_qa`/`create_tag`等）経由で行う方針が確立している。これは、タグの循環参照チェック等の業務ロジックをKnowledge MCPに一本化し、二重実装による仕様乖離を避けるためである（ADR-0006）。一括インポート機能も、この既存方針との整合を取る必要がある。

## 決定

**Knowledge MCPサーバに、複数件のQA・タグをまとめて登録・更新する新規MCPツール（`import_qa_batch`、仮称）を追加する。`web_backend`はCSVをパースした上でこのツールを呼び出し、`chatbot`データベースへは直接書き込まない。**

- **新規ツールの位置付け**: `import_qa_batch`は、既存の`create_qa`/`update_qa`（`knowledge_mcp/src/knowledge_mcp/mcp/tools.py`、`repository/qa_management_repository.py`）が持つバリデーション・embedding計算・タグ紐付けロジックをループ処理で複数件に適用する薄いラッパーとして実装する（新たな業務ロジックを追加するのではなく、既存の単発処理を束ねる）。
- **`web_backend`の役割**: `front_dev`からアップロードされたCSVファイルの構文解析（列数・必須項目の存在チェック等の機械的なバリデーション）のみを担い、業務的なバリデーション（タグの循環参照チェック等）はこれまで通りKnowledge MCP側に委ねる。
- **部分成功の扱い**: `import_qa_batch`は行単位で成功・失敗を判定し、レスポンスとして行ごとの結果（成功/失敗、エラー内容）を返す。1件のエラーで全体を中断しない（既存の`create_qa`が単発でエラーになった場合の挙動と整合させ、他の行への影響を避ける）。
- **既存ツールへの影響**: `create_qa`/`update_qa`等の既存ツールのシグネチャ・挙動は変更しない。`import_qa_batch`は独立した新規ツールとして追加する。

## 検討した代替案

- **`web_backend`が`chatbot`データベースへ直接バルクINSERTする**: 実装は単純だが、ADR-0013が確立した「QA・タグの書き込みはKnowledge MCP経由に統一する」という既存方針に反する。タグの循環参照チェック・embedding計算等の業務ロジックを`web_backend`側に複製することになり、二重実装のリスク（既存の懸念そのもの）を新たに生む。ADR-0006・0013の原則を維持するため不採用とした。
- **`front_dev`から既存の`create_qa`/`update_qa`を1件ずつ、行数分繰り返し呼び出す（新規ツールを追加しない）**: 実装コストが最小で済む利点があるが、CSVの行数が多い場合にMCP呼び出し回数・レイテンシが線形に増加し、UIの応答性が悪化する。また、行ごとの部分成功・エラー収集のロジックを`web_backend`側で作り込む必要があり、Knowledge MCP側にバッチ処理をまとめる方が責務として自然（既存の単発処理を呼び出す層と業務ロジック層を分離する既存の設計、ADR-0013のBFF構成）と判断し、専用ツールの新設を優先した。
- **`db_hiroba_qa_init`のシード機構（CSV読み込み＋embedding計算、既存）を流用し、コンテナ再作成によって一括投入する**: 既存の仕組みをそのまま使える利点があるが、`db_hiroba_qa_init`はコンテナ初回起動時（データが空の場合）の初期シードを目的としたワンショットサービスであり、稼働中のシステムに対して運用者が任意のタイミングでデータを追加・更新する用途には設計上適さない（コンテナの再作成を伴う操作を、日常的な業務データ登録の手段として使うのは運用上不自然）。ブラウザからのオンデマンド操作という要件（QA管理UIの一部としての一括インポート）に対しては、既存の管理系API・MCPツール経由の方式がより自然と判断した。

## 結果・影響

- `knowledge_mcp`に新規ツール（`import_qa_batch`）とその実装（既存リポジトリ層のループ呼び出し）が追加される。既存の`tools.py`・`qa_management_repository.py`の既存関数には変更を加えない。
- `web_backend`にCSVアップロード受付・パース処理（新規コントローラまたは既存`qa_controller.py`の拡張）が追加される。
- `front_dev`のQA管理画面に、CSVアップロードUIとインポート結果表示（成功件数・行ごとのエラー）が追加される。
- 未知のタグ名は自動的に新規タグとして作成し、既存QAの更新時にCSVへ含まれない項目は既存値を維持する部分更新とすることが、発注者確認（2026-08-26）により決定した（要件定義書2.3節#7・#12）。`import_qa_batch`の実装は、この2点を満たすようリポジトリ層の呼び出しを設計する必要がある。
- CSVフォーマットの詳細（列構成、`tags`列の区切り文字等）は、要件定義書12章Open Issue #2として引き継ぐ。
