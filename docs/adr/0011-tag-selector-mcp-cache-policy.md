# ADR-0011: タグ知識ベースのキャッシュ方針（起動時ロード＋明示的リロード＋定期ポーリング）

- ステータス: Accepted
- 日付: 2026-08-05
- 関連: `docs/requirement/202608051636.md`, ADR-0006, ADR-0008, ADR-0009

## コンテキスト

ADR-0006では、Knowledge MCPサーバは `tag` テーブルの内容を一切キャッシュせず、呼び出しの都度DBを参照する方針としている。これは、Knowledge MCP以外の経路（他の管理ツール・手動SQL等）からの `tag` テーブルへの変更を即座に反映させるためであった。

Tag Selector MCPも同様に、Knowledge MCP側のタグ管理ツールによる `tag` / `tag_alias` テーブルの変更を追従できる必要がある。一方で、Tag Selector MCPはLLM呼び出しの都度タグ一覧をコンテキストに含める（ADR-0009）ため、リクエストごとに都度DBへ問い合わせる方式自体はADR-0006と同様に採用可能ではあるが、**将来Embedding層（ADR-0009で見送ったが将来追加予定）を追加した場合、Embeddingの計算コストが高く、リクエストの都度全タグ分を再計算することは非現実的になる**。この将来要件を見据えたキャッシュ方針をあらかじめ決めておく必要がある。

## 決定

Tag Selector MCPは、起動時に `tag` / `tag_alias`（将来的にはEmbeddingも含む）をメモリへロードし、以後はメモリ上のキャッシュを参照する。キャッシュの更新は次の2つの手段を併用する。

1. **明示的リロード**: `reload_taxonomy` というMCPツールを提供し、呼び出された時点で即座にキャッシュを再構築する。
2. **定期ポーリング**: 一定間隔（環境変数 `TAXONOMY_RELOAD_INTERVAL_SEC`、デフォルト値は詳細設計で確定、参考値300秒）で自動的にキャッシュを再構築する。

## 検討した代替案

- **ADR-0006と同様に完全無キャッシュ（毎回DB参照）とする**: MVP時点（Embeddingなし）では問題にならないが、将来Embedding層を追加した際に性能要件を満たせなくなることが明らかであり、その時点で大きな設計変更（キャッシュ層の後付け）が必要になる。あらかじめキャッシュ方針を組み込んでおく方が手戻りが少ないと判断し採用しなかった。
- **Knowledge MCP側のタグ変更時にイベント通知（Pub/Sub等）でリロードをトリガーする**: 実現できれば変更を即座に反映できるが、現行構成にメッセージング基盤がなく、導入コストがMVPの範囲を超えるため将来検討事項とした。

## 結果・影響

- タグ変更後、最大で `TAXONOMY_RELOAD_INTERVAL_SEC` 分のタイムラグが生じる可能性がある。即時反映が必要な運用（タグ追加直後に選択させたい等）では、Knowledge MCP側でのタグ変更後に `reload_taxonomy` を明示的に呼び出す運用でカバーする。
- ADR-0006（Knowledge MCPは無キャッシュ）とは異なる方針となる。これは、Knowledge MCPが「呼び出しの都度DBを参照するコストが小さい単純な参照」であるのに対し、Tag Selector MCPは「将来Embedding計算という重い前処理を伴う」という性質の違いによるものであり、要件定義書に両者の使い分けの理由を明記する。
- `reload_taxonomy` の呼び出し主体（Knowledge MCP側のタグ変更ツールから自動的に呼び出すのか、運用者が手動で呼び出すのか）は、要件定義書のOpen Issueとして別途整理する。
