# ADR-0036: ネットワーク基盤（VPC・サブネット）の外部管理化 — 既存リソースをdata sourceで参照する

- ステータス: Accepted
- 日付: 2026-08-17
- 関連: ADR-0023, ADR-0026, ADR-0027, ADR-0037, `docs/requirement/202608100910_MCPサーバークライアントAWSデプロイ要件定義書.md`

## コンテキスト

現在の`terraform/modules/network`は、VPC本体・プライベート/パブリックサブネット・ルートテーブル・セキュリティグループ・VPCエンドポイントを一括して新規作成する構成になっている（IMPL-202608101542 §5.1、ADR-0023）。一方で、本プロジェクトのAWS環境には、他プロジェクト・基盤チームが別途運用する既存VPC（プライベートサブネットを含む）が用意されており、これをchatbot_invitroのTerraform構成からも利用したいという要望が生じた。

VPC・サブネットをこの構成自身で新規作成し続けた場合、ネットワーク基盤のライフサイクル（作成・変更・削除）がアプリケーション側のTerraform stateに取り込まれてしまい、次の問題が生じる。

- ネットワーク基盤の管理責任が、本来の管理主体（基盤チーム、または別プロジェクト）とアプリケーション側のTerraformとで二重化する。
- 将来的にネットワーク層とアプリケーション層のstateが混在したままだと、`terraform destroy`等の操作が意図せず共有ネットワーク基盤にまで及ぶリスクを排除しにくい。

検討した選択肢は次の2案。

1. **既存VPC・既存サブネットを外部管理のまま参照する（data source方式）**: VPC・サブネットの実体をこのTerraform構成の管理外に置き、`data "aws_vpc"` / `data "aws_subnet"`（IDまたはタグ検索）で参照値のみを取得する。セキュリティグループ・VPCエンドポイントは、参照したVPC/サブネットのID上に、引き続きこの構成で作成する。
2. **現状維持（このTerraform構成でVPC・サブネットを新規作成し続ける）**: 既存VPCとの統合は行わず、chatbot_invitro専用のVPCを引き続き新規作成する。

## 決定

**既存VPC・既存プライベートサブネットを、このTerraform構成の管理対象外とし、data sourceで参照する（案1を採用）。**

- VPC・サブネットは、`resource`ブロックではなく`data "aws_vpc"` / `data "aws_subnet"`（IDまたはタグ検索）で参照する。`modules/network`から`aws_vpc` / `aws_subnet`（プライベート）の`resource`定義を削除し、参照用のdata sourceに置き換える。
- パブリックサブネット・インターネットゲートウェイ・NATゲートウェイ（`enable_nat_gateway`時のみ作成、ADR-0023）についても、既存VPC側に同等の経路が用意されている場合はそちらを参照する運用とし、本構成側での新規作成は行わない想定とする（既存VPC側にNAT経路が無い場合の扱いは別途確認、下記「結果・影響」参照）。
- セキュリティグループ（`agent_invitro`・`tag_selector_mcp`・`knowledge_mcp`・`rds`・`verification_task`・`vpc_endpoints`）およびVPCエンドポイント（S3ゲートウェイ・Interface型）は、引き続きこのTerraform構成で作成する。これらは参照したVPC ID・サブネットIDに紐づけて作成するため、既存VPC化による変更は「入力元がresourceの出力からdata sourceの出力に変わる」点のみであり、SG・VPCエンドポイントの設計自体（ADR-0023の許可ルール）に変更はない。
- 既存VPC・サブネットの具体的な特定方法（VPC ID直接指定か、タグ名によるフィルタ検索か）、および既存サブネットの空きIPアドレス数・CIDR設計がこの構成の要件（各AZ1サブネット、DBサブネットグループ含む、ADR-0026）を満たしているかの確認は、実装フェーズで基盤チーム（またはVPC管理主体）に確認する。

## 検討した代替案

- **案2（現状維持、専用VPC新規作成）**: このTerraform構成だけで完結し、既存VPCとの整合確認が不要な点はシンプルだが、AWSアカウント内に目的の異なるVPCが複数併存することになり、Peering等の追加設定なしには他プロジェクトのリソースとの接続性が得られない。既存VPCが既に用意されている前提のもとでは、あえて別VPCを増やす理由がなく不採用とした。

## 結果・影響

- `modules/network`は「VPC・サブネットも含めて全て新規作成するモジュール」から「既存VPC/サブネットを参照しつつ、SG・VPCエンドポイントのみを新規作成するモジュール」に役割が変わる。モジュールのvariables（`vpc_cidr`・`availability_zones`等、新規作成前提の入力）は、既存VPC ID・既存サブネットIDを受け取る形に置き換える必要がある（詳細設計・実装フェーズで確定）。
- 既存VPCがどのAWSアカウント・どのTerraform（あるいは手動運用）で管理されているかは本ADRの範囲外であり、参照に必要な最小限の情報（VPC ID、サブネットID、既存のNAT/エンドポイント有無）を運用主体から入手する前提を置く。
- 既存サブネットのCIDR・ルーティングがこの構成の要件（DBサブネットグループに2つ以上のAZ、ADR-0026）を満たさない場合、既存サブネットの一部利用のみで完結できない可能性がある。この点は実装フェーズで既存ネットワーク構成の詳細を確認した上で、必要であれば本ADRを見直す。
- ADR-0023（AWS内部限定・ネットワーク境界方針）が定める到達性の制御方針（SGによる許可ルール）自体には影響しない。VPCの所有・管理主体が変わるのみで、境界方針そのものは維持される。
- 本ADRはADR-0037（Terraform state分割方針）と対になる決定であり、既存VPCを外部管理とすることで、ネットワーク層・DB層・アプリケーション層の3層でstateとリソースオーナーシップの境界を揃えることができる。
