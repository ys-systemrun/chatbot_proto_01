# ADR-0009: MVPのタグ選択アルゴリズム（Embedding層・階層探索は見送り、Alias辞書+LLMの一段階構成とする）

- ステータス: Accepted
- 日付: 2026-08-05
- 関連: `docs/requirement/202608051636.md`, `docs/requirement/202608051630.md`, ADR-0004, ADR-0008

## コンテキスト

参照資料（`docs/requirement/202608051630.md`）では、タグ選択の実現方式として次の6アプローチが検討されている。

1. LLM単体によるタグ分類
2. Embeddingによるタグとの類似度判定
3. LLM + Embedding（候補絞り込み後にLLMで最終判定、参照資料が「おすすめ」とする方式）
4. 階層タグを用いた多段階探索（Best-First Search相当）
5. エージェント型（複数MCPサーバの組み合わせ、責務分離の話であり選択アルゴリズムそのものではない）
6. ルール（Alias辞書等） + LLM のハイブリッド（「企業システムでおすすめ」とされる方式）

一方、実装指示書（`docs/implementation_handoff/202608041013_implementation.md`）に記載のとおり、現行 `tag` テーブルの `parent_tag_id` は全件 `NULL` であり階層構造は未整備である。また、既存QAデータの `tags` 実績（例:「操作方法」「積算システム」「直接費」「調査」等）から見て、タグ件数は現時点では数十件程度と推定され、アプローチ3が想定するような「500タグ規模でLLMに全件渡すのは非効率」という前提は、現状のデータ規模には当てはまらない。

## 決定

MVPでは **アプローチ6（Alias辞書によるルールベース処理 + LLMによる一段階選択）** を採用する。

- Retrieval Engine: `tag_alias` に登録された同義語との一致により、候補タグを即時確定・優先付けする。
- Inference Engine: Embeddingによる候補絞り込みは行わず、タグ一覧（id・name・description）を全件そのままLLMへ渡し、最終的な選択タグとスコアを得る一段階の構成とする。
- 階層構造（`parent_tag_id`）を用いた多段階探索（アプローチ4）は、既存データに階層情報が存在しないため本MVPでは実装しない。

Retrieval Engine はインターフェースとして独立させ、将来タグ件数が増加した際にEmbeddingによる絞り込み層（アプローチ3相当）を追加できる拡張ポイントとして設計しておく。

## 検討した代替案

- **アプローチ1（LLM単体、Alias辞書なし）**: 実装は最小だが、同義語・表記ゆれ（「歩掛」→「積算」等）に弱く、LLMの判定精度のみに依存するため、簡易なAlias辞書を組み合わせるアプローチ6を採用した。
- **アプローチ3（LLM + Embedding）**: 将来タグ件数が数百〜数千件規模に増加した場合には有効だが、現状のタグ件数・階層未整備の状況でEmbedding基盤（ベクトル化・ベクトルストア）を導入するのは、ADR-0004（Knowledge MCPのMVPスコープ限定方針）と同様の考え方に基づき過剰投資と判断し、MVPでは見送った。
- **アプローチ4（階層タグの多段階探索）**: `parent_tag_id` が現状全件 `NULL` であり階層データが存在しないため、実装しても効果を検証できず、本MVPの対象外とした。

## 結果・影響

- MVPの実装・検証範囲を小さく保てるため、リリースまでの期間を短縮できる。
- Retrieval Engineを抽象化しておくことで、将来Embedding層を追加する際もInference Engine・MCP Toolインターフェース（`select_tags`）側の変更を必要としない。
- タグ件数が将来的に増加した場合、全件をLLMへ渡す方式ではコンテキスト長・レイテンシ・APIコストの観点で非効率になる。タグ件数がどの程度に達したらEmbedding層の追加を検討すべきかは、要件定義書のOpen Issueとして管理する。
- 階層探索を実装しないため、`select_tags` のレスポンスの `path` フィールドはMVP時点では常にタグ名1件のみを含む（ADR-0010参照）。
