# ADR-0097: ナレッジデータのバージョン管理に DVC（S3 リモート）を導入し、イメージビルド前の `dvc pull` で同梱する

- ステータス: Proposed（草案）
- 日付: 2026-10-05
- 関連: ADR-0016〜0018（yoyo マイグレーション・シード再実行安全性）、ADR-0030（db_hiroba_qa_init の AWS 展開）、ADR-0034（シード元データのイメージ同梱。本ADRは同梱方針を維持したまま供給元を変更）、ADR-0035（embedding キャッシュ再利用）、ADR-0037 / ADR-0039（Terraform state 分割・2層構成）、ADR-0038 / ADR-0040（`.env` 一元化・デプロイオーケストレーターのコンテナ化）、ADR-0047（全データエクスポート）、ADR-0066（全データインポートの全消去上書き方式）、ADR-0098（命名整理。本ADRの決定以降のパスは同ADR適用後の名称で記載）

## コンテキスト

このチャットボットは、次のループで回答品質を改善していきたい。

1. ローカル（Claude Code）でナレッジデータ・プロンプト・コードを改善する
2. AWS 検証環境へ反映する
3. Bedrock を使い、チャットで実際に試す
4. 結果をリポジトリへ持ち帰り、次の改善につなげる

このループを回すには、**ナレッジデータにどんな改善をしたのかをバージョンで管理し、改善の過程を後から追えること**が前提になる。

一方、現状は次のとおりである。

- シード元データ（`db_hiroba_qa_init/data/` 配下の `exportjson_withguid.json`・`question_altered.csv`・`category.csv`・`trouble_shooting*.html`）は **git の管理外**（未追跡）である。どのデータでいつデプロイしたのかを特定できない。
- ナレッジ DB（`db_chatbot_knowledge_base`）のスキーマに、バージョン列・履歴テーブルはない。
- データファイルは1つあたり 0.2〜5MB 程度で、更新のたびに全体が書き換わる形式である（エクスポート JSON・CSV）。データの性質や機密性の観点からも、**CSV/JSON の本体は git に入れたくない**。
- ADR-0034 により、シード元データは `db_hiroba_qa_init` イメージに同梱されている（`COPY data /data`）。イメージは、デプロイオーケストレーター（ADR-0040）がホストのリポジトリ（`/work` にマウント）をビルドコンテキストにして build / push している。

データ本体を git の外に置きつつバージョン管理する方式として、次を比較した。

- (A) バージョニングを有効にした S3 と自前の manifest
- (B) DVC（リモートに S3 を指定）
- (C) Git LFS
- (D) DB 側の監査トリガーと履歴テーブル

あわせて、B を採用した場合の AWS への反映方式として次の2案を比較した。

- 案1: ビルド前に `dvc pull` してイメージに同梱する
- 案2: ECS タスクが S3 から内容ハッシュを指定して直接取得する

## 決定

**ナレッジデータのバージョン管理には DVC を採用し、データ本体は DVC リモート（専用 S3 バケット）に置く。git には `.dvc` ポインタファイル（内容ハッシュ）だけを記録する。AWS への反映はデプロイオーケストレーターがイメージをビルドする直前に `dvc pull` を行い、ADR-0034 と同じくイメージに同梱する（案1）。**

### 1. 管理対象

| 対象 | 扱い |
|---|---|
| シード元データ（ADR-0098 適用後の `db_init/data/` 配下） | 情報源ディレクトリ単位で `dvc add` し、`db_init/data/hiroba_qa.dvc`・`db_init/data/troubleshooting.dvc` を git で管理する（構成は ADR-0098 §3） |
| リポジトリ直下の `data/`（加工前データ・作業ファイル・評価用 CSV） | 本ADRの対象外。評価ループの設計（別ADR）で扱いを決める |
| 全データインポート用の SQL ダンプ（`terraform/chatbot.sql` など、ADR-0066） | 本ADRの対象外。管理画面での編集結果をスナップショットとして DVC で管理するかどうかは、評価ループの設計とあわせて別途判断する |

- 情報源ディレクトリ単位で管理するので、その情報源の1ファイルでも変われば対応する `.dvc` の md5 が変わる。この md5 を**情報源ごとのデータバージョン識別子**とし、全情報源の md5 の組をシード元データ一式の版とする。
- 意味のある版には git タグ（例: `kb-2026.10.05-1`）を付ける。データの変更理由はコミットメッセージに書く。

### 2. DVC リモート（S3 バケット）

- `terraform/bootstrap`（state バケットと同じ、destroy の対象にならない層）に、DVC リモート専用の S3 バケットを新設する。
  - バージョニングを有効にする
  - パブリックアクセスをブロックする
  - SSE-S3 で暗号化する
  - DVC は内容アドレス形式（`files/md5/<hash>`）でファイルを保存し、既存のオブジェクトを上書きしない。そのため、ライフサイクルで古いバージョンを削除するルールは設けない。
- `.dvc/config` には remote URL だけを書き、git で管理する。認証情報は `terraform/.env` の AWS 認証情報（ADR-0038 / ADR-0040）を環境変数で渡し、`.dvc/config.local` には書かない。

### 3. 実行環境

- `dvc[s3]` と `git` をデプロイオーケストレーターのイメージ（`terraform/deploy/Dockerfile`）に追加する。ホストに Python や dvc を入れる必要がない状態を保つ（ADR-0040 の方針）。
- 開発者が使う操作（`dvc add` / `dvc push` / `dvc pull` / `dvc status` / `dvc diff`）は、`deploy` に dvc のコマンドをそのまま渡すサブコマンドを追加して提供する。呼び出し口として `terraform/dvc.bat` を新設する。
- `/work` にマウントしたリポジトリの所有者がコンテナ内のユーザーと異なると、git の `safe.directory` チェックで失敗する。オーケストレーター側で `safe.directory=/work` を設定して回避する。

### 4. デプロイ時の取得と同梱（案1）

`db_init`（旧 `db_hiroba_qa_init`）イメージを build する全ての経路（現状は `apply-database` の `build_and_push`）で、ビルドの直前に次を行う。

1. `dvc pull db_init/data/*.dvc` で、各 `.dvc` が指すデータを S3 から取得する。
2. `dvc status` でワークスペースのデータが各 `.dvc` と一致しているか確認する。一致しない場合（ローカルで編集したまま `dvc add` していない場合）は**デプロイを中止する**。どのバージョンかを特定できないデータをデプロイしないためである。
3. 取得できなかった場合（誰かが `dvc push` をし忘れて、リモートに実体がない場合）も、ビルド前に中止する。
4. 各情報源の md5 と git の commit hash を、イメージのラベル（`org.opencontainers.image.revision` と独自の `kb.data.<情報源>.md5`）とタスクの環境変数（`KB_DATA_VERSION`。`hiroba_qa=<md5>,troubleshooting=<md5>` の形式）に渡す。

- イメージ内の配置（`COPY data /data`）、`seed_helpers.py` / `db.py` / `main.py` のロジック、`CSV_DATA_DIR` の扱いは **ADR-0034 のまま変更しない**。
- ローカルの docker-compose 環境では、開発者が事前に `dvc pull` しておく。`./data:/data` のマウントで差し替える運用は従来どおり使える。

### 5. 日常の運用フロー

```
(データを編集 / エクスポート結果を配置)
dvc.bat add db_init/data/hiroba_qa          （変更した情報源のみ）
git add db_init/data/hiroba_qa.dvc db_init/data/.gitignore
git commit -m "kb: <変更理由>"
dvc.bat push
git tag kb-YYYY.MM.DD-N          （意味のある版のみ）
apply-database.bat → seed.bat    （データを反映）
```

- 過去の版を再現するときは、`git checkout <tag>` の後に `dvc.bat checkout` を実行する。
- 版どうしの差分は、`dvc.bat diff <旧> <新>` でどのファイルが変わったかまで分かる。中身の差分（QA の追加・変更・削除の件数や ID）を要約するスクリプトは、評価ループ側の別ADRで用意する。

## 検討した代替案

- **(A) バージョニングを有効にした S3 と自前の manifest**
  - 追加ツールが不要で仕組みは最小になる。
  - 一方で、ハッシュ計算・アップロード・取得・整合性チェックを自分で実装する必要がある。また、評価指標とパラメータの比較（`dvc metrics diff`・`dvc exp`）まで含めた改善ループの基盤として、標準ツールの方が長く運用しやすい。
  - 以上から不採用とした。
- **(C) Git LFS**
  - git の操作をほとんど変えずに済む。
  - 一方で、自社管理のホスティングでは LFS ストレージの容量と認証の運用が問題になりやすい。データを AWS の外に置くことにもなり、評価パイプラインとの統合手段もない。
  - 以上から不採用とした。
- **(D) DB の監査トリガーと履歴テーブルだけで管理する**
  - 管理画面での1件単位の編集履歴は残せる。
  - 一方で、シード元データのバージョンや「どのデータ一式でデプロイしたか」は表せない。
  - 単独では不採用とした。管理画面での編集履歴が必要になった場合は、本ADRと併用する形で別途検討する。
- **案2: ECS タスクが S3 から内容ハッシュを指定して直接取得する（イメージに同梱しない）**
  - データだけを更新するときにイメージの再ビルドが不要になる。
  - 一方で、次の作業が新たに必要になる。
    - 新しい取得処理の実装
    - タスクロールへの S3 読み取り権限の追加
    - ADR-0034 の見直し
    - ADR-0018 で「状態を持たないワンショットコンテナ」と位置づけたコンテナが、外部ストレージに依存するようになることの整理
  - 今のデータ量（数 MB）ならイメージの再ビルドの負担は小さい。そのため、まずは変更が最小になる案1を採用し、案2はデータ量や更新頻度が増えたときの発展先とする。
- **ECS タスク内で `dvc pull` する**
  - タスクのイメージに git・dvc・リポジトリのメタデータが必要になり重い。また、タスクに DVC リモートの認証情報を渡す必要も出る。
  - 以上から不採用とした。

## 結果・影響

- **デプロイしたデータを特定できるようになる。**
  - 各情報源の `.dvc` の md5 と git の commit で、シード元データの版を一意に特定できる。
  - イメージのラベルとタスクの環境変数にも残るので、AWS 上で今どの版が動いているかを確認できる。
  - 回答と評価を版に結び付けること（会話 DB への `release_id` 記録など）は、評価ループの別ADRで扱う。
- **データ本体は git の外（S3）に置かれ**、リポジトリの肥大化と機密データの混入を避けられる。
- **運用上の新しい注意点**として、`dvc push` を忘れると他の開発者やデプロイが `dvc pull` できない。デプロイ時はビルド前に中止されるので、壊れたイメージは作られない。手順書（`terraform/README.md`）に、push まで含めた手順を明記する。
- **実装時の変更点**
  - `terraform/bootstrap`: DVC リモート用の S3 バケットを追加する。
  - `terraform/deploy/Dockerfile`: `dvc[s3]` と `git` を追加する。
  - `terraform/deploy/src/commands.py`: dvc パススルーのサブコマンドと、ビルド前の pull・status 検証・ラベル付与を追加する。
  - `terraform/dvc.bat`: 新設する。コメントは英語で書く。
  - リポジトリ直下: `dvc init` で `.dvc/` を作り、`db_init/data/hiroba_qa.dvc`・`db_init/data/troubleshooting.dvc` を作成する（ADR-0098 のディレクトリ整理の後に行う）。
  - `terraform/README.md`: 手順を追記する。
- ADR-0034 の同梱方針と読み込み処理は変わらない。変わるのは「ビルドコンテキストの `data/` をどこから持ってくるか」だけである。
- 将来、本番相当のデータ量や更新頻度になった場合や、データだけを即時に反映したくなった場合は、案2（タスクが S3 から直接取得する方式）への移行を別ADRで検討する。
