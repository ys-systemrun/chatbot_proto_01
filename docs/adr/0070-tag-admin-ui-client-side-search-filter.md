# ADR-0070: タグ管理画面・タグ選択UIへの検索・絞り込み機能の追加（クライアント側フィルタ方式）

- ステータス: Accepted
- 日付: 2026-09-02
- 関連: `docs/requirement/202609021050_タグ運用ガイドライン.md`、`docs/requirement/202609021102_タグ管理画面・タグ選択UI改修要件定義書.md`、ADR-0006

## コンテキスト

`TagPicker`（QA編集フォーム・タグ階層ページ双方から利用）・`TagTreePage`（タグ管理画面）は、`list_tags`が返すツリーをインデント付きの平坦なリストとして全件表示するのみで、フリーテキストによる絞り込み手段を持たない。タグ運用ガイドライン（202609021050）が指摘した通り、タグ件数が数十〜百件規模に増えると目的のタグを一覧から探しづらくなる。

`list_tags`は現状パラメータなしで`tag`テーブル全件を1クエリで読み込み、階層構造（ツリー）に組み立てて返す設計（`TagRepository.list_tags`、キャッシュしない方針、ADR-0006）になっており、`TagPicker`・`TagTreePage`はいずれもこの全件レスポンスをフロントエンドで保持している。

## 決定

**タグの検索・絞り込みは、新規のバックエンドAPI・SQLを追加せず、`TagPicker`・`TagTreePage`が既に保持している`list_tags`の全件レスポンスに対する、フロントエンド（クライアント側）でのフィルタ処理として実装する。**

- 絞り込みの一致対象は、タグ名（部分一致・大文字小文字を区別しない）およびエイリアス名（同条件）とする。
- 一致したタグは、そのタグ自身に加え祖先タグ（親を辿った経路）をパンくず形式で表示する。絞り込みでヒットしないタグ・その他の兄弟タグは、絞り込み中は非表示にする（該当タグの祖先のみ表示を維持する）。
- 絞り込み未実施時（全件表示時）は、既存のインデント表示をそのまま維持する。

## 検討した代替案

- **バックエンドに新規の検索APIを追加する（SQL `LIKE`検索、または`pg_trgm`等を用いた全文検索）**: タグ件数が将来大きく増加した場合のスケーラビリティには優れるが、現状のタグ件数（数十〜百件規模）に対しては、新規エンドポイント・SQL・MCPツールの実装・テストコストに見合わないと判断し、MVPでは不採用とした。タグ件数が数千件規模になった場合は、本ADRの前提（全件クライアント側フィルタ）を見直す必要がある（結果・影響参照）。
- **`tag_alias`同様、専用の全文検索基盤（`pg_trgm`拡張等）を導入する**: 上記と同じ理由に加え、`tag`/`tag_alias`という軽量なマスタテーブルに対して専用の検索基盤を導入するのは過剰投資と判断し見送った。

## 結果・影響

- `list_tags`のMCPツール・APIレスポンス形式には変更を加えない。`TagPicker.tsx`・`TagTreePage.tsx`への検索欄・フィルタロジックの追加のみで完結する。
- `knowledge_mcp`・`web_backend`のバックエンド側には変更が発生しない。
- タグ件数が今後大幅に増加し、全件クライアント側フィルタでは性能・操作性が成立しなくなった場合は、本ADRを見直しバックエンド検索APIの追加を別途検討する必要がある（要件定義書202609021102 Open Issue該当なし、本ADRで新たに記録する将来課題）。
