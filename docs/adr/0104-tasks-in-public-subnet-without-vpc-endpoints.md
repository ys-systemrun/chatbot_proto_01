# ADR-0104: VPC エンドポイントを廃止し、ECS タスクをパブリックサブネットにパブリック IP 付きで置いてインターネット経由で AWS サービスへ接続する

- ステータス: Proposed（実装済み。パブリックサブネットで apply-database・apply-app を実行し、タスクの起動とシードが通ることを確認したら Accepted にする）
- 日付: 2026-10-21
- 関連: ADR-0023（AWS 内部限定のネットワーク境界。本 ADR がタスクの配置について一部を上書き）, ADR-0036（既存 VPC・サブネットの data 参照。本 ADR が VPC エンドポイントについて上書き）, ADR-0041（admin_ui の ALB。「ALB のみ公開」は維持）, ADR-0095（単一 AZ・単一サブネット配置。本 ADR でエンドポイントの部分を廃止）, ADR-0103（退避付き一括破棄。本 ADR の実装を先に行う）

## コンテキスト

database 構成の `modules/network` は、既存 VPC・サブネットを data source で参照したうえで（ADR-0036）、NAT を持たないプライベートサブネットに置いた ECS タスクから AWS サービスへ到達するために、VPC エンドポイントを作成していた。

| 種別 | サービス | 用途 |
|---|---|---|
| Gateway | `s3` | ECR のイメージレイヤ取得、import バケット（ADR-0066） |
| Interface | `ecr.api`・`ecr.dkr` | イメージの pull |
| Interface | `logs` | CloudWatch Logs への出力 |
| Interface | `secretsmanager` | 接続文字列などのシークレット取得 |
| Interface | `ssm`・`ssmmessages` | ECS Exec |
| Interface | `bedrock-runtime` | Bedrock の呼び出し |

あわせて、Interface エンドポイント用のセキュリティグループ（`<name_prefix>-sg-vpce`）も作っていた。作成は変数 `create_vpc_endpoints` で切り替えられた。

この VPC は、検証用 AWS アカウントの中で他のプロジェクト（`izumiv8-*` など）と共用している。エンドポイントを本プロジェクトの Terraform が持っていると、次の問題がある。

- **プライベート DNS の競合**: プライベート DNS を有効にした Interface エンドポイントは、1 つの VPC に 1 サービスにつき 1 つしか作れない。他のプロジェクトが先に作っていると、本プロジェクトの `apply` が失敗する。
- **巻き添えの削除**: `destroy-database` でエンドポイントも消えるため、同じエンドポイントを使う他のプロジェクトの通信も止まる。
- **費用**: Interface 型 7 種 × 1 AZ で月額約 $51 かかる（ADR-0095）。検証環境の固定費の大きな部分を占める。

最初は「エンドポイントを Terraform の管理から外し、コンソール等で共用のものを作って参照する」方式を検討し、実装まで行った（apply はしていない）。しかし、共用エンドポイントの作成・調整の手間と費用が残るため、エンドポイント自体を使わない方式に切り替えることになった（2026-10-21、発注者の判断）。

エンドポイントを使わずに AWS サービスへ到達する方法は 2 つある。

- **NAT ゲートウェイ**: タスクはプライベートサブネットのまま。固定費は月約 $33 で、加えて通信量 1 GB あたり $0.045 かかる。
- **パブリックサブネット＋パブリック IP**: タスクがインターネットゲートウェイ経由で直接接続する。費用はパブリック IPv4 アドレス代（1 個 $0.005/時）だけ。

既存 VPC には、admin_ui の ALB を置くパブリックサブネット（`public_subnet_ids`, ADR-0041）がすでにある。

なお、本 ADR の時点で、Terraform が作っていたエンドポイント（`chatbot-invitro-vpce-*`）は削除済みである。

## 決定

**VPC エンドポイントを廃止する。ECS タスク（集約サービス）と run-task は、パブリックサブネットにパブリック IP 付きで置き、ECR・CloudWatch Logs・Secrets Manager・SSM・Bedrock・S3 へはインターネットゲートウェイ経由で接続する。外から入ってくる通信は、タスク用セキュリティグループのインバウンドだけで止める。RDS はプライベートサブネットのままにする。**

1. **タスクの配置**: タスクを置く単一サブネット（`workload_subnet_id`, ADR-0095）を、パブリックサブネットにする。未指定のときの既定は `public_subnet_ids` の先頭にする（従来は `private_subnet_ids` の先頭）。`private_subnet_ids`（2 AZ）は、RDS の DB サブネットグループ専用として残す。
2. **パブリック IP**: 集約サービス（`modules/ecs-app-task` の `assign_public_ip`）と、オーケストレータの run-task（`deploy/src/aws.py`。seed・migrate・import-data・query・今後の export）を、パブリック IP を付けて起動する。README に書いた手動の run-task（seed・MCP Inspector）の例も `assignPublicIp=ENABLED` にする。
3. **エンドポイントの廃止**: `modules/network` から VPC エンドポイント（S3 Gateway・Interface 7 種）、エンドポイント用のセキュリティグループとそのルールを削除する。変数 `create_vpc_endpoints` も削除する。本プロジェクトにエンドポイントを作る経路も参照する仕組みも残さない。
4. **state の移行**: 旧エンドポイントは削除済みのため、`removed { from = ...; lifecycle { destroy = false } }` で state の記録だけを外す（記録が無ければ何も起きない）。旧エンドポイント用のセキュリティグループとそのルールは、使うものが無くなったので通常どおり Terraform で削除する。すべての環境で 1 回 `apply-database` を実行した後、`removed` ブロックは削除してよい。
5. **経路の照合**: `modules/network` で、ワークロードサブネットが使うルートテーブルを取得する。明示的な関連付けが無ければ、VPC のメインルートテーブルを使う。そのルートテーブルに `0.0.0.0/0 → インターネットゲートウェイ（igw-*）` の経路があることを、`postcondition` で `plan` の段階に確かめる。
   - 無ければ、サブネット ID とルートテーブル ID を示して止まる。何も作成されないうちに止まる。
   - 以前の設定のまま `workload_subnet_id` にプライベートサブネットを指定している場合も、ここで止まる。
   - ワークロードサブネットが決まらない場合（`workload_subnet_id` も `public_subnet_ids` も無い）も、`precondition` で止める。
6. **外からの通信の扱い**: タスクはインターネットから到達できるアドレスを持つ。入ってくる通信を止めるのはセキュリティグループだけになる。
   - 集約タスク用 SG（`<name_prefix>-sg-app-task`）は、今までどおり ALB（admin_ui のポート）と検証タスク（MCP のポート）からのインバウンドだけを許可する。
   - 検証タスク・db_init 用 SG はインバウンドを一切許可しない。
   - インターネット（`0.0.0.0/0` など）からのインバウンドルールを追加しないことを、コードのコメントと README に明記する。
   - ADR-0041 の「公開するのは ALB だけ」という方針は変えない。
7. **送信**: タスク用 SG の送信は、今までどおりすべて許可する。AWS サービスへの 443 もこれで賄う。

## 検討した代替案

- **エンドポイントを Terraform の管理から外し、コンソール等で作った共用のものを data source で参照する**: 閉域のまま、プロジェクト間の競合と巻き添えの削除を避けられる。不足していれば `plan` で止める照合まで実装した。しかし、共用エンドポイントを作る手間・他のプロジェクトとの調整・月約 $51 の費用は残る。発注者の判断で、エンドポイント自体を使わない方式に切り替えた。閉域が必要になった場合は、この方式に戻すのが第一候補になる。
- **NAT ゲートウェイを使う（タスクはプライベートサブネットのまま）**: タスクがパブリック IP を持たず、ADR-0023 の閉じた配置を保てる。しかし固定費が月約 $33 かかる。加えてイメージの pull（4 イメージ）やログの通信量に応じた費用がかかる。NAT も VPC の共有部品で、他のプロジェクトと調整が必要になる。採らない。
- **Interface エンドポイントは廃止し、無料の S3 Gateway エンドポイントだけ残す**: S3 への通信を VPC 内に閉じられる。しかしパブリック IP 経由でも、同一リージョンの S3 への通信に追加の費用はかからない。また、Gateway エンドポイントもルートテーブルに関わる VPC の共有部品で、管理と競合の問題が残る。採らない。
- **パブリック IP は付けず、IPv6（Egress-only インターネットゲートウェイ）で外に出る**: インバウンドを経路の段階で遮断できる。しかし、既存 VPC・サブネットの IPv6 対応と、ECR・Bedrock などの各サービスのデュアルスタック対応を確かめる必要がある。検証環境には過大なので、採らない。

## 結果・影響

- エンドポイント（月約 $51）も NAT も不要になる。かかるのはパブリック IPv4 アドレス代だけで、常駐タスク 1 つで月約 $3.6、run-task は動いている間だけかかる。他のプロジェクトとの競合と巻き添えの削除もなくなる。
- ADR-0023 の「プライベートサブネットに置き、インターネットゲートウェイ経由の外部公開を行わない」のうち、**タスクの配置**を上書きする。タスクはインターネットから到達できるアドレスを持つ。ただし入ってくる通信はセキュリティグループで ALB・検証タスクからに限っており、MCP サーバ・agent_invitro への AWS 外からの直接アクセスを許さないという ADR-0023 の目的は保つ。そのぶん、セキュリティグループの設定を誤ったときの影響が大きくなる。インターネットからのインバウンドルールは追加しないこと。
- AWS サービスへの通信は、VPC 内の閉じた経路ではなく、インターネットゲートウェイ経由で公開エンドポイントへ向かう。TLS と IAM 認証は変わらない。ネットワークを閉域で完結させる要件がある環境（本番など）には、この方式を使わない。その場合は代替案の 1 つ目（外部管理のエンドポイントを参照）か NAT にする。
- RDS はプライベートサブネットに残り、パブリックアクセスも無効のままである。タスクから RDS への通信は VPC 内で届き、セキュリティグループのルールも変わらない。
- 既存環境の移行では、まず `TF_VAR_workload_subnet_id` をパブリックサブネットに変える（または削除して `public_subnet_ids` の先頭を使う）。そのあと `apply-database` → `apply-app` を実行する。集約サービスは、パブリック IP 付きの新しいタスクに置き換わる。
- `modules/network` の役割は「SG と VPC エンドポイントを作る」から「タスク・RDS・ALB 用の SG を作り、タスクを置くサブネットの経路を照合する」に変わる。`terraform/README.md`・`terraform/.env.example`・`deploy/src/commands.py` の表示文言を合わせて更新する。
- ネットワーク構成図（`docs/network_diagram/`）を更新するときは、エンドポイントを消し、タスクをパブリックサブネットに描く。
- `removed` ブロックは移行のための一時的なもので、すべての環境で 1 回 `apply-database` を実行した後に削除する。
