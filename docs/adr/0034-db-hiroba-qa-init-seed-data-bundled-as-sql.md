# ADR-0034: db_hiroba_qa_init のシード元データ（CSV/JSON）をイメージに同梱する

- ステータス: Accepted
- 日付: 2026-08-12
- 関連: `docs/requirement/202608061016_DBマイグレーションシード自動化要件定義書.md`（7.3節）, `docs/requirement/202608100910_MCPサーバークライアントAWSデプロイ要件定義書.md`（6.8節）, ADR-0016, ADR-0017, ADR-0018, ADR-0030, ADR-0031

## コンテキスト

現行、`db_hiroba_qa_init` のシード元データ（`category.csv` / `exportjson_withguid.json` / `question_altered.csv`）は、リポジトリ直下の `data/` ディレクトリに置かれ、`docker-compose.yml` の `./${CSV_DATA_DIR:-data}:/data` というホストパスのボリュームマウントで供給されている。`db_hiroba_qa_init` のビルドコンテキストは `./db_hiroba_qa_init` であり、`data/` はそのコンテキスト外にある。読み込みは `seed_helpers.py` がCSV/JSONをパースし、`db.py` がテーブル単位の存在チェック（ADR-0018）を経てINSERTする方式である。一方、スキーマ作成（マイグレーション）は既にSQLファイル（`db_hiroba_qa_init/migrations/0001〜0005*.sql`）としてイメージに同梱済みで、`COPY . .`（Dockerfile）によりビルド時にイメージへ取り込まれている。

ADR-0030では、RDS移行に伴い `db_hiroba_qa_init` をAmazon ECR + ECS Fargate Run Taskとして「既存のDockerイメージをそのまま利用する」方針を決定したが、この時点では上記のホストボリュームマウントによるシード元データ供給がECS Fargate環境で機能しないという点は検討対象になっていなかった。ECS Fargateタスクには、開発者のローカルリポジトリ（`data/` ディレクトリ）へアクセスする手段が存在しないため、AWS環境で `db_hiroba_qa_init` を実行するには、シード元データの供給方法を別途用意する必要がある。これはADR-0030の「結果・影響」節で「実行手順は実装フェーズで確定する」として保留されていた事項の一部にあたる。また、`docs/requirement/202608061016.md` 7.3節では「データソース自体の変更は本書の対象外」と明記されており、本ADRはその後続の設計判断として位置づけられる。

対応方式として、シードデータをSQL（`INSERT`文）に変換してマイグレーションと同じ形式でイメージに同梱する案（SQL化案）と、既存のCSV/JSONファイルをフォーマット変更なしにそのままイメージへ`COPY`する案（同梱化案）を比較検討した。

SQL化案は、`category` / `qa_original` については投入時に外部API呼び出しを伴わないため技術的に成立するが、以下の理由から実装コスト・リスクが見合わないと判断した。

- CSV/JSONからSQLへの変換処理（変換スクリプト）を新たに実装する必要がある。
- `qa_original` の質問文・回答文は自由記述テキストであり、SQLリテラルへのエスケープ（引用符・改行・Unicode等）を正しく行う必要があるため、CSV/JSONのまま扱う場合より不具合の余地が増える。
- 約1,150件相当の`INSERT`文になる見込みで、生成後のSQLファイルは人間がレビューするには不向きであり、データ1件の変更でも差分が大きくなりがちである。
- `question_altered` は埋め込みAPI呼び出し（ADR-0031でlmstudio/bedrock切り替え）を伴うためSQL化の対象外とせざるを得ず、この方式では当該テーブルのシード元データ供給という課題がAWS環境で未解決のまま残ってしまう。

## 決定

**シード元データ（`category.csv` / `exportjson_withguid.json` / `question_altered.csv`）を、フォーマットを変更せずそのまま `db_hiroba_qa_init` のDockerイメージに同梱する。**（発注者確認済み）

- 3ファイルとも、既存フォーマット（CSV/JSON）のまま `db_hiroba_qa_init` のビルドコンテキスト内に配置し、Dockerfileの `COPY` でイメージに含める。配置場所（例: `db_hiroba_qa_init/data/` 等の新設、またはビルドコンテキスト自体をリポジトリルートに広げる案との比較）は実装フェーズで確定する。
- `seed_helpers.py` によるCSV/JSONパース、`db.py` によるテーブル単位の存在チェック（ADR-0018）・INSERT処理は変更しない。変わるのは読み込み元パス（ホストボリュームマウント経由 → イメージ内に焼き込まれたパス）のみとする。
- `question_altered` は引き続き、投入時に埋め込みAPI（`EMBEDDING_PROVIDER` に応じてLM StudioまたはAmazon Bedrock、ADR-0031）を呼び出してベクトルを計算する現行方式を維持する。データの供給方法（イメージ同梱）のみが変わり、埋め込み計算のロジック自体には影響しない。
- `CSV_DATA_DIR` 環境変数は、イメージ内の固定パスを指す既定値に変更する想定（ローカル開発でホストの `data/` ディレクトリを差し替えたい場合の運用は、実装フェーズで別途整理する）。

## 検討した代替案

- **SQL化案（`category` / `qa_original` のみをSQLに変換してイメージに同梱、`question_altered` は現行方式を維持）**: マイグレーション（SQL）とデータ投入（SQL）の形式が揃うという一貫性の利点はあるが、コンテキストで述べた変換処理の実装コスト・自由記述テキストのエスケープリスク・生成SQLのレビュー困難さに加え、`question_altered` のシード元データ供給という課題がAWS環境で未解決のまま残る点を踏まえ、不採用とした。
- **現状のCSV/JSON方式を維持し、AWS側にEFS等の共有ストレージを追加してシード元データを供給する**: `db_hiroba_qa_init` 自体のロジック変更が不要という利点はあるが、ADR-0030が前提とした「既存のDockerイメージをそのまま利用する（追加インフラを増やさない）」という方針と整合しない。また、ADR-0018で `db_hiroba_qa_init` を「状態を持たない、揮発してよいワンショットコンテナ」と位置づけた設計思想に対し、外部共有ストレージへの依存を新たに追加することになり好ましくないため見送った。

## 結果・影響

- `db_hiroba_qa_init` のビルドコンテキストに、3ファイル分のシード元データ（現行 `data/category.csv` 477B・`data/exportjson_withguid.json` 約1.1MB・`data/question_altered.csv` 約590KB相当）を新たに配置する必要がある。配置方法（ビルドコンテキストの変更、ファイルのコピー/移動）は実装フェーズで確定する。
- `docker-compose.yml` の `db_hiroba_qa_init` サービスにおける `./${CSV_DATA_DIR:-data}:/data` ボリュームマウントは不要になる可能性がある（ローカル開発でのデータ差し替え運用を残すかどうかは実装フェーズで確定）。
- `seed_helpers.py` / `db.py` / `main.py` のロジック自体には変更が不要であり、SQL化案と比べて実装リスクが低い。
- イメージサイズがわずかに増加する（3ファイル合計で数MB程度）。ECRへのpush/pull対象になる点は許容範囲と考えられるが、本検証（MVP）は最小限のQA・タグデータのみを対象とする前提（要件定義書7章）であることを踏まえ、将来的に本番相当データを扱う場合はイメージへのデータ同梱方式自体を再検討する必要がある（例: 本番データは機密性・更新頻度の観点でイメージに焼き込まず、別の配布方式に切り替える等）。
- ローカルdocker-compose環境でも同じイメージ・同じシード元データが使われるため、ローカル/AWS間でのシードデータの差異が生じにくくなる。
- マイグレーション（SQL）とシード（CSV/JSON）とで形式・実行経路が異なる状態は変わらない（ただしこれはADR-0016〜0018時点からの既存の前提であり、本ADRによる新たな影響ではない）。
