# ADR-0022: `agent_invitro` のグラフ構造（自律的ReActエージェント方式を採用）

- ステータス: Accepted
- 日付: 2026-08-06
- 関連: `docs/requirement/202608061621.md`, ADR-0019, ADR-0020, ADR-0021

## コンテキスト

`agent_invitro` のLangGraphグラフをどのように構成するかについて、要件定義書（`docs/requirement/202608061621.md`）6.1節では次の2方式を検討していた。

- **方式A（自律的ReActエージェント）**: `select_tags` と `search_knowledge` の両方をツールとしてLLMに束縛（bind）し、LLM自身がいつ・どの順でツールを呼ぶか、いつ最終回答とするかを判断する（LangGraphの `create_react_agent` 相当のReActループ）。
- **方式B（固定シーケンス）**: グラフのノード・エッジを `select_tags` → `search_knowledge` → 回答生成の順に固定し、LLMにツール選択の自由度を与えない。

本ADR起票時点では要件定義書 Open Issue #1として未決定だったが、発注者より方式Aを採用する方針が示された。

## 決定

`agent_invitro` のグラフ構造は **方式A（自律的ReActエージェント）を採用する**。`select_tags`（Tag Selector MCP）・`search_knowledge`（Knowledge MCP）の両ツールをLLMに束縛し、ツール呼び出しの有無・順序・回数、および最終回答とするタイミングをLLM自身の判断に委ねる。

`docs/requirement/202608051636.md` 5.1節・本要件定義書5.1節のアーキテクチャ図（Tag Selector MCP → Knowledge MCPの順）は、方式Aのもとでの「期待される呼び出し順序」として位置づける。実際にその順で呼ばれるかどうかは固定されず、要件定義書6.4節の手動テストクエリによる動作確認で確認する。

## 検討した代替案

- **方式B（固定シーケンス）**: `select_tags` → `search_knowledge` → 回答生成の順にグラフを固定する。既存アーキテクチャ図に忠実で、動作確認・デバッグが容易（呼び出し順序が保証されるため、ツール呼び出し自体の成否のみに着目して検証できる）という利点がある。しかし、本実験の目的である「LangGraphで動作するMCPホスト」の検証、すなわちLLMが自律的に複数のMCPツールから適切なものを選択・呼び出す能力の確認にはならないため、不採用とした。

## 結果・影響

- LangGraphの実装は `create_react_agent`（または同等のReActループ）を用い、`select_tags` と `search_knowledge` をツールとして同時にLLMへ束縛する構成になる。
- LLMがツール呼び出し方式（Tool Calling / Function Calling）に対応していることが前提となるため、要件定義書 Open Issue #3（ロード済みLLMモデルのFunction Calling対応可否）の重要度が上がる。対応していない場合、方式Aはそのままでは機能しない可能性があり、プロンプトベースの疑似Function Calling等の代替実装が必要になる。
- 方式Bと異なり、LLMの判断ミスにより期待順序と異なる呼び出しや、不要なツール呼び出し・呼び出し漏れが発生する可能性がある。この残存リスクへの対応方針（許容するか、システムプロンプトでガードレールを設けるか等）は要件定義書 Open Issue #6に記録し、実験フェーズの動作確認結果を踏まえて判断する。
- 6.4節の動作確認シナリオでは、ツール呼び出しのログ（呼び出されたツール名・引数・順序）を必ず出力し、期待順序との一致・不一致を目視で確認できるようにする。
