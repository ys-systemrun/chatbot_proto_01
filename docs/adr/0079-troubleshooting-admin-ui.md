# ADR-0079: トラブルシューティング記事管理UIの実装方式

- ステータス: Accepted
- 日付: 2026-09-07
- 関連: `docs/requirement/202609071337_トラブルシューティング情報源追加要件定義書.md`, ADR-0013, ADR-0014, ADR-0015, ADR-0076

## コンテキスト

ADR-0076によりトラブルシューティング記事用テーブル（`troubleshooting_article`・`troubleshooting_article_tag`）が新設される。記事の初期投入はHTMLインポート（要件定義書10章）で行われるが、投入後のタグ付け（キーワード欄の記入率が低く自動タグ化ができないため、タグ運用ガイドラインREQ-202609021050に従った人手でのタグ付けが前提）と、内容の継続的な編集（現象・原因・案内内容等の追記修正）を行うための手段が必要になる。

既存のQA管理UI（`front_dev/feature/qa_admin`・`web_backend/main/controllers/qa_controller.py`）およびタグ管理UI（`feature/tag_admin`・`tag_controller.py`）は、既にADR-0013（QA・タグ書き込みはKnowledge MCP経由）・ADR-0014（QA管理ツール）・ADR-0015（管理画面ルーティング）に基づく確立されたパターンを持つ。発注者に、この管理UI拡張を今回の要件定義スコープに含めるかを確認したところ、含める方針を確認した。

## 決定

**既存のQA管理UI・タグ管理UIと同一の構成パターンで、トラブルシューティング記事専用の一覧・編集・タグ付け管理UIを新設する。新規作成・削除は初期スコープに含めず、一覧・詳細編集・タグ付けに限定する。**

1. **バックエンド**: `web_backend/src/main/controllers/troubleshooting_controller.py`を新設し、一覧取得・詳細取得・更新・タグ付けのAPIエンドポイントを提供する。QA管理と同様、書き込みは`knowledge_mcp`経由（ADR-0013の方針を踏襲）とするか`web_backend`が直接DBを扱うかは、既存のQA管理・タグ管理それぞれの経路（QAはADR-0013でMCP経由、タグもMCP経由）に倣い、実装フェーズで確定する。
2. **フロントエンド**: `front_dev/src/feature/troubleshooting_admin/`に一覧ページ・編集ページを新設する。編集ページのタグ付けUIは、既存のタグツリー選択コンポーネント（タグフォルダ階層・検索絞り込みを含む、ADR-0070〜0074で拡張済みのもの）をそのまま再利用する。ルーティングは既存の管理画面サブツリー（ADR-0015）に追従させる。
3. **新規作成・削除は対象外**: 記事の新規追加は要件定義書10章のHTMLインポート処理のみを経路とし、管理UIからの新規作成・削除機能は初期スコープに含めない。削除が必要になった場合はQAレコード削除機能（ADR-0067）と同様のカスケード削除設計を要する別要件とする。
4. **API/UI命名**: DB層の`troubleshooting_`接頭辞をAPIパス・ルート・feature/domainディレクトリ名にそのまま反映する（例:`/api/troubleshooting_articles`、`front_dev/src/feature/troubleshooting_admin/`）。冗長性が問題になる場合はQA・タグと同様に詳細設計フェーズで見直す。

## 検討した代替案

- **管理UIを新設せず、初期スコープはインポートスクリプト＋DBスキーマ整備のみに留める**: 実装範囲を最小化でき、本要件を「データ基盤整備」に集中できる。タグ付けはSQL直接実行や簡易スクリプトで代替可能。しかし、タグ運用ガイドライン（REQ-202609021050）が前提とする継続的な人手でのタグ付け・見直し作業を、管理UIなしで運用チームが安全に行うのは現実的でない（SQL直接操作は誤操作リスクが高く、既存のQA・タグ管理UIが提供する検索・階層表示等の支援機能を失う）。発注者は今回のスコープに含めることを選択した。

- **既存のQA管理UI（`feature/qa_admin`）にトラブルシューティング記事も統合表示する（データソース種別で切り替えるタブ形式等）**: 画面数を増やさずに済む。しかしQAとトラブルシューティング記事は保持する構造化フィールドが大きく異なり（現象・原因・エラーメッセージ等 vs 質問文・回答文）、統合すると編集フォームの複雑化・条件分岐の増大を招く。既存の`feature/tag_admin`のように独立した画面として新設する方が、既存パターンとの整合性・保守性の両面で優れるため不採用とした。

## 結果・影響

- `front_dev`に新規`feature/troubleshooting_admin/`・`domain/admin/troubleshooting.ts`が追加され、`routes.tsx`・`api.ts`に対応するエントリが追加される。
- `web_backend`に新規`troubleshooting_controller.py`が追加される。
- タグ付けUIは既存コンポーネントの再利用のため、タグフォルダ階層・表示順序（ADR-0072〜0074）の変更の影響をトラブルシューティング記事側も同様に受ける（望ましい一貫性）。
- 監査ログのエンティティ種別ラベル（例:`"troubleshooting_article"`）の追随要否は詳細設計フェーズで確定する（要件定義書 Open Issue #3）。
- 新規作成・削除機能が必要になった場合は、本ADRの対象外として別途要件化する。
