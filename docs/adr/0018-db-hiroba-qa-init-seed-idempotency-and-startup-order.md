# ADR-0018: シード実行制御方式（存在チェックによる冪等性）と起動順序制御方式

- ステータス: Accepted
- 日付: 2026-08-06
- 関連: `docs/requirement/202608061016.md`, ADR-0016, ADR-0017

## コンテキスト

要件として、「シードが毎回は回らないように `db_nomic/data` 等にデータ実体を保存する」ことが求められている。現行、`web_backend` の `seed` 系スクリプトは、テーブル単位の存在チェック（`DB.exists_category` / `exists_qa_original` / `exists_question_altered`）により、既にデータが存在するテーブルへの再投入をスキップする冪等性を既に持っている。また、`db_hiroba_qa` のPostgreSQLデータディレクトリは `./${DB_DIR}/data` にバインドマウントされており、`docker compose down` / `up` を跨いでデータが永続化されている。

一方、シードが `db_hiroba_qa_init`（ADR-0016）によって `docker compose up` のたびに自動実行されるようになるため、①シードを再実行しても安全であることの担保方法、②DBの初期化（マイグレーション・シード）が完了する前に他サービスが起動してしまわないようにする起動順序の担保方法、の2点を新たに設計判断として明確化する必要がある。

## 決定

### シードの再実行防止方式

既存の**テーブル単位の存在チェックによる冪等性をそのまま踏襲する**。新たな「シード済みフラグ」テーブルやマーカーファイルは導入しない。

- `db_hiroba_qa_init` は、シード対象テーブル（`category` / `qa_original` / `question_altered`）ごとに存在チェックを行い、データが存在するテーブルへの投入をスキップする。
- この判定の前提となるデータの永続化は、既存の `db_hiroba_qa` のPostgreSQLデータボリューム（`./${DB_DIR}/data`）にのみ依存する。`db_hiroba_qa_init` 自身は状態を持たない（揮発してよい、常に作り直せる）ワンショットコンテナとする。

### 起動順序制御方式

Docker Composeの `depends_on` における `condition: service_completed_successfully` を用いる。

- `db_hiroba_qa_init` は `db_hiroba_qa` に対して `condition: service_healthy` で依存する。
- `web_backend` / `knowledge_mcp` / `tag_selector_mcp` は、`db_hiroba_qa_init` に対して `condition: service_completed_successfully` で依存する（`db_hiroba_qa` への直接の `service_healthy` 依存は、`db_hiroba_qa_init` を経由する形に置き換える、または両方を満たす形とする。詳細設計時に確定）。
- `db_hiroba_qa_init` がマイグレーション・シードいずれかの段階で失敗した場合は非0で終了し、依存する各サービスは起動しない。

## 検討した代替案

### シードの再実行防止

- **グローバルな「シード済み」フラグ（専用テーブルまたはマーカーファイル）を新設する**: 「全体として1回シードした」ことを1箇所で記録できる分かりやすさはあるが、①一部テーブルのみ投入済みの状態（前回実行が途中で失敗した等）からの再実行時に、フラグが立っていないことを理由に全テーブルへ再投入を試みてしまう（既存の投入済み行との重複・一意制約違反のリスク）、②既存の `exists_*` 実装を流用できず、テーブル単位の判定ロジックと二重に持つことになる、という理由から見送った。テーブル単位の存在チェックは、部分的な失敗からの再実行に対して自然に安全である。
- **マイグレーションツールの適用履歴テーブルを「シード済みか」の判定にも転用する**: マイグレーション適用状況とシード実行状況は別の関心事であり、（例えば）シードデータの投入元ファイルを差し替えて再シードしたいといった将来の運用要求が生じた際に、両者を混同すると柔軟性を失う。関心事を分離し、シードの判定は既存のテーブル存在チェックに委ねる。

### 起動順序制御

- **`db_hiroba_qa` の `healthcheck` 自体をマイグレーション・シード完了まで拡張する（例: 特定テーブルの存在確認をヘルスチェックに含める）**: DBコンテナ（PostgreSQL公式/pgvectorイメージ）のヘルスチェックに、アプリケーション固有のスキーマ・データ有無の判定ロジックを混在させることになり、ADR-0016で決定した「`db_hiroba_qa` はDB本体の責務のみに縮小する」方針と矛盾するため見送った。
- **各アプリケーションサービス（`web_backend` 等）のエントリポイントで、DB初期化完了をポーリングして待つ**: `depends_on` の宣言的な制御に比べ、各サービスに待機ロジックの実装・保守が必要になり、サービスごとに実装がずれるリスクがあるため見送った。`service_completed_successfully` は Docker Compose の標準機能で宣言的に表現できる。
- **`restart: always` 等で `db_hiroba_qa_init` を常駐に近い形にし、内部でポーリングにより初期化完了を待たせる**: ワンショットで完了・終了するという設計（ADR-0016）と矛盾し、不要な複雑化になるため見送った。

## 結果・影響

- 新たな永続化機構・状態管理テーブルを追加しないため、実装・保守コストが抑えられる。
- Docker Composeの `condition: service_completed_successfully` の対応バージョンを、開発者・CI環境で確認する必要がある（要件定義書 Open Issue #3）。対応していない場合、代替の待機処理を別途検討する必要が生じる。
- `db_hiroba_qa_init` が失敗した場合、依存する全アプリケーションサービスが起動しないため、障害の切り分け（DB初期化の問題か、各アプリケーション自体の問題か）が明確になる一方、初回起動時にLM Studio等のembeddingエンドポイントが未起動だと、シード全体が失敗し他サービスも起動できなくなる。運用手順（README）で、embeddingエンドポイントを先に起動しておくことを前提条件として明記する必要がある（要件定義書 Open Issue #5）。
- 既存のテーブル単位存在チェックのロジック（`web_backend/src/db.py` の `exists_*` 相当）を `db_hiroba_qa_init` 側へ移管して再利用する（要件定義書10章）。
