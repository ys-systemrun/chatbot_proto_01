# ADR-0058: search_knowledgeにおける祖先タグの動的展開方式

- ステータス: Accepted
- 日付: 2026-08-26
- 関連: `docs/requirement/202608261450_タグ階層展開・タグ構成類似度スコアリング機能要件定義書.md`, ADR-0005, ADR-0009, ADR-0057

## コンテキスト

`tag`テーブルは`parent_tag_id`による自己参照の親子構造を持つが、ADR-0005は「タグ階層を用いた検索（親タグ指定時に子タグを含める等）」を将来課題として明示的にスコープ外とし、`search_knowledge`の`tags`フィルタは指定タグ名との完全一致のみを行ってきた。

発注者から「子タグで検索する場合は同時に親タグでも検索していることにし、子タグと紐づいているQAは同時に親タグにも紐づいていてほしい」という要望が示された（要件定義書1章）。これは検索クエリ側・QA側の双方について、タグの祖先方向への展開（子→親）を検索マッチングに反映することを求めている。

この展開をどのようにデータとして持たせるかについて、次の2案が考えられた。

1. **検索時に動的展開する**: `qa_tag`テーブル自体は変更せず、検索クエリのたびにSQL上で祖先タグを計算する。
2. **`qa_tag`へ祖先タグ行を事前に生成する（非正規化）**: QAに子タグを紐づける操作の際、その祖先タグへの`qa_tag`行もあわせて自動生成し、常に「直接紐づくタグ＋祖先タグ」が`qa_tag`に格納された状態を維持する。

発注者に確認の結果、「検索時に祖先タグを動的に展開する（`qa_tag`は変更しない）」との回答を得た。

## 決定

**`qa_tag`テーブルのスキーマ・データは変更しない。検索クエリ（`QARepository.search`）の実行時に、SQL上で「タグ閉包」（あるタグ集合に、そのすべての祖先タグを加えた集合）を動的に計算し、入力タグ（`tags`引数）とQAの直接紐づくタグの両方に同じ展開を適用する。**

- 入力タグ閉包 = `tags`引数で指定された各タグ自身 ∪ それぞれの祖先タグすべて（`parent_tag_id`を根まで再帰的に辿る）。
- QAタグ閉包 = あるQAが`qa_tag`で直接紐づくタグ自身 ∪ それぞれの祖先タグすべて。
- 両閉包の計算は、`WITH RECURSIVE`によるSQLクエリ（要件定義書6.1節）で行う。Pythonアプリケーション層でのループ処理（タグごとにDBへ祖先を問い合わせる）は行わない（往復回数を抑えるため）。
- この対称な展開（クエリ側・QA側の両方に適用）により、「子タグで検索した場合に親タグにのみ紐づくQAも一致する」「子タグに紐づくQAが親タグでの検索にも一致する」という発注者の要望2点を、単一の仕組み（タグ閉包）で満たす。

## 検討した代替案

- **`qa_tag`への祖先タグ行の事前生成（非正規化）**: 検索クエリはシンプルになる（祖先展開のJOINが不要）利点があるが、次の理由で不採用とした。
  - タグ階層を変更する操作（`move_tag`、既存の`TagRepository`が提供）が発生するたびに、影響を受けるすべての`qa_tag`行（該当タグ・子孫タグに紐づく全QA分）を再計算・再生成する必要があり、整合性維持のロジックが複雑になる。
  - 「直接紐づくタグ」と「祖先展開により暗黙的に紐づいたタグ」が同じ`qa_tag`テーブルに混在すると、QA・タグ管理UI（`QaListPage`等）でのタグ表示・タグ由来のQA一覧・タグ削除時の参照チェック（`TagRepository.delete_tag`の「`qa_tag`から参照されていれば削除拒否」ロジック）等、既存機能の意味づけに影響が及ぶ範囲が広い。
  - 発注者への確認でも「検索時に動的展開」が明示的に選好された。
- **クエリ側のみ、またはQA側のみに展開を適用する（非対称な展開）**: 実装は単純になるが、発注者の要望2点（子タグ検索→親タグ紐づけQAも一致、子タグ紐づけQA→親タグ検索にも一致）のうち片方しか満たせない。両方を満たすには対称な展開が必要と判断した。
- **タグ階層の展開をアプリケーション層（Python）でタグごとに逐次問い合わせる**: `tag_selector_mcp`の`TagMetadataRepository`のように全タグをメモリキャッシュしてアプリケーション側でツリーを辿る方式も考えられるが、`knowledge_mcp`の`TagRepository`は既存方針として「キャッシュしない（呼び出しの都度SQLでDBを参照する）」（`tag_repository.py`冒頭コメント）としており、この方針との一貫性を優先し、SQL側での再帰計算を採用した。

## 結果・影響

- `knowledge_mcp/src/knowledge_mcp/repository/qa_repository.py`の`search`メソッドに、タグ閉包計算のSQL（`WITH RECURSIVE`）が追加される。`tag`/`qa_tag`テーブルのスキーマ・既存データには変更を加えない。
- タグ階層が深い場合、または`tag`件数が多い場合の閉包計算のパフォーマンスは、実装フェーズで計測し、必要に応じて`tag.parent_tag_id`へのインデックス付与等のチューニングを行う（要件定義書8章）。
- タグ管理UI（`QaListPage`/`TagTreePage`）・タグ管理ツール（`create_tag`/`move_tag`/`delete_tag`等）には変更を加えない。タグ階層を変更しても、次回の`search_knowledge`呼び出し時から新しい階層が即座に検索へ反映される（キャッシュを持たないため）。
- `agent_invitro`の`select_tags`結果（`path`フィールド、現状MVPでは`[name]`のみ、ADR-0010）には影響しない。`select_tags`自体は変更しない。
