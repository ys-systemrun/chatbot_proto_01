# ADR-0041: 管理UI（admin_uiサービス）のAWSネットワーク配置とブラウザアクセス経路（ADR-0023の限定的な見直し）

- ステータス: Accepted
- 日付: 2026-08-21
- 関連: `docs/requirement/202608211014_AWS環境向けQAタグ管理UI要件定義書.md`, ADR-0013, ADR-0023, ADR-0024, ADR-0036

## コンテキスト

QAデータ・タグ管理UI（`front_dev` / `web_backend`、`docs/requirement/202608060826.md`）は、ローカルの`docker-compose`環境向けにすでに機能実装済みである。これをAWS上にデプロイし、AWS上の`chatbot-invitro-rds`（ADR-0026）に対して、社内の運用担当者がブラウザから利用できるようにする必要がある。

一方、既存のADR-0023は、Knowledge MCPサーバ・Tag Selector MCPサーバ・agent_invitroについて「AWS内部限定（VPC内）に配置し、インターネットゲートウェイを経由した外部公開を行わない。オンプレ社内LANとの新規VPN/専用線接続も本フェーズでは構築しない。開発者・運用者の動作確認はECS Exec・SSMポートフォワーディングで代替する」と決定している。この決定は、「利用者はagent_invitroの呼び出し元、または動作確認を行う開発者・インフラ担当のごく少数であり、AWS CLI等の操作を前提にできる」という利用者像を前提にしている。

しかし、本件のQA・タグ管理UIは、AWS操作の知識を持たない一般の運用担当スタッフも利用者に含む想定であり、次の制約がある。

- 利用者はブラウザのみで到達できる必要がある（AWS CLI・SSMポートフォワーディング・VPNクライアントの操作を前提にできない）。
- 社内LANとAWS VPC間のVPN・専用線は現状用意されておらず、新設もコスト・工数の観点から見送る方針である（ADR-0023の検討時と同様の判断）。
- 到達可能な範囲は社内ネットワークのみに限定したい（発注者の要望）。

検討した選択肢は次の4案。

1. **SSMポートフォワーディングを利用者ごとに設定**: 追加コストなし。ADR-0023の方針をそのまま継続できる。しかし、利用者ごとにAWS CLI・IAMユーザー・Session Manager pluginの設定が必要になり、AWS操作の知識を持たない一般スタッフには運用負荷が高い。
2. **AWS Client VPNを新設**: 利用者はVPN接続後は通常のブラウザ操作で済む。ただし、月額の稼働コストとクライアント証明書の発行・配布・失効管理という運用負荷が新たに発生する。
3. **社内LANとの拠点間VPN（Site-to-Site VPN等）を新設**: 他システムとの共用も見込める恒久的な接続だが、構築コスト・工数が最も大きく、本件（管理UI1件のブラウザアクセス）に対しては過大である。
4. **インターネット向けALBを新設し、セキュリティグループで社内IPアドレスからのインバウンドのみを許可する**: 追加コストはALBの稼働費用のみ。利用者は通常のブラウザ操作のみで済み、AWS側の追加設定は不要。ただし、インターネットゲートウェイ経由の到達性を許可する点でADR-0023の「外部公開を行わない」という方針の一部を見直すことになる。

発注者に確認した結果、**案4（インターネット向けALB＋社内IPアドレス限定）** を採用する方針が確定した。VPN・専用線の新設は見送り、利用者がブラウザのみで到達できることを優先した。

## 決定

QA・タグ管理UI（`admin_ui`サービス）に限り、次の構成でブラウザからのアクセスを許可する。**Knowledge MCPサーバ・Tag Selector MCPサーバ・agent_invitro・RDSについては、ADR-0023の方針（AWS内部限定、VPC内のみ、SG参照ベースの到達制御）を変更しない。**

- インターネット向け（internet-facing）のApplication Load Balancer（ALB）を新設し、パブリックサブネットに配置する。
- ALBのセキュリティグループは、発注者から提供される社内IPアドレス（固定グローバルIPアドレス、または少数のCIDR範囲）からのインバウンド（80/443）のみを許可し、それ以外はすべて拒否する。
- ALB配下の`admin_ui`サービス（ECS Fargateタスク）自体は、既存のknowledge_mcp等と同様にプライベートサブネットに配置し、パブリックIPアドレスを持たせない。`admin_ui`タスク用のセキュリティグループは、ALBのセキュリティグループからのインバウンドのみを許可する。
- `admin_ui`サービスからKnowledge MCPサーバへの到達性は、既存の`agent_invitro → knowledge_mcp`と同様の形式（セキュリティグループの参照許可、`modules/network`への追加）で許可する。`admin_ui`サービスからRDSへの直接アクセスは許可しない（ADR-0013の方針を維持）。
- アプリケーションレベルの追加ログイン認証（Basic認証等）は、本フェーズでは実装しない。社内IPアドレス限定というネットワークレベルの制御のみで十分とする（発注者確認済み）。

## 検討した代替案

- **案1（SSMポートフォワーディング）**: 追加コストがなくADR-0023との整合性が最も高いが、AWS操作の知識を前提としない一般スタッフの利用には不向きであり、今回の利用者像（運用担当者を含む）に合わないため不採用とした。
- **案2（AWS Client VPN）**: 利用者の操作はブラウザのみで済むが、月額コスト・証明書配布運用が発生する。社内IPアドレスが十分に安定している（12章相当のOpen Issueで発注者確認要）前提であれば案4の方が低コストで同等の目的を達成できるため、本フェーズでは見送った。将来、社内グローバルIPアドレスが恒常的に変動する、または社外拠点からの利用が必要になった場合は、本ADRを見直し、Client VPNへの切り替えを別途ADRで検討する。
- **案3（拠点間VPN）**: コスト・工数が最も大きく、本件単独では正当化できないため不採用とした。将来、他システムとのAWS VPCアクセスとの共用ニーズが具体化した場合に再検討する。

## 結果・影響

- Knowledge MCPサーバ・Tag Selector MCPサーバ・agent_invitro・RDSは、引き続きADR-0023の「AWS内部限定」の方針下にあり、本ADRによる変更はない。本ADRが新設するインターネットゲートウェイ・パブリックサブネット・ALBは、`admin_ui`サービス専用であり、他コンポーネントとのネットワーク到達性を変えるものではない。
- 既存VPC（ADR-0036, data source参照）にALB配置に必要なパブリックサブネット・インターネットゲートウェイへのルーティングが用意されているかは未確認であり、実装フェーズで基盤チームに確認する必要がある（要件定義書12章Open Issue #2）。用意されていない場合、本ADRの前提（既存VPCを流用する）が崩れ、追加のネットワーク基盤検討が必要になる。
- 社内IPアドレスが変動する環境の場合、Terraform変数の更新・再applyが都度必要になる運用上の負荷が生じる（要件定義書8.1節）。恒常的な変動がある場合は、上記「検討した代替案」のとおりAWS Client VPNへの切り替えを別途検討する。
- ALBの稼働費用（時間課金＋LCU）が新たに発生する。VPN・専用線を新設しないことで、それらに比べたコスト増は抑えられている。
- 通信の暗号化（HTTPS化、ドメイン・証明書の要否）は本ADRの範囲外とし、要件定義書12章Open Issue #3として別途確定する。
- 将来、社内IPアドレス限定という制約を超えた利用（社外拠点、利用者ごとの権限分離等）が必要になった場合は、本ADRおよびADR-0023を見直し、認証方式（OAuth等）やAWS Client VPN／拠点間VPNの追加を含めて別途ADRを起票する。この位置づけは、ADR-0023が残した将来課題の考え方を引き継ぐものである。
