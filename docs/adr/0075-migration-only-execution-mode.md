# ADR-0075: マイグレーション専用実行モードの新設（シードスキップ対応、既存db_hiroba_qa_initイメージ再利用）

- ステータス: Accepted
- 日付: 2026-09-04
- 関連: `docs/requirement/202609040859_マイグレーション専用実行機能要件定義書.md`, ADR-0016, ADR-0017, ADR-0018, ADR-0040, ADR-0051, ADR-0052, ADR-0066

## コンテキスト

現状、AWS環境にデプロイした RDS（`chatbot`・`conversation` データベース）へマイグレーションを適用する手段は、`terraform/deploy` の `seed` コマンド（`db_hiroba_qa_init` の ECS ワンショットタスク実行）のみである。`db_hiroba_qa_init`（`src/main.py`）の通常起動は、次の6ステップを常に一体で実行する。

1. chatbot ロール作成（migrator/app、ADR-0052）
2. chatbot マイグレーション適用（yoyo, ADR-0017）
3. chatbot シード投入（QA原本・言い換え質問・カテゴリ。`question_altered` 投入時に embedding 計算を伴いうる）
4. chatbot app ロールへの DML 権限付与
5. conversation データベース作成→ロール作成→マイグレーション適用（yoyo, ADR-0051）→権限付与
6. エクスポート専用読み取りロール作成（ADR-0046）

一方、運用上は QA・検証データの投入・更新を `import-data`（全消去→上書き投入、ADR-0066）で行うことが多く、`seed` が投入したシードデータ（手順3）は、その後 `import-data` 実行時に上書き・破棄される。そのため、スキーマ変更のみを RDS に反映したい場合にも、事後的に捨てられるシード処理を伴う `seed` を実行せざるを得ず、実行時間・コストの両面で無駄が生じていた（`docs/requirement/202609040859_マイグレーション専用実行機能要件定義書.md`）。

`import-data` コマンドは、既に類似の課題（通常起動とは異なる処理を、新規インフラを増やさずに切り替えたい）に対して前例を確立している（ADR-0066）。`db_hiroba_qa_init` と同一のイメージ・同一の ECS タスク定義（`db_init_task_family`）を再利用し、`run-task` のコンテナ環境変数オーバーライドで `IMPORT_MODE=true` を注入することで、通常起動とは異なる処理へ分岐させている。`terraform/deploy/src/aws.py` の `run_import_task` は、環境変数オーバーライドを汎用的に受け付ける実装に既になっている。

## 決定

**`db_hiroba_qa_init` に、シード投入のみを除外する「マイグレーション専用モード」を追加し、既存イメージ・既存ECSタスク定義を再利用した2つの実行入口（新規 `migrate` コマンド、既存 `seed` コマンドへの `--skip-seed` オプション）を新設する。**

1. **`db_hiroba_qa_init` 側のモード分岐**: 環境変数（例: `MIGRATE_ONLY`、名称は実装フェーズで確定。既存 `IMPORT_MODE` と同じ真偽値判定方式を踏襲）を新設する。`MIGRATE_ONLY` が真の場合、`main()` の通常フローのうち、コンテキストに挙げた手順3（chatbot シード投入）の呼び出しのみをスキップする。手順1・2・4・5・6（両データベースのロール作成・マイグレーション適用・権限付与・エクスポート専用ロール作成）は通常どおり全て実行する。`MIGRATE_ONLY` が未設定・偽の場合は既存動作を完全に維持する（後方互換）。
2. **実行基盤の再利用**: 新規のECSタスク定義・ECRイメージは作成しない。既存の `db_init_task_family` に対し、`run_import_task` と同型の environment オーバーライド機構（`{"MIGRATE_ONLY": "true"}`）で `run-task` を起動する。`terraform/deploy/src/aws.py` 自体への変更は不要と見込む。
3. **新規 `migrate` コマンド**: `terraform/deploy` に新規サブコマンド `migrate`（`cmd_migrate`）を追加する。処理内容は既存 `cmd_seed` と同型（database/app構成の apply 済み確認→構成出力取得→`run-task`起動→`STOPPED`まで待機→`exitCode`確認）とし、`MIGRATE_ONLY=true` の環境変数オーバーライドを付与する点のみが異なる。対応する `terraform/migrate.bat`（既存 `seed.bat` と同じ形式）を新設する。
4. **既存 `seed` コマンドへの `--skip-seed` オプション追加**: `seed` サブコマンドに任意フラグ `--skip-seed` を追加する。指定時は `migrate` コマンドと同一の `MIGRATE_ONLY=true` オーバーライドを付与して起動する（`migrate` と同一の実行結果になる）。未指定時は既存動作を維持する。`migrate` コマンドと `--skip-seed` オプションを両方新設するのは、（a）ダブルクリックで完結する専用の運用導線を用意しつつ、（b）既存の `seed` コマンド体系のままオプションで挙動を切り替えたいスクリプト運用の両方に対応するためである。
5. **実行確認プロンプトなし**: マイグレーション専用モードの実行は、スキーマ追加・冪等なロール作成・権限付与のみを行う非破壊的操作であるため、`destroy-app`・`destroy-database`・`import-data` が要求する `confirm_typed` による型入力確認は設けない。既存の `seed` と同じく、確認プロンプトなしの無人実行を可能にする。

## 検討した代替案

- **マイグレーション専用の新規ECSタスク定義・ECRイメージを新設する**: 責務分離は明確になるが、ビルド・保守対象（Dockerfile・ECRリポジトリ・Terraformリソース）が増える。ADR-0066が確立した「同一イメージ・環境変数によるモード切替」という設計との一貫性も崩れる。本機能はコスト削減が目的であり、インフラを増やす結果になる本代替案は不採用とした。
- **`--skip-seed` オプションのみを追加し、専用の `migrate` コマンド・`.bat` は新設しない**: 実装対象を絞れるが、ダブルクリックで完結する専用の運用導線（既存 `.bat` 群と同じUX、ADR-0040）を用意したいという要望に応えられないため、`migrate` コマンドの新設と併存させることとした。
- **専用の `migrate` コマンドのみを新設し、`seed` への `--skip-seed` オプションは追加しない**: 実装対象を絞れるが、既存の `seed` コマンド体系のままオプションでシード有無を切り替えたい運用（スクリプト等）の柔軟性を損なうため、両方を新設することとした。
- **`seed` コマンドの既定動作自体を「シードなし」に反転させ、シードしたい場合にオプションを指定させる**: 既存の初回セットアップ・再シード運用（`apply-all` が内部で呼ぶ `seed` を含む）への影響が大きく、後方互換性を損なうため不採用とした。
- **マイグレーション専用モードで、ロール作成・権限付与・エクスポート専用ロール作成（手順1・4・6）も併せてスキップし、yoyoマイグレーション適用（手順2・5）のみに限定する**: 実行対象を最小化できるが、これらはいずれも冪等かつ外部API呼び出し（embedding計算等）を伴わない低コスト処理であり、スキップする実益が乏しい。むしろ、マイグレーションでテーブルが新設された直後に権限付与（`_grant_app_privileges`）が行われないと、アプリケーションロールが新テーブルへ即座にアクセスできない状態が残るリスクがある。シード投入のみを除外し、それ以外は通常どおり実行するフルセット方式を採用した。
- **マイグレーション専用モードの実行にも `confirm_typed` 等の追加確認を設ける**: 本番RDSのスキーマを直接変更する操作であるため慎重さの観点はあるが、非破壊的操作である点で `destroy-*`・`import-data` とは性質が異なり、`seed` と同様の運用感（無人実行可）を優先し、確認は設けないこととした。

## 結果・影響

- `db_hiroba_qa_init/src/main.py` の `main()` に環境変数分岐を1箇所追加する（既存の `IMPORT_MODE` 分岐と同型のパターン）。既存フローへの影響は、シード投入呼び出し（手順3）をスキップする条件分岐を挟む範囲に限定される。
- `terraform/deploy/src/commands.py` に `cmd_migrate` を追加し、`cmd_seed` に `skip_seed` 引数を追加する。両者とも、ADR-0066で実装済みの環境変数オーバーライド対応 `run-task` 関数を呼び出す形にできる見込みであり、`terraform/deploy/src/aws.py` 自体の変更は不要と見込む。
- `terraform/deploy/src/__main__.py` の `build_parser()` に `migrate` サブコマンドの追加、および `seed` サブコマンドへの `--skip-seed` 引数追加が発生する。
- 新規のIAM権限・ECRリポジトリ・Terraformリソースは不要。デプロイオーケストレータのAWS認証情報が持つ既存の `ecs:RunTask` 権限（`db_init_task_family` に対するもの）をそのまま利用できる。
- `terraform/README.md`（コマンド一覧・実行手順）の更新、`terraform/migrate.bat` の新設、ローカル `docker-compose` 環境での呼び出し方法の確定は、実装フェーズの作業として発生する（要件定義書 Open Issue #1・#3参照）。
- 運用手順として、「スキーマ変更のみをRDSに反映したい場合は `migrate`（または `seed --skip-seed`）を使い、データの投入・更新は引き続き `import-data` を使う」という使い分けが明文化される。
- `migrate`・`import-data` がいずれも同一の `db_init_task_family` を起動するため、CloudWatch Logs 上で実行種別をどう識別するか（要件定義書 Open Issue #4）は、運用要件次第で別途検討する。
- 個々のマイグレーションファイル（yoyo migration）が、既存データに対して後方互換性のある変更（例: `NOT NULL` 制約なしでの列追加）になっているかどうかは、本ADRの対象外（マイグレーション専用モードという実行経路の追加のみを扱う）であり、引き続き各マイグレーション作成時の個別の設計判断に委ねる。
