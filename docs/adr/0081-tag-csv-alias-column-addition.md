# ADR-0081: タグCSV一括インポート/エクスポートへのエイリアス列追加（ADR-0065のエイリアス対象外方針の見直し、パイプ区切り・追加専用方式）

- ステータス: Accepted
- 日付: 2026-09-09
- 関連: `docs/requirement/202609091119_タグエイリアス管理機能要件定義書.md`, ADR-0053, ADR-0061, ADR-0065

## コンテキスト

タグ単体の一括インポート（ADR-0061）・CSVエクスポート（ADR-0065）は、いずれも`name`/`parent_name`/`description`の3列のみを対象とし、`tag_alias`を意図的に対象外としてきた。ADR-0065は次のように理由を明示している。

> エイリアス（`tag_alias`）は対象外とする: タグ一括インポート（ADR-0061）が`name`/`parent_name`/`description`の3列のみでエイリアスに対応していないため、エクスポートに含めると「そのまま再インポートしても情報が失われない」という前提が崩れる。

ADR-0080でエイリアスのCRUD機能が管理画面に追加されたことに伴い、発注者よりCSV一括インポート/エクスポートにもエイリアスを含めたいという要望が示された。ADR-0065が懸念した「往復整合性の崩れ」を避けつつエイリアスをCSVに含める方式を決定する必要がある。

## 決定

**CSVに`aliases`列を追加する（`name`/`parent_name`/`description`/`aliases`の4列）。`aliases`列は複数のエイリアスをパイプ`|`区切りで1セルにまとめた文字列とし、インポートは追加専用（additive-only、CSVに列挙されていない既存エイリアスの削除は行わない）とする。**

1. **列構成**: `export_tags`ツールが返す各タグレコードに`aliases`（文字列配列）を追加する（`TagRepository`が既存の`list_tags`同様、`tag_alias`をJOINして集約する）。`web_backend`の`build_export_csv`はこれをパイプ`|`区切りの文字列に変換してCSVへ出力する。`import_tag_batch`側は、`_parse_tag_import_csv`がCSVの`aliases`列をパイプ区切りで文字列配列に分割し、他の列と同様に行データの一部として`import_tag_batch`ツールへ渡す。
2. **インポートは追加専用とする（削除しない）**: CSVの`aliases`列に列挙された各文字列のうち、対象タグ（当該行の`name`で解決されたタグ）にまだ登録されていないものだけを`add_tag_alias`相当のロジックで登録する。CSVから省かれた既存のエイリアスを削除する処理は行わない。この方針は、タグ本体の一括インポート（ADR-0061）が「既存タグの削除・リネームを扱わない」という一貫して非破壊的な設計にしていることと揃える。
3. **エイリアス単位でのエラー許容**: CSV内のあるエイリアス文字列が既に別のタグに登録済み（`tag_alias.alias`のUNIQUE制約に抵触）の場合、そのエイリアス1件のみをエラーとして`TagImportRowResult`に記録し（`alias_warnings`項目を追加）、タグ本体の作成・更新、および同じ行の他のエイリアスの登録は継続する。これはADR-0053・ADR-0061が確立した「行単位でのエラー許容（1行の失敗が他行の処理を止めない）」という設計思想を、1行の中のエイリアス単位にも広げたものである。
4. **リネームは対象外のまま**: ADR-0061の決定（`name`列は識別キーであり、名称変更はこの一括インポートでは扱わない）は変更しない。同様に、エイリアスを「別のタグに付け替える」操作もこの一括インポートでは扱わない（対象タグへの新規追加のみ）。
5. **後方互換性**: `aliases`列は任意列とし、列自体が存在しない（旧形式の）CSVも、エイリアス操作なしのタグ登録・更新として引き続き成功させる。

## 検討した代替案

- **現状維持（ADR-0065の決定どおりエイリアスをCSV対象外のままにする）**: 発注者からの要望（CSVでのエイリアス一括登録・整理）に応えられないため不採用とした。
- **完全置換方式（CSVの`aliases`列の内容で、対象タグのエイリアスを完全に置き換える。列に無いものは削除する）**: ADR-0065が懸念した「情報の意図しない喪失」のリスクが最も高い方式である。CSVの一部の行・一部のセルだけを編集して再インポートするという運用（Excel等での部分編集）は現実的に起こりうるため、意図せず他のエイリアスを削除してしまう事故が発生しやすい。タグ本体の一括インポート（ADR-0061）が一貫して非破壊的（既存タグを削除しない）である設計思想とも矛盾するため不採用とし、追加専用方式を採用した。
- **エイリアスを別ファイル（`tag_alias.csv`、1行1エイリアス、列: `tag_name`/`alias`）として独立させる**: タグ本体のCSVと列構成を分離でき、1行1エイリアスなので区切り文字のエスケープ問題（後述のOpen Issue）を避けられる利点がある。しかし、`TagTreePage`のCSV機能は現状「タグ一覧を1つのCSVで一括管理する」という単一ファイルのUXで一貫しており、2つ目のファイル形式・アップロードUIを新設するのは利用者にとって分かりにくく、実装・説明コストも増える。1タグあたりのエイリアス数は運用ガイドライン上も少数（表記ゆれの範囲）であることが見込まれるため、単一ファイル内のパイプ区切り列で十分と判断し不採用とした。
- **区切り文字にカンマ`,`やセミコロン`;`を使う**: CSVの列区切り自体がカンマであるため、セル内容にカンマを含めるとCSVパーサ側でのクォート処理に依存し、Excel等での手作業編集時に事故が起きやすい。パイプ`|`は`tag_alias`に想定される日本語の同義語表記に含まれる可能性が低く、既存システム内でも他に予約された意味を持たないため採用した。

## 結果・影響

- `knowledge_mcp`の`export_tags`/`import_tag_batch`の返り値・引数スキーマに`aliases`が追加される。両ツールの既存の`name`/`parent_name`/`description`に関する挙動（upsertキー、循環参照チェック等）には変更を加えない。
- `web_backend`の`_TAG_IMPORT_COLUMNS`/`_TAG_EXPORT_COLUMNS`に`aliases`が追加され、`TagImportRowResult`に`alias_warnings`が追加される。
- `TagTreePage`のCSV一括インポート/エクスポートの説明文言に、エイリアス列の追加・追加専用（削除されない）である旨の説明を加える必要がある（詳細設計フェーズで反映）。
- エイリアス文字列自体にパイプ`|`を含むケースは本MVPでは非対応（要件定義書202609091119 Open Issue #2）。
- CSVエクスポート→（無編集のまま）再インポートは、既存エイリアスがすべて既に登録済みのため実質的に無変化（no-op）となり、ADR-0065が目指した往復整合性は維持される。一方、エクスポート後にCSV上でエイリアスを削除して再インポートしても、DB側のエイリアスは削除されない（追加専用の方針による意図した非対称性）。
