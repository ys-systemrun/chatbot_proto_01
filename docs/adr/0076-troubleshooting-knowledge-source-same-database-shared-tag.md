# ADR-0076: トラブルシューティング情報源の追加方式（同一実DB内新設・単一テーブル＋出自列・共有タグマスタ参照）

- ステータス: Accepted
- 日付: 2026-09-07
- 関連: `docs/requirement/202609071337_トラブルシューティング情報源追加要件定義書.md`, ADR-0005, ADR-0069, ADR-0077

## コンテキスト

発注者は、維津美の広場QAデータ（`hiroba_qa_original`系6テーブル）とは別の情報源として、2つの静的HTML文書（`trouble_shooting.html`：維津美V7システム全般のトラブルシューティング35トピック、`trouble_shooting_netauth.html`：ネット認証まわりのトラブルシューティング30トピック）をチャットボットの回答材料として追加したい。両ファイルは同一のテンプレート構造（`<h2>`単位のトピック、多くは現象/原因/ユーザーに案内すべき内容等の固定フィールドを持つ`<table>`を内包）を持つ。

発注者からの要求は「別テーブルで管理したいが、タグ情報は共有したい」というものであった。ADR-0069はサポート知識DB基盤化にあたり「発注者は今後、維津美の広場とは異なるデータソースを追加し、データソースごとに実データベースを分離して、それぞれ独立したマイグレーション・シーディング機構で管理する方針」を示していた、という将来像を記録している。一方でPostgreSQLは実データベースをまたいだ外部キー制約を持たず、複数の実DBにまたがってタグマスタを共有するには定期同期やFDW（外部データラッパー）等の追加の仕組みが別途必要になる。ADR-0069自身も「将来、複数ソースのテーブルが同一DB内に同居する運用に移行した場合でも接頭辞で識別できる余地を残す」と、同一DB内共存という代替経路を明示的に想定していた。

発注者に、(a)同一実DB内への新設（タグ共有が容易）と(b)専用の別実DB新設（ADR-0069が示した将来像に忠実だがタグ共有に追加の仕組みが必要）を提示して確認したところ、(a)を選択した。

## 決定

**トラブルシューティング記事用のテーブル（`troubleshooting_article`・`troubleshooting_article_tag`）を、維津美の広場QAデータと同一の実データベースに新設する。2つのHTMLファイルは単一の`troubleshooting_article`テーブルにまとめ、`source_key`列（`trouble_shooting`/`trouble_shooting_netauth`）で出自を区別する。タグは`troubleshooting_article_tag`を介して、維津美の広場QAと共有する単一のタグマスタ（ADR-0077でリネームする`tag`/`tag_alias`/`tag_folder`）を参照する。**

1. **同一実DB内配置**: `hiroba_qa_original`等と同じ実データベース（ADR-0077でリネーム後は`db_chatbot_knowledge_base`）にテーブルを追加する。PostgreSQLの通常の外部キー制約でタグマスタとの整合性を保証でき、複数DBにまたがる同期の仕組みが不要になる。ADR-0069が想定していた代替経路（同一DB内共存＋接頭辞識別）を採用する形になる。
2. **単一テーブル＋出自列**: 2ファイルは同一テンプレート構造を持つため、`troubleshooting_article`テーブル1つに集約し、`source_key`列で区別する。将来3つ目のHTML文書が追加された場合も、テーブル追加やスキーマ変更を伴わず`source_key`の値を増やすだけで対応できる。
3. **ソース別プレフィックスの命名**: 新テーブルは`troubleshooting_`接頭辞を用いる。`hiroba_`が「維津美の広場」という固有の出自を示す接頭辞であるのに対し、トラブルシューティング記事はRedmine Wiki由来の技術サポート文書であり、由来の異なるデータであることを名称面でも明示する。
4. **タグ結合テーブルの新設（マスタは新設しない）**: `troubleshooting_article_tag(article_id, tag_id)`を新設し、`hiroba_qa_tag`と対称的な構造とする。タグマスタ自体（`hiroba_tag`系）は新設せず、ADR-0077でリネームした共有マスタをそのまま参照する。
5. **カテゴリは新設しない**: `hiroba_category`に相当する分類テーブルはトラブルシューティング記事には設けない。HTML原本にカテゴリに相当する構造がなく、かつ発注者の「タグ情報を共有したい」という意図に沿い、分類は共有タグ体系のみで行う。

## 検討した代替案

- **専用の別実データベースを新設する（ADR-0069が示した将来像に忠実な案）**: データソースの分離単位が実DBとして明確になり、将来的に異なるマイグレーション・シード機構で独立管理する運用にも直結する。しかしPostgreSQLは実DBをまたいだ外部キーを持たないため、タグ共有には(i)アプリケーション層での整合性チェックのみに頼る、(ii)`postgres_fdw`等の外部データラッパーでタグマスタを参照する、(iii)定期的なタグデータの複製・同期処理を別途実装する、のいずれかが必要になり、設計・運用コストが本要件の主眼（既存タグ体系を使ったトラブルシューティング記事の分類）に見合わない。発注者が「タグ情報の共有」を明確に要求したため不採用とした。

- **ファイルごとに別テーブル（`trouble_shooting_article`/`netauth_article`等）とする**: 出自ごとの独立性は高まり、将来ファイルごとにスキーマが分岐しても対応しやすい。しかし現時点で両ファイルの構造は完全に同一であり、別テーブル化は`troubleshooting_article_tag`のような結合テーブルも2系統必要になるなど、検索・タグ付けロジックの重複を招く。将来スキーマが実際に分岐した時点で分割する方が実装コストに見合うと判断し、今回は不採用とした。

- **`hiroba_qa_original`に統合し、`source_type`列で区別する（QAと同一テーブル）**: 新テーブルを増やさずに済む。しかしトラブルシューティング記事は`question_text`/`answer_text`という単純なQA構造ではなく、現象・原因・エラーメッセージ等の多数の構造化フィールドを持つ。単一テーブルに無理に統合すると大半の列がQA側では常にNULLになる、あるいは逆にトラブルシューティング側で`answer_text`のような汎用列に複数フィールドを詰め込む必要が生じ、データモデルの表現力が低下する。発注者の「別テーブルで管理したい」という明示的な要求とも整合しないため不採用とした。

## 結果・影響

- `db_hiroba_qa_init`のmigrationsに`troubleshooting_article`/`troubleshooting_article_tag`を追加する（ADR-0077の再構築サイクルにまとめて適用する）。
- `knowledge_mcp`に新規`troubleshooting_repository.py`が必要になる（ADR-0078で詳述）。
- `web_backend/src/export/tables.py`の`CHATBOT_TABLES`（またはその後継）に新テーブルを追加する必要があり、`db_hiroba_qa_init/src/import_data.py`の対応するテーブル一覧との同期が必須になる（ADR-0069で既知のリスクパターンを継承）。
- タグの一元管理により、タグ運用ガイドライン（REQ-202609021050）・タグフォルダ階層（ADR-0072〜0074）がトラブルシューティング記事にもそのまま適用される。
- 将来、真に独立したマイグレーション・シード機構が必要なデータソース（例:法人向け契約管理データ等、性質が大きく異なるもの）が追加される場合は、本ADRとは別に「専用の別実DB」案を再検討する余地を残す。
