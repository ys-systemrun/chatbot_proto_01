# ADR-0051: conversationデータベースのマイグレーション方式をyoyo-migrationsへ統一する（ADR-0044の限定的な見直し）

- ステータス: Accepted
- 日付: 2026-08-26
- 関連: `docs/requirement/202608261002_DBマイグレーション・データインポート機能要件定義書.md`, ADR-0016, ADR-0017, ADR-0018, ADR-0044, ADR-0048

## コンテキスト

`chatbot`データベースは、ADR-0016〜0018により、`db_hiroba_qa_init`がyoyo-migrationsでスキーマをバージョン管理している。一方`conversation`データベースは、ADR-0044により「`db_conversation/init.sql`と同内容の冪等なDDL（`CREATE TABLE IF NOT EXISTS`）を直接実行する」方式が採用され、yoyoによる履歴管理は明示的に見送られた。

ADR-0044がyoyo導入を見送った理由は、「現時点でのスキーマは2テーブル（`conversation`/`message`）・1バージョンのみであり、ADR-0017がyoyo採用を決定した際の背景（複数マイグレーション・embedding次元パラメータ化への対応）が当てはまらない」というものだった。

しかし、その後のADR-0048（検証機能のデータ配置、本日付）により、`conversation`データベースに`verification_question`/`verification_run`/`verification_run_tag`/`verification_run_source`の4テーブルが追加され、`conversation`データベースは計6テーブル・複数バージョンの状態になった。これは、ADR-0044が前提とした「2テーブル・1バージョン」という状況ではなく、むしろADR-0017が`chatbot`データベースについて問題視した「バージョン管理されない、追跡不能なスキーマ変更の積み重ね」と同種の状態に近づいている。

現状の冪等DDL方式には、次の課題が残る。

- どのDDLが「いつ・なぜ」適用されたかの履歴が残らない。`db_conversation/init.sql`を直接読めば最終状態は分かるが、変更の経緯（要件定義書・ADRとの対応）を辿るには、Gitのコミット履歴やADR文書を別途参照する必要がある。
- 今後もテーブルが追加され続けると（本書の一括インポート機能自体も新規テーブルを追加しうる）、`chatbot`データベースがモデル別`init.sql`のドリフトで直面した課題（要件定義書202608061016 2.1節）と同種のリスク、すなわち「ローカルとAWSでスキーマ適用処理の記述が二重管理され、どちらかへの反映漏れが生じる」リスクが積み上がる。

## 決定

**`conversation`データベースのスキーマ管理を、`chatbot`データベースと同様にyoyo-migrationsへ移行する。** `db_hiroba_qa_init`は、`chatbot`データベース向け（既存）と`conversation`データベース向け（新規）の、2つの独立したマイグレーション履歴を、同一サービス内で管理する。

- **既存DDLのマイグレーションファイル化**: `db_conversation/init.sql`の内容（`conversation`/`message`テーブル）と、ADR-0048で追加された4テーブルのDDLを、時系列順のマイグレーションファイル（例: `0001_initial_conversation_message.sql`, `0002_add_verification_tables.sql`）に再構成する。
- **既存環境のベースライン化**: 既にテーブルが作成済みの環境（ローカルの`db_conversation/data`ボリューム、AWSの既存`conversation`データベース）に対しては、既存README「既存環境（手動migration適用済みボリューム）からの移行」節と同様に、`yoyo mark`によるベースライン登録手順を用意する。
- **`chatbot`データベースとは独立した履歴とする**: `question_altered`のembedding次元パラメータ化（ADR-0017）のような`conversation`データベース固有の複雑さは現時点でないため、単純な`.sql`ファイル形式のマイグレーションのみとし、Pythonステップの追加機構は導入しない（必要になった時点で個別に追加できる、yoyoの既存機能を使う）。
- **ローカル`db_conversation`サービスの役割縮小**: `chatbot`データベース（`db_hiroba_qa`）と同様、`db_conversation`サービスはPostgreSQL本体とデータ永続化のみを担い、`init.sql`によるスキーマ作成は廃止する。`db_hiroba_qa_init`が両データベースのスキーマ作成を一手に担う唯一の実行者になる。

## 検討した代替案

- **現状の冪等DDL方式を維持する**: 実装コストがゼロで済む利点があるが、コンテキストで述べた「バージョン履歴の欠如」「今後のテーブル追加に伴うリスクの蓄積」が解消されない。本書が新たに追加しようとしているQA・検証質問の一括インポート機能自体が将来スキーマ変更を伴う可能性もあり、先送りするほど移行コストが増大すると判断し不採用とした。
- **`chatbot`データベースと`conversation`データベースを単一のyoyo履歴で管理する**: マイグレーション管理の仕組みを1つに集約できる利点はあるが、yoyo-migrationsは1つの接続文字列（1データベース）に対して1つの履歴を管理する設計であり、無理に1履歴にまとめると「どのマイグレーションがどちらのデータベースに対するものか」をファイル名や条件分岐で作り込む必要が生じ、ADR-0017が採用した「単一履歴＋パラメータ化」の考え方（同一データベース内でのモデル差異を吸収する目的）とは性質が異なる。データベースが物理的に分かれている以上、履歴も分けるのが自然と判断した。
- **Alembic等、より高機能なツールへの全面移行**: `chatbot`データベース側で既に不採用と判断した理由（ADR-0017、SQLAlchemy非採用のプロジェクトでは過剰）がそのまま当てはまる。`conversation`データベース側だけ別ツールを採用すると、`db_hiroba_qa_init`が2種類のマイグレーションツールに依存することになり、保守性が悪化するため不採用とした。

## 結果・影響

- `db_hiroba_qa_init`に、`conversation`データベース向けのyoyo-migrations実行ステップ（既存の`chatbot`向けとは別の接続文字列・別のマイグレーションディレクトリ）が追加される。
- `db_conversation/init.sql`は廃止され、`docker-compose.yml`の`db_conversation`サービス定義から`init.sql`マウントが削除される。
- 既存の`conversation`データベース（ローカル・AWSとも）に対するベースライン化作業が、移行時に一度必要になる（要件定義書12章Open Issue #6）。
- 今後`conversation`データベースにテーブルを追加する機能（例: 本書のQA・検証質問一括インポートに伴う追加テーブルが生じた場合）は、`chatbot`データベースと同じ手順（マイグレーションファイルの追加）で統一的に扱えるようになる。
- ベースライン化作業の実施タイミングは、発注者確認（2026-08-26）により、開発環境・AWS環境とも本要件の実装フェーズ内でまとめて実施することとした（要件定義書2.3節#11）。
