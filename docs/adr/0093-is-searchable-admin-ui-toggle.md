# ADR-0093: 検索対象フラグ（is_searchable）の切り替えは既存の更新ツール・更新エンドポイントの部分更新で行い、一覧から即時保存する

- ステータス: Accepted
- 日付: 2026-09-16
- 関連: ADR-0013（管理UIの書き込み経路）、ADR-0014（QA管理ツール）、ADR-0015（front_devのルーティング・依存方針）、ADR-0064（言い換え質問文管理）、ADR-0068（一覧ページの検索条件URL同期）、ADR-0074（並べ替えの専用ツール `reorder_tag`）、ADR-0079（トラブルシューティング記事管理UI）、ADR-0092（is_searchableの新設と検索除外）、`docs/requirement/202609160930_情報源レコード検索対象フラグ（is_searchable）機能要件定義書.md`（6.4〜6.6節）

## コンテキスト

ADR-0092で新設する `is_searchable` を、運用者が管理画面から切り替えられるようにする必要がある。対象は3つの一覧ページ（QA一覧・言い換え質問文一覧・トラブルシューティング記事一覧）と、対応する3つの編集ページである。

既存の管理機能の書き込みには、次の2つのパターンが混在している。

| パターン | 例 | 特徴 |
|---|---|---|
| 汎用の部分更新ツール | `update_qa`（`None`＝変更なし）、`update_troubleshooting_article`（`fields` dict） | 編集ページのフォーム保存に対応。引数が増えても呼び出し側は影響を受けない |
| 単一操作の専用ツール | `reorder_tag` / `reorder_tag_folder`（ADR-0074）、`set_tag_folder`、`add_tag_alias` | 一覧・ツリー画面のボタン1つに対応。操作の意味がツール名に現れる |

`is_searchable` の切り替えは、性格としては後者（一覧上の1操作）に近い一方、値としては単なるレコードの属性であり、編集ページでも他項目と同時に保存したい。どちらの型に寄せるかを決める必要がある。

また、`update_question_altered(id, text)` は現在 `text` を必須引数として取り、常にembeddingを再計算する。フラグだけを変えたい一覧のトグルからこれを呼ぶと、**1クリックごとにBedrockのembedding呼び出しが発生する**（ADR-0031）。この点は設計上避けなければならない。

保存タイミングについても、一覧上のトグルを押した瞬間に保存するのか、編集ページを開かせるのかという選択がある。

## 決定

**専用のツール・専用のAPIエンドポイントを新設せず、既存の更新ツール・更新エンドポイントの部分更新として `is_searchable` を扱う。一覧ページのトグルは楽観的更新による即時保存、編集ページはフォーム保存時の反映とする。**

### 決定1: 専用ツール・専用エンドポイントを新設しない

| ツール | 変更 |
|---|---|
| `update_qa` | `is_searchable: Optional[bool] = None`（`None`＝変更なし）を追加 |
| `update_question_altered` | `text` を `Optional[str] = None` へ変更し、`is_searchable: Optional[bool] = None` を追加 |
| `update_troubleshooting_article` | `fields` に `is_searchable` を指定可能にする |

APIも同様に、既存の `PUT /api/qa/{qa_id}` ・ `PUT /api/hiroba_question_altered/{id}` ・ `PUT /api/troubleshooting_articles/{id}` へ部分更新として送る。ルートの追加は行わない。一覧のトグルは、`is_searchable` のみを含むボディでこれらを呼ぶ。

`reorder_tag`（ADR-0074）が専用ツールである必要があったのは、「1つ上へ」という操作が `display_order` の具体値ではなく**兄弟ノードとの相対関係から値を導出する処理**だったためである。`is_searchable` は値をそのまま書くだけであり、専用ツールに閉じ込める処理が存在しない。ツールを増やさないほうが、MCPのツール一覧（現在すでに40近い）を不必要に膨らませずに済む。

### 決定2: `update_question_altered` の `text` を任意化し、フラグのみの更新では embedding を再計算しない

`text` が `None` のときは `text` とembeddingをどちらも更新しない。`text` と `is_searchable` がともに `None` の場合はエラーとする（更新内容が無いため）。`is_searchable` のみの更新で外部AIサービスの呼び出しを発生させないことは、本ADRの必須要件である。

同様に `update_troubleshooting_article` でも、`is_searchable` は**embedding再計算の判定対象フィールドに含めない**（埋め込み元は `title` / `subtitle` / `symptom` / `cause` / `guidance`、ADR-0079）。

対象が主質問文行（`is_primary = true`）の場合にエラーとする既存ルール（ADR-0064）は維持する。主質問文行の `is_searchable` は管理機能から変更しない（ADR-0092 決定5）。

### 決定3: 一覧ページのトグルは楽観的更新による即時保存とする

1. クライアント側の表示を即座に切り替え、当該行のトグルを `disabled` にする。
2. 更新APIを呼ぶ。
3. 成功: レスポンスの値で確定し、トグルを操作可能に戻す。
4. 失敗: 表示を元の値へロールバックし、ページ上部の既存エラー表示領域にメッセージを出す。

1行あたりの更新要求は同時に1つまでとする。トグル操作では一覧全体の再取得を行わない（ページ位置・検索条件・スクロール位置を保たせるため）。

確認ダイアログは出さない。削除（ADR-0067）と異なり操作は完全に可逆であり、確認を挟むと一覧上で複数件を続けて切り替える作業が煩雑になる。

### 決定4: 編集ページはフォーム保存時に反映する

編集ページ上のチェックボックスは即時保存しない。編集ページは「複数項目をまとめて編集し、保存ボタンで確定する」というモデルであり、その中で1項目だけが即時保存されると、保存せずに離脱したときの状態が項目ごとに食い違う。一覧＝即時、編集＝フォーム保存、という区別を明確にする（発注者の選択）。

### 決定5: UI部品は素の `<input type="checkbox">` にCSSでスイッチ外観を与える

新規のUIライブラリは導入しない（ADR-0015、ADR-0087と同じ抑制）。トグルのスタイルは `style.css` に追加する。検索対象外（実効検索可否が `false`）の行は淡色表示等で視覚的に区別する。

### 決定6: 言い換え質問文一覧では親QAの状態を併せて表示する

AND合成（ADR-0092 決定3）により、行自身が `true` でも親QAが `false` なら検索されない。この乖離を利用者が誤解しないよう、`list_question_altered` ・ `get_question_altered` の出力へ読み取り専用項目 `qa_is_searchable` を追加し、UI側で「親QAが検索対象外」のバッジを表示する。行のトグル自体は親の状態にかかわらず操作可能とする（自身の値は独立して保持されるため）。

### 決定7: 一覧に3値の絞り込みを追加し、URL同期の既存方式に従う

各一覧ページの検索条件に「すべて／検索可のみ／検索不可のみ」のセレクトを追加する。ツール側・API側は `is_searchable: Optional[bool]`（`None`＝すべて）で受ける。

QA一覧・言い換え質問文一覧では選択値をURLクエリ `is_searchable=true|false` として同期する（既定「すべて」はURLから省略、ADR-0068の方針を踏襲）。トラブルシューティング記事一覧は現状URL同期を実装していないため、本ADRでも同ページのURL同期は行わない。

言い換え質問文一覧の絞り込みは**行自身の値**を対象とし、親QAの状態は条件に含めない。「親QAが落ちている行」を条件に含めると、絞り込み結果と表示中のトグル状態が一致せず、一覧としての読み取りが難しくなる。

## 検討した代替案

- **専用ツール `set_qa_searchable` / `set_question_altered_searchable` / `set_troubleshooting_searchable` を新設する**: 操作の意図がツール名に現れ、`update_question_altered` の `text` 必須という既存シグネチャを壊さずに済む。しかし3情報源ぶんでツールが3つ増え、同じ属性の更新経路が「専用ツール」と「update系ツール」の2つに分かれる（編集ページはやはり update 系で送るため）。同一列に更新経路が2本ある状態は、権限・ログ・バリデーションの二重管理を招く。ツールを増やさず、`text` の任意化という小さな互換変更で済ませるほうが総量が小さいと判断した。

- **`PATCH /api/qa/{qa_id}/searchable` のような専用エンドポイントを設ける**: RESTとしては意図が明快。しかし `web_backend` はMCPツールへの薄い中継であり（ADR-0013）、エンドポイントを増やしても中身は `update_qa` の呼び出しに帰着する。`app.py` のルート定義が3つ増えるだけの利得となるため不採用とした。

- **`update_question_altered` の `text` を必須のまま残し、一覧のトグルでは現在の `text` を再送する**: シグネチャを変えずに済む。しかし毎回embeddingが再計算され、Bedrockの呼び出し課金と数百msの待ちがトグル1回ごとに発生する。さらに再送の間に他者が `text` を編集していた場合、その編集を古い値で上書きする危険がある。採用できない。

- **一覧では即時保存せず、変更をまとめて「保存」ボタンで確定する（一括保存方式）**: APIリクエスト数を抑えられ、誤操作を保存前に取り消せる。しかし未保存状態をページ送り・検索条件変更・離脱と整合させる必要があり、一覧ページの状態管理が大きく複雑化する。1クリックで効く即時性のほうが運用要求に合う（発注者の選択）。

- **切り替え時に確認ダイアログを出す（削除と同様、ADR-0067）**: 誤操作を防げる。しかし削除と異なり完全に可逆であり、一覧上で複数件を続けて切り替える作業が確認のたびに中断される。ロールバック付きの楽観的更新で十分と判断した。

- **トグル操作後に一覧を再取得して整合させる**: サーバー側の実際の値で確実に同期できる。しかしページ位置・検索条件・スクロール位置の復元が必要になり、連続操作のたびに一覧全体の再取得が走る。単一レコードの真偽値更新に対しては過剰である。更新レスポンスの値で当該行のみ確定させれば足りる。

- **言い換え質問文一覧の絞り込みを「実効検索可否」（親とのAND後の値）で行う**: 利用者の関心（結局この行は検索されるのか）に直接答えられる。しかし絞り込み結果と行のトグル表示（自身の値）が一致しない行が現れ、「検索不可のみ」で絞ったのにトグルがONの行が並ぶ、という読み取りにくい状態になる。バッジで親の状態を示す（決定6）ほうが誤解が少ない。

- **主質問文行にもトグルを出す**: 「主質問文だけ外す」操作が可能になる。しかし言い換え質問文管理機能の対象は言い換え行のみという既存方針（ADR-0064）に反し、主質問文はQA本体の質問文でもあるため、QA単位のフラグとの関係が二重になる。ADR-0092 決定5に従い対象外とした。

## 結果・影響

- `knowledge_mcp`: `mcp/tools.py` ・ `mcp/schemas.py` と、`repository/qa_management_repository.py` ・ `question_altered_repository.py` ・ `troubleshooting_management_repository.py`、`models/qa.py` ・ `question_altered.py` ・ `troubleshooting.py` を更新する。`update_question_altered` の `text` が任意になるのは**後方互換のある変更**であり（既存の呼び出しは `text` を渡している）、`web_backend` 以外の呼び出し元は存在しない。
- `web_backend`: 3つのコントローラのPydanticモデルに項目を追加し、一覧エンドポイントへクエリパラメータ `is_searchable` を追加する。新規ルートの追加はない。`PUT /api/hiroba_question_altered/{id}` は `text` を任意化し、`text` ・ `is_searchable` がともに未指定の場合に400を返す。
- `front_dev`: 3つの一覧ページに「検索対象」列・トグル・絞り込みセレクトを、3つの編集ページにチェックボックスを追加する。`domain/admin/` の型定義・`api.ts` の引数を更新し、`style.css` にトグルのスタイルを追加する。新規依存パッケージはない。
- 切り替え操作は既存の管理操作ログ（`log_admin_operation`）に `update` として記録される。専用の履歴テーブルは設けない。
- 一覧上のトグル操作は embedding を再計算しないため、Bedrockの呼び出しも課金も発生しない（決定2）。
- 楽観的更新のロールバックのみを行い、レコード単位のロック・更新競合検出は行わない（管理者が少数である前提。既存の編集機能と同一方針）。同一レコードを2名が同時に切り替えた場合、後着の値が残る。
