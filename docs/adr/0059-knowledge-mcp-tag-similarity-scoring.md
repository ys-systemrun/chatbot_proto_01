# ADR-0059: タグ構成類似度と埋め込み類似度を統合したスコアリング方式

- ステータス: Accepted
- 日付: 2026-08-26
- 関連: `docs/requirement/202608261450_タグ階層展開・タグ構成類似度スコアリング機能要件定義書.md`, ADR-0003, ADR-0005, ADR-0049, ADR-0057, ADR-0058

## コンテキスト

現状の`search_knowledge`（`QARepository.search`）は、次の2つの独立した仕組みでQAを絞り込み・ランキングしている。

1. `tags`引数: 指定タグをすべて持つQAのみに絞り込む（完全一致・AND条件、ハードフィルタ）。
2. 埋め込みベクトルの距離（`question_altered.embedding <=> query`）: `distance_to_score`（`1 / (1 + distance)`）でスコア化し、降順で`top_k`件を返す。

発注者から「1つのQAは複数のタグを持つので、入力タグの構成と近い構成でタグ群を持つQAが優先的に取れてくるようにしたい」という要望が示された。これは、タグによる絞り込みを「全一致でなければヒットしない」ハードフィルタから、「タグ構成の近さに応じて順位が変わる」ソフトなランキングシグナルへ変えることを意味する。

また、ADR-0057は、AND条件のハードフィルタが持つ「タグ数が増えるほど該当件数が0件に近づく」という制約を発見し、`agent_invitro`側でタグ別複数回呼び出し＋結果統合というワークアラウンドを実装済みである。この制約は`knowledge_mcp`側のマッチング方式そのものに起因するため、`knowledge_mcp`側で解消できれば、複数の呼び出し元（`agent_invitro`・検証機能・将来の呼び出し元）が同様のワークアラウンドを個別に実装する必要がなくなる。

適用範囲について発注者に確認した結果、「`search_knowledge`全体（全呼び出し元共通）の基本挙動として変える」との回答を得た（要件定義書2章 回答1）。

## 決定

**タグによる絞り込みをハードなAND条件フィルタから撤廃し、ADR-0058のタグ閉包同士のJaccard係数（タグ類似度）を算出した上で、既存の埋め込み類似度と重み付き線形結合した「総合スコア」でランキングする。この総合スコアを`search_knowledge`の`results[].score`とする。**

```
tag_similarity = |入力タグ閉包 ∩ QAタグ閉包| / |入力タグ閉包 ∪ QAタグ閉包|   （Jaccard係数）
combined_score = (1 - w) * embedding_score + w * tag_similarity
```

- `w`（タグ類似度の重み）は環境変数`TAG_SIMILARITY_WEIGHT`（既定値`0.5`）とする。
- `tags`引数が未指定または空配列の場合、`tag_similarity`は算出せず`combined_score = embedding_score`とする（既存の呼び出し元との後方互換性を保つ。要件定義書6.2節）。
- `min_score`は`combined_score`に対して適用する（既存と同じ意味づけを維持する）。
- ハードフィルタの撤廃に伴い、埋め込みベクトルの近傍検索は`top_k`件ちょうどではなく、より多めの「候補プール」（環境変数`SEARCH_CANDIDATE_POOL_SIZE`、既定値`max(top_k * 10, 50)`）を取得し、その中で`combined_score`を計算してから`top_k`件に絞り込む（要件定義書6.4節）。
- `results[].metadata`に`embedding_score`・`tag_similarity`・`tag_similarity_weight`の内訳を追加する（既存の`metadata`は自由記述の`object`型のため、出力スキーマの構造変更にはあたらない）。担当者が検証機能等で結果の妥当性を判断する際、順位の根拠を確認できるようにするため。

## 検討した代替案

- **`tags`をOR条件（いずれか1件でも一致すればヒット）にする**: AND条件の0件化問題は解消できるが、「入力タグの構成に近いQAを優先する」という要望（構成の重なりの多寡を順位に反映する）には応えられない（OR条件は「1件でも一致するか」の二値判定であり、重なりの度合いを表現できない）。Jaccard類似度による連続的なスコアリングを採用した。
- **タグ一致数（重なりの単純カウント）でランキングする**: Jaccard係数より実装がシンプルだが、QAごとにタグの総数が異なる場合に不公平が生じる（タグを多数持つQAほど、入力タグとの偶然の一致数が増えやすい）。Jaccard係数は分母に和集合を取ることでこの偏りを補正できるため、こちらを採用した。
- **`min_score`によるハードフィルタは維持しつつ、`tags`のみソフト化する（2つの異なる絞り込みロジックを併存させる）**: 実装は本決定と大きく変わらないが、「タグは完全一致でなければヒットしない」という現状の直感的な理解と、「タグは加点要素」という新しい挙動が混在すると、呼び出し元・利用者にとって仕様が分かりにくくなる。`tags`引数の意味を完全にソフトなシグナルへ統一する方が、仕様として一貫性がある。
- **埋め込み類似度とタグ類似度を掛け合わせる（乗算）**: 「タグが1件も一致しないQAは`tag_similarity=0`となり、乗算では`combined_score`が常に0になってしまう」ため、埋め込み類似度のみで関連性が高いQA（タグ付けが不十分なQA等）を検索結果から排除してしまう。加重線形結合（和）であれば、タグの重なりがなくても埋め込み類似度のみで結果に含まれ得るため、こちらを採用した。
- **候補プールを設けず全件に対して`combined_score`を計算する（`LIMIT`を使わない全件走査）**: 常に正確なランキングが得られる利点があるが、QA件数が多い場合にベクトル近傍検索のインデックス（pgvectorのANN検索）を活用できず、性能上のリスクが大きい。候補プール方式（一次的にベクトル近傍検索で絞り込んでから再ランキングする、いわゆるハイブリッド検索の一般的な実装パターン）を採用した。候補プールの外側にあるQA（埋め込み類似度が低い）は、タグ類似度が高くても本方式では浮上しない制約が残る（要件定義書12章 Open Issue #3）。

## 結果・影響

- `knowledge_mcp/src/knowledge_mcp/repository/qa_repository.py`の`search`メソッドのSQL・スコア計算ロジックが変更される。`SEARCH_KNOWLEDGE_INPUT_SCHEMA`/`SEARCH_KNOWLEDGE_OUTPUT_SCHEMA`（`mcp/schemas.py`）の型定義自体は変更しない。
- `tags`引数を渡す既存の呼び出し元（`agent_invitro`のADR-0057実装、検証機能のADR-0049実装）は、コード変更なしに新しい挙動（ソフトなランキング）へ自動的に移行する。ただし、`score`が返す値の意味が変わるため、`score`をしきい値判定や表示に使っている箇所は、新しい意味（総合スコア）での動作になる。
- ADR-0057の`search_with_merged_tags`（タグ別複数回呼び出し＋統合）は、本ADRによりAND条件の0件化リスクが解消されるため、単純化（マージタグ全件を1回の`tags`引数で渡す）できる可能性が高い。ただし本ADRの範囲では`agent_invitro`側の実装変更は行わず、別途評価の上で判断する（要件定義書12章 Open Issue #1）。
- `TAG_SIMILARITY_WEIGHT`・`SEARCH_CANDIDATE_POOL_SIZE`の適正値はプレースホルダーの既定値であり、実データでの検索精度評価を通じて調整が必要（要件定義書12章 Open Issue #2・#3）。
