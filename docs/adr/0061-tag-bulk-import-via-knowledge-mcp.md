# ADR-0061: タグ単体の一括インポート機能の実装方式（Knowledge MCP経由の新規バッチツール、タグ名によるupsert）

- ステータス: Accepted
- 日付: 2026-08-26
- 関連: `docs/requirement/202608261600_タグデータ一括インポート機能要件定義書.md`, 実装指示書 `docs/implementation_handoff/202608261630_タグデータ一括インポート機能実装指示書.md`, ADR-0005, ADR-0006, ADR-0008, ADR-0013, ADR-0053

## コンテキスト

ADR-0053により、QAデータの一括インポート機能（`import_qa_batch`）が実装され、CSVの`tags`列で指定したタグ名は既存タグを名前で解決し、存在しないタグ名は自動的に新規タグとして作成されるようになった。ただし、この自動作成ロジック（`qa_management_repository.py`の`_resolve_tag_names`）は`tag_repository.create_tag(name=name)`を`parent_tag_id`を指定せずに呼び出しており、作成されるタグは常にルート直下のフラットなタグになる。

一方、`tag`テーブルは当初から`parent_tag_id`による自己参照の親子構造を持つ設計になっており（ADR-0005）、`create_tag`/`move_tag`等の既存のタグ管理ツール（ADR-0006）は`parent_tag_id`を指定した階層登録・再配置に対応している。しかし、これらは`front_dev`のタグ管理画面（`TagTreePage`）から1件ずつ操作する経路のみが提供されており、まとまった数のタグ（階層構造を含む）を一度に登録・更新する手段がない。

発注者より、QAデータとは独立して「タグ単体」の一括登録・更新機能を追加したいという要望が示された。想定される主なユースケースは、既存のタグ体系をCSV等でまとめて整理・登録し直す運用（例: `data/tags.txt`のような既存の階層データからの初期タキソノミー投入）である。

## 決定

**Knowledge MCPサーバに、複数件のタグをまとめて登録・更新する新規MCPツール（`import_tag_batch`、仮称）を追加する。`web_backend`はCSVをパースした上でこのツールを呼び出し、`chatbot`データベースへは直接書き込まない（ADR-0013の既存方針を維持）。**

- **CSV列構成**: `name`（必須、タグ名）, `parent_name`（任意、親タグ名。空欄はルート直下＝親なしを意味する）, `description`（任意）。
- **新規/更新の判定**: タグ名（`name`列）の一致でupsertする。CSVの`name`が既存の`tag.name`と一致すれば更新（`parent_name`・`description`を反映）、一致しなければ新規作成する。`tag.name`は既存のUNIQUE制約（DB全体で一意）を維持し、変更しない。
- **リネームは対象外**: `name`列を更新対象の識別キーとして使うため、この一括インポートでは既存タグの名称変更（リネーム）は扱えない。CSVで新しい名前を指定すると別タグとして新規作成されてしまうため、リネームは既存の`rename_tag`（個別編集、`TagTreePage`）に委ねる。この制約は要件定義書・UI双方で明示する。
- **親タグの解決順序**: `parent_name`はCSV内の行の並び順に依存せず解決する。実装は、1パス目で名前解決できる行から確定させ、未解決の行は次パスに繰り越す、という反復処理（複数パス）で行う。全パス終了後も親タグ名が解決できない行（既存タグにもCSV内の他行にも存在しない）はエラーとして報告し、他行の処理は継続する（ADR-0053と同様、行単位のエラー許容）。
- **循環参照チェック**: 既存の`create_tag`/`move_tag`が持つ循環参照防止ロジック（ADR-0006）をそのまま再利用する。CSV内で循環する親子関係（例: AをBの親、BをAの親と指定）が指定された行は、検出された時点でエラーとして報告する。
- **新規ツールの位置付け**: `import_tag_batch`は、既存の`create_tag`/`rename_tag`/`move_tag`（`knowledge_mcp/src/knowledge_mcp/mcp/tools.py`、`repository/tag_repository.py`）が持つバリデーション・循環参照チェックロジックをループ処理で複数件に適用する薄いラッパーとして実装する（ADR-0053の`import_qa_batch`と同じ設計方針）。
- **`web_backend`の役割**: CSVの構文解析（列数・必須項目の存在チェック等の機械的なバリデーション）のみを担い、業務的なバリデーション（循環参照チェック等）はKnowledge MCP側に委ねる。
- **UI**: `front_dev`のタグ管理画面（`TagTreePage`）に、既存のQA管理画面（`QaListPage`）のCSVインポートUIと同様のパターン（アップロードボタン＋結果一覧表示）で追加する。

## 検討した代替案

- **同一タグ名を異なる親タグの下に複数許容する（`tag`のUNIQUE制約を`name`単独から`(name, parent_tag_id)`の複合制約に変更する）**: 発注者との検討の中で候補に挙がったが、既存のQA一括インポート（ADR-0053）のタグ名解決ロジック（`_resolve_tag_names`、名前のみで検索）をはじめ、タグ名をキーに参照している既存コンポーネントへの影響範囲が広く、既存システムの前提（タグ名はシステム全体で一意）を大きく変える改修になる。発注者確認の結果、タグ名は引き続き全体で一意とする方針に決定し、不採用とした。
- **`tag_id`列による明示的な更新（QA一括インポート、ADR-0053と同一方式）**: `uuid`列を使うQAとは異なり、タグの主要ユースケース（既存タキソノミーのCSVからの初期投入・整理）では、CSV作成者が内部の`tag_id`を事前に把握していないことが多い。IDを必須にすると新規タキソノミー投入という主要ユースケースに使いづらくなるため不採用とし、名前ベースのupsertを採用した。
- **既存の`import_qa_batch`の`tags`列の自動作成ロジックを拡張し、階層指定に対応させるだけで済ませる（専用ツールを追加しない）**: QAを1件も伴わない「タグ体系だけの整理・投入」というユースケースに対応できず、ダミーのQA行を用意する不自然な運用が必要になる。タグ単体の登録・更新は独立した操作として提供する方が自然と判断し、専用ツールの新設を優先した。

## 結果・影響

- `knowledge_mcp`に新規ツール（`import_tag_batch`）とその実装（既存`tag_repository`のループ呼び出し）が追加される。既存の`create_tag`/`rename_tag`/`move_tag`/`delete_tag`の既存関数には変更を加えない。
- `web_backend`にCSVアップロード受付・パース処理（新規コントローラまたは既存タグ関連コントローラの拡張）が追加される。
- `front_dev`のタグ管理画面（`TagTreePage`）に、CSVアップロードUIとインポート結果表示（成功件数・行ごとのエラー）が追加される。
- `import_qa_batch`（ADR-0053）の新規タグ自動作成ロジックには変更を加えない（フラット作成のまま）。両機能は独立したツールとして併存する。
- CSVフォーマットの詳細（区切り文字、文字コード等）、ファイルサイズ・件数上限は、要件定義書のOpen Issueとして引き継ぐ。
