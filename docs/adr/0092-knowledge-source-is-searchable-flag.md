# ADR-0092: 情報源レコードに検索対象フラグ（is_searchable）を新設し、検索除外を候補取得SQLの述語として実装する

- ステータス: Accepted
- 日付: 2026-09-16
- 関連: ADR-0004（MVPスコープ・Repository構成）、ADR-0014（QA管理ツール）、ADR-0017（マイグレーションツール）、ADR-0058（祖先タグ展開）、ADR-0059（タグ構成類似度スコアリング）、ADR-0064（言い換え質問文管理）、ADR-0067（QAレコード削除）、ADR-0076 / ADR-0078（トラブルシューティング情報源）、ADR-0088（Agentic回答生成）、`docs/requirement/202609160930_情報源レコード検索対象フラグ（is_searchable）機能要件定義書.md`（4章 / 6.1〜6.3節）

## コンテキスト

現在、`search_knowledge` が返しうる情報源レコードは次の3種類である。

| 情報源 | テーブル | 検索の単位 |
|---|---|---|
| 維津美の広場QA | `hiroba_qa_original` + `hiroba_question_altered` | 質問文（主質問文行・言い換え行）1行 = 1候補 |
| トラブルシューティング記事 | `troubleshooting_article` | 記事1件 = 1候補（ADR-0078 決定3） |

いずれの Repository も、候補プール（`max(top_k * 10, 50)` 件）をベクトル距離順に取得し、タグ構成類似度と重み付き合成して `top_k` 件を返す。**レコードを検索対象から外す条件は現在どこにも存在しない**（`troubleshooting_article.embedding IS NOT NULL` の除外のみ）。

このため、運用上「内容が古い」「誤りが判明した」「公開前である」といった理由でチャットの回答根拠に使わせたくないレコードが見つかっても、運用者が取れる手段は次の2つしかない。

1. 内容を直す（是正方針が決まるまで時間がかかる。その間も誤答し続ける）
2. 削除する（ADR-0067。`hiroba_qa_tag` ・ `hiroba_question_altered` をカスケード削除するため、復帰にはタグ付け・言い換えの再作成が必要で事実上不可逆）

「一時的に検索から外す」という、実運用で最も頻度が高い中間的な対処ができない。運用者向けアドホックSQL実行（ADR-0083）で直接DBを書き換えることは可能だが、これは緊急時の手段であり日常運用の手順としては適切でない。

また、言い換え質問文の単位でも「この言い換えだけがノイズとして過剰にヒットする」という事象が起こりうるが、現状の対処は当該言い換え行の削除のみである。

## 決定

**`hiroba_qa_original` ・ `hiroba_question_altered` ・ `troubleshooting_article` の3テーブルに `is_searchable BOOLEAN NOT NULL DEFAULT true` を追加し、`search_knowledge` の除外を各 Repository の候補取得SQLの `WHERE` 句の述語として実装する。QAと言い換え行の関係はAND合成（QAが親スイッチ）とする。**

### 決定1: 列は3テーブルすべてに持たせ、既定値は `true`

| テーブル | 列 | 意味 |
|---|---|---|
| `hiroba_qa_original` | `is_searchable` | QA全体（配下の主質問文行・言い換え行を含む）を検索対象とするか |
| `hiroba_question_altered` | `is_searchable` | 当該の質問文を候補とするか |
| `troubleshooting_article` | `is_searchable` | 当該記事を検索対象とするか |

`NOT NULL DEFAULT true` とし、NULL許容（三値論理）は採らない。既存行にはすべて `true` が入るため、**マイグレーション適用直後の検索挙動は適用前と完全に同一**である。マイグレーション（`migrations/0010`）は `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` による冪等なSQLステップとし（`0004` `0005` と同形式）、ダウングレードステップは用意しない。

索引は追加しない。値の大半が `true` で選択率が低いこと、検索側の候補取得は既にベクトル距離順の全走査であること（ベクトル索引を張っていない）、管理画面の一覧は `limit`/`offset` ページングであることによる。

### 決定2: 除外は Repository の候補取得SQLで、候補プールの `LIMIT` より前に適用する

`QARepository` の候補取得SQLの `WHERE` 句へ次を追加する。

```sql
hiroba_question_altered.is_searchable
AND COALESCE(hiroba_qa_original.is_searchable, true)
```

`TroubleshootingRepository` は既存の `WHERE troubleshooting_article.embedding IS NOT NULL` へ `AND troubleshooting_article.is_searchable` を追加する。

いずれも `ORDER BY ... LIMIT %(pool_size)s` の**前**に適用される位置に置く。これにより、検索対象外のレコードが候補プールの枠を消費せず、除外した分だけ他の候補が繰り上がる。Python側でのフィルタ（取得後に落とす）は採らない（代替案の節を参照）。

第2項を `COALESCE(..., true)` とするのは、現行SQLが `hiroba_qa_original` を `LEFT JOIN` しており、親QAが存在しない孤児行が理論上ありうるためである。従来これらは検索結果に含まれていたため、**孤児行の扱いを本変更で変えない**。

スコアリング（ADR-0058の祖先タグ展開、ADR-0059のタグ構成類似度と埋め込み類似度の合成）・`min_score` ・ `top_k` の意味論には一切手を加えない。除外は候補集合の定義のみに作用する。

### 決定3: QAと言い換え行はAND合成（QAが親スイッチ）

言い換え行（および主質問文行）が候補となるのは、`当該行の is_searchable = true` かつ `親QAの is_searchable = true` の場合に限る。

- QAの `is_searchable = false` は、配下の全行を一括で無効化する親スイッチとして働く。
- QAを `false` にしても配下の言い換え行の値は**書き換えない**。QAを `true` に戻すと、各行は切り替え前の自身の値のまま復帰する。

「QA単位で止める」と「特定の言い換えだけ止める」という、運用上要求される2つの操作がどちらも1つの列で表現でき、しかも前者の操作が後者の設定を破壊しない（発注者の選択）。

### 決定4: `search_knowledge` の入出力スキーマは変更しない

検索側に「検索対象外も含める」といった引数は追加しない。結果として、`search_knowledge` を呼び出すすべての経路（`agent_invitro` の `/ask-pipeline` ・ `/ask-agentic`、検証機能の実行パイプライン（ADR-0049）、デバッグ用スクリプト）は**コード変更なしで一律に除外が効く**。除外の意味論がMCPサーバー側に1箇所だけ存在する状態を保つ。

`/ask-agentic` のAgenticループ（ADR-0088）は、除外されたレコードを再検索でも得られない。十分な情報源が見つからない場合は既存の縮退挙動（回答不能・逆質問）に従う。

### 決定5: 主質問文行の `is_searchable` は管理機能から変更しない

`hiroba_question_altered` の主質問文行（`is_primary = true`）にも列は存在するが、管理ツール・管理UIからは変更できず常に `true` のままとする。主質問文はQA本体の質問文そのものであり、QA単位のフラグ（決定3）で制御できる。言い換え質問文管理機能の操作対象を言い換え行のみとする既存方針（ADR-0064）と一致させる。

### 決定6: 「除外」は完全除外であり、スコア減衰や注記付き返却は採らない

`is_searchable = false` のレコードは検索結果に一切現れない。低いスコアを与えて残す、メタデータに印を付けて返す、といった中間状態は設けない。運用者がフラグを落とす動機は「この情報を根拠に使わせたくない」であり、部分的に残る挙動はその意図を裏切る。

## 検討した代替案

- **削除（ADR-0067）で運用し、フラグを設けない**: 変更コストはゼロ。しかしカスケード削除により復元不能であり、「一時的に外す」という主要な運用要求を満たさない。復帰時のタグ付け・言い換えの再作成コストも大きい。

- **`status` 列（`draft` / `published` / `archived` 等の列挙型）にする**: 将来の状態追加に強く、ワークフロー（承認フロー）へ発展させやすい。しかし現時点で必要な区別は「検索に出す／出さない」の二値のみであり、列挙型にすると「どの状態が検索対象なのか」を検索SQL・管理UI・CSV・インポータの各所で解釈する必要が生じる。二値で足りる要求に対して解釈の分岐点を増やすことになるため不採用とした。承認フローが要件化された段階で、`is_searchable` を導出値とする `status` の導入を改めて検討する。

- **除外用の別テーブル（`excluded_record` 等）を新設する**: 既存テーブルのスキーマを変更せずに済み、除外理由・除外日時・操作者を併せて持たせられる。しかし検索SQLに `NOT EXISTS` の相関サブクエリが3箇所増え、全データエクスポート（ADR-0047）・全消去インポート（ADR-0066）の対象テーブルも増える。除外理由の記録は現時点の要求に含まれておらず（要件定義書4.2節）、構成の複雑化に見合わないと判断した。

- **Python側で候補取得後にフィルタする**: SQLを変更せずに済み、Repository間で共通のフィルタ関数に切り出せる。しかし検索対象外のレコードが候補プール（`max(top_k * 10, 50)` 件）の枠を消費するため、除外されたレコードが上位に固まっている場合に返却件数が `top_k` に満たなくなる。候補プールを広げる補正は、除外件数に依存する不安定な調整になる。SQLの述語であればこの問題が構造的に発生しない。

- **`SearchService` に共通のフィルタ層を設けて一括除外する**: Repository ごとの重複（同じ述語を2箇所に書く）を避けられる。しかし `SearchService` は Document の集約・整列のみを責務とする薄い層であり（ADR-0004）、除外条件のためにレコードの出自テーブルを知る必要が生じる。また前項と同じく候補プール消費の問題が残る。Repository が自分の情報源の「検索に出せる集合」を定義するほうが責務として自然である。

- **QAと言い換え行を完全に独立させる（親のANDを採らない）**: 検索SQLの述語が1つ減り、意味論も単純になる。しかし「このQAを丸ごと止めたい」という最も頻度の高い操作のたびに、配下の全言い換え行を個別に落とす必要があり、復帰時には「元々どの行が有効だったか」が失われる。発注者の選択によりAND合成を採用した。

- **言い換え行にフラグを持たせず、QA単位だけにする**: 列が1つ減り管理UIも単純になる。しかし「特定の言い換えだけがノイズになる」事象への対処が当該行の削除のみとなり、削除を避けるという本ADRの動機と矛盾する。

- **`search_knowledge` に `include_unsearchable` 引数を足し、管理用途では全件を見えるようにする**: 管理画面のプレビュー用途には便利。しかしフラグの意味が呼び出し側次第で変わり、「除外されているはずのレコードが特定経路では返る」という状態が生まれる。管理画面が必要としているのは検索結果ではなく管理ツール（`list_qa` 等）による一覧であり、そちらに絞り込み引数を設ければ足りる（ADR-0093）。

## 結果・影響

- `db_hiroba_qa_init/migrations/0010_add_is_searchable.sql` を追加する。適用は冪等であり、既存の全レコードが `true` となるため**適用直後の検索結果・スコアは適用前と完全に一致する**。
- `knowledge_mcp/src/knowledge_mcp/repository/qa_repository.py` ・ `troubleshooting_repository.py` の候補取得SQLに述語が1〜2行加わる。Python側のスコアリング処理・戻り値の構造は変更しない。
- `knowledge_mcp` の管理系 Repository・モデル・ツール（`list_qa` 等）にも `is_searchable` の入出力が加わる。詳細はADR-0093。
- `agent_invitro` ・ `tag_selector_mcp` ・ `terraform` ・ `conversation` データベースには変更がない。
- 検証機能（ADR-0048〜0050）の実行結果は実行時点のフラグ状態に依存するようになる。過去の実行履歴（`verification_run_source`）と再実行結果が食い違いうるが、履歴は実行時点のスナップショットであるという既存方針の範囲内として許容する。
- 全データエクスポート／全消去インポート（ADR-0047・ADR-0066）の対象3テーブルに列が1つ増える。SQLダンプの `INSERT` は列名を明示する形式であるため、**本変更前に取得した既存ダンプはそのまま投入でき、全レコードが `true` となる**。事前自動バックアップは `information_schema` から列を動的に取得するため変更不要。
- デプロイ順序は **マイグレーション（0010）→ `knowledge_mcp` → `web_backend` → `front_dev`** とする。列が存在しない状態で新しい `knowledge_mcp` が動くとSQLエラーになる。逆にマイグレーションのみ先行適用した状態は無害である。
- 運用上、「検索対象外のまま放置されるレコード」が蓄積しうる。棚卸しの運用ルールは要件定義書11章のOpen Issueとして残す（`hiroba_qa_original` ・ `hiroba_question_altered` には更新日時列がないため、更新日時順の棚卸しを行うには別途列追加が必要）。
