# 調査報告: 実チャットの情報源検索結果が検証ページと異なる（AWS環境）

- ステータス: 根本原因を再特定（下記「7. 追記」参照）。当初結論（4章）はADR-0063により訂正済み。
- 日付: 2026-08-27
- 報告種別: 検出された問題（`docs/detected_problems/`）
- 関連: ADR-0057, ADR-0058, ADR-0059, ADR-0060, ADR-0062, ADR-0063, `docs/requirement/202608261450_タグ階層展開・タグ構成類似度スコアリング機能要件定義書.md`（12章 Open Issue #1）

> **注意（2026-08-27 追記）**: 本報告の当初の根本原因（4章）は、後日のAWS実機ログ確認により**誤り**であったことが判明した。実際の原因は「MCPアダプタ戻り値のパース欠陥により会話タグが常に空になっていたこと」である。詳細は末尾「7. 追記」およびADR-0063・`docs/requirement/202608271500_agent_invitroタグ選択結果取得不具合修正要件定義書.md`を参照。

## 1. 報告された事象

AWSデプロイ環境において、検証ページ（質問→タグ抽出→情報源検索の精度検証機能、ADR-0048〜0050/0060）では質問に対するタグ抽出・タグからの情報源取得が意図通りに機能しているように見える一方、実際のChat機能（`agent_invitro`の`POST /ask-sl`、ADR-0043/0057）で同種の質問をすると、情報源の取得がうまくいっていないように見える。

## 2. 調査方法

`docs/adr/`配下の関連ADR（0009, 0011, 0021〜0023, 0025, 0043, 0045, 0049, 0056〜0060）および関連要件定義書・実装指示書を確認したうえで、以下のソースコードを確認した。

- `web_backend/src/main/controllers/verification_controller.py`（検証ページのオーケストレーション）
- `agent_invitro/src/main/api/server.py`・`agent_invitro/src/tags.py`（実チャットのオーケストレーション）
- `knowledge_mcp/src/knowledge_mcp/repository/qa_repository.py`（`search_knowledge`のスコアリング実装）
- `terraform/main/app/main.tf`（AWS上のネットワーク到達性・環境変数）

AWS環境固有の設定差異（サービスディスカバリ、環境変数、セキュリティグループ等）についても比較したが、`agent_invitro`と検証ページ（`web_backend`/`admin_ui`）はいずれも`tag_selector_mcp`・`knowledge_mcp`へ同一の経路・同等の設定で到達しており、AWS特有の接続不備は見つからなかった。差異はアプリケーションロジック側にある。

## 3. 判明した事実

### 3.1 検証ページの検索方式（現行・ADR-0060準拠）

`verification_controller.py`（327行目付近）:

```python
# --- search_knowledge: 既存タグ＋新規タグを1回で渡す（ADR-0060、4章の前提に注意） ------ #
merged_tag_names = list(dict.fromkeys(existing_tags + [t.tag_name for t in tags]))
...
search_result = await _knowledge_client.call_tool(
    "search_knowledge",
    {"query": question.question_text, "tags": merged_tag_names, "top_k": top_k, "min_score": min_score},
)
```

マージ済みタグ全件を**1回**の`search_knowledge`呼び出しに渡す。これはADR-0058/0059により`search_knowledge`の`tags`引数が「完全一致AND条件」から「タグ類似度によるソフトなランキングシグナル」に変更されたことを前提にした実装であり、この変更以降（2026-08-26）に作られた検証ページ・ADR-0060はこの新方式に準拠している。

### 3.2 実チャットの検索方式（ADR-0057策定時のワークアラウンドが残存）

`agent_invitro/src/tags.py`の`search_with_merged_tags`（`main/api/server.py`の`_ask_impl`から呼ばれる）:

```python
calls = [
    search_tool.ainvoke({"query": query, "tags": [t.name], "top_k": top_k})
    for t in merged_tags
]
if fallback_enabled:
    calls.append(search_tool.ainvoke({"query": query, "top_k": top_k}))
...
if doc_id not in by_id or doc.get("score", 0) > by_id[doc_id].get("score", 0):
    by_id[doc_id] = doc
```

マージ済みタグを**1件ずつ**別々に`search_knowledge`へ渡し（最大`TAG_CONTEXT_MAX_TAGS`＝5回）、さらにタグ指定なしのフォールバック呼び出しを1回追加し、合計最大6回の呼び出し結果をQA単位でスコア最大値により統合している。`top_k`もハードコードで3（検証ページの既定5とも異なる）。

この方式はADR-0057策定時点（2026-08-26、`search_knowledge`の`tags`引数がまだ完全一致AND条件だった時点）で、「マージタグ数が増えるほど『全タグを同時に持つQA』が減り、会話が進むほど検索結果が0件に近づくリスクがある」という制約を回避するために採用されたワークアラウンドである（ADR-0057本文に明記）。

### 3.3 プロジェクト自身がこの不整合を既知の未解決課題として記録している

`docs/requirement/202608261450_タグ階層展開・タグ構成類似度スコアリング機能要件定義書.md`（179行目、12章 Open Issue #1）に以下の記載がある（原文引用）:

> 「ADR-0057の`search_with_merged_tags`（`agent_invitro/src/tags.py`）は、AND条件によるタグ数増加時の0件化を避けるために『タグ別複数回呼び出し＋統合』というワークアラウンドを実装済みである。本書により`tags`引数がソフトなランキングシグナルに変わるため、このワークアラウンドを使わずマージタグ全件を1回の`tags`引数で渡しても、以前のような0件化のリスクは大幅に下がると見込まれる。ただし、本書のスコープでは`agent_invitro`側の実装変更（ワークアラウンドの単純化）は行わない。要否・実施タイミングは別途判断する。」

つまり、`knowledge_mcp`のスコアリング方式が変更された際（ADR-0058/0059）、`agent_invitro`側のワークアラウンド（ADR-0057）が前提としていた制約（AND条件による0件化リスク）自体は解消されたが、`agent_invitro`側の実装はこの変更に追随せず、旧方式のまま残された。検証ページ（ADR-0060）は新方式を前提に実装されたため、両者の間に実装上の世代差（バージョンスキュー）が生じている。

## 4. 根本原因（結論）

**実チャット（`agent_invitro`）の情報源検索が、検証ページとは異なる、かつ`knowledge_mcp`の現行スコアリング方式（ADR-0058/0059）とは整合しない旧方式（ADR-0057のタグ別複数回呼び出し＋最大値統合ワークアラウンド）のままになっていることが根本原因である。**

具体的には、タグ別に個別実行される各`search_knowledge`呼び出しは、そのタグ単独の閉包に対するタグ類似度のみでスコアが計算され、かつタグ指定なしのフォールバック呼び出し（埋め込み類似度のみ）の結果とも混在して「QAごとの最大スコア」で統合される。これは検証ページが行う「マージタグ全件を1回で渡した場合の、全体最適なタグ類似度計算」とは数学的に異なる結果になり、実チャットの情報源検索結果が検証ページの結果より劣化・不一致になり得る。

これはAWS環境固有の設定不備ではなく、コード実装レベルの世代差であるため、**ローカル環境や他の環境でも同様に再現する**と考えられる（本調査ではAWS特有のネットワーク・環境変数設定に不整合がないことを確認済み）。

## 5. 未確認事項（ユーザーへの確認が必要な事項）

対応方針を判断する前に、以下の確認をお願いしたい。

1. **再現条件**: 事象は会話の1ターン目から発生するか、それとも2ターン目以降（会話タグが蓄積された後）のみで発生するか。
2. **観測方法**: 「情報源の取得がうまくいっていない」という判断は、どこで何を見て判断したか（例: 回答内容が的外れに見える／管理画面の評価済みメッセージ一覧`EvaluatedMessagesPage`の`input`列に表示される参考情報が検証ページの結果と違う、など）。実チャットのエンドユーザー向けUIには「情報源」を直接表示する要素が現状存在しない（`front_dev`のチャットUIコンポーネントを確認したが、「情報源」に相当する表示は検証ページ側にのみ存在する）ため、判断根拠を確認したい。
3. **ローカル環境での再現有無**: ローカル/開発環境でも同一質問で同様の差異が再現するか（AWS特有ではないことの追加確認として）。
4. **本事象はリグレッションか**: ADR-0057〜0060がリリースされた2026-08-26以降に発生し始めたものか、それ以前から一貫して見られる傾向か。

## 6. 対応方針（選択肢・要判断）

本書では実装（コーディング）は行わないため、対応方針の決定と、それに基づく要件定義・ADR起票を行うかどうかはユーザー側の判断を仰ぎたい。プロジェクト自身の記録（上記3.3のOpen Issue #1）でも「対応要否は別途判断する」とされているため、今回の調査結果をもってその判断を行う好機と考える。選択肢は概ね以下の通り。

- (a) `agent_invitro`側のワークアラウンド（タグ別複数回呼び出し＋統合）を、検証ページと同じ「マージタグ全件を1回で渡す」方式に単純化する方向で、新たな要件定義・ADRを起票する。
- (b) 現状維持のまま、両方式の実測比較（検索結果・レイテンシ）を先に行い、その結果を踏まえて要件定義・ADRを起票する。
- (c) その他の方針（例: 一部条件下のみ方式を切り替える等）を検討する。

ご希望であれば、上記4章の未確認事項へのご回答を踏まえて、(a)または(b)に沿った要件定義書・ADRのドラフト作成に着手する。

## 7. 追記（2026-08-27）: 根本原因の再特定 — 4章の結論は誤りだった

上記6章(a)の方針で単一`search_knowledge`呼び出し化（ADR-0062）を実装しAWSへデプロイしたが、**事象は解消しなかった**。その後、AWS実機（CloudWatch Logs `/ecs/agent_invitro`・ECSタスク定義）を直接確認し、真因を再特定した。

- **デプロイは正しく反映されていた**: `agent_invitro`タスク定義 rev 11 が 2026-08-27 10:20（JST）にロールアウト完了、環境変数`TAG_SEARCH_FALLBACK_ENABLED`も削除済み。反映漏れではない。
- **実チャットのログは、デプロイ前後を通じて一貫して `merged_tags=0`**（例: デプロイ後10:28のトレースで、`select_tags`は`HTTP 200 OK`で成功しているのに`search_with_merged_tags ... merged_tags=0 hits=1`）。すなわち会話タグが常に空で、検索は常にタグなしの埋め込み類似度のみで動いていた。

**真の根本原因**: `agent_invitro`は`langchain-mcp-adapters`（ADR-0021）でMCPへ接続しているが、`select_tags`結果を取り出す`_extract_selected_tags`（`agent_invitro/src/tags.py`）が、アダプタの返す「テキストブロックのlist」形式に対応しておらず無言で空配列を返していた。このため`new_tags`＝`merged_tags`が常に0となり、タグ選択がリリース以来一度も機能していなかった。検索側`_extract_results`にも同種の欠陥がある疑いが強い（`hits`が観測上つねに1）。動作している検証ページは独自クライアントで`structuredContent`を直接読むため差が出ていた。

**4章の結論（「呼び出し方式の世代差」）は誤りであり、呼び出し方式の単純化（ADR-0062）は事象と無関係だった**（ADR-0059により`tags`未指定と空配列は同一扱いのため、マージタグが常に空である以上、旧方式と新方式は同一結果になる）。

**是正**: MCPアダプタ戻り値のパース頑健化と診断ログ追加として、`docs/requirement/202608271500_agent_invitroタグ選択結果取得不具合修正要件定義書.md`・ADR-0063を起票した。ADR-0062の単一呼び出し化自体は正しい方向のため維持する（差し戻さない）。
