## 2. T1: `db_hiroba_qa_init/src/main.py`（マイグレーション専用モード）

### 2.1 環境変数の追加

`IMPORT_MODE` 定義の直後に、同じ真偽値判定方式で `MIGRATE_ONLY` を追加する。

```python
MIGRATE_ONLY = os.environ.get("MIGRATE_ONLY", "").strip().lower() in ("1", "true", "yes")
```

### 2.2 `main()` のシード投入呼び出しをガード

`migrate(chatbot_work_url)` の直後、`seed_if_empty(chatbot_work_url)` の呼び出しを条件分岐に置き換える。**手順1・2・4・5・6（`ensure_chatbot_roles` / `migrate` / `grant_chatbot_app_privileges` / conversation 一式 / `ensure_export_reader_role`）は一切変更しない。**

```python
migrate(chatbot_work_url)
if MIGRATE_ONLY:
    print(
        f"{_now()} MIGRATE_ONLY is set; skipping chatbot seed insertion "
        "(ADR-0075). Roles / migrations / grants are still applied."
    )
else:
    seed_if_empty(chatbot_work_url)
if chatbot_roles_enabled:
    grant_chatbot_app_privileges()
```

### 2.3 位置づけ・非機能

- `IMPORT_MODE` 分岐（`main()` 冒頭で `run_import_mode()` へ抜ける）とは独立。`MIGRATE_ONLY` は通常フロー内でシード投入のみを飛ばすため、`IMPORT_MODE` の破壊的経路（TRUNCATE 等）は一切通らない（REQ 7 非破壊性）。
- 冪等性・終了コード（正常時0/異常時非0）・例外処理は既存 `main()` のまま（ADR-0018）。
- モジュール docstring に3モード（通常 / `MIGRATE_ONLY` / `IMPORT_MODE`）の要約を追記する。

## 3. T2: `terraform/deploy/src/commands.py`

### 3.1 共通処理 `_run_db_init_task` の抽出

既存 `cmd_seed` の「両構成 apply 済み確認 → output 取得 → run-task → STOPPED 待機 → exitCode 確認」を、`migrate_only` フラグと `label`（ログ用）を受け取る内部関数へ抽出する。`migrate_only=True` のときのみ、ADR-0066 で実装済みの `aws.run_import_task` を `environment={"MIGRATE_ONLY": "true"}` で呼び出す（`container_name=family`）。それ以外は既存の `aws.run_seed_task` を使う。**`aws.py` は変更しない。**

```python
def _run_db_init_task(cfg, *, migrate_only: bool, label: str) -> None:
    region = cfg.aws_region
    # 両構成 apply 済み確認 → database/app output 取得（既存 cmd_seed と同一）
    ...
    if migrate_only:
        task_arn = aws.run_import_task(
            cluster, family, subnets, sg, region,
            container_name=family, environment={"MIGRATE_ONLY": "true"},
        )
    else:
        task_arn = aws.run_seed_task(cluster, family, subnets, sg, region)
    task = aws.wait_task_stopped(cluster, task_arn, region)
    if str(aws.task_exit_code(task)) != "0":
        raise DeployError(f"{label}が異常終了しました ... CloudWatch Logs /ecs/{family} ...")
```

### 3.2 `cmd_seed` への `skip_seed` 追加（後方互換）

`cmd_seed(assume_yes=False, skip_seed=False)` に変更する。`skip_seed=True` のときは `_run_db_init_task(cfg, migrate_only=True, label="マイグレーション")` を呼んで return する。`skip_seed=False`（既定）のときは従来どおり `migrate_only=False` で実行し、末尾の「knowledge_mcp を起動するには apply-app（desired_count=1）...」案内も従来どおり出す。`cmd_apply_all` が呼ぶ `cmd_seed(assume_yes=True)` は挙動不変。

### 3.3 `cmd_migrate` の新設

```python
def cmd_migrate() -> None:
    cfg = config.load_config()
    prerequisites(cfg)
    _run_db_init_task(cfg, migrate_only=True, label="マイグレーション")
```

- `--yes` 相当・`confirm_typed` は設けない（REQ 6.2、非破壊のため常に無人実行可）。
- `cmd_seed(skip_seed=True)` と `cmd_migrate()` は同一の `MIGRATE_ONLY=true` オーバーライドに収束する（同一結果）。

### 8.1 手動確認手順

- ローカル: `MIGRATE_ONLY=true docker compose run --rm db_hiroba_qa_init` を実行し、ログに `skipping chatbot seed insertion` が出て exitCode=0 になること、`hiroba_qa_original` 等が空のまま（シード未投入）でマイグレーションが適用されていることを確認する。
- AWS: 両構成 apply 済みの環境で `migrate.bat` をダブルクリック（または `deploy migrate`）し、`/ecs/db-hiroba-qa-init` ロググループでシードスキップと exitCode=0 を確認する。再実行して「適用対象なし」で正常終了することを確認する。

## 9. 影響範囲・非互換

- 後方互換: `MIGRATE_ONLY` 未設定時の main.py、`seed`（`--skip-seed` 未指定）、`apply-all`、`import-data`、`destroy-*` は挙動不変。
- 新規インフラ（ECSタスク定義・ECR・IAM）は追加しない。既存 `db_init_task_family` への `ecs:RunTask` 権限をそのまま利用する（REQ 8.2）。
