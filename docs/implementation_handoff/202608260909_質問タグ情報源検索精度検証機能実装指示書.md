## 5. リソース仕様

### 5.1 DDL（T1・T3で共通の4テーブル定義）

`db_conversation/init.sql`（ローカル、既存の`conversation`/`message`テーブルに続けて追加）と、`db_hiroba_qa_init/src/main.py`の`_CONVERSATION_SCHEMA_DDL`（AWS、同一文字列を追記）の両方に、次のDDLを追加する。両ファイルで内容が食い違わないよう、同一のSQL文字列をコピーすること（既存の`conversation`/`message`テーブルも両ファイルで同一内容が保たれている、ADR-0044の既存方針）。

```sql
CREATE TABLE IF NOT EXISTS verification_question (
    id             SERIAL PRIMARY KEY,
    question_text  TEXT NOT NULL,
    memo           TEXT,
    created_at     TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at     TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS verification_run (
    id                        SERIAL PRIMARY KEY,
    question_id               INTEGER NOT NULL REFERENCES verification_question(id) ON DELETE CASCADE,
    question_text_snapshot    TEXT NOT NULL,
    executed_at               TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    status                    VARCHAR NOT NULL,
    error_message             TEXT,
    max_tags                  INTEGER,
    confidence_threshold      REAL,
    top_k                     INTEGER,
    min_score                 REAL,
    tag_selector_latency_ms   INTEGER,
    knowledge_mcp_latency_ms  INTEGER,
    evaluation                SMALLINT,
    evaluation_comment        TEXT,
    evaluated_at              TIMESTAMP WITH TIME ZONE
);

CREATE TABLE IF NOT EXISTS verification_run_tag (
    id        SERIAL PRIMARY KEY,
    run_id    INTEGER NOT NULL REFERENCES verification_run(id) ON DELETE CASCADE,
    rank_no   INTEGER NOT NULL,
    tag_id    INTEGER,
    tag_name  VARCHAR NOT NULL,
    score     REAL,
    path      TEXT
);

CREATE TABLE IF NOT EXISTS verification_run_source (
    id           SERIAL PRIMARY KEY,
    run_id       INTEGER NOT NULL REFERENCES verification_run(id) ON DELETE CASCADE,
    rank_no      INTEGER NOT NULL,
    source_id    VARCHAR,
    source_type  VARCHAR,
    title        TEXT,
    content      TEXT,
    score        REAL,
    metadata     TEXT
);
```

`path`（`verification_run_tag`）・`metadata`（`verification_run_source`）はJSON文字列として`json.dumps(...)`で保存し、読み出し時に`json.loads(...)`する（5.3節）。

### 5.2 `TagSelectorMcpClient`（T4・T5）

`web_backend/src/mcp_client/tag_selector_mcp_client.py`に、既存`knowledge_mcp_client.py`と同一構造で実装する。

```python
"""Tag Selector MCP 用の MCP クライアントラッパー（IMPL-202608260909 T4、ADR-0049）。

既存の KnowledgeMcpClient（web_backend/src/mcp_client/knowledge_mcp_client.py）と全く同一の
方式（Streamable HTTP、リクエストごとに新規セッション、業務エラーの専用例外への変換）を、
呼び出し先を tag_selector_mcp に変えて複製する。
"""

from __future__ import annotations

import json
from typing import Any, Optional

from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client


class TagSelectorMcpError(Exception):
    """Tag Selector MCP 側の業務エラーをラップする例外。"""

    def __init__(self, message: str):
        super().__init__(message)
        self.message = message


def _first_text(result) -> str:
    for block in getattr(result, "content", None) or []:
        text = getattr(block, "text", None)
        if text:
            return text
    return ""


class TagSelectorMcpClient:
    def __init__(self, url: str):
        self.url = url  # 環境変数 TAG_SELECTOR_MCP_URL（例: http://tag_selector_mcp:8200/mcp）

    async def call_tool(self, name: str, arguments: Optional[dict] = None) -> Any:
        arguments = arguments or {}
        async with streamablehttp_client(self.url) as (read, write, _):
            async with ClientSession(read, write) as session:
                await session.initialize()
                result = await session.call_tool(name, arguments)

        if getattr(result, "isError", False):
            raise TagSelectorMcpError(_first_text(result) or f"{name} failed")

        structured = getattr(result, "structuredContent", None)
        if structured is not None:
            return structured

        text = _first_text(result)
        if not text:
            return {}
        try:
            return json.loads(text)
        except json.JSONDecodeError:
            return {"text": text}
```

- `list_questions(keyword: str | None, limit: int, offset: int) -> tuple[list[VerificationQuestionRecord], int]`
  - 質問一覧を`created_at DESC`で取得し、各質問について`LEFT JOIN LATERAL (SELECT * FROM verification_run WHERE question_id = q.id ORDER BY executed_at DESC LIMIT 1) r ON true`で最終実行のみを結合する。`keyword`指定時は`question_text ILIKE`/`memo ILIKE`の`OR`条件を追加する。
  - 取得した最終実行の`run_id`一覧に対し、`SELECT * FROM verification_run_tag WHERE run_id = ANY(%s) ORDER BY run_id, rank_no`と`verification_run_source`側も同様のクエリをそれぞれ1回ずつ発行し、Python側で`run_id`ごとにグルーピングして`VerificationRunRecord.tags`/`sources`へ詰める（0章の「N+1回避」方針）。
  - 総件数は`COUNT(*) OVER()`または別クエリで取得する。
- `create_question(question_text: str, memo: str | None) -> VerificationQuestionRecord`
- `get_question(question_id: int) -> VerificationQuestionRecord | None`（`latest_run`のみ、一覧用の軽量版。内部で`run_question`実行前の存在確認に使う）
- `get_question_detail(question_id: int) -> VerificationQuestionRecord | None`（`runs`に全実行履行を`executed_at DESC`で格納。タグ・情報源も`list_questions`と同様のバッチ取得方式で結合する）
- `update_question(question_id: int, question_text: str | None, memo: str | None) -> VerificationQuestionRecord | None`（`updated_at = NOW()`を併せて更新。未指定フィールドは変更しない、既存の`QaUpdateRequest`と同じ「送られた項目のみ更新」方針）
- `delete_question(question_id: int) -> bool`（`DELETE FROM verification_question WHERE id = %s`。`ON DELETE CASCADE`により実行履行も削除される）
- `create_run(question_id: int, question_text_snapshot: str, status: str, error_message: str | None, max_tags: int | None, confidence_threshold: float | None, top_k: int | None, min_score: float | None, tag_selector_latency_ms: int | None, knowledge_mcp_latency_ms: int | None, tags: list[VerificationTagRecord], sources: list[VerificationSourceRecord]) -> VerificationRunRecord`

- `save_evaluation(run_id: int, evaluation: int, comment: str | None) -> VerificationRunRecord | None`
  - `UPDATE verification_run SET evaluation = %s, evaluation_comment = %s, evaluated_at = NOW() WHERE id = %s`

`run_question()`のオーケストレーション（要件定義書6.3節の実装）:

```python
_tag_selector_client = TagSelectorMcpClient(config.TAG_SELECTOR_MCP_URL)
_knowledge_client = KnowledgeMcpClient(config.KNOWLEDGE_MCP_URL)  # 既存インスタンスを再利用してよい

async def run_question(question_id: int) -> VerificationRunOut:
    question = verification_db.get_question(question_id)
    if question is None:
        raise HTTPException(status_code=404, detail="verification question not found")

    max_tags = config.VERIFICATION_MAX_TAGS
    confidence_threshold = config.VERIFICATION_CONFIDENCE_THRESHOLD
    top_k = config.VERIFICATION_TOP_K
    min_score = config.VERIFICATION_MIN_SCORE

    t0 = time.monotonic()
    try:
        tags_result = await _tag_selector_client.call_tool("select_tags", {
            "query": question.question_text,
            "max_tags": max_tags,
            "confidence_threshold": confidence_threshold,
        })
        tag_selector_latency_ms = int((time.monotonic() - t0) * 1000)
    except Exception as e:
        run = verification_db.create_run(
            question_id, question.question_text, status="error",
            error_message=f"select_tags failed: {e}",
            max_tags=max_tags, confidence_threshold=confidence_threshold,
            top_k=None, min_score=None,
            tag_selector_latency_ms=int((time.monotonic() - t0) * 1000),
            knowledge_mcp_latency_ms=None, tags=[], sources=[],
        )
        return _to_run_out(run)

    tags = [
        VerificationTagRecord(
            rank_no=i + 1, tag_id=t["id"], tag_name=t["name"],
            score=t["score"], path=t.get("path", []),
        )
        for i, t in enumerate(tags_result.get("selected", []))
    ]

    t1 = time.monotonic()
    try:
        search_result = await _knowledge_client.call_tool("search_knowledge", {
            "query": question.question_text,
            "tags": [t.tag_name for t in tags],   # 0件なら [] を渡す（11章 Open Issue #1）
            "top_k": top_k,
            "min_score": min_score,
        })
        knowledge_mcp_latency_ms = int((time.monotonic() - t1) * 1000)
    except Exception as e:
        run = verification_db.create_run(
            question_id, question.question_text, status="error",
            error_message=f"search_knowledge failed: {e}",
            max_tags=max_tags, confidence_threshold=confidence_threshold,
            top_k=top_k, min_score=min_score,
            tag_selector_latency_ms=tag_selector_latency_ms,
            knowledge_mcp_latency_ms=int((time.monotonic() - t1) * 1000),
            tags=tags, sources=[],
        )
        return _to_run_out(run)

    sources = [
        VerificationSourceRecord(
            rank_no=i + 1, source_id=r["id"], source_type=r["source_type"],
            title=r["title"], content=r["content"], score=r["score"],
            metadata=r.get("metadata", {}),
        )
        for i, r in enumerate(search_result.get("results", []))
    ]

    run = verification_db.create_run(
        question_id, question.question_text, status="success", error_message=None,
        max_tags=max_tags, confidence_threshold=confidence_threshold,
        top_k=top_k, min_score=min_score,
        tag_selector_latency_ms=tag_selector_latency_ms,
        knowledge_mcp_latency_ms=knowledge_mcp_latency_ms,
        tags=tags, sources=sources,
    )
    return _to_run_out(run)
```

`except Exception`という広い捕捉は、`TagSelectorMcpError`/`KnowledgeMcpError`（業務エラー）と、接続失敗・タイムアウト等の基盤エラーの両方を、検証実行の結果として一貫して扱うためである（0章）。他の書き込み系API（`create_qa`等）のように例外を上位へ伝播させて409へ変換する既存パターンとは意図的に異なる扱いである点を実装時に混同しないこと（10章）。

その他のCRUD関数（`list_questions`/`create_question`/`get_question_detail`/`update_question`/`delete_question`/`save_evaluation`）は、既存`qa_controller.py`の各関数と同様、`verification_db`の対応メソッドを呼び出してPydanticモデルへ変換するだけの薄い層とする。

既存の`aws_security_group.tag_selector_mcp`の説明文（`"tag_selector_mcp: inbound from agent_invitro / verification only"`）にある「verification」は、MCP Inspectorによるプロトコル層検証（ADR-0029）を指す既存の用語であり、本機能（検証機能）とは無関係である。本タスクで追加するルール名・コメントには、既存の「verification」ルール（`verification -> tag_selector_mcp`, 128〜135行目）と混同しない命名（`tag_selector_from_admin_ui`）を用いること（0章）。

## 10. 実装時の注意点・落とし穴

- **検証実行のエラーを409へ変換しない**: `app.py`の`@app.exception_handler(KnowledgeMcpError)`は、QA・タグの登録編集削除（書き込み系）における業務エラー用である。検証実行（`run_question`）では、`TagSelectorMcpError`/`KnowledgeMcpError`/接続失敗のいずれも`verification_controller`内で捕捉し、`verification_run`へ記録した上で200系（`VerificationRunOut`、`status="error"`）を返す。誤って例外を伝播させると、既存のグローバルハンドラにより意図しない409応答になる（0章）。
- **Terraformの「verification」という既存用語との混同**: `terraform/modules/network/main.tf`には、MCP Inspectorによるプロトコル層検証（ADR-0029）を指す既存のSG・ルール（`aws_security_group.tag_selector_mcp`の説明文、`verification -> tag_selector_mcp`ルール等）が既に存在する。本機能のために追加するリソース名・コメントには、この既存の「verification」と混同しない命名（`tag_selector_from_admin_ui`）を用いること（5.8節）。
- **実行データの不変性**: `verification_run`・`verification_run_tag`・`verification_run_source`は、`create_run()`で作成した後は`evaluation`関連列（`evaluation`/`evaluation_comment`/`evaluated_at`）以外を更新しない。再実行のたびに新規行を作成する（ADR-0050）。
- **`tag_id`/`source_id`に外部キー制約を設定しない**: `chatbot`データベースと`conversation`データベースは別データベースであり、PostgreSQLの外部キー制約はデータベースを跨いで設定できない。実装時に誤って`REFERENCES tag(id)`のような制約を追加しないこと（ADR-0048）。
- **`path`/`metadata`のJSON化**: `verification_run_tag.path`・`verification_run_source.metadata`は`TEXT`列であり、`INSERT`時に`json.dumps(...)`、読み出し時に`json.loads(...)`を行う。空リスト・空辞書の場合も`"[]"`/`"{}"`として保存し、`None`と区別する。
- **N+1回避**: 一覧・詳細のいずれも、`verification_run_tag`/`verification_run_source`の取得は対象`run_id`をまとめた1回のクエリ（`WHERE run_id = ANY(%s)`）で行い、質問（または実行）の件数分ループしてクエリを発行しないこと（5.3節）。
- **`select_tags`の`max_tags`/`confidence_threshold`と`search_knowledge`の`top_k`/`min_score`は`web_backend`側の環境変数から都度渡す**: `tag_selector_mcp`/`knowledge_mcp`自体のデフォルト値に暗黙に依存すると、`verification_run`に記録する「実際に使用したパラメータ値」が不正確になる（要件定義書6.3節、再現性のため明示的に渡す）。

## 11. Open Issues（実装時に確定が必要な事項）

要件定義書12章のOpen Issueのうち、実装着手前に優先して確認すべき事項を再掲する。

1. **`tags=[]`と`tags`未指定の扱いの一致確認**（要件定義書12章#1、本書8.4節T22で実装時に確認する）: `knowledge_mcp`の`search_service`・各`repository`の`search`実装が、`tags=[]`を「フィルタなし」として扱うか「0件」として扱うかを確認する。「0件」として扱われ、かつそれが検証機能の目的（タグが選択されなかったこと自体を観測する）に反すると判断される場合、`verification_controller.run_question()`側で`tags`が空リストのときは`search_knowledge`の`tags`引数自体を渡さない（`None`）分岐を追加する必要がある。
2. **検証質問削除時の実行履行の扱い**（要件定義書12章#2）: 本書はCASCADE削除を前提に実装するが、運用開始後に論理削除への変更要望が出た場合は、`verification_question`への`is_active`列追加、一覧APIの`WHERE is_active`条件追加等が必要になる（現時点では未実装）。
3. **タグ・情報源単位の評価粒度**（要件定義書12章#3）: 現在の実装は実行単位の評価のみ。項目単位評価が必要になった場合は`verification_run_tag`/`verification_run_source`への評価列追加、およびUI変更が必要。
4. **全データエクスポート機能への追加要否**（要件定義書12章#4）: 含める場合、`web_backend/src/export/tables.py`の`CONVERSATION_TABLES`に4テーブル分の`TableSpec`を追記する（既存のパターンに倣う。本書はこの追記を実装対象に含めていない）。
5. **検証質問の件数・運用ルール**（要件定義書12章#5）: 一覧・詳細のページング方式、将来のバッチ再実行機能の必要性に影響する。
