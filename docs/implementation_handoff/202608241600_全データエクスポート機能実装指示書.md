## 5. リソース仕様

### 5.1 `db_hiroba_qa_init`: `ensure_export_reader_role()`（T2）

`ensure_conversation_database()`と同様、`DATABASE_URL`（`chatbot`データベース、マスター権限）に`autocommit=True`で接続し、次の手順を冪等に実行する。

```
1. SELECT 1 FROM pg_roles WHERE rolname = %s（EXPORT_READER_ROLE_NAME）
   - 存在しなければ: CREATE ROLE {role} WITH LOGIN PASSWORD %s（EXPORT_READER_PASSWORD）
   - 存在すれば:     ALTER ROLE {role} WITH PASSWORD %s（Terraformでパスワードを再生成した場合に追従する）
2. GRANT CONNECT ON DATABASE {CHATBOT_DB_NAME} TO {role}
3. GRANT USAGE ON SCHEMA public TO {role}
4. GRANT SELECT ON ALL TABLES IN SCHEMA public TO {role}
5. ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO {role}
6. REVOKE CONNECT ON DATABASE {CONVERSATION_DB_NAME} FROM {role}
   （このステートメントは chatbot データベースへの接続のまま発行してよい。GRANT/REVOKE ... ON DATABASE
   はクラスタ共通のカタログに対する操作であり、接続先データベースを問わず有効である）
7. INSERT/UPDATE/DELETE・DDL権限は一切付与しない（GRANTを追加しないだけでよい）
```

テーブル名・ロール名はSQLインジェクション対策として`psycopg2.sql.Identifier`で組み立てること（既存の`ensure_conversation_database()`が`sql.Identifier(CONVERSATION_DB_NAME)`で行っているのと同じパターン）。

呼び出し順序: `main()`内で`migrate()` → `seed_if_empty()`の**後**に呼ぶこと（0章参照）。`CONVERSATION_DB_URL`の分岐と同様、`EXPORT_READER_PASSWORD`が空文字の場合は呼び出しをスキップし、ログにその旨を出力する。

### 5.2 Terraform: `modules/database`の追加リソース（T4〜T8）

```
variable "export_reader_username" {
  type    = string
  default = "chatbot_export_reader"
}

resource "random_password" "export_reader" {
  length  = 24
  special = false
}

# db_hiroba_qa_init が CREATE ROLE / ALTER ROLE に使う生パスワード専用シークレット。
resource "aws_secretsmanager_secret" "export_reader_password" {
  name_prefix = "${var.name_prefix}-export-reader-password-"
}
resource "aws_secretsmanager_secret_version" "export_reader_password" {
  secret_id     = aws_secretsmanager_secret.export_reader_password.id
  secret_string = random_password.export_reader.result
}
output "export_reader_password_secret_arn" {
  value = aws_secretsmanager_secret.export_reader_password.arn
}

# admin_ui が使う、chatbot_export_reader ロールでの完全な接続文字列シークレット。
```

### 5.5 `web_backend`: ダンプ生成・APIエンドポイント仕様（T16〜T19）

- `dump.py`:
  - `fetch_table_csv(conn, table_name: str, columns: list[str]) -> bytes`: `psycopg2.copy_expert(f"COPY (SELECT {cols} FROM {table} ORDER BY {pk}) TO STDOUT WITH CSV HEADER", buf)`でCSVバイト列を取得する。
  - `fetch_table_sql(conn, table_name: str, columns: list[str], create_ddl: str) -> str`: 同様に行を取得し、`create_ddl`に続けて`INSERT INTO {table} ({cols}) VALUES (...), (...), ...;`をバッチ（実装フェーズで確定、目安500行単位）で組み立てる。値のエスケープは`psycopg2.extensions.adapt`または`cur.mogrify`を使い、手組みの文字列結合による SQL インジェクションを避けること。
- `zipper.py`: `build_zip(files: dict[str, bytes]) -> bytes`（ファイル名→中身のバイト列の辞書を受け取り、`zipfile.ZipFile(io.BytesIO(), "w")`でZIP化して返す）。
- `export_controller.py`:
  - `build_export(format: str) -> tuple[bytes, str]`: `format`に応じて`chatbot`・`conversation`両方のDB接続を開き（`config.CHATBOT_EXPORT_DB_URL`・`config.CONVERSATION_DB_URL`）、CSVは8ファイル、SQLは2ファイルを`zipper.build_zip`でまとめ、`(zip_bytes, filename)`を返す。ファイル名は`chatbot_invitro_export_<YYYYMMDDHHmmss>_<format>.zip`（6章参照）。
  - 呼び出しの最後に、エクスポート実行の事実（日時・形式）をログに記録する（既存`src/log.log_admin_operation`のパターンを踏襲、T20）。
- `app.py`のルート:
  ```
  @app.get("/api/export")
  def export_data(format: str = Query(..., pattern="^(sql|csv)$")):
      zip_bytes, filename = export_controller.build_export(format)
      return Response(
          content=zip_bytes,
          media_type="application/zip",
          headers={"Content-Disposition": f'attachment; filename="{filename}"'},
      )
  ```
  `format`が`sql`/`csv`以外の場合はFastAPIの`pattern`バリデーションにより422を返す（追加のtry/exceptは不要）。

### 5.6 `front_dev`: `/admin/export`画面仕様（T21〜T24）

- `ExportPage.tsx`: ラジオボタン（`sql`/`csv`、初期値は詳細設計フェーズで確定）、「エクスポート」ボタン。クリックで`api.downloadExport(format)`を呼び、処理中はボタンを無効化する（`useState`によるローディングフラグ）。成功・失敗をページ内にメッセージ表示する。
- `api.ts`の`downloadExport`: `fetch("/api/export?format=...")`のレスポンスを`res.blob()`で取得し、`URL.createObjectURL(blob)`から`<a download="...">`要素を生成してクリックを発火させ、直後に`URL.revokeObjectURL`で解放する（既存の`jsonFetch`とは異なり、JSONではなくBlobを扱うための専用関数として実装する）。
- `routes.tsx`: `/admin`配下に`<Route path="export" element={<ExportPage />} />`を追加し、`AdminLayout`のナビ（`admin-nav`）に「エクスポート」リンクを追加する（既存の「QA」「タグ」と並記）。

## 10. 実装時の注意点・落とし穴

- **ロール作成の実行タイミング**: `ensure_export_reader_role()`は必ず`migrate()`・`seed_if_empty()`の後に呼ぶこと。`GRANT SELECT ON ALL TABLES IN SCHEMA public`は実行時点で存在するテーブルにしか効かないため、マイグレーション未適用・シード未投入の段階で呼ぶと、後から作成されるテーブル（またはこの時点でまだ存在しないテーブル）へのSELECT権限が漏れる可能性がある。`ALTER DEFAULT PRIVILEGES`はあくまで「今後作成されるテーブル」に対する既定権限であり、既存テーブルへの遡及効果はない。
- **`CREATE ROLE`と`CREATE DATABASE`の違い**: `ensure_conversation_database()`は`CREATE DATABASE`がトランザクションブロック内で実行できないため`autocommit=True`が必須だったが、`CREATE ROLE`・`GRANT`はトランザクション内で実行可能である。ただし本書では`ensure_conversation_database()`との実装の一貫性を優先し、同様に`autocommit=True`の専用接続で処理してよい（必須ではないが、既存パターンとの統一を推奨する）。
- **パスワードのローテーション**: `random_password.export_reader`は`terraform apply`時に一度だけ生成され、以後は状態ファイルに固定される。ロールのパスワードを変更したい場合は、既存のマスターパスワード（`random_password.master`）と同様、明示的な`terraform taint`等の操作が必要になる。運用上のローテーション方針は本書のスコープ外とし、必要になった時点で別途検討する。
- **`REVOKE CONNECT ON DATABASE conversation`の発行元**: `GRANT`/`REVOKE ... ON DATABASE`はクラスタ共通のカタログ（`pg_database`）に対する操作であり、`chatbot`データベースへの接続のまま`conversation`データベースに対して発行できる。`conversation`データベースへ改めて接続し直す必要はない。
- **ZIPのメモリ上での組み立て**: 本書の設計は、テーブルデータを一度メモリ上のバッファ（`io.BytesIO`）に集めてからZIP化する。現時点のデータ規模では問題にならないが、将来`conversation`/`message`が大きく増加した場合、メモリ使用量・レスポンス時間の観点でこの設計を見直す必要が生じ得る（要件定義書12章Open Issue #3）。
- **コンテナイメージへの追加依存なし**: `psycopg2`は既存依存（`db.py`・`conversation_db/db.py`が既に使用）、ZIP生成はPython標準ライブラリ（`zipfile`, `io`）のみで完結するため、`web_backend`のDockerfile（ローカル用・`Dockerfile.admin_ui`のいずれも）に変更は不要である。
