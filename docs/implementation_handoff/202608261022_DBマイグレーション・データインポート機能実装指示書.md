### 5.2 conversation データベースのyoyo移行（T3, T4、ADR-0051）

`db_hiroba_qa_init/migrations_conversation/0001_initial_conversation_message.sql`は、現行`db_conversation/init.sql`の内容をそのまま移す。

```sql
CREATE TABLE IF NOT EXISTS conversation (
    id          VARCHAR PRIMARY KEY,
    created_at  TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS message (
    id              VARCHAR PRIMARY KEY,
    conversation_id VARCHAR NOT NULL REFERENCES conversation(id),
    "order"         INTEGER NOT NULL,
    role            SMALLINT NOT NULL,
    evaluation      SMALLINT,
    input           TEXT,
    model           VARCHAR,
    content         TEXT,
    created_at      TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    UNIQUE(conversation_id, "order")
);
```

`0002_add_verification_tables.sql`は、要件定義書202608260909 7.2節に記載された4テーブルのDDL（`verification_question`/`verification_run`/`verification_run_tag`/`verification_run_source`、いずれも`CREATE TABLE IF NOT EXISTS`）をそのまま用いる。

`main.py`の`migrate_conversation()`は、既存`migrate()`と同一パターンで、`MIGRATIONS_CONVERSATION_DIR`（`migrations_conversation/`）を対象にyoyoを実行する。接続先は`CONVERSATION_DB_URL`のmigrator版（`conversation_migrator_database_url()`、5.1節と同様に組み立てる）とする。

```python
CONVERSATION_MIGRATIONS_DIR = os.path.join(
    os.path.dirname(os.path.dirname(os.path.abspath(__file__))), "migrations_conversation"
)

def migrate_conversation():
    print(f"{_now()} ====== Applying conversation migrations from {CONVERSATION_MIGRATIONS_DIR} ...")
    backend = get_backend(conversation_migrator_database_url())
    migrations = read_migrations(CONVERSATION_MIGRATIONS_DIR)
    with backend.lock():
        to_apply = backend.to_apply(migrations)
        backend.apply_migrations(to_apply)
    print(f"{_now()} Conversation migrations applied ({len(to_apply)} pending step(s)).")
```

既存の`ensure_conversation_database()`（`CREATE DATABASE`の存在チェック）はそのまま残す。既存の`apply_conversation_schema()`（直書きDDL関数）は、`migrate_conversation()`に置き換えて削除する。`main()`内の呼び出し条件（`if CONVERSATION_DB_URL:`）も、ローカル・AWS双方で`CONVERSATION_DB_URL`が常に設定されるようになる（T6）ため、条件分岐自体が不要になる可能性がある。ローカル・AWS双方の起動シーケンスを揃えるため、条件分岐を撤去し、常に`ensure_conversation_database()`（AWSのみ意味を持つ。ローカルは既存の`conversation_db`コンテナが自身でデータベースを保持するため`CREATE DATABASE`は不要／早期リターンでよい）→`migrate_conversation()`→`ensure_conversation_roles()`を実行する構成に統一することを推奨する。

### 5.6 QA一括インポート: `import_qa_batch`（T9、ADR-0053）

`qa_management_repository.py`に追加する。既存の`create_qa`/`update_qa`（`self.embed_fn`によるembedding計算、`_assert_category_exists`/`_assert_tags_exist`）のロジックを、行単位に適用する。

```python
def import_qa_batch(
    self,
    rows: List[dict],
    tag_repository: "TagRepository",
) -> List[dict]:
    """CSVの各行（dict: uuid, title, question_text, answer_text, category_id, tags）を
    まとめて登録・更新する。行ごとに独立してコミットし、1行のエラーが他行に波及しないようにする
    （ADR-0053）。

    - `uuid` が空: create_qa 相当（新規作成、qa_id は自動採番）。
    - `uuid` が既存: update_qa 相当（部分更新。CSVの列が空の項目は変更しない、2.3節#12）。
    - `tags`: タグ名のカンマ区切り文字列。既存タグは名前で解決、存在しないタグ名は
      tag_repository.create_tag() で自動作成してから tag_id を得る（2.3節#7）。
    - 戻り値: [{"row": <行番号>, "status": "success"|"error", "qa_id": ..., "error": ...}, ...]
    """
    results = []
    for i, row in enumerate(rows):
        try:
            tag_ids = self._resolve_tag_names(row.get("tags"), tag_repository)
            if row.get("uuid"):
                detail = self.update_qa(
                    row["uuid"],
                    title=row.get("title") or None,
                    question_text=row.get("question_text") or None,
                    answer_text=row.get("answer_text") or None,
                    category_id=row.get("category_id") or None,
                    tag_ids=tag_ids if row.get("tags") else None,  # 空欄は「変更なし」
                )
            else:
                detail = self.create_qa(
                    title=row["title"],
                    question_text=row["question_text"],
                    answer_text=row["answer_text"],
                    category_id=row.get("category_id"),
                    tag_ids=tag_ids,
                )
            results.append({"row": i, "status": "success", "qa_id": detail.id})
        except (QaError, TagError) as e:
            results.append({"row": i, "status": "error", "error": str(e)})
    return results

def _resolve_tag_names(self, tags_field, tag_repository) -> Optional[List[int]]:
    if not tags_field:
        return None
    names = [t.strip() for t in tags_field.split(",") if t.strip()]
    ids = []
    for name in names:
        tag = tag_repository.find_by_name(name)  # 新設: 既存 create_tag の重複チェックと同じ
        if tag is None:
            tag = tag_repository.create_tag(name=name)  # 自動作成（2.3節#7）
        ids.append(tag.id)
    return ids
```

`tag_repository.py`に`find_by_name(name: str) -> Optional[TagNode]`（`SELECT ... WHERE name = %s`、`create_tag`内の重複チェッククエリと同一条件）を新設する。既存`create_tag`は重複時に`TagError`を送出する設計のため、`import_qa_batch`からは直接`create_tag`を呼ばず、必ず`find_by_name`で存在確認してから未存在の場合のみ`create_tag`を呼ぶ。

`update_qa`の`tag_ids`引数は「Noneで変更なし、[]で全解除」という既存の契約（`qa_controller.py`のコメント参照）を持つため、CSVの`tags`列が空の場合は`None`を渡し、既存のタグ紐付けを変更しないようにする（2.3節#12）。`title`/`question_text`等も同様に、CSVの値が空文字の場合は`None`（変更なし）として渡す。

### 5.9 検証質問一括インポート（T13, T14、ADR-0054）

`verification_db/db.py`（IMPL-202608260909で新設）の`VerificationDB`クラスに、既存の単発登録メソッド（`create_verification_question`相当、正式名称はIMPL-202608260909の実装に従う）と同じSQLをループで複数件に適用するメソッドを追加する。

```python
def bulk_create_questions(self, rows: list[dict]) -> list[dict]:
    """rows: [{"question_text": ..., "memo": ...}, ...]。
    question_text が空文字の行はスキップしエラーとして報告する（重複チェックは行わない、2.3節#8）。
    """
    results = []
    for i, row in enumerate(rows):
        text = (row.get("question_text") or "").strip()
        if not text:
            results.append({"row": i, "status": "error", "error": "question_text is required"})
            continue
        with self.conn.cursor() as cur:
            cur.execute(
                "INSERT INTO verification_question (question_text, memo) VALUES (%s, %s) RETURNING id",
                (text, row.get("memo") or None),
            )
            new_id = cur.fetchone()[0]
        self.conn.commit()
        results.append({"row": i, "status": "success", "id": new_id})
    return results
```

## 10. 実装時の注意点・落とし穴

- **ロール切り替えのタイミング**: `GRANT SELECT ON ALL TABLES`等の権限付与は、実行時点で存在するテーブルにのみ効く。`ensure_chatbot_roles()`・`ensure_conversation_roles()`は、必ず対応するマイグレーション（`migrate()`・`migrate_conversation()`）とシード（`seed_if_empty()`）の後に呼び出すこと（既存`ensure_export_reader_role()`が同じ制約を持つことに倣う）。
- **`CREATE DATABASE`のトランザクション制約**: 既存の`ensure_conversation_database()`と同様、`CREATE ROLE`はトランザクション内実行も可能だが、既存コードとの一貫性のため`autocommit=True`のパターンを踏襲すること。
- **CSVの文字コード・改行コード**: Windows環境（開発者の`SourceTree`環境）で作成されたCSVはShift_JIS・CRLFの可能性がある。`_parse_qa_import_csv`・検証質問側のパーサーは、UTF-8（BOM付き含む）を前提としつつ、実装時にエンコーディング自動判定または明示的なエラーメッセージ（「UTF-8で保存してください」）を用意することが望ましい。
- **`import_qa_batch`のトランザクション粒度**: 行ごとに独立してコミットする設計（5.6節）のため、大量行のインポート中に処理が中断した場合、どこまで反映されたかが行番号から追跡できるようにログを残すこと。
- **`db_hiroba_qa_init`の役割拡大**: 本書でロール作成・2系統のマイグレーション（chatbot/conversation）を1つのワンショットサービスに集約するため、`main()`の処理順序（ロール作成→マイグレーション→シードの依存関係）を誤ると、権限不足でシードが失敗する。5.1節・5.2節の順序（ロールは常にマスター接続で作成し、その後の処理をmigrator接続に切り替える）を厳守すること。
