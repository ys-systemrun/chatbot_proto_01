## 0. 本書作成にあたり確定した事項

要件定義書（REQ-202608211014）12章のOpen Issuesのうち、実装着手には確定が必要だが未決だった項目、および本書作成にあたり補足した項目を整理する。

| `admin_ui`サービスのTerraform構成上の位置付け | `terraform/main/app/`（既存の`knowledge_mcp`等と同一構成）に追加する。`web_backend`は既存chat機能（`/ask`等）を含むため、AWS上でも本サービスがchat機能のエンドポイントも兼ねる（要件定義書のスコープはQA・タグ管理UIのみだが、`web_backend`は単一プロセスであるため両機能が同一コンテナに同居する点を明記） | **本書での補足**（要件定義書は管理UI機能のみを対象とするが、実装上`web_backend`を分割しない前提のため、影響範囲として明記） |

残るOpen Issueは次の3点であり、これは本書・要件定義書のいずれでも決定できない、発注者・基盤チーム側の情報または承認である。**これらが確定するまで、Phase 2以降（実際のリソース作成）には着手できない。**

- **社内IPアドレスの具体的な値**（要件定義書12章Open Issue #1）: 発注者から受領し、Terraform変数（6.1節）に設定すること。
- **既存VPCのパブリックサブネット・インターネットゲートウェイの有無**（要件定義書12章Open Issue #2）: 基盤チームに確認すること。用意されていない場合、本書5.1節の前提（既存VPCのパブリックサブネットを流用する）が崩れ、実装方針の見直しが必要になる。
- **ALBの追加コストに対する予算承認**（要件定義書12章Open Issue #5）: 発注者の承認を受けること。

## 5. リソース仕様

### 5.1 ネットワーク（T8〜T10、ADR-0041）

| リソース | 仕様 |
|---|---|
| `sg-admin-ui-alb` | インバウンド: 発注者から受領した社内IPアドレス（CIDR）からの80番（HTTPのみ、0章の暫定方針）を許可。アウトバウンド: `sg-admin-ui-task`宛のコンテナポートのみ |
| `sg-admin-ui-task` | インバウンド: `sg-admin-ui-alb`からのコンテナポート（`web_backend`の既存ポート8000を踏襲）のみ許可。アウトバウンド: 既存パターン（全許可、到達可否は相手側ingressで制御） |
| `sg-knowledge-mcp`への追加ルール | `sg-admin-ui-task` → `sg-knowledge-mcp`（8100番）を許可。既存の`agent_invitro → knowledge_mcp`ルールと同一形式 |
| パブリックサブネット | 既存VPC（ADR-0036）のパブリックサブネットIDを変数として受け取る。Open Issue（0章）が解消するまで値を確定できない |

### 5.2 ALB関連（T11、ADR-0041）

| リソース | 仕様 |
|---|---|
| Application Load Balancer | `internal = false`（internet-facing）、5.1節のパブリックサブネットに配置、`sg-admin-ui-alb`を関連付け |
| リスナー | 80番（HTTP）。0章の暫定方針によりHTTPS（443番）は本フェーズでは作成しない。将来HTTPS化する場合、ACM証明書発行後にリスナー追加・80番からのリダイレクト設定を別途行う | 
| ターゲットグループ | プロトコル`HTTP`、ポートは`web_backend`の既存ポート（8000）、ターゲットタイプ`ip`（Fargateの`awsvpc`ネットワークモード対応）、ヘルスチェックパス`/health`（T1で追加） |

### 5.3 `ecs-service`モジュール拡張（T12）

| 変更点 | 仕様 |
|---|---|
| 追加する入力変数（例） | `target_group_arn`（省略可、既定値`null`） |

| 既存3サービスへの影響 | `target_group_arn`を渡さない既存の`tag_selector_mcp`・`knowledge_mcp`・`agent_invitro`の呼び出しには影響しないこと（`terraform plan`で差分が出ないことを確認する） |

|---|---|

### 5.5 デプロイCLI（T16）

- `terraform/deploy/src/commands.py`の`cmd_apply_app`内、イメージビルド対象の`components`リストに`("admin_ui", "admin-ui")`を追加する。
- ただし既存の`dockercli.build_and_push(paths.repo_root() / src_dir, image, src_dir, repo)`は「`src_dir`をビルドコンテキストとする」実装であり、T6の通り`admin_ui`は例外的にリポジトリルートをビルドコンテキストとする必要がある。既存関数の呼び出し方（`src_dir`の扱い）を確認し、`admin_ui`専用の呼び出し（ビルドコンテキスト＝リポジトリルート、Dockerfileパス＝T5で新設したファイル）に対応させる実装指示とする。既存3コンポーネントの呼び出しには影響を与えないこと。

既存の`knowledge_mcp`向け`KNOWLEDGE_MCP_URL`（Service Connect名、`terraform/main/app/main.tf`の既存パターン）をそのまま踏襲する。新規の環境変数追加は本フェーズでは発生しない（既存の`/ask`系エンドポイントが必要とする環境変数（`DATABASE_URL`等）についても、既存の`web_backend`要件を踏襲する。ただし、これらをAWS上でも必要とするかは、既存chat機能自体をAWSにデプロイするかという別課題であり、本書の対象外である点に注意。管理UI機能（`/api/*`）のみを稼働させる場合、`DATABASE_URL`等の直接DB接続用環境変数は未設定でも`/api/*`の動作に影響しない想定だが、起動時に必須環境変数としてチェックされている場合は実装時に確認すること、11章Open Issue参照）。

## 10. 実装時の注意点・落とし穴

- **ビルドコンテキストの違い**: 既存4コンポーネントはコンポーネントディレクトリ単体がDockerビルドコンテキストだが、`admin_ui`用イメージは`front_dev/`と`web_backend/`の両方を`COPY`するため、リポジトリルートをビルドコンテキストにする必要がある（T6）。デプロイCLI（`dockercli.build_and_push`）の既存呼び出し方をそのまま流用すると失敗するため、実装時に呼び出し方を個別に確認すること。
- **ALBヘルスチェックとECSコンテナヘルスチェックの違い**: 既存の`knowledge_mcp`等はECSタスク定義の`healthCheck`（コンテナ内部でのコマンド実行）のみを使っているが、ALB配下のサービスはこれに加えてターゲットグループのHTTPヘルスチェックが必要になる。両者は独立した仕組みであり、`/health`エンドポイント（T1）はALBのターゲットグループヘルスチェック専用として追加するものである。
- **`assign_public_ip`の設定ミスへの注意**: ALBをパブリックサブネットに配置することと、ECS Fargateタスク自体をパブリックサブネットに配置することは別の設定である。`admin_ui`タスクは既存の`knowledge_mcp`等と同様、プライベートサブネット・`assign_public_ip=false`を維持すること（T13）。誤ってタスクをパブリックサブネットに配置すると、ADR-0041が意図した「タスク自体は非公開」という前提が崩れる。
- **既存`web_backend`起動時の必須環境変数**: `main/main.py`は現状、`DATABASE_URL`・`LMSTUDIO_CHAT_URL`等を`os.environ[...]`で必須値として読み込んでいる（未設定だと起動時に`KeyError`で落ちる）。管理UI機能のみをAWS上で稼働させる場合にこれらの値をどう扱うか（ダミー値を設定するか、起動時の読み込み方式自体を見直すか）を実装時に確認する必要がある（11章Open Issue）。
- **コスト管理**: ALBは時間課金＋LCU課金で常時発生する。検証終了後の扱い（`destroy-app`に含めるか、`admin_ui`のみ個別に停止できるようにするか）を運用ルールとして明確にすること。
