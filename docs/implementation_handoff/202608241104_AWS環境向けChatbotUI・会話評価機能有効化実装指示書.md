## 0. 本書作成にあたり確定した事項

要件定義書（REQ-202608240949）12章のOpen Issuesのうち、実装着手には確定が必要だが未決だった項目、および本書作成にあたり補足した項目を整理する。

| 項目 | 決定内容 | 根拠・備考 |
|---|---|---|
| `agent_invitro`常駐HTTPサーバーのフレームワーク | FastAPI + Uvicorn | `web_backend`・`knowledge_mcp`・`tag_selector_mcp`と技術スタックを揃える（**本書での補足**）。`agent_invitro/pyproject.toml`に`fastapi`, `uvicorn`を追加する（既存の`langgraph`, `langchain-mcp-adapters`, `langchain-openai`, `langchain-aws`, `ipython`はそのまま維持） |
| `agent_invitro`の回答生成方式（ADR-0043 Open Issue #2） | **単発プロンプト生成方式を採用**: 既存の`graph/agent.py`のReActエージェント（`build_agent`）はそのまま流用せず、`web_backend/src/llm/gen_answer_llm_bedrock.py`と同様の構造（`boto3` `bedrock-runtime`の`invoke_model`を直接呼ぶ）を`agent_invitro`側に新設し、コンテキストは既存のMCPクライアント（`mcp_clients/client.py`）経由でKnowledge MCPの`search_knowledge`ツールを直接呼び出して構築する | **本書での補足**（ADR-0043は「単一プロンプト生成に留めるか、ReActループ全体を経由するかは実装フェーズで確定する」としていた）。ReActループ全体を経由する方式は、既存の`build_agent`がツール呼び出し順序をLLMの自律判断に委ねる設計であり、`/ask-sl`のステートレス設計（要約済み履歴・コンテキストを毎回受け渡す構造）との整合を取るための追加設計が必要になる。単発プロンプト生成方式は`web_backend`の既存実装（`GenerateAnswerLLMBedrock`）とほぼ同一の構造を複製できるため、変更・検証範囲が最小であることを理由に採用する |
| `conversation`データベース作成のトランザクション制御 | `CREATE DATABASE`は`autocommit=True`の単発接続で実行し、既存のyoyo-migrations（`migrate()`、`chatbot`データベース用）とは完全に独立したステップとして`db_hiroba_qa_init`に追加する | **本書での補足**。`CREATE DATABASE`はPostgreSQLのトランザクションブロック内では実行できないため、既存の`migrate()`（yoyoが内部でトランザクションを張る）とは別関数・別接続で行う必要がある |
| `agent_invitro`の常駐HTTPサーバー起動コマンド | `["python", "-m", "uvicorn", "agent_invitro.main.api.server:app", "--host", "0.0.0.0", "--port", "8300"]`（AWS環境の`terraform/main/app/main.tf`の`module "agent_invitro"`の`command`引数にのみ設定） | **本書での補足**。`agent_invitro/pyproject.toml`の`package-dir = {"agent_invitro" = "src"}`により、`src/main/api/server.py`は`agent_invitro.main.api.server`としてimportできる（※本書作成時点では`src/server.py`（`agent_invitro.server`）として新設。その後、エントリポイントを用途別に整理し`src/main/api/server.py`へ移設。IPythonエントリの`main.py`も`src/main/ipython/main.py`へ移設） |
| ローカル`docker-compose`環境への影響 | `agent_invitro/pyproject.toml`への依存追加（`fastapi`, `uvicorn`）はローカルの`agent_invitro`イメージにも反映される（ビルド時間・イメージサイズがやや増加する）が、`docker-compose.yml`の`command: ["sleep", "infinity"]`は変更しないため、ローカルでの起動時の振る舞い（IPython対話シェル用コンテナ）は変わらない | **本書での補足**（要件定義書10章、ADR-0043） |

残るOpen Issueは次の2点であり、これは本書・要件定義書のいずれでも決定できない、発注者側の情報または承認である。**これらが確定するまで、Phase 1（`agent_invitro`のBedrock呼び出し実装）の動作確認、およびPhase 6（検証）には着手できない。**

- **Bedrockチャットモデルの確定**（要件定義書12章Open Issue #3）: `BEDROCK_CHAT_MODEL_ID`は`.env.example`上未確定（空）。発注者・実装担当者間でモデル（Anthropic Claude系等）を確定すること。
- **会話データの保持期間・削除方針の再確認**（要件定義書12章Open Issue #5）: 2026-08-21時点の回答（無期限保存で問題ない）を維持するかを改めて確認すること。本書のスキーマ実装（Phase 3）自体はどちらの回答でも変更不要だが、将来の自動削除機能の要否に影響する。

## 10. 実装時の注意点・落とし穴

- **`main_stateless.py`はローカル・AWS共有ファイル**: `/ask-sl`の条件分岐（T11）を実装する際、`AGENT_INVITRO_URL`が空文字の場合の既存パスを誤って削除・変更しないこと。ローカル環境の回帰テスト（T13）を必ず実施する。
- **`CREATE DATABASE`はトランザクション不可**: `ensure_conversation_database()`（T16）は、既存の`migrate()`（yoyoが内部でトランザクションを使用）と同じ接続・関数で実装できない。`psycopg2.connect(...)`に`autocommit=True`を明示すること。
- **`db_hiroba_qa_init`はローカルでも動く**: ローカル環境では`conversation`データベースは別コンテナ（`conversation_db`）が既に保持しているため、`db_hiroba_qa_init`に`CONVERSATION_DB_URL`を渡さない（ローカル`docker-compose.yml`は変更しない）。T16・T17は`CONVERSATION_DB_URL`が空の場合にスキップする条件分岐を必ず入れること（入れ忘れると、ローカルの`db_hiroba_qa_init`実行時に`KeyError`等で失敗する）。
- **`agent_invitro`のイメージ肥大化**: `fastapi`, `uvicorn`の追加（T1）は、ローカル用の`agent_invitro`イメージにも影響する（ビルド時間増加）が、実行コマンドが変わらない限り動作には影響しない。気になる場合はビルドキャッシュの活用を検討する（本フェーズでは対応不要）。
- **ALBヘルスチェックとの違い**: `agent_invitro`はALB配下ではないため、T2で追加する`/health`はECSコンテナレベルのヘルスチェック（`health_check_command`）専用であり、ALBターゲットグループのヘルスチェックとは異なる（`admin_ui`のケース、`docs/implementation_handoff/202608211050_...`10章と同じ区別）。
- **資格情報スコープの徹底**: T28で`admin_ui`に`secrets`ブロックを新設する際、誤って既存の`DATABASE_URL`（`chatbot`データベース用）シークレットも一緒に注入しないよう、`CONVERSATION_DB_URL`のみを追加すること。ADR-0045が前提とする「ネットワークは到達可能だが資格情報でchatbotデータベースへのアクセスを防ぐ」という設計が、ここで崩れると意味をなさなくなる。
- **タイムアウト**: `admin_ui → agent_invitro`のHTTP呼び出し（T12）、および`agent_invitro`内のBedrock呼び出し・`search_knowledge`呼び出しの合計時間が、ALBのアイドルタイムアウト（既定60秒）や`httpx`クライアントの既定タイムアウトを超えないか、Phase 6で実測し、必要なら明示的に延長設定する（11章Open Issue）。
- **コスト管理**: `agent_invitro`が常駐HTTPサーバー化することで、これまでの「ECS Exec専用・呼ばれない限りCPU使用がほぼゼロ」という状態から、常時起動プロセスとしてリクエストを受け付ける状態に変わる。Fargateの課金は`desired_count=1`の常駐自体で既に発生しているため追加のインフラコスト増分はないが、Bedrock呼び出し回数が増える点（管理UIのタグ選択等と合わせた合計呼び出し量）は既存のBedrockコスト予算アラート（ADR-0040）の監視対象に含まれることを確認する。
