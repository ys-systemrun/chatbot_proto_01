## 0. 本書作成にあたり確定した事項

要件定義書12章・ADR-0065で「実装フェーズで確定」とされた事項について、本書で次の通り確定する。

| 項目 | 決定内容 | 根拠・備考 |
|---|---|---|
| MCPツールの追加方式 | 既存 `TagRepository` に新規メソッド `export_tags()` を追加する（新規リポジトリ・新規モデルは作らない）。`list_tags()` が構築するツリーをそのまま深さ優先で走査してフラット化する薄いラッパーであり、新規SQL・新規業務ロジックは追加しない | ADR-0065 決定1・結果 |
| `export_tags` の戻り値 | `[{"id", "name", "parent_name", "description"}, ...]`。`id` は含めるが（`export_question_altered` と同様に読み取り整合性のため）、`web_backend` のCSV組み立ては `name`/`parent_name`/`description` の3列のみを使用し `id` は参照しない | ADR-0065 決定2・要件6.3 |
| CSVの列 | `name`/`parent_name`/`description` の3列。`import_tag_batch`（ADR-0061）と完全一致。`id` 列は出力しない（upsertキーが `name` のため誤解防止） | ADR-0065 決定2・要件6.4 |
| ルート直下タグの `parent_name` | 空欄で出力（`parent_name` が `None`／空文字） | 要件3・7.2 |
| エイリアス（`tag_alias`） | エクスポート対象外（`import_tag_batch` が非対応のため往復整合性を優先） | ADR-0065 決定3・要件4.2 |
| 対象範囲 | 常に全タグ（絞り込みなし）。`TagTreePage` に絞り込みUIがなく `list_tags` も全件返すため | ADR-0065 決定4・要件4.2 |
| 出力順序 | 既存ツリーを深さ優先で走査し、親タグが子タグより先に出現する階層順。再インポートの正しさには影響しない（ADR-0061は並び順非依存）が可読性のため | ADR-0065 決定5・要件6.5 |
| CSVの文字コード | UTF-8 BOM付き（Excel互換）。既存の `import_tag_batch`（`utf-8-sig` で読める）とそのまま往復可能 | 要件12章#1・IMPL-202608281100踏襲 |
| エクスポートファイル名 | `tags_<YYYYMMDDHHmmss>.csv`（Asia/Tokyo）。既存の全データエクスポート（`chatbot_invitro_export_*`）と明確に区別する | ADR-0065 決定6・要件12章#5 |
| 操作ログ | `log_admin_operation("export", "tag", None, {"total": ...})` を記録（既存 `export_question_altered` と同一方式） | 要件8章 |

## 2. 実装詳細

### 2.1 knowledge_mcp: `TagRepository.export_tags()`（T1）

`list_tags(parent_tag_id=None)` が返すルート起点のツリーを深さ優先で走査し、各ノードについて親ノードの `name` を `parent_name` として持ち回る。ルート直下は `parent_name=None`。戻り値は `[{"id", "name", "parent_name", "description"}, ...]`。エイリアス・`children` は含めない。新規SQLは発行しない（`list_tags` の1クエリのみを再利用）。

### 2.2 knowledge_mcp: MCPツール `export_tags`（T2）

`tools.py` の `register_tools` 内、`import_tag_batch` の直後に登録する。

```python
@mcp.tool(
    name="export_tags",
    description="全タグを id/name/parent_name/description のフラットな配列で返す"
                "（親が子より先の階層順、エイリアス除外。CSV組み立ては web_backend 側で行う）。",
)
def export_tags() -> dict:
    return {"items": tag_repository.export_tags()}
```

引数なし・読み取りのみ。`server.py` の DI 配線は既存の `tag_repository` をそのまま使うため変更不要。

### 2.3 web_backend: `GET /api/tags/export`（T3）

`tag_controller.py` に `export_question_altered` と同型の `build_export_csv()` を追加する。
- `export_tags` ツールを呼び出し、`name`/`parent_name`/`description` の3列でCSV（UTF-8 BOM付き）を組み立てる。
- ファイル名 `tags_<timestamp>.csv`（`_timestamp()` は `question_altered_controller` と同一方式、Asia/Tokyo）。
- `log_admin_operation("export", "tag", None, {"total": len(items)})`。

`app.py` に `GET /api/tags/export` を追加する。`/api/tags/{tag_id}` の GET ルートは存在しない（PUT/DELETE のみ）ため経路衝突はないが、可読性のため `/api/tags/import` の近くに配置する。`text/csv` + `Content-Disposition: attachment` で返す。

### 2.4 front_dev: エクスポートボタン（T4）

- `api.ts`: 既存 `downloadBlob` を用いた `downloadTagsExport()` を追加（`downloadQuestionAlteredExport` と同型、fallback名 `tags.csv`）。
- `TagTreePage.tsx`: `exporting` 状態と `onExport()` を追加し、「CSV 一括インポート」`<details>` の近く（ヘッダ部）に「CSVエクスポート」ボタンを置く。処理中は `disabled` + 「エクスポート中...」表示。

### 2.5 テスト（T5）

`tests/test_tools.py` に `export_tags` の単体テストを追加する（既存 `FakeTagDatabase`/`repo` フィクスチャを利用）。ルート・子・孫を作成し、`export_tags()` が親→子の階層順で `parent_name` を正しく持つこと、ルート直下は `parent_name is None` であること、エイリアス列を含まないことを確認する。

## 3. 検証・受け入れ（T6）

- [ ] `export_tags` 単体テストが通る。
- [ ] `GET /api/tags/export` が `name`/`parent_name`/`description` の3列CSV（UTF-8 BOM付き）を返す。
- [ ] `TagTreePage` の「CSVエクスポート」ボタンで全タグをダウンロードできる。
- [ ] ダウンロードしたCSVをそのまま `import_tag_batch`（CSV一括インポート）へ再投入しても、タグの内容（親子関係・説明）が変化しない（往復整合性、no-op更新）。
- [ ] エイリアス（`tag_alias`）がCSVに含まれない。
- [ ] 既存の個別CRUD・タグ一括インポート・全データエクスポート・`tag_selector_mcp` に影響がない。
