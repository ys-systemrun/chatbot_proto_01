## 0. 本書作成にあたり確定した事項

要件定義書・ADR-0074で「実装時判断」とされた事項を、本書で次の通り確定する。

| 項目 | 決定内容 | 根拠 |
|---|---|---|
| GAP 定数 | `tag_repository.py` のモジュール定数 `_DISPLAY_ORDER_GAP = 1000.0` として1箇所に定義し、新規採番・末尾追加・「1つ下へ」で共用する | ADR-0074 決定3 |
| 兄弟集合の取得SQL | `parent` が `NULL`（ルート）と非NULLで分岐する（`= %s` に `None` を渡すと SQL 上 `= NULL` となり常に偽になるため）。テーブル名・列名は内部リテラルのみで組み立てる | psycopg2 の NULL 挙動 |
| 一覧の並び順 | `list_tags`/`list_tag_folders` の SELECT を `ORDER BY display_order, id` に変更する（`display_order` 同値時は `id` をタイブレーク、ADR-0074 決定4）。ツリー構築のグルーピングは行の出現順を保持するため、兄弟集合内の相対順序はこの並びで正しく決まる | ADR-0074 決定4 |
| reorder の共通計算 | 「上/下」の中間値計算は `_compute_reordered_value(siblings, target_id, direction)` に共通化し、タグ版・フォルダ版から呼び出す。境界（先頭で"up"／末尾で"down"）は No-Op（`None` を返し UPDATE しない）でエラーにしない | ADR-0074 決定2/3、要件6.2 |
| move 時の再採番タイミング | reparent の UPDATE で `parent` と `display_order` を同時に更新する。新しい兄弟集合の末尾値は「親を付け替える前」の対象親の兄弟集合の最大値 + GAP で計算する（付け替え後だと移動ノード自身の旧値が混入するため） | ADR-0074 決定3 |
| direction バリデーション | `"up"`/`"down"` 以外は `TagError`（→ web_backend で 4xx）とする | 要件6.2 |
| GET レスポンスの `display_order` | `TagNode.to_dict()`・フォルダ dict・型定義（TS）に `display_order` を含める（境界判定は配列位置で行うため必須ではないが、デバッグ・将来のD&D拡張のため。ADR-0074 結果・影響/要件6.3） | 要件6.3 |
| 境界（先頭/末尾）判定 | フロントは各兄弟集合の配列内での位置（先頭/末尾）で「↑」「↓」ボタンを無効化する（`display_order` 値そのものは使わない） | 要件6.4 |

## 2. 実装詳細

### 2.1 マイグレーション（T1）

`db_hiroba_qa_init/migrations/0008_add_tag_display_order.sql` を新規追加する。既存 0007 と同じく yoyo が `.sql` を適用する。冪等（`IF NOT EXISTS`／`WHERE display_order IS NULL` による再実行安全）。DDL は要件6.1と同一:

1. `hiroba_tag`・`hiroba_tag_folder` に `display_order DOUBLE PRECISION` を追加。
2. `parent_tag_id`／`parent_folder_id` ごとに現行 `id` 順で `ROW_NUMBER() * 1000.0` を採番（`display_order IS NULL` の行のみ＝再実行安全）。
3. 両列を `SET NOT NULL`。
4. `(parent_tag_id, display_order)`・`(parent_folder_id, display_order)` の複合インデックスを追加。

### 2.2 `TagNode`（T2）

`models/tag.py` に `display_order: Optional[float] = None` を追加し、`to_dict()`（`include_children` 双方）に `"display_order": self.display_order` を含める。

### 2.3 `TagRepository`（T3）

モジュール定数 `_DISPLAY_ORDER_GAP = 1000.0` を追加する。

- `list_tags`: SELECT を `id, name, parent_tag_id, description, folder_id, display_order`、`ORDER BY display_order, id` に変更。`TagNode` 構築時に `display_order=r[5]`。
- `list_tag_folders`: SELECT を `id, name, description, parent_folder_id, display_order`、`ORDER BY display_order, id` に変更。ノード dict に `"display_order": r[4]`。
- `_get_node`: SELECT に `display_order` を追加し `TagNode.display_order` に設定（create/rename/move/reorder の戻り値が値を持つ）。
- 単一フォルダ SELECT（`rename_tag_folder`/`move_tag_folder`/`create_tag_folder` 戻り値）: `display_order` を含めて dict に載せる。
- 共通ヘルパ:
  - `_sibling_max_display_order(cur, table, parent_col, parent_id) -> Optional[float]`: `parent_id` の NULL/非NULL で分岐し `SELECT MAX(display_order)` を返す。
  - `_next_display_order(cur, table, parent_col, parent_id) -> float`: `max` があれば `max + GAP`、無ければ `GAP`。
  - `_ordered_siblings(cur, table, parent_col, parent_id) -> list[tuple[int, float]]`: `SELECT id, display_order ... ORDER BY display_order, id`（NULL/非NULL分岐）。
  - `@staticmethod _compute_reordered_value(siblings, target_id, direction) -> Optional[float]`:
    - `up`: idx==0 → `None`。B=前, A=前々（無ければ None）。`(A+B)/2`（A無し→`B/2`）。
    - `down`: idx==末尾 → `None`。C=後, D=後々（無ければ None）。`(C+D)/2`（D無し→`C+GAP`）。
- `create_tag`: INSERT に `display_order` 列を追加し、`_next_display_order(cur, "hiroba_tag", "parent_tag_id", parent_tag_id)` を採番。
- `create_tag_folder`: 同様に `parent_folder_id` 単位で採番。
- `move_tag`: 新しい `display_order` を「付け替え前」に `_next_display_order(..., new_parent_tag_id)` で計算し、`UPDATE hiroba_tag SET parent_tag_id = %s, display_order = %s WHERE id = %s` で同時更新。
- `move_tag_folder`: 同様に `UPDATE hiroba_tag_folder SET parent_folder_id = %s, display_order = %s WHERE id = %s`。
- `reorder_tag(tag_id, direction)` 新設: direction 検証→`_get_node`で存在確認→`_ordered_siblings`→`_compute_reordered_value`→非Noneなら `UPDATE hiroba_tag SET display_order = %s WHERE id = %s`→更新後 `TagNode` を返す。
- `reorder_tag_folder(folder_id, direction)` 新設: 同様のロジックで、更新後のフォルダ dict を返す。

### 2.4 MCPツール・スキーマ（T4）

`tools.py` の `move_tag` 登録直後に `reorder_tag`、`move_tag_folder` 直後に `reorder_tag_folder` を追加（`TagError`→`ToolError`）。`schemas.py` の `TAG_NODE_SCHEMA`・`TAG_FOLDER_SCHEMA` に `display_order`（`number`）を追加し、`REORDER_INPUT_SCHEMA`（`direction: enum[up,down]`）を追加する。

### 2.5 web_backend（T5）

`tag_controller.py` に `ReorderRequest(BaseModel){ direction: str }` と `reorder_tag`/`reorder_tag_folder` ハンドラ（`_client.call_tool` 呼び出し + `log_admin_operation`）を追加。`app.py` に:

- `PATCH /api/tags/{tag_id}/reorder` → `tag_controller.reorder_tag(tag_id, body)`
- `PATCH /api/tag-folders/{folder_id}/reorder` → `tag_controller.reorder_tag_folder(folder_id, body)`

### 2.6 front_dev（T6）

- `domain/admin/tag.ts`: `TagNode`・`TagFolder` に `display_order: number` を追加。`TagReorderRequest { direction: "up" | "down" }` を追加。
- `api.ts`: `reorderTag(id, body)`（`PATCH /api/tags/${id}/reorder`）、`reorderTagFolder(id, body)`（`PATCH /api/tag-folders/${id}/reorder`）。
- `TagTreePage.tsx`: `actions(node, siblings)` にタグ用「↑/↓」、フォルダ行に「↑/↓」ボタンを追加。境界（兄弟配列の先頭/末尾）で該当ボタンを `disabled`。押下で `run(() => reorderTag(...))`（成功後 `reload()`）。兄弟集合の判定は「同じ `parent_tag_id`／`parent_folder_id` を持つノード列」で行う。

### 2.7 テスト（T7）

`tests/test_tools.py` の Fake DB を新SQLに追随させる（`display_order` を store に保持、`INSERT`の列増、`MAX(display_order)`／`SELECT id, display_order ... ORDER BY display_order, id`／`SET parent_..., display_order`／`SET display_order` を解釈、`list`系の `ORDER BY display_order, id` 対応）。追加テスト: 末尾採番（create の display_order が単調増加）、`reorder_tag` up/down で並びが入れ替わる、境界 No-Op、`move_tag` 後に移動先兄弟集合の末尾に付く。

## 3. 動作確認（T8）

- `cd knowledge_mcp && python -m pytest tests/test_tools.py`。
- `docker compose` で `db_hiroba_qa_init` を再実行し、0008 マイグレーション適用後に既存タグ一覧の表示順が従来（id順）と一致すること。
- 管理画面でタグ・タグフォルダを「↑/↓」で入れ替えられること、先頭/末尾でボタンが無効なこと、新規作成・reparent が末尾に付くこと。
- `search_knowledge` の `combined_score`/`tag_similarity`/`embedding_score` が並べ替え前後で不変であること（表示専用属性のため）。
