# docs/improvements — 改善記録

回答品質の改善ループ（ADR-0099 §6）で行った改善を、1件ずつ「仮説 → 変更 → 結果 → 判断」の形で残します。
ADR が「設計の判断」を残すのに対し、ここは「ナレッジデータ・プロンプト・設定を変えて回答がどう変わったか」を残します。

## 進め方

1. **材料を集める**: `evals\eval.bat pull-feedback` で人手評価を取り込む（`evals/feedback/`）。
   段階③以降はゴールデンセット評価（`evals/runs/`）も使う。
2. **仮説を立てる**: 👎 とその理由、回答時の参考情報（`context`）、リリースを見て、何が悪いかを考える。
   Claude Code に `evals/feedback/` を読ませて分析・修正案を出させてよい。
3. **記録を作る**: `_template.md` をコピーして `NNNN-<題名>.md` を作り、「仮説」まで書く（ステータス: 検証中）。
4. **変更する**: 次のどれかを変えてコミットする。
   - ナレッジデータ: `db_init/data/` を編集 → `terraform\dvc.bat add` → コミット → `dvc.bat push`（ADR-0097）
   - 管理画面での編集（QA・タグ・言い換え・検索対象フラグ）: 編集内容を記録に書く
   - プロンプト: `agent_invitro/prompts/*.md` を編集してコミット（ADR-0099 §3）
   - 設定値（top_k など）: 環境変数・terraform の変更をコミット
5. **反映して評価する**: デプロイ後、同じ質問で試す。回答には新しい `release_id` が付く
   （プロンプト・コード・設定の変更で変わる。管理画面での編集だけでは変わらない）。
6. **結果と判断を書く**: 変更前後の評価（`evals/feedback/` の該当行、段階③以降は `evals/runs/` の比較）を書き、
   採用・差し戻し・追加調査を決める。ステータスを更新し、下の一覧にも反映する。

## 番号と命名

- `NNNN` は 4 桁の連番（0001 から）。題名は内容が分かる短い日本語でよい（例: `0001-見積書複製の手順を現行版に更新.md`）。
- 1 件 = 1 つの仮説。複数の変更をまとめて試した場合も、仮説が 1 つなら 1 件にする。
