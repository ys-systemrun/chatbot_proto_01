# タグフォルダ階層化 要件定義書

- 文書番号: REQ-202609030857
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `db_hiroba_qa_init`（マイグレーション）、`knowledge_mcp`（`TagRepository`・タグフォルダ関連MCPツール）、`web_backend`（`tag_controller.py`）、`front_dev`（`TagTreePage.tsx`／`TagPicker.tsx`／`tagFilter.ts`／`domain/admin/tag.ts`）
- 変更なしのコンポーネント: `search_knowledge`のスコアリングロジック（ADR-0058祖先展開・ADR-0059タグ構成類似度）、`qa_tag`テーブル、`tag_selector_mcp`、タグ自体のis-a階層（`hiroba_tag.parent_tag_id`）
- 参照資料: ADR-0072、ADR-0073、`docs/requirement/202609021050_タグ運用ガイドライン.md`、`docs/requirement/202609021102_タグ管理画面・タグ選択UI改修要件定義書.md`

## 1. 目的

ADR-0072で新設したタグフォルダ（`hiroba_tag_folder`）を、フラットな1階層の一覧から、フォルダ同士が親子関係を持てるツリー構造へ拡張する。分類軸（「対象システム」「文脈」等）自体をさらに細分化して管理できるようにし、タグ件数の増加に伴う分類の粒度不足に対応する。

## 2. 背景

ADR-0072・要件定義書202609021102で実装したタグフォルダは、`id/name/description`のみを持つフラットなマスタであり、フォルダ同士の親子関係を持たない。運用が進むにつれ、1つの分類軸をさらに下位区分に分けてグルーピングしたいニーズが生じている（例:「対象システム」の下に「フロントエンド」「バックエンド」を設ける等）。ADR-0073はこれを受けて、`hiroba_tag_folder`への`parent_folder_id`列追加、フォルダ名の一意性制約撤廃、フォルダ削除時の子フォルダ繰り上げ処理を決定した。本書は、この決定を実装可能な粒度の要件に落とし込む。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| ルートフォルダ | `parent_folder_id`が`NULL`のタグフォルダ。階層の最上位。 |
| 子フォルダ / 親フォルダ | `parent_folder_id`によって連結される、タグフォルダ同士の親子関係。 |
| 繰り上げ | 親フォルダの削除時に、その子フォルダの`parent_folder_id`を削除対象フォルダの親（祖父母フォルダ）の値へ更新する処理。 |

## 4. スコープ

### 4.1 対象範囲

- `hiroba_tag_folder`への`parent_folder_id`列追加、および`name`列のUNIQUE制約撤廃のマイグレーション。
- `TagRepository`（`knowledge_mcp`）のタグフォルダ関連メソッドの改修・新設（`list_tag_folders`のツリー化、`create_tag_folder`への`parent_folder_id`パラメータ追加、`rename_tag_folder`の同名チェック撤廃、`move_tag_folder`新設、`delete_tag_folder`の繰り上げロジック追加）。
- 上記に対応するMCPツール定義（`mcp/tools.py`・`mcp/schemas.py`）の改修・新設。
- `web_backend`の`/api/tag-folders`エンドポイント（レスポンスのツリー化、`parent_folder_id`の入出力、移動用エンドポイントの新設）の改修。
- `front_dev`のタグフォルダ管理UI（`TagTreePage.tsx`）のツリー表示・移動操作への改修、および`TagPicker.tsx`・`tagFilter.ts`（`groupTagsByFolder`）のネストしたフォルダのグルーピング表示への改修。

### 4.2 対象外（本書のスコープに含めない）

- タグ自体のis-a階層（`hiroba_tag.parent_tag_id`）への変更。本書はタグフォルダ同士の階層のみを対象とする。
- タグフォルダのCSVインポート/エクスポート（ADR-0072 Open Issue #2の結論待ち）。
- `search_knowledge`・`QARepository`・ADR-0058/0059のロジック変更（ADR-0072・ADR-0073の方針により対象外）。
- タグフォルダマスタの作成・削除権限（ADR-0006・ADR-0072が残したOpen Issueと同じ論点、本書では扱わない）。

## 5. 全体アーキテクチャ

```
front_dev
  ├─ TagTreePage.tsx  … タグフォルダ管理UI（ツリー表示・作成・改名・移動・削除）（改修）
  ├─ TagPicker.tsx     … タグフォルダ別グルーピング表示（ネスト対応）（改修）
  └─ tagFilter.ts      … groupTagsByFolder のネスト対応（改修）
        │ HTTP: /api/tag-folders（改修）, /api/tag-folders/{id}/move（新設）
        ▼
web_backend / tag_controller.py（改修）
        │ MCP: list_tag_folders / create_tag_folder / rename_tag_folder / move_tag_folder（新設） / delete_tag_folder
        ▼
knowledge_mcp / TagRepository（改修）
        │
        ▼
db_hiroba_qa（hiroba_tag_folder に parent_folder_id 列追加、name の UNIQUE 制約を撤廃）
```

## 6. 機能要件

### 6.1 データモデル

```sql
ALTER TABLE hiroba_tag_folder
    ADD COLUMN IF NOT EXISTS parent_folder_id INTEGER REFERENCES hiroba_tag_folder(id);

CREATE INDEX IF NOT EXISTS idx_hiroba_tag_folder_parent_folder_id
    ON hiroba_tag_folder (parent_folder_id);

ALTER TABLE hiroba_tag_folder DROP CONSTRAINT IF EXISTS hiroba_tag_folder_name_key;
```

- 既存フォルダの`parent_folder_id`は全件`NULL`（ルート直下）として移行する。
- `hiroba_tag.folder_id`のスキーマ・意味（1タグにつき0または1件、階層のどの深さのフォルダにも割当可）は変更しない。

### 6.2 タグフォルダマスタの管理（`knowledge_mcp` / MCPツール）

- `list_tag_folders`: 戻り値をフラットな一覧から、`parent_folder_id`によるツリー構造（`children`を持つ入れ子構造）へ変更する。既存の呼び出し元（`web_backend`・`front_dev`）はツリー構造を前提に改修する。
- `create_tag_folder(name, description=None, parent_folder_id=None)`: `parent_folder_id`パラメータを追加する。指定された場合、当該IDのフォルダが存在することを検証する。**同名フォルダの存在チェック（作成拒否）は撤廃する**（ADR-0073決定1）。
- `rename_tag_folder(folder_id, new_name, description=None)`: **同名フォルダの存在チェック（改名拒否）は撤廃する**（ADR-0073決定1）。
- `move_tag_folder(folder_id, new_parent_folder_id)`: 新設。指定フォルダの`parent_folder_id`を更新する。`new_parent_folder_id`が`folder_id`自身、または`folder_id`の子孫である場合は循環参照としてエラーとする（`move_tag`の`_assert_no_cycle`と同じ考え方、フォルダ版の再帰CTEで検証）。
- `delete_tag_folder(folder_id)`: 既存の「`hiroba_tag`から参照されている場合は削除を拒否する」判定は維持する。加えて、削除対象フォルダに子フォルダが存在する場合、それらの子フォルダの`parent_folder_id`を削除対象フォルダの`parent_folder_id`（祖父母フォルダ、削除対象がルートだった場合は`NULL`）へ更新してから、削除対象フォルダを削除する（ADR-0073決定3、繰り上げ）。

### 6.3 `web_backend`（`tag_controller.py`）

- `/api/tag-folders`（GET）: レスポンスをツリー構造（`children`を持つ）へ変更する。
- `/api/tag-folders`（POST）: リクエストボディに`parent_folder_id`（省略可）を追加する。
- `/api/tag-folders/{folder_id}`（PATCH）: 同名チェックに起因するエラーレスポンスがなくなる点を除き、既存の`name`/`description`更新の挙動は維持する。
- `/api/tag-folders/{folder_id}/move`（PATCH、新設）: `new_parent_folder_id`を受け取り、`move_tag_folder`を呼び出す。
- `/api/tag-folders/{folder_id}`（DELETE）: 挙動は変更しない（レスポンスコード・エラー内容は既存のまま）。子フォルダの繰り上げは`knowledge_mcp`側で完結し、`web_backend`は結果を透過的に返す。

### 6.4 `front_dev`

- `domain/admin/tag.ts`の`TagFolder`型に`parent_folder_id: number | null`と`children: TagFolder[]`を追加する。
- `TagTreePage.tsx`のタグフォルダ管理UI（現状: フラットな一覧＋作成フォーム）を、インデントまたはツリー表示に改修する。作成フォームに親フォルダ選択欄を追加する。移動操作（ドラッグ&ドロップ、または親フォルダ選択プルダウンによる移動）を追加する。
- 同名フォルダが複数存在しうるため、フォルダ選択UI（作成フォームの親フォルダ選択、タグへの割当プルダウン等）では、フォルダ名だけでなく親フォルダの経路（パンくず、例:「対象システム ＞ フロントエンド」）を併記し、利用者が同名フォルダを識別できるようにする。
- `tagFilter.ts`の`groupTagsByFolder`を、フラットな「フォルダごとに1セクション」から、ネストしたフォルダ階層を反映したグルーピングへ改修する。中間フォルダに直接割り当てられたタグと、子フォルダに割り当てられたタグを同一セクション内でどう区別表示するかは、実装時にUIデザインとして確定する（本書では「フォルダ階層をセクションの入れ子として表示し、各セクション見出しに直下のタグ数を併記する」を基本方針とする）。
- `TagPicker.tsx`も同様の改修を行う。

## 7. データ要件

- `db_hiroba_qa_init`のマイグレーションとして、6.1節のDDLを追加する（既存の番号体系に従い新規マイグレーションファイルを作成、`IF NOT EXISTS`／`DROP CONSTRAINT IF EXISTS`による冪等性を維持する）。
- 既存の`hiroba_tag_folder`データ・`hiroba_tag.folder_id`データには変更を加えない（`parent_folder_id`は全件`NULL`として扱う）。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 後方互換性 | `hiroba_tag.folder_id`のスキーマ・挙動は変更しない。既存タグの`search_knowledge`検索結果・スコアには影響しない。 |
| データ整合性 | フォルダの移動・削除時の循環参照防止・繰り上げ処理は、`hiroba_tag`のis-a階層で確立済みの方式（再帰CTEによる祖先集合の算出）を踏襲する。 |
| UI一貫性 | フォルダ名の重複を許容するため、フォルダを選択・表示するすべての箇所（作成フォームの親選択、タグへの割当、グルーピング見出し）で、親フォルダの経路を併記し同名フォルダの混同を防ぐ。 |

## 9. インフラ・実行環境要件

- 新規の環境変数・AWSリソースは発生しない。`db_hiroba_qa_init`のマイグレーション実行フロー（ローカル`docker-compose`・AWS双方）に、7章のマイグレーションが追加されるのみ。

## 10. 既存システムとの関係・影響範囲

- `tag_selector_mcp`の`TagMetadataRepository`は`hiroba_tag`を明示的な列指定で読み込んでおり、`hiroba_tag_folder`自体は参照していないため、本書の変更による影響はない。
- `search_knowledge`・`QARepository.search`・`qa_tag`・ADR-0058/0059のロジックには変更を加えない。
- `import_tag_batch`/`export_tags`（ADR-0061/0065）はタグ自体の一括インポート/エクスポートであり、タグフォルダを対象としていないため、本書の変更による直接の影響はない（タグフォルダ自体のCSV化は引き続きADR-0072 Open Issue #2の検討事項）。

## 11. 受け入れ基準（Definition of Done）

- [ ] `TagTreePage`のタグフォルダ管理UIで、親フォルダを指定してタグフォルダを新規作成できる。
- [ ] `TagTreePage`のタグフォルダ管理UIで、既存のタグフォルダを別の親フォルダの下へ移動できる。移動先が自分自身または自分の子孫の場合はエラーになりブロックされる。
- [ ] 子フォルダを持つタグフォルダを削除すると、その子フォルダは削除対象フォルダの親（祖父母フォルダ、ルートだった場合は最上位）の下へ繰り上がる。子フォルダに割り当てられたタグの`folder_id`は変化しない。
- [ ] `hiroba_tag`から参照されているタグフォルダの削除は、従来通り拒否される。
- [ ] 同名のタグフォルダを異なる親の下に作成できる（一意性制約エラーが発生しない）。
- [ ] `TagPicker`・`TagTreePage`のタグフォルダ選択UIで、同名フォルダが複数ある場合でも親フォルダの経路（パンくず）により区別して選択できる。
- [ ] タグフォルダの階層化・移動・削除を行っても、`search_knowledge`の検索結果・スコア（`combined_score`/`tag_similarity`/`embedding_score`）に変化がないことを確認する。

## 12. Open Issues（要追加確認事項）

1. **フォルダ階層の深さに上限を設けるか**: 本書では上限を設けない想定とした。UI表示（インデント幅等）の観点から実用上の上限を設けるべきかは、実装時のUI設計と合わせて確認が必要。
2. **`groupTagsByFolder`のネスト表示の具体的なデザイン**: 6.4節で基本方針のみ示した。中間フォルダに直接割り当てられたタグの表示位置（子フォルダのセクションと並べるか、専用の「（このフォルダ直下）」枠を設けるか）は、実装時にUIモックアップを見ながら確定する必要がある。
3. **タグフォルダのCSVインポート/エクスポート（ADR-0072 Open Issue #2）**: 本書では対象外としたが、対応する場合はフォルダ階層を表す列（親フォルダIDまたは経路）の設計が別途必要になる。
4. **タグフォルダマスタの作成・削除・移動権限**: ADR-0006・ADR-0072が残したタグ管理全般の権限に関するOpen Issueと同じ論点であり、本書では決定しない。
