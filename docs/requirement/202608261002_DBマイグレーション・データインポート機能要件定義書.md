# DBマイグレーション・データインポート機能 要件定義書

- 文書番号: REQ-202608261002
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `db_hiroba_qa_init`（マイグレーション処理の拡張）, `db_conversation/init.sql`（マイグレーション化への置き換え）, `front_dev`（QA管理画面・検証質問画面の拡張）, `web_backend`（新規インポートAPI・新規モジュール）, `knowledge_mcp`（新規MCPツール）, `docs/`
- 参照資料: `docs/requirement/202608061016_DBマイグレーションシード自動化要件定義書.md`, `docs/requirement/202608060826_QAタグ管理UI要件定義書.md`, `docs/requirement/202608241530_全データエクスポート機能要件定義書.md`, `docs/requirement/202608260909_質問タグ情報源検索精度検証機能要件定義書.md`
- 前提の決定事項: 本書末尾「14. 関連ADR一覧」参照

## 1. 目的

本プロジェクトでは、これまで個別の機能追加のたびに「DBスキーマをどう変更するか」「初期データ・関連データをどう投入するか」を、その機能ごとに最小限の方式で決めてきた（`chatbot`データベースはyoyo-migrations、`conversation`データベースは冪等DDLの追記、等）。この積み重ねにより、次の2つの課題が顕在化している。

1. **マイグレーション方式がデータベースによって異なり、`conversation`データベース側はバージョン管理・適用履歴の追跡ができていない。** 特に`conversation`データベースは、当初2テーブル（`conversation`/`message`）のみだったものが、直近の検証機能追加（ADR-0048）で4テーブルが加わり計6テーブルとなっており、`chatbot`データベースでyoyo-migrations導入の引き金になった「モデル別`init.sql`のドリフト」（要件定義書202608061016 2.1節）と同種のリスクが、`conversation`データベース側でも顕在化しうる規模になってきている。
2. **データの一括インポート機能が、複数の要件定義書で「対象外」として繰り返し先送りされてきた。** 具体的には次の3件である。
   - QAタグ管理UI要件定義書（202608060826）4.2節: 「タグ・QAデータの一括インポート/エクスポート（CSV等）」
   - 全データエクスポート機能要件定義書（202608241530）4.2節: 「インポート機能（エクスポートしたSQL/CSVを別環境に取り込む操作自体は本書の対象外）」
   - 検索精度検証機能要件定義書（202608260909）4.2節: 「検証質問のCSV等によるインポート・エクスポート機能」

本書は、この2つの課題を1本の要件定義書として整理し、次を目的とする。コーディングは対象外とし、要件定義および設計判断（ADR）の整理にとどめる。

- `conversation`データベースのスキーマ管理を、`chatbot`データベースと同水準の、バージョン管理された正式なマイグレーション方式に統一すること。
- `chatbot`データベースのマイグレーション運用について、既存要件定義書（202608061016）13章で積み残されたOpen Issueのうち、本書の範囲で対応可能なものを整理すること。
- 上記3件の「一括インポート対象外」を解消し、QA・タグデータ、検証質問データ、および全データエクスポート機能が生成したダンプの、3種類のデータインポート機能を要件として整理すること。

## 2. 背景・参照資料

### 2.1 現状のマイグレーション方式（データベースごとの差異）

| データベース | 現状の方式 | バージョン管理 | 適用履歴 |
|---|---|---|---|
| `chatbot`（`db_hiroba_qa`, pgvector） | `db_hiroba_qa_init`がyoyo-migrationsで管理（ADR-0016〜0018） | あり（yoyoの追跡テーブル） | あり |
| `conversation`（`db_conversation`） | `db_conversation/init.sql`への冪等DDL追記、AWSでは`db_hiroba_qa_init`内の専用ステップ（ADR-0044、ADR-0048） | なし（yoyo導入は見送り） | なし |

`conversation`データベースについてyoyo-migrations導入を見送った際の判断（ADR-0044「検討した代替案」）は、「現時点でのスキーマは2テーブル・1バージョンのみであり、複数マイグレーション・パラメータ化への対応というADR-0017の前提が当てはまらない」というものだった。しかし、直後の検証機能追加（ADR-0048、本日付）で4テーブルが追加され、計6テーブル・複数バージョンの状態になっている。ADR-0044時点の前提はすでに崩れている。

### 2.2 データインポートが「対象外」とされてきた3つの箇所

- **QA・タグの一括インポート**（202608060826 4.2節）: QA管理UI・タグ管理UIの初回要件定義時点では、個別登録・編集フォームのみをMVPとし、一括インポートは見送られた。
- **全データエクスポートの対（インポート）**（202608241530 4.2節）: エクスポート機能は「生成するSQLファイルが`psql -f`等で再投入可能な形式であることの確認にとどめる」とされ、実際に別環境へ取り込むための手順・機能自体は要件化されなかった。
- **検証質問の一括インポート**（202608260909 4.2節）: 検証機能の初回要件定義時点では、質問の個別登録フォームのみをMVPとし、CSV等による一括登録は見送られた。

いずれも「まず個別機能を成立させ、一括インポートは運用が回り始めてから」という共通の先送り理由を持つ。本書時点で、これら3件を要件化する。

### 2.3 発注者への確認・回答

本書作成にあたり、発注者（ユーザー）に以下の点を確認し、回答を得た。本書はこの回答を前提に要件を定義する。

1. データインポートの対象 → 「QA・タグデータの一括インポート」「検証質問データの一括インポート」「会話履歴等の他環境データ取り込み」の3点すべてを対象とする。
2. マイグレーション整備の対象 → 「conversationデータベースの正式なマイグレーション管理」「chatbotデータベースの改善」の2点を対象とする。
3. 「他環境データ取り込み」の具体的なケース → 既存の全データエクスポート機能（ADR-0046/0047）が生成したデータの取り込み（2.2節「全データエクスポートの対」と同一の課題）。
4. ドキュメント構成 → 機能ごとに分割せず、1本の要件定義書にまとめる。

本書初版公開後、残るOpen Issue（初版12章）について追加で確認し、以下の回答を得た（2026-08-26）。

5. 全データインポート時、投入先データベースに既存データがある状態を想定するか → 常に空のデータベースへの投入のみを想定する。
6. 全データインポートの実行方式（ADR-0055提案の採否） → 提案通り、ブラウザUIは作らず運用者によるCLI／一時タスク実行のみとする。
7. QA一括インポートで、CSVに指定されたタグ名が既存のタグマスタに存在しない場合の挙動 → 自動的に新規タグとして作成する。
8. 検証質問一括インポートで、同一の質問文が既に登録済みの場合の挙動 → 重複チェックは行わない（常に新規追加する）。
9. 一括インポート機能（QA・検証質問）へのアクセス制御 → 既存の管理画面群と同様、ネットワークレベルの制限のみとし、追加のログイン認証は設けない。
10. 全データインポート実行中、対象サービス（`web_backend`等）を停止するか → メンテナンス時間帯を設け、対象サービスを停止した上で実行する運用とする。
11. `conversation`データベースのyoyo移行に伴う既存環境のベースライン化作業の実施タイミング → 本要件の実装フェーズ内でまとめて実施する。
12. QA一括インポートで既存QAを更新（`uuid`指定）する際、CSVに含まれない項目（例: `tags`列が空）の挙動 → 既存値を維持する（部分更新とする）。

### 2.4 本書公開後の追加確認（2026-08-31）

全データインポート機能の詳細設計を検討する過程で、2.3節#5・#6で確認済みだった前提について見直しが必要になり、発注者に追加で確認し、以下の回答を得た。本節の内容はADR-0066に反映し、2.3節#5・#6の該当部分を置き換える。

13. 投入先データベースに既存データがある状態を想定するか（2.3節#5の見直し） → 想定する。全データインポート実行時は、投入対象（下記15.の選択に従い`chatbot`/`conversation`のいずれか、または両方）の既存データを全消去した上で、インポートデータで上書きする方式に変更する（ADR-0066）。
14. 全データインポートの実行方式（2.3節#6の見直し） → ECS Execによる手順（ADR-0055）は障害時の手動対応手段として残しつつ（併存）、通常運用は`db_hiroba_qa_init`を拡張したバッチ実行（1コマンドの起動のみで完結、ADR-0066）を新設する。
15. 全消去の対象範囲の指定 → 1回の実行で`chatbot`・`conversation`の両方を対象にする場合と、いずれか一方のみを対象にする場合とを、実行時のパラメータで使い分けられるようにする。
16. 全消去前の安全策 → 既存の全データエクスポート機能（ADR-0046/0047）を同一バッチ内から自動的に呼び出し、消去対象データの退避SQLを生成してから消去・上書きを行う。
17. 破壊的操作（全消去→上書き）の実行確認方式 → 対象環境名のタイプ確認（既存の`destroy-app`等と同様の方式）とする。
18. 全消去の実装方式 → 対象テーブルを`TRUNCATE ... RESTART IDENTITY CASCADE`でデータのみ消去し、スキーマ（テーブル定義）はそのまま流用する（エクスポート元と投入先が同一マイグレーションバージョンであることを前提とする）。
19. 全データインポート実行時に停止する対象サービスの範囲 → `chatbot`/`conversation`データベースに接続する全アプリケーションサービス（`web_backend`・`knowledge_mcp`・`tag_selector_mcp`）とする。
20. S3アップロードの扱い → 引き続きS3経由とするが、ローカルのSQLダンプをS3へアップロードする操作自体も同一バッチ処理に含める（運用者による事前手動アップロードを廃止する）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| マイグレーション | `CREATE TABLE`/`ALTER TABLE`等、スキーマを段階的に変更するための、適用履歴を追跡可能な処理単位（既存要件定義書202608061016と同義） |
| 一括インポート | 個別登録フォームによる1件ずつの登録ではなく、CSV等のファイルをアップロードし、複数件のデータを一度に登録・更新する操作 |
| 全データインポート | 全データエクスポート機能（ADR-0046/0047）が生成したSQL/CSVダンプを、別環境（ローカル⇔AWS等）の`chatbot`/`conversation`データベースへ取り込む操作。本書で新たに定義する「一括インポート」とは対象データ・実行主体が異なるため区別する（4.1節） |
| マイグレーター（migrator）ロール | DDL実行権限を持つ、`db_hiroba_qa_init`専用のデータベースロール（6.2節、ADR-0052） |

## 4. スコープ

### 4.1 対象範囲（MVP）

本書は、次の5件を対象範囲とする。

- a. **conversationデータベースのマイグレーション方式の統一**: `conversation`データベースのスキーマ管理を、`chatbot`データベースと同様にyoyo-migrationsへ移行する（6.1節、ADR-0051）。
- b. **chatbotデータベースのマイグレーション運用改善**: マイグレーション実行ユーザー（現状`postgres`スーパーユーザーを全処理で共用）の権限分離を行う（6.2節、ADR-0052）。
- c. **QA・タグデータの一括インポート機能**: `front_dev`のQA管理画面にCSVアップロードを追加し、Knowledge MCP経由でQA・タグを一括登録・更新する（6.3節、ADR-0053）。
- d. **検証質問データの一括インポート機能**: `front_dev`の検証質問一覧画面にCSVアップロードを追加し、`verification_db`経由で検証質問を一括登録する（6.4節、ADR-0054）。
- e. **全データインポート機能**: 全データエクスポート機能（ADR-0046/0047）が生成したSQL/CSVダンプを、別環境の`chatbot`/`conversation`データベースへ取り込むための、公式な手順・実行手段を整備する（6.5節、ADR-0055・ADR-0066）。実行手段はECS Exec手順（ADR-0055、障害時の手動対応用に併存）と、`db_hiroba_qa_init`拡張によるバッチ自動実行（ADR-0066、通常運用の第一手段）の2方式とし、後者は既存データの全消去・上書きを伴う（2.4節）。

### 4.2 対象外（将来検討・別スコープ）

- 実際のマイグレーションファイル・インポート処理のコーディング、Dockerfile・Terraform変更等の実装作業（本書は要件定義・ADRの整理までを対象とする）。
- embedding計算プロバイダの抽象化（ローカルLLM/Bedrock/OpenAIの切り替え機構）。既存要件定義書202608061016 13章Open Issue #1を引き継ぐ未解決課題であり、本書のインポート機能もこの既存の抽象化状況（未実装）を前提とする。
- 利用者ごとのログイン認証・操作権限分離。既存の管理画面群・エクスポート機能と同様、本書のインポート機能（QA・検証質問の一括インポート）もネットワークレベルの制限（社内IPアドレス限定, ADR-0041）のみとし、追加の認証は設けない（2.3節#9で確認済み）。
- インポートデータのスキーマ・値の高度なバリデーション（既存QA登録フォームが行う程度の必須項目チェックを超える、業務ルールに基づく整合性検証等）。基本的なフォーマットチェック・重複検出の範囲にとどめる（7章・8章）。
- 一括削除機能（インポートは登録・更新のみを対象とし、CSV等による一括削除は扱わない）。
- `qa_original`/`question_altered`の削除機能（202608060826 4.2節で既に対象外とされている既存の未解決課題であり、本書のQA一括インポートも「登録・更新のみ」とすることでこの制約と整合させる）。
- 全データインポート機能について、エクスポートと同一のブラウザボタン一つのUXを実現すること（6.5節・ADR-0055のとおり、書き込み権限のリスクを踏まえ、本書ではCLI／運用手順ベースの実現方式を軸とする。ブラウザUI化は将来検討とする）。

## 5. 全体アーキテクチャ

### 5.1 システム構成（追加・変更分）

│ db_hiroba_qa_init（既存, ワンショット）                              │

│  2. conversation DB: yoyo-migrations（新規, ADR-0051）           │

        ┌────────────────┼─────────────────┬───────────────────┐
        ▼                ▼                 ▼                   ▼
 knowledge_mcp     tag_selector_mcp    web_backend          （AWS: ECS一時タスク /
 （新規: QA一括     （既存, 変更なし）   （新規: QA一括インポートAPI,    ローカル: CLIスクリプト）
  インポートツール,                     検証質問一括インポートAPI,      全データインポート実行
  ADR-0053）                          全データインポート起点,ADR-0055）  （ADR-0055）
        │                                    │
        ▼                                    ▼

- `tag_selector_mcp`・`agent_invitro`には変更を加えない。
- QA・タグの一括インポート（c）は、既存の個別登録（ADR-0013）と同じく`web_backend → knowledge_mcp`経由の書き込み経路を維持する。
- 検証質問の一括インポート（d）は、既存の個別登録（ADR-0048）と同じく`web_backend`から`conversation`データベースへの直接書き込み経路を維持する。
- 全データインポート（e）のみ、既存の書き込み経路（Knowledge MCP経由／`conversation`直接）のいずれとも異なる、運用者による専用の実行経路を新設する（ADR-0055）。

## 6. 機能要件

### 6.1 conversationデータベースのマイグレーション方式の統一（ADR-0051）

- `conversation`データベースのスキーマ（`conversation`/`message`/`verification_question`/`verification_run`/`verification_run_tag`/`verification_run_source`の既存6テーブル）を、yoyo-migrationsのマイグレーション履歴として再構成する。
- `db_hiroba_qa_init`は、`chatbot`データベース向け（既存）と`conversation`データベース向け（新規）の、2つの独立したyoyo-migrations履歴を管理する（同一ツール・同一サービス内で、接続先データベースが異なる2系統の履歴を持つ）。
- 既存環境（ローカルの`db_conversation/data`ボリューム、AWSの既存`conversation`データベース）に対しては、README既存の「既存環境（手動migration適用済みボリューム）からの移行」節（`yoyo mark`によるベースライン化）と同様の手順を適用し、既に作成済みのテーブルを「適用済み」として履歴に登録できるようにする。
- ローカル`docker-compose`環境の`db_conversation`サービス（`init.sql`マウント）は廃止し、`chatbot`データベースと同様に、DB本体はデータ永続化のみを担う構成に変更する（`db_hiroba_qa_init`が唯一のスキーマ作成・変更の実行者になる）。
- 既存環境のベースライン化作業は、開発環境・AWS環境とも、本要件の実装フェーズ内でまとめて実施する（2.3節#11で確認済み）。

### 6.2 chatbotデータベースのマイグレーション運用改善（ADR-0052）

- 現状、`db_hiroba_qa_init`（マイグレーション・シード実行）と`web_backend`/`knowledge_mcp`/`tag_selector_mcp`（アプリケーションからのDML実行）が、同一の`postgres`スーパーユーザー資格情報（`DATABASE_URL`）を共用している（既存要件定義書202608061016 13章Open Issue #4）。
- 本書では、DDL実行権限を持つ「マイグレーター」ロールと、DML（SELECT/INSERT/UPDATE/DELETE）のみを実行できる「アプリケーション」ロールを分離する（ADR-0052）。`db_hiroba_qa_init`のみがマイグレーター権限を用い、`web_backend`/`knowledge_mcp`/`tag_selector_mcp`はアプリケーションロールの資格情報を用いる。
- `conversation`データベースについても、6.1節のyoyo移行に合わせて同様のロール分離を行う。
- 既存のエクスポート専用読み取りロール（`chatbot_export_reader`, ADR-0046）とは独立したロールとして新設し、責務（マイグレーション実行／アプリケーションDML／エクスポート読み取り）ごとに最小権限を割り当てる方針を統一する。

### 6.3 QA・タグデータの一括インポート機能（ADR-0053）

- `front_dev`のQA一覧ページ（`QaListPage`）に「CSVインポート」ボタンを追加し、CSVファイルをアップロードできるようにする。
- CSVフォーマット（案、詳細設計フェーズで確定）: `uuid`（空の場合は新規作成、値がある場合は既存QAの更新）, `title`, `question_text`, `answer_text`, `category_id`, `tags`（タグ名をカンマ区切り等で複数指定）。
- `web_backend`は、アップロードされたCSVをパースし、行ごとに`knowledge_mcp`の新規ツール（`import_qa_batch`、仮称）を呼び出す。当該ツールは、既存の`create_qa`/`update_qa`と同一のバリデーション・embedding計算・タグ紐付けロジックを再利用し、複数件をまとめて処理する（ADR-0053）。
- 存在しないタグ名が指定された場合は、自動的に新規タグとして作成する（2.3節#7で確認済み）。
- 既存QAの更新（`uuid`指定）時、CSVの列が空・未指定の場合は既存値を維持する部分更新とする（2.3節#12で確認済み）。`tags`列が空の場合も、既存のタグ紐付けは変更しない。
- インポート結果（成功件数、行ごとのエラー内容）を画面に一覧表示する。一部の行がエラーになっても、他の行の処理は継続する（行単位の部分成功を許容する）。

### 6.4 検証質問データの一括インポート機能（ADR-0054）

- `front_dev`の検証質問一覧ページ（`VerificationListPage`）に「CSVインポート」ボタンを追加する。
- CSVフォーマット（案）: `question_text`（必須）, `memo`（任意）のみ。`verification_question`には自然な一意キーがないため、既存行との重複判定は行わず、CSVの全行を新規`verification_question`として登録する（2.3節#8で確認済み）。
- `web_backend`は、既存の単発登録API（`POST /api/verification/questions`）の処理ロジックを再利用する`verification_db`の一括登録関数を新設し、CSVの内容をまとめて登録する。
- インポート結果（登録件数、行ごとのエラー内容）を画面に表示する。

### 6.5 全データインポート機能（ADR-0055）

- 全データエクスポート機能（ADR-0046/0047）が生成するSQL形式のダンプ（`chatbot.sql`、`conversation.sql`）を、別環境の対応するデータベースへ投入するための、公式な実行手順・実行手段を整備する。
- 実行手段は、ブラウザからのボタン操作（エクスポートと対称のUI）ではなく、運用者が実行する専用の手段（CLIスクリプトまたはワンショットの実行タスク）とする（2.3節#6で確認済み）。理由・比較検討はADR-0055を参照。
  - ローカル`docker-compose`環境: 既存の`docker compose exec`によるコンテナ内`psql`実行、または`db_hiroba_qa_init`と同系統の専用ワンショットサービスとして実行する。
  - AWS環境: ECS Execによる一時タスク実行（既存のMCP Inspector検証, ADR-0029と同様の実行形態）で、投入対象データベースに接続してSQLファイルを適用する。
- 投入時は、CSV形式ではなくSQL形式のダンプのみを対象とする（CSV形式は`embedding`列を含まず、そのままでは完全な再構築ができないため。ADR-0047参照）。
- 投入先データベースは常に空の状態であることを前提とする（2.3節#5で確認済み）。既存データがある状態への投入（`INSERT`の主キー衝突時の扱い等）は本書のスコープ外とし、必要になった場合に別途要件化する。
- 実行中は対象サービス（`web_backend`等）を停止するメンテナンス時間帯を設ける運用とする（2.3節#10で確認済み）。停止・再開の具体的な手順は実装フェーズで明文化する。

- **バッチ自動実行方式の追加（ADR-0066、2.4節）**: 上記のECS Exec手順に加え、`db_hiroba_qa_init`を拡張した専用モードにより、1コマンドの起動のみで完結するバッチ実行を新設する。ECS Exec手順は障害時の手動対応手段として残す（併存）。
  - 実行時に対象（`chatbot`/`conversation`のいずれか、または両方）を選択できる。
  - 投入先の既存データは、対象テーブルを`TRUNCATE ... RESTART IDENTITY CASCADE`で全消去した上で、SQLダンプの内容を投入する（2.3節#5の前提を撤回。2.4節参照）。
  - 全消去の直前に、既存の全データエクスポート機能を自動的に呼び出し、消去対象データの退避SQLを生成する（安全策）。
  - ローカルのSQLダンプをS3へアップロードする操作も同一バッチに含める。
  - 実行対象に応じて、接続する全アプリケーションサービス（`web_backend`・`knowledge_mcp`・`tag_selector_mcp`）を停止し、完了後に再起動する処理も同一バッチに含める。
  - 破壊的操作であるため、実行前に対象環境名のタイプ確認を必須とする。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 冪等性（マイグレーション） | `conversation`データベース向けyoyo-migrationsも、既存の`chatbot`データベース向けと同様、何度`db_hiroba_qa_init`を再作成・再実行しても、未適用のマイグレーションのみが適用される（既存ADR-0018の方針を踏襲） |
| 部分失敗時の扱い（一括インポート） | QA・タグ一括インポート、検証質問一括インポートは、行単位でエラーを許容し、成功した行は反映され、失敗した行のみエラーとして報告する（6.3節・6.4節） |
| 部分失敗時の扱い（全データインポート） | SQLダンプの投入は、既存のトランザクション単位（`psql -f`実行）に準じ、エラー時の途中終了・ロールバック方針を運用手順として明文化する（実装フェーズで確定） |
| ファイルサイズ・件数 | CSV一括インポートの上限件数・ファイルサイズは、既存の全データエクスポート機能が想定する規模（README記載のシードデータ規模）を目安とし、詳細は実装フェーズで確定する |
| セキュリティ・権限 | マイグレーター・アプリケーション・エクスポート読み取り専用の3系統のロールを最小権限の原則で分離する（8章・ADR-0052、既存ADR-0046と同一方針の拡張） |
| アクセス制御 | QA・検証質問の一括インポートは、既存の管理画面群と同様、ネットワークレベルの制限（社内IPアドレス限定, ADR-0041）のみとし、追加のログイン認証は設けない（2.3節#9で確認済み） |
| ログ | QA・タグ一括インポート、検証質問一括インポートの実行は、既存の管理系操作ログ（`log_admin_operation`）と同様の方式で記録する。全データインポートの実行は、運用者による手順実行のログ（コマンド実行記録）として別途運用ルールを定める |
| 可用性 | 全データインポートの実行中は、対象サービス（`web_backend`/`knowledge_mcp`等）を停止するメンテナンス時間帯を設ける運用とする（2.3節#10で確認済み）。停止・再開の具体的な手順は実装フェーズで明文化する |

## 9. インフラ・実行環境要件

### 9.1 ローカルdocker-compose環境

- `db_conversation`サービスの`init.sql`マウントを廃止し、`db_hiroba_qa_init`が`conversation`データベースのマイグレーションも実行するよう`docker-compose.yml`の依存関係（`depends_on`）を見直す。
- 全データインポートは、`docker compose exec`によるコンテナ内`psql`実行、またはこれに準じるスクリプトで行う（6.5節）。

### 9.2 AWS環境

- `db_hiroba_qa_init`（ECS一時タスク、ADR-0030）が、`conversation`データベース向けマイグレーションおよびロール作成ステップも実行するよう変更する。
- 全データインポートは、ECS Execによる一時タスク実行（ADR-0029と同様の実行形態）で行う。新規のALBエンドポイント・常時稼働リソースは追加しない。

## 10. 既存システムとの関係・影響範囲

- `db_conversation/init.sql`は廃止され、`db_hiroba_qa_init`のマイグレーションファイル群に統合される（ADR-0051）。
- `web_backend`/`knowledge_mcp`/`tag_selector_mcp`が使用するDB資格情報が、現状の単一の`postgres`スーパーユーザーから、用途別のロールに切り替わる（`docker-compose.yml`・Terraform・Secrets Managerの更新が必要、ADR-0052）。
- `knowledge_mcp`に新規MCPツール（一括インポート用）が追加されるが、既存ツール（`create_qa`等）には変更を加えない（ADR-0053）。
- `web_backend`の`verification_db`（202608260909の実装で新設予定）に、一括登録用の関数が追加される（ADR-0054）。既存の単発登録APIには変更を加えない。
- 全データインポートは、エクスポートが生成する既存のファイル形式（`CREATE TABLE IF NOT EXISTS`＋`INSERT`）をそのまま利用する（ADR-0055）。ただし全データインポート（ADR-0066）が`conversation`データベースの検証4テーブル（`verification_*`）も往復対象に含めるため、全データエクスポート機能の対象テーブルを`conversation`の2テーブルから6テーブルへ拡張する（7.2節の12テーブルに一致させる）。エクスポートの出力形式・実行経路（読み取り専用ロール／ブラウザボタン）自体は変更しない。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] `conversation`データベースのスキーマ変更が、yoyo-migrationsのマイグレーション履歴として追跡できる。
- [ ] 既存の`conversation`データベース（ローカル・AWSとも既存データを含む）に対して、ベースライン化の手順を実行した上でマイグレーションを導入しても、既存データ・既存テーブルが破壊されない。
- [ ] `db_hiroba_qa_init`・`web_backend`・`knowledge_mcp`・`tag_selector_mcp`が、用途別に分離されたDBロールで接続し、アプリケーション用ロールがDDL権限を持たないことを確認する。
- [ ] QA管理画面からCSVをアップロードし、複数件のQA・タグが一括で登録・更新できる。一部の行に誤りがあっても、正しい行は登録され、誤った行はエラーとして表示される。
- [ ] 検証質問一覧画面からCSVをアップロードし、複数件の検証質問が一括で登録できる。
- [ ] 全データエクスポート機能で生成したSQLダンプを、別環境（例: ローカル→別のローカル環境、またはAWSの別環境）に投入する手順が確立され、投入後にアプリケーションが正常に動作することを確認する。
- [ ] バッチ自動実行（ADR-0066）により、対象環境名の確認 → 既存データの自動退避 → 全消去 → SQLダンプ投入 → 対象サービス再起動、までが1回のコマンド実行で完了することを確認する。
- [ ] 既存のQA・タグ管理UI、検証機能、会話評価機能、全データエクスポート機能の動作に影響がないことを確認する。

## 12. Open Issues（要追加確認事項）

本書初版（2026-08-26午前）で挙げたOpen Issue #1〜#6は、同日中に発注者へ確認し解決済みとなった（回答内容は2.3節#5〜#12、各節への反映は6章・8章を参照）。以下は、その後も残る未確定事項である。

1. **`db_hiroba_qa_init`のロール作成対象の拡張範囲**: ADR-0052のロール分離を、本書が扱う`chatbot`/`conversation`の主要ロールに加え、将来追加されうるデータベース・サービスにも一貫して適用する運用ルールを、実装フェーズで明文化する必要がある。
2. **CSVフォーマットの最終確定**: 6.3節・6.4節に示したCSV列構成は現時点では案であり、詳細設計フェーズで最終確定する。特にQA一括インポートの`tags`列（複数タグの区切り文字・表現方法）は未確定。
3. **一括インポートのファイルサイズ・件数上限**: 8章に記載の通り、具体的な上限値（CSV行数、ファイルサイズ）は実装フェーズで確定する。
4. **全データインポートのAWS環境でのSQLファイル受け渡し方法**: ADR-0055に記載の通り、S3経由での一時アップロードか、ECS Execセッション内でのファイル転送かは実装フェーズで確定する。
5. **メンテナンス時間帯の運用ルール**: 全データインポート実行のための対象サービス停止（2.3節#10）について、告知方法・実施可能な曜日時間帯等の具体的な運用ルールを、実装フェーズ着手前に定める必要がある。
