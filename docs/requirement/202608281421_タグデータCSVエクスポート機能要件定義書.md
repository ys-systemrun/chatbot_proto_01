# タグデータCSVエクスポート機能 要件定義書

- 文書番号: REQ-202608281421
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `knowledge_mcp`（新規MCPツール）, `web_backend`（新規エクスポートAPI）, `front_dev`（タグ管理画面拡張）
- 変更なしのコンポーネント: `tag`/`tag_alias`テーブルのスキーマ、既存の`list_tags`/`create_tag`/`rename_tag`/`set_tag_description`/`move_tag`/`delete_tag`/`import_tag_batch`、既存の全データエクスポート機能（`/api/export`）、QA一括インポート（`import_qa_batch`）、`tag_selector_mcp`、`agent_invitro`
- 参照資料: `docs/requirement/202608261600_タグデータ一括インポート機能要件定義書.md`、`docs/requirement/202608271750_言い換え質問文（question_altered）管理機能要件定義書.md`、`docs/requirement/202608241530_全データエクスポート機能要件定義書.md`
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照

## 1. 目的

`front_dev`のタグ階層ページ（`TagTreePage`）に、言い換え質問文一覧ページ（`QuestionAlteredListPage`、ADR-0064）と同様、既存のタグ一括インポート機能（`import_tag_batch`、ADR-0061）へそのまま再インポートできる形式で、タグデータ（`tag`テーブル）をCSVエクスポートする機能を追加する。

## 2. 背景・参照資料

- タグ単体の一括インポート機能（ADR-0061）は既に実装済みで、CSVの`name`/`parent_name`/`description`の3列を対象に、タグ名によるupsertで階層構造を含めて登録・更新できる。同機能の要件定義書（202608261600）は、Open Issue #3として「既存のタグ一覧（`list_tags`）をCSV形式でエクスポートする機能が別途必要かどうかは、本書のスコープ外とし、必要になった場合に別途要件化する」としており、本書はこのOpen Issueに対応するものである。
- 言い換え質問文管理機能（ADR-0064）は、一覧ページに対する「そのまま再インポートできる形式」のCSVエクスポート機能を既に実装しており、（1）列構成をインポートと一致させる、（2）既存の全データエクスポート（ADR-0046/0047）とは独立した別機能として、Knowledge MCP経由の同一経路で実装する、という設計パターンを確立している。本書はこのパターンをタグデータに踏襲する。
- 既存の全データエクスポート機能（ADR-0046/0047）は、既に`tag.csv`（列: `id`/`name`/`parent_tag_id`/`description`）を8テーブル分のZIPの一部として出力しているが、`parent_tag_id`は数値IDであり、タグ一括インポート（`parent_name`による名前解決）へそのまま再投入できる形式ではない。本書が新設するCSVエクスポートは、この既存機能とは別に、タグ単体を「そのまま再インポートできる形式」で出力する機能として独立に追加する。
- タグの一覧取得ツール（`list_tags`）は、ページングや`is_primary`等の絞り込みが必要だった言い換え質問文一覧（`list_question_altered`）とは異なり、元々全タグを一度にツリー構造で返す設計になっている（`knowledge_mcp/src/knowledge_mcp/repository/tag_repository.py`）。
- 本書は、発注者との確認を経て、次の方針を確認済みである。
  1. エイリアス（`tag_alias`、同義語）: エクスポート対象に含めない。既存のタグ一括インポート（ADR-0061）が`name`/`parent_name`/`description`の3列のみでエイリアスに対応していないため、含めると「そのまま再インポートしても情報が失われない」という往復整合性が崩れる。エイリアスは引き続き既存の個別操作（`add_tag_alias`/`remove_tag_alias`、`TagTreePage`の個別編集）でのみ管理する。
  2. 実装方式: Knowledge MCPに新規ツール（`export_tags`、仮称）を追加する。既存`list_tags`の結果を`web_backend`側でフラット化する案（新規ツールを追加しない案）も検討したが、`web_backend`を「MCPツール呼び出し＋レスポンス変換のみ」の薄いBFFに留める既存の役割分担（ADR-0013）を優先し、ツリー→フラット変換ロジックはKnowledge MCP側に置く。
  3. 対象範囲: 全タグ（階層全体）を常に対象とする。現状の`TagTreePage`に絞り込みUIがなく、`list_tags`自体も常に全件を返す設計のため、部分エクスポート（特定の親タグ配下のみ等）は本書のMVPでは提供しない。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| タグ一括エクスポート | 本書が新設する機能。タグ階層ページ（`TagTreePage`）から、全タグをCSV形式で一括ダウンロードする操作。既存のタグ一括インポート（ADR-0061）とは対になる、独立した機能 |
| upsert（アップサート） | タグ名（`name`）の一致を基準に、既存タグがあれば更新、なければ新規作成する処理方式（既存のタグ一括インポートに適用済み）。エクスポートしたCSVをそのまま再インポートした場合、全行が既存タグ名と一致するため、内容が変化しない更新（no-op）として処理される |
| フラット化 | `list_tags`が返す親子関係を持つツリー構造（`TagNode`、`children`を含む）を、CSVの1行＝1タグに対応する平坦な配列（`parent_name`で親を表現する形式）に変換する処理 |
| ルート直下 | `parent_tag_id`が`NULL`のタグ。エクスポートCSVでは`parent_name`が空欄として出力される |

## 4. スコープ

### 4.1 対象範囲（MVP）

- `front_dev`のタグ階層ページ（`TagTreePage`）に「CSVエクスポート」ボタンを追加する（既存のCSV一括インポートUIの近くに配置）。
- ボタンクリックで`GET /api/tags/export`を呼び出し、レスポンスのBlobをブラウザのファイル保存ダイアログにつなげる（既存の`downloadExport`・`downloadQuestionAlteredExport`と同様のダウンロード処理パターン）。エクスポート中はボタンをローディング状態（「エクスポート中...」）にする（`QuestionAlteredListPage`と同様）。
- `knowledge_mcp`に、全タグをフラットな配列として返す新規MCPツール`export_tags`を追加する。既存`TagRepository.list_tags()`が構築するツリーをそのまま走査し、各ノードの親ノード名を`parent_name`として持ち回ってフラット化する（新たなSQLクエリ・新たな循環参照チェック等の業務ロジック追加は不要な薄いラッパーとする）。
- `web_backend`に、`export_tags`ツールを呼び出し、結果をCSV（`name`/`parent_name`/`description`の3列、既存のタグ一括インポートと完全一致）として組み立てる新規エンドポイント（`GET /api/tags/export`）を追加する。
- 対象は常に全タグ（階層全体）とし、絞り込み結果に応じた部分エクスポートは提供しない。

### 4.2 対象外（将来検討・別スコープ）

- **エイリアス（`tag_alias`）のエクスポート**: タグ一括インポートがエイリアスに対応していないため対象外とする。将来、エイリアスを含めた往復（インポート側の対応拡張を含む）が必要になった場合は、別途要件定義・ADRが必要になる。
- **絞り込み結果に応じた部分エクスポート**（特定の親タグ配下のみ等）: 現状の`TagTreePage`に絞り込みUIがなく、運用ニーズも明確でないため対象外とする。
- **既存の全データエクスポート機能（ADR-0046/0047）の変更**: `tag.csv`（`id`/`name`/`parent_tag_id`/`description`、数値ID）を含む既存の8テーブルZIP出力は変更しない。本書のCSVエクスポートとは対象範囲・列構成・実装経路が異なる独立した機能として併存させる。
- **タグ一括インポート（`import_tag_batch`、ADR-0061）・既存の個別CRUD（`create_tag`/`rename_tag`/`move_tag`/`delete_tag`）の変更**: いずれも変更を加えない。
- **アクセス制御の強化**: 既存の管理画面群と同様、ネットワークレベルの制限（社内IPアドレス限定, ADR-0041）のみとし、追加のログイン認証は設けない。

## 5. 全体アーキテクチャ

### 5.1 システム構成（本フェーズ）

```
front_dev（TagTreePage: CSVエクスポートボタン追加）
        │  GET /api/tags/export
        ▼
web_backend（tag_controller.py 拡張: CSV組み立てのみ）
        │  MCPツール呼び出し（既存の読み取り経路、ADR-0013の原則をエクスポートにも適用、ADR-0064踏襲）
        ▼
knowledge_mcp（新規ツール: export_tags）
        │  既存 TagRepository.list_tags() のツリー構築ロジックを再利用し、フラット化
        ▼
chatbot データベース（tag テーブル、読み取りのみ）
```

- `tag_selector_mcp`・`agent_invitro`・既存の全データエクスポート（`web_backend/src/export/`、ADR-0046/0047の読み取り専用ロール経路）・タグ一括インポート（`import_tag_batch`）・既存の個別CRUD（`create_tag`等）には変更を加えない。
- タグ一覧・CSVインポート・CSVエクスポートのすべてを、`web_backend → knowledge_mcp`経由の同一経路で実装する（読み取り・書き込みいずれもKnowledge MCP経由とするADR-0013の原則を、エクスポートにも適用する）。

### 5.2 コンポーネント一覧と責務（追加・変更分）

| コンポーネント | 変更内容 |
|---|---|
| `knowledge_mcp`（新規ツール） | 全タグをフラットな配列（`name`/`parent_name`/`description`）で返す新規MCPツール`export_tags`の追加 |
| `web_backend`（新規API） | `GET /api/tags/export`の追加。既存`tag_controller.py`と同様、MCPツール呼び出し＋CSV組み立てのみを行うBFF |
| `front_dev`（既存画面拡張） | タグ階層ページ（`TagTreePage`）に「CSVエクスポート」ボタンを追加 |

## 6. 機能要件

### 6.1 front_dev: タグ階層ページへのCSVエクスポート機能追加

- `TagTreePage`に「CSVエクスポート」ボタンを追加する。既存のCSV一括インポート（`<details>`要素）の付近に配置する。
- クリックで`GET /api/tags/export`を呼び出し、レスポンスのBlobをブラウザのファイル保存ダイアログにつなげる（既存`ExportPage`・`QuestionAlteredListPage`のダウンロード処理と同様のパターン）。
- エクスポート中はボタンを無効化し、「エクスポート中...」を表示する（`QuestionAlteredListPage`の`onExport`と同様）。
- 絞り込み条件は存在しないため（`TagTreePage`は元々全タグを表示する画面）、常に全タグを対象とする。

### 6.2 web_backend: 新規APIエンドポイント

| メソッド・パス | 説明 |
|---|---|
| `GET /api/tags/export` | 全タグをCSVでダウンロード（`Content-Disposition: attachment`）。列は`name`/`parent_name`/`description`の3列 |

`export_tags`ツールを呼び出し、結果をCSVに変換するのみとし、`chatbot`データベースへの直接アクセスは行わない（既存`tag_controller.py`・`question_altered_controller.py`と同様の役割分担）。

### 6.3 Knowledge MCP: 新規ツール `export_tags`

| ツール名 | 説明 |
|---|---|
| `export_tags` | 引数なし。全タグ（親子関係を含む全件）を、`id`/`name`/`parent_name`/`description`のフラットな配列として返す（`web_backend`側のCSV組み立ては`name`/`parent_name`/`description`の3列のみを使用し、`id`は参照しない）。実装は、既存`TagRepository.list_tags()`が構築するツリー（ルートから）をそのまま深さ優先で走査し、各ノードについて親ノードの`name`を`parent_name`として持ち回るだけであり、新たなSQL・新たな業務ロジックの追加は不要な薄いラッパーとする |

### 6.4 CSVフォーマット（案）

| 列名 | 必須/任意 | 説明 |
|---|---|---|
| `name` | 必須 | タグ名。既存のタグ一括インポート（ADR-0061）のupsertキーと同一 |
| `parent_name` | 任意 | 親タグ名。ルート直下のタグは空欄で出力される |
| `description` | 任意 | タグの説明。未設定のタグは空欄で出力される |

既存のタグ一括インポート（ADR-0061）の列構成（`name`/`parent_name`/`description`）と完全に一致させる。`id`列は出力しない。タグのupsertキーは`name`であり（`question_altered`の`id`列とは異なる）、`id`列を出力すると「idも一致条件に使われるのか」という誤解を招く恐れがあるため、既存インポートUIが案内する列構成とそのまま揃える。

エクスポートしたCSVをそのまま再度タグ一括インポートへアップロードした場合、全行の`name`が既存タグと一致するため、内容が変化しない更新（no-op）として処理される（往復整合性）。

### 6.5 出力順序

親タグが子タグより先に出現する階層順（`export_tags`が既存ツリーを深さ優先で走査する順序）で出力する。タグ一括インポートの`parent_name`解決は行の並び順に依存しない（ADR-0061の複数パス反復解決）ため、出力順序は再インポートの正しさには影響しないが、CSVを人が確認する際の可読性のために階層順とする。

## 7. データ要件

### 7.1 対象テーブル（再掲、変更なし）

| テーブル | 列 | 本機能での扱い |
|---|---|---|
| `tag` | `id`, `name`, `parent_tag_id`, `description` | 全件読み取り対象。スキーマ変更なし |
| `tag_alias` | `id`, `tag_id`, `alias` | 対象外（4.2節） |

### 7.2 API入出力例（`GET /api/tags/export`のCSV内容、イメージ）

```csv
name,parent_name,description
サポート,,サポート関連の最上位タグ
ログイン,サポート,ログイン・認証に関する問い合わせ
パスワード再設定,ログイン,パスワード再設定手順に関する問い合わせ
```

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 対象データ量 | 全タグを一度に返す（`list_tags`と同様、ページングなし）。タグ数が既存の想定規模を大きく超える場合の性能は、実装フェーズで確認する |
| ファイルサイズ・件数 | CSV出力の上限件数・ファイルサイズは、既存のタグ一括インポートの想定規模を目安とし、詳細は実装フェーズで確定する（12章 Open Issue #2） |
| アクセス制御 | 既存の管理画面群と同様、ネットワークレベルの制限（社内IPアドレス限定, ADR-0041）のみとし、追加のログイン認証は設けない |
| ログ | 既存の管理系操作ログ（`log_admin_operation`）と同様の方式で、CSVエクスポートの実行を記録する |
| データ整合性 | 読み取りのみの機能であり、業務バリデーションは発生しない。`export_tags`は既存`list_tags`と同じ最新のDB状態を都度参照する（キャッシュしない、既存`TagRepository`の方針を踏襲） |

## 9. インフラ・実行環境要件

- 追加のインフラ変更は想定しない。既存の`knowledge_mcp`・`web_backend`・`front_dev`のコンテナ構成（ローカルdocker-compose・AWS ECS Fargate）をそのまま利用する。
- 新規の環境変数追加は想定しない。

## 10. 既存システムとの関係・影響範囲

- `tag`/`tag_alias`のスキーマは変更しない。
- 既存の`list_tags`/`create_tag`/`rename_tag`/`set_tag_description`/`move_tag`/`delete_tag`/`import_tag_batch`（ADR-0006/0061）の実装・シグネチャには変更を加えない。
- 既存の全データエクスポート機能（`/api/export`、ADR-0046/0047）には変更を加えず、独立した別機能として併存させる。`tag.csv`は両機能で列構成が異なる（全データエクスポート: `id`/`name`/`parent_tag_id`/`description`の数値ID形式、本機能: `name`/`parent_name`/`description`の名前解決形式）ため、画面上の説明・ファイル名で混同を避ける（詳細は実装フェーズで確定、12章 Open Issue #5）。
- QA一括インポート（`import_qa_batch`、ADR-0053）・言い換え質問文管理機能（ADR-0064）には影響しない。
- `tag_selector_mcp`・`agent_invitro`には影響しない。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] タグ階層ページから「CSVエクスポート」を実行し、全タグ（階層全体）がCSVとしてダウンロードできる。
- [ ] エクスポートされたCSVの列が`name`/`parent_name`/`description`であり、既存のタグ一括インポート機能へそのままアップロードできる。
- [ ] ダウンロードしたCSVを再度インポートしても、タグの内容（親子関係・説明）が変化しない（往復整合性）。
- [ ] エイリアス（`tag_alias`）はエクスポート対象に含まれない。
- [ ] 既存のタグ個別CRUD、タグ一括インポート、既存の全データエクスポート、`tag_selector_mcp`の動作に影響がないことを確認する。

## 12. Open Issues（要追加確認事項）

1. **CSVフォーマットの最終確定**: 6.4節に示した列構成（`name`/`parent_name`/`description`）は現時点では案であり、区切り文字・文字コード（UTF-8 BOM付き可、既存のタグ一括インポートに合わせる想定）を含め詳細設計フェーズで最終確定する。
2. **ファイルサイズ・件数上限**: 8章に記載の通り、具体的な上限値（タグ件数）は実装フェーズで確定する。現状のタグ数を踏まえ、性能上の懸念が小さいことを実装フェーズで確認する。
3. **絞り込み結果に応じた部分エクスポート**: 4.2節の通り本書のMVPでは全タグのみを対象とするが、運用開始後にタグ数が増え、特定の親タグ配下のみをエクスポートしたいという要望が出た場合、別途要件化する。
4. **エイリアスのエクスポート**: 4.2節の通り対象外とするが、将来的にエイリアスを含めた往復運用（タグ一括インポート側の対応拡張を含む）が必要になった場合、別途要件定義・ADRが必要になる。
5. **エクスポートファイル名・画面上の説明文の確定**: 10章に記載の、既存の全データエクスポートとの混同防止のための表示・命名の詳細は、実装フェーズで確定する（例: `tags_<timestamp>.csv`のようなファイル名とする案、詳細設計フェーズで確定）。

| ADR-0046 | chatbotデータベースのエクスポート専用読み取り経路の新設 | 既存の全データエクスポートが用いる読み取り専用ロール。本書のCSVエクスポートはこの経路を使わず、Knowledge MCP経由の別経路とする |
| ADR-0047 | 全データエクスポート機能のダンプ生成方式・配信方式 | 既存の`tag.csv`列構成（`id`/`name`/`parent_tag_id`/`description`）。本書のCSVエクスポートはこれとは異なる列構成（`name`/`parent_name`/`description`）を採用し、対象・実装経路が異なる独立機能とする |
| ADR-0061 | タグ単体の一括インポート機能の実装方式 | 本書がエクスポート列構成を完全一致させる対象。タグ名によるupsert・親タグ名による階層指定 |
| ADR-0064 | 言い換え質問文（question_altered）管理機能の実装方式 | 本書が踏襲する「一覧ページに、既存インポートと同一列構成の、再インポート可能なCSVエクスポートを追加する」という設計パターンの先例 |
