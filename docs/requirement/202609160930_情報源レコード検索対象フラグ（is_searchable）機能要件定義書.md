# 情報源レコード 検索対象フラグ（is_searchable）機能 要件定義書

- 文書番号: REQ-202609160930
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `db_hiroba_qa_init`（マイグレーション）、`knowledge_mcp`（検索Repository・管理ツール）、`web_backend`（管理API・全データエクスポート定義）、`front_dev`（管理UI）
- 変更なしのコンポーネント: `agent_invitro`、`tag_selector_mcp`、`terraform`、`conversation`データベースのスキーマ
- 参照資料: `knowledge_mcp/src/knowledge_mcp/repository/qa_repository.py`、`同/troubleshooting_repository.py`、`同/qa_management_repository.py`、`同/question_altered_repository.py`、`同/troubleshooting_management_repository.py`、`knowledge_mcp/src/knowledge_mcp/mcp/tools.py`、`web_backend/src/main/controllers/{qa,question_altered,troubleshooting}_controller.py`、`web_backend/src/export/tables.py`、`front_dev/src/feature/{qa_admin,question_altered,troubleshooting_admin}/`、`db_hiroba_qa_init/migrations/`
- 前提の決定事項: 本書末尾「12. 関連ADR一覧」参照

## 1. 目的

QA（`hiroba_qa_original`）・言い換え質問文（`hiroba_question_altered`）・トラブルシューティング記事（`troubleshooting_article`）の各レコードに、**Knowledge MCP の `search_knowledge` による検索でヒット対象とするか否か**を表す `is_searchable` 列（既定値 `true`）を新設する。あわせて、管理UIの一覧ページ・編集ページからトグルスイッチで当該フラグを切り替えられるようにする。これにより、

1. 内容が古くなった／誤りが判明した／公開前である等の理由で**チャットの回答根拠に使わせたくないレコードを、削除せずに検索対象から外せる**ようにする。現状はレコード削除（ADR-0067）以外に除外手段がなく、削除は復元不能かつタグ付け・言い換えも失われる。
2. 除外・復帰の操作を運用者が管理画面上で即座に行えるようにし、DBへの直接SQL実行（ADR-0083）に頼らずに済むようにする。
3. 言い換え質問文の単位でも除外できるようにし、「特定の言い換えだけがノイズとして過剰にヒットする」場合に、QA本体を残したままその言い換えのみを無効化できるようにする。

## 2. 背景・現状の課題

### 2.1 現状の実装

- `search_knowledge` は `SearchService` が複数 Repository の結果を集約する構成であり（ADR-0004・ADR-0078）、現在は `QARepository`（QA、`hiroba_question_altered` 単位のベクトル近傍）と `TroubleshootingRepository`（トラブルシューティング記事、記事単位の単一embedding）の2つが登録されている。
- いずれの Repository も、候補プール（`max(top_k * 10, 50)` 件、または `SEARCH_CANDIDATE_POOL_SIZE`）をベクトル距離順に取得し、タグ構成類似度（ADR-0058・ADR-0059）と重み付き合成して `top_k` 件を返す。**レコードを検索対象から外す条件は現在どこにも存在しない**（`troubleshooting_article.embedding IS NOT NULL` の除外のみ）。
- 管理UI（`QaListPage` / `QuestionAlteredListPage` / `TroubleshootingListPage`、ADR-0064・ADR-0079）からは、レコードの登録・編集・削除は可能だが、「登録したまま検索から外す」操作は提供していない。

### 2.2 課題

- 誤答の原因になっているQA・言い換え・記事を見つけても、運用者が取れる手段は「内容を直す」か「削除する」かの二択しかない。**内容の是正方針が決まるまで一時的に検索から外す**という、実運用で最も多い中間的な対処ができない。
- 削除（ADR-0067）は `hiroba_qa_tag` ・ `hiroba_question_altered` をカスケード削除するため、復帰時にタグ付け・言い換えを再作成する必要があり、事実上不可逆である。
- 検証機能（ADR-0048〜0050）で「このQAはヒットさせたくない」と判断しても、その判断をデータに反映する場所がない。

### 2.3 既存基盤

- スキーマ変更は `db_hiroba_qa_init` の yoyo-migrations（ADR-0017）で一元管理されており、`0009` まで適用済み。列追加は `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` による冪等なSQLステップで追加できる（`0004` `0005` が先行事例）。
- 管理UIからの chatbot データベースへの書き込みは、すべて Knowledge MCP のツール経由に統一されている（ADR-0013）。`web_backend` は薄いBFF層であり、`front_dev` は `react` / `react-router-dom` のみに依存を絞っている（ADR-0015）。
- 一覧ページの検索条件はURLクエリと同期する方式が確立している（ADR-0068、QA一覧・言い換え一覧）。
- 全データエクスポート／全消去インポート（ADR-0047・ADR-0066）は `web_backend/src/export/tables.py` の13テーブル定義を唯一の対象集合とし、列定義もここに集約されている。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| `is_searchable` | 本書で新設する真偽値の列。`true` のとき当該レコードは `search_knowledge` の検索結果に含まれうる。`false` のとき検索結果には一切含まれない。既定値は `true` |
| 検索対象フラグ | `is_searchable` 列の日本語呼称。管理UIの表示ラベルもこれに準じる |
| 実効検索可否 | 親子関係（QAと言い換え行）のAND合成後に、実際に検索でヒットしうるかどうかの状態。6.2節で定義する |
| 主質問文行 | `hiroba_question_altered` のうち `is_primary = true` の行。`create_qa` / `update_qa` が `question_text` から生成・更新する（ADR-0014・ADR-0064） |
| 言い換え行 | `hiroba_question_altered` のうち `is_primary = false` の行。言い換え質問文管理機能（ADR-0064）の操作対象 |
| トグルスイッチ | 一覧ページの各行に配置する、押下で即座に検索対象フラグを切り替えるUI部品 |

## 4. スコープ

### 4.1 対象範囲（MVP）

- **3テーブルへの `is_searchable BOOLEAN NOT NULL DEFAULT true` の追加**: `hiroba_qa_original`（QA）、`hiroba_question_altered`（主質問文行・言い換え行の両方）、`troubleshooting_article`（トラブルシューティング記事）。
- **`search_knowledge` における除外**: `QARepository` ・ `TroubleshootingRepository` の候補取得SQLに `is_searchable` 条件を追加し、`false` のレコードを検索結果から完全に除外する（6.2節）。
- **親子のAND合成**: QAの `is_searchable = false` は、その配下の全言い換え行（主質問文行を含む）を検索対象外にする（発注者確認済み、13章参照）。
- **Knowledge MCP 管理ツールの拡張**: 一覧・詳細の出力への `is_searchable` 追加、一覧の絞り込み引数追加、登録・更新ツールでの設定・変更（6.4節）。
- **`web_backend` 管理APIの拡張**: 一覧の絞り込みクエリパラメータ、レスポンスへの項目追加、部分更新リクエストでの `is_searchable` 受理（6.5節）。
- **管理UIのトグルスイッチ**: QA一覧・言い換え質問文一覧・トラブルシューティング記事一覧の各行にトグルを配置し、**押下で即時保存**する。あわせて各編集ページにもチェックボックスを配置し、フォーム保存時に反映する（発注者確認済み、13章参照。6.6節）。
- **一覧ページの絞り込み**: 「すべて／検索可のみ／検索不可のみ」の3値セレクトを検索条件に追加し、URLクエリと同期する（発注者確認済み、13章参照。6.6.4節）。
- **CSV一括インポート／エクスポートへの列追加**: QA一括インポート・言い換え質問文の一括インポート／エクスポートに `is_searchable` 列を追加する。列・値が省略された場合は「新規は `true`、既存は変更なし」とし、既存CSVがそのまま通る後方互換を保つ（発注者確認済み、13章参照。6.7節）。
- **全データエクスポート／全消去インポート定義の更新**: `export/tables.py` の対象3テーブルの `columns` ・ `_create_ddl` に `is_searchable` を追加する（6.8節）。

### 4.2 対象外（将来検討・別スコープ）

- **タグ・タグフォルダ・タグエイリアスへの `is_searchable` 付与**: タグは検索対象のレコードではなく分類メタデータであるため対象外。タグCSV（ADR-0065・ADR-0081）の列構成も変更しない。
- **主質問文行（`is_primary = true`）の個別切り替えUI**: 主質問文行はQA本体の質問文そのものであり、QA単位のフラグで制御する。言い換え質問文管理機能の対象が言い換え行のみである既存方針（ADR-0064）を踏襲し、主質問文行の `is_searchable` は常に `true` のままとする（列自体はテーブル共通で存在する。11章 Open Issue 参照）。
- **公開期間・予約による自動切り替え（期間指定での自動無効化・自動復帰）**: 本書は運用者の手動切り替えのみを対象とする。
- **切り替え履歴の保持・監査ログのDB化**: 既存の管理操作ログ（`log_admin_operation`、標準出力へのアプリケーションログ）への出力に留め、履歴テーブルの新設は行わない。
- **検索対象外レコードへの別扱い（低スコアで含める、注記付きで返す等）**: 本書では完全除外のみとする。
- **チャットUI・エンドユーザー向け画面への影響**: エンドユーザーからは除外されたレコードが単に存在しないものとして見えるだけであり、UI上の追加表示は行わない。
- **`agent_invitro` ・ `tag_selector_mcp` の変更**: いずれも `search_knowledge` の呼び出し側・タグ選定側であり、本書による変更はない（9章）。

## 6. 機能要件

### 6.1 DBスキーマ（マイグレーション 0010）

- 次の3テーブルへ列を追加する。いずれも `BOOLEAN NOT NULL DEFAULT true`。

| テーブル | 列 | 意味 |
|---|---|---|
| `hiroba_qa_original` | `is_searchable` | QA全体（配下の主質問文行・言い換え行を含む）を検索対象とするか |
| `hiroba_question_altered` | `is_searchable` | 当該の質問文（主質問文行・言い換え行）をベクトル近傍の候補とするか |
| `troubleshooting_article` | `is_searchable` | 当該記事を検索対象とするか |

- 既存行にはすべて `true` が入る（`DEFAULT` による）。**本マイグレーション適用直後の検索挙動は適用前と完全に同一**である。
- マイグレーションは `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` による冪等なSQLステップとし（`0004` `0005` と同形式）、再実行しても無害とする。ダウングレードステップ（列の削除）は用意しない（既存マイグレーションの方針を踏襲）。
- **索引は追加しない**。理由: 値の大半が `true` であり選択率が低いこと、検索側の候補取得は既にベクトル距離順の全走査であること（ベクトル索引を張っていない）、管理画面の一覧は `limit`/`offset` ページングであることによる。データ量が増えた段階で必要になれば別途検討する（11章 Open Issue）。

### 6.2 検索での除外（`search_knowledge`）

#### 6.2.1 QA（`QARepository`）

- 候補取得SQLの `WHERE` 句に次の条件を追加する。

```sql
hiroba_question_altered.is_searchable
AND COALESCE(hiroba_qa_original.is_searchable, true)
```

- 第2項を `COALESCE(..., true)` とするのは、現行SQLが `hiroba_qa_original` を `LEFT JOIN` しており、親QAが存在しない孤児行（`qa_id` が不整合な行）が理論上ありうるためである。従来これらは検索結果に含まれていたため、**孤児行の扱いを本変更で変えない**。
- 上記条件は**候補プールの `LIMIT` より前に適用する**。すなわち、検索対象外のレコードが候補プールの枠を消費しない（除外した分だけ他の候補が繰り上がる）。
- **実効検索可否の定義**: 言い換え行（および主質問文行）がベクトル近傍の候補となるのは、`当該行の is_searchable = true` かつ `親QAの is_searchable = true` の場合に限る（AND合成）。QAの `is_searchable = false` は配下の全行を一括で無効化する親スイッチとして働く。
- カテゴリ絞り込み（`category`）・タグ構成類似度（ADR-0058・ADR-0059）・`min_score` ・ `top_k` の挙動は変更しない。

#### 6.2.2 トラブルシューティング記事（`TroubleshootingRepository`）

- 候補取得SQLの既存 `WHERE troubleshooting_article.embedding IS NOT NULL` に `AND troubleshooting_article.is_searchable` を追加する。適用位置は同様に候補プールの `LIMIT` より前とする。

#### 6.2.3 影響範囲

- `search_knowledge` の**入出力スキーマは変更しない**。検索側に「検索対象外も含める」といった引数は追加しない（4.2節）。
- したがって `search_knowledge` を呼び出すすべての経路（`agent_invitro` の `/ask-pipeline` ・ `/ask-agentic`、検証機能の実行パイプライン（ADR-0049）、`web_backend` のデバッグ用スクリプト）は、**コード変更なしで一律に除外が効く**。
- `/ask-agentic` のAgenticループ（ADR-0088）は、検索結果が不十分と判定された場合にクエリを再定式化して再検索するが、除外されたレコードは再検索でも返らない。結果として十分な情報源が見つからない場合は既存の縮退挙動（回答不能・逆質問）に従う。

### 6.3 管理操作の意味論

- QAの `is_searchable` を `false` にしても、配下の言い換え行の `is_searchable` は書き換えない（値を保持する）。QAを `true` に戻したとき、各言い換え行は**切り替え前の自身の値のまま復帰する**。
- レコードの新規作成時の既定は `true`（`create_qa` ・ `create_question_altered` ともに引数省略時 `true`）。
- `update_qa` で `question_text` を変更した場合の主質問文行のembedding再計算（ADR-0014）、`update_question_altered` で `text` を変更した場合の再計算、`update_troubleshooting_article` の埋め込み元フィールド変更時の再計算は、いずれも従来どおり。**`is_searchable` のみの更新では embedding を再計算しない**（7章 非機能要件）。
- QA削除（ADR-0067）の挙動は変更しない。検索対象外であるか否かにかかわらず削除できる。

### 6.4 Knowledge MCP ツールの変更

| ツール | 変更内容 |
|---|---|
| `list_qa` | 引数に `is_searchable: Optional[bool]`（`None`＝すべて、`true`＝検索可のみ、`false`＝検索不可のみ）を追加。出力 `QaSummary` に `is_searchable` を追加 |
| `get_qa` | 出力 `QaDetail` に `is_searchable` を追加 |
| `create_qa` | 引数に `is_searchable: bool = True` を追加 |

### 6.6 管理UI（front_dev）

#### 6.6.1 一覧ページ共通（QA一覧・言い換え質問文一覧・トラブルシューティング記事一覧）

- 一覧テーブルに**「検索対象」列**を追加する。各行にトグルスイッチ（`<input type="checkbox">` にCSSでスイッチ外観を与えたもの。新規UIライブラリは導入しない、ADR-0015）を配置する。
- トグル押下で**即時保存**する。処理順序は次のとおり（楽観的更新）:
  1. クライアント側の表示を即座に切り替え、当該行のトグルを操作不可（`disabled`）にする。
  2. 更新APIを呼ぶ。
  3. 成功: レスポンスの値で行の状態を確定し、トグルを操作可能に戻す。
  4. 失敗: 表示を元の値へ戻し（ロールバック）、ページ上部の既存エラー表示領域にエラーメッセージを出し、トグルを操作可能に戻す。
- 連続操作への配慮として、1行あたりの更新要求は同時に1つまでとする（処理中の行は再操作不可）。
- 検索対象外（実効検索可否が `false`）の行は、行全体を淡色表示するなど視覚的に区別する。
- 一覧の再取得（ページ送り・検索条件変更）は従来どおり。トグル操作では一覧全体の再取得を行わない。

#### 6.6.2 言い換え質問文一覧における親QAの表示

- 行自身の `is_searchable` が `true` であっても親QAの `is_searchable` が `false` の場合、その行は実際には検索されない。この状態を利用者が誤解しないよう、**「親QAが検索対象外」である旨のバッジ・注記を当該行に表示する**。
- 行のトグル自体は親QAの状態にかかわらず操作可能とする（自身の値は独立して保持されるため、6.3節）。

#### 6.6.3 編集ページ

- QA編集（`QaFormPage`）・言い換え質問文編集（`QuestionAlteredFormPage`）・トラブルシューティング記事編集（`TroubleshootingFormPage`）に「検索対象」チェックボックスを追加し、**フォームの保存ボタン押下時に他の項目とまとめて送信**する（編集ページでは即時保存しない）。
- QA新規作成・言い換え質問文新規作成の初期値は `true`（チェック済み）とする。

#### 6.6.4 絞り込み

- 各一覧ページの検索条件に「検索対象」セレクト（**すべて**／検索可のみ／検索不可のみ、既定＝すべて）を追加する。
- QA一覧・言い換え質問文一覧では、選択値をURLクエリ `is_searchable=true|false` として同期する（既定「すべて」の場合はURLから省略する。ADR-0068の方針を踏襲）。トラブルシューティング記事一覧は現状URL同期を実装していないため、本書でも同ページのURL同期は行わない（画面内の状態のみ）。
- 言い換え質問文一覧の絞り込みは**行自身の値**を対象とする（親QAの状態は絞り込み条件に含めない、6.4節）。

### 6.7 CSV一括インポート／エクスポート

- 対象は QA一括インポート（`/api/qa/import`）と言い換え質問文の一括インポート／エクスポート（`/api/hiroba_question_altered/import` ・ `/export`）とする。タグCSV（ADR-0065・ADR-0081）は対象外（4.2節）。

| CSV | 変更後の列 |
|---|---|
| QA一括インポート | `uuid`, `title`, `question_text`, `answer_text`, `category_id`, `tags`, **`is_searchable`** |
| 言い換え質問文 インポート | `id`, `qa_id`, `text`, `is_primary`, **`is_searchable`** |
| 言い換え質問文 エクスポート | `id`, `qa_id`, `text`, `is_primary`, **`is_searchable`** |

- **値の解釈**: `true` / `false`（大文字小文字を区別しない）および `1` / `0` を受理する。これら以外の非空値は当該行のエラーとし、行単位でスキップする（既存のエラー許容方式を踏襲）。
- **省略時の解釈（後方互換）**: 列自体が存在しない場合、または値が空欄の場合は、**新規行は `true`、既存行は変更なし**とする。これにより、本機能追加前に出力した既存CSVをそのまま再インポートしても、現在の設定値が意図せず上書きされない。
- エクスポートは実際の値を `true` / `false` の文字列で出力する。

### 6.8 全データエクスポート／全消去インポート

- `web_backend/src/export/tables.py` の次の3テーブルの `columns` 末尾および `_create_ddl` に `is_searchable BOOLEAN NOT NULL DEFAULT true` を追加する: `hiroba_qa_original` ・ `hiroba_question_altered` ・ `troubleshooting_article`。
- SQLダンプの `INSERT` は列名を明示する形式であるため、**本機能追加前に取得した既存ダンプは、列の `DEFAULT true` によりそのまま投入できる**（投入後、全レコードが検索対象となる）。
- 全消去インポート（ADR-0066）の事前自動バックアップは `information_schema` から列を動的に取得するため、追加の変更を要しない。
- `db_hiroba_qa_init` のシード処理・トラブルシューティング記事インポート処理は、いずれも列名を明示した `INSERT` であるため変更不要であり、投入されたレコードは既定値 `true` となる。

## 7. 非機能要件

| 分類 | 要件 |
|---|---|
| 後方互換性 | マイグレーション適用直後は全レコードが `is_searchable = true` であり、検索結果・スコアは適用前と完全に一致する。既存CSV・既存SQLダンプはそのまま利用できる（6.7節・6.8節） |
| 検索性能 | 追加するのは真偽値の単純な述語であり、候補プール取得の計算量に実質的な変化はない。索引は追加しない（6.1節） |
| 埋め込み再計算の抑止 | `is_searchable` のみの更新では embedding を再計算しない。とくに一覧のトグル操作が Bedrock（ADR-0031）の埋め込み呼び出しを誘発しないこと |
| 即時性 | トグル操作による変更は、次回以降の `search_knowledge` 呼び出しに即座に反映される（キャッシュを介さずDBを都度参照するため）。`tag_selector_mcp` のタグ知識ベースキャッシュ（ADR-0011）は本フラグと無関係であり、影響を受けない |
| 操作の可逆性 | 切り替えは何度でも往復可能であり、レコードの内容・タグ付け・言い換えを一切失わない |
| アクセス制御 | 変更なし。既存の管理画面群と同様、ネットワークレベルの制限（社内IPアドレス限定、ADR-0041）のみとする |
| ログ | 切り替え操作は既存の管理操作ログに記録される（6.5節）。専用の履歴テーブルは設けない（4.2節） |
| 排他制御 | 楽観的更新のロールバックのみとし、レコード単位のロック・更新競合検出は行わない（管理者が少数である前提。既存の編集機能と同一方針） |

## 8. インフラ・実行環境要件

- 追加のインフラ変更は想定しない。新規の環境変数・依存パッケージの追加もない。
- 適用手順は既存のマイグレーション実行手順に従う。スキーマ変更のみを先行適用する場合は、マイグレーション専用実行モード（ADR-0075）を利用できる。
- デプロイ順序は **DBマイグレーション（0010）→ `knowledge_mcp` → `web_backend` → `front_dev`** とする。列が存在しない状態で新しい `knowledge_mcp` が動くとSQLエラーとなるため、マイグレーションを先行させる必要がある。逆に、マイグレーションのみを適用して各サービスが旧版のままである状態は無害である（列が参照されないだけ）。

## 9. 既存システムとの関係・影響範囲

- `agent_invitro`（`/ask-pipeline` ・ `/ask-agentic`）は `search_knowledge` の呼び出し側であり、**コード変更は不要**。除外はMCPサーバー側で完結する。
- 検証機能（ADR-0048〜0050・ADR-0060）も同様にコード変更不要。ただし、**検証実行の結果は実行時点の `is_searchable` の状態に依存する**ため、過去の実行履歴（`verification_run_source`）と再実行結果が異なりうる。これは仕様として許容する（履歴は実行時点のスナップショットであるという既存方針どおり）。
- `tag_selector_mcp` はタグマスタのみを参照するため無関係。
- `conversation` データベースのスキーマ・マイグレーションには変更がない。
- 全データエクスポートの出力（SQL/CSV）は列が1つ増えるため、**出力ファイルを外部ツールで機械的に処理している運用がある場合は列の追加に注意が必要**。

## 10. 受け入れ基準（Definition of Done, MVP）

- [ ] マイグレーション 0010 を適用すると3テーブルに `is_searchable` 列が追加され、既存の全レコードが `true` になっていることを確認する。再実行してもエラーにならないことを確認する。
- [ ] マイグレーション適用直後、同一の質問に対する `search_knowledge` の結果（件数・順序・スコア）が適用前と一致することを確認する。
- [ ] あるQAの `is_searchable` を `false` にすると、そのQA（主質問文・全言い換えを含む）が `search_knowledge` の結果に一切現れないことを確認する。`true` に戻すと元どおり現れることを確認する。
- [ ] ある言い換え行のみ `is_searchable` を `false` にすると、その言い換え文に強く一致する質問でも当該QAが（他の言い換え・主質問文経由でヒットしない限り）返らないこと、かつ同一QAの他の言い換え経由では引き続きヒットすることを確認する。

- [ ] 検索対象外のレコードが候補プールの枠を消費せず、その分だけ他の候補が繰り上がって `top_k` 件が返ることを確認する。

- [ ] `is_searchable` 列を含まない既存のQA一括インポートCSV・言い換え質問文CSVをそのままインポートしても、既存レコードの `is_searchable` が変化しないことを確認する。
- [ ] `is_searchable` 列を含むCSVで、`true` / `false` / `1` / `0` / 空欄が期待どおりに解釈され、不正値は当該行のみエラーとなることを確認する。
- [ ] 言い換え質問文のCSVエクスポートに `is_searchable` 列が出力され、その内容をそのまま再インポートすると設定が保持されることを確認する。

## 11. Open Issues（要追加確認事項）

1. **主質問文行の個別切り替え**: 4.2節のとおり本書では対象外とし、QA単位のフラグで制御する。「主質問文だけを検索から外し、言い換えのみでヒットさせたい」という要望が出た場合は、`update_question_altered` の主質問文行拒否ルール（ADR-0064）の見直しを含めて別途要件化する。
2. **索引の要否**: 6.1節のとおり当面は索引を追加しない。検索対象外レコードが全体の多数を占めるようになった場合、または管理画面の絞り込みが遅くなった場合に、部分索引（`WHERE is_searchable = false` 等）の導入を検討する。
3. **検索対象外レコードの棚卸し**: 除外したまま放置されるレコードが増えることが想定される。「検索対象外の一覧」を定期的に見直す運用ルール、または最終更新日時での並べ替え・通知が必要かは運用開始後に判断する（現状 `hiroba_qa_original` ・ `hiroba_question_altered` に更新日時列がないため、並べ替えを行う場合は列追加が必要）。
4. **一括切り替え**: 複数レコードをチェックボックスで選択して一括で切り替える操作は本書では対象外とした。タグ単位・カテゴリ単位での一括除外の要望が出た場合に別途要件化する。
5. **エンドユーザーへの見え方**: 除外されたQAについて、利用者が同じ質問を繰り返した場合に「該当なし」となるだけでよいか（誘導文言の要否）は、運用開始後の実データで判断する。

## 13. 発注者確認済み事項

| # | 確認事項 | 回答 |
|---|---|---|
| 1 | QAと配下の言い換え行の `is_searchable` の関係 | **AND合成（QAが親スイッチ）**。QA=false ならその配下の全言い換え行も検索対象外。QA=true のときのみ各言い換え行の値が効く |
| 2 | 管理UIのトグルの保存タイミング | **一覧で即時保存＋編集画面にも配置**（編集画面はフォーム保存時に反映） |
| 3 | 管理用CSVへの列追加 | **追加する**。省略時は「新規は true／既存は変更なし」 |
| 4 | 一覧ページの検索可否での絞り込み | **追加する**（すべて／検索可のみ／検索不可のみ） |
