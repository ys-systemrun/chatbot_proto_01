## 1. 目的

`docs/requirement/202608041002.md`・`docs/requirement/202608051636.md` はいずれも、ユーザーの質問を受けて Tag Selector MCP → Knowledge MCP の順に呼び出して回答を生成する「Conversation Agent（MCP Client）」の存在を前提としつつ、その実装自体は両書のスコープ外としてきた。

本書は、この Conversation Agent を **LangGraph を用いた MCP クライアント（MCPホスト）として実験的に実装する** ための要件を整理したものである。目的は次の1点に絞る。

> LangGraph で構築したグラフ（エージェント）が、既存の Tag Selector MCP サーバおよび Knowledge MCP サーバの両方に接続し、それぞれが提供する MCP ツールを呼び出して動作することを、Python コンテナ内で確認する。

コーディングは対象外とし、要件定義および設計判断（ADR）の整理にとどめる。フロントエンド統合・会話履歴の永続化・本番運用化は本書の対象外（4.2節）とする。

## 2. 背景・参照資料

- Knowledge MCP サーバ（`knowledge_mcp/`）・Tag Selector MCP サーバ（`tag_selector_mcp/`）は、いずれも実装済みであり、Streamable HTTP（MCPエンドポイント `/mcp`、ヘルスチェック `/health`）で `docker-compose.yml` 上の独立コンテナとして稼働している（README.md「Knowledge MCP サーバ」「Tag Selector MCP サーバ」節）。
- `docs/requirement/202608051636.md` 5.1節には、以下のアーキテクチャ図が既に示されている。

```
                         ┌───────────────────────────┐
                         │     Conversation Agent      │
User ── (自然言語) ──→   │   (LangGraph / MCP Client)  │
                         └──────────┬───────┬─────────┘
                                    │       │
                     ① select_tags  │       │ ② search_knowledge(tags=...)
                                    ▼       ▼
                    ┌───────────────────┐ ┌───────────────────────┐
                    │ Tag Selector MCP  │ │  Knowledge MCP サーバ   │
                    │ サーバ             │ │                       │
                    └────────────────────┘ └───────────────────────┘
```

- `agent_invitro/` は、リポジトリ直下に空のスカフォールド（`src/main/`）としてすでに用意されている。本書は、このディレクトリに実装される内容の要件を定義する。
- 既存の `web_backend`（既存app、FastAPI）は `search_similar` を直接呼び出す従来型の実装であり、MCP経由ではない。本実験は既存appの置き換えを意図したものではなく、将来の Conversation Agent の技術検証（Proof of Concept）として位置づける。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| Conversation Agent | ユーザーの質問を受け、複数のMCPサーバーを呼び出して回答を生成するオーケストレーション主体。本書では `agent_invitro` として実験的に実装する対象 |
| MCPホスト / MCPクライアント | MCP（Model Context Protocol）サーバーに接続し、提供されるツールを呼び出す側のアプリケーション。本書ではLangGraphで構築するプロセスを指す |
| LangGraph | LLMを用いたエージェント・ワークフローをグラフ（ノード・エッジ）として構築するためのPythonライブラリ（LangChain系） |
| ReActエージェント | 質問に対し、LLMが「どのツールを呼ぶか／いつ最終回答を返すか」を都度自律的に判断しながら実行するエージェント形式。LangGraphの `create_react_agent` 等が該当 |
| Tool Calling / Function Calling | LLMがテキストではなく構造化された「ツール呼び出し要求」（ツール名・引数）を出力できるAPI機能。OpenAI互換API（LM Studio含む）で提供される場合がある |
| Streamable HTTP | 既存2 MCPサーバーが採用しているMCPの通信方式（HTTP/SSEベース）。本書の `agent_invitro` も同方式で両サーバーに接続する |
| 対話シェル/Notebook | 本書における動作確認の実行形態。コンテナ内でIPython等の対話的なPython実行環境を起動し、開発者が手動でグラフを実行して結果を確認する方式 |

## 4. スコープ

### 4.1 対象範囲（実験フェーズ）

- LangGraphで構築したグラフ（またはReActエージェント）が、以下2つのMCPツールをこの順（あるいは自律判断の結果として同順）で呼び出せることの確認。
  - Tag Selector MCP の `select_tags`（質問文 → タグ集合）
  - Knowledge MCP の `search_knowledge`（タグ集合 → 関連QA検索結果）
- 単発の質問文（1ターン、会話履歴の保持なし）を入力に、最終的にLLMがKnowledge MCPの検索結果を踏まえた回答テキストを生成するまでの一連の流れを、コンテナ内の対話シェル/Notebookから手動実行して確認する。
- MCPサーバーへの接続はStreamable HTTP（既存2サーバーと同一プロトコル）とする。
- LangGraphからMCPサーバーへの接続実装方式の比較検討（6.2節、ADR-0021、Open Issue）。
- 実行環境: `docker-compose.yml` 上の新規コンテナ（対話シェル/Notebook用途。常駐HTTPサーバーとはしない、ADR-0019）。
- エージェント用LLM: ローカルLLM（LM Studio）（ADR-0020）。ロード済みモデルがFunction Calling（Tool Calling）に対応しているかの確認を含む（6.3節、Open Issue）。

### 4.2 対象外（将来検討・別プロジェクトスコープ）

- `front_dev` / `web_backend` からの呼び出し、Web API化（HTTPエンドポイントとしての公開）。
- 会話履歴の永続化（`conversation_db` の利用）、マルチターン対応、セッション管理。
- Knowledge MCP・Tag Selector MCP以外の新規MCPサーバー（検討メモで言及されている User Context MCP・Document Fetch MCP等）の追加。
- 認証・アクセス制御の本格実装（既存2 MCPサーバーと同様、社内ネットワーク限定を前提とする）。
- 精度評価・レイテンシ計測などの定量評価（Tag Selector MCP要件定義書と同様、暫定的に不要と扱う）。
- 本実験の結果を踏まえた本番 Conversation Agent の実装（Web API化・会話履歴対応・既存appとの統合方針等）は、別途要件定義を行う。

## 6. 機能要件

### 6.1 LangGraphグラフ構成

**方式A（自律的ReActエージェント）を採用する**（発注者確認済み、13章 Open Issue #1解消、ADR-0022）。

- `select_tags` と `search_knowledge` の両方をツールとしてLLMに束縛（bind）し、LLM自身がいつ・どの順でツールを呼ぶか、いつ最終回答とするかを判断する（LangGraphの `create_react_agent` 相当の ReAct ループ）。
- 採用理由: 本実験の目的（「LangGraphで動作するMCPホスト」の検証）に最も忠実であり、MCPホストとしての自律的なツール選択能力を確認できるため。
- 検討したが採用しなかった代替案（方式B・固定シーケンス）: グラフのノード・エッジを `select_tags` → `search_knowledge` → 回答生成の順に固定し、LLMにはツール選択の自由度を与えない方式。5.1節の既存アーキテクチャ図に忠実で動作確認・デバッグは容易だが、エージェントとしての自律性の検証にはならないため見送った（詳細はADR-0022参照）。
- 5.1節のアーキテクチャ図（Tag Selector MCP → Knowledge MCPの順）は、方式Aにおける「期待される呼び出し順序」として位置づけ、実際にその順で呼ばれるかは6.4節の動作確認シナリオで確認する（LLMが期待通りの順序で呼ばないリスクは13章 Open Issue #6参照）。
- 最終ノードでLLMがKnowledge MCPの検索結果（QA本文・スコア等）を踏まえて回答テキストを生成する。

### 6.2 MCPクライアント実装方式

LangGraphはMCPプロトコルを直接扱う機能を持たないため、接続用のアダプタ層が必要になる。**`langchain-mcp-adapters`（(a)）を採用する**（発注者確認済み、13章 Open Issue #2解消、ADR-0021）。

| 観点 | (a) `langchain-mcp-adapters`（採用） | (b) MCP公式SDK直接利用（不採用） |
|---|---|---|
| ツールスキーマ変換（MCP Tool → LangGraphツール） | 自動（ライブラリが対応） | 自前実装が必要（JSON Schema変換を含む） |
| 複数MCPサーバーの集約 | `MultiServerMCPClient` で標準対応 | 自前でセッション管理・ツール集約が必要（同等機能なし） |
| Streamable HTTP対応 | 対応（既存2サーバーの転送方式と一致） | 対応（SDK自体の機能） |
| 依存関係 | LangChain/LangGraph一式に依存が増える（`agent_invitro` はLangGraphを前提としているため実質追加負担は小さい） | `mcp` パッケージのみで依存は最小 |
| 実装コスト（本プロジェクトの用途） | 低い。`create_react_agent` へそのまま束縛できる | 高い。変換層・集約層をすべて自作する必要がある |
| プロトコルの細部制御 | ライブラリの実装に委ねる | 自分で完全に制御できる |
| ライブラリの成熟度リスク | LangChain系の開発速度に追従する必要がある（対応MCPプロトコルバージョン等は実装時に再確認） | 公式SDKのため相対的に安定 |

採用理由: Tag Selector MCP・Knowledge MCPの2サーバーへ同時接続し、それぞれのツールをLangGraphのReActエージェント（6.1節、ADR-0022）へ束縛するという本実験の用途に対し、(a)の `MultiServerMCPClient` がほぼそのまま要求を満たす設計になっており、(b)との実装コストの差が大きいため。詳細な比較・代替案の検討はADR-0021を参照。

### 6.3 LLM・Tool Calling要件

- エージェントのツール呼び出し判断には、ADR-0020に基づきローカルLLM（LM Studio）を用いる。
- LangGraphの一般的なツール呼び出し方式（`bind_tools` 等）は、LLM側がOpenAI互換のFunction Calling（Tool Calling）APIに対応していることを前提とする。**現在LM Studioにロードされているモデル（`.env.example` 記載の `google/gemma-4-e4b` 等）がこれに対応しているかは未検証**であり、検証・確認が必要（13章 Open Issue #3）。
- LM Studioのモデルカタログにおける「ハンマー」アイコン（Native tool use support バッジ）は、判定の参考情報として利用できる。ハンマーアイコン付きのモデル（Qwen2.5、Llama-3.1/3.2、Ministral系等）は、ツール利用向けに学習されたチャットテンプレートを持ち、LM Studio側がそのツール呼び出しフォーマットを正しく解釈できることを意味し、OpenAI互換のTool Calling APIとの相性が一般的に良いとされている。一方、LM Studioの仕様上、バッジのないモデルもフォールバック実装（既定のシステムプロンプト・ツール形式）により一定程度ツールを利用できるが、出力フォーマットが崩れる可能性はバッジ付きモデルより高く、バッジ付きモデルであっても崩れないことの保証にはならない。
- したがって、ハンマーアイコンの有無はモデル選定時の一次的な判断材料とするが、**最終的な対応可否の判断は本書6.4節の手動テストクエリによる実際の動作確認をもって行う**（13章 Open Issue #3）。
- 対応していないことが判明した場合の代替方針（プロンプトベースの疑似Function Calling、Tool Calling対応モデルへの変更等）は、検証結果を踏まえて別途決定する。

### 6.4 動作確認シナリオ（手動テストクエリ）

以下のような質問文を対話シェル/Notebookから入力し、想定される挙動を確認する（件数・内容は例）。

| 質問文（例） | 期待する挙動 |
|---|---|
| 「積算システムの操作方法を教えてください」 | `select_tags` が該当タグを返し、そのタグで `search_knowledge` が呼ばれ、関連QAに基づく回答が生成される |
| 「橋梁工事の数量総括表について教えてください」 | 同上（`docs/requirement/202608051636.md` 6.1節の例と同一質問） |
| 既存タグに全く関連しない質問（例: 「今日の天気は？」） | `select_tags` が確信度の低い結果・空集合を返す場合の挙動（検索結果なしでの回答、あるいはエラーハンドリング）を確認する |

### 6.5 ログ・出力要件

実験フェーズでは、構造化ログ基盤の導入は不要とし、各ステップ（ツール呼び出し内容・ツール応答・最終回答）を標準出力へ表示することで動作確認可能とする。

## 7. データ要件

- `agent_invitro` は既存 `chatbot_db`（pgvector）に対して直接の接続を行わない。データアクセスは常にMCPツール呼び出し経由（読み取り専用）とする。
- 会話状態（質問・中間のツール呼び出し結果・最終回答）は、対話シェル/Notebookのプロセスメモリ上にのみ保持し、プロセス終了とともに破棄される。永続化（DB保存等）は本実験のスコープ外とする（4.2節）。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | 明確な目標値は設定しない（対話シェルでの手動検証のため）。1回のやり取り（ツール呼び出し2回＋LLM呼び出し複数回）が数十秒程度で完了することを目安とする |
| 同時実行 | 対象外。開発者1名による手動検証を前提とする |
| 可用性 | 対象外。実験用途のため単発起動・単発実行で問題ない |
| ログ | 6.5節参照。標準出力への出力で十分 |
| セキュリティ | 既存Knowledge MCP・Tag Selector MCPと同様、社内ネットワーク内で完結する構成とする。ローカルLLM（LM Studio）のみを利用するため、質問文・タグ情報・検索結果が外部へ送信されることはない（ADR-0012・ADR-0020と同様の理由）。`agent_invitro` コンテナはホスト側へのポート公開を行わない（ADR-0019） |
| 保守性・拡張性 | MCPクライアント実装方式（6.2節）を後から切り替え可能な構成とし、将来ツール（新規MCPサーバー）を追加する際にグラフ定義への変更のみで対応できることを目指す。ただし本書の対象は実験フェーズであり、厳密な抽象化の要件化は本番実装フェーズで行う |

## 9. インフラ・実行環境要件

### 9.1 デプロイ構成

- ADR-0019に基づき、`chatbot_invitro` リポジトリ直下の既存 `agent_invitro/` ディレクトリに実装し、`docker-compose.yml` へ新規サービスを追加する。
- 他のMCPサーバーとは異なり常駐HTTPサーバーとはせず、`tty: true` によりコンテナを起動させ続け、`docker compose exec agent_invitro ipython` で接続して手動実行する構成とする。対話シェルは **IPython を採用する**（発注者確認済み、13章 Open Issue #4解消、ADR-0019）。Jupyter Labは追加のポート公開・認証設定が発生するため採用しない。
- `knowledge_mcp` / `tag_selector_mcp` の起動（healthy）を前提に、`depends_on` で起動順序を制御する。
- 両MCPサーバーへは、docker-composeの内部ネットワーク経由でサービス名で到達する（`http://knowledge_mcp:8100/mcp`, `http://tag_selector_mcp:8200/mcp`）。
- LM Studioへの接続は、既存パターン（`host.docker.internal`）を踏襲する。

**docker-compose.yml への追加イメージ（例、最終形は詳細設計フェーズで確定）**

```yaml
  agent_invitro:
    build: ./agent_invitro
    container_name: chatbot_agent_invitro
    environment:
      - KNOWLEDGE_MCP_URL=${KNOWLEDGE_MCP_URL:-http://knowledge_mcp:8100/mcp}
      - TAG_SELECTOR_MCP_URL=${TAG_SELECTOR_MCP_URL:-http://tag_selector_mcp:8200/mcp}
      - LLM_PROVIDER=${LLM_PROVIDER:-lmstudio}
      - LMSTUDIO_CHAT_URL=${LMSTUDIO_CHAT_URL}
      - LMSTUDIO_CHAT_MODEL=${LMSTUDIO_CHAT_MODEL:-${MODEL_CHAT}}
    tty: true
    volumes:
      - ./agent_invitro:/app
    depends_on:
      knowledge_mcp:
        condition: service_healthy
      tag_selector_mcp:
        condition: service_healthy
```

`ipython` は `agent_invitro` の依存パッケージ（`pyproject.toml`）に含め、コンテナ内に事前インストールしておく。動作確認は `docker compose exec agent_invitro ipython` で対話シェルへ接続して行う。

### 9.2 ディレクトリ構成（要件レベルの想定案）

## 13. Open Issues（要追加確認事項）

1. ~~**グラフ構造の方針**~~ → 発注者確認の結果、自律的ReActエージェント（方式A）を採用することが確定した（6.1節、ADR-0022）。ただし、LLMが5.1節の期待順序（Tag Selector MCP → Knowledge MCP）で確実にツールを呼ぶとは限らない点は残存リスクとして13章 Open Issue #6に記録する。
2. ~~**LangGraph→MCP接続の実装方式**~~ → 発注者確認の結果、`langchain-mcp-adapters`（(a)）を採用することが確定した（6.2節、ADR-0021）。比較検討の詳細（ツールスキーマ変換・複数サーバー集約・依存関係・実装コスト等）はADR-0021に記録済み。
3. **ロード済みLLMモデルのFunction Calling対応可否**: LM Studioにロードするモデル（例: `google/gemma-4-e4b`）がOpenAI互換のTool Calling APIに対応しているかの検証結果（6.3節）。対応していない場合の代替方針（プロンプトベース疑似Function Calling／対応モデルへの変更）。方式A（ReActエージェント）の採用によりTool Calling対応が事実上の前提となったため、本Issueの重要度は上がっている。**（追記, 2026-08-06）** LM Studioのモデルカタログの「ハンマー」アイコン（Native tool use support バッジ）は有力な一次判定材料になる（バッジ付きモデルはOpenAI互換のTool Calling APIとの相性が一般的に良い）。ただしバッジがなくてもLM Studio側のフォールバック実装により一定程度動作する場合があり、バッジ付きモデルであっても出力フォーマットの崩れが完全に排除されるわけではない。したがって、バッジの有無を初期選定の参考情報としつつ、最終的な対応可否の判断は6.4節の手動テストクエリによる実際の動作確認をもって行う（未解消のまま残す）。
4. ~~**対話シェル/Notebookの具体的な選定**~~ → 発注者確認の結果、IPython（`docker compose exec agent_invitro ipython`）を採用することが確定した（9.1節、ADR-0019）。Jupyter Labは追加のポート公開・認証設定が発生するため不採用。
5. ~~**既存スカフォールド（`agent_invitro/src/main/`）と9.2節ディレクトリ構成案との整合**~~ → 実装指示書（`docs/implementation_handoff/202608061725_implementation.md`、IMPL-202608061725）0節・3節にて、既存スカフォールドが空であるため9.2節の構成へ再編することを決定した（実装レベルの判断のため発注者への確認は事後報告）。
6. ~~**実験完了の成功条件の具体化／方式A採用に伴う残存リスク**~~ → 実装指示書（IMPL-202608061725）10章にて、完了条件チェックリストとして具体化した（暫定提案であり実測値を踏まえて見直しうる）。ReActエージェントの判断ミスへのガードレールは、同書5.4節のシステムプロンプトで一次的に対応する。
