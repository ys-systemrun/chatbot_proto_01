## 1. 目的

`knowledge_mcp`・`tag_selector_mcp`（既存2 MCPサーバー）および、そのMCPクライアントである`agent_invitro`を、**Terraformを用いてAWS上にデプロイし、AWS上で実際に動作することを検証する**ための要件を整理する。目的は次の2点に絞る。

> (1) 現在ローカルの`docker-compose.yml`で構築されている構成を、Terraformでコード管理されたAWSインフラ構成として再現できることを確認する。
>
> (2) AWS上に配置したMCPサーバー・クライアントが、**社内（AWS内部）からのみアクセス可能な状態**で、ローカル環境と同等にMCP通信・ツール呼び出しの連携が機能することを検証する。

Terraformモジュールやアプリケーションコードの実装自体（コーディング）は本書の対象外とし、要件定義および設計判断（ADR）の整理にとどめる。

## 2. 背景・参照資料

- `knowledge_mcp`・`tag_selector_mcp`は、いずれも独立Dockerコンテナ + Streamable HTTP方式（MCPエンドポイント`/mcp`、ヘルスチェック`/health`）で`docker-compose.yml`上に構築済みである（ADR-0002, ADR-0007）。
- `agent_invitro`は、この2サーバーに接続するMCPクライアント（LangGraph ReActエージェント、`langchain-mcp-adapters`使用）として実験実装済みだが、常駐HTTPサーバーではなく、`docker compose exec agent_invitro ipython`による対話シェル形態である（ADR-0019, 0021, 0022）。ホスト側へのポート公開は行っていない。
- README.mdには「本フェーズでは追加認証を実装していません。社内ネットワーク外へポートを公開しないでください」という運用上の制約が明記されている。
- 現状、AWS上のインフラ構成（Terraformを含む）は存在せず、すべてローカルのdocker-compose環境で運用されている。
- アクセス範囲（AWS内部限定）はADR-0023で確定済み。本書はその前提のもとで、コンピュート基盤・サービス間通信・動作検証方法を具体化する。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| ECS Fargate | コンテナをサーバー管理なしで実行できるAWSのコンテナ実行基盤。Dockerイメージをそのままタスクとして起動できる |
| プライベートサブネット | インターネットゲートウェイへの直接ルートを持たないサブネット。インバウンドの外部到達性を持たない |
| セキュリティグループ | AWSのインスタンス/タスク単位のステートフルなファイアウォール機能。本書ではサービス間通信の許可制御に用いる |
| ECS Service Connect / AWS Cloud Map | ECSサービス同士を名前（サービス名）で相互に解決・接続できるようにする仕組み。docker-composeの内部DNS（`http://knowledge_mcp:8100`等）に相当する役割を担う |
| Terraform | HashiCorp社のIaC（Infrastructure as Code）ツール。AWSリソースをコードで定義・適用する |
| Terraform state | Terraformが管理するリソースの現在状態を記録したファイル。複数人での運用にはS3等の共有バックエンドが必要 |
| MCP Inspector | MCP公式の開発者向け検証ツール。MCPサーバーに対して`tools/list`・`tools/call`等を対話的に実行できる |
| ECS Exec | 稼働中のECSタスク（コンテナ）内部へ、AWS CLI経由でシェル接続できる機能。踏み台サーバーを別途用意せずにコンテナ内を確認できる |

## 4. スコープ

### 4.1 対象範囲

- `knowledge_mcp`・`tag_selector_mcp`・`agent_invitro`の3コンポーネントを、AWS上にTerraformでデプロイする構成の設計。
- `knowledge_mcp`が利用するRDS（ADR-0026）へのマイグレーション・シード実行を担う`db_hiroba_qa_init`を、ECR + ECSでAWSにも展開する構成の設計（ADR-0030、7章）。
- アクセス範囲: **AWS内部限定**（ADR-0023）。外部（インターネット）およびオンプレ社内LANからの直接アクセスは行わない。
- デプロイしたMCPサーバー・クライアントが、ローカルdocker-compose環境と同様にMCP通信（`tools/list`・`tools/call`）・ツール呼び出しの連携が機能することの**検証方法の定義**（9章）。

### 4.2 対象外（将来検討・別プロジェクトスコープ）

- 外部公開、第三者MCPクライアントからの利用、MCP仕様のAuthorization機能（OAuth 2.1ベース）の実装。
- オンプレ社内LANとAWS VPC間のVPN／専用線構築（ADR-0023により本フェーズでは不要と確定）。
- `agent_invitro`の本番Web API化・会話履歴永続化（`docs/requirement/202608061621_会話エージェント実験要件定義書.md`の対象外事項を踏襲）。
- 既存DB（pgvector、`chatbot_db`）自体のAWS移行方式の詳細設計（7章でOpen Issueとして扱う）。
- 負荷試験・オートスケーリングの実運用チューニング、コスト最適化（本検証はMVPであり対象外）。
- CI/CDパイプラインの構築（別途要件定義）。
- Terraformモジュール・アプリケーションコードの実装そのもの（本書は要件・設計判断の整理のみ）。

## 6. 機能要件

### 6.1 コンピュート基盤（確定、ADR-0024）

**ECS Fargateを採用する。**（発注者確認済み、14章 Open Issue #1解消、ADR-0024）

- 既存の各コンポーネントが独立Dockerコンテナとして稼働する設計（ADR-0002, ADR-0007, ADR-0019）と最も自然に対応し、既存のDockerイメージをほぼそのまま利用できる。
- Streamable HTTP（SSEベース）のような長時間コネクションを維持する必要があるMCPサーバーの特性上、実行時間制限やコールドスタートの影響を受けやすいLambdaより適している。

| 観点 | ECS Fargate（採用） | Lambda | EKS |
|---|---|---|---|
| 既存Dockerイメージの再利用 | そのまま利用可能 | コンテナイメージ対応だが実行時間制限あり | そのまま利用可能 |
| 長時間コネクション（Streamable HTTP/SSE）への適性 | 適している | 不向き（実行時間上限、接続維持が難しい） | 適している |
| 運用の複雑さ（3サービス規模に対して） | 小さい | 小さいがMCPサーバー用途には制約が大きい | 大きい（クラスタ管理コストが3サービス規模には過大） |
| Terraformでの構成の書きやすさ | 標準的なモジュールパターンが確立している | イベントトリガー設計が別途必要 | クラスタ構築自体が大きな作業になる |

代替案（Lambda・EKS）は上記の理由で不採用とする。比較の詳細はADR-0024を参照。

### 6.2 サービス間通信・名前解決

- ECS Service Connect（またはAWS Cloud Map）を用いて、既存のdocker-compose内部DNS名（`http://knowledge_mcp:8100/mcp`、`http://tag_selector_mcp:8200/mcp`）と同等の名前解決をAWS上で再現する。
- 転送方式は既存方針（ADR-0002, ADR-0007）を継続し、Streamable HTTPとする。

### 6.3 ネットワーク境界・アクセス制御

ADR-0023で確定済みの方針（AWS内部限定、外部公開なし）を踏襲する。

- 全サービスをプライベートサブネットに配置し、インターネットゲートウェイ経由のインバウンド到達性を持たせない。
- セキュリティグループで「`agent_invitro` → `tag_selector_mcp`」「`agent_invitro` → `knowledge_mcp`」の通信のみを許可し、それ以外のソースからの到達を拒否する。
- アプリケーションレベルの認証（OAuth等）は、差し当たり本フェーズでは実装しない（発注者確認済み、14章 Open Issue #2解消、ADR-0023追記）。将来、外部公開や他部門からの利用が必要になった場合に再検討する。

### 6.4 `agent_invitro`の実行形態変更（確定、ADR-0025）

- 現行のIPython対話シェル形態（ADR-0019）は、ホスト側にポートを公開せず、ローカルdocker-compose内で人間が`docker compose exec`により手動実行する前提であり、AWS上で継続的に動作確認するにはそのままでは適さない。
- **決定**（発注者確認済み、14章 Open Issue #3解消、ADR-0025）: ECS Fargateサービスとして常駐させ、動作確認は`aws ecs execute-command`（ECS Exec）でコンテナ内シェルに接続し、IPython等で対話的に実行する形態とする。すなわち「対話シェルによる手動実行」という検証方針自体（ADR-0019の考え方）は継続しつつ、接続手段のみ`docker compose exec`から`ECS Exec`へ置き換える。
- 常駐HTTPサーバー化（外部からのリクエストを受け付けるAPIとして公開すること）は、ADR-0019が示す「将来の本番Conversation Agent化」に該当するため、本書の対象外とし、必要になった時点で別ADRを起票する。

### 6.6 シークレット・設定管理

- AWS環境のチャット・エンベディング用LLMは**Amazon Bedrockを利用する**ことが確定した（発注者確認済み、ADR-0031）。APIキー管理は不要とし、ECSタスクロール（IAM）にBedrock呼び出し権限（`bedrock:InvokeModel`等）を付与する。
- 万一、将来的にOpenAI等の外部APIを利用する場合のAPIキーは、AWS Secrets Managerに格納し、ECSタスク定義から`secrets`参照で注入する想定を残す（本デプロイでは未使用）。

### 6.7 データベース基盤（確定、ADR-0026）

**`knowledge_mcp`が利用するDBは、Amazon RDS for PostgreSQL（pgvector拡張）へ移行する。**（発注者確認済み、14章 Open Issue #4解消、ADR-0026）

- RDSインスタンスは、ECS Fargateサービスと同一VPC内のプライベートサブネット（DBサブネットグループ）に配置し、インターネットからの到達性を持たせない。
- セキュリティグループにより、`knowledge_mcp` → RDS、および`db_hiroba_qa_init` → RDS（マイグレーション・シード実行のため、ADR-0030）の通信のみを許可する。`tag_selector_mcp`・`agent_invitro`から直接DBへアクセスすることはない（既存構成と同様、通常のクエリ経路は`knowledge_mcp`経由に閉じる）。
- DB認証情報（マスターパスワード等）は6.6節と同様にAWS Secrets Managerで管理し、`knowledge_mcp`のECSタスク定義から注入する。
- Amazon Aurora PostgreSQLも代替案として検討したが、MVPの動作検証という目的に対しては構成・コストの両面で過剰と判断し、通常のRDS for PostgreSQLを採用する（詳細な比較はADR-0026参照）。
- 既存データ（QA・タグ等）をRDSへ投入する手順（マイグレーション・シード）は、**既存の`db_hiroba_qa_init`をECR + ECSでAWSにも展開し、再利用する**ことが確定した（発注者確認済み、14章 Open Issue #8解消、6.8節、ADR-0030）。

### 6.8 `db_hiroba_qa_init`のAWS展開（確定、ADR-0030）

**`db_hiroba_qa_init`をAmazon ECR + ECSでAWSにも展開する。**（発注者確認済み）

- 既存のDockerイメージ（マイグレーション: yoyo-migrations採用、ADR-0017／シード: 存在チェックによる冪等性、ADR-0018）をそのまま利用し、Amazon ECRにpushする。
- ECS Fargate上では、`knowledge_mcp`等（常駐サービス、ADR-0024）とは異なり、**一回限り実行して終了するタスク**（`aws ecs run-task`によるRun Task方式）として扱う。初回の検証データ投入時や、マイグレーション追加時など、必要なタイミングで都度実行する。
- RDSへの接続は`db_hiroba_qa_init`から直接行う（6.7節のセキュリティグループ方針に追加済み）。
- `knowledge_mcp`サービスの起動・更新は、`db_hiroba_qa_init`タスクの実行完了後に行う（既存のADR-0018が示す起動順序制御という関心事に相当する）。ECSにはdocker-composeの`depends_on: condition: service_healthy`に相当する自動順序制御機能がないため、この順序保証はデプロイ手順（Terraform適用やタスク実行の手順）側の運用ルールとして担保する。

## 7. データ要件

- `knowledge_mcp`は既存の`chatbot_db`（pgvector拡張付きPostgreSQL）に依存している。このDBは、ADR-0023（オンプレ-AWS間の新規接続を構築しない方針）との整合上、AWS上に配置する以外の選択肢が実質的になく、**Amazon RDS for PostgreSQL（pgvector拡張）へ移行する**ことが確定した（6.7節、ADR-0026）。
- 本検証（MVP）では、動作確認に必要な最小限のQA・タグデータのみを対象とし、本番データそのものの移行は対象外とする。
- 既存データ（QA・タグ）をRDSへ投入する手順は、**既存の`db_hiroba_qa_init`（ADR-0016〜0018の仕組み）をECR + ECSでAWSにも展開し、そのまま利用する**ことが確定した（6.8節、ADR-0030）。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | 明確な目標値は設定しない（動作検証目的のため）。ローカル環境と比べてネットワーク経路が変わる分のレイテンシ変化は、9章の検証で参考情報として記録する |
| 可用性 | 対象外。検証用途のため単一AZ・単一タスクでの起動で問題ない（複数AZ化は本番フェーズで検討） |
| セキュリティ | AWS内部限定（ADR-0023）。アプリケーションレベルの認証は本フェーズでは実装せず、ネットワーク境界（VPC・セキュリティグループ）による制御で代替する |
| ログ | CloudWatch Logsへの出力を基本とする。ローカル環境の標準出力ログ（会話エージェント実験要件定義書6.5節）と同等の内容をCloudWatch Logsで確認できることを要件とする |
| コスト | ECS Fargateの常時起動によるコストが発生する。検証終了後の停止・破棄方針（`terraform destroy`等）を運用ルールとして定める（Open Issue #7） |
| 保守性・拡張性 | Terraformモジュール化（6.5節）により、将来のコンポーネント追加・環境追加（dev/prod分離等）に対応しやすい構成を目指す |

## 9. 動作検証方針

動作検証は「インフラ層」「プロトコル層」「クライアント統合層」の3段階に分けて行う。いずれの段階も、AWS内部限定（ADR-0023）を前提に、VPC内部からのアクセス手段を用いて行う。

### 9.1 インフラ層の検証

- `terraform plan`のレビュー後、`terraform apply`が正常終了することを確認する。
- 各ECSサービスの「Running Count」が「Desired Count」と一致していること、コンテナヘルスチェックがPassingであることをCloudWatchまたはECSコンソール相当の情報で確認する。
- `db_hiroba_qa_init`のRun Task（6.8節、ADR-0030）が正常終了（Exit Code 0）すること、およびRDSに想定したQA・タグデータが投入されていることを確認する。この確認は、`knowledge_mcp`サービスを起動・更新する前に完了させる（6.8節の起動順序の考え方）。
- セキュリティグループが意図通りであることを、**否定的な確認**（許可されていないソース、例えば一時的に立てた検証用タスクやVPC外からの接続を試行し、到達できないことを確認する）によって検証する。到達性の「ある」ことだけでなく「ない」ことの確認を必須項目とする。

### 9.2 プロトコル層の検証（確定、ADR-0029）

- MCP Inspector（公式の開発者向け検証ツール）を、AWS上の`tag_selector_mcp`・`knowledge_mcp`のエンドポイントに向けて実行し、`tools/list`・`tools/call`がローカル環境と同様に機能することを確認する。
- **実行方式**（発注者確認済み、14章 Open Issue #5解消、ADR-0029）: MCP Inspectorを含む検証用タスクをECS Fargateで一時的に起動し、ECS Exec（`aws ecs execute-command`）でタスク内シェルに接続してMCP Inspectorを実行する。検証終了後は当該タスクを停止する。SSMポートフォワーディングによるローカル端末からの接続は、開発者ごとの環境セットアップが不要な点でECS Exec方式を優先し、不採用とした（詳細はADR-0029参照）。

### 9.3 クライアント統合層の検証

- 既存の手動テストクエリ（`docs/requirement/202608061621_会話エージェント実験要件定義書.md` 6.4節）を、接続先エンドポイントをdocker-compose内部DNSからAWS上のサービス名（ECS Service Connect経由）に向け直して再実行する。
- ローカル環境と同様に、想定順序（`select_tags` → `search_knowledge`）でツールが呼び出され、最終的にKnowledge MCPの検索結果を踏まえた回答テキストが生成されることを、ログ（CloudWatch Logs）で確認する。

### 9.4 検証項目のまとめ

| 層 | 確認内容 | 確認手段 |
|---|---|---|
| インフラ層 | ECSサービスの起動・ヘルスチェック、意図しない経路からの到達不可 | ECS/CloudWatchコンソール相当の情報、否定的アクセス試行 |
| プロトコル層 | MCPプロトコルレベルでの`tools/list`・`tools/call`の応答 | MCP Inspector（VPC内部から実行） |
| クライアント統合層 | エージェントによる自律的なツール呼び出し順序・最終回答生成 | 既存手動テストクエリの再実行、CloudWatch Logs確認 |

## 10. インフラ・実行環境要件

- AWSアカウント・リージョンの具体的な値の選定（既存の他プロジェクトでの利用実績があれば揃える）は、Open Issue #6として別途確定する。管理方式自体は**Git管理外の`terraform.tfvars`に記述する**ことが確定している（発注者確認済み、ADR-0028）。リポジトリには`terraform.tfvars.example`のみをコミットする。
- Terraform stateの管理方式は**S3バックエンドを採用する**（発注者確認済み、ADR-0027）。ロック方式（S3ネイティブロックかDynamoDBロックテーブルか）は利用するTerraformのバージョンに応じて実装フェーズで確定する。stateバケット自体の作成（ブートストラップ）手順、および既存の社内Terraform運用ルール（もしあれば）との整合は詳細設計フェーズで確認する。
- IAM権限方針: ECSタスクロールには、必要最小限の権限（CloudWatch Logsへの書き込み、Secrets Managerからの読み取り、Bedrock利用時はBedrock呼び出し権限）のみを付与する。Terraform実行主体（開発者/将来のCI）には、stateバケットへの読み書き権限を別途付与する。MCP Inspector検証用タスク（ADR-0029）には、ECS Exec用のIAM権限（SSMセッション確立）を付与する。

## 11. 既存システムとの関係・影響範囲

- `knowledge_mcp`・`tag_selector_mcp`の既存ツール自体（`search_knowledge`・`select_tags`等）に変更は不要。既存のDockerイメージをECS Fargateタスクとしてそのまま利用する想定。
- `agent_invitro`は、ADR-0019で確定した「実験フェーズの実行形態」から、常駐サービス化（6.4節）という変更が発生する。この変更範囲は本書のスコープ内だが、実装自体は対象外。
- `db_hiroba_qa_init`（ADR-0016〜0018）の既存処理内容（マイグレーション・シードのロジック自体）に変更は不要。ECR + ECS Run Task（6.8節、ADR-0030）という新たな実行経路が追加される点のみが変更範囲であり、実装自体は対象外。
- ローカルのdocker-compose環境（README.md記載の既存運用）には影響しない。AWS環境は検証用の別環境として構築し、既存のローカル開発フローと並行して存在する。

## 12. 受け入れ基準（Definition of Done）

- [ ] Terraformで定義したAWSインフラ（VPC、プライベートサブネット、ECS Fargateクラスタ、3サービス、セキュリティグループ）が`terraform apply`で構築できる。
- [ ] 3つのECSサービスが起動し、ヘルスチェックがPassingになる。
- [ ] 意図していない経路（許可されていないソース）からMCPエンドポイントへ到達できないことを確認できる。
- [ ] MCP Inspectorから、AWS上の`tag_selector_mcp`・`knowledge_mcp`の両エンドポインへ接続し、`tools/list`・`tools/call`が正しく応答することを確認できる。
- [ ] 既存の手動テストクエリ（会話エージェント実験要件定義書6.4節）を、AWS上のエンドポイントに向けて再実行し、`select_tags` → `search_knowledge`の順にツールが呼び出され、最終回答が生成されることをCloudWatch Logsで確認できる。
- [ ] `db_hiroba_qa_init`のECR + ECS Run Taskが正常終了し、RDSに検証用のQA・タグデータが投入されていることを確認できる。
- [ ] `knowledge_mcp`からRDS（PostgreSQL + pgvector拡張）への接続が成立し、ベクトル検索を含むクエリが正しく応答することを確認できる。
- [ ] `tag_selector_mcp`・`agent_invitro`からRDSへの直接到達ができないこと（`knowledge_mcp`経由に限定されていること）を確認できる。
- [ ] 検証終了後、`terraform destroy`等でAWSリソース（RDSを含む）を破棄できることを確認する（コスト管理）。

精度評価・レイテンシの定量評価・負荷試験は、本検証（MVP）の受け入れ基準には含めない（既存の`tag_selector_mcp`・`agent_invitro`要件定義書と同様の方針）。
