# ナレッジベース MCP サーバ 要件定義書

- 文書番号: REQ-202608041002
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: Knowledge MCP サーバ（新規）
- 参照資料: `docs/requirement/202608040945.md`（ナレッジMCPサーバ構成に関する検討メモ）
- 前提の決定事項: 本書末尾「14. 関連ADR一覧」参照

## 1. 目的

現行の chatbot_invitro は、FastAPI アプリ（`app/`）が PostgreSQL(pgvector) に直接クエリを発行して類似QA検索を行う構成になっている。今後 LangGraph ベースのエージェント構成へ移行し、QA以外の情報源（マニュアル、PDF、API連携データ等）を段階的に追加していくにあたり、検索対象のデータソースをエージェント側から隠蔽し、単一のインターフェースで呼び出せる「ナレッジベース検索」を提供する MCP サーバを新設する。

本書は、この Knowledge MCP サーバを新規プロジェクトとして立ち上げる際の要件を整理したものである。コーディングは対象外とし、要件定義および設計判断（ADR）の整理にとどめる。

## 2. 背景・参照資料

- `docs/requirement/202608040945.md` にて、「JSONファイルをそのまま検索するMCPサーバ」ではなく「ナレッジリポジトリを提供するMCPサーバ」として設計する方針が提示されている。
- 現行データソースは QA JSON（`data/exportjson_withguid.json` 等、質問・回答・カテゴリ・タグ・GUIDを持つ）のみだが、将来的にマニュアル・PDF・API取得データ等を同一インターフェースで検索できるようにしたいという要望がある。
- 既存実装（`app/src/db.py`, `app/src/embedding.py`, `db_nomic/init.sql`）を調査した結果、以下が判明している。
  - PostgreSQL は pgvector 拡張済みで、`qa_original`（uuid, question_text, answer_text, category_id）、`question_altered`（id, qa_id, text, embedding VECTOR(768)）、`category`（id, name）の3テーブルで構成される。
  - 類似検索は `question_altered.embedding` を軸に `<=>` 演算子でベクトル距離検索し、`qa_original` と結合して回答を取得している（`DB.search_similar`）。
  - embedding は LM Studio 経由のローカルモデル（`nomic-embed-text-v1.5` 等）を HTTP 経由で呼び出して取得している。
  - **現行スキーマには `title` と `tags` に相当するカラムが存在しない。** 参照資料が前提とする共通 Document モデル（`title`, `metadata.tags` を含む）を満たすには、スキーマ拡張が必要である（詳細は 7.3 節）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| Knowledge MCP サーバ | 本書が対象とする、複数データソースを横断検索するための MCP サーバ |
| Repository | データソースごとの検索処理を抽象化した層（QA・PDF・マニュアル等） |
| Document | どのデータソース由来であっても統一されるレスポンス上の共通データモデル |
| Adapter | 特定データソース形式（QA JSON等）から共通 Document への変換を担う実装 |
| Tag Selector MCP サーバ | 参照資料内で言及されている、タグ・カテゴリ推定を担う別MCPサーバ（本書のスコープ外、11章参照） |

## 4. スコープ

### 4.1 対象範囲（MVP）

- QA JSON データソースを検索対象とする `QARepository` の要件定義。
- 複数データソースを束ねる `SearchService` の要件定義（ただし MVP では Repository はQAの1系統のみ）。
- 単一の MCP ツール `search_knowledge` のインターフェース定義。
- 将来 Repository を追加する際に変更が波及しないための抽象化（Repository / Document インターフェース）の設計要件。
- 既存 pgvector スキーマの拡張要件（title / tags 対応）。
- タグマスタ（`tag`テーブル）の登録・リネーム・親子関係編集を行うMCPツール群の要件定義（ADR-0006、6.6節）。
- Docker Compose への新規サービスとしての組み込み要件。

### 4.2 対象外（将来検討・別プロジェクトスコープ）

- PDF・マニュアル・外部API・他DB等、QA以外の Repository の実装（インターフェースの受け皿のみ用意し、実装は将来フェーズ）。
- タグ・カテゴリ推定ロジック（Tag Selector MCP サーバ側の責務と想定。11章参照）。
- LangGraph Agent / Client 側の実装（本書は Knowledge MCP サーバの提供側のみを対象とする）。
- 既存 FastAPI アプリ（`app/`）を Knowledge MCP 呼び出しへ切り替える移行作業そのもの（移行方針は Open Issue として記載するに留める）。
- 認証基盤・IDP連携等の全社的な認証方式（アクセス制御の要件レベルまでを本書の対象とする）。

## 5. 全体アーキテクチャ

### 5.1 システム構成（MVP時点）

```
                 ┌───────────────────────────┐
                 │   既存 FastAPI app (chatbot_app)  │
User ── HTTP ──→ │   / 将来: LangGraph Agent          │
                 └───────────────┬─────────────┘
                                 │ MCP over HTTP/SSE
                                 ▼
                 ┌───────────────────────────┐
                 │     Knowledge MCP サーバ (新設)     │
                 │   tool: search_knowledge          │
                 └───────────────┬─────────────┘
                                 │
                          QARepository
                                 │
                                 ▼
                 既存 chatbot_db (pgvector, PostgreSQL)
                 qa_original / question_altered / category
                 （title カラム追加 + tag/qa_tag 関連テーブル新設）
```

将来的に PDF/マニュアル/API 等の Repository を追加する場合も、`SearchService` と `search_knowledge` ツールのインターフェースは変更せず、Repository 実装の追加のみで対応できる構成とする。

### 5.2 コンポーネント一覧と責務

| コンポーネント | 責務 |
|---|---|
| MCP Tool 層 (`search_knowledge`) | クライアントからの検索要求を受け付け、`SearchService` を呼び出し、結果をMCPレスポンス形式に整形する |
| SearchService | 複数 Repository を束ね、結果を統合・スコア順に整形する（MVPではQARepositoryのみ束ねる） |
| Repository（QARepository） | 特定データソース（QA JSON由来のpgvectorデータ）に対する検索を実装し、共通 Document を返す |
| Embedding 連携 | クエリ文字列をベクトル化する。既存 `app/src/embedding.py` と同じ LM Studio embedding API を利用する想定 |
| データストア | 既存 chatbot_db（pgvector）を読み取り専用で利用する（ADR-0003参照） |

## 6. 機能要件

### 6.1 MCP ツール仕様: `search_knowledge`

**入力（例、インターフェース仕様としての参考例）**

```json
{
  "query": "内訳備考欄の内直接人件費の集計項目は確認できますか。",
  "top_k": 5,
  "tags": ["積算", "操作方法"],
  "category": "積算システムの操作方法に関するご質問",
  "min_score": 0.0
}
```

| フィールド | 必須 | 説明 |
|---|---|---|
| query | ○ | 検索クエリ文字列 |
| top_k | - | 取得件数上限（デフォルト値は設計時に確定、参考値5） |
| tags | - | タグによる絞り込み（呼び出し元、あるいはTag Selector MCPが解決済みの値を渡す想定。Knowledge MCP自体はタグ推定を行わない） |
| category | - | カテゴリによる絞り込み |
| min_score | - | 関連度スコアの下限フィルタ |

**出力（例）**

```json
{
  "results": [
    {
      "id": "1ca063f6-1e0d-4448-be1c-52caaec81dc6",
      "source_type": "qa",
      "title": "内訳備考欄の内直接人件費の集計項目は確認できますか。",
      "content": "質問：...\n回答：...",
      "score": 0.94,
      "metadata": {
        "tags": ["操作方法", "積算システム", "直接費", "調査"],
        "category": "積算システムの操作方法に関するご質問",
        "guid": "1ca063f6-1e0d-4448-be1c-52caaec81dc6"
      }
    }
  ]
}
```

エラー時のレスポンス形式（MCPエラーレスポンスに準拠、詳細は詳細設計フェーズで確定）も要件として定める必要がある。

### 6.2 共通 Document モデル

| フィールド | 型 | 説明 |
|---|---|---|
| id | string | データソース内で一意なID（QAの場合は既存の `guid`） |
| source_type | string | `"qa"`（MVP時点はこの値のみ。将来 `"pdf"`, `"manual"`, `"api"` 等を追加） |
| title | string | 見出し（QAの場合は元の質問タイトル） |
| content | string | 検索結果本文（質問＋回答を整形したもの） |
| score | float | 関連度スコア（0.0〜1.0に正規化する方針とする。距離→スコア変換式は詳細設計で確定） |
| metadata | object | `tags`, `category`, `guid` 等、ソース固有の付随情報 |

### 6.3 QARepository（QA JSON アダプタ）

現行データソース（`data/exportjson_withguid.json` 等）のフィールドと共通 Document モデルの対応関係を以下の通りとする。

| ソースフィールド | Document 上の対応 |
|---|---|
| guid | id, metadata.guid |
| title | title |
| question | content の一部（質問部として整形） |
| answer | content の一部（回答部として整形） |
| category | metadata.category |
| tags | metadata.tags |

- QARepository は、既存 `DB.search_similar` と同様に `question_altered.embedding` を軸としたベクトル距離検索を行い、`qa_original` と結合して回答本文を取得する。
- tags / category によるフィルタに対応する必要があるが、現行スキーマには該当するカラム・テーブルがないため 7.3 節のスキーマ拡張（tag / qa_tag 関連テーブルの新設）が前提となる。tagsによる絞り込みは `qa_tag` / `tag` テーブルとの結合により実現する（ADR-0005）。
- スコアは pgvector の距離（`<=>`）から 0.0〜1.0 のスコアへ変換する方式を定義する（変換式は詳細設計フェーズで確定。例: `score = 1 / (1 + distance)`）。

### 6.4 SearchService

- 複数 Repository の検索結果を集約し、スコア順に整列した上で `top_k` 件に絞り込んで返す。
- MVP では Repository は QARepository のみだが、将来 Repository が複数になった場合の集約・重み付け・リランキングの拡張ポイントとして設計しておく。
- Repository の登録は DI（依存性注入）的に行い、新規 Repository 追加時に SearchService 本体の変更が不要な構成とする。

### 6.5 インデックス・データ同期方針

- MVP では、既存 chatbot_db にすでに投入済みの QA embedding データ（`question_altered`）をそのまま読み取り専用で再利用する。Knowledge MCP サーバ自身が独自の Indexer を持って再インデックスする必要はない（ADR-0003参照）。
- ただし title / tags カラムを追加するスキーマ拡張に伴い、既存データへの値補完（マイグレーション）が必要になる（7.3節）。
- 将来 PDF・マニュアル等、既存の投入パイプラインを持たないデータソースを追加する場合は、当該データソース専用の Indexer（JSON/PDF→Document化→Embedding→ベクトルストア格納）を新設する。

### 6.6 タグ管理機能（ADR-0006）

タグマスタ（`tag`テーブル）の登録・リネーム・親子関係編集は、暫定的に Knowledge MCP サーバ自身がMCPツールとして提供する。ただし、将来的に別の管理ツールや手動SQL等、Knowledge MCP以外の経路からも `tag` テーブルが直接操作される可能性があることを前提とし、Knowledge MCP は `tag` テーブルの内容を**一切キャッシュせず、呼び出しの都度DBを参照する**設計とする（外部からの変更が即座に反映される状態を保つため）。

提供するツール（案）:

| ツール | 概要 | 主なパラメータ |
|---|---|---|
| `list_tags` | タグ一覧を取得する（親子関係を含む） | なし、または `parent_tag_id`（部分木の取得） |
| `create_tag` | 新規タグを作成する | `name`（必須）, `parent_tag_id`（任意） |
| `rename_tag` | タグ名を変更する | `tag_id`（必須）, `new_name`（必須） |
| `move_tag` | 親タグを変更する（再配置） | `tag_id`（必須）, `new_parent_tag_id`（必須、ルートに戻す場合は `null`） |
| `delete_tag` | タグを削除する | `tag_id`（必須） |

要件:

- `create_tag` / `move_tag` では、循環参照（あるタグの子孫を自身の親に設定する等）が発生しないことを検証すること。
- `delete_tag` は、`qa_tag` から参照されている、または子タグが存在するタグの削除をデフォルトで拒否すること（安全側優先）。
- これらのツールは書き込み系操作であるため、`search_knowledge` のような読み取り専用ツールとは異なるアクセス制御の検討が必要（Open Issue #4と合わせて検討）。
- 参照資料の設計方針（Knowledge MCPは「検索実行」に専念し、周辺機能は別コンポーネントに任せる）からは責務がやや拡大するため、将来的にタグ管理専用の別MCPサーバへ切り出す可能性も残しておく（Open Issue参照）。

## 7. データ要件

### 7.1 現行スキーマ

```sql
-- 現行 db_nomic/init.sql
qa_original(uuid TEXT PK, question_text TEXT, answer_text TEXT, category_id INTEGER)
question_altered(id SERIAL PK, qa_id TEXT, text TEXT, embedding VECTOR(768))
category(id INTEGER PK, name TEXT)
```

### 7.2 課題

- `title` に相当するカラムが存在しない（現行 `exportjson_withguid.json` には `title` フィールドがあるが、DB投入時に破棄されている）。
- `tags` に相当するカラム・テーブルが存在しない（同様に `tags` 配列がJSON側にはあるが、DBには反映されていない）。
- そのため、現行の pgvector を Knowledge MCP のデータソースとしてそのまま使うと、共通 Document モデルが要求する `title` と `metadata.tags` を返せない。

### 7.3 スキーマ拡張案（要件レベル）

- `qa_original` テーブルに `title TEXT` カラムを追加する。
- タグは、タグ自体の管理機能（タグの木構造化等）が将来的に必要になる可能性があるため、`tags TEXT[]` のような配列カラムではなく、**`tag` マスタテーブル（自己参照の `parent_tag_id` を持つ）と `qa_tag` 関連テーブルによるリレーショナル構造**を採用する（ADR-0005）。これにより、タグのリネームや将来の階層化（親子関係の設定）をタグマスタの更新のみで完結できる。
- 追加したカラム・テーブルへの既存データの補完は、既存投入元データ（`data/exportjson_withguid.json`）から再投入するバッチ処理が必要になる。この処理は既存の `seed_helpers.py` 相当の仕組みを拡張する想定。タグについては、まずユニークなタグ名を `tag` テーブルに投入し、その後QAレコードとの紐付けを `qa_tag` に投入する2段階の処理が必要になる。
- タグの階層構造（`parent_tag_id`）を用いた検索（親タグ指定時の子孫タグ展開等）はMVPのスコープ外とし、列の用意のみ行う（13章 Open Issue参照）。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | `search_knowledge` 呼び出しからレスポンスまで（embedding計算・ネットワーク往復を除くDB検索処理）を目安として1秒以内（暫定目標値、詳細設計時に見直し） |
| 同時実行 | 既存アプリと同程度（数〜数十セッション）の同時利用を想定 |
| 可用性 | 社内利用ツールとして単一インスタンス構成で可とし、冗長化・自動フェイルオーバーは対象外とする |
| ログ | クエリ内容・ヒット件数・処理時間・エラーを記録する。既存 `app/src/log` のロギング方針との整合を取る |
| 監視 | ヘルスチェック手段（MCPリソースまたはHTTPエンドポイント）を用意し、`docker-compose.yml` の `healthcheck` に登録できるようにする |
| セキュリティ | 社内ネットワーク内での利用を前提としたアクセス制御を行う（具体的な認証方式は Open Issue）。将来 Bedrock/OpenAI 等の外部APIを利用する構成に切り替わる場合、ナレッジ内容が外部送信される可能性があるため、情報の機密区分の確認を要件として明記する |
| 保守性・拡張性 | Repository / Document をインターフェースとして抽象化し、新規データソース追加時に `SearchService` および `search_knowledge` ツールの変更が不要な構成とする |

## 9. インフラ・実行環境要件

### 9.1 デプロイ構成

- ADR-0001（配置）、ADR-0002（実行形態）に基づき、chatbot_invitro リポジトリ直下に新規ディレクトリ（例: `knowledge_mcp/`）を追加し、独立した Docker コンテナとして `docker-compose.yml` に新規サービスを追加する。
- 既存 `db`（chatbot_db, pgvector）サービスに対し、`depends_on` で起動順序を制御し、`DATABASE_URL` 相当の接続情報を環境変数経由で受け渡す。

**docker-compose.yml への追加イメージ（例、最終形は詳細設計フェーズで確定）**

```yaml
  knowledge_mcp:
    build: ./knowledge_mcp
    container_name: chatbot_knowledge_mcp
    ports:
      - "${KNOWLEDGE_MCP_PORT:-8100}:8100"
    environment:
      - DATABASE_URL=postgresql://postgres:postgres@db:5432/chatbot
      - LMSTUDIO_EMBEDDING_URL=${LMSTUDIO_EMBEDDING_URL}
      - MODEL_EMBEDDING=${MODEL_EMBEDDING}
    depends_on:
      db:
        condition: service_healthy
```

### 9.2 ディレクトリ構成（要件レベルの想定案）

```
chatbot_invitro/
├── app/                 … 既存 FastAPI アプリ
├── front_dev/            … 既存デバッグUI
├── knowledge_mcp/        … 新設: Knowledge MCP サーバ
│   ├── src/
│   │   ├── mcp/          … MCPサーバ定義・ツール定義
│   │   ├── services/     … SearchService
│   │   ├── repository/   … Repository抽象＋QARepository
│   │   └── models/       … 共通Documentモデル
│   └── tests/
├── docs/
│   ├── requirement/
│   └── adr/
└── docker-compose.yml
```

### 9.3 環境変数（想定、詳細設計時に確定）

| 変数名 | 説明 |
|---|---|
| KNOWLEDGE_MCP_PORT | Knowledge MCP サーバの待受ポート |
| DATABASE_URL | 既存 chatbot_db への接続文字列（既存appと共有） |
| LMSTUDIO_EMBEDDING_URL / MODEL_EMBEDDING | クエリのベクトル化に用いる既存embedding APIの接続情報（既存appと共有） |

## 10. 既存システムとの関係・影響範囲

- 既存 `app/src/db.py` の `search_similar` はそのまま残す（並行運用）。Knowledge MCP サーバへの切り替えタイミングは Open Issue とする。
- 既存 chatbot_db のスキーマ拡張（title / tags カラム追加）は既存アプリの動作に影響しない設計とする（既存クエリはカラム追加の影響を受けない）。
- 既存 `.env` / `docker-compose.yml` の変更が発生するため、README の利用手順（利用前の手順1〜3）にも追記が必要になる。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] `search_knowledge` ツールが MCP クライアントから呼び出せる。
- [ ] 既存 `data/eval_queries.csv` を用いた MRR 評価で、既存 `search_similar` と同等以上の精度を確認できる。
- [ ] レスポンスの `metadata` に `title` / `tags` / `category` / `guid` が正しく含まれる。
