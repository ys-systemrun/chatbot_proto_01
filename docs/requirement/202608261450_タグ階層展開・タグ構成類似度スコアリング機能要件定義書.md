# タグ階層展開・タグ構成類似度スコアリング機能 要件定義書

- 文書番号: REQ-202608261450
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `knowledge_mcp`（`search_knowledge`ツールの検索・スコアリングロジック）
- 変更なしのコンポーネント: `knowledge_mcp`のDBスキーマ（`tag`/`qa_tag`テーブルの構造は変更しない）、`tag_selector_mcp`、`agent_invitro`のコード自体（呼び出し方は変更しないが、挙動の変化を受ける）
- 参照資料: `docs/requirement/202608041002.md`（Knowledge MCPサーバ要件定義書）、`docs/requirement/202608261330_会話タグ管理機能要件定義書.md`、ADR-0005、ADR-0009、ADR-0010、ADR-0049、ADR-0057
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照

## 1. 目的

`knowledge_mcp`の`search_knowledge`ツールにおけるタグによる検索・ランキングの精度を高めるため、次の2点を実現する。

1. タグは親子階層（`tag.parent_tag_id`）を持つが、現状（ADR-0005）は「指定タグ名との完全一致」でのみ絞り込みに使われ、階層関係は検索に反映されていない。子タグで検索した場合に、その親タグ（より上位の分類）に紐づくQAも検索対象に含める。
2. 現状の`tags`引数はAND条件（指定した全タグを持つQAのみに絞り込む）であり、指定タグ数が増えるほど該当件数が0件に近づきやすい。QAが持つタグの構成（複数タグの組み合わせ）が入力タグの構成に近いほど、そのQAを検索結果の上位に取れるようにする（完全一致でなくても、タグの重なりが多いQAほど優先されるようにする）。

これにより、1回のQAが複数タグを持つ場合や、検証機能（`docs/requirement/202608260909_質問タグ情報源検索精度検証機能要件定義書.md`）・会話タグ管理機能（`docs/requirement/202608261330_会話タグ管理機能要件定義書.md`）のように複数タグ（既存タグ＋新規タグ、または会話タグ）を同時に検索へ渡したいケースで、AND完全一致方式では取得できなかった「タグ構成が近いQA」を、より自然な形で検索結果に反映できるようにする。

## 2. 背景・参照資料

- `tag`テーブルは`parent_tag_id`による自己参照の親子構造を持つ（ADR-0005）。しかし同ADRは「本ADRの時点ではツリー構造を用いた検索（親タグ指定時に子タグも含めて検索する等）の実装はスコープ外とし、将来の拡張ポイントとして列を用意するに留める」「`search_knowledge`の`tags`フィルタは、MVPでは指定されたタグ名との完全一致検索のみとし、階層を辿った祖先/子孫タグの展開は行わない」と明記しており、本書はこのADR-0005が残した課題（Open Issue）に着手するものである。
- `search_knowledge`の`tags`引数は、`QARepository.search`（`knowledge_mcp/src/knowledge_mcp/repository/qa_repository.py`）において「指定タグをすべて持つQAのみに絞り込む（完全一致・AND条件）」として実装されている。
- ADR-0057（会話タグ管理機能、`agent_invitro`）は、このAND条件により「マージ後のタグ集合をそのまま1回の`tags`引数として渡すと、タグ数が増えるほど『全タグを同時に持つQA』は少なくなり、会話が進むほど検索結果が0件に近づくリスクがある」という制約を発見し、対応として「タグ1件につき1回`search_knowledge`を呼び出し、結果をQA単位で統合する」というワークアラウンド（`agent_invitro/src/tags.py`の`search_with_merged_tags`、実装済み）を採用した。同ADRは、この制約の根本的な解決策として「`search_knowledge`をOR条件や部分一致条件に対応させる」案を検討したが、当時のスコープ（`knowledge_mcp`は変更しない）に反するため見送っていた。
- 発注者から、次の2つの要望が示された。
  1. 「1つのQAは複数のタグを持つので、入力タグの構成と近い構成でタグ群を持つQAが優先的に取れてくるようにしたい」
  2. 「タグは親子関係を持つが、子タグで検索する場合は同時に親タグでも検索していることにし、子タグと紐づいているQAは同時に親タグにも紐づいていてほしい」
- 発注者への確認の結果、本機能は`search_knowledge`全体（`agent_invitro`のチャット生成、検証機能、その他将来の呼び出し元すべて）に適用する基本挙動の変更として実装する方針とした（2章の回答1）。これにより、ADR-0057のワークアラウンド（タグ別複数回呼び出し）が不要になる可能性がある（10章参照）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| タグ閉包（クロージャ） | あるタグ集合に対して、各タグ自身とその祖先タグ（`parent_tag_id`を辿って到達できるすべての上位タグ）をすべて加えた集合。本書が新設する概念 |
| 入力タグ閉包 | `search_knowledge`の`tags`引数（タグ名の配列）を`tag`テーブルで名前解決した上で計算したタグ閉包 |
| QAタグ閉包 | あるQAが`qa_tag`で直接紐づいているタグ集合に対して計算したタグ閉包 |
| タグ類似度 | 入力タグ閉包とQAタグ閉包の間で計算する集合の類似度（Jaccard係数、6.2節） |
| 埋め込み類似度 | 既存の`distance_to_score`（`1 / (1 + distance)`）によるベクトル距離ベースのスコア。変更しない |
| 総合スコア | タグ類似度と埋め込み類似度を重み付き合成したスコア。`search_knowledge`が返す`score`フィールドの新しい意味（6.3節） |
| 候補プール | 総合スコアを計算する前に、埋め込み類似度（ベクトル近傍検索）で一次的に絞り込むQAの集合（6.4節） |

## 4. スコープ

### 4.1 対象範囲（MVP）

- `knowledge_mcp`の`QARepository.search`（および`SearchService`）のタグ絞り込み・ランキングロジックを変更する。
  - 指定タグ（および指定タグの祖先）とQAのタグ（およびQAのタグの祖先）を、それぞれタグ閉包に展開する（6.1節）。
  - 両者のタグ閉包間のJaccard類似度を「タグ類似度」として算出する（6.2節）。
  - タグ類似度と既存の埋め込み類似度を重み付き合成した「総合スコア」でランキングする（6.3節）。
  - `tags`引数は、これまでの「絞り込みフィルタ（AND条件、該当しないQAはヒットしない）」から「ランキングに反映するシグナル（ソフトな優先度、タグの重なりがなくても埋め込み類似度のみで結果に含まれ得る）」へ意味を変更する（6.3節）。
- `tag`/`qa_tag`テーブルのスキーマは変更しない（`parent_tag_id`は既存のまま利用する）。タグの登録・階層編集（`create_tag`/`move_tag`等）のAPI・挙動も変更しない。
- `search_knowledge`のMCPツール入出力スキーマ（`query`/`top_k`/`tags`/`category`/`min_score`、および`results`の`id`/`source_type`/`title`/`content`/`score`/`metadata`）の型定義自体は変更しない。`score`の算出方法が変わる点、および`metadata`にスコア内訳を追加する点が変更点である（6.3節）。
- 適用範囲は`search_knowledge`の全呼び出し元（`agent_invitro`のチャット生成・ReActエージェント、`web_backend`の検証機能）とする（2章 回答1）。

### 4.2 対象外（将来検討・別スコープ）

- `tag`テーブル自体への変更（例: `qa_tag`への祖先タグ行の自動生成によるデータの非正規化）は行わない。祖先タグの展開は検索時に動的に計算する（ADR-0058）。
- `QARepository`以外のリポジトリ（将来のPDF/Manual等、`SearchService`が複数リポジトリを束ねる設計、`search_service.py`のコメント参照）へのタグ類似度スコアリングの適用は、それらのリポジトリが実装される際に別途検討する。
- タグ類似度・埋め込み類似度の重み付け（6.3節の`w`）を画面から動的に調整する機能は設けない。MVPでは環境変数による固定値とする。
- `agent_invitro`側の実装（ADR-0057の`search_with_merged_tags`によるタグ別複数回呼び出しワークアラウンド）の見直し・簡素化は、本書のスコープでは行わない。本書による`knowledge_mcp`側の変更が、そのワークアラウンドの必要性にどう影響するかは10章で整理し、対応要否は別途判断する。
- 評価用CLIスクリプト（`web_backend/src/main/evaluate.py`）は、現状`search_knowledge`を経由せず`DB.search_similar`を直接呼び出しているため、本書の変更の影響を受けない。評価スクリプトを新しいスコアリング方式に合わせて更新するかどうかは別途検討する（12章 Open Issue #5）。

## 5. 全体アーキテクチャ

### 5.1 変更箇所

```
呼び出し元（agent_invitro / web_backend、変更なし）
        │ MCP: search_knowledge(query, tags, category, top_k, min_score)
        ▼
knowledge_mcp
  ├─ SearchService.search（変更なし: 複数リポジトリの結果を集約）
  └─ QARepository.search（変更: タグ閉包展開・タグ類似度・総合スコア算出を追加）
        │
        ▼
  chatbot データベース（tag / qa_tag / question_altered / qa_original、スキーマ変更なし）
```

### 5.2 処理の流れ（`QARepository.search`内、概念）

1. `tags`引数（タグ名の配列）を`tag`テーブルで名前解決し、タグIDの集合を得る。解決できない名前（`tag`テーブルに存在しない名前）は無視する（`select_tags`が未知の`tag_id`を無視する既存の方針、`InferenceEngine._parse_response`と同様の考え方）。
2. 各タグIDについて、祖先タグ（`parent_tag_id`を再帰的に辿った上位タグすべて）を含む「入力タグ閉包」を計算する（6.1節）。
3. 埋め込みベクトル距離による近傍検索で、候補プール（`top_k`より多めの件数、6.4節）を取得する。
4. 候補プールの各QAについて、`qa_tag`から直接紐づくタグを取得し、同様に祖先タグを含む「QAタグ閉包」を計算する。
5. 入力タグ閉包とQAタグ閉包からタグ類似度（Jaccard係数）を算出する（6.2節）。
6. 埋め込み類似度とタグ類似度を重み付き合成し、総合スコアを算出する（6.3節）。
7. 総合スコアが`min_score`以上のQAを、総合スコア降順で`top_k`件に整形して返す。

## 6. 機能要件

### 6.1 タグ閉包（祖先タグの動的展開）

- あるタグ集合のタグ閉包 = 集合内の各タグ自身 ∪ 各タグの祖先タグすべて（`parent_tag_id`を根に達するまで再帰的に辿る）。
- 祖先タグの展開は検索の都度、SQL上で計算する（`qa_tag`テーブルへの祖先タグ行の事前挿入は行わない、ADR-0058）。概念的なSQLは次の通り（実装フェーズで最終確定する）。

```sql
WITH RECURSIVE tag_closure(tag_id, closure_id) AS (
    SELECT id, id FROM tag                      -- 自分自身を含む
    UNION ALL
    SELECT tc.tag_id, t.parent_tag_id
    FROM tag_closure tc
    JOIN tag t ON t.id = tc.closure_id
    WHERE t.parent_tag_id IS NOT NULL
)
SELECT tag_id, array_agg(DISTINCT closure_id) AS closure
FROM tag_closure
GROUP BY tag_id;
```

- 「入力タグ閉包」「QAタグ閉包」の両方に同じ展開を適用する。これにより、次の両方の要望を1つの仕組みで満たす。
  - 子タグで検索した場合、親タグにのみ紐づくQA（子タグへの直接の紐づけを持たない）も、入力タグ閉包に親タグが含まれることで一致対象になる（要望2「子タグで検索する場合は同時に親タグでも検索している」に対応）。
  - 子タグに紐づくQAは、QAタグ閉包に親タグが含まれるため、親タグで検索した場合にも一致対象になる（要望2「子タグと紐づいているQAは同時に親タグにも紐づいていてほしい」に対応）。
- タグの階層が深い場合の閉包計算のパフォーマンスは8章で扱う。

### 6.2 タグ類似度（Jaccard係数）

- 入力タグ閉包を`Q`、QAタグ閉包を`T`とすると、タグ類似度は次のJaccard係数で算出する。

```
tag_similarity(Q, T) = |Q ∩ T| / |Q ∪ T|
```

- `tags`引数が指定されない、または空配列の場合（`Q`が空集合）、タグ類似度は算出せず、6.3節の総合スコアは埋め込み類似度のみとする（`tags`未指定の既存の呼び出し元に対する後方互換性を保つため。`tags=[]`と`tags`未指定は同じ扱いとする。これにより既存の要件定義書202608260909 12章Open Issue #1「`tags=[]`と`tags`未指定の扱いの一致確認」は本書により解消される）。
- QAが1件も`qa_tag`を持たない場合（`T`が空集合）、`Q`が非空であれば`tag_similarity = 0`（重なりなし）として扱う。

### 6.3 総合スコア（タグ類似度と埋め込み類似度の合成）

- 総合スコアは次の重み付き線形結合で算出する。

```
combined_score = (1 - w) * embedding_score + w * tag_similarity
```

- `w`（タグ類似度の重み、0.0〜1.0）は`knowledge_mcp`の環境変数`TAG_SIMILARITY_WEIGHT`で指定する（既定値`0.5`。8章）。
- `tags`が未指定・空配列の場合（6.2節）は`combined_score = embedding_score`とする（`w`を適用しない。タグを使わない呼び出しは従来と同じ挙動になる）。
- `search_knowledge`が返す`results[].score`は、この`combined_score`とする（既存の出力スキーマの型は変更しない、`number`型のまま）。
- 検証機能（202608260909）・会話タグ管理機能（202608261330）のように、担当者やログが「なぜこの順位になったか」を確認できることが望ましいため、`results[].metadata`に次の内訳を追加する（`metadata`は既存スキーマ上`object`型で自由記述のため、追加は出力スキーマの構造変更にあたらない）。

```json
{
  "embedding_score": 0.83,
  "tag_similarity": 0.40,
  "tag_similarity_weight": 0.5
}
```

- `min_score`は、この`combined_score`に対して適用する（既存と同じ意味づけ: `combined_score >= min_score`のQAのみを返す）。

### 6.4 候補プール（`top_k`とのAND条件廃止に伴う取得件数の扱い）

- 従来の実装は、埋め込みベクトルの近傍検索（`ORDER BY question_altered.embedding <=> query LIMIT top_k`）の`LIMIT`をそのまま最終的な返却件数として使っていた（タグはAND条件のWHERE句として先にSQLレベルで絞り込んでいたため、`LIMIT`後の並べ替えは不要だった）。
- 本書の変更により、タグはWHERE句によるハードな絞り込みではなくスコアへの加点要素になるため、埋め込み類似度だけでは`top_k`に入らないQAが、タグ類似度により総合スコアで上位に入る可能性がある。したがって、埋め込みベクトルの近傍検索は`top_k`件ちょうどではなく、より多めの「候補プール」を取得し、その中で総合スコアを計算してから`top_k`件に絞り込む2段階の処理にする。
- 候補プールの件数は、`knowledge_mcp`の環境変数`SEARCH_CANDIDATE_POOL_SIZE`で指定する（既定値`max(top_k * 10, 50)`。8章）。
- 候補プールに入らなかったQA（埋め込み類似度が低く、かつ候補プール件数の外側にあるQA）は、タグ類似度がどれだけ高くても本書の変更では検索結果に浮上しない。この制約は8章・12章で扱う。

## 7. データ要件

- 本書は`tag`/`qa_tag`テーブルのスキーマを変更しない。既存のマイグレーション（ADR-0005由来）・タグ管理API（ADR-0006）・データ（既存タグの`parent_tag_id`）をそのまま利用する。
- 新規テーブル・新規カラムは発生しない。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | `QARepository.search`のSQLに、タグ閉包計算（`WITH RECURSIVE`）・候補プールの取得・総合スコア計算が追加されるため、既存より処理コストが増える。実装フェーズで、想定データ量（タグ数・QA件数、12章Open Issue #4）に対する応答時間を計測し、`SEARCH_CANDIDATE_POOL_SIZE`の既定値・`tag.parent_tag_id`へのインデックスの要否を確定する |
| 後方互換性 | `tags`引数を指定しない既存の呼び出し（`min_score`のみで埋め込み類似度によるランキングを行う呼び出し）は、本書の変更後も同じ結果になる（6.2節・6.3節） |
| 設定 | `TAG_SIMILARITY_WEIGHT`・`SEARCH_CANDIDATE_POOL_SIZE`は`knowledge_mcp`の環境変数として追加し、ローカル`docker-compose`環境・AWS環境の両方に設定する |
| 監視・ログ | タグ閉包計算・候補プール取得のいずれかで異常（想定外の階層深さ、想定外の候補プール0件等）が発生した場合、既存の`search_knowledge`のログ方針に準じてログへ記録する（詳細は実装フェーズで確定） |

## 9. インフラ・実行環境要件

- ローカル`docker-compose`環境: `knowledge_mcp`サービスの環境変数に`TAG_SIMILARITY_WEIGHT`（既定値`0.5`）・`SEARCH_CANDIDATE_POOL_SIZE`（既定値は`top_k`依存のため、`knowledge_mcp`アプリケーション側の既定値として実装する。環境変数で明示的に上書き可能にする）を追加する。
- AWS環境: `terraform/main/app/main.tf`の`module`（`knowledge_mcp`のAWS上のサービス）の環境変数に同様の設定を追加する。新規のネットワーク経路・新規のAWSリソースは発生しない（`knowledge_mcp`自体のコンピュート・DB接続は既存のまま）。

## 10. 既存システムとの関係・影響範囲

- `tag_selector_mcp`（`select_tags`）には変更を加えない。タグの選択方式（Alias辞書＋LLM一段階選択、ADR-0009）・レスポンス形式（ADR-0010）は本書の対象外である。
- `agent_invitro`のコード自体は変更しないが、次の2点で挙動に影響がある。
  1. `search_knowledge`が返す`score`の意味が変わる（埋め込み類似度のみ→総合スコア）。`agent_invitro`側で`score`をしきい値判定や表示に使っている箇所（`min_score`環境変数等）は、本書の変更後の意味で動作することになる。
  2. ADR-0057の`search_with_merged_tags`（`agent_invitro/src/tags.py`）は、AND条件によるタグ数増加時の0件化を避けるために「タグ別複数回呼び出し＋統合」というワークアラウンドを実装済みである。本書により`tags`引数がソフトなランキングシグナルに変わるため、このワークアラウンドを使わずマージタグ全件を1回の`tags`引数で渡しても、以前のような0件化のリスクは大幅に下がると見込まれる。ただし、本書のスコープでは`agent_invitro`側の実装変更（ワークアラウンドの単純化）は行わない。要否・実施タイミングは別途判断する（12章 Open Issue #1）。
- 検証機能（202608260909、ADR-0048〜0050）・検証機能の既存タグ入力拡張（`docs/requirement/202608261510_検証機能既存タグ入力・新規タグ記録機能要件定義書.md`）は、本書の変更を前提として設計する（ADR-0060参照）。
- QA・タグ管理UI（`QaListPage`/`TagTreePage`等）・その他の`knowledge_mcp`のツール（`list_qa`/`list_tags`/タグ管理系ツール）には変更を加えない。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] 子タグのみを`tags`引数に指定して`search_knowledge`を呼び出すと、そのタグの祖先（親タグ）にのみ直接紐づくQA（子タグへの直接の紐づけがない）も検索結果に含まれる。
- [ ] 親タグを`tags`引数に指定して`search_knowledge`を呼び出すと、その子タグにのみ直接紐づくQAも検索結果に含まれる。
- [ ] 入力タグと重なりが多いタグ構成を持つQAほど、重なりが少ない・重なりがないQAより`score`が高くなる（重なりがなくても埋め込み類似度のみで結果に含まれ得る）。
- [ ] `tags`を指定しない呼び出しの結果（順位・`score`）が、本書の変更前後で変わらない。
- [ ] `results[].metadata`に`embedding_score`・`tag_similarity`・`tag_similarity_weight`が含まれる。
- [ ] 既存の呼び出し元（`agent_invitro`のチャット生成、検証機能）が、コード変更なしに動作し続ける（MCPツールの入出力スキーマの型は変更されていないため）。
- [ ] ローカル`docker-compose`環境・AWS環境の両方で本機能が動作する。

## 12. Open Issues（要追加確認事項）

1. **`agent_invitro`側ワークアラウンド（ADR-0057）の見直し要否**: 本書により`tags`引数のAND完全一致が廃止されるため、ADR-0057が採用した「タグ別複数回呼び出し＋統合」（`agent_invitro/src/tags.py`の`search_with_merged_tags`）は、単純化（マージタグ全件を1回の`tags`引数にまとめる）できる可能性が高い。本書のリリース後、実際の検索結果・レイテンシを比較評価した上で、別途ADRを起票して見直すかどうかを判断する必要がある。
2. **`TAG_SIMILARITY_WEIGHT`の適正値**: 既定値`0.5`は暫定値であり、実際のQA・タグデータでの検索精度評価（`evaluate.py`相当、または検証機能を用いた目視評価）を通じて調整する必要がある。
3. **`SEARCH_CANDIDATE_POOL_SIZE`の適正値**: 既定値`max(top_k * 10, 50)`は暫定値である。QA件数・タグの階層の深さ・分布によって、この値が小さすぎるとタグ類似度の高いQAを取りこぼし、大きすぎると性能に影響する。実データでの計測が必要。
4. **想定QA件数・タグ件数の規模**: 8章の性能要件・12章Open Issue #3の適正値検討の前提として、現在および将来想定されるQA件数・タグ件数（特にタグ階層の深さ）の規模感を発注者に確認する必要がある。
5. **評価スクリプト（`evaluate.py`）との整合**: `evaluate.py`は現状`search_knowledge`を経由しないため本書の対象外としたが（4.2節）、新しいスコアリング方式の効果を定量的に評価したいというニーズが生じた場合、`evaluate.py`を`search_knowledge`経由に変更する、または同等のロジックをスクリプト側にも実装するかどうかを別途検討する必要がある。
6. **タグ閉包の循環参照**: `tag.move_tag`は循環参照を防止する検証を持つため（`TagRepository._assert_no_cycle`）、通常運用ではタグ階層に循環は発生しない前提とする。万一データ不整合により循環が生じた場合の`WITH RECURSIVE`の無限ループ対策（深さ上限等）は実装フェーズで確認する。
