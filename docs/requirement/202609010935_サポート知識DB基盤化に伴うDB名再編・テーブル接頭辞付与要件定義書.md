# サポート知識DB基盤化に伴うDB名再編・テーブル接頭辞付与 要件定義書

- 文書番号: REQ-202609010935
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `docker-compose.yml`（サービス/ホスト名・接続文字列）, `terraform`（`chatbot.sql`, `modules/database` の `db_name`）, `db_hiroba_qa_init`（migrations・src・tests）, `knowledge_mcp`（repository・tests）, `web_backend`（`db.py`・`export/tables.py`・`export_controller.py`・API経路）, `tag_selector_mcp`（`tag_metadata_repository.py`）, `front_dev`（ルート・`api.ts`・feature・domain）, `README.md`・`.env.example`, `terraform/deploy`

## 1. 目的

現在の QA/ナレッジ用データベースは、単一のデータソース（ユーザーサポート「維津美の広場」由来のQAデータ）専用の構成になっている。今後、**維津美の広場とは異なるデータソースを追加**し、PostgreSQL上でデータソースごとに実データベースを分離して、それぞれ独立したマイグレーション・シーディング機構で管理していきたい。

このため、単一データソース前提の命名を「サポート知識（support knowledge）を載せる基盤サーバ＋データソース別の実データベース」という構造に再編する。具体的には次の3層のリネームを行う。

1. **PostgreSQLサーバ（＝docker-composeサービス/ホスト名）** を、複数データソースDBを載せる基盤として `db_hiroba_qa` → **`db_support_knowledge`** にリネームする。
2. **維津美の広場由来データの実データベース名** を `chatbot` → **`db_hiroba_qa`** にリネームする（将来の別ソースは別実DBとして同一サーバ上に追加する）。
3. **維津美の広場由来の6テーブル** に `hiroba_` 接頭辞を付与し、データソースを識別可能にする。

あわせて、エクスポート済みの `terraform/chatbot.sql` を新命名に変換し、terraformで基盤を作り直したあと**そのまま再インポートして復元できる**状態にする。

> 補足: 本再編は「実DB名が `db_hiroba_qa` かつテーブル接頭辞も `hiroba_`」という一見冗長な命名になるが、これは意図的である。実DB名はデータソースの分離単位（別ソース＝別DB）を、テーブル接頭辞はデータソースの出自を、それぞれ独立して明示する。将来、複数ソースのテーブルが同一DB内に同居する運用に移行した場合でも接頭辞で識別できる余地を残す。

## 2. 背景・参照資料

### 2.1 現状の命名構造（調査結果）

リポジトリ調査の結果、「`db_hiroba_qa`」という語は**3つの別物**を指していることが判明した。ユーザー指示の「`db_hiroba_qa` ⇒ `db_support_knowledge`」を正しくマッピングするうえで前提となる。

| 実体 | 現在の名前 | 定義箇所 |
|---|---|---|
| PostgreSQLサーバ / docker-composeサービス / 接続ホスト名 | `db_hiroba_qa` | `docker-compose.yml`（`container_name: chatbot_db`、`image: pgvector/pgvector:pg15`） |
| 維津美の広場QAデータの**実データベース名** | `chatbot` | ローカル: `POSTGRES_DB: chatbot` / AWS: terraform `var.db_name`（既定`"chatbot"`）/ 環境変数 `CHATBOT_DB_NAME`（既定`"chatbot"`） |
| 初期化（マイグレーション・シード・インポート）サービス/ディレクトリ/ECSタスク | `db_hiroba_qa_init` | ディレクトリ `db_hiroba_qa_init/` + ECSタスク定義 + ECRイメージ `db-hiroba-qa-init` |

現在の接続文字列は `postgresql://<role>@db_hiroba_qa:5432/chatbot`（ホスト=`db_hiroba_qa`、DB=`chatbot`）である。

### 2.2 対象6テーブルの構造（`terraform/chatbot.sql` 実測）

`terraform/chatbot.sql`（6150行、`CREATE TABLE IF NOT EXISTS` + `INSERT INTO "…" VALUES` 形式。`pg_dump`ではなく `web_backend` のエクスポート機能が生成する schema+data スクリプト。**DB名・`CREATE DATABASE`・`\connect`・`GRANT`・`CREATE ROLE`・`COPY` はいずれも含まない**）で確認した6テーブルと外部キーは次の通り。

| 変更前テーブル | 変更後テーブル | 主な制約 | 外部キー参照 | データ行数(目安) |
|---|---|---|---|---|
| `category` | `hiroba_category` | `id INTEGER PRIMARY KEY` | なし | 8 |
| `qa_original` | `hiroba_qa_original` | `uuid TEXT PRIMARY KEY` | なし | 約824 |
| `tag` | `hiroba_tag` | `id SERIAL PRIMARY KEY` | `parent_tag_id → tag(id)`（自己参照） | 31 |
| `question_altered` | `hiroba_question_altered` | `id SERIAL PRIMARY KEY`（`embedding VECTOR`列を持つ） | なし（`qa_id`列はあるがFKなし） | 約5115 |
| `tag_alias` | `hiroba_tag_alias` | `id SERIAL PRIMARY KEY`, `alias UNIQUE` | `tag_id → tag(id)` | 0（データなし） |
| `qa_tag` | `hiroba_qa_tag` | `PRIMARY KEY(qa_id, tag_id)` | `qa_id → qa_original(uuid)`, `tag_id → tag(id)` | 99 |

作成順（FK依存順）: `category` → `qa_original` → `tag` → `question_altered` → `tag_alias` → `qa_tag`。この順序はリネーム後も維持する。

### 2.3 テーブル名がハードコードされている前提

対象6テーブル名は、**中央集約された定数モジュールが存在せず**、各SQLクエリ・DDL・テストにインラインのリテラル文字列としてハードコードされている。したがって全出現箇所を個別に変更する必要がある。詳細は「10. 既存システムとの関係・影響範囲」に列挙する。

### 2.4 発注者との確認済み方針

1. **命名モデル**（1章の3層リネーム）で確定。実DB名は `db_hiroba_qa`、サーバ名は `db_support_knowledge`、テーブルは `hiroba_` 接頭辞。
2. **`chatbot` を冠する識別子は据え置き**。変更するのはDB名の「値」とテーブル接頭辞のみであり、ロール名（`chatbot_app`/`chatbot_migrator`）・シークレット名・環境変数名（`CHATBOT_*`）・ダンプファイル名（`chatbot.sql`）・定数名（`CHATBOT_TABLES`）の**名称自体は変更しない**（`CHATBOT_DB_NAME` の“値”は `chatbot`→`db_hiroba_qa` に変わるが、変数名は据え置く）。
3. **移行方式は「再構築＋再インポートのみ」**。既存マイグレーションファイルは新テーブル名で書き換え、terraformでDBを作り直し（destroy+apply）、変換済み `chatbot.sql` を再インポートして復元する。既存DBを無停止で改名する `ALTER TABLE … RENAME` マイグレーションは作成しない。
4. **API/UI名も新テーブル名に揃える**。`front_dev` のルート・APIパス・応答フィールド名等も新命名に追随させる（DB層のテーブル改名に限定しない）。
5. **conversationデータベースは今回のスコープ外**（`hiroba_` 接頭辞の付与対象ではない）。ただし 2.4-3 の再構築でRDSインスタンスを作り直す場合、同一インスタンス上の会話DBも再投入対象になる点は運用手順として扱う（9章）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| サポート知識基盤（`db_support_knowledge`） | 複数データソースの実DBを載せるPostgreSQLサーバ。ローカルではdocker-composeのサービス名かつ接続ホスト名。AWSではRDSインスタンスに相当（ホスト名はRDSエンドポイント） |
| 維津美の広場QA DB（`db_hiroba_qa`） | 維津美の広場由来QAデータを保持する実データベース。本再編で `chatbot` から改名する |
| `hiroba_`接頭辞 | 維津美の広場由来6テーブルに付与する接頭辞。データソースの出自を識別する |
| 初期化サービス（`db_hiroba_qa_init`） | マイグレーション・シード・インポートを担うワンショットサービス/ECSタスク。**名称は本再編で変更しない** |
| 構文限定置換 | `chatbot.sql`/コード内で、テーブル名として現れる箇所（`CREATE TABLE`/`INSERT INTO "…"`/`REFERENCES <name>(…)` 等）のみを対象とし、列名（`tag_id`, `qa_id`, `parent_tag_id`, `category_id`）やCTEエイリアス（`tag_closure`）を巻き込まない置換方式 |
| 再構築＋再インポート | terraformでDB実体を destroy+apply して作り直し、変換済みダンプ（`chatbot.sql`）を投入して復元する移行方式（ADR-0066の全データインポート経路を利用） |

## 4. スコープ

### 4.1 対象範囲

- **命名再編（1章の3層）**: サーバ/サービス/ホスト名 `db_hiroba_qa`→`db_support_knowledge`、実DB名 `chatbot`→`db_hiroba_qa`、6テーブルへの `hiroba_` 接頭辞付与。
- **`terraform/chatbot.sql` の変換**: 6テーブルの `CREATE TABLE` / `INSERT INTO "…"` / 外部キー `REFERENCES` を新テーブル名へ構文限定置換し、そのまま再インポート可能にする（列名・データ内容は不変）。
- **アプリ/インフラ各層のテーブル名追随**: `db_hiroba_qa_init`（migrations/src/tests）, `knowledge_mcp`（repository/tests）, `web_backend`（`db.py`/`export/tables.py`/`export_controller.py`）, `tag_selector_mcp`（`tag_metadata_repository.py`）の全SQL・DDL・テスト。
- **接続構成の更新**: `docker-compose.yml`（サービス名・全`DATABASE_URL`のホスト部とDBパス部・`depends_on`・`POSTGRES_DB`）, terraform `var.db_name` の既定値, 環境変数 `CHATBOT_DB_NAME` の値, `.env.example`・`README.md` の記述。
- **API/UI名の追随**（発注者方針2.4-4）: `web_backend` のREST APIパス・応答フィールド名、`front_dev` のルート・`api.ts`・feature/domain の該当命名。具体的対象は 6章・10章に列挙する。
- **移行・デプロイ手順の整備**: 再構築＋再インポート手順（ローカル・AWS）を文書化する。

### 4.2 対象外（将来検討・別スコープ）

- **conversationデータベースおよびその配下テーブル**（`conversation`/`message`/`verification_*` 等）への `hiroba_` 接頭辞付与。会話系は維津美の広場由来ではないため対象外（`terraform/conversation.sql` も変換しない）。
- **`chatbot` を冠する識別子の名称変更**（ロール・シークレット・環境変数名・ファイル名・定数名）。発注者方針2.4-2により据え置く。将来 support_knowledge 系へ統一する場合は別途要件化する（Open Issue参照）。
- **既存DBの無停止改名（`ALTER TABLE … RENAME` マイグレーションの追加）**。発注者方針2.4-3により作成しない。
- **新データソース（維津美の広場以外）の追加そのもの**。本書は既存データの命名再編に限定し、別ソースDBの新規追加は将来の別要件とする。
- **複数ソースDBを同一 `db_support_knowledge` サーバ上で運用するための権限設計・監視・バックアップ方針の全面見直し**。今回は既存の役割分離（ADR-0052）をDB名変更に追随させる範囲にとどめる。
- **embedding再計算**。テーブル名変更に伴う `question_altered`（→`hiroba_question_altered`）の `embedding` 列の再計算は不要（データはダンプから復元し内容は不変）。

## 5. 全体アーキテクチャ

### 5.1 命名モデル（変更前 → 変更後）

```
【変更前】
  PostgreSQLサーバ/ホスト: db_hiroba_qa
    └─ 実DB: chatbot
         ├─ category / qa_original / tag / question_altered / tag_alias / qa_tag
    └─ 実DB: conversation（会話・検証。今回対象外）
  初期化サービス: db_hiroba_qa_init

  接続文字列: postgresql://<role>@db_hiroba_qa:5432/chatbot

【変更後】
  PostgreSQLサーバ/ホスト: db_support_knowledge
    └─ 実DB: db_hiroba_qa
         ├─ hiroba_category / hiroba_qa_original / hiroba_tag
         ├─ hiroba_question_altered / hiroba_tag_alias / hiroba_qa_tag
    └─ 実DB: conversation（変更なし）
    └─（将来）実DB: <別ソース>（別マイグレーション・シード機構）
  初期化サービス: db_hiroba_qa_init（名称据え置き）

  接続文字列: postgresql://<role>@db_support_knowledge:5432/db_hiroba_qa
```

ホスト名（`db_hiroba_qa`）が新しい実DB名（`db_hiroba_qa`）に「横滑り」する形になるため、置換作業では**ホスト部とDBパス部を取り違えない**こと（8章・11章のリスクとして明記）。

### 5.2 AWS環境における対応（サーバ名の扱い）

AWSでは接続ホストはRDSエンドポイント（terraformが出力）であり、「`db_hiroba_qa` というホスト名」は存在しない。したがって **サーバ名 `db_hiroba_qa`→`db_support_knowledge` のリネームはローカル docker-compose 限定の変更**である。AWS側で必須なのは実DB名 `chatbot`→`db_hiroba_qa`（`var.db_name`）の変更のみ。RDSリソース名・タグの `db_support_knowledge` への整合は任意（機能に影響しない）とし、本書では必須としない。

## 6. 命名再編仕様

### 6.1 テーブル名マッピング（確定）

| 変更前 | 変更後 |
|---|---|
| `category` | `hiroba_category` |
| `qa_original` | `hiroba_qa_original` |
| `tag` | `hiroba_tag` |
| `question_altered` | `hiroba_question_altered` |
| `tag_alias` | `hiroba_tag_alias` |
| `qa_tag` | `hiroba_qa_tag` |

### 6.2 変更してはならない識別子（誤置換防止リスト）

以下はテーブル名に部分一致するが**改名対象ではない**。構文限定置換で保護すること。

- 列名: `tag_id`, `parent_tag_id`, `qa_id`, `category_id`, `question_text`, `answer_text`, `question_altered_count`（応答フィールドはAPI/UI方針に従い別途扱う。DB列ではない）
- CTE/クエリエイリアス: `tag_closure`（`knowledge_mcp/qa_repository.py` の再帰CTE。テーブルではない）, `question_altered qa` 等の別名
- yoyo管理テーブル: `_yoyo_migration`/`_yoyo_log`/`_yoyo_version`/`yoyo_lock`（別ネームスペース、衝突しない）
- conversation系テーブル: `conversation`/`message`/`verification_*`（対象外）
- `chatbot` を冠する各種識別子（2.4-2、据え置き）

### 6.3 接続文字列・DB名の値

- ローカル `docker-compose.yml`: サービス名 `db_hiroba_qa`→`db_support_knowledge`、`POSTGRES_DB: chatbot`→`db_hiroba_qa`、全 `DATABASE_URL` を `…@db_support_knowledge:5432/db_hiroba_qa` へ、`depends_on` の参照名も更新。会話DB用URL（`…/conversation`）はホスト部のみ更新しDBパスは据え置き。
- terraform: `modules/database/main.tf` の `variable "db_name"` 既定値 `"chatbot"`→`"db_hiroba_qa"`（`aws_db_instance.db_name`・各接続シークレット・`CHATBOT_DB_NAME` 環境変数へ自動伝播）。
- 環境変数 `CHATBOT_DB_NAME`: 既定値/設定値を `chatbot`→`db_hiroba_qa`（変数名は据え置き）。

## 7. `terraform/chatbot.sql` 変換仕様

`chatbot.sql` にはDB名・`CREATE DATABASE` 等が含まれないため、変換は**テーブル識別子のみ**を対象とする。次の3パターンを新テーブル名へ置換する（構文限定置換）。

1. `CREATE TABLE IF NOT EXISTS <name> (` の `<name>`（6箇所）
2. `INSERT INTO "<name>" (` の `<name>`（引用符付き識別子。`category`/`qa_original`(2ブロック)/`tag`/`question_altered`(11ブロック)/`qa_tag` に出現。`tag_alias` はデータなしのため出現しない）
3. 外部キー `REFERENCES <name>(…)` の `<name>`（`REFERENCES tag(id)`×3、`REFERENCES qa_original(uuid)`×1）

- 列名・`VALUES` の値・pgvector埋め込みデータは一切変更しない。
- 変換後も `CREATE EXTENSION IF NOT EXISTS vector;`（先頭行）は維持する。
- 変換は自動スクリプト（構文パターン限定）で行い、変換前後で「CREATE TABLE 6件・INSERT 総ブロック数・REFERENCES 4件」の件数一致を検証する（受け入れ基準11章）。
- **`web_backend/src/export/tables.py` を新テーブル名へ更新すれば、次回以降のエクスポートは新命名の `chatbot.sql` を自動生成する**（`dump.py` は `spec.name` を介した汎用実装のため変更不要）。よって本変換は「既存ダンプの一度きりの移行」であり、恒久対応は `tables.py` 側にある。

## 8. 移行・デプロイ手順（方針）

発注者方針2.4-3「再構築＋再インポートのみ」に基づく。

### 8.1 ローカル（docker-compose）

1. コード・設定・migrations・`chatbot.sql` を新命名へ更新（本書の全対象）。
2. 既存ボリュームを破棄して作り直す（`docker compose down -v` 相当）。`POSTGRES_DB=db_hiroba_qa` で新DBが初期化され、`db_hiroba_qa_init` が新命名のmigration/seedを適用する。
3. 必要に応じて変換済み `chatbot.sql` を全データインポート経路（ADR-0066）で投入する。

### 8.2 AWS

1. 実DB名変更（`var.db_name=db_hiroba_qa`）はRDSの初期データベース名の変更にあたり、`aws_db_instance` の置換（再作成）を伴う。DB用stateレイヤ（ADR-0037）を destroy+apply して作り直す。
2. 作り直したインスタンスに対し、`terraform/deploy` の import-data 経路で変換済み `chatbot.sql` を S3 経由で投入（ADR-0066）。
3. **同一RDSインスタンス上の会話DB（`conversation`）も再作成対象**となるため、`conversation.sql` の再投入も同手順で行う（会話DBの命名自体は変更しない）。
4. `db_hiroba_qa_init` がロール（`chatbot_migrator`/`chatbot_app` 等、名称据え置き）・拡張（pgvector）・権限（GRANT）を新DB `db_hiroba_qa` に対して再設定する。

> 注: RDSインスタンス置換を避けたい場合の代替（初期化コンテナによる `CREATE DATABASE db_hiroba_qa` 方式）は ADR-0069「検討した代替案」に記載する。本書は発注者の「作り直し」方針に従い再構築方式を採用する。

## 9. 非機能要件

| 分類 | 要件 |
|---|---|
| データ保全 | 移行はダンプ（`chatbot.sql`）からの完全復元による。変換は列名・値・件数を保存し、変換前後の件数一致を検証する |
| 一貫性 | テーブル名変更は全コンポーネント（DB初期化・knowledge_mcp・web_backend・tag_selector_mcp・front_dev・chatbot.sql）で同一マッピングを用い、部分適用による不整合（旧名参照の残存）を残さない |
| 冪等性 | 既存の存在チェックによるシード冪等性（ADR-0018）・`IF NOT EXISTS` を新命名でも維持する。ただし旧名テーブルが残るDBに新名DDLを適用すると空の新テーブルが二重生成される罠があるため、移行は必ず作り直し（空DB）から行う |
| 可搬性 | 変換済み `chatbot.sql` はDB名非依存（`\connect`等を含まない）を維持し、任意の実DB（`db_hiroba_qa`）へ投入可能とする |
| アクセス制御 | 既存の役割分離（ADR-0052: migrator/app、ADR-0046: export専用reader）をDB名変更に追随させる。ロール名・権限体系自体は変更しない |
| 停止影響 | AWSはRDSインスタンス置換を伴うため計画停止が発生する。会話DBの再投入を含む復旧手順を事前に確定する |

## 10. 既存システムとの関係・影響範囲

調査で特定した変更対象を層別に示す（`file:line` は調査時点。実装時に再確認する）。

### 10.1 DB名・サーバ名（値・ホスト）

- `docker-compose.yml`: サービス `db_hiroba_qa` 定義、全 `DATABASE_URL`（ホスト部・DBパス部）、`depends_on`、`POSTGRES_DB`。
- `terraform/modules/database/main.tf`: `variable "db_name"` 既定値（`:55`）→ `aws_db_instance.db_name`（`:116`）・接続シークレット（`:144`/`:224`/`:318`）・出力（`:396`）へ伝播。`terraform/main/database/main.tf:72` `CHATBOT_DB_NAME`。
- `.env.example`・`README.md`: ホスト名/DB名/手順記述（`db_hiroba_qa` 表記、psql例、import手順）。
- `db_hiroba_qa_init/src/main.py`: `CHATBOT_DB_NAME` 既定値（`:48`,`:55`）。
- `terraform/deploy`: `_IMPORT_DUMP_DEFAULT`（`commands.py:271`）の論理キー`"chatbot"`・ファイル名`chatbot.sql`は据え置き（2.4-2）。投入先DBは `CHATBOT_DB_NAME` の値変更で追随。

### 10.2 テーブル名（`hiroba_` 接頭辞付与）

- **`db_hiroba_qa_init`**（初期化・シード）:
  - migrations: `0001_initial_schema.sql`（`qa_original`,`category`）, `0002_question_altered_table.py`（`question_altered`）, `0003_add_title_and_tag_tables.sql`（`qa_original`,`tag`,`qa_tag`＋index＋FK）, `0004_add_question_altered_is_primary.sql`, `0005_add_tag_description_and_alias.sql`（`tag`,`tag_alias`＋index＋FK）。**新命名で書き換え**（作り直し前提）。index名（`idx_tag_parent_tag_id` 等）は任意で追随。
  - src: `db.py`（各テーブルの存在チェック/INSERT）, `backfill_title_and_tags.py`（`qa_original`/`tag`/`qa_tag`）, `seed_description_and_aliases.py`（`tag`/`tag_alias`）, `import_data.py` の `CHATBOT_TABLES` リスト（`:38-45`。**`web_backend/src/export/tables.py` と同期必須**）。
  - tests: `tests/test_import_data.py`（期待テーブル一覧`:26-30`、シーケンス名 `public.tag_id_seq`→`public.hiroba_tag_id_seq`、`resync_sequences` 対象）。
- **`knowledge_mcp`**（リポジトリSQL、中央定数なし）:

- **`web_backend`**:
  - `src/db.py`（`search_similar` の `question_altered`/`qa_original` とその列修飾子）。
  - `src/export/tables.py`（`CHATBOT_TABLES` の各 `TableSpec.name` と `_create_ddl` 内の `CREATE TABLE`・FK `REFERENCES`。**恒久対応の要**）。`CONVERSATION_TABLES` は対象外。
  - `src/main/controllers/export_controller.py`（`:48` の `"question_altered"` リテラル）。
  - `src/export/dump.py`: 変更不要（`spec.name` 汎用）。
- **`tag_selector_mcp`**: `infrastructure/repository/tag_metadata_repository.py`（`:53-54` `FROM tag` / `LEFT JOIN tag_alias`）。テストは `FakeDatabase` がSQLを無視するため変更不要。docstring は任意で追随。

### 10.3 API/UI名の追随（発注者方針2.4-4）

DB層のテーブル改名に加えて、対応するHTTP API/フロントエンドの命名を新テーブル名へ揃える。**HTTP契約の変更を伴うため、バックエンド・フロントエンドを同時に更新する**こと。

- `web_backend`: `/api/question_altered*` 等、改名テーブルに対応するAPIパス、および `question_altered_count` 等の応答フィールド名（`qa_controller.py` の `QaSummaryModel` 等）。監査ログのエンティティ種別ラベル（`log_admin_operation(..., "question_altered"/"tag", …)`）の追随要否は詳細設計で確定（Open Issue）。
- `front_dev`: ルート（`routes.tsx` の `/admin/question_altered` 等）、`api.ts` のパス・ダウンロードファイル名、feature ディレクトリ（`feature/question_altered/`）、domain 型（`domain/admin/question_altered.ts`、`question_altered_count` 参照箇所）。フロントは直接DBに触れないため、変更はAPI契約の追随に限られる。

> 注: 6テーブルのうちAPI/UIに露出しているのは主に `question_altered`（言い換え質問文管理）と `tag` 系である。`hiroba_` を付けた命名（例: `/api/hiroba_question_altered`）が過度に冗長であれば、UI表示名は据え置きつつ内部識別子のみ追随させる案も含め、具体的な対応表を詳細設計フェーズで確定する（Open Issue #3）。

### 10.4 影響を受けないことを確認済みの箇所

- `front_dev` は直接DB非依存（DB層の改名のみでは変更不要。API契約を揃える方針2.4-4に限り追随）。
- `web_backend/src/export/dump.py`、`web_backend` のモデル dataclass（テーブル名を持たない）。
- conversation系（`conversation`/`message`/`verification_*`）とその `verification_run_source` はタグ**名**をJSON文字列で保持しFKを持たないため、テーブル改名の影響を受けない。
- yoyo管理テーブル群（別ネームスペース）。

## 12. Open Issues（要追加確認事項）

1. **AWS RDS再構築の停止影響と会話DB再投入**: `var.db_name` 変更はRDSインスタンス置換を伴い、同一インスタンスの会話DBも再作成される。停止時間・会話データ（`conversation.sql`）の最新性確保・切戻し手順を運用計画として確定する。RDS置換を避ける代替（初期化コンテナによる `CREATE DATABASE` 方式、ADR-0069代替案）を採るかは運用要件次第で再検討可能。
2. **監査ログ・エンティティラベルの追随範囲**: `log_admin_operation` のエンティティ種別文字列（`"question_altered"`/`"tag"` 等）を新命名に揃えるか、既存ログとの互換のため据え置くかを確定する。
3. **API/UI命名の具体的対応表**: `hiroba_` 接頭辞をAPIパス・応答フィールドへどこまで反映するか（内部識別子のみか、表示名も含むか）を、冗長性とのバランスを見て確定する（10.3の注）。
4. **`chatbot` 冠識別子の将来的な統一**: 今回据え置くロール/シークレット/環境変数名/ファイル名/定数名を、将来 `support_knowledge` 系へ統一するかは別途要件化する。
5. **index名・シーケンス名の命名規約**: `idx_tag_*`・`public.tag_id_seq` 等を `hiroba_` 付きに揃えるかの規約を確定する（機能影響はないが一貫性のため）。
