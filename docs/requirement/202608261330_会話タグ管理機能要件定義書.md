# 会話タグ管理機能 要件定義書

- 文書番号: REQ-202608261330
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `front_dev`（チャット画面 `/`, `StateContainer`）, `web_backend`（`/api/ask-sl`中継層のスキーマ拡張のみ。処理ロジックは変更なし）, `agent_invitro`（`POST /ask-sl`実装、AWS環境限定, ADR-0043）
- 利用する既存コンポーネント（コード変更なし）: `tag_selector_mcp`（`select_tags`ツール）, `knowledge_mcp`（`search_knowledge`ツール）
- 参照資料: `docs/requirement/202608051636.md`（Tag Selector MCPサーバ要件定義書）, `docs/requirement/202608240949_AWS環境向けChatbotUI・会話評価機能有効化要件定義書.md`, `docs/requirement/202608260909_質問タグ情報源検索精度検証機能要件定義書.md`
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照

## 1. 目的

ChatbotUI（`/ask-sl`）における情報源検索（`knowledge_mcp`の`search_knowledge`）の精度を、会話の文脈（それまでの質問で関連していたタグ）を踏まえて高めることを目的とする。具体的には、次の3点を実現する。

1. クライアント（ブラウザ）側で、「この会話で使っているタグ」をTypeScriptの状態として保持する。
2. チャットのリクエストで、クライアントが保持するタグをbackendへ送り、情報源検索（`search_knowledge`）にもこのタグを反映させる。
3. backendは、クライアント由来のタグと`tag_selector_mcp`（`select_tags`）から得られたタグを突き合わせ、この会話で引き続き使うべきタグを判定してクライアントへ返す。クライアントは次回リクエスト時にこれをそのまま送り返す。

これにより、単発の質問文だけでは`select_tags`が正しいタグを選びきれない場合（指示語・省略を含む質問等）でも、直前までの会話で使われていたタグを検索の絞り込みに活用できるようにする。

## 2. 背景・参照資料

- `tag_selector_mcp`の`select_tags`は、質問文単体から関連タグを`id`/`name`/`score`/`path`で返す（`docs/requirement/202608051636.md`、ADR-0007〜0012）。質問文単体のみを入力とするため、会話の文脈（過去のやり取りで使っていたタグ）は考慮しない。
- `knowledge_mcp`の`search_knowledge`は`tags`引数（タグ名の配列）でQAを絞り込めるが、**指定した全タグを持つQAのみに絞り込むAND条件**である（`knowledge_mcp/src/knowledge_mcp/repository/qa_repository.py`、ADR-0005のタグ関連テーブル方針を踏まえた実装）。本書の要件定義にあたりコードを確認した結果判明した制約であり、5.1節・6.4節の設計に大きく影響する。
- 現在の`POST /ask-sl`（AWS環境, `agent_invitro/src/main/api/server.py`）は、ADR-0043が実装フェーズの選択肢として残していた「単一プロンプト生成方式」を採用した結果、`graph/agent.py`のReActエージェント（ADR-0022、`select_tags`→`search_knowledge`をLLMが自律的に呼ぶ方式）を経由しない**固定シーケンス**になっている。`select_tags`は一切呼ばれておらず、`search_knowledge`も`tags`引数を渡さず（絞り込みなしで）呼び出されている。本書はこの現状の固定シーケンスに手を加える形で要件を定義する（5.1節）。
- `front_dev`の既存チャット画面（`StateContainer.tsx`）は、`summary`（会話要約）を同様の方式ですでに扱っている。`summary`はサーバー側DBに保存されず、`Response.summary`をブラウザ側の状態としてそのまま保持し、次回リクエストの`Request.summary`として送り返す（クライアントエコー方式）。本書のタグ管理も同じ設計思想を踏襲する（2章末尾の確認事項、ADR-0056）。
- 本書作成にあたり、ユーザーに4点を確認し、回答を得た。本書はこの回答を前提に要件を定義する。
  1. 適用範囲 → 「AWS環境（`agent_invitro`）のみ」。ローカル`docker-compose`環境（`web_backend`が`chatbot`データベースへ直接クエリする既存パイプライン。現状`tag_selector_mcp`/`knowledge_mcp`を一切呼んでいない）は対象外とする。
  2. 検索への反映方式 → 「`search_knowledge`に渡すタグは、`select_tags`で得たタグ群とクライアント由来のタグ群をマージしたものとする」。単なるプロンプトでの誘導（ソフト強制）ではなく、確実にマージした集合を検索に使う。
  3. 継続タグ（次の会話でも使うタグ）の判定ロジック → 「まだ決めていない、たたき台を提案してほしい」。本書6.4.3節で判定ロジックの案を提示する。
  4. 永続化範囲 → 「ブラウザ側のみで保持し、サーバー（`conversation`データベース等）には保存しない」（既存`summary`と同一方針）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| 会話タグ | ある会話（`conversation_id`）において、情報源検索の絞り込みに使う・使ってきたタグの集合。クライアント（ブラウザ）が状態として保持する |
| 継続タグ | あるリクエストの処理後、backendが「次回リクエストでも引き続き使うべき」と判定し、クライアントへ返すタグの集合。次回リクエストの会話タグとしてそのまま使われる |
| マージタグ | あるリクエストの処理中に、`select_tags`が返したタグとクライアント由来の会話タグを突き合わせて作る、そのリクエストの情報源検索に実際に使うタグの集合。6.4.3節の判定ロジックにより、その回のレスポンスの継続タグと同一の集合になる |
| `missed_turns` | 会話タグ1件ごとに backend が保持・更新する数値。その会話タグがその回の`select_tags`で再選択されなかった連続回数。6.4.3節参照 |
| クライアントエコー方式 | サーバー側でDBに保存せず、レスポンスに含めた値をクライアントが保持し、次回リクエストにそのまま含めて送り返すことでサーバーの「記憶」を代替する設計方式。既存の`summary`・`messages`がこの方式を採る |

## 4. スコープ

### 4.1 対象範囲（MVP）

- `front_dev`のチャット画面（`StateContainer.tsx`）に、会話タグを保持するReact stateを追加し、`Request.tags`として送信、`Response.tags`で更新する（6.1節）。
- `web_backend`（`web_backend/src/main/controllers/chat_controller.py`）の`Request`/`Response`モデルに`tags`フィールドを追加する。**ローカル`docker-compose`環境の直接処理ロジック（LM Studio経由）には変更を加えない**（`tags`を読み書きしない）。AWS環境（`AGENT_INVITRO_URL`設定時）の中継処理は、`tags`フィールドを含めてそのまま`agent_invitro`へ転送・レスポンスをそのまま返す（6.3節）。この中継層の変更が必要になった理由は6.3節を参照。
- `agent_invitro`の`POST /ask-sl`（`agent_invitro/src/main/api/server.py`、AWS環境限定）に、`select_tags`の明示呼び出し・クライアント由来タグとのマージ・マージタグを使った`search_knowledge`呼び出し・継続タグの判定を追加する（6.4節）。
- `tag_selector_mcp`・`knowledge_mcp`・`chatbot`/`conversation`データベース・Terraformのネットワーク設定には変更を加えない（9章・10章）。

### 4.2 対象外（将来検討・別スコープ）

- ローカル`docker-compose`環境（`web_backend`の直接処理パイプライン）への本機能の展開。現状`tag_selector_mcp`/`knowledge_mcp`を一切呼んでいないパイプラインへの新規組み込みは、影響範囲が大きいため別途要件定義する（2章 回答1、12章 Open Issue #4）。
- 会話タグの`conversation`データベースへの永続化。ブラウザを閉じる・再読み込みすると会話タグは失われる（既存の`messages`・`summary`と同じ制約、2章 回答4）。
- 会話タグを画面上に表示する、またはユーザーが手動で追加・削除できるUI。本書はデータの流れ（クライアント⇔backend）のみを対象とし、画面表示・編集機能は要求されていない（12章 Open Issue #1）。
- `knowledge_mcp`の`search_knowledge`のタグ絞り込み条件をAND条件からOR条件（またはタグ数に応じた条件切り替え）へ変更すること。本書はこの制約を`agent_invitro`側の呼び出し方（6.4.2節）で吸収し、`knowledge_mcp`自体は変更しない（4.1節）。
- `graph/agent.py`のReActエージェント（ADR-0022）・`main/ipython/main.py`（IPython対話シェル）の変更。本書が対象とするのは`main/api/server.py`（AWS環境限定のHTTPサーバー）のみである。

## 5. 全体アーキテクチャ

### 5.1 現状構成の確認（本書の前提）

事前調査の結果、AWS環境の`POST /ask-sl`（`agent_invitro/src/main/api/server.py`）の現状の処理順序は次の通りであることを確認した。

```
1. （15件以上のとき）会話要約
2. search_knowledge(query=req.text, top_k=3)   ※tags引数なし＝絞り込みなし、select_tagsは呼ばれない
3. 検索結果からコンテキスト文字列を生成
4. Bedrock invoke_model で回答生成
```

`select_tags`は呼ばれておらず、`search_knowledge`もタグによる絞り込みを行っていない。ADR-0022が定めたReActエージェント方式（LLMが自律的に`select_tags`→`search_knowledge`を呼ぶ）は、この`POST /ask-sl`エンドポイントには使われていない（`main/ipython/main.py`側の実験でのみ使われている）。

本書は、この既存の固定シーケンス（ステップ2）に、`select_tags`呼び出しとタグによる絞り込みを追加する形で要件を定義する。ReActエージェントの自律的なツール選択（ADR-0022）とは独立しており、本書の変更はADR-0022の決定を見直すものではない。

## 6. 機能要件

### 6.1 クライアント側（`front_dev`）の会話タグ管理

- `StateContainer.tsx`に、`summary`と同様の方式で会話タグのReact stateを追加する。

```ts
const [tags, setTags] = useState<ConversationTag[]>([]);
```

- 初回メッセージ送信時は`tags = []`（未選択状態）で送信する。ユーザーが手動でタグを選択・入力する画面は設けない（4.2節）。
- リクエスト送信時、`Request.tags`に現在のstateをそのまま含める。
- レスポンス受信時、`res.tags`が含まれていれば`setTags(res.tags)`で置き換える。**`res.tags`が含まれない場合（ローカル環境等）は、直前の値をそのまま保持する**（後述6.2節の互換性要件）。
- セッションリセット（新しい会話を開始する操作）時は、`tags`を`[]`にリセットする（`messages`・`summary`のリセットと同様の扱い）。

### 6.2 API契約（`Request`/`Response`拡張）

`front_dev`・`web_backend`・`agent_invitro`の3箇所で、`Request`/`Response`に以下の型を追加する。

```ts
export interface ConversationTag {
  id: number;
  name: string;
  score: number;        // backendが直近で算出したスコア（select_tagsのscore、または前回値を維持）
  missed_turns: number;  // 6.4.3節。backendが算出・更新する。クライアントは値の意味を解釈せずそのまま送り返す
}
```

```ts
export interface Request {
  conversation_id?: string;
  text: string;
  messages: Message[];
  summary: Summary;
  tags?: ConversationTag[];   // 追加。未送信時は [] 相当として扱う
}

export interface Response {
  conversation_id: string;
  messages: Message[];
  summary: Summary;
  tags?: ConversationTag[];   // 追加。ローカル環境の応答には含まれない（6.3節）
}
```

- `score`・`missed_turns`はbackend（`agent_invitro`）が算出する値であり、クライアントはこれを解釈・加工せず、そのまま次回リクエストへ渡す「不透明な値（opaque value）」として扱う。
- 既存の`id`（`Summary.id`と同様の用途、UI側での`key`管理等）は`ConversationTag`には設ける必要がないと判断した（タグの`id`自体が一意キーとして使えるため）。

### 6.3 `web_backend`中継層でのスキーマ拡張（重要な技術的制約）

事前調査の結果、`web_backend/src/main/controllers/chat_controller.py`のAWS中継処理（`AGENT_INVITRO_URL`設定時）は、リクエストボディをそのまま右から左へ転送しているのではなく、**一度自身の`Request`Pydanticモデルでパースし、`req.model_dump()`で再シリアライズしてから`agent_invitro`へ転送している**ことを確認した。

```python
resp = httpx.post(f"{config.AGENT_INVITRO_URL}/ask-sl", json=req.model_dump(), ...)
...
return Response(**resp.json())
```

そのため、`chat_controller.py`の`Request`/`Response`モデルに`tags`フィールドを追加しない限り、`front_dev`が送った`tags`はパース時に破棄され、AWS環境であっても`agent_invitro`に届かない（Pydanticの既定動作である、モデルに定義のない入力フィールドの無視によるもの）。同様に、`agent_invitro`が返す`tags`も、`chat_controller.py`の`Response`モデルに定義がなければ`front_dev`へ返る前に失われる。

したがって、**「AWS環境のみを対象とする」という4.1節のスコープであっても、`web_backend`（中継層）への最小限のスキーマ変更（フィールド追加のみ、ロジック追加なし）が必要である**。ローカル`docker-compose`環境の直接処理ロジック（`AGENT_INVITRO_URL`未設定時の分岐）は、`tags`フィールドを一切参照せず、`Response`構築時にも指定しない（デフォルト値`None`のまま）ため、動作は現状から変化しない。

### 6.4 `agent_invitro`（`POST /ask-sl`）での処理内容

以下を`_ask_impl`（`agent_invitro/src/main/api/server.py`）に追加する。

#### 6.4.1 `select_tags`の明示呼び出し

- 毎リクエスト、`req.text`を`query`として`select_tags`を呼び出す（`_get_components`で取得済みの`tools`一覧から、既存の`search_tool`取得と同じ方式で`select_tags`ツールも取得する）。
- `max_tags`・`confidence_threshold`は、新規環境変数`TAG_SELECTOR_MAX_TAGS`・`TAG_SELECTOR_CONFIDENCE_THRESHOLD`（未設定時は`tag_selector_mcp`自体の既定値と同じ3・0.0）を使う。
- 呼び出しに失敗した場合（接続エラー・タイムアウト等）、`select_tags`の結果を空集合として扱い、処理を継続する（回答生成自体を失敗させない。既存の`search_knowledge`呼び出し失敗時の扱いと同様、エラーはログに記録する）。

#### 6.4.2 マージタグを使った`search_knowledge`呼び出し（AND制約への対応）

- **背景となる制約**: `search_knowledge`の`tags`引数は、指定した全タグを持つQAのみに絞り込むAND条件である。会話タグはターンを重ねるごとに蓄積されうるため、マージタグ全件を1回の`tags`引数にまとめて渡すと、タグ数が増えるほど検索結果が0件に近づくリスクがある。
- **対応方針**: マージタグ（`select_tags`結果 ∪ `req.tags`、6.4.3節でタグ数の上限あり）について、**タグ1件につき1回、`search_knowledge(query=req.text, tags=[そのタグのname], top_k=N)`を呼び出す**。これに加えて、タグによる絞り込みを行わない`search_knowledge(query=req.text, tags=None, top_k=N)`を1回呼び出す（フォールバック）。
- フォールバック呼び出しは、環境変数`TAG_SEARCH_FALLBACK_ENABLED`（既定`true`）で無効化できるようにする。無効化した場合、タグ選択・会話タグがいずれも空のとき（マージタグ0件）は、`search_knowledge`が一度も呼ばれず情報源が得られない状態になりうる点に注意する（12章 Open Issue #2）。
- 全呼び出しの結果を、QA単位（`metadata.guid`）で重複排除する。同一QAが複数回ヒットした場合はスコアの高い方を採用する。重複排除後、スコア降順に並べ替え、既存と同じ`top_k`（既定3）件を最終的なコンテキストとして使用する。
- 呼び出し回数は最大で「マージタグ数の上限＋1（フォールバック分）」となる（6.4.3節でマージタグ数に上限を設ける理由の1つ）。

#### 6.4.3 継続タグの判定ロジック（たたき台）

2章 回答3を受けて、以下のロジックを提案する。判定に使う情報は`select_tags`の結果（`id`/`name`/`score`）と、クライアントから送られてきた会話タグ（`id`/`name`/`score`/`missed_turns`）のみであり、`conversation`データベース等の永続的な参照は行わない（クライアントエコー方式、2章 回答4）。

1. 今回の`select_tags`結果（`new_tags`）と、クライアントから送られてきた会話タグ（`client_tags`）を`id`で突き合わせる。
2. `client_tags`のうち、`new_tags`に同じ`id`が含まれるもの: `missed_turns = 0`、`score`を今回の`select_tags`のスコアで更新する（「今回も再選択された」として鮮度をリセット）。
3. `client_tags`のうち、`new_tags`に含まれないもの: `missed_turns = missed_turns + 1`（`score`は前回値を維持）。
4. `new_tags`のうち、`client_tags`に含まれない（＝今回新たに選ばれた）もの: `missed_turns = 0`として追加する。
5. `missed_turns`が環境変数`TAG_CONTEXT_MAX_MISSED_TURNS`（既定2）を超えたタグは破棄する。すなわち、あるタグは直近`TAG_CONTEXT_MAX_MISSED_TURNS`ターン連続で選ばれなかった場合に会話タグから外れる（話題が変わった場合に古いタグが徐々に外れていく、一種の減衰）。
6. 上記の結果、件数が環境変数`TAG_CONTEXT_MAX_TAGS`（既定5）を超える場合、`missed_turns`が大きい順、次に`score`が低い順に間引き、上限件数に収める。
7. この最終的な集合が、その回の`Response.tags`（継続タグ）であり、同時に6.4.2節で使う「マージタグ」そのものでもある（検索に使った集合＝次回に引き継ぐ集合、という単一の管理にする）。

この判定ロジックの各種しきい値（`TAG_CONTEXT_MAX_MISSED_TURNS`・`TAG_CONTEXT_MAX_TAGS`）は環境変数化し、実運用のフィードバックを踏まえてチューニングできるようにする。具体的な既定値の妥当性は実装フェーズ・運用開始後に見直す（12章 Open Issue #3）。

### 6.5 新規環境変数一覧

| 環境変数 | 既定値 | 説明 |
|---|---|---|
| `TAG_SELECTOR_MAX_TAGS` | 3 | `agent_invitro`が`select_tags`を呼び出す際の`max_tags`（`tag_selector_mcp`自体の既定値と同じ） |
| `TAG_SELECTOR_CONFIDENCE_THRESHOLD` | 0.0 | 同上、`confidence_threshold` |
| `TAG_CONTEXT_MAX_TAGS` | 5 | マージタグ（＝継続タグ）の件数上限。`search_knowledge`の呼び出し回数の上限にも影響する（6.4.2節） |
| `TAG_CONTEXT_MAX_MISSED_TURNS` | 2 | 会話タグが連続でこの回数`select_tags`に再選択されなかった場合に破棄する（6.4.3節） |
| `TAG_SEARCH_FALLBACK_ENABLED` | true | タグによる絞り込みを行わない`search_knowledge`呼び出しを毎回1回追加するかどうか（6.4.2節） |

## 7. データ要件

- 本機能はデータベースのスキーマ変更を伴わない。`chatbot`データベース・`conversation`データベースのいずれにもテーブル追加・列追加は発生しない（2章 回答4、4.2節）。
- 会話タグは、`Request`/`Response`のJSON構造として6.2節の形式でやり取りされ、クライアント（ブラウザのメモリ）にのみ保持される。ページ再読み込み・タブを閉じる操作で失われる（既存の`messages`・`summary`と同じ制約）。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| レイテンシ | `search_knowledge`の呼び出し回数が、既存の1回から最大「`TAG_CONTEXT_MAX_TAGS`＋1（フォールバック）」回（既定値では最大6回）に増える。加えて`select_tags`呼び出し（LLMを伴う、ADR-0009）が新たに毎リクエスト発生する。既存の`/ask-sl`のレイテンシ（数秒〜十数秒程度、`docs/requirement/202608260909.md`8章と同水準の想定）からの増加幅を実装フェーズで計測する必要がある（12章 Open Issue #5） |
| `tag_selector_mcp`への負荷 | 検証機能（ADR-0049、`web_backend`から）に加え、`agent_invitro`からも`select_tags`が毎リクエスト呼ばれるようになる。既存のReActエージェント経由の呼び出し（`main/ipython/main.py`側の実験）と合わせた負荷を運用開始後に監視する必要がある |
| 後方互換性 | ローカル`docker-compose`環境（`AGENT_INVITRO_URL`未設定）は、`Request.tags`を無視し`Response.tags`を含めないことで、既存動作を一切変更しない。`front_dev`は`res.tags`が存在しない場合に直前の値を保持することで、ローカル・AWSいずれの環境でも同一のフロントエンドコードで動作する（6.1節） |
| 可用性 | `select_tags`の呼び出し失敗時は会話タグ・検索結果を空集合として扱い、回答生成自体は継続する（6.4.1節）。既存の「検索結果が得られない場合の回答」と同様の挙動になる |
| 保守性 | `search_knowledge`複数回呼び出し・重複排除・継続タグ判定のロジックは、`server.py`内に直接実装するか、新規モジュール（例: `agent_invitro/src/tags.py`）へ切り出すかを実装フェーズで判断する |

## 9. インフラ・実行環境要件

### 9.1 ローカル`docker-compose`環境

- 変更なし。`agent_invitro`サービスは引き続き`command: ["sleep", "infinity"]`のままであり、`main/api/server.py`はローカルでは起動しない（ADR-0043）。

### 9.2 AWS環境

- `terraform/main/app/main.tf`の`module "agent_invitro"`の`environment`に、6.5節の新規環境変数5件を追加する。
- ネットワーク（`terraform/modules/network`）の変更は不要。`agent_invitro → tag_selector_mcp`（8200番）の到達性は、既存の`graph/agent.py`（ADR-0021/0022）向けにすでに確立済みである。
- `web_backend`（AWS上は`admin_ui`）側のTerraform設定（環境変数・ネットワーク）に変更は不要。中継処理自体はスキーマ拡張のみであり、新規の接続先は発生しない。

## 10. 既存システムとの関係・影響範囲

- `tag_selector_mcp`・`knowledge_mcp`・`chatbot`データベース・`conversation`データベースには変更を加えない。
- `graph/agent.py`（ADR-0022のReActエージェント）・`main/ipython/main.py`（IPython対話シェル）には変更を加えない。ADR-0022の決定（ReActエージェント方式の採用）自体は見直さない（5.1節）。
- ローカル`docker-compose`環境の`/ask-sl`（`web_backend`の直接処理パイプライン）の挙動は変更しない（6.3節・8章）。
- `front_dev`の既存画面（管理画面・評価済みメッセージ・エクスポート・検証機能）には変更を加えない。チャット画面（`StateContainer.tsx`）のみが対象である。
- 会話評価機能（`/evaluate_response`・`/evaluated_messages`、ADR-0045）には影響しない。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] AWS環境で、1回目のチャット送信後、`Response.tags`に`select_tags`が選んだタグ（存在すれば）が含まれる。
- [ ] AWS環境で、2回目以降のチャット送信時、`Request.tags`に前回の`Response.tags`が送られ、`agent_invitro`が`select_tags`結果とマージした上で情報源検索に使う。
- [ ] 会話タグが複数件蓄積した状態でも、`search_knowledge`の呼び出しが0件ヒットに陥らない（AND条件による過絞り込みが起きない）ことを、6.4.2節の呼び出し方式（タグ別複数回呼び出し）で確認する。
- [ ] 一定回数（`TAG_CONTEXT_MAX_MISSED_TURNS`）連続して選択されなかった会話タグが、継続タグから外れることを確認する。
- [ ] ローカル`docker-compose`環境で、本機能導入前と同じ挙動（`select_tags`が呼ばれない、`search_knowledge`にタグ絞り込みがない）が維持されることを確認する。
- [ ] `front_dev`を、ローカル環境・AWS環境のいずれに対しても同一ビルドで動作させられることを確認する（`res.tags`が無い場合に会話タグが失われない）。
- [ ] `select_tags`呼び出しが失敗しても、`/ask-sl`全体がエラーにならず、既存同様に回答が生成されることを確認する。

## 12. Open Issues（要追加確認事項）

1. **会話タグの可視化・手動編集UI**: 本書はデータの流れのみを定義しており、画面上にタグを表示する・ユーザーが手動で追加/削除するUIは要求されていない（4.2節）。運用上、ユーザーが「今どのタグで検索されているか」を確認したいニーズがあるかどうかは、運用開始後に確認を推奨する。
2. **フォールバック検索（タグなし検索）の要否**: 6.4.2節で提案した「タグなし検索を毎回1回追加する」方式は、タグ選択の精度が低い場合の検索結果の再現率を保険する目的だが、`search_knowledge`の呼び出し回数（ひいてはレイテンシ）を増やすトレードオフがある。無効化した場合の挙動（マージタグ0件時に検索が一度も行われない）が許容できるかどうかは、実装フェーズで動作確認しながら判断する。
3. **継続タグ判定ロジックのしきい値**: `TAG_CONTEXT_MAX_MISSED_TURNS`（既定2）・`TAG_CONTEXT_MAX_TAGS`（既定5）は本書のたたき台（6.4.3節）における暫定値であり、実際の会話パターンに対する妥当性は未検証である。実装フェーズでの手動テスト・運用開始後のフィードバックを踏まえて見直す。
4. **ローカル環境への展開**: 現時点ではAWS環境のみを対象とするが（2章 回答1）、将来ローカル`docker-compose`環境（`web_backend`の直接処理パイプライン）にも同様の会話タグ機能を展開したいニーズが生じた場合、`tag_selector_mcp`/`knowledge_mcp`を新たに呼び出す構成変更が必要になる（現状ローカルは`chatbot`データベースへの直接クエリのみで完結している）。別途要件定義が必要になる見込み。
5. **レイテンシへの影響**: 8章に記載の通り、`select_tags`呼び出しの追加、および`search_knowledge`呼び出し回数の増加（最大6回）による`/ask-sl`全体のレイテンシ増加を実装フェーズで計測し、許容範囲かどうかを確認する必要がある。許容できない場合、`TAG_CONTEXT_MAX_TAGS`の既定値引き下げ、または呼び出しの並列化を検討する。
6. **タグのリネーム・削除との整合性**: 管理画面（`/admin/tags`）でタグがリネーム・削除された場合、クライアントが保持している会話タグの`id`/`name`が古い状態のまま残る可能性がある。`select_tags`結果とのマージ時に`id`一致で突き合わせる設計（6.4.3節）のため、削除されたタグの`id`はいずれ`select_tags`に再選択されなくなり、`missed_turns`の増加を経て自然に会話タグから外れる想定だが、削除直後に即座に無効化されるわけではない点を許容できるか確認が必要。
