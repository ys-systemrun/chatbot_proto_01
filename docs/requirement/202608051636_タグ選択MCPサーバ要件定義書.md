# タグ選択（Tag Selector）MCP サーバ 要件定義書

- 文書番号: REQ-202608051636
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: Tag Selector MCP サーバ（新規）
- 参照資料: `docs/requirement/202608051630.md`（タグ選択MCPサーバ構成に関する検討メモ）
- 前提の決定事項: 本書末尾「14. 関連ADR一覧」参照。特に Knowledge MCP サーバに関する既存決定（ADR-0001〜0006、`docs/requirement/202608041002.md`）を前提とする。

## 1. 目的

現行の chatbot_invitro には、Knowledge MCP サーバ（`docs/requirement/202608041002.md` にて要件定義済み）が `search_knowledge` ツールを通じてタグ・カテゴリによる絞り込み検索を提供している。ただし Knowledge MCP は「タグを使って検索する」ことのみを責務とし、「ユーザーの自然文の質問から検索すべきタグ集合を推定する」処理はスコープ外（同書 Open Issue #1）としている。

本書は、この「自然言語の質問 → 検索すべきタグ集合への変換」を専任で担う Tag Selector MCP サーバを新規プロジェクトとして立ち上げる際の要件を整理したものである。コーディングは対象外とし、要件定義および設計判断（ADR）の整理にとどめる。

## 2. 背景・参照資料

- `docs/requirement/202608051630.md` にて、タグ判定を独立した MCP サーバとして切り出す設計方針、および LLM 単体／Embedding類似度／LLM+Embedding／階層タグ探索／エージェント型／ルール+LLMハイブリッドという6つのアプローチが検討されている。
- 同メモでは、Tag Selector MCP を「タグ知識ベース」と「タグ選択エンジン（Retrieval Engine + Inference Engine）」を持つ小さな推論サービスとして設計する案、およびクリーンアーキテクチャ的なディレクトリ構成案・docker-compose構成案が提示されている。
- 一方、本プロジェクトでは既に Knowledge MCP サーバの要件定義・ADR（ADR-0005, ADR-0006）にて、タグは `tag`（自己参照の `parent_tag_id` を持つマスタ）と `qa_tag`（QAとの関連）から成るリレーショナル構造で管理することが確定しており、これが本書時点での唯一の正本である。
  - 実装指示書（`docs/implementation_handoff/202608041013_implementation.md`）記載のとおり、既存データの `parent_tag_id` は現状すべて `NULL`（フラットな一覧）であり、階層構造は未整備である。
  - `tag` テーブルには現状 `id` / `name` / `parent_tag_id` のみが存在し、タグ選択に必要な説明文（description）や同義語（alias）に相当するカラムは存在しない。
- そのため、検討メモが前提とする `taxonomy.yaml` によるタグ知識ベース管理をそのまま採用すると、Knowledge MCP 側の `tag` テーブルと二重管理になり、同期ズレのリスクがある。本書では、この点を含めて実装可能な形に要件を再整理する（詳細は 11 章 ADR-0008 参照）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| Tag Selector MCP サーバ | 本書が対象とする、自然言語の質問からタグ集合を推定する MCP サーバ |
| Knowledge MCP サーバ | 既存の要件定義済みコンポーネント。タグ・カテゴリによる絞り込み検索（`search_knowledge`）と、タグマスタの書き込み系管理ツール（`create_tag` 等）を提供する（`docs/requirement/202608041002.md`） |
| Tag Metadata Repository | Tag Selector MCP がタグ一覧（id・name・description・alias・親子関係）を参照するための内部コンポーネント。本書では既存 `tag`/`tag_alias` テーブルをメモリへロードしたキャッシュとして実装する |
| Retrieval Engine | 全タグから候補を絞り込む処理（本書MVPではAlias辞書によるルールベース処理のみ。Embeddingによる絞り込みは将来拡張） |
| Inference Engine | LLM を用いて最終的な選択タグを決定する処理 |
| Alias | タグの同義語・表記ゆれ（例: 「歩掛」→「積算」）。ルールベースでの即時確定に用いる |
| Conversation Agent | ユーザーの質問を受け、Tag Selector MCP と Knowledge MCP を順に呼び出して回答を生成するオーケストレーション主体（本書スコープ外） |
| SearchPlan | 検討メモで言及されている、タグに加えて `weight` や `expand_children`（階層展開要否）等の検索方針まで返す将来的な応答形式。本書MVPでは採用しない（ADR-0010参照） |

## 4. スコープ

### 4.1 対象範囲（MVP）

- 自然言語の質問文字列を入力とし、選択タグ一覧を返す MCP ツール `select_tags` のインターフェース定義。
- Alias辞書によるルールベースの即時確定・絞り込み（Retrieval Engine）の要件定義。
- LLM を用いた最終タグ判定（Inference Engine）の要件定義。
- 既存 `tag` テーブルを唯一の正本として参照するための設計（`description` カラム・`tag_alias` テーブルの追加を含むスキーマ拡張要件）。
- タグ知識ベースのメモリキャッシュ方針と、Knowledge MCP 側のタグ変更に追従するための `reload_taxonomy` ツールの要件定義。
- LLM 呼び出し先（ローカルLLM／Amazon Bedrock／OpenAI）を設定で切り替え可能にするための抽象化要件。MVP時点の主たる接続先はローカルLLM（LM Studio）とする（ADR-0012）。
- Docker Compose への新規サービスとしての組み込み要件。

### 4.2 対象外（将来検討・別プロジェクトスコープ）

- Embedding による候補絞り込み（検討メモのアプローチ2・3相当）。現状のタグ件数・階層未整備の状況では過剰投資と判断し見送る（ADR-0009）。
- タグの階層構造を用いた多段階探索（検討メモのアプローチ4、Best-First Search相当）。既存 `parent_tag_id` が全件 `NULL` であり階層データが存在しないため、本MVPでは対象外。
- `weight` / `expand_children` を含む SearchPlan 形式での応答（ADR-0010）。
- Knowledge MCP 側のタグ管理ツール（`create_tag` 等）を `description` / `alias` 編集に対応させる拡張実装そのもの（要件は本書 6.6 節・13 章 Open Issue に記載するが、実装は Knowledge MCP 側の変更管理として別途扱う）。
- Conversation Agent（LangGraph等）側の実装（本書は Tag Selector MCP サーバの提供側のみを対象とする）。
- 認証基盤・IDP連携等の全社的な認証方式（アクセス制御の要件レベルまでを本書の対象とする）。

## 5. 全体アーキテクチャ

### 5.1 システム構成（MVP時点）

```
                         ┌───────────────────────────┐
                         │     Conversation Agent      │
User ── (自然言語) ──→   │   (LangGraph / MCP Client)  │
                         └──────────┬───────┬─────────┘
                                    │       │
                     ① select_tags  │       │ ② search_knowledge(tags=...)
                                    ▼       ▼
                    ┌───────────────────┐ ┌───────────────────────┐
                    │ Tag Selector MCP  │ │  Knowledge MCP サーバ   │
                    │ サーバ (新設)       │ │ （要件定義済み・別書）    │
                    └─────────┬─────────┘ └───────────┬───────────┘
                              │                        │
                     Tag Metadata Repository            │
                     （tag / tag_alias をロード）          │
                              │                        │
                              ▼                        ▼
                     既存 chatbot_db (pgvector, PostgreSQL) ── 読み取り専用
                     tag / tag_alias / qa_tag / qa_original
```

Conversation Agent は、まず `select_tags` を呼び出してタグ集合を取得し、そのタグ集合をそのまま Knowledge MCP の `search_knowledge` の `tags` パラメータへ渡す、という2段階の呼び出しを行う。Tag Selector MCP と Knowledge MCP サーバの間に直接の通信は発生しない（両者ともに Conversation Agent から独立して呼び出される）。

### 5.2 コンポーネント一覧と責務

| コンポーネント | 責務 |
|---|---|
| MCP Tool 層（`select_tags` 等） | クライアントからのタグ選択要求を受け付け、Retrieval Engine → Inference Engine の順に処理を実行し、結果をMCPレスポンス形式に整形する |
| Tag Metadata Repository | 既存 `tag` / `tag_alias` テーブルをメモリへロードし、タグの一覧・説明文・同義語・親子関係をアプリケーション内で高速に参照可能にする（7章・ADR-0008/0011参照） |
| Retrieval Engine | Alias辞書との照合により、候補タグの即時確定・絞り込みを行う（MVPではEmbeddingは行わない） |
| Inference Engine | 質問文とタグ候補（id・name・description）を LLM へ渡し、最終的な選択タグとスコアを得る |
| LLMClient | LLM 呼び出しを抽象化するインターフェース。MVP時点ではローカルLLM（LM Studio）の実装を主として提供し、将来 Amazon Bedrock／OpenAI へ設定で切り替え可能にする（ADR-0012） |
| データストア | 既存 chatbot_db（pgvector）の `tag` / `tag_alias` テーブルを読み取り専用で利用する |

## 6. 機能要件

### 6.1 MCP ツール仕様: `select_tags`

**入力（例、インターフェース仕様としての参考例）**

```json
{
  "query": "橋梁工事の数量総括表について教えてください",
  "max_tags": 3,
  "confidence_threshold": 0.5
}
```

| フィールド | 必須 | 説明 |
|---|---|---|
| query | ○ | ユーザーの自然言語の質問文字列 |
| max_tags | - | 返却するタグ数の上限（デフォルト値は設計時に確定、参考値3） |
| confidence_threshold | - | スコアの下限フィルタ（デフォルト値は設計時に確定、参考値0.0） |

**出力（例）**

```json
{
  "selected": [
    { "id": 12, "name": "積算システムの操作方法", "score": 0.94, "path": ["積算システムの操作方法"] },
    { "id": 3,  "name": "積算システム",           "score": 0.81, "path": ["積算システム"] }
  ]
}
```

| フィールド | 型 | 説明 |
|---|---|---|
| id | integer | `tag.id` |
| name | string | `tag.name` |
| score | float | 選択の確信度（0.0〜1.0）。変換式・算出方法は詳細設計フェーズで確定 |
| path | array[string] | 将来の階層対応を見据えた経路表現。MVP時点ではタグ名1件のみを含む配列とする（ADR-0010） |

エラー時のレスポンス形式（MCPエラーレスポンスに準拠、詳細は詳細設計フェーズで確定）も要件として定める必要がある。

### 6.2 Tag Metadata Repository

- サーバ起動時に、既存 chatbot_db の `tag` / `tag_alias` テーブルの内容を全件読み込み、メモリ上のキャッシュ（タグ一覧・親子関係・alias逆引き辞書）を構築する。
- キャッシュの更新は `reload_taxonomy` ツール（6.5節）による明示的なリロード、および一定間隔でのポーリングによる自動リロードの両方をサポートする（ADR-0011）。
- MVPでは `parent_tag_id` は全件 `NULL` である前提のため、親子関係を用いた探索ロジックは実装しないが、将来の拡張に備えデータ構造としては親子関係を保持できるようにしておく。

### 6.3 Retrieval Engine（Alias辞書によるルールベース処理）

- `tag_alias` テーブルに登録された同義語との完全一致・部分一致により、候補タグを確定・優先付けする（例:「歩掛」という語が質問に含まれる場合、対応する `tag`（例:「積算」）を候補へ加える）。
- MVPでは Embedding による候補絞り込みは行わない。タグ件数が少数（現行データの `tags` 実績からは数十件程度と推定）であるため、Alias辞書で確定しなかった残りのタグも含め、タグ一覧全件（id・name・description）をそのまま Inference Engine（6.4節）へ渡す一段階の構成とする（ADR-0009）。
- 将来タグ件数が数百〜数千件規模に増加した場合は、Embeddingによるベクトル検索で候補を数十件程度に絞り込む層を Retrieval Engine 内に追加する（インターフェースは変更せず、実装のみ差し替え可能な設計とする）。

### 6.4 Inference Engine（LLM判定）

- 質問文、Retrieval Engine が確定・絞り込んだタグ候補（id・name・description）を LLM へ渡し、最終的な選択タグ集合とスコアを取得する。
- プロンプト設計（タグ候補の提示形式、スコアの算出方法・正規化方式）は詳細設計フェーズで確定する。
- `confidence_threshold` 未満のタグは結果から除外する。
- `max_tags` を超える候補が得られた場合、スコア上位から `max_tags` 件に絞り込む。

### 6.5 タグ知識ベース参照系ツール

| ツール | 概要 | 主なパラメータ |
|---|---|---|
| `select_tags` | 質問文からタグ集合を推定する（6.1節） | `query`, `max_tags`, `confidence_threshold` |
| `list_taxonomy` | 現在キャッシュされているタグ一覧（親子関係・description・aliasを含む）を取得する。動作確認・デバッグ用途を想定 | なし |
| `reload_taxonomy` | Tag Metadata Repository のキャッシュを即時に再読み込みする（ADR-0011） | なし |

いずれも読み取り専用ツールであり、Knowledge MCP のようなタグ書き込み系ツール（`create_tag` 等）は Tag Selector MCP 側には設けない。タグの登録・リネーム・alias登録等は、引き続き Knowledge MCP 側のツールで一元的に行う（6.6節）。

### 6.6 Knowledge MCP との連携・依存する変更点

- Tag Selector MCP のタグ選択には `tag.description` と `tag_alias.alias` が必要だが、これらは現状の `tag` テーブルには存在しないカラム・テーブルである（7章参照）。
- ADR-0006の方針（タグマスタの書き込みは Knowledge MCP のツールに一元化する）を踏襲し、`description` の設定・更新、および `tag_alias` の追加・削除は、Tag Selector MCP 側に新たな書き込みツールを設けるのではなく、**Knowledge MCP 側の既存タグ管理ツール（`create_tag` / `rename_tag` 等）を拡張する形で対応する**ことを要件とする。この拡張自体は Knowledge MCP 側の変更管理となるため、本書では要件として明記するに留め、実装は別途 Knowledge MCP 側の設計変更として扱う。
- **着手順序（発注者確認済み、Open Issue #1解消）**: Knowledge MCP側のこの拡張は、まず Tag Selector MCP のMVPが動作することを確認した後に着手する。したがって MVP の検証時点では `description` / `tag_alias` への値の登録は、Knowledge MCP のツールを介さず DB へ直接 `INSERT`/`UPDATE` する暫定手段で行ってよいものとする（実運用開始前には Knowledge MCP 側の拡張により本来の経路へ切り替える）。
- Tag Selector MCP は `tag` / `tag_alias` テーブルに対して読み取り専用でアクセスし、書き込みは一切行わない。

## 7. データ要件

### 7.1 現行スキーマ（ADR-0005にて確定済み、抜粋）

```sql
CREATE TABLE IF NOT EXISTS tag (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL UNIQUE,
    parent_tag_id INTEGER REFERENCES tag(id)
);

CREATE TABLE IF NOT EXISTS qa_tag (
    qa_id TEXT NOT NULL REFERENCES qa_original(uuid),
    tag_id INTEGER NOT NULL REFERENCES tag(id),
    PRIMARY KEY (qa_id, tag_id)
);
```

### 7.2 課題

- `tag` テーブルには `description`（タグの説明文）に相当するカラムが存在しない。
- 同義語（alias）を管理するテーブル・カラムが存在しない。
- そのため、現行スキーマをそのまま Tag Selector MCP の Tag Metadata Repository として利用すると、Retrieval Engine（Alias辞書照合）・Inference Engine（LLMへ渡すタグ説明文）のいずれも要求水準を満たせない。

### 7.3 スキーマ拡張案（要件レベル）

- `tag` テーブルに `description TEXT`（NULL許容）カラムを追加する。
- 同義語は、タグ本体と同様の理由（ADR-0005の考え方を踏襲: 個々の同義語を独立して追加・削除・一意性管理できるようにするため）から、配列カラムではなく **`tag_alias` 関連テーブル**（`tag_id` の自己参照、`alias` に一意制約）で表現する。

```sql
CREATE TABLE IF NOT EXISTS tag_alias (
    id SERIAL PRIMARY KEY,
    tag_id INTEGER NOT NULL REFERENCES tag(id),
    alias TEXT NOT NULL UNIQUE
);

CREATE INDEX IF NOT EXISTS idx_tag_alias_tag_id ON tag_alias (tag_id);
```

- 既存タグには `description` / `alias` のデータが存在しないため、マイグレーション直後はいずれも `NULL` または空（未登録）で問題ない。運用開始後、Knowledge MCP 側の拡張ツールを通じて順次登録していく想定とする。
- `parent_tag_id` を用いた階層構造・階層検索は本書スコープ外（4.2節）とし、既存ADR-0005の方針（列のみ用意、検索ロジックは未実装）をそのまま踏襲する。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | `select_tags` 呼び出しからレスポンスまで（LLM呼び出し時間を含む）を目安として数秒以内（暫定目標値、LLM呼び出し先・モデルにより変動するため詳細設計時に見直し） |
| 同時実行 | Conversation Agent からの呼び出しに対応できる程度（既存appと同程度、数〜数十セッション）の同時利用を想定 |
| 可用性 | 社内利用ツールとして単一インスタンス構成で可とし、冗長化・自動フェイルオーバーは対象外とする |
| ログ | クエリ内容・確定したタグ・処理時間・LLM呼び出し結果・エラーを記録する。既存 `app/src/log` のロギング方針との整合を取る |
| 監視 | ヘルスチェック手段（MCPリソースまたはHTTPエンドポイント）を用意し、`docker-compose.yml` の `healthcheck` に登録できるようにする |
| セキュリティ | **MVP時点では追加の認証は実装せず、Knowledge MCPと同様にDocker内部ネットワーク限定公開（ホスト側ポート公開は開発時のみ）で運用する**（発注者確認済み、Open Issue #6解消。恒久対応ではなく、将来必要になった時点で改めて認証方式を検討する）。読み取り専用ツールのみを提供する。MVP時点ではローカルLLM（LM Studio、社内ネットワーク内で完結）を主たる接続先とするため、質問文・タグ情報が外部へ送信されることはない（ADR-0012）。将来 Bedrock/OpenAI 等の外部LLM APIへ切り替える場合は、情報の機密区分の確認を要件として別途明記する（Knowledge MCP要件定義書8章と同様の論点） |
| 保守性・拡張性 | Retrieval Engine / Inference Engine / LLMClient をそれぞれ差し替え可能なインターフェースとして抽象化し、将来のEmbedding層追加・LLMプロバイダ変更・階層探索対応の際に `select_tags` ツールのインターフェース変更が不要な構成とする |

## 9. インフラ・実行環境要件

### 9.1 デプロイ構成

- ADR-0007に基づき、chatbot_invitro リポジトリ直下に新規ディレクトリ（例: `tag_selector_mcp/`）を追加し、Knowledge MCP と同様に独立した Docker コンテナとして `docker-compose.yml` に新規サービスを追加する。
- 既存 `db`（chatbot_db, pgvector）サービスに対し、`depends_on` で起動順序を制御し、`DATABASE_URL` 相当の接続情報を環境変数経由で受け渡す。
- LLM 呼び出し先（ローカルLLM／Bedrock／OpenAI）は環境変数で切り替え可能とし、MVP時点のデフォルトはローカルLLM（LM Studio）とする（ADR-0012）。既存 Knowledge MCP・既存appと同じ LM Studio embedding API 用の接続情報（`LMSTUDIO_EMBEDDING_URL` 等）とは別に、チャット補完（タグ判定）用のLM StudioエンドポイントをTag Selector MCP専用の環境変数として持つ。

**docker-compose.yml への追加イメージ（例、最終形は詳細設計フェーズで確定）**

```yaml
  tag_selector_mcp:
    build: ./tag_selector_mcp
    container_name: chatbot_tag_selector_mcp
    ports:
      - "${TAG_SELECTOR_MCP_PORT:-8200}:8200"
    environment:
      - DATABASE_URL=postgresql://postgres:postgres@db:5432/chatbot
```

## 10. 既存システムとの関係・影響範囲

- Knowledge MCP サーバの `search_knowledge` ツールはそのまま変更不要（`tags` パラメータへ Tag Selector MCP の出力をそのまま渡す構成のため）。
- Knowledge MCP のタグ管理ツール（`create_tag` / `rename_tag` 等）は `description` / `tag_alias` の編集に対応させる拡張が必要になる（6.6節）。発注者確認済みのとおり、この拡張は Tag Selector MCP のMVP動作確認後に着手する（Open Issue #1解消）。それまでの間、`description` / `alias` はDBへ直接投入する暫定運用とする。
- 既存 `tag` テーブルへの `description` カラム追加、および `tag_alias` テーブルの新設は、既存 Knowledge MCP・既存アプリの動作に影響しない設計とする（既存クエリはカラム・テーブル追加の影響を受けない）。
- 既存 `.env` / `docker-compose.yml` の変更が発生するため、README の利用手順にも追記が必要になる。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] `select_tags` ツールが MCP クライアントから呼び出せる。
- [ ] Alias辞書に登録した同義語を含む質問に対し、対応するタグが確定・優先されることを確認できる。
- [ ] レスポンスの `selected` に `id` / `name` / `score` / `path` が正しく含まれる。
- [ ] `max_tags` / `confidence_threshold` によるフィルタが機能する。
- [ ] `reload_taxonomy` 呼び出し後、DBを直接更新した `tag` / `tag_alias` の内容が反映されることを確認できる。
- [ ] `docker-compose up` で他サービスと同様に起動し、ヘルスチェックが正常応答する。
- [ ] 将来 Embedding 層・階層探索を追加する際に `select_tags` ツールのインターフェース変更が不要であることを設計レビューで確認する。

MVPの受け入れ基準には、精度評価用データセットによる定量評価は含めない（Open Issue #3解消、暫定的に不要と確認済み）。動作確認は上記チェックリストと少数の手動テストクエリで行う。

## 13. Open Issues（要追加確認事項）

1. ~~**Knowledge MCP側タグ管理ツールの拡張時期・優先度**~~ → 発注者確認の結果、まず Tag Selector MCP のMVPが動作することを確認した後に着手する方針が確定した（6.6節）。MVP検証時点では `description` / `tag_alias` はDBへの直接投入で対応する。
2. **既存タグへの description / alias の初期投入**: 運用開始時点でどの程度のタグに説明文・同義語を登録しておく必要があるか（登録が薄いままだとRetrieval Engine・Inference Engineの精度が上がらない可能性がある）。
3. ~~**タグ選択の精度評価方法**~~ → 発注者確認の結果、精度評価用データセットの整備は暫定的に不要と確定した。MVPでは少数の手動テストクエリによる動作確認に留める。将来、精度の定量評価が必要になった時点で改めて評価用データセットの整備を検討する。
4. ~~**LLMプロバイダの初期選定**~~ → 発注者確認の結果、MVP時点ではローカルLLM（LM Studio）を主たる接続先とすることが確定した（ADR-0012）。Bedrock/OpenAIへの切り替えは将来対応とし、`LLMClient` インターフェースの実装差し替えのみで対応できる設計とする。
5. **タグ件数の将来見込み**: Embedding層の追加要否を再検討するタイミング（タグ件数がおおよそ何件を超えたら着手するか）の目安値。
6. ~~**認証・アクセス制御方式**~~ → 発注者確認の結果、MVP時点では追加の認証は実装せず、Knowledge MCPと同様にDocker内部ネットワーク限定公開で運用することが確定した（8章）。恒久対応ではなく、継続管理のOpen Issueとして残す（将来必要になった時点で認証方式を検討する）。
7. **外部API（Bedrock/OpenAI）利用時のデータ送信可否**: MVP時点はローカルLLMのため該当しないが、将来Bedrock/OpenAIへ切り替える場合に質問文・タグ情報の機密区分確認が必要になる（Knowledge MCP要件定義書 Open Issue #7と同様の論点）。
8. **`reload_taxonomy` の自動ポーリング間隔**: 何秒〜何分程度が妥当か（タグ変更の反映速度とDB負荷のトレードオフ）。
9. **将来のSearchPlan形式への移行方針**: Knowledge MCP側で階層展開検索（`expand_children`相当）が実装された場合、`select_tags` のレスポンスへ `weight` / `expand_children` 等をどう追加するか（後方互換性の維持方法を含む）。
