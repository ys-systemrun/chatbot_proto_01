# マイグレーション専用実行機能（シードスキップ対応） 要件定義書

- 文書番号: REQ-202609040859
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `db_hiroba_qa_init`（`src/main.py`）, `terraform/deploy`（`src/commands.py`・`src/__main__.py`）, `terraform/migrate.bat`（新設）
- 変更なしのコンポーネント: 既存`seed`コマンドのオプション未指定時の動作、`import-data`・`destroy-app`・`destroy-database`コマンド、`terraform/deploy/src/aws.py`（既存の環境変数オーバーライド機構をそのまま再利用する想定）、Terraformのリソース定義（ECSタスク定義・IAM・ECR）、`web_backend`/`knowledge_mcp`/`tag_selector_mcp`等のアプリケーション本体
- 参照資料: `docs/adr/0016-db-hiroba-qa-init-service-separation.md`, `docs/adr/0017-db-hiroba-qa-init-migration-tool-selection.md`, `docs/adr/0018-db-hiroba-qa-init-seed-idempotency-and-startup-order.md`, `docs/adr/0040-deploy-orchestration-containerized-python.md`, `docs/adr/0051-conversation-db-migration-tool-adoption.md`, `docs/adr/0052-chatbot-db-migration-role-separation.md`, `docs/adr/0066-full-data-import-batch-automation-and-overwrite.md`, `docs/requirement/202608061016_DBマイグレーションシード自動化要件定義書.md`, `docs/requirement/202608261002_DBマイグレーション・データインポート機能要件定義書.md`
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照（本書に対応するADRは ADR-0075）

## 1. 目的

現状、AWS環境にデプロイした RDS（`chatbot`・`conversation` データベース）へスキーマ変更（マイグレーション）を反映する手段は、`terraform/deploy` の `seed` コマンド（`db_hiroba_qa_init` の ECS ワンショットタスク実行）のみである。このタスクは、ロール作成・マイグレーション適用に加えて、`chatbot` データベースへのシードデータ投入（QA原本・言い換え質問・カテゴリの投入、embedding計算を伴いうる処理）を常に一体で実行する。

一方、運用上は QA・検証データの投入・更新を `import-data`（全消去→上書き投入、ADR-0066）で行うことが多く、`seed` が投入したシードデータは、その後 `import-data` 実行時にまとめて上書き・破棄される。そのため、スキーマ変更のみを RDS に反映したい場合にも、事後的に捨てられる不要なシード処理を伴う `seed` を実行せざるを得ず、実行時間・コスト（embedding計算等）の両面で無駄が生じている。

本書は、AWS 上の RDS に対して、`destroy-app`・`destroy-database` 等の破壊的操作は伴わず、かつ不要なシード処理も伴わずに、**マイグレーション適用のみ**を実行できる機能（新規 `migrate` コマンド、および既存 `seed` コマンドへのシードスキップオプション）を新設するための要件を定義する。

## 2. 背景・参照資料

### 2.1 現状のコマンド構成（調査結果）

`terraform/deploy` の CLI（`__main__.py`）が提供するサブコマンドは次の9個であり、破壊的操作（`destroy-app`・`destroy-database`）とマイグレーション適用（`seed` 経由）は元々完全に別のサブコマンドとして分離されている。

| コマンド | 概要 |
|---|---|
| `bootstrap` | state用S3バケット作成 |
| `apply-database` / `apply-app` / `apply-all` | Terraform apply（ネットワーク・RDS・ECS等） |
| `seed` | `db_hiroba_qa_init` の ECS ワンショットタスクを起動（ロール作成→マイグレーション→シード→権限付与、6ステップ一体） |
| `import-data` | 全消去→上書き投入（ADR-0066、`IMPORT_MODE` 環境変数オーバーライドで同一タスクを起動） |
| `destroy-app` / `destroy-database` | Terraform destroy（`confirm_typed` による型入力確認あり） |
| `shell` | デバッグ用シェル |

`db_hiroba_qa_init`（`src/main.py`）の通常起動（`main()`）は、次の6ステップを常に一体で実行する。

1. chatbot ロール作成（migrator/app、ADR-0052）
2. chatbot マイグレーション適用（yoyo, ADR-0017）
3. **chatbot シード投入**（QA原本・言い換え質問・カテゴリ、embedding計算を伴いうる）
4. chatbot app ロールへの DML 権限付与
5. conversation データベース作成→ロール作成→マイグレーション適用（yoyo, ADR-0051）→権限付与
6. エクスポート専用読み取りロール作成（ADR-0046）

このうち、マイグレーション適用は手順2・5のみであり、手順3（シード投入）とは元々main.py内では独立した関数呼び出しである。

### 2.2 IMPORT_MODE の既存前例（ADR-0066）

`import-data` コマンドは、`db_hiroba_qa_init` と同一のイメージ・同一の ECS タスク定義（`db_init_task_family`）を再利用し、`run-task` のコンテナ環境変数オーバーライドで `IMPORT_MODE=true` を注入することで、通常起動とは異なる処理（全消去→上書き投入）に分岐させている（`terraform/deploy/src/aws.py` の `run_import_task` が汎用の environment オーバーライド機構として既に実装済み）。新規のECSタスク定義・ECRイメージを追加することなく、`main.py` 内の分岐追加と `terraform/deploy` の新規サブコマンド追加のみで実現している。本書が新設する「マイグレーション専用実行」も、同型のアプローチを踏襲する。

### 2.3 コスト面の課題（ユーザー確認）

- QA・検証データの投入・更新は `import-data.bat` で行うことが多く、`seed` が投入するシードデータは事後的に上書きされるため、スキーマ変更適用のためだけに `seed` を実行するのは費用対効果が悪い。

### 2.4 発注者との確認済み方針（2026-09-04）

1. **実装方針**: 新規 `migrate` コマンドを新設し、かつ既存 `seed` コマンドにもシードスキップ用のオプション（`--skip-seed`）を追加する（両方実装する）。
2. **マイグレーション専用モードの処理範囲**: `db_hiroba_qa_init` の6ステップのうち、シード投入（2.1節の手順3）のみを除外し、ロール作成・マイグレーション適用（両データベース）・権限付与・エクスポート専用ロール作成は通常どおり実行する。
3. **実行基盤**: 新規のECSタスク定義・ECRイメージは作成せず、既存の `db_hiroba_qa_init` イメージ・タスク定義（`db_init_task_family`）を再利用し、環境変数によるモード切替（IMPORT_MODEと同様の方式）で実現する。
4. **実行確認**: マイグレーション専用モードの実行は非破壊的操作であるため、`destroy-*`・`import-data` のような型入力確認（`confirm_typed`）は設けず、既存の `seed` と同様に確認プロンプトなしで実行できるようにする（無人実行可）。
5. **対象データベース**: `chatbot`・`conversation` の両データベースを対象とする（片方のみに限定するオプションは本書のスコープでは設けない）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| マイグレーション専用モード（`MIGRATE_ONLY`、仮称） | `db_hiroba_qa_init` に新設する起動モード。通常起動の6ステップからシード投入（手順3）のみを除外して実行する |
| `migrate` コマンド | `terraform/deploy` に新設するサブコマンド。マイグレーション専用モードで `db_hiroba_qa_init` の ECS ワンショットタスクを起動する |
| `migrate.bat` | `migrate` コマンドに対応する、ダブルクリック起動用バッチファイル（既存 `seed.bat` 等と同じ導線、ADR-0040） |
| `--skip-seed` オプション | 既存 `seed` コマンドに追加するオプション。指定時は `migrate` コマンドと同じくマイグレーション専用モードで起動する |
| `db_init_task_family` | `db_hiroba_qa_init` の ECS タスク定義ファミリー名（Terraform出力）。`seed`・`import-data`・`migrate` のいずれも同一のタスク定義を `run-task` で起動する |

## 4. スコープ

### 4.1 対象範囲

- `db_hiroba_qa_init`（`src/main.py`）へのマイグレーション専用モード（環境変数分岐）の追加。
- `terraform/deploy` への新規サブコマンド `migrate` の追加（`commands.py` の `cmd_migrate`、`__main__.py` への登録）。
- 既存 `seed` サブコマンドへの `--skip-seed` オプション追加。
- 対応する `terraform/migrate.bat` の新設方針の明文化（実装フェーズでの作業内容として整理する。バッチファイル自体の作成は本書のスコープに含む）。
- ローカル `docker-compose` 環境・AWS環境の両方で、同一のモード分岐ロジック（`db_hiroba_qa_init` イメージ）が動作すること。

### 4.2 対象外（将来検討・別スコープ）

- `chatbot`・`conversation` のいずれか一方のみを対象にマイグレーションを適用するオプション（`import-data` の `--target` のような選択機能）。2.4節#5により両データベース一律実行とする。
- マイグレーション専用モードにおけるロール作成・権限付与・エクスポート専用ロール作成ステップの省略（2.4節#2により、シード投入以外の全ステップを実行する方針とした）。
- 個々のマイグレーションファイル（yoyo migration）の内容そのものの設計指針（後方互換性のある列追加か等）。本書はモード切替の実行経路のみを対象とする。
- `terraform/README.md` の記述更新、運用手順書への反映等の実装フェーズの文書作業（本書は要件定義・ADRの範囲に留める）。

## 5. 全体アーキテクチャ

### 5.1 実行フロー（変更前 → 変更後）

```
【変更前】
  スキーマ変更をRDSに反映したい場合 → seed 実行（ロール作成→migrate→seed投入→権限付与→conversation migrate→export reader作成）
    → chatbotシード投入（不要な場合でも常に実行される。import-data で後日上書きされる）

【変更後】
  スキーマ変更のみをRDSに反映したい場合
    → migrate 実行（または seed --skip-seed）
       → ロール作成 → chatbot migrate → （シード投入をスキップ） → 権限付与
       → conversation DB作成 → ロール作成 → conversation migrate → 権限付与
       → エクスポート専用ロール作成
  データ投入・更新をしたい場合 → 引き続き import-data を使用（変更なし）
  初回セットアップ等、シードも含めて実行したい場合 → 引き続き seed（オプションなし）を使用（変更なし）
```

### 5.2 コマンドとECS実行タスクの対応

| コマンド | ECSタスク定義 | 環境変数オーバーライド | 実行される処理 |
|---|---|---|---|
| `seed`（オプションなし） | `db_init_task_family`（既存） | なし | 6ステップ全て（シード投入含む） |
| `seed --skip-seed`（新規） | `db_init_task_family`（既存, 変更なし） | `MIGRATE_ONLY=true`（新規） | シード投入以外の5ステップ |
| `migrate`（新規） | `db_init_task_family`（既存, 変更なし） | `MIGRATE_ONLY=true`（新規） | シード投入以外の5ステップ（`seed --skip-seed` と同一結果） |
| `import-data`（既存, 変更なし） | `db_init_task_family`（既存） | `IMPORT_MODE=true` 等（既存） | 全消去→上書き投入（マイグレーションは実行しない） |

`migrate` と `seed --skip-seed` は、同一の `MIGRATE_ONLY` 環境変数分岐を呼び出す2つの入口として意図的に併存させる。前者はダブルクリックで完結する専用の運用導線（既存 `.bat` 群と同じUX）を提供し、後者はスクリプト実行時等に既存の `seed` コマンド体系のままオプションで挙動を切り替えたい場合の手段として提供する。

## 6. 機能要件

### 6.1 `db_hiroba_qa_init` へのマイグレーション専用モード追加

- 環境変数（例: `MIGRATE_ONLY`、真偽値。既存 `IMPORT_MODE` と同じ文字列判定方式を踏襲）を新設する。
- `MIGRATE_ONLY` が真の場合、`main()` の通常フローのうち、chatbot シード投入（`seed_if_empty` 相当）の呼び出しのみをスキップする。それ以外の全ステップ（chatbot ロール作成・chatbot マイグレーション適用・chatbot app 権限付与・conversation データベース作成・conversation ロール作成・conversation マイグレーション適用・conversation app 権限付与・エクスポート専用ロール作成）は通常どおり実行する。
- `MIGRATE_ONLY` が未設定または偽の場合、既存の動作（6ステップ全実行）を完全に維持する（後方互換）。
- 実行完了時・異常終了時のログ出力・終了コードの扱い（正常時0、異常時非0、ADR-0018の方針）は既存の `main()` と同様とする。

### 6.2 新規 `migrate` コマンドの追加

- `terraform/deploy` に新規サブコマンド `migrate` を追加する。
- 処理内容は既存 `cmd_seed` と同型とする: database/app 構成の apply 済み確認 → 構成出力（`private_subnet_ids`・`sg_verification_task_id`・`db_init_task_family`・`cluster_name`）取得 → `db_init_task_family` を対象に `run-task` 起動（環境変数オーバーライド `MIGRATE_ONLY=true` を付与） → `STOPPED` まで待機 → `exitCode` 確認。
- 異常終了時（`exitCode != 0`）は、`seed` と同様にエラーメッセージと CloudWatch Logs ロググループ名を表示して非0終了する。
- 確認プロンプト（`confirm_typed` 等）は設けない。`--yes` 相当の概念も不要（非破壊的操作のため常に無人実行可）。
- 対応するバッチファイル `terraform/migrate.bat` を新設する（既存 `seed.bat` と同じ形式: `deploy/run.bat` 経由で `deploy migrate` を実行する薄いラッパ）。

### 6.3 既存 `seed` コマンドへの `--skip-seed` オプション追加

- `seed` サブコマンドに、既存の `--yes`/`-y` と同様の任意フラグとして `--skip-seed` を追加する。
- 指定時は、`run-task` 起動時に環境変数オーバーライド `MIGRATE_ONLY=true` を付与する（`migrate` コマンドと同一の実行結果になる）。
- 未指定時は、既存の `seed` の動作（環境変数オーバーライドなし）を完全に維持する。

## 7. 非機能要件

| 分類 | 要件 |
|---|---|
| 非破壊性 | マイグレーション専用モードは、スキーマ追加・冪等なロール作成・権限付与のみを行い、既存データの削除・上書きを一切行わない。`destroy-app`・`destroy-database`・`import-data` のいずれの処理経路も呼び出さない |
| 冪等性 | 既存の yoyo-migrations の適用管理（未適用分のみ適用、ADR-0017）、ロール作成の存在チェック（ADR-0052）をそのまま踏襲する。同一環境に対して `migrate` を何度実行しても、2回目以降は「適用対象なし」として安全に完了する |
| コスト | シード投入（embedding計算を伴いうる処理）を伴わないため、`seed` 全体を実行する場合に比べて実行時間・API呼び出しコストを削減できる |
| 後方互換性 | `seed`（オプションなし）・`import-data`・`destroy-app`・`destroy-database`・`apply-all` 等、既存コマンドの動作・呼び出し方は一切変更しない |
| 運用性 | 無人実行可能（確認プロンプトなし）とし、CI/自動化スクリプトからも呼び出せるようにする |
| インフラコスト | 新規のECSタスク定義・ECRリポジトリ・IAMポリシーの追加は行わない（既存 `db_init_task_family` に対する既存の `ecs:RunTask` 権限をそのまま利用する） |

## 8. インフラ・実行環境要件

### 8.1 ローカル docker-compose 環境

- ローカル環境でも同一の `db_hiroba_qa_init` イメージを使うため、`MIGRATE_ONLY` 環境変数をコンテナに渡す手段（`docker compose run` 時の環境変数指定等）を用意する。ローカルでの呼び出し方法（専用スクリプトの要否）は実装フェーズで確定する。

### 8.2 AWS環境

- `terraform/deploy` の `migrate` コマンドが、既存の `db_init_task_family`（`database` 構成の Terraform 出力）に対して `run-task` を実行する。Terraform リソース定義自体の変更は不要と見込む。
- 実行に必要な AWS 権限（`ecs:RunTask`・`ecs:DescribeTasks` 等）は、既存の `seed`・`import-data` コマンドが利用しているものと同一であり、追加の IAM ポリシー変更は不要と見込む。

## 9. 既存システムとの関係・影響範囲

- `db_hiroba_qa_init/src/main.py` の `main()` に環境変数分岐を1箇所追加する。既存の `IMPORT_MODE` 分岐と同様のパターンであり、既存フローへの影響は「シード投入呼び出しをスキップする条件」を挟む範囲に限定される。
- `terraform/deploy/src/commands.py` に `cmd_migrate` を追加し、`cmd_seed` に `skip_seed` 引数を追加する。両者とも既存の環境変数オーバーライド対応 run-task 関数（ADR-0066で実装済みのもの）を呼び出す形にできる見込みであり、`terraform/deploy/src/aws.py` 自体への変更は不要と見込む。
- `terraform/deploy/src/__main__.py` の `build_parser()` に `migrate` サブコマンドの追加、および `seed` サブコマンドへの `--skip-seed` 引数追加が発生する。
- `terraform/README.md`（コマンド一覧・実行手順の説明）、`terraform/migrate.bat`（新設）の追加が実装フェーズで発生する。
- 既存の `seed`・`import-data`・`destroy-app`・`destroy-database`・`apply-all` の動作・呼び出し方には変更がない。

## 10. 受け入れ基準（Definition of Done）

- [ ] AWS環境で `migrate` コマンド（または `seed --skip-seed`）を実行すると、`chatbot`・`conversation` 両データベースの未適用マイグレーションが適用され、シードデータ（QA原本・言い換え質問・カテゴリ）は一切投入・変更されないことを確認する。
- [ ] `migrate` 実行後、chatbot/conversation それぞれの migrator/app ロールへの権限付与、エクスポート専用ロールの作成が、通常の `seed` 実行時と同様に行われていることを確認する。
- [ ] `migrate` を、マイグレーション適用済みの環境に対して再実行しても、エラーにならず「適用対象なし」として正常終了（`exitCode=0`）することを確認する（冪等性）。
- [ ] `migrate` 実行が、`destroy-app`・`destroy-database`・`import-data` のいずれのコード経路も呼び出さないことをコードレビューで確認する。
- [ ] `migrate` 実行に確認プロンプトが表示されず、無人実行できることを確認する。
- [ ] `seed`（オプションなし）・`import-data`・`destroy-app`・`destroy-database` の既存の動作が、本機能追加前後で変化していないことを確認する（回帰確認）。
- [ ] ローカル `docker-compose` 環境でも、同一のマイグレーション専用モードが動作することを確認する。

## 11. Open Issues（要追加確認事項）

1. **ローカル `docker-compose` 環境での呼び出し方法**: AWS向けの `migrate`/`seed --skip-seed` に相当する、ローカル環境での実行手段（専用スクリプトの新設か、`docker compose run` の直接実行を案内するだけか）を実装フェーズで確定する。
2. **環境変数名の最終決定**: 本書では `MIGRATE_ONLY` を仮称として用いているが、実装フェーズで既存の命名規約（`IMPORT_MODE`・`IMPORT_TARGET` 等）との整合を踏まえて最終決定する。
3. **`terraform/README.md` 等の文書更新範囲**: コマンド一覧・実行手順・運用ルール（「スキーマ変更のみの反映は `migrate` を使う」等）への反映範囲・記述内容は、実装フェーズ（実装指示書）で確定する。
4. **CloudWatch Logs 上での `migrate` 実行の識別**: `seed`・`import-data`・`migrate` がいずれも同一ロググループ（`/ecs/db_init_task_family`）に出力されるため、実行種別をログ本文以外（タスクのタグ付け等）で識別する必要があるかは、運用要件次第で別途検討する。
