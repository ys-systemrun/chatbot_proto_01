# db_hiroba_qa_init（DBマイグレーション・シード専用サービス）要件定義書

- 文書番号: REQ-202608061016
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: db_hiroba_qa_init（新規）, db_hiroba_qa（既存、責務縮小）, web_backend（既存seed機能の移管）, knowledge_mcp（既存 `migrations/` の統合）, tag_selector_mcp（既存 `migrations/` の統合）, docker-compose.yml, .env.example, README.md
- 参照資料: `docs/requirement/202608041002.md`（Knowledge MCP サーバ要件）, `docker-compose.yml`, `README.md`「Knowledge MCP サーバ」「Tag Selector MCP サーバ」節（既存の手動migration手順）
- 前提の決定事項: 本書末尾「14. 関連ADR一覧」参照

## 1. 目的

現状、`db_hiroba_qa`（PostgreSQL + pgvector, コンテナ名 `chatbot_db`）のスキーマ作成は、利用する embedding モデルに対応するフォルダ（`db_nomic/init.sql` または `db_multilingual/init.sql`）を PostgreSQL 公式イメージの `docker-entrypoint-initdb.d` に読み込ませる方式で行われている。この方式は **データディレクトリが空の初回起動時にしか実行されない** ため、スキーマ変更（テーブル追加・列追加）は `knowledge_mcp/migrations/` や `tag_selector_mcp/migrations/` 配下の一回限りのSQLファイルを `docker compose exec ... psql ...` で運用者が手動適用する運用になっている。また、初期データ投入（シード）も `web_backend` の `seed` 系スクリプトを手動実行する運用であり、いずれも「コンテナを作ればすぐ使える」状態にはなっていない。

本書は、この「スキーマ作成（マイグレーション）」と「初期データ投入（シード、embedding計算を含む）」の責務を、`db_hiroba_qa` および `web_backend` から切り出し、`db_hiroba_qa_init` という専用の一時的（ワンショット）サービスに集約するための要件を整理する。コーディングは対象外とし、要件定義および設計判断（ADR）の整理にとどめる。

## 2. 背景・参照資料

### 2.1 現行のスキーマ作成方式とその課題

- `docker-compose.yml` の `db_hiroba_qa` サービスは、`./${DB_DIR:-db_nomic}/init.sql` を `/docker-entrypoint-initdb.d/init.sql` にマウントしている。PostgreSQL公式イメージの仕様上、このディレクトリ配下のスクリプトは **データディレクトリ（`/var/lib/postgresql/data`）が空の場合にのみ** 実行される。
- そのため、稼働中の環境にスキーマ変更を反映する手段として、`knowledge_mcp/migrations/0001_add_title_and_tag_tables.sql` / `0002_add_question_altered_is_primary.sql`、`tag_selector_mcp/migrations/0001_add_tag_description_and_alias.sql` が個別に作成され、README「事前準備（DBスキーマ移行）」節の手順に従って運用者が `docker compose exec -T db_hiroba_qa psql -U postgres -d chatbot < <file>` を手動実行する運用になっている。
- これらの手動migrationには、**どこまで適用済みかを追跡するテーブルや仕組みが存在しない**。適用漏れ・二重適用の防止は、README手順を運用者が順守すること、および各SQLが `IF NOT EXISTS` 等で書かれていることに依存している。
- この課題を裏付ける実例として、`db_nomic/init.sql` と `db_multilingual/init.sql` の内容には既にドリフト（差分）が生じている。`db_nomic/init.sql` には `qa_original.title`、`tag`／`qa_tag`／`tag_alias` テーブル、`question_altered.is_primary` 列が存在するが、`db_multilingual/init.sql` にはこれらが存在しない。これは、上記の手動migrationが稼働中の `db_nomic` 環境にのみ適用され、チェックイン済みの `init.sql` 側（特に `db_multilingual`）へ反映されなかった結果と考えられる。本要件が解決しようとしている「手動運用によるスキーマの一貫性維持コスト」が、既に実際の不整合として表出している。

### 2.2 現行のシード方式とその課題

- `web_backend` は `pyproject.toml` の `[project.scripts]` で `seed` / `seed_category` / `seed_qa_original` / `seed_question_altered` を公開しており、実体は `web_backend/main/seed.py` から `web_backend/src/seed_helpers.py`（CSV/JSON読込）・`web_backend/src/embedding.py`（LM Studio embedding API呼び出し）・`web_backend/src/db.py`（INSERT）を呼び出す構成である。
- 各シード関数は、対象テーブルにレコードが1件でも存在する場合は投入をスキップする（`DB.exists_category` / `exists_qa_original` / `exists_question_altered`）。この「テーブル単位の存在チェック」による冪等性は、既に実装済みであり、本要件でも踏襲する（8.2節、ADR-0018）。
- `main_seed_question_altered` は、CSVの各行に埋め込みベクトルが未設定の場合、`get_embedding()`（LM Studio の `/v1/embeddings` 互換エンドポイント呼び出し）で1行ずつ計算してから投入する。
- 現状、これらのスクリプトは `web_backend` コンテナ起動後に運用者が手動で実行するものであり、README「利用前に」節の手順3に「シーディング(不要な場合スキップ)」という記載がある通り、コンテナ作成だけでは投入が完了しない。
- 投入済みデータの永続化自体は、`db_hiroba_qa` の PostgreSQL データディレクトリが `./${DB_DIR}/data` にバインドマウントされていることで、既に実現されている（`docker compose down` / `up` を跨いでデータは保持される）。本要件の「シードが毎回は回らないようにする」は、**この既存の永続化ボリュームと、既存の存在チェックによる冪等性をそのまま活用する** ことで満たす（新たな永続化機構を別途作る必要はない。8.2節）。

### 2.3 埋め込みモデルによるスキーマ差異

- `question_altered.embedding` の次元数（`VECTOR(N)`）は使用する embedding モデルに依存する（`db_nomic`: 768次元 = nomic-embed-text-v1.5、`db_multilingual`: 384次元）。`.env` の `DB_DIR` でどちらのフォルダ（データボリューム）を使うか切り替える現行方式は変更しない前提とする（README `.env` 設定項目表）。
- 本書が扱う `db_hiroba_qa_init` は、この `DB_DIR` の選択と整合する形で、対象の embedding モデルに応じた次元でスキーマを作成できる必要がある（6.2節、ADR-0017 Open Issue参照）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| `db_hiroba_qa_init` | 本書で新設する、マイグレーション実行とシード実行のみを行う一時的（ワンショット）サービス。処理完了後は正常終了（exit code 0）し、常駐しない |
| マイグレーション | `CREATE TABLE` / `ALTER TABLE` / `CREATE EXTENSION` 等、スキーマを段階的に変更するための、適用履歴を追跡可能な処理単位 |
| シード | `category` / `qa_original` / `question_altered` 等への初期データ投入。`question_altered` の投入時は embedding 計算を伴う |
| 存在チェック（exists check） | 対象テーブルに1件以上データが存在するかを確認し、存在する場合はシードをスキップする現行の冪等性確保方式（`DB.exists_*`） |
| ワンショットサービス | コンテナ起動後に一度だけ処理を実行して終了する、常駐プロセスを持たない Docker Compose サービス |

## 4. スコープ

### 4.1 対象範囲

- a. `db_hiroba_qa_init` サービスの新設（Docker Compose定義、起動時にマイグレーション→シードを順に実行し終了する）。
- b. マイグレーションツール・ライブラリの選定と、それによる `CREATE EXTENSION vector` / `CREATE TABLE` / 既存テーブルへの列追加の実行（現行の `db_nomic/init.sql`・`db_multilingual/init.sql`、および `knowledge_mcp/migrations/`・`tag_selector_mcp/migrations/` に存在する内容を、単一のマイグレーション履歴に統合する）。
- c. マイグレーション完了後、テーブルにデータが存在しない場合のみシードを実行する処理（現行の `web_backend/main/seed.py` 系の責務の `db_hiroba_qa_init` への移管）。
- d. シード時の embedding 計算（現行の `web_backend/src/embedding.py` 相当の呼び出しの移管）。
- e. `db_hiroba_qa` の起動を待ってから `db_hiroba_qa_init` を実行し、さらに `web_backend` / `knowledge_mcp` / `tag_selector_mcp` が `db_hiroba_qa_init` の完了を待って起動する、Docker Compose上の起動順序制御。
- f. 上記変更に伴う `docker-compose.yml` / `.env.example` / README の記載整合（項目定義のみ。実際の記述変更は実装フェーズ）。

### 4.2 対象外（将来検討・別プロジェクトスコープ）

- 実際のマイグレーションファイル・シードスクリプトのコーディング、Dockerfile作成等の実装作業（本書は要件定義・ADRの整理までを対象とする）。
- `qa_original` / `question_altered` 等のスキーマ自体の変更（列追加等）。本書は「スキーマ作成の実行方式」を変更するものであり、スキーマの内容変更は対象外。
- embedding計算をローカルLLM（LM Studio）以外（Amazon Bedrock, OpenAI等）で行うための抽象化・切り替え機構の実装（13章 Open Issue #1）。
- 認証・権限管理、マイグレーション実行ユーザーの権限分離（現行同様、単一の `postgres` スーパーユーザーで動作する前提を維持する。13章 Open Issue #4）。
- 既存の `knowledge_mcp/migrations/backfill_title_and_tags.py`、`tag_selector_mcp/migrations/seed_description_and_aliases.py` の内容そのものの見直し（本書はこれらを `db_hiroba_qa_init` のシード処理へ統合する方針までを扱い、内容の妥当性再検証は対象外とする）。

### 5.1 システム構成（変更後）

```
                        docker compose up
                              │
                              ▼
                     ┌──────────────────┐
                     │  db_hiroba_qa      │  PostgreSQL + pgvector

                     │  2. seed if empty   │  存在チェック→未投入なら
                     │     (embedding計算) │  embedding計算しつつ投入
                     │  exit 0             │
                     └─────────┬────────┘
              depends_on       │ condition: service_completed_successfully

┌───────────┐         ┌───────────────┐        ┌────────────────────┐
│ web_backend │         │ knowledge_mcp   │        │ tag_selector_mcp     │
│ (既存seed    │         │ (既存migrations │        │ (既存migrations       │
│  機能は撤去) │         │  手動適用は撤去) │        │  手動適用は撤去)      │
└───────────┘         └───────────────┘        └────────────────────┘
```

## 6. 機能要件

### 6.1 マイグレーション実行

- `db_hiroba_qa_init` は起動時、マイグレーションツール・ライブラリ（選定はADR-0017）を用いて、未適用のマイグレーションを検出し、適用順に実行する。
- マイグレーションの適用状況は、DB内の追跡テーブル（マイグレーションツールが管理するもの）に記録され、`db_hiroba_qa_init` が何度再起動・再作成されても、未適用分のみが実行される（毎回全件再実行にはならない）。
- 対象範囲は、現行 `db_nomic/init.sql` 相当のスキーマ一式（`qa_original`, `question_altered`, `category`, `tag`, `qa_tag`, `tag_alias` と各インデックス、`CREATE EXTENSION vector`）に加え、`knowledge_mcp/migrations/0001`・`0002`、`tag_selector_mcp/migrations/0001` の内容を、単一のマイグレーション履歴として統合する（4.1節）。
- 既にこれらの手動SQLを適用済みの既存環境（開発者のローカル `db_nomic/data` 等）に対して本方式を導入した場合の整合性確保方法は、13章 Open Issue #2で扱う。

### 6.2 embedding モデル差異への対応

- `question_altered.embedding` の次元数は `.env` の `DB_DIR`（使用する embedding モデル）に応じて異なる（2.3節）。マイグレーション実行時、対象の次元数を正しく反映してテーブル・列を作成できることを要件とする。
- 具体的な実現方法（例: モデル別に独立したマイグレーション履歴を持つか、次元数のみを環境変数でパラメータ化した単一の履歴を持つか）はADR-0017で検討する。後者を採用する場合、2.1節で確認された「モデル別ファイルの内容drift」というリスクそのものを解消できる点を評価基準に含める。

### 6.3 シード実行（存在チェック＋条件付き実行）

- マイグレーション正常終了後、`db_hiroba_qa_init` は `category` → `qa_original` → `question_altered` の順で、各テーブルの存在チェック（既存の `exists_*` 相当）を行い、データが存在しないテーブルにのみ投入を行う（既存 `main_seed_all` の処理順序・冪等性を踏襲）。
- 一部テーブルのみ投入済み（前回実行が途中で失敗した等）の状態からの再実行時も、投入済みテーブルはスキップされ、未投入テーブルのみ投入が行われることを維持する。
- `knowledge_mcp/migrations/backfill_title_and_tags.py`、`tag_selector_mcp/migrations/seed_description_and_aliases.py` が担っている「既存データへの `title` 補完」「`tag.description` / `tag_alias` の暫定投入」も、同様に冪等な処理として本サービスのシードフローに統合する（4.1節）。

### 6.4 embedding計算

- `question_altered` のシード時、埋め込みベクトルが未設定の行について、既存の `get_embedding()` 相当の呼び出し（LM StudioのOpenAI互換 `/v1/embeddings` エンドポイント）で計算してから投入する。
- embedding計算元をローカルLLM以外（Amazon Bedrock, OpenAI等）に切り替える抽象化は、既存の `web_backend/src/llm/format_query_to_embed.py` / `format_query_to_embed_bedrock.py`（クエリ整形LLMの抽象化パターン）を参考に将来検討できるが、本書のスコープには含めない（4.2節、13章 Open Issue #1）。

### 6.5 起動順序制御

- `db_hiroba_qa_init` は `db_hiroba_qa` が `service_healthy` になった後に起動する。
- `web_backend` / `knowledge_mcp` / `tag_selector_mcp` は、`db_hiroba_qa_init` が正常終了（`service_completed_successfully`）した後に起動する（現行の `db_hiroba_qa: condition: service_healthy` への依存に加える、または置き換える。詳細はADR-0018）。
- `db_hiroba_qa_init` がマイグレーションまたはシードの途中でエラー終了（exit code 非0）した場合、依存する各サービスは起動しない。これにより、スキーマ未作成・未シードのDBに対してアプリケーションが接続する事態を防止する。

## 7. データ要件

### 7.1 対象スキーマ（現行 `db_nomic/init.sql` + 既存手動migration適用後の状態を正本とする）

```sql
qa_original(uuid TEXT PK, title TEXT, question_text TEXT, answer_text TEXT, category_id INTEGER)
question_altered(id SERIAL PK, qa_id TEXT, text TEXT, embedding VECTOR(N), is_primary BOOLEAN NOT NULL DEFAULT false)
category(id INTEGER PK, name TEXT)
tag(id SERIAL PK, name TEXT UNIQUE, parent_tag_id INTEGER, description TEXT)
tag_alias(id SERIAL PK, tag_id INTEGER, alias TEXT UNIQUE)
qa_tag(qa_id TEXT, tag_id INTEGER, PRIMARY KEY(qa_id, tag_id))
```

`VECTOR(N)` の `N` は使用する embedding モデルに依存する（768: nomic-embed-text-v1.5, 384: multilingual系モデル）。`db_multilingual` 側は現時点で `title` / `tag` / `qa_tag` / `tag_alias` / `is_primary` が未適用であり、本書のマイグレーション統合によりこの差分は解消される。

### 7.2 マイグレーション適用履歴データ

- マイグレーションツールが内部で管理する追跡テーブル（ツール依存、例: `_yoyo_migration` / `_yoyo_log` 等）を、`db_hiroba_qa`（`chatbot` データベース）内に保持する。このテーブル自体もマイグレーションツールが自動作成するため、本書で個別にスキーマ定義は行わない。

### 7.3 シードデータソース

- 現行と同様、`CSV_DATA_DIR` 配下の `QA_ORIGINAL_FILE`（JSON）・`QUESTION_ALTERED_FILE`（CSV）・`CATEGORY_FILE`（CSV）を読み込む（README `.env` 設定項目表を参照）。データソース自体の変更は本書の対象外。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 冪等性 | `db_hiroba_qa_init` は何度再作成・再実行されても、未適用のマイグレーションのみを適用し、未投入のシードデータのみを投入する。全件の再実行・重複投入を発生させない |
| データ永続化 | シード済みデータは `db_hiroba_qa` の既存の永続化ボリューム（`./${DB_DIR}/data`）にのみ依存して保持される。`db_hiroba_qa_init` 自身は状態を持たず、揮発してよい |
| 障害時の安全性 | マイグレーションまたはシードが途中で失敗した場合、`db_hiroba_qa_init` は非0で終了し、後続サービスを起動させない。再実行により、成功済みの処理はスキップされ未完了分のみ再試行される（8.1節の冪等性に依存） |
| 起動時間 | 初回起動（未シード状態からの全件投入、embedding計算を含む）は、投入件数・embedding計算のレイテンシに比例して時間を要することを許容する。2回目以降（シード済み）の起動は、マイグレーションの差分チェックのみで完了し、大幅に短縮される |
| ログ | マイグレーション・シードの実行ログは `docker compose logs db_hiroba_qa_init` で確認できる（現行の `seed.py` の `print` ベースのログ出力方針を踏襲） |
| 運用手順 | README「利用前に」節・「事前準備（DBスキーマ移行）」節の記載を、手動手順の説明から「`docker compose up` で自動的に完了する」旨の説明へ更新する必要がある（10章） |

## 9. インフラ・実行環境要件

### 9.1 Docker Compose 起動順序制御

- `depends_on` の `condition: service_completed_successfully` を用いた一時的サービスへの依存指定には、Docker Compose のバージョン要件がある。実装フェーズ着手前に、開発者・CI環境で使用している Docker Compose のバージョンが対応しているかを確認する必要がある（13章 Open Issue #3）。

### 9.2 環境変数（想定、詳細設計時に確定）

| 変数名 | 説明 |
|---|---|
| DATABASE_URL | `db_hiroba_qa_init` が接続するDB。現行 `web_backend` と同一の接続文字列を再利用する想定 |
| CSV_DATA_DIR, QA_ORIGINAL_FILE, QUESTION_ALTERED_FILE, CATEGORY_FILE | 現行 `web_backend` から `db_hiroba_qa_init` へ移管する（10章） |
| LMSTUDIO_EMBEDDING_URL, MODEL_EMBEDDING | 現行 `web_backend` から `db_hiroba_qa_init` へ移管する（10章） |
| DB_DIR | 既存同様、使用する embedding モデル（データボリューム）の選択に用いる。`db_hiroba_qa_init` 側でも同じ値を参照し、マイグレーション内容（6.2節）・シードデータの整合を取る |

### 9.3 コンテナイメージ・ビルド

- `db_hiroba_qa_init` は `knowledge_mcp` / `tag_selector_mcp` と同様、専用ディレクトリ（例: `db_hiroba_qa_init/`）に `Dockerfile` を持つ独立サービスとする想定（実装フェーズで確定）。

## 10. 既存システムとの関係・影響範囲

- **`web_backend`**: `pyproject.toml` の `[project.scripts]` から `seed` / `seed_category` / `seed_qa_original` / `seed_question_altered` を撤去し、`main/seed.py`・`src/seed_helpers.py` の責務を `db_hiroba_qa_init` へ移管する。`src/embedding.py`（`get_embedding`）は、チャット機能（`/ask` 等、クエリのembedding計算）でも使用されているため、完全な撤去ではなく、シード用途のコード（`main/seed.py` 等）のみを移管対象とする。
- **`knowledge_mcp` / `tag_selector_mcp`**: `migrations/` 配下のSQLファイル・バックフィル/暫定シードスクリプトを `db_hiroba_qa_init` のマイグレーション履歴・シード処理へ統合し、各サービスのディレクトリからは撤去する。README「事前準備（DBスキーマ移行）」節の手動適用手順（`docker compose exec -T db_hiroba_qa psql ...`）は不要になる。
- **`docker-compose.yml`**: `db_hiroba_qa_init` サービスの追加、`db_hiroba_qa` の `init.sql` ボリュームマウントの削除、`web_backend` / `knowledge_mcp` / `tag_selector_mcp` の `depends_on` に `db_hiroba_qa_init: condition: service_completed_successfully` を追加。
- **README.md**: 「利用前に」節の手順3、「Knowledge MCP サーバ」「Tag Selector MCP サーバ」の「事前準備」節の記載を、自動化後の運用に合わせて更新する必要がある。
- **既存データへの影響**: 既にシード済み・手動migration適用済みの開発環境（既存の `db_nomic/data`）に対する移行方法は、13章 Open Issue #2 で別途整理する。本書の変更は、あくまで「今後の起動時の自動化」を目的とし、既存ボリュームのデータを破壊・再投入するものではない。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] `docker compose up` を実行するだけで（`db_nomic/data` 等が空の新規環境において）、`db_hiroba_qa_init` がマイグレーションとシードを自動実行し、正常終了する。
- [ ] シード完了後に再度 `docker compose up`（または `db_hiroba_qa_init` の再作成）を行っても、既存データの重複投入・エラーが発生しない。

## 13. Open Issues（要追加確認事項）

1. **embedding計算のプロバイダ抽象化**: 現状 `web_backend/src/embedding.py` はLM Studio固定であり、Amazon Bedrock / OpenAI 等への切替機構は存在しない（チャット応答生成・クエリ整形にはBedrock版クラスが既に存在するが、embedding計算には対応するBedrock/OpenAI実装がない）。`db_hiroba_qa_init` のシード処理をどのプロバイダ抽象に合わせて設計するかは、本プロジェクト全体の「ローカルLLM/Bedrock/OpenAI対応」方針の確定と合わせて別途検討する。
2. **既存環境（手動migration適用済み）との整合**: 既に `knowledge_mcp/migrations/0001`・`0002`、`tag_selector_mcp/migrations/0001` を手動適用済みの開発環境に対し、マイグレーションツール導入後に同内容を「未適用」として再実行してしまわないか（あるいは逆に、ツールの追跡テーブルが存在しないことで毎回適用を試みてエラーになるか）を確認し、既存環境向けの移行手順（ベースライン化等）を別途整理する必要がある。
3. **Docker Compose バージョン要件**: `condition: service_completed_successfully` の利用可否について、開発者・CI環境のDocker Composeバージョンを確認する必要がある。対応していない環境がある場合、代替の起動順序制御方式（例: エントリポイントスクリプトでの待機処理）を検討する。
4. **マイグレーション実行ユーザーの権限**: 現行は `postgres` スーパーユーザーで全処理を行う前提だが、将来的に本番運用を見据えた際、マイグレーション専用ユーザーとアプリケーション用ユーザーを分離すべきかは別途検討課題とする（既存要件定義書のアクセス制御関連Open Issueと同種の課題）。
5. **LM Studio 等 embedding エンドポイントの起動待ち**: シードが `docker compose up` 時に自動実行されるようになるため、embeddingエンドポイント（LM Studio等）が未起動の状態で `db_hiroba_qa_init` が実行されるとシードが失敗する。起動前提条件のドキュメント化のみで十分か、リトライ・待機処理を要件に加えるべきかを検討する。
6. **`db_hiroba_qa_init` という名称の確定**: 本書では例示された名称をそのまま用いているが、実装フェーズで最終的なサービス名・ディレクトリ名を確定する。
