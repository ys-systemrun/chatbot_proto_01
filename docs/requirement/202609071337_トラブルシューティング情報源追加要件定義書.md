# トラブルシューティング情報源追加 要件定義書

- 文書番号: REQ-202609071337
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `db_hiroba_qa_init`（migrations・データ投入・シード）, `knowledge_mcp`（新規repository・search_knowledge統合・タグ系repository）, `tag_selector_mcp`（`tag_metadata_repository.py`）, `web_backend`（新規controller・`db.py`・`export/tables.py`・`export_controller.py`）, `front_dev`（新規feature・route・domain・`api.ts`）, `docker-compose.yml`（`DATABASE_URL`・`POSTGRES_DB`）, `terraform`（`modules/database` の `db_name`）, `README.md`・`.env.example`
- 変更なしのコンポーネント: conversationデータベース（`conversation`/`message`/`verification_*`）, `hiroba_qa_original`／`hiroba_question_altered`／`hiroba_category`／`hiroba_qa_tag`（テーブル名・列とも変更なし）, `chatbot` を冠する識別子（ロール・シークレット・環境変数名・ダンプファイル名・定数名。ADR-0069の方針を継続）, `web_backend/src/export/dump.py`（汎用実装）
- 参照資料: ADR-0005（タグの関連テーブル化）, ADR-0006（タグ管理ツール）, ADR-0008（タグ知識ベースの正本）, ADR-0018（シード冪等性）, ADR-0034（シード元データのイメージ同梱）, ADR-0058（祖先タグ展開）, ADR-0059（タグ構成類似度スコアリング）, ADR-0069（DB名再編・`hiroba_`接頭辞付与）, ADR-0072〜0074（タグフォルダ・表示順序）, REQ-202609010935, REQ-202609021050（タグ運用ガイドライン）
- 前提の決定事項: 本書16章「関連ADR一覧」参照。本書に対応するADRは ADR-0076〜ADR-0079。

## 1. 目的

現在のチャットボットは、ユーザーサポート「維津美の広場」由来のQAデータ（`hiroba_qa_original` 系6テーブル）のみを情報源として質問に応答している。発注者は、これとは別の情報源として次の2つの静的HTML文書（Redmine Wikiのミラーで、社内スタッフによりトラブル事例が随時追記される）を新たにチャットボットの回答材料として利用したい。

- `db_hiroba_qa_init/data/trouble_shooting.html`（維津美V7システム全般のトラブルシューティング、35トピック）
- `db_hiroba_qa_init/data/trouble_shooting_netauth.html`（ネット認証まわりのトラブルシューティング、30トピック）

発注者からは、この新情報源を維津美の広場QAデータとは**別テーブル**で管理しつつ、**タグ情報は共有**したいという方針が示された。本書は、この新情報源の追加を実現するためのデータモデル・DB配置・検索(RAG)統合・管理UI・データ投入方式を要件として定義する。

## 2. 背景・調査結果

### 2.1 対象HTMLファイルの構造（実測）

両ファイルとも同一のテンプレート構造を持つ（ファイル冒頭のコメントにテンプレート定義がある）。`<h2>` 見出し1つが1トラブル事例（または1手順記事）に対応し、多くは次の固定フィールドを持つ `<table>` を内包する。

| フィールド | 意味 | 記入率（実測） |
|---|---|---|
| 現象 | 症状の要約 | ほぼ全件 |
| 操作履歴 | 発生時の操作手順 | 空欄（`-`）が多い |
| エラーコード | エラーコード | 空欄が多い |
| エラーメッセージ | 実際のエラーメッセージ文字列 | 記入あり |
| システム環境 | OS等の環境情報 | 空欄が多い |
| ハードウェア環境 | ハードウェア情報 | 空欄が多い |
| バージョン情報 | 製品バージョン | 空欄が多い |
| ユーザーに案内すべき内容 | 顧客対応時に案内する回答本文 | 記入あり（最重要フィールド） |
| 原因 | 原因の説明 | 記入あり |
| 備考 | 補足メモ | 記入あり |
| キーワード | フリーテキストのキーワード | **`trouble_shooting.html`で35件中4件、`trouble_shooting_netauth.html`で30件中2件のみ記入**。自動タグ化の元データとしては不十分 |
| 最終更新日時 | `YYYY-MM-DD HH:MM` 形式の日時 | ほぼ全件 |

一方、各ファイル冒頭の数トピック（例:「サポートページへのアクセス」「ファイアウォールの設定」「遠隔操作の開始手順」）は上記テーブル形式を持たず、`<h3>` によるサブ見出しと `<ol>`/`<p>` の自由記述のみで構成される手順書スタイルである。**構造は事例ごとに完全一様ではない**ため、インポート設計はテーブル形式・自由記述形式の両方を吸収できるものにする必要がある。

### 2.2 既存アーキテクチャとの整合性（重要な既存資産）

調査の結果、既存の `knowledge_mcp` は複数情報源の追加を既に見込んだ抽象化を持っていることが判明した。

- `Document` モデル（`models/document.py`）は `source_type` フィールドを持ち、現状は `"qa"` 固定だが複数種別を想定した設計になっている。
- `SearchService`（`services/search_service.py`）は複数の `Repository` を受け取り、各repositoryの検索結果を統合してscore降順で返す設計であり、docstringに「MVPではQARepositoryのみが渡される想定だが、将来のPDF/Manual追加を見据え、複数repositoryを渡しても動作するよう実装する」と明記されている。
- `QARepository.search()`（`repository/qa_repository.py`）は、祖先タグ展開（ADR-0058）とタグ構成類似度・埋め込み類似度の重み付き合成スコアリング（ADR-0059）を実装済みであり、`hiroba_tag`/`hiroba_qa_tag` を経由してタグを扱う。

この既存設計により、本要件の検索統合は **`SearchService` 自体の変更を必要とせず**、新規 `Repository` を1つ追加してDIで登録するだけで実現できる（5章・8章で詳述）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| トラブルシューティング記事 | `trouble_shooting.html`/`trouble_shooting_netauth.html` 由来の1トピック（`<h2>` 単位）を表すレコード |
| 出自列（`source_key`） | トラブルシューティング記事がどちらのHTMLファイルに由来するかを示す識別子列（例: `trouble_shooting` / `trouble_shooting_netauth`） |
| 共有タグマスタ | 維津美の広場QAとトラブルシューティング記事の両方から参照される、データソース非依存のタグ定義テーブル群（本書で `hiroba_tag` 系から中立名称へリネームする） |
| ソース別コンテンツテーブル | データソースごとの実データを保持するテーブル（`hiroba_qa_original` 等、`troubleshooting_article`） |
| ソース別タグ結合テーブル | ソース別コンテンツと共有タグマスタを結ぶ中間テーブル（`hiroba_qa_tag`、新設する `troubleshooting_article_tag`） |

## 4. スコープ

### 4.1 対象範囲

1. **トラブルシューティング記事テーブルの新設**: `troubleshooting_article`（1テーブル、`source_key`列で出自を区別）と `troubleshooting_article_tag`（共有タグマスタとの中間テーブル）を、維津美の広場QAデータと同一の実データベースに新設する。
2. **共有タグマスタの中立名称化**: `hiroba_tag`/`hiroba_tag_alias`/`hiroba_tag_folder` を `tag`/`tag_alias`/`tag_folder` へリネームし、データソースを問わず共有されるマスタであることを名称面でも明示する。`hiroba_qa_tag`（維津美の広場QA側の結合テーブル）は改名しない。
3. **実データベース名の再改名**: 実DB名を `db_hiroba_qa` → `db_chatbot_knowledge_base` に変更する（サーバ/ホスト名 `db_support_knowledge` は変更しない）。ADR-0069と同方式（再構築＋再インポート）で実施する。
4. **データ投入（インポート）方式の整備**: 両HTMLファイルをパースし、`troubleshooting_article` へ初期投入するインポート処理を要件化する（存在チェックによる冪等投入、ADR-0018踏襲）。
5. **search_knowledge へのマルチソース統合**: `knowledge_mcp` に新規 `TroubleshootingRepository` を追加し、`SearchService` へ登録することで、チャットボットの検索（RAG）がトラブルシューティング記事も対象にする。
6. **管理UI（front_dev/web_backend）の拡張**: トラブルシューティング記事の一覧・編集・タグ付けを行う管理画面を、既存のQA管理UI・タグ管理UIと同様の構成で新設する。

### 4.2 対象外（将来検討・別スコープ）

- conversationデータベース（`hiroba_`接頭辞・今回のリネームいずれの対象外）。
- `chatbot` を冠する識別子（ロール・シークレット・環境変数名・ダンプファイル名・定数名）の名称変更（ADR-0069の方針を継続し据え置く）。
- キーワード欄からの自動タグ抽出・自動タグ付け（記入率が低く実用に耐えないため、タグ付けは人手による運用を前提とする。ADR運用ガイドライン REQ-202609021050 に従う）。
- トラブルシューティング記事の削除機能（初期スコープでは一覧・編集・タグ付けのみとし、削除はQAレコード削除機能（ADR-0067）と同様の設計を要する別要件とする）。
- HTML原本（Redmine Wiki側）との継続的な自動同期（15章 Open Issue #1 参照）。

## 5. 全体アーキテクチャ

### 5.1 DB配置モデル（変更後）

```
PostgreSQLサーバ/ホスト: db_support_knowledge（変更なし）
  └─ 実DB: db_chatbot_knowledge_base（db_hiroba_qa から改名）
       ├─ 【維津美の広場QA・ソース別】
       │    hiroba_category / hiroba_qa_original / hiroba_question_altered / hiroba_qa_tag
       ├─ 【トラブルシューティング・ソース別】（新設）
       │    troubleshooting_article / troubleshooting_article_tag
       ├─ 【共有タグマスタ】（hiroba_接頭辞を除去して中立化）
       │    tag / tag_alias / tag_folder
  └─ 実DB: conversation（変更なし）
  └─（将来）実DB: <別ソース＞（本書のパターンに従わない、実DBそのものを分離する場合の選択肢として残す）
```

タグは `tag`/`tag_alias`/`tag_folder` に一本化され、`hiroba_qa_tag.tag_id` と `troubleshooting_article_tag.tag_id` はいずれも同一の `tag(id)` を参照する。タグの階層（`tag.parent_tag_id`）・フォルダ分類（`tag.folder_id`）・表示順序（`tag.display_order`）は、データソースを問わず単一の体系として運用される。これは発注者の「タグ情報を共有したい」という要求に対する直接的な回答である。

### 5.2 検索（RAG）統合アーキテクチャ

```
agent_invitro ──(MCP)──> knowledge_mcp.search_knowledge
                              │

                              │
                    両者とも Document(id, source_type, title, content, score, metadata) を返す

```

### 5.3 管理UIアーキテクチャ

```

  domain/admin/troubleshooting.ts（新設）
        │ HTTP
web_backend
  main/controllers/troubleshooting_controller.py（新設。qa_controller.py, tag_controller.py と同様の構成）

```

## 6. データモデル仕様

### 6.1 `troubleshooting_article`（新設）

| 列名 | 型 | 説明 |
|---|---|---|
| `id` | SERIAL PRIMARY KEY | 内部ID |
| `source_key` | TEXT NOT NULL | 出自識別子。当面 `trouble_shooting` / `trouble_shooting_netauth` の2値。将来の3つ目のHTML文書追加時は値を増やすだけで対応可（列挙型ではなく自由記入、ただしアプリ側でホワイトリスト管理する） |
| `title` | TEXT NOT NULL | `<h2>` 見出しテキスト |
| `subtitle` | TEXT NULL | `<h3>` サブ見出しテキスト（「Windows11」「TeamViewer」等、ネストしている場合のみ） |
| `symptom` | TEXT NULL | 現象 |
| `operation_history` | TEXT NULL | 操作履歴 |
| `error_code` | TEXT NULL | エラーコード |
| `error_message` | TEXT NULL | エラーメッセージ |
| `system_environment` | TEXT NULL | システム環境 |
| `hardware_environment` | TEXT NULL | ハードウェア環境 |
| `version_info` | TEXT NULL | バージョン情報 |
| `guidance` | TEXT NOT NULL | ユーザーに案内すべき内容（回答本文に相当。テーブル形式を持たない自由記述トピックの場合は本文全体をここに格納する） |
| `cause` | TEXT NULL | 原因 |
| `notes` | TEXT NULL | 備考 |
| `keyword_raw` | TEXT NULL | キーワード欄の原文（自動タグ化はしないが、記入されている場合は参考情報として保持し、管理UIのタグ付け画面に表示する） |
| `body_html` | TEXT NOT NULL | 当該 `<h2>` ブロックの元HTML全体（構造化フィールドへの分解が漏れた情報を失わないためのフォールバック保持） |
| `source_updated_at` | TIMESTAMP NULL | 最終更新日時（`YYYY-MM-DD HH:MM` 形式をパース。パース失敗時はNULLとし原文を`notes`等に退避しない＝失敗を許容し運用側で気付けるようログ出力する） |
| `embedding` | VECTOR(次元数は既存 `hiroba_question_altered.embedding` と同一次元に合わせる) | 検索用埋め込み（8章参照） |
| `created_at` / `updated_at` | TIMESTAMP NOT NULL DEFAULT now() | 管理UI経由の編集監査用 |

一意性制約: `UNIQUE (source_key, title)` — インポート時の冪等判定キーとして用いる（10章）。カテゴリ（`hiroba_category`相当）は新設しない。分類は共有タグのみで行う（発注者の「タグ共有」意図に一本化する）。

### 6.2 `troubleshooting_article_tag`（新設）

| 列名 | 型 | 説明 |
|---|---|---|
| `article_id` | INTEGER NOT NULL REFERENCES `troubleshooting_article(id)` | |
| `tag_id` | INTEGER NOT NULL REFERENCES `tag(id)` | 共有タグマスタを参照 |

`PRIMARY KEY (article_id, tag_id)`。`hiroba_qa_tag` と対称的な構造。

### 6.3 共有タグマスタのリネーム（`hiroba_tag` 系 → 中立名称）

| 変更前 | 変更後 | 備考 |
|---|---|---|
| `hiroba_tag` | `tag` | 列構成は変更なし（`id`/`name`/`parent_tag_id`/`description`/`folder_id`/`display_order`） |
| `hiroba_tag_alias` | `tag_alias` | 列構成は変更なし |
| `hiroba_tag_folder` | `tag_folder` | 列構成は変更なし |

`hiroba_qa_tag.tag_id` の参照先を `tag(id)` に更新する（列名・`hiroba_qa_tag` 自体の名称は変更しない）。ADR-0069の「構文限定置換（`CREATE TABLE`/`INSERT INTO "…"`/`REFERENCES …(`のみを対象とする）」の方針をそのまま踏襲する。詳細はADR-0077参照。

## 7. 実データベース名の再改名仕様

7.1 実DB名を `db_hiroba_qa` → `db_chatbot_knowledge_base` に変更する。サーバ/ホスト名（docker-composeサービス名）`db_support_knowledge` は変更しない。`chatbot` を冠する識別子（ロール`chatbot_app`/`chatbot_migrator`、環境変数`CHATBOT_*`、ダンプファイル名`chatbot.sql`、定数`CHATBOT_TABLES`）は名称を据え置く（ADR-0069踏襲、値のみ`CHATBOT_DB_NAME=db_chatbot_knowledge_base`に更新）。

7.2 移行方式はADR-0069と同一の「再構築＋再インポート」。既存マイグレーションファイルを新名称（テーブル名は現行のまま、DB名は接続設定側の変更のみ）で整合させ、ローカルはボリューム破棄、AWSはDB用stateレイヤ（ADR-0037）のdestroy+applyで作り直す。**AWSでは`var.db_name`変更がRDSインスタンスの置換を伴い、同一インスタンス上のconversationDBも再作成・再投入対象になる**（ADR-0069で一度経験済みのコストの再発生。発注者確認済み、7章のOpen Issueとしては扱わない）。

7.3 併せて6.3節のタグマスタリネームと6.1〜6.2節の新規テーブル追加を、同一の再構築サイクルで一度に適用する（マイグレーションファイルの新規追加・書き換えを1回のリリースにまとめ、rebuildを複数回発生させない）。

7.4 変換済みダンプ（`chatbot.sql`）は、`tag`/`tag_alias`/`tag_folder` への構文限定置換を追加した上で再インポートする。`troubleshooting_article`/`troubleshooting_article_tag` は新設テーブルのためダンプには含まれず、10章のHTMLインポート処理によって別途初期投入する。

詳細な意思決定はADR-0077を参照。

## 8. search_knowledge 統合仕様

8.1 `knowledge_mcp/src/knowledge_mcp/repository/` に `TroubleshootingRepository` を新設する。`QARepository` と同一のインターフェース（`repository/base.py` の `Repository`）を実装し、`SOURCE_TYPE = "troubleshooting"` とする。

8.2 検索クエリは、`troubleshooting_article.embedding <=> query_vec` による近傍探索を基本とし、`QARepository` と同一の祖先タグ展開（`tag`の再帰CTE）・タグ構成類似度（Jaccard係数）・埋め込みスコアとの重み付き合成（ADR-0058・ADR-0059と同一の計算式・同一の環境変数 `TAG_SIMILARITY_WEIGHT` を共用）を適用する。共通ロジックの重複を避けるため、`distance_to_score`/`_jaccard`等のヘルパーは実装フェーズで共通モジュールへ切り出すことを推奨する（本書は設計方針の提示に留め、実装詳細はADR-0078および実装指示書で確定する）。

8.3 埋め込み対象テキストは「記事ごとに単一embedding」方式とする（`hiroba_question_altered` のような言い換え質問の複層構造は持たない）。埋め込み元テキストは `title + subtitle + symptom + cause + guidance` を結合したものを既定とし、`error_message`・`system_environment`等のノイズになりやすいフィールドは含めない。埋め込み対象テキストの具体的な組み立てロジックは実装フェーズで調整可能なパラメータとして扱う。

8.4 `SearchService` への `TroubleshootingRepository` の登録（DI）のみで統合が完了し、`SearchService` 自体の変更は不要（2.2節参照）。`search_knowledge` MCPツールの説明文（`description="ナレッジベース（QA等）を意味検索し…"`）は現状のまま流用可能（「QA等」に含意されているため変更不要）。

8.5 `Document.metadata` にトラブルシューティング記事固有の情報（`source_key`）を含める。`category` は本情報源では存在しないため `None` とする。

詳細な意思決定はADR-0078を参照。

## 9. 管理UI仕様

9.1 `web_backend` に `troubleshooting_controller.py` を新設し、一覧取得・詳細取得・更新・タグ付けのAPIエンドポイントを提供する（`qa_controller.py`/`tag_controller.py`と同様の構成）。新規作成・削除は初期スコープに含めない（10章のインポート処理が唯一の新規作成経路）。

9.2 `front_dev` に `feature/troubleshooting_admin/` を新設し、一覧ページ・編集ページ（現象・原因・案内内容等の構造化フィールドの表示編集、既存のタグツリー選択コンポーネントを流用したタグ付けUI）を実装する。ルーティングは既存の管理画面サブツリー（ADR-0015）に追従する。

9.3 API/UIの命名は、DB層の`troubleshooting_`接頭辞をそのまま反映する（例: `/api/troubleshooting_articles`）。冗長性の判断が必要な場合はQA/タグ同様に詳細設計フェーズで確定する。

詳細な意思決定はADR-0079を参照。

## 10. データ投入（インポート）方式

10.1 両HTMLファイルを `<h2>` 単位でブロック分割し、内包する `<table>` の行から6.1節の構造化フィールドを抽出する。`<table>` を持たないブロック（手順書スタイル）は、`guidance` 列に本文全体を格納し、他の構造化フィールドはNULLとする。いずれのケースでも `body_html` に元HTMLブロック全体を保持する。

10.2 投入は `(source_key, title)` の一意性チェックによる冪等挿入とする（ADR-0018のシード冪等性方針を踏襲）。既存レコードが存在する場合は**上書きしない**（管理UI経由での手動編集・タグ付けを保護するため）。新規追加されたトピックのみを追加投入する。この方針の妥当性は15章 Open Issue #1 で扱う（HTML原本の継続更新との関係）。

10.3 シード元データ（両HTMLファイル）は `db_hiroba_qa_init` イメージに同梱する（ADR-0034踏襲）。投入タイミングは既存の起動時シード処理（ADR-0018の起動順序制御）に追従させる。

10.4 初回投入時点ではタグは一切付与されない（キーワード欄の記入率が低く自動タグ化ができないため）。運用チームが管理UI（9章）経由で、タグ運用ガイドライン（REQ-202609021050）に従いタグ付けを行うことを前提とする。

## 11. 非機能要件

| 分類 | 要件 |

| 一貫性 | `tag`系リネームは`db_hiroba_qa_init`・`knowledge_mcp`・`web_backend`・`tag_selector_mcp`の全SQL・DDL・テストで同一マッピングを用いる |

## 15. Open Issues（要追加確認事項）

1. **HTML原本（Redmine Wiki）との継続更新の関係**: 運用チームは今後、トラブルシューティング記事の追記・修正をどちらで行うか未確定。(a) 引き続きHTML/Redmine Wiki側を正本とし、定期的に再インポートする運用、(b) 初回投入後は管理UI・DBを正本とし、HTML側の更新は追随させない運用、のいずれかを確定する必要がある。10.2節は(b)を前提に「既存レコードは上書きしない」設計としているが、(a)の運用を志向する場合は「HTML側の変更検知・上書き反映（アップサート）」の設計に変更が必要であり、その場合は管理UI側の手動編集が定期的なインポートで失われるリスクをどう扱うか、追加の要件定義が必要になる。
2. **`troubleshooting_article.embedding`の再計算タイミング**: 管理UI経由で`symptom`/`cause`/`guidance`等が編集された場合、embeddingの再計算をいつ行うか（保存時同期再計算・非同期ジョブ・手動トリガー）を詳細設計フェーズで確定する。
3. **監査ログのエンティティ種別ラベル**: `log_admin_operation`等の監査ログにトラブルシューティング記事の操作を記録する場合のエンティティ種別文字列（例:`"troubleshooting_article"`）を確定する。
4. **`tag_selector_mcp`のタグ提案対象**: `select_tags`がトラブルシューティング記事のタグ付け支援にも使えるかは、既存のQA向けタグ提案ロジック（ADR-0009〜0012）がデータソースに依存しない設計であるため利用可能と想定されるが、実装フェーズで動作確認する。
5. **`troubleshooting_article`の削除・出自ファイル自体が廃止された場合の扱い**: 4.2節で今回のスコープ外としたが、運用上必要になった際は別途要件化する。
