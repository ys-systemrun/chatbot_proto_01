# AWS環境向けChatbotUI・会話評価機能有効化要件定義書

- 文書番号: REQ-202608211542（Rev.2: サービス構成をadmin_ui統合方式からagent_invitro分離方式へ変更）
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `agent_invitro`（ChatbotUI・会話評価機能の実処理を新規実装、常駐HTTPサービス化）, `web_backend`（`admin_ui`サービス、`agent_invitro`への薄いリバースプロキシ機能のみ追加）, `front_dev`（既存ビルド資産のAWS配信、変更なし）, `db_hiroba_qa_init`（conversation データベースの新設・スキーマ適用への拡張）, `terraform/`（既存ネットワーク・RDS・ECSリソースの拡張）
- 参照資料: `docs/requirement/202608211014_AWS環境向けQAタグ管理UI要件定義書.md`（以下「QA管理UI要件定義書」）, `docs/requirement/202608100910_MCPサーバークライアントAWSデプロイ要件定義書.md`, `docs/requirement/202608061621_会話エージェント実験要件定義書.md`（agent_invitroの元々の要件定義）
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照
- **改訂履歴**: 初版（Rev.1）は、ChatbotUI・会話評価機能を既存`admin_ui`サービスに直接統合する方式（`web_backend`が実処理を担う）で作成した。ユーザーからの方針転換指示（「admin_uiはfrontend層のみを担当し、agent_invitroを拡張して実処理を担わせたい」）を受け、本Rev.2でサービス構成を全面的に変更した。

## 1. 目的

AWS上のChatbotUI・会話評価機能を、次の役割分担で有効化する。

1. **ChatbotUI**（`front_dev`のルートパス「/」、`POST /ask-sl`）: 製品に関する質問への回答をLLMで生成するメインの会話画面。
2. **会話評価機能**（`POST /evaluate_response`, `GET /evaluated_messages`）: アシスタント回答への👍/👎評価の記録と、評価済み会話の一覧確認ページ。

この2機能の**実処理**（QA類似検索、LLMによる回答生成、会話要約、評価データの読み書き）は、既存の`agent_invitro`（Conversation Agent実験、ADR-0019〜0022）を常駐HTTPサービス化して担わせる。既存の`admin_ui`サービス（QA管理UI要件定義書、ADR-0041/0042）は、静的資産配信とQA・タグ管理BFF（`/api/*`）という既存の役割を維持したまま、ChatbotUI・会話評価機能については`agent_invitro`への薄い中継（リバースプロキシ）のみを行う。これにより、`admin_ui`は実質的に「frontend層」としての位置づけを保ち、チャット関連の業務ロジック・LLM呼び出し・DB接続を持たない。

コーディングは対象外とし、要件定義・ADR整理・実装指示書の作成にとどめる。

## 2. 背景・参照資料

- QA管理UI要件定義書（202608211014）は、`front_dev`本番ビルド資産・`web_backend`を`admin_ui`という単一ECS Fargateサービスとして、社内IPアドレス限定のALB経由でAWS上に展開する構成を確定した（ADR-0041/0042）。
- `web_backend/main/main_stateless.py`には、QA・タグ管理向けの`/api/*`ルータに加えて、ChatbotUI・会話評価機能のエンドポイント（`/ask-sl`, `/evaluate_response`, `/evaluated_messages`）が実装済みである。本書Rev.1では、これらをそのまま`admin_ui`で有効化する方針を検討したが、Rev.2では**この実装をリファレンス（API契約・ロジックの移植元）として扱い、実際の実行主体を`agent_invitro`に変更する**。
- `agent_invitro`（`docs/requirement/202608061621_会話エージェント実験要件定義書.md`、ADR-0019〜0022）は、Knowledge MCP・Tag Selector MCPをMCPクライアントとして呼び出すLangGraph ReActエージェントとして実装済みである。現状は常駐HTTPサーバーではなく、ECS Exec（`docker compose exec agent_invitro ipython`）による対話的な動作確認専用のコンテナという位置づけである（ADR-0019, ADR-0025）。チャット用LLMはAWS環境でAmazon Bedrockへ切り替えることが既に決定・設定済みである（ADR-0031、`terraform/main/app/main.tf`の`module "agent_invitro"`に`LLM_PROVIDER=bedrock`等が既に反映されている）。
- `web_backend/main.py`（旧`/ask`＋`/session`方式、`InMemorySessionStore`）と`front_dev`の`App.tsx`/`api.ts`は、現在の`front_dev`のルーティングでは使用されていないレガシー実装であり、本書の対象外とする（Rev.1からの継続方針、ユーザー確認済み）。
- 会話履歴・評価データを保存する`conversation_db`は、ローカル`docker-compose`環境専用の独立したPostgreSQLコンテナであり、AWS側には対応するデータストアが存在しない（ADR-0044）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| ChatbotUI | `front_dev`のルートパス「/」（`AppStateless`）で提供される、質問応答のメイン会話画面。API契約は既存の`POST /ask-sl`と同一。 |
| 会話評価機能 | アシスタントの回答に対する👍/👎評価の記録（`POST /evaluate_response`）と、評価済み会話の一覧確認ページ（`GET /evaluated_messages`、`front_dev`の`/evaluated_messages`）の総称。 |
| conversation_db | 会話履歴・評価データ（`conversation`/`message`テーブル）を保存するデータストア。AWSでは`chatbot-invitro-rds`上の`conversation`データベース（ADR-0044）。 |
| admin_ui サービス | QA管理UI要件定義書で新設した、`web_backend`と`front_dev`本番ビルド資産を配信するECS Fargateサービス。本書ではChatbotUI・会話評価機能について、`agent_invitro`への薄い中継（リバースプロキシ）のみを追加する（ADR-0045）。 |
| agent_invitro | Conversation Agent実験として実装済みのLangGraph ReActエージェント。本書でECS Fargate上の常駐HTTPサービスとし、ChatbotUI・会話評価機能の実処理を担わせる（ADR-0043）。 |

## 4. スコープ

### 4.1 対象範囲（MVP）

- `agent_invitro`を常駐HTTPサービス化し、`POST /ask-sl`, `POST /evaluate_response`, `GET /evaluated_messages`と同一のAPI契約を実装する（ADR-0043）。ロジックは既存`web_backend`の実装を踏まえつつ、次の点を変更する。
  - QA類似検索は、`chatbot_db`への直接クエリではなく、既存のKnowledge MCP `search_knowledge`ツール（MCP経由）を呼び出す方式に統一する。
  - チャット用LLM呼び出しは、既存のAmazon Bedrock接続（ADR-0031、既に`agent_invitro`にterraform設定済み）をそのまま利用する。
  - 会話要約ロジックは`agent_invitro`側に複製実装する。
- `admin_ui`（`web_backend`）に、上記3エンドポイントを`agent_invitro`へ転送する薄いリバースプロキシ機能を追加する（ADR-0045）。`admin_ui`自身はDB接続・Bedrock呼び出しを行わない。
- 会話履歴・評価データ（`conversation_db`相当）を、既存の`chatbot-invitro-rds`インスタンス上に新規データベース（`conversation`）として追加し、スキーマ適用を既存の`db_hiroba_qa_init`ワンショットサービスに統合する（ADR-0044）。アクセス元は`agent_invitro`。
- `admin_ui_task → agent_invitro`、`agent_invitro → rds`の到達性を許可するネットワーク設定を追加する（ADR-0043/0045）。`agent_invitro`はALBからは到達不可のまま維持する（ADR-0023準拠）。
- 利用者は社内関係者のみとし、既存のQA管理UIと同じ社内IPアドレス限定のブラウザアクセスとする（アクセス経路自体は`admin_ui`のALBのみで変更なし）。

### 4.2 対象外（将来検討・別スコープ）

- MRR検索精度評価スクリプト（`evaluate`コマンド）のAWS上での実行環境整備（ユーザー確認済み、Rev.1から継続）。
- `web_backend/main.py`（旧`/ask`＋`/session`方式）・`front_dev`の`App.tsx`/`api.ts`のAWS対応（レガシー実装として対象外、ユーザー確認済み、Rev.1から継続）。
- 既存のQA・タグ管理API（`/api/*`、Knowledge MCP経由のBFF、ADR-0013）の変更。`admin_ui`が引き続き処理し、本書の対象外とする。
- ChatbotUI・会話評価機能の機能自体の変更・追加（画面項目、評価軸の追加等）。
- ChatbotUIの実際の顧客（社外エンドユーザー）向け公開。
- `/evaluated_messages`ページへの追加ログイン認証の実装（社内IPアドレス限定のみで運用する、ユーザー確認済み）。
- 会話履歴・評価データの保持期間・自動削除・アーカイブの仕組み（MVPでは無期限保存、ユーザー確認済み）。
- `admin_ui`・`agent_invitro`サービスの冗長化・自動スケール（既存QA管理UI同様、単一インスタンス`desired_count=1`を維持、ユーザー確認済み）。
- ALBのパスベースルーティングによる`agent_invitro`への直接振り分け（ADR-0045で検討し、ADR-0023の境界維持を優先して不採用とした代替案）。
- QA管理UI要件定義書（202608211014）が残したOpen Issue（社内IPアドレスの具体値、既存VPCのパブリックサブネット/IGWの有無、HTTPS化の要否等）は、本書でも同一のOpen Issueとして引き継ぐ（12章）。

## 6. 機能要件

本書では機能要件（画面項目、API仕様、評価UIの表示内容等）の新規追加・変更は行わない。既存実装（`front_dev`の`AppStateless`/`AppEvaluatedMessages`、既存の`/ask-sl`/`/evaluate_response`/`/evaluated_messages`のAPI契約）をそのまま維持し、**実行主体のみ`agent_invitro`に変更する**。

| # | 機能 | API契約 | 実処理の提供元 | 備考 |
|---|---|---|---|---|
| F1 | 質問応答（ChatbotUI） | `POST /ask-sl`（既存契約） | `agent_invitro`（`admin_ui`が中継） | 会話履歴・要約はクライアント側（ブラウザ）が保持し、リクエストごとにサーバーへ送信するステートレス設計を維持する（front_dev側の変更なし）。QA類似検索はKnowledge MCPの`search_knowledge`ツール経由に変更する。 |
| F2 | 回答への評価記録 | `POST /evaluate_response`（既存契約） | `agent_invitro`（`admin_ui`が中継） | メッセージ単位で👍(1)/👎(2)を`conversation`データベースへupsertする。 |
| F3 | 評価済み会話の一覧確認 | `GET /evaluated_messages`（既存契約） | `agent_invitro`（`admin_ui`が中継） | 全会話・全メッセージ（LLM入力プロンプト相当を含む）を新しい順に一覧表示する。 |

## 7. データ要件

- `conversation`/`message`テーブルのスキーマは、既存の`db_conversation/init.sql`と同一とする（変更なし）。
- 保存先は`chatbot-invitro-rds`インスタンス上の新規`conversation`データベースとする（ADR-0044）。アクセス元は`agent_invitro`。
- 保持期間・削除方針: MVPでは無期限保存とする（ユーザー確認済み、Rev.1から継続）。
- `message.content` / `message.input`には、ユーザーの質問文・LLMへの入力情報（検索結果を含む）が平文で保存される。`agent_invitro`がReActエージェントとして動作する場合、「LLM入力」に相当する情報の定義（単一プロンプトか、ツール呼び出しの推論過程を含むか）は実装フェーズで確定する（12章Open Issue参照）。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| アクセス制御（ネットワーク） | ChatbotUI・会話評価機能へのアクセスは、既存のQA管理UIと同じALB・同じ社内IPアドレス限定ルール（ADR-0041）を適用する。ブラウザからの到達経路は`admin_ui`のみであり、`agent_invitro`はVPC内部限定のまま（ADR-0023）。 |
| アクセス制御（アプリケーション） | 追加のログイン認証は実装しない（`/evaluated_messages`を含む）。社内IPアドレス限定のネットワークレベル制御のみとする（ユーザー確認済み）。 |
| 通信の暗号化 | QA管理UI要件定義書のOpen Issue（HTTPS化の要否）を本書でも引き継ぐ。`admin_ui ↔ agent_invitro`間の内部通信（Service Connect）はAWS内部のプライベートネットワークで完結するため、この暗号化は本書のスコープに含めない。 |
| 性能 | ChatbotUI（LLMによる回答生成を伴う`/ask-sl`）については、厳密な応答時間の数値目標は設けず、「実用的な応答時間」であることを確認する（ユーザー確認済み）。`admin_ui`によるリバースプロキシ処理自体の追加レイテンシは、実装フェーズで許容範囲か確認する。 |
| 可用性 | 既存のQA管理UIと同じ単一インスタンス構成（`desired_count=1`）を`admin_ui`・`agent_invitro`双方で維持する（ユーザー確認済み）。 |
| ログ | 既存のQA管理UI要件定義書の方針（ALBアクセスログの有効化）を維持する。会話内容そのもの（質問・回答・評価）は`conversation`データベースに保存されることをもって記録とする。 |
| コスト | Bedrock呼び出し（チャット生成・会話要約）に伴う追加コストが発生する。既存のBedrockコスト予算アラート（ADR-0040）の対象に自然に含まれる。RDSインスタンスへの新規データベース追加自体に追加のインスタンス費用は発生しない（ADR-0044）。 |
| 保守性・拡張性 | ChatbotUI・会話評価機能（`agent_invitro`）とQA・タグ管理UI（`admin_ui`内の`/api/*`）が別サービスに分離されることで、障害・負荷の影響範囲が分離される（当初案の同一プロセス統合と比べた利点）。 |

## 9. インフラ・実行環境要件

### 9.1 Terraform構成への反映

- `terraform/modules/database`: `conversation_db_name`変数、`conversation_db_url_secret_arn`出力を追加する（ADR-0044、変更なし）。
- `terraform/main/database/main.tf`: `module "db_init_task"`の`environment`/`secrets`に、`conversation`データベース作成・スキーマ適用のための設定を追加する（変更なし）。
- `terraform/main/app/main.tf`:
  - `module "agent_invitro"`: `container_port`（新設、例: 8300）、`health_check_command`を追加し、`command = ["sleep", "infinity"]`を削除する。`secrets`に`CONVERSATION_DATABASE_URL`（`conversation_db_url_secret_arn`）を追加する。既存の`LLM_PROVIDER=bedrock`等・`enable_bedrock=true`は変更しない。
  - `module "admin_ui"`: `environment`に`AGENT_INVITRO_URL`（新設）を追加する。Bedrock関連・DB関連の環境変数・secrets・`enable_bedrock`は追加しない（Rev.1からの変更点）。
- `terraform/modules/network`:
  - `admin_ui_task → agent_invitro`（新設コンテナポート）の到達性を許可するセキュリティグループルールを追加する。
  - `agent_invitro → rds`（5432番）の到達性を許可するセキュリティグループルールを追加する。
  - Rev.1で予定していた`admin_ui_task → rds`ルールは不要になった。
- 上記変数はいずれも既存の`.env`（`TF_VAR_*`, ADR-0038/0040方式）で管理する。

### 9.2 db_hiroba_qa_init の拡張

- `conversation`データベースの存在確認・作成（`CREATE DATABASE`）、および`conversation`/`message`テーブルの冪等なDDL適用ステップを追加する（ADR-0044、変更なし）。

### 9.3 agent_invitro の変更

- 常駐HTTPサーバー（例: FastAPI）を追加し、`POST /ask-sl`, `POST /evaluate_response`, `GET /evaluated_messages`を実装する（ADR-0043）。
- QA類似検索はKnowledge MCPの`search_knowledge`ツール（既存のMCPクライアント構成、ADR-0021）経由に統一する。
- 会話要約ロジックを、既存のBedrockチャットクライアントを使って複製実装する。
- `conversation`データベースへの読み書きロジックを実装する（`web_backend/src/conversation_db/`相当の移植）。
- `/health`エンドポイントを追加する（ECSレベルのヘルスチェック用）。
- ECS Execによる対話的検証（ADR-0019/0025の元来の目的）は、常駐サーバーとは独立して引き続き利用できることを実装フェーズで確認する。

### 9.4 admin_ui（web_backend）の変更

- `main/main_stateless.py`に、`/ask-sl`, `/evaluate_response`, `/evaluated_messages`を`agent_invitro`へ転送する薄いリバースプロキシルートを追加する（ADR-0045）。
- 既存の`/api/*`ルータ・静的資産配信・SPAフォールバックには変更を加えない。
- 具体的な変更内容は実装指示書（`docs/implementation_handoff/202608211610_AWS環境向けChatbotUI・会話評価機能実装指示書.md`）で指示する。

## 10. 既存システムとの関係・影響範囲

- Knowledge MCP・Tag Selector MCP・RDSインスタンス自体の構成・ネットワーク境界方針（ADR-0023, 0026, 0036）は変更しない。
- QA管理UI要件定義書（202608211014）が定めた機能・API・アクセス制御方針は変更しない。`admin_ui`の`/api/*`・静的資産配信・ALB構成はそのまま維持される。
- `agent_invitro`の元々の要件定義（202608061621、ADR-0019〜0022）が定めた「IPython対話シェル用コンテナ」という位置づけは、本書により常駐HTTPサービスとしての機能が追加される形で見直される（ADR-0043）。ローカル`docker-compose`環境での`agent_invitro`の使い方（`docker compose exec agent_invitro ipython`）自体は変更しない。
- ADR-0013（管理UIの書き込みはKnowledge MCP経由に統一）は、QA・タグの書き込みパスに関する決定であり、本書の対象範囲外（`/api/*`は変更しない）である。
- ローカルの`docker-compose`環境（開発用）は本書の対象外として現状のまま維持する。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] 社内IPアドレスからブラウザでALBのエンドポイント（URL）のルートパスにアクセスし、ChatbotUIで質問を送信し、LLMによる回答が返る。
- [ ] 回答生成の過程で、Knowledge MCPの`search_knowledge`ツール経由でQA類似検索が行われていることを確認する（`chatbot_db`への直接クエリを行っていないことをログ・コードレビューで確認する）。
- [ ] 回答生成・会話要約が、Amazon Bedrock経由で行われていることを確認する（LM Studioへの到達を試みていないことを確認する）。
- [ ] 回答に👍/👎評価を記録し、`/evaluated_messages`ページで当該会話・評価が確認できる。
- [ ] 会話履歴・評価データが、AWS上の`chatbot-invitro-rds`の`conversation`データベースに保存されていることを確認する（`agent_invitro`が直接読み書きしていることをコードレビューで確認する）。
- [ ] `admin_ui`が`/ask-sl`等のリクエストを`agent_invitro`へ中継するだけであり、DB接続・Bedrock呼び出しを行っていないことをコードレビューで確認する。
- [ ] 既存のQA・タグ管理UI（`/admin`配下、`/api/*`）の動作に影響がないことを確認する。
- [ ] 既存のKnowledge MCP・Tag Selector MCPの動作（ADR-0023のネットワーク境界を含む）に影響がないことを確認する。`agent_invitro`がALBから直接到達不可であることを確認する。
- [ ] ローカルの`docker-compose`環境での既存UI（ChatbotUI・会話評価機能・QA管理UI）・`agent_invitro`のIPython対話シェル動作に影響がないことを確認する。
- [ ] 社内IPアドレス以外からのアクセスが、ネットワークレベル（SG）で拒否されることを確認する。

## 12. Open Issues（要追加確認事項）

QA管理UI要件定義書（202608211014）12章のOpen Issueのうち、次の項目は本書の対象にもそのまま適用される。

1. 社内IPアドレスの具体的な値・管理方法。
2. 既存VPCのパブリックサブネット・インターネットゲートウェイの有無。
3. HTTPS化（ドメイン・証明書）の要否。
4. 社内グローバルIPアドレスの変動性。
5. ALBのコスト承認。
6. 将来的な認証・権限管理の要否。
7. `front_dev`のディレクトリ・位置付けの見直し。

本書固有の新規Open Issueは次のとおり。

8. **`search_knowledge`経由での検索品質**: 既存の`web_backend`実装は、クエリ整形（`FormatQueryToEmbed`）を明示的なステップとして行っていたが、`agent_invitro`のReActエージェントに検索クエリの組み立てを委ねる方式に変更する（ADR-0043）。実装フェーズで、既存と同等の検索精度・回答品質が得られるかを確認し、不十分な場合は明示的なクエリ整形ステップの追加を検討する。
9. **「LLM入力」の定義**: `/evaluated_messages`の`input`列（既存実装では単一の生成プロンプト）に相当する情報を、ReActエージェントの複数ステップの推論過程を持つ`agent_invitro`でどう定義するか（実装フェーズで確定、7章参照）。
10. **会話データの機密情報取り扱い**: `message.content`/`message.input`に、ユーザーが入力した問い合わせ内容が平文で保存される。社内規程上の情報取り扱いルールを運用担当者に確認する。
11. **`db_hiroba_qa_init`のマスター権限依存**: `conversation`データベースの`CREATE DATABASE`実行に必要な権限を実装フェーズで確認する。
12. **`agent_invitro`のBedrockチャットモデルの呼び出し形式確認**: 既存のterraform設定（`bedrock_chat_model_id`）で選定されるモデルが、`agent_invitro`のLangGraphエージェント実装（Converse API、または`invoke_model`）が使う形式に対応していることを確認する。
13. **`admin_ui`のリバースプロキシによる追加レイテンシ・タイムアウト設定**: LLM生成に時間がかかる`/ask-sl`について、`admin_ui`のプロキシ実装のタイムアウト値を、`agent_invitro`側の想定応答時間より十分に長く設定する必要がある。
