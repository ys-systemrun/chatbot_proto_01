# タグ管理画面・タグ選択UI改修 要件定義書

- 文書番号: REQ-202609021102
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `knowledge_mcp`（`tag`関連MCPツール・`TagRepository`）、`web_backend`（`tag_controller.py`）、`front_dev`（`TagTreePage.tsx`／`TagPicker.tsx`／`domain/admin/tag.ts`）、`db_hiroba_qa_init`（マイグレーション）
- 変更なしのコンポーネント: `search_knowledge`のスコアリングロジック（ADR-0058祖先展開・ADR-0059タグ構成類似度）、`qa_tag`テーブル、`tag_selector_mcp`
- 参照資料: `docs/requirement/202609021050_タグ運用ガイドライン.md`、ADR-0005、ADR-0006、ADR-0008、ADR-0058、ADR-0059、ADR-0061、ADR-0065

## 1. 目的

タグ運用ガイドライン（202609021050）が定めた運用ルールを、担当者が実際に実行しやすくするため、タグ管理画面（`TagTreePage`）・タグ選択UI（`TagPicker`）に次の3つの改修を行う。

1. **検索・絞り込みの追加**: タグ件数が増えても目的のタグを名前・エイリアスから素早く見つけられるようにする。
2. **新規作成時の重複・類似名チェック**: ガイドライン5章「新規タグ作成前の確認手順」を、担当者の記憶・手作業の検索だけに頼らずUI側で支援する。
3. **タグフォルダの追加**: ガイドライン3章が示す「文脈」「話題」のような分類軸を、`tag.parent_tag_id`による本来の親子階層とは独立したメタデータとして持たせ、管理画面・選択UIをタグフォルダ単位でグルーピング表示できるようにする。

## 2. 背景

- `TagPicker`（QA編集フォーム・タグ階層ページ双方から利用）は`list_tags`が返すツリーをインデント付きの平坦なリストとして表示するのみで、フリーテキストでの絞り込み手段を持たない。タグ件数が数十〜百件規模に増えると目的のタグを探しづらくなる（運用ガイドライン1章の課題2・3）。
- `TagTreePage`の新規作成フォームは、名前を入力してもリアルタイムでの重複・類似候補の提示を行わない。DB制約（`hiroba_tag.name`の`UNIQUE`）により完全一致の重複は`create_tag`実行時にエラーになるが、「ネットワーク認証」「ネット認証」のような**表記ゆれ・概念の混同**は完全一致では検出できず、事後に発覚している（運用ガイドライン1章の課題3、7章）。
- 運用ガイドライン3章は、タグの分類軸（文脈・話題等）が事前に確定できず、しかも相対的な役割であることを踏まえ、「タグ階層（親子関係）は本当のis-a関係にのみ使い、独立した2軸の組み合わせは階層化せずQA側の組み合わせタグ付けで表現する」という方針を示した。この方針を運用する担当者が、既存タグを分類軸ごとに見渡せないと、どの組み合わせが既に使われているか、どのタグがどの軸に属するかを把握しづらい。この見渡しを助けるための表示上の区分（タグフォルダ）を、既存のis-a階層とは別に持たせる。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| タグフォルダ | タグを「対象システム」「動作環境」等の種別で分類するための、`parent_tag_id`による親子階層とは独立したメタデータ属性。本書が新設する概念。検索ロジック（ADR-0058/0059）には一切関与しない、管理画面・選択UI表示専用の属性とする。 |
| 類似候補 | 新規タグ作成時に、入力された名前と既存タグ名・エイリアスとの間で一定の類似性が認められた既存タグ。運用ガイドライン5章の「既存タグ・エイリアスの確認」をUIが支援するために算出する。 |

## 4. スコープ

### 4.1 対象範囲

- `TagPicker`・`TagTreePage`へのフリーテキスト検索（名前・エイリアス対象）の追加。
- `TagTreePage`の新規作成フォームへの、入力中の名前に対する類似候補提示（非ブロッキングの警告表示）の追加。
- `tag`にタグフォルダ属性を追加するためのスキーマ拡張、および関連MCPツール・管理API・UIの追加。
- 上記に伴う`knowledge_mcp`のタグ関連MCPツール、`web_backend`の`tag_controller.py`、`front_dev`の該当コンポーネントの改修。

### 4.2 対象外（本書のスコープに含めない）

- 説明文（description）入力の必須化・未記入タグの一覧化（運用ガイドラインの別項目、本書のヒアリングで今回は見送りとした）。
- 棚卸し支援レポート画面（説明文未記入一覧・QA紐付けゼロタグ一覧等、同じく今回は見送り）。
- タグの多親化・タグ名一意性のnameからidへの変更（運用ガイドライン9章で対象外と明記済み）。
- 検索結果が文脈によって割れる場合の会話上の聞き返し機能（`agent_invitro`側の別機能、本書とはコンポーネントが異なる）。
- タグ作成・編集の権限・レビュー体制（ADR-0006のOpen Issueのまま、本書では扱わない）。

## 6. 機能要件

### 6.1 検索・絞り込み

- `TagPicker`・`TagTreePage`の一覧上部に、フリーテキスト入力欄を追加する。
- 絞り込みは`list_tags`が既に全件取得している`TagNode`ツリーに対してクライアント側（フロントエンド）で行う。新規のバックエンドAPI・SQLは不要とする（タグ件数は現状数十〜百件規模であり、全件クライアント側フィルタで十分な性能が見込めるため）。
- 一致対象は、タグ名（部分一致・大文字小文字を区別しない）およびエイリアス名（同条件）とする。
- 一致したタグについては、そのタグ自身に加え、**祖先タグ（親を辿った経路）をパンくず形式で表示**する（例:「認証 > ネットワーク認証」）。既存のインデント表示は、絞り込み未実施時（全件表示時）はそのまま維持する。
- 絞り込みでヒットしないタグ・その他の兄弟タグは、絞り込み中は非表示にする（該当タグの祖先のみ表示を維持する）。

### 6.2 新規作成時の重複・類似名チェック

- `TagTreePage`の新規作成フォームで、名前欄の入力中（または送信前）に、既存タグ名・エイリアスとの類似候補を計算し、フォーム内に候補一覧として表示する。
- 一致条件（MVP）: 次のいずれかを満たす既存タグ・エイリアスを類似候補とする。
  - 入力文字列が既存の名前／エイリアスを含む、または既存の名前／エイリアスに含まれる（部分文字列一致、全角・半角/大文字・小文字を正規化した上で比較）。
  - 編集距離（Levenshtein距離）が閾値以下（既定値は実装時に調整するが、初期値2文字を仮置きとする）。
- 類似候補が見つかった場合も**作成をブロックしない**（完全一致の重複禁止は既存のDB制約・`create_tag`のエラーが担保する）。候補の名前・説明文・所属階層（親タグ名）を表示し、担当者が「別概念として続行する」か「既存タグ・エイリアスを使う（作成を中断する）」かを判断できるようにする。
- 本チェックは新規作成時のみを対象とする（リネーム時への適用要否は12章Open Issue #4）。

### 6.3 タグフォルダ属性

#### 6.3.1 データモデル

- `hiroba_tag_folder`テーブルを新設する。

```sql
CREATE TABLE IF NOT EXISTS hiroba_tag_folder (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL UNIQUE,
    description TEXT
);
```

- `hiroba_tag`に`folder_id`列を追加する（1タグにつきタグフォルダは0または1件、NULL許容）。

```sql
ALTER TABLE hiroba_tag
    ADD COLUMN IF NOT EXISTS folder_id INTEGER REFERENCES hiroba_tag_folder(id);

CREATE INDEX IF NOT EXISTS idx_hiroba_tag_folder_id ON hiroba_tag (folder_id);
```

- タグフォルダは`parent_tag_id`による階層とは独立した属性であり、階層上のどの深さのタグにも付与できる（タグフォルダ付与とis-a階層上の位置は無関係）。
- **`folder_id`はADR-0058の祖先展開・ADR-0059のタグ構成類似度計算に一切使用しない。** `search_knowledge`の検索結果・スコアには影響を与えない、管理画面・選択UI表示専用の属性とする。

#### 6.3.2 タグフォルダマスタの管理

- `knowledge_mcp`に、タグフォルダマスタ用のMCPツールを追加する（既存の`tag_alias`管理ツール群と同様の構成とする）。
  - `list_tag_folders`: タグフォルダ一覧の取得。
  - `create_tag_folder(name, description=None)`: タグフォルダの新規作成。
  - `rename_tag_folder(folder_id, new_name, description=None)`: タグフォルダの名称・説明文の変更。
  - `delete_tag_folder(folder_id)`: タグフォルダの削除。`hiroba_tag`から参照されている場合は削除を拒否する（既存の`delete_tag`と同じ考え方）。
- `web_backend`に`/api/tag-folders`のCRUDエンドポイントを追加し、`tag_controller.py`と同様の構成で上記ツールを呼び出す。
- `create_tag`/`rename_tag`（またはそれに相当する更新系ツール）に`folder_id`パラメータを追加し、タグへのタグフォルダ付与・変更・解除（`null`指定）ができるようにする。

#### 6.3.3 表示

- `TagPicker`・`TagTreePage`に、タグフォルダごとのタブまたはセクション見出しによるグルーピング表示を追加する。タグフォルダが未設定のタグは「未分類」セクションにまとめる。
- 各タグフォルダのセクション内は、既存通り`parent_tag_id`による親子階層をインデント表示する（タグフォルダは階層を置き換えるものではなく、階層の上位に重ねる分類軸として扱う）。
- `TagTreePage`にタグフォルダマスタの管理UI（一覧・作成・リネーム・削除）を追加する。
- `TagPicker`のQA編集フォームでの利用時も、同じタグフォルダ別グルーピング表示を適用する。

## 7. データ要件

- `db_hiroba_qa_init`のマイグレーションとして、6.3.1節のDDLを追加する（既存の番号体系に従い新規マイグレーションファイルを作成、`IF NOT EXISTS`による冪等性を維持する）。
- 既存タグは`folder_id = NULL`（未分類）として扱う。既存タグへのタグフォルダ付与（移行作業）の方法は12章Open Issue #3で扱う。
- `qa_tag`・`tag_alias`のスキーマ・データには変更を加えない。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 後方互換性 | `folder_id`はNULL許容のため、既存の`list_tags`/`create_tag`等の呼び出し元（`tag_selector_mcp`のロード処理含む）は変更なしに動作を継続する。`search_knowledge`の検索結果・スコアは本書の変更による影響を受けない。 |
| 性能 | タグ検索・絞り込みは全件クライアント側フィルタとするため、バックエンドへの新規負荷は発生しない。類似候補チェックも、既に取得済みの全件データに対するクライアント側計算とする。 |
| 実装のシンプルさ | 6.2節の類似候補チェックは、複雑な自然言語処理・外部ライブラリを用いず、正規化＋部分一致／編集距離という説明可能なロジックに留める。誤検知（本来別概念のものを類似候補として出す）は許容し、あくまで「担当者への気づきの提示」と位置づける。 |

## 9. インフラ・実行環境要件

- 新規の環境変数・AWSリソースは発生しない。`db_hiroba_qa_init`のマイグレーション実行フロー（ローカル`docker-compose`・AWS双方）に、6.3.1節のマイグレーションが追加されるのみ。

## 10. 既存システムとの関係・影響範囲

- `tag_selector_mcp`の`TagMetadataRepository`は`hiroba_tag`を`SELECT *`ではなく明示的な列指定で読み込んでいるため（`infrastructure/repository/tag_metadata_repository.py`）、`folder_id`列の追加によって自動的に取り込まれることはない。`folder_id`を`tag_selector_mcp`側で利用する予定がないため、本書では同リポジトリのSELECT文への追加は行わない。
- `import_tag_batch`/`export_tags`（ADR-0061/0065）の列構成にタグフォルダを表す列（列名候補: `folder`）を含めるかどうかは、12章Open Issue #2で扱う未決事項とする。含めない場合、CSV経由で作成・更新されたタグのタグフォルダは管理画面上で個別に設定する運用になる。
- `QARepository.search`・`qa_tag`・ADR-0058/0059のロジックには変更を加えない。

## 11. 受け入れ基準（Definition of Done）

- [ ] `TagPicker`・`TagTreePage`の検索欄に文字列を入力すると、タグ名またはエイリアスに一致するタグのみが、祖先タグへのパンくず（またはインデント経路）とともに表示される。
- [ ] `TagTreePage`の新規作成フォームで、既存タグ・エイリアストと類似した名前を入力すると、候補一覧が表示される。候補が表示されても作成操作はブロックされない。
- [ ] 完全一致する名前を入力した場合は、従来通り`create_tag`のエラー（`TagError`）により作成が拒否される（本書による変更なし）。
- [ ] `TagTreePage`にタグフォルダの作成・リネーム・削除ができる管理UIがあり、タグ作成・編集画面でタグフォルダを選択・解除できる。
- [ ] `TagPicker`・`TagTreePage`で、タグがタグフォルダごとのタブ/セクションに分かれて表示される。タグフォルダ未設定のタグは「未分類」に表示される。
- [ ] タグフォルダを設定・変更しても、`search_knowledge`の検索結果・スコア（`combined_score`/`tag_similarity`/`embedding_score`）に変化がないことを確認する。
- [ ] 既存の`tag_selector_mcp`の`select_tags`、CSVインポート/エクスポート（タグフォルダ列を含めないと決定した場合）が、本書の変更前と同じ入出力で動作を継続する。

## 12. Open Issues（要追加確認事項）

1. **タグフォルダは1タグにつき1つまでとしてよいか**: 本書では単純化のためNULL許容の単一`folder_id`とした。1タグが複数のタグフォルダに属したいケース（例:「認証」が「機能」でもあり「文脈」の一部でもある等）が実際に出てきた場合、多対多化（`tag_folder_assignment`関連テーブル）への拡張が必要になる。現時点では想定するか確認が必要。
2. **CSV一括インポート/エクスポート（ADR-0061/0065）にタグフォルダ列を含めるか**: 含める場合、`import_tag_batch`/`export_tags`・`tag_controller.py`の列構成（`_TAG_IMPORT_COLUMNS`/`_TAG_EXPORT_COLUMNS`）およびフロントエンドの説明文言の改修が追加で必要になる。
3. **既存タグへのタグフォルダ付与（移行）の方法**: 新設時点では全既存タグが`folder_id = NULL`になる。運用ガイドラインで想定した「文脈」「話題」等の軸へ既存タグを割り当てる作業を、管理画面から手動で行うのか、それとも一括インポート（Open Issue #2の結論次第）で行うのかを決める必要がある。
4. **重複・類似名チェックをリネーム時にも適用するか**: 6.2節はタグ新規作成時のみを対象としたが、`rename_tag`（`TagTreePage`の「名称」ボタン、現状`window.prompt`によるUI）についても同様の気づきが有用かどうかは別途確認する。
5. **類似候補チェックの閾値・アルゴリズムの調整**: 6.2節の編集距離閾値（仮置き2文字）・部分一致の正規化ルール（長音記号統一等の表記ゆれ対応をどこまで含めるか)は、実データでの試行を経て調整が必要。
6. **タグフォルダマスタの作成・削除権限**: ADR-0006が残したタグ管理全般の権限に関するOpen Issueと同じ論点が、タグフォルダマスタにも当てはまる。運用ガイドライン9章の指摘と合わせて別途検討する。
