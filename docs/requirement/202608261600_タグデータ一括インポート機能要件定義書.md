# タグデータ一括インポート機能 要件定義書

- 文書番号: REQ-202608261600
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `knowledge_mcp`（新規MCPツール）, `web_backend`（新規インポートAPI）, `front_dev`（タグ管理画面拡張）
- 変更なしのコンポーネント: `tag`/`qa_tag`テーブルのスキーマ（既存のUNIQUE制約・`parent_tag_id`構造を維持）、既存の`create_qa`/`update_qa`/`import_qa_batch`、`tag_selector_mcp`、`agent_invitro`
- 参照資料: `docs/requirement/202608060826_QAタグ管理UI要件定義書.md`、`docs/requirement/202608261002_DBマイグレーション・データインポート機能要件定義書.md`、ADR-0005、ADR-0006、ADR-0008、ADR-0013、ADR-0053
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照

## 1. 目的

タグデータ（`tag`テーブル）を、QAデータとは独立して、CSV等のファイルから複数件まとめて登録・更新できるようにする。

現状、タグの登録・階層編集は、`front_dev`のタグ管理画面（`TagTreePage`）から1件ずつ行う個別操作のみが提供されている（ADR-0006）。QAデータについては既にADR-0053により一括インポート機能（`import_qa_batch`）が実装済みだが、これはQAレコードに付随する形でしかタグを作成できず、常にルート直下のフラットなタグとして作成される（親子階層を指定できない）。

タグ体系そのもの（階層構造を含む）を、既存の外部データ（例: `data/tags.txt`のような階層的なタグ一覧）から一括で投入・整理し直したいという運用ニーズに応えるため、タグ単体の一括インポート機能を新設する。

## 2. 背景・参照資料

- `tag`テーブルは`id`, `name`（`NOT NULL UNIQUE`）, `parent_tag_id`（自己参照）の構造を持つ（`db_hiroba_qa_init/migrations/0003_add_title_and_tag_tables.sql`、ADR-0005）。タグ名はデータベース全体で一意という制約が既に存在する。
- タグマスタ管理は、`knowledge_mcp`のMCPツール（`list_tags`/`create_tag`/`rename_tag`/`move_tag`/`delete_tag`）として提供されており（ADR-0006）、`create_tag`/`move_tag`は親子関係設定時の循環参照防止バリデーションを備える。
- QA・タグの一括インポート機能（ADR-0053）は、CSVの`tags`列（タグ名のカンマ区切り）で指定されたタグ名を、既存タグは名前で解決し、存在しないタグ名は自動的に新規タグとして作成する。ただし、この自動作成は`parent_tag_id`を指定しないため、常にルート直下のタグになる。
- 本書は、この「タグ単体の一括登録・更新」を新たな要件として整理する。発注者との確認を経て、次の方針を確認済みである。
  1. 対象操作範囲: 新規登録＋既存更新（削除は対象外）
  2. 階層構造の指定方法: CSVの列で親タグ名を指定する
  3. 更新対象タグの識別方法: タグ名の一致によるupsert
  4. タグ名の一意性: 既存のDBスキーマ（`tag.name`のUNIQUE制約）を変更せず、タグ名はシステム全体で一意という前提を維持する（同一タグ名を異なる親タグの下に複数持たせることは不可）
  5. インポートUIの配置: タグ管理画面（`TagTreePage`）にCSVアップロード機能を追加する

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| タグ一括インポート | 本書が新設する機能。CSVファイルをアップロードし、複数件のタグ（名前・親タグ・説明）を一度に登録・更新する操作。既存のQA一括インポート（ADR-0053）とは独立した機能 |
| upsert（アップサート） | タグ名（`name`）の一致を基準に、既存タグがあれば更新、なければ新規作成する処理方式 |
| ルート直下 | `parent_tag_id`が`NULL`のタグ、すなわち親を持たないタグ |
| リネーム | 既存タグの`name`自体を変更する操作。本書のupsert方式では名前が識別キーのため対象外とし、既存の`rename_tag`（個別編集）で行う |

## 4. スコープ

### 4.1 対象範囲（MVP）

- `front_dev`のタグ管理画面（`TagTreePage`）に「CSVインポート」ボタンを追加し、CSVファイルをアップロードできるようにする。
- CSVフォーマット（案、詳細設計フェーズで確定）: `name`（必須）, `parent_name`（任意、空欄はルート直下）, `description`（任意）。
- `web_backend`は、アップロードされたCSVをパースし、`knowledge_mcp`の新規ツール（`import_tag_batch`、仮称）を呼び出す。当該ツールは、既存の`create_tag`/`rename_tag`/`move_tag`と同一の循環参照防止バリデーションを再利用し、複数件をまとめて処理する（ADR-0061）。
- 新規/更新の判定は、CSVの`name`列と既存`tag.name`の一致によるupsertとする。一致すれば`parent_name`・`description`を反映して更新、一致しなければ新規作成する。
- `parent_name`の解決は、CSV内の行の並び順に依存しない（親タグが同一CSV内の後続行にあっても解決できる）。
- インポート結果（成功件数、行ごとのエラー内容）を画面に一覧表示する。一部の行がエラーになっても、他の行の処理は継続する（行単位の部分成功を許容する、ADR-0053と同様の方針）。

### 4.2 対象外（将来検討・別スコープ）

- タグの一括削除（本書は新規登録・更新のみを対象とし、削除は扱わない）。
- 既存タグのリネーム（名称変更）。本機能はタグ名をupsertの識別キーとするため、CSVでの名前変更指定は「別タグの新規作成」として扱われてしまう。リネームは既存の個別編集画面（`TagTreePage`の`rename_tag`）で行う。
- 同一タグ名を異なる親タグの下に複数存在させること（タグ名の一意性は既存のDBスキーマ通りシステム全体一意を維持する）。
- `tag`テーブルのスキーマ変更（`UNIQUE`制約の複合キー化等）。
- QA一括インポート（`import_qa_batch`、ADR-0053）側の新規タグ自動作成ロジック（現状フラット作成）の変更。本書のタグ単体インポートとは独立した機能として併存させる。
- インポートデータの高度な業務バリデーション（基本的な必須項目チェック・循環参照チェックを超えるもの）。
- アクセス制御の強化（既存の管理画面群と同様、ネットワークレベルの制限のみとし、追加のログイン認証は設けない）。

## 5. 全体アーキテクチャ

### 5.1 変更箇所

```
front_dev（TagTreePage: CSVアップロードUI追加）
        │
        ▼
web_backend（新規: タグCSVパース＋インポートAPI）
        │  MCPツール呼び出し（既存の書き込み経路、ADR-0013を維持）
        ▼
knowledge_mcp（新規: import_tag_batchツール）
        │  既存の create_tag / rename_tag / move_tag の
        │  バリデーション・循環参照チェックをループ適用
        ▼
chatbot データベース（tag テーブル）
```

- `tag_selector_mcp`・`agent_invitro`には変更を加えない。
- タグ単体の一括インポートも、既存の個別登録（ADR-0013・ADR-0006）と同じく`web_backend → knowledge_mcp`経由の書き込み経路を維持する。`web_backend`から`chatbot`データベースへの直接書き込みは行わない。

### 5.2 コンポーネント一覧と責務（追加・変更分）

| コンポーネント | 変更内容 |
|---|---|
| `knowledge_mcp`（新規ツール） | タグの一括登録・更新を行う新規MCPツール（`import_tag_batch`）の追加 |
| `web_backend`（新規API） | タグCSVアップロード受付・パース処理、`import_tag_batch`呼び出し |
| `front_dev`（既存画面拡張） | タグ管理画面（`TagTreePage`）にCSVアップロードUI・結果表示を追加 |

## 6. 機能要件

### 6.1 CSVフォーマット（案）

| 列名 | 必須 | 説明 |
|---|---|---|
| `name` | 必須 | タグ名。既存タグと一致する場合は更新対象として扱う |
| `parent_name` | 任意 | 親タグ名。空欄はルート直下（親なし）を意味する。CSV内の他行、または既存タグのいずれかで解決できる必要がある |
| `description` | 任意 | タグの説明。空欄の場合、更新時は既存値を維持する部分更新とする（ADR-0053のQA一括インポートと同様の方針） |

区切り文字・文字コード（UTF-8 BOM付き可）等の詳細は、既存のQA一括インポート（ADR-0053）のCSV仕様に合わせることを基本方針とし、詳細設計フェーズで確定する（12章 Open Issue #1）。

### 6.2 新規登録・更新の判定（upsert）

- CSVの`name`が既存`tag.name`と一致すれば更新、一致しなければ新規作成する。
- 更新時、`parent_name`・`description`が空欄の場合は既存値を維持する（部分更新）。
- タグ名（`name`）自体の変更（リネーム）は本機能では扱わない（4.2節）。

### 6.3 階層（親タグ）の解決

- `parent_name`は、既存`tag`テーブルまたは同一CSV内の他行の`name`のいずれかで解決する。CSV内での行の並び順（親が子より先か後か）には依存しない。
- 実装上は、複数パスによる反復解決（1パス目で解決できた行を確定し、未解決の行を次パスへ繰り越す）を想定する（ADR-0061）。
- 全パス終了時点で親タグ名が解決できない行（CSVにも既存タグにも見つからない）は、エラーとして報告し、他行の処理は継続する。

### 6.4 循環参照の防止

- CSV内で循環する親子関係（例: AをBの親、BをAの親と指定する行の組み合わせ）が指定された場合、既存の`create_tag`/`move_tag`が持つ循環参照防止バリデーション（ADR-0006）を再利用して検出し、該当行をエラーとして報告する。

### 6.5 インポート結果表示（UI）

- `TagTreePage`に、成功件数・失敗件数・行ごとのエラー内容（行番号、エラー理由）を一覧表示する。既存のQA一括インポート（`QaListPage`）の結果表示UIと同様のパターンを踏襲する。

## 7. データ要件

| 項目 | 内容 |
|---|---|
| 入力形式 | CSV |
| 対象テーブル | `tag`（Knowledge MCP経由） |
| 対象外テーブル | `qa_tag`（本機能はタグマスタのみを対象とし、QAとタグの紐付けは変更しない） |

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 部分失敗時の扱い | 行単位でエラーを許容し、成功した行は反映され、失敗した行のみエラーとして報告する（既存QA一括インポートと同一方針） |
| ファイルサイズ・件数 | CSV一括インポートの上限件数・ファイルサイズは、既存のQA一括インポートの想定規模を目安とし、詳細は実装フェーズで確定する（12章 Open Issue #2） |
| アクセス制御 | 既存の管理画面群と同様、ネットワークレベルの制限（社内IPアドレス限定, ADR-0041）のみとし、追加のログイン認証は設けない |
| ログ | 既存の管理系操作ログ（`log_admin_operation`）と同様の方式で、タグ一括インポートの実行を記録する |
| データ整合性 | 循環参照防止・タグ名一意性（既存UNIQUE制約）は既存のバリデーションロジックをそのまま適用し、本機能独自の緩和は行わない |

## 9. インフラ・実行環境要件

- 追加のインフラ変更は想定しない。既存の`knowledge_mcp`・`web_backend`・`front_dev`のコンテナ構成（ローカルdocker-compose・AWS ECS Fargate）をそのまま利用する。

## 10. 既存システムとの関係・影響範囲

- `tag`テーブルのスキーマ（`UNIQUE`制約・`parent_tag_id`構造）は変更しない。
- 既存の`create_tag`/`rename_tag`/`move_tag`/`delete_tag`ツールには変更を加えない。
- QA一括インポート（`import_qa_batch`、ADR-0053）の新規タグ自動作成ロジック（フラット作成）にも変更を加えない。両機能は独立したツールとして併存する。
- `tag_selector_mcp`（タグ知識ベースのキャッシュ、ADR-0011）は、`tag`テーブルを起動時ロード＋明示的リロード＋定期ポーリングで参照する設計のため、本機能で一括投入されたタグも、既存のキャッシュ更新の仕組みにより反映される（新たな連携は不要）。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] タグ管理画面からCSVをアップロードし、複数件のタグが一括で登録・更新できる。
- [ ] CSVで親タグ名を指定した新規タグが、正しい親子関係で登録される（親タグが同一CSV内の後続行にあっても解決できる）。
- [ ] 既存タグ名と一致する行は、`parent_name`・`description`が更新され、空欄の項目は既存値が維持される。
- [ ] CSV内に循環する親子関係が含まれる場合、該当行がエラーとして報告され、他の正しい行は登録される。
- [ ] 一部の行に誤りがあっても、正しい行は登録され、誤った行のみエラーとして表示される。
- [ ] 既存のQA一括インポート、タグ管理画面の個別CRUD、`tag_selector_mcp`の動作に影響がないことを確認する。

## 12. Open Issues（要追加確認事項）

1. **CSVフォーマットの最終確定**: 6.1節に示した列構成（`name`/`parent_name`/`description`）は現時点では案であり、区切り文字・文字コードを含め詳細設計フェーズで最終確定する。
2. **ファイルサイズ・件数上限**: 8章に記載の通り、具体的な上限値（CSV行数、ファイルサイズ）は実装フェーズで確定する。
3. **エクスポート機能の要否**: 本書はインポートのみを対象とする。既存のタグ一覧（`list_tags`）をCSV形式でエクスポートする機能が別途必要かどうかは、本書のスコープ外とし、必要になった場合に別途要件化する。
4. **`data/tags.txt`相当の既存データの実際の投入作業**: 本機能の実装後、実際に`data/tags.txt`のような既存データをCSV化してインポートする初期投入作業を行うかどうか、行う場合の実施タイミングは、実装フェーズで別途確認する。
