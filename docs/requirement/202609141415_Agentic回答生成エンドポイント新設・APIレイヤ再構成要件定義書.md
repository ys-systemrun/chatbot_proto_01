# Agentic回答生成エンドポイント（/ask-agentic）新設・agent_invitro APIレイヤ再構成 要件定義書

- 文書番号: REQ-202609141415
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `agent_invitro`（`main/api/server.py`の再構成、`main/api/`配下の新設モジュール群、新設する`usecases/`・`graph/agentic_search.py`・`assess.py`・`clarify.py`、`config.py`）, `web_backend`（`main/controllers/chat_controller.py`・`main/config.py` … 中継先パスの切替のみ）
- 変更なしのコンポーネント: `knowledge_mcp`（`search_knowledge`のツール契約）, `tag_selector_mcp`（`select_tags`のツール契約）, `front_dev`（Request/Response契約が不変のため画面・型定義とも変更なし）, `conversation`データベースおよび`db_chatbot_knowledge_base`のスキーマ
- 参照資料: ADR-0019（agent_invitroの配置・実行形態）, ADR-0021（MCPクライアント実装）, ADR-0022（ReActエージェント方式）, ADR-0032（src平坦化）, ADR-0033（Settings注入）, ADR-0043（常駐HTTPサービス化・/ask-pipeline移管）, ADR-0045（admin_ui⇄agent_invitro連携）, ADR-0062（タグ検索の単一呼び出し簡素化）, ADR-0063（MCP戻り値パース）, ADR-0084（会話文脈のsummary一本化）, ADR-0085（Query Condensation）, ADR-0086（Alias確定タグ）, `docs/requirement/202609091730_タグ選定・会話文脈管理再設計要件定義書.md`
- 前提の決定事項: 本書に対応するADRはADR-0088〜ADR-0090（15章参照）。本書は2026-09-14のセッションにおける発注者との協議（Agentic方式・エンドポイント併存方針・API契約・レイヤ構成・反復制御・探索手段・レイテンシ許容度の選択）を踏まえて起票する。

## 1. 目的

本書は、次の2つの要求を実現するための要件を定義する。

1. **Agenticな回答生成の実現**: 現行の`POST /ask-pipeline`（`agent_invitro`）は、「言い換え→タグ選定→情報源検索1回→回答生成」という一本道の固定パイプライン（ADR-0043 0章「単発プロンプト生成方式」）である。検索が空振りした場合・部分的にしか当たらなかった場合でも、その事実を踏まえて探し直すことができず、そのまま「関連する情報が見つかりませんでした」相当の回答になる。**検索結果の十分性を評価し、不足していればクエリを組み立て直して探し直す**、Agenticな回答生成エンドポイント`POST /ask-agentic`を新設する。

2. **APIレイヤの再構成**: `main/api/server.py`は現在1ファイル約370行で、スキーマ定義・コンポーネント初期化（DI）・ルーティング・実処理（検索・要約・タグ選定・生成の手続き）を全て抱えている。エンドポイントを追加すると更に肥大化する。`server.py`を**薄いアプリ組み立て役**に縮退させ、ルーティングと実処理をエンドポイント単位のモジュールへ分離する。

本書では、まず2の再構成を行い、その構造の上に1の`/ask-agentic`を新設する、という順序を前提とする。

## 2. 背景・課題

### 2.1 現行`/ask-pipeline`の処理構造

`agent_invitro/src/main/api/server.py`の`_ask_impl()`は次の順に処理する。

1. `messages`が15件以上なら古い3件を要約して畳み込む（`SummarizeLLMBedrock`）
2. `build_alias_match_text()`でAlias一致対象の生テキストを構築（ADR-0086）
3. `CondenseQueryLLMBedrock.condense()`で`condensed_query`を生成（ADR-0085）
4. `select_tags`を1回呼び出してタグを選定（ADR-0086）
5. `search_knowledge`を1回呼び出して情報源を検索（ADR-0062・ADR-0084、`query=condensed_query`, `tags=選定タグ`, `top_k=3`）
6. 検索結果を`Q:/A:`形式に整形して`context`とし、`GenerateAnswerLLMBedrock.generate()`で回答を生成

`server.py`のソース中にも、発注者による`### ↓この辺をもう少しAgenticに？` / `### ↑この辺をもう少しAgenticに？`というコメントが4〜6の区間を囲む形で残されており、本書はこの区間を対象とする。

### 2.2 一本道パイプラインの限界

Bedrock LLMの呼び出しは3箇所（要約・言い換え・回答生成）あるが、いずれも**探索の結果を受けて次の行動を決める**呼び出しではない。具体的には次の状況に対処できない。

- **検索が空振りした場合**: `search_knowledge`が0件、あるいは質問と無関係な3件を返しても、そのまま`context`として回答生成へ渡る。`GenerateAnswerLLMBedrock`のシステムプロンプト（ルール3・4）により定型の謝罪文が返るが、「別の言い方で探し直す」機会が一度もない。
- **部分的にしか当たらない場合**: 複合的な質問（例:「Aの設定をBの環境で行う手順」）に対し、Aに関するQAだけがヒットしBに関する情報が欠けていても、その欠落は検知されない。
- **言い換えが外れた場合**: `condensed_query`（ADR-0085）はLLMによる1回きりの生成であり、外した場合のリカバリ手段がない。`select_tags`・`search_knowledge`の両方が同一の`condensed_query`に依存しているため、外れの影響が二重にかかる。

### 2.3 既存ReActエージェント（ADR-0022）との関係

`agent_invitro`には`graph/agent.py`にLangGraphの`create_react_agent`によるReActエージェントが存在する（ADR-0022）。LLMが自律的に`select_tags`→`search_knowledge`を呼ぶ構成であり、名目上は「Agentic」である。しかしADR-0043の実装（0章）では、この経路は`/ask-pipeline`では使われておらず、`search_knowledge`を直接呼ぶ単発プロンプト方式が採られた。ReActは**ツール呼び出しの順序・回数・実行有無をLLMに委ねる**ため、`graph/agent.py`の`SYSTEM_PROMPT`にもある通り「ツールを呼ばずに一般知識で答えてしまう」リスクをプロンプトによるベストエフォートのガードでしか抑えられない（REQ-202608061621 Open Issue #6）。

本書における「Agentic化」は、ReActへの回帰ではなく、**必須ステップ（タグ選定・情報源検索・回答生成）は決定論的に固定したまま、「もう一度探すか」という判断だけをLLMに委ねる**という設計を採る（ADR-0088）。

### 2.4 `server.py`の肥大化

`server.py`（約370行）は次の5つの関心事を1ファイルに抱えている。

| 関心事 | 該当箇所 |
|---|---|
| API契約（スキーマ） | `Message` / `Summary` / `Request` / `Response` |
| コンポーネントの遅延初期化・DI | `_components` / `_init_lock` / `_get_components()` |
| ルーティング・例外処理 | `@app.post("/ask-pipeline")` の`ask()`、`@app.get("/health")` |
| 実処理 | `_ask_impl()` |
| ドメインヘルパー | `_extract_results()` / `_search_knowledge()` / `_build_context()` / `_summarize_oldest()` |

`/ask-agentic`を同一ファイルに追加すると、実処理・ヘルパーが更に増え、どのヘルパーがどのエンドポイントに属するのかが判別できなくなる。また`web_backend`側は既に`main/app.py`（ルート定義）＋`main/controllers/*.py`（実処理）の2層構成を採っており（`chat_controller.py`冒頭コメント参照）、`agent_invitro`だけが単一ファイル構成のままである。

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| Agenticループ | 「情報源検索 → 検索結果の十分性評価 → 不十分ならクエリを再定式化して再検索」を反復する処理。本書ではLangGraphの`StateGraph`で実装する（ADR-0088）。 |
| 十分性評価（assess） | 蓄積された検索結果が、ユーザーの質問に回答するために十分かをLLMに判定させるステップ。判定結果に加えて「不足している観点」と「次に試すべきクエリ」を出力させる。 |
| クエリ再定式化 | 十分性評価が出力した「次に試すべきクエリ」で`search_knowledge`を再度呼び出すこと。 |
| 逆質問（clarify） | 反復上限まで探索しても十分な情報が得られなかった場合に、推測で回答せず、ユーザーへ追加情報を求める応答を返すこと。 |
| 周回（iteration） | `search_knowledge`呼び出し1回と、それに続く十分性評価1回の組を1周回と数える。 |
| `condensed_query` | 会話文脈を踏まえて今回の発話を単体で意味が通る質問文へ言い換えたもの（ADR-0085）。 |
| ユースケース層 | HTTP（FastAPI）に依存しない実処理を担うモジュール群。`agent_invitro/src/usecases/`に置く。 |

## 4. スコープ

### 4.1 対象範囲

1. `agent_invitro`のAPIレイヤ再構成（`server.py`の薄いアプリ組み立て役への縮退、`main/api/`配下の分割、`usecases/`層の新設）。既存`/ask-pipeline`・`/health`の外部挙動は不変とする。
2. `agent_invitro`への`POST /ask-agentic`の新設（Agenticループによる回答生成）。
3. Agenticループを構成する新規モジュール（LangGraph `StateGraph`、十分性評価LLM、逆質問生成LLM）の追加。
4. Agenticループの挙動を制御する環境変数の追加（反復上限等）。
5. `web_backend`（admin_ui）から`agent_invitro`への中継先パスを`/ask-pipeline`・`/ask-agentic`の間で切り替える手段の追加。

### 4.2 対象外

1. **`/ask-pipeline`の廃止**: 併存させる（ADR-0089）。`/ask-agentic`の精度・レイテンシが確認できるまで既存経路を温存する。移行・廃止は本書の対象外とし、別途判断する。
2. **API契約の変更**: `Request`・`Response`・`Message`・`Summary`のスキーマは`/ask-pipeline`と完全に同一とする（ADR-0089）。したがって`front_dev`のコード（`StateContainer.tsx`・`domain/stateless/{request,response}.ts`）には変更を加えない。反復の経過（trace）はサーバーログにのみ出力する。
3. **ローカルdocker-compose環境の構成変更**: `agent_invitro`は引き続き`sleep infinity`で常駐し、HTTPサーバーはAWS環境限定で起動する（ADR-0019・ADR-0043を維持）。`Dockerfile`・`docker-compose.yml`は変更しない。
4. **`conversation`データベースへのアクセス**: `agent_invitro`は引き続き一切アクセスしない（ADR-0043）。`/ask-agentic`もステートレスである。
5. **`select_tags`・`search_knowledge`のツール契約変更**: いずれも既存の入力・出力スキーマのまま呼び出す。`knowledge_mcp`・`tag_selector_mcp`のコードは変更しない。
6. **ReActエージェント（`graph/agent.py`）の変更・削除**: IPython経由の実験用途（ADR-0022）としてそのまま残す。
7. **`web_backend`のローカル直接処理経路（LM Studio経由）のAgentic化**: `chat_controller.ask()`の処理内容は変更しない（2026-09-15 改訂: 分岐の除去と`POST /api/ask-local`への切り出しのみ行い、応答生成のロジック自体は一切変更しない）。
8. **`front_dev`からのエンドポイント選択UI**: 本書では設けない（12章 Open Issue #3）。

### 5.2 変更後

front_dev ──POST /ask-pipeline──▶ web_backend(admin_ui)

`main/api/server.py`は`create_app()`を呼び出して`app`を公開するだけのモジュールとなる（Terraformの起動コマンドが参照するモジュールパス`agent_invitro.main.api.server:app`を変えないため、ファイル名・変数名は維持する。ADR-0090）。

### 5.3 Agenticループのグラフ構造

```
        [start]
           │
      condense           … condensed_query 生成（ADR-0085・現行と同一）
           │
     select_tags         … タグ選定（ADR-0086・現行と同一、1回のみ）
           │
           ▼
    ┌── search ◀────────────────┐   … search_knowledge 1回（query は周回ごとに変わる）
    │      │                    │
    │      ▼                    │
    │   assess                  │   … 十分性評価 LLM（sufficient / missing / next_query）
    │      │                    │
    │      ├─ sufficient ──────────────▶ generate ─▶ [end]
    │      ├─ 不十分 & 周回数 < 上限 ──┘（next_query で再検索）
    │      └─ 不十分 & 周回数 = 上限
    │              │
    │              ├─ 蓄積結果あり ─────▶ generate ─▶ [end]   … ベストエフォート回答
    └──────────────┴─ 蓄積結果が空 ─────▶ clarify  ─▶ [end]   … 逆質問
```

`condense`・`select_tags`は周回に入らない（各1回）。周回に入るのは`search`と`assess`の組のみである。

## 6. 機能要件

### 6.1 `POST /ask-agentic` エンドポイント

- **F-6.1.1** `agent_invitro`に`POST /ask-agentic`を新設する。リクエスト・レスポンスのスキーマは`POST /ask-pipeline`と完全に同一とする（`Request{conversation_id, text, messages, summary}` → `Response{conversation_id, messages, summary}`、`Message{order, role, content, input, model, evaluation}`、`Summary{content, summarized_upto}`）。
- **F-6.1.2** `conversation_id`が`None`の場合はサーバー側で`uuid4()`を発行する（`/ask-pipeline`と同一）。
- **F-6.1.3** `messages`が15件以上の場合、`order`の昇順で先頭3件を要約して`messages`から除外し`summary`を更新する（`/ask-pipeline`と同一のロジックを共有する）。
- **F-6.1.4** 応答の`messages`には、`/ask-pipeline`と同じ形式で`user`メッセージ（`参考情報:\n{context}\n\n質問:\n{req.text}`）と`assistant`メッセージ（`content=回答`, `input=LLMへ渡したプロンプト`, `model=BEDROCK_CHAT_MODEL_ID`, `evaluation=0`）を追加する。`context`には**全周回で得られた検索結果を統合したもの**を入れる（6.4参照）。
- **F-6.1.5** 例外時の扱いは`/ask-pipeline`と同一とする（`HTTPException`はそのまま透過、その他の例外はスタックトレースをログ出力し、`500`の`detail`に`{型名}: {メッセージ}`を含めて返す）。
- **F-6.1.6** `agent_invitro`は`conversation`データベースへ一切アクセスしない（ADR-0043を維持）。

### 6.2 前処理（現行踏襲）

- **F-6.2.1** `build_alias_match_text(req.text, messages, summary.summarized_upto)`によりAlias一致対象の生テキストを構築する（ADR-0086）。言い換え前の`req.text`を使うという既存方針を維持する。
- **F-6.2.2** `CondenseQueryLLMBedrock.condense()`で`condensed_query`を生成する（ADR-0085）。会話の最初のターンやLLM失敗時は`req.text`へフォールバックする。
- **F-6.2.3** `select_tags`を1回だけ呼び出す（`query=condensed_query`, `alias_match_text`, `max_tags`, `confidence_threshold`）。失敗時は空集合として継続する。**周回のたびに`select_tags`を呼び直すことはしない**（発注者確認済み。探索手段としては「クエリ再定式化」のみを採用する。ADR-0088）。

### 6.3 Agenticループ

- **F-6.3.1（初回検索）** 1周回目は`search_knowledge(query=condensed_query, tags=選定タグ, top_k=3)`を呼び出す。`tags`は全周回で共通（6.2.3）。
- **F-6.3.2（十分性評価）** 各周回の検索後、LLM（Bedrock Converse API）に次を入力して評価させる。
  - ユーザーの質問（`condensed_query`）
  - これまでに蓄積された検索結果（各件の`title`・`content`）
  - これまでに試したクエリの一覧
- **F-6.3.3（評価の出力）** 十分性評価LLMは次の3項目をJSONで出力する。
  | 項目 | 型 | 内容 |
  |---|---|---|
  | `sufficient` | boolean | 蓄積結果だけで質問に回答できるか |
  | `missing` | string | 不足している観点（`sufficient=true`のときは空文字） |
  | `next_query` | string | 次に`search_knowledge`へ渡すべきクエリ（`sufficient=true`のときは空文字） |
- **F-6.3.4（分岐）** 評価結果に応じて次のように分岐する。
  1. `sufficient=true` → 回答生成へ進む。
  2. `sufficient=false` かつ 周回数 < 上限 かつ `next_query`が非空 → `next_query`で`search_knowledge`を再度呼び出し、次の周回へ入る。
  3. `sufficient=false` かつ 周回数 = 上限（または`next_query`が空） → 蓄積結果が1件以上あれば回答生成へ、0件なら逆質問へ進む。
- **F-6.3.5（反復上限）** 周回数の上限は既定2とし、環境変数`AGENTIC_MAX_ITERATIONS`で変更できるようにする（発注者確認済み。「最大2周回程度」）。上限に達した時点で必ずループを抜ける。
- **F-6.3.6（同一クエリの抑止）** `next_query`が既に試したクエリと（前後空白を除去し完全一致で）同一の場合は再検索せず、上限到達と同じ扱い（F-6.3.4の3）にする。無限ループ・無意味な再検索を防ぐため。
- **F-6.3.7（結果の蓄積と重複排除）** 各周回の検索結果は蓄積する。同一の情報源が複数周回でヒットした場合は、結果`dict`の`id`（存在しない場合は`title`）をキーに重複を除去する。蓄積件数の上限は`top_k × 上限周回数`（既定6件）とする。
- **F-6.3.8（十分性評価の失敗時）** 十分性評価のLLM呼び出しが例外を送出した場合、またはJSONとして解釈できない出力を返した場合は、`sufficient=true`とみなしてループを抜ける（＝現行`/ask-pipeline`と同等の単発検索の挙動へ縮退する）。エラーはログに記録する。
- **F-6.3.9（検索の失敗時）** `search_knowledge`呼び出しが例外を送出した場合、その周回の結果は0件として扱いループを継続する。全周回で失敗した場合は蓄積結果0件となり、逆質問へ進む。

### 6.4 回答生成

- **F-6.4.1** 蓄積された検索結果（F-6.3.7）を`Q: {title}\nA: {content}`形式で連結して`context`を構築する（現行の`_build_context()`と同一形式）。
- **F-6.4.2** `GenerateAnswerLLMBedrock.generate(context, req.text, summary.content, history)`で回答を生成する。**回答生成のプロンプト・システムプロンプトは現行`/ask-pipeline`と同一のものを使う**（`generate.py`を共有する。回答文の体裁を`/ask-pipeline`と揃え、A/B比較の際に「検索の当たり方」の差だけを見られるようにするため）。
- **F-6.4.3** `history`・`next_order`の算出は`/ask-pipeline`と同一とする。

### 6.5 逆質問（情報不足時）

- **F-6.5.1** 反復上限まで探索しても蓄積結果が0件の場合、推測で回答せず、ユーザーへ追加情報を求める応答を返す（発注者確認済み。探索手段として「ユーザへの逆質問」を採用）。
- **F-6.5.2** 逆質問の文面はLLM（Bedrock Converse API）で生成する。入力は「ユーザーの質問（`condensed_query`と`req.text`）」「試したクエリの一覧」「十分性評価が出力した不足観点（`missing`）」とする。出力は、社内QAナレッジベースに該当情報が見つからなかったことを伝えたうえで、**回答に必要な具体的な情報（製品名・画面名・エラーメッセージの全文・操作手順のどこで発生したか等）を1〜3点に絞って尋ねる**日本語の文章1件とする。
- **F-6.5.3** 逆質問生成のLLM呼び出しが失敗した場合は、`GenerateAnswerLLMBedrock`のシステムプロンプト ルール3と同一の定型文（`申し訳ございません、ご提供いただいた情報が不足しています。より詳しい情報を入力してください。`）を返す。
- **F-6.5.4** 逆質問を返す場合も、応答の`messages`の形式は通常の回答時と同一とする（`assistant`メッセージに`input`・`model`・`evaluation=0`を設定する）。`user`メッセージの`context`部分は空文字となる。
- **F-6.5.5** 連続ターンでの逆質問の抑止（何ターン続けて逆質問してよいか）は本書では規定しない（12章 Open Issue #2）。

### 6.6 ログ・可観測性

- **F-6.6.1** 1リクエストにつき、次を`logger.info`で出力する。`conversation_id`を含め、1リクエスト分の周回を追跡できるようにする。
  - `condensed_query`と`req.text`（現行と同一）
  - 選定タグ（件数と名称）
  - 各周回の: 周回番号 / 検索クエリ / ヒット件数 / 十分性評価の`sufficient`・`missing`・`next_query`
  - 最終の: 総周回数 / 蓄積結果件数 / 分岐結果（`generate` or `clarify`）/ 回答長
- **F-6.6.2** 十分性評価のパース失敗・LLM呼び出し失敗は`logger.warning`または`logger.exception`で、生の出力の先頭一部とともに記録する（ADR-0063と同様の診断ログ方針）。

## 8. 非機能要件

- **N-8.1（レイテンシ）** Bedrock呼び出し回数は、現行`/ask-pipeline`の最大3回（要約・言い換え・回答生成）に対し、`/ask-agentic`では最大6回（要約・言い換え・十分性評価×2・回答生成 or 逆質問生成）となる。`search_knowledge`呼び出しは最大2回（現行1回）。反復上限を既定2に抑えることで、レイテンシの悪化を1周回分（十分性評価1回＋検索1回）に限定する。実測値の取得は実装フェーズの課題とする（12章 Open Issue #1）。
- **N-8.2（タイムアウト）** `web_backend`側の中継タイムアウトは既存の`AGENT_INVITRO_TIMEOUT`を用いる。`/ask-agentic`の実測レイテンシが現行の設定値を超える場合は、設定値の見直しを実装フェーズで行う。
- **N-8.3（縮退動作）** Agenticループの追加要素（十分性評価・逆質問生成）が失敗しても、`/ask-agentic`は必ず`200`で応答を返す（F-6.3.8・F-6.5.3）。最悪の場合でも現行`/ask-pipeline`と同等の挙動（1回検索＋回答生成）へ縮退する。
- **N-8.4（ステートレス性）** `/ask-agentic`はリクエスト間で状態を持たない。周回の状態はリクエスト処理中のグラフ`State`にのみ存在し、レスポンスにも含めない（会話文脈の持ち回りは`summary`に一本化するというADR-0084の方針を維持する）。
- **N-8.5（並行性）** 現行同様、Bedrockの`boto3`同期APIは`run_in_threadpool`経由で呼び出し、イベントループを塞がない。
- **N-8.6（テスト容易性）** ユースケース層・十分性評価のパース処理は、MCP・Bedrockへ接続せずに単体テストできること（既存`tests/`と同様、モックで検証可能な純関数として切り出す）。

## 10. Agenticループの実装方式（概要）

`graph/agentic_search.py`に、LangGraphの`StateGraph`で5.3節のグラフを構築する。`create_react_agent`は使わない。

- **State**: `text` / `condensed_query` / `alias_match_text` / `tags` / `current_query` / `tried_queries: list[str]` / `results: list[dict]` / `iteration: int` / `assessment: dict` / `outcome: "answer" | "clarify"` を持つ`TypedDict`。
- **ノード**: `search`（`knowledge.search_knowledge`を呼び、結果を`results`へ重複排除して追加、`iteration`をインクリメント）、`assess`（`assess.SufficiencyAssessorBedrock`を呼び`assessment`を設定）。`condense`・`select_tags`はグラフの前段（ユースケース層）で実行し、初期Stateへ入れる。
- **条件付きエッジ**: `assess`の後に`_route_after_assess(state)`を置き、F-6.3.4の3分岐（`search`へ戻る / `generate`へ / `clarify`へ）を返す。`generate`・`clarify`はグラフの終端ノードとしてもよいし、グラフを`assess`までとしてユースケース層で分岐してもよい（実装フェーズで決定してよい。テスト容易性を優先する）。
- **十分性評価のプロンプト**: `summarize.py`・`condense.py`と同型の構成（Bedrock `converse` API、プロンプト定数を自己完結で保持）を踏襲する。出力は`{"sufficient": bool, "missing": str, "next_query": str}`のJSONオブジェクト1件のみとし、前置き・コードフェンス・説明を含めないようシステムプロンプトで制約する。パースは`json.loads`を試み、失敗した場合は文字列中の最初の`{`から最後の`}`までを切り出して再試行し、それでも失敗すればF-6.3.8のフォールバックに入る。

## 11. 受け入れ基準（Definition of Done）

1. `main/api/server.py`が、`create_app()`の呼び出しと`app`の公開のみを行う10行程度のモジュールになっていること。ルーティング定義・スキーマ定義・実処理のいずれも含まないこと。
2. `agent_invitro.main.api.server:app`というモジュールパスで、再構成前と同じくUvicornが起動できること（Terraformの起動コマンドが変更不要であること）。
3. 再構成後も`GET /health`が`{"status": "ok"}`を返し、`POST /ask-pipeline`が再構成前と同一のリクエスト・レスポンスで動作すること。
4. `POST /ask-agentic`が`/ask-pipeline`と同一のスキーマで応答を返すこと。
5. 初回検索で十分な情報が得られた質問について、周回数1で`generate`へ抜けること（ログで確認）。
6. 初回検索が空振りする質問について、十分性評価が`sufficient=false`と`next_query`を返し、別クエリで`search_knowledge`が再度呼ばれること（ログで確認）。
7. 反復上限（既定2）に達した場合、それ以上`search_knowledge`が呼ばれないこと。`AGENTIC_MAX_ITERATIONS`で上限を変更できること。
8. 上限まで探索しても結果が0件の場合、定型の謝罪文ではなく、不足情報を尋ねる逆質問が返ること。
9. 十分性評価のLLM呼び出しを意図的に失敗させた場合でも、`/ask-agentic`が`500`にならず、1回検索＋回答生成の結果を返すこと。
10. チャット画面のトグルで「エージェント方式」を選ぶとAgentic経路で、「パイプライン方式」を選ぶと従来経路で回答が返ること（ログの`agentic start`の有無で確認できる）。選択がリロード後も維持されること。応答待ちの間はトグルが操作できないこと。`web_backend`の`chat_controller`に中継処理が、`agent_controller`にLLM呼び出し・DBクエリが含まれていないこと（2026-09-15 改訂）。
11. ユースケース層・十分性評価のパース処理に対する単体テストがMCP・Bedrock非接続で通ること（既存`tests/`と同様）。
12. `agent_invitro/README.md`のディレクトリ構成表・ファイル役割表・環境変数表が実態と一致していること。

## 12. Open Issues（要追加確認事項）

1. **レイテンシの実測**: `/ask-agentic`の応答時間（周回1回時／2回時）を実装フェーズで計測し、`AGENT_INVITRO_TIMEOUT`の妥当性を確認する。ADR-0085で既に記録済みの「Bedrock呼び出し追加によるレイテンシ影響の計測」と併せて実施する。

5. **`/ask-pipeline`の廃止時期**: `/ask-agentic`の精度・レイテンシが確認できた後、`/ask-pipeline`を非推奨とするか併存を続けるかを判断する（ADR-0089）。

## 13. 全体スケジュール上の位置づけ（参考）

1. APIレイヤ再構成（`/ask-pipeline`・`/health`の挙動を変えないリファクタリング）
2. Agenticループの実装（`assess.py`・`clarify.py`・`graph/agentic_search.py`・`usecases/ask_agentic.py`）と`/ask-agentic`の追加
3. `web_backend`の中継先パス設定化
4. AWS環境での動作確認・レイテンシ計測・`/ask-pipeline`とのA/B比較

1と2は分離可能であり、1のみを先行してマージしてよい（外部挙動が変わらないため）。
