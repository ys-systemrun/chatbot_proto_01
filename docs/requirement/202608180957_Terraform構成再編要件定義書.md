## 1. 目的

`terraform/`配下の構成が3層（`envs/verify-network` / `envs/verify-database` / `envs/verify`）に分かれていることで理解しづらくなっているという課題を解消するため、次の方針で構成を再編する際の要件を整理する。

1. RDS本体・その前提となるネットワーク基盤・RDSへのシード投入用ECS周辺リソースを1つの構成（以下「database構成」）にまとめる。
2. アプリケーション側のECS常駐サービス周辺リソースを、database構成とは別の1つの構成（以下「app構成」）にまとめる。
3. database構成・app構成のstateファイルは分離するが、既存と同じS3バケットの異なるパスにそれぞれ配置する。
4. database構成・app構成それぞれを単独でapplyするスクリプト、両方をまとめてapplyするスクリプトを用意する。
5. database構成・app構成それぞれを単独でdestroyするスクリプトを用意する。
6. database構成のRDSに対してシード（データ投入）を行うスクリプト（実体はECSタスクをRun Taskとして起動するもの）を用意する。

Terraformコード自体の実装・スクリプトの実装（コーディング）は本書の対象外とし、要件定義および設計判断（ADR-0039）の整理にとどめる。実装は本書を入力として、別途の実装フェーズ（実装指示書の作成含む）で行う。

## 2. 背景・課題

現行の`terraform/`は、ADR-0036〜0038により次の3層のTerraform root（各々独立state、ADR-0027のS3バックエンド）に分割されている（詳細は`terraform/README.md`）。

- `envs/verify-network`（ネットワーク層）: 既存VPC/サブネット参照 + セキュリティグループ5種 + VPCエンドポイント
- `envs/verify-database`（DB層）: RDS(pgvector) + DBサブネットグループ + `DATABASE_URL`シークレット
- `envs/verify`（アプリ層）: ECR5リポジトリ + ECS Fargateクラスタ + Service Connect名前空間 + 常駐サービス3種 + `db_hiroba_qa_init`のRun Taskタスク定義 + MCP Inspector検証タスク定義 + Bedrock予算アラート

この3層構成は、ADR-0037が課題視した「RDSの誤destroy防止」「DB層とアプリ層の変更頻度の違いの分離」には対応できているが、実際に運用してみると次の問題がある。

- ディレクトリが3つに分かれ、かつ`terraform_remote_state`による層間参照（network ← database ← app）があるため、あるリソースを変更したいときにどのディレクトリを触ればよいか、他層にどう影響するかを都度確認する必要があり、構成全体の見通しが悪い。
- ネットワーク層とDB層は、実務上ほぼ常にセットで扱われており（`deploy.ps1`も両者を連続してapplyする)、3層に分けている実益が薄い。
- シード用ECSリソース（`db_hiroba_qa_init`のタスク定義）は「RDSにデータを投入するための専用リソース」であるにもかかわらず、現状はDB層ではなくアプリ層に置かれており、DB関連のリソースがDB層とアプリ層に分散している。

これらを踏まえ、ADR-0039にて「ネットワーク・DB・シード用ECSリソースをdatabase構成、アプリ側ECS常駐サービス周辺リソースをapp構成とする2層構成」への再編を決定した。本書はその具体的な要件を整理する。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| database構成（`terraform/main/database`） | 本書で新設する、RDS本体・ネットワーク基盤・シード用ECS周辺リソースをまとめたTerraform root（state）。現行の`envs/verify-network`と`envs/verify-database`、および`envs/verify`内の`db_hiroba_qa_init`関連リソースを統合したもの |
| app構成（`terraform/main/app`） | 本書で新設する、アプリケーション側ECS常駐サービス周辺リソースをまとめたTerraform root（state）。現行の`envs/verify`からdatabase構成へ移設する分（シード用リソース）を除いたもの |
| シード | `db_hiroba_qa_init`をECSのRun Taskとして実行し、RDSへマイグレーション・QA/タグデータ投入（embedding計算含む）を行う処理（ADR-0016〜0018, 0030） |
| Run Task | ECSで常駐サービスを作らず、必要なときだけ`aws ecs run-task`で都度起動するタスク実行方式。`db_hiroba_qa_init`・MCP Inspector検証タスクで採用 |
| state分離 | Terraformの管理単位（root）ごとに異なるstateファイル（本書では同一S3バケット内の別パス）を持たせること（ADR-0027） |

## 4. スコープ

### 4.1 対象範囲

- `terraform/`配下のディレクトリ構成の再編（database構成・app構成への2分割）。
- database構成・app構成のstate配置（同一S3バケット、別パス）の要件。
- database構成・app構成それぞれのapply/destroyスクリプト、両方をまとめてapplyするスクリプト、database構成のRDSに対するシード実行スクリプトの機能要件。
- 現行3層構成から新2層構成への移行方針（既存ファイルの削除方針）。

### 4.2 対象外

- Terraformコード自体の実装（`.tf`ファイルの作成・編集）およびスクリプト（`.ps1`/`.bat`）自体の実装。本書は要件定義のみを行う。
- ECS/RDS/ネットワーク等、AWSリソースそのものの設計変更（ADR-0023〜0031, 0034, 0036は本書のスコープ外であり、内容を変更しない。単にそれらのリソースがどのTerraform rootに属するかの再配置のみを扱う）。
- アプリケーションコード（`knowledge_mcp`等）の変更。
- 本番環境・複数環境対応（現行同様、検証環境`verify`のみを対象とする。将来別環境を追加する場合の拡張性は15章オープンイシューで触れるに留める）。

## 5. 現状構成の整理

### 5.1 現行の3層とモジュールの対応

| 層（現行ディレクトリ） | 含まれるモジュール | 主なリソース |
|---|---|---|
| `envs/verify-network` | `modules/network` | 既存VPC/サブネットのdata参照、SG5種（`agent_invitro`/`tag_selector_mcp`/`knowledge_mcp`/`rds`/`verification_task`/`vpc_endpoints`）、VPCエンドポイント（S3 Gateway + Interface×7） |
| `envs/verify-database` | `modules/database` | RDS(pgvector)、DBサブネットグループ、`DATABASE_URL`シークレット |
| `envs/verify` | `modules/ecr`、`modules/service-discovery`、`modules/ecs-cluster`、`modules/ecs-service`(×3)、`modules/db-init-task`、`modules/mcp-inspector-task`、`modules/cost-alert` | ECR5リポジトリ、Service Connect名前空間、ECS Fargateクラスタ、常駐サービス3種、`db_hiroba_qa_init`タスク定義、MCP Inspectorタスク定義、Bedrock予算アラート |

このほか`terraform/bootstrap`（state保管用S3バケット作成、Phase 0）は、いずれの層にも属さない前提処理として現行どおり独立して存在する。

### 5.2 現行の層間依存

`envs/verify-database`は`envs/verify-network`の出力（`private_subnet_ids`・`sg_rds_id`）を、`envs/verify`は`envs/verify-network`と`envs/verify-database`の両方の出力を、それぞれ`terraform_remote_state`（S3バックエンド、同一バケット内の別キー参照）で読み込んでいる。依存の向きは一方向（network ← database ← app）。

## 6. 新構成（database構成/app構成）の全体方針

ADR-0039の決定に基づき、次の方針で再編する。

- database構成とapp構成は独立したTerraform root（別ディレクトリ、別state）とする。
- 依存は現行同様に一方向とし、**app構成 → database構成**の出力参照のみとする（database構成はapp構成の出力を参照しない）。参照方式は現行と同じ`terraform_remote_state`（S3バックエンド、同一バケット内の別パス）を踏襲する。
- 現行の`envs/verify-network`と`envs/verify-database`は廃止し、database構成に統合する。
- 現行の`envs/verify`のうち、`db_hiroba_qa_init`のタスク定義（シード用）とそのECRリポジトリはdatabase構成へ移設する。それ以外（常駐サービス・クラスタ・MCP Inspector・予算アラート・残りのECR）はapp構成として存続する。
- `terraform/bootstrap`（state用S3バケット作成）は変更しない。database構成・app構成どちらの前提としても、現行どおり最初に一度だけ実行する独立処理のままとする。
- RDS（database構成に含まれる）を通常運用のdestroy対象外とする方針（ADR-0037の中核方針）は維持する。対象範囲が「DB層のみ」から「database構成全体」に広がる点が変更点。

## 9. State/バックエンド要件

- Terraform state用S3バケット名は次を既定値とする: **`chatbot-invitro-terraform-state-349131272460-us-east-1-an`**（`bootstrap`の`state_bucket_name`にこの値を指定する）。database構成・app構成とも同一のこのバケットを使用し、新規バケットは作成しない。
- state key（パス）は次を既定値とする。
  - database構成: `database/state.tfstate`
  - app構成: `app/state.tfstate`
- 完全なS3上のパスは既定値としてそれぞれ次のとおり。
  - `chatbot-invitro-terraform-state-349131272460-us-east-1-an/database/state.tfstate`
  - `chatbot-invitro-terraform-state-349131272460-us-east-1-an/app/state.tfstate`
- **バケット名・keyのいずれも、`.tf`ファイルやスクリプト本体への直書き（ハードコード）は行わず、`scripts/.env`（ADR-0038のTF_VAR_*供給方式を拡張）または`terraform.tfvars`から注入できるようにする。** 上記の値は「変更しない限り使われる既定値」であり、必要であれば`.env`側の値を書き換えるだけで別のバケット名・パスに切り替えられる状態を要件とする。
- ただし、この注入方法にはTerraformの仕様上の制約があるため、参照経路を次の2種類に分けて扱う（実装フェーズではこの区別を明確にすること）。
  1. **自分自身のstateの保存先（`backend "s3" { ... }`ブロック）**: Terraformの`backend`ブロックは`var.*`を参照できない（変数解決より前に評価されるため）。そのため、bucket/key/regionはいずれも`backend.tf`に固定値を書き込まず、`terraform init -backend-config="bucket=..." -backend-config="key=..." -backend-config="region=..."`で都度渡す運用とする（現行の`bucket`/`region`と同じ扱いに`key`も揃える）。この`-backend-config`に渡す値（`STATE_BUCKET`・`STATE_KEY_DATABASE`・`STATE_KEY_APP`）は`scripts/.env`で一元管理し、`common.ps1`の`Initialize-Backend`ヘルパーがそこから読み取って渡す（10章）。手動`terraform init`を行う場合も、README上で`.env`の値を確認したうえで同じ`-backend-config`を渡す手順を明記する。
  2. **他方の構成のstateを参照する`terraform_remote_state`データソースの`key`引数**: これは通常のリソース引数であり、`backend`ブロックとは異なり`var.*`を参照できる。app構成がdatabase構成の出力を参照するために使う`key`は、`variable "database_state_key"`（既定値`database/state.tfstate`）としてapp構成側に定義し、`.env`の`STATE_KEY_DATABASE`を`TF_VAR_state_key_database`として供給する（`terraform.tfvars`側で個別に上書きすることも可能）ことで、通常の意味での「tfvars/envからの変数注入」を実現する。
- この2系統に分けることで、「database構成が自分のstateをどのkeyに保存するか」と「app構成がdatabase構成のどのkeyを参照するか」の値のズレ（例えばdatabase構成側のkeyだけ変更してapp構成側の参照設定を更新し忘れる）を、`.env`側の値を1箇所変えるだけで両方に反映できるようにする。
- 旧3層のkey（`chatbot-invitro/verify-network.tfstate`／`verify-database.tfstate`／`verify.tfstate`、旧バケット名の場合を含む）は新構成では使用しない。13章のとおり移行対象のリソース・stateは存在しないため、単純に新しいバケット名・パスで構築する。
- ロック方式（Terraform 1.10以上のS3ネイティブロック`use_lockfile=true`、またはそれ未満でのDynamoDBロックテーブル）は現行のまま変更しない。
- `backend.tf`の`encrypt = true`・`default_tags`（`Project`/`Env`/`Layer`/`Managed`）等のタグ付け方針も踏襲する。`Layer`タグの値はdatabase構成/app構成を識別できる値（`database`/`app`）とする。

## 10. 変数・tfvars要件

- ADR-0038の方針（`aws_region`/`aws_account_id`/`name_prefix`/`state_bucket`は`scripts/.env`から`TF_VAR_*`として供給し、各rootの`terraform.tfvars`には書かない）は、対象rootが3つから2つに減る点を除きそのまま踏襲する。`state_bucket`の値は9章の既定値`chatbot-invitro-terraform-state-349131272460-us-east-1-an`を`.env`の`STATE_BUCKET`に設定する（変更したい場合はここを書き換えるだけでよい）。
- **9章の方針に基づき、`.env`にstate keyの2項目を新設する。**
  - `STATE_KEY_DATABASE`（既定値: `database/state.tfstate`）… database構成が自分のstateを保存するkey。`common.ps1`が`-backend-config="key=..."`として使う。
  - `STATE_KEY_APP`（既定値: `app/state.tfstate`）… app構成が自分のstateを保存するkey。同上。
  - `STATE_KEY_DATABASE`はあわせて`TF_VAR_state_key_database`としてもexportし、app構成側の`variable "state_key_database"`（`terraform_remote_state`でdatabase構成を参照する際の`key`引数）に自動的に渡るようにする。個別に上書きしたい場合はapp構成の`terraform.tfvars`で`state_key_database`を指定すれば`.env`の値より優先される。
- database構成の`terraform.tfvars`に残す層固有値: 既存VPC/サブネットID（`vpc_id`/`private_subnet_ids`）、VPCエンドポイント作成要否（`create_vpc_endpoints`）、RDSエンジンバージョン（`rds_engine_version`）等のRDS設定、`deletion_protection`/`skip_final_snapshot`、シード関連の環境変数（`csv_data_dir`等）。
- app構成の`terraform.tfvars`に残す層固有値: BedrockモデルID（チャット・埋め込み）、`embedding_vector_dim`、`service_namespace`、イメージタグ関連、予算アラート関連（`bedrock_monthly_budget_usd`/`budget_alert_emails`）、必要であれば`state_key_database`の上書き値。
- app構成がdatabase構成の出力を参照するために必要な`state_bucket`・`state_key_database`は、引き続き`.env`（`TF_VAR_state_bucket`・`TF_VAR_state_key_database`）経由で供給する。
- `scripts/.env.example`のコメント（現行「全層（network/database/app）に供給する」等の記述）は、2層構成・新しいstate key変数に合わせて更新する。

## 11. スクリプト要件

現行の`deploy.ps1`（3層一括apply+ECRビルド+シード+ゲート解除）・`destroy.ps1`（アプリ層のみ）・`destroy-database.ps1`（DB層、要確認）が持っていた安全策・運用フローは、2層構成でも機能として維持する。以下、各スクリプトの機能要件を整理する（実装は対象外）。

### 11.1 共通要件

- いずれのスクリプトも、現行の`common.ps1`が提供する仕組み（前提ツール確認、AWS認証確認、`.env`読み込みによる`TF_VAR_*`供給、`terraform init -backend-config`によるバックエンド初期化ヘルパー、確認プロンプト`Confirm-Or-Exit`）を踏襲・再利用する。
- `Initialize-Backend`ヘルパーに渡す`key`引数は、現行のようにスクリプト内に文字列を直書きするのではなく、`Import-Config`が`.env`から読み込んだ`STATE_KEY_DATABASE`/`STATE_KEY_APP`（9章・10章）を渡す形に変更する。
- `common.ps1`内のディレクトリ変数（`NetworkDir`/`DatabaseDir`/`VerifyDir`）は、2層構成に合わせて`DatabaseDir`（`terraform/main/database`）・`AppDir`（`terraform/main/app`）に再編する。
- ~~Windows PowerShell 5.1互換、`.bat`からの起動という現行の実行方式（ダブルクリック実行）を維持する。~~
  → **ADR-0040 により改訂**: デプロイ実行系は **Docker コンテナ内の Python** とし、`.bat` からの起動（ダブルクリック実行）は維持する（`.bat` は `docker run` の薄いラッパになる）。Windows PowerShell 5.1 互換要件は撤回する（CP932×PS5.1 固有の不具合を根本回避するため）。上記で「`common.ps1` が提供する仕組み」「`Initialize-Backend`」「`Import-Config`」「`Get-Tfvars`」等の PowerShell 実装に言及している箇所は、ADR-0040 以降は同等機能の Python 実装（`terraform/deploy/src/`）に読み替える。設定は単一 `terraform/.env`（`TF_VAR_*` を含む）へ集約し、`terraform.tfvars` は廃止する。

### 11.2 apply-database（database構成のみapply）

- database構成ディレクトリで`terraform init`（バックエンドkey: `.env`の`STATE_KEY_DATABASE`、既定値`database/state.tfstate`）→ ECRリポジトリ（シード用1件）を先行apply → シード用イメージ（`db_hiroba_qa_init`）のdocker build/push → database構成全体をapply、という順序をとる（現行`deploy.ps1`のECR先行apply+build/pushの流れをdatabase構成に適用したもの）。
- database構成の`terraform.tfvars`が未作成の場合は雛形を生成して安全に停止する（現行`Get-Tfvars`の挙動を踏襲）。
- 単独実行できることを想定する（例: ネットワーク設定やRDSパラメータのみ変更したい場合に、app構成へ影響を与えずに適用したいケース）。

### 11.3 apply-app（app構成のみapply）

- 前提としてdatabase構成が既にapply済み（database構成のstateが存在し出力が参照可能）であることを確認する。未applyの場合はエラーメッセージで停止する。
- app構成ディレクトリで`terraform init`（バックエンドkey: `.env`の`STATE_KEY_APP`、既定値`app/state.tfstate`）→ ECRリポジトリ（残り4件）を先行apply → 4イメージのdocker build/push → app構成全体をapply、という順序をとる。`knowledge_mcp`はシード未完了時のゲート（`knowledge_mcp_desired_count=0`）を維持できるよう、デフォルト値または呼び出し元からの指定を受け付ける。
- 単独実行できることを想定する（例: アプリイメージの更新・再デプロイのみ行いたいケース。RDS・ネットワークには影響しない）。

### 11.4 apply-all（database構成・app構成一括apply）

- `apply-database` → `apply-app`（`knowledge_mcp_desired_count=0`で起動） → `seed`（11.6節） → シード完了（exitCode=0）確認後、app構成を再apply（`knowledge_mcp_desired_count=1`）、という一連の流れを自動化する。現行`deploy.ps1`のPhase0〜5の流れを、2層構成向けに再構成したものに相当する。
- Phase 0（`bootstrap`によるstateバケット作成、未作成時のみ）の実行は現行同様に維持する。バケット名は`.env`（`STATE_BUCKET`）の既定値`chatbot-invitro-terraform-state-349131272460-us-east-1-an`を使用する。
- 全体の実行前に課金リソース作成に関する確認プロンプトを表示する（現行`Confirm-Or-Exit`を踏襲）。`-AutoApprove`相当のオプションも維持する。
- MCP Inspectorによる検証（現行README Phase 6）は、現行同様に本スクリプトの対象外（手動実施）とする。

### 11.5 destroy-database（database構成のみdestroy）

- **RDS本体を含む取り消し不可能な操作**であるため、現行`destroy-database.ps1`と同等以上の安全策を維持する: 実行前に警告文（RDSと投入済みQA/タグデータが完全に失われ、再構築には再シード＝Bedrock再計算が必要になる旨）を表示し、`destroy-database`等の文字列入力によるタイプ確認を要求する。
- RDSは`deletion_protection=true`が既定のため、`terraform apply -var deletion_protection=false`で保護解除してから`terraform destroy -var deletion_protection=false -var skip_final_snapshot=true`を実行する2段階の手順を維持する（現行`destroy-database.ps1`の手順を踏襲）。
- **実行前提として、app構成が既にdestroy済み（またはそもそも未applyである）ことを確認・警告する。** ネットワーク層がdatabase構成に統合されたことにより、app構成のリソース（ECSサービス等）がdatabase構成のセキュリティグループやサブネットIDを利用している状態のままdatabase構成のdestroyを実行すると、AWS側の依存関係違反でdestroyが失敗する可能性があるため（ADR-0039「結果・影響」参照）。少なくとも警告メッセージで明示し、可能であればapp構成のstateが空でないことを検出した場合に停止する。
- 実行後、VPCエンドポイント（Interface型は時間課金）も含めて完全に削除される旨をメッセージで案内する。

### 11.6 destroy-app（app構成のみdestroy）

- 現行`destroy.ps1`と同等の位置づけ（コスト管理目的で日常的に実行する、RDS・ネットワークは残る安全な操作）とする。確認は`destroy-database`ほど厳重でなくてよいが、タイプ確認（例: `destroy-app`）は維持する。
- destroy後もRDS（database構成）は残ること、再度使う場合は`apply-app`のみで復旧できることをメッセージで案内する。

### 11.7 seed（database構成のRDSに対するシード実行）

- database構成・app構成の両方が既にapply済みであることを前提とする（タスク定義はdatabase構成、実行先のECSクラスタはapp構成にあるため、両方のTerraform出力が必要）。
- 処理内容は現行`deploy.ps1`のPhase 4相当をそのまま踏襲する: app構成の`cluster_name`・database構成の`private_subnet_ids`・`sg_verification_task_id`・`db_init_task_family`を`terraform output`で取得し、`aws ecs run-task`でシードタスクを起動、`STOPPED`になるまでポーリングし、`exitCode=0`を確認する。タイムアウト・異常終了時は明確なエラーメッセージ（CloudWatch Logsのロググループ名を含む）で停止する。
- `apply-all`から呼び出されるほか、**単独でも実行できる**ようにする（データ修正後の再シードなど、インフラのapplyを伴わずにシードだけやり直したいケースに対応するため）。
- 実行前に「既存データを消さずに追記/更新するのか、既存データがある場合の冪等性はどう扱うか」は現行のシード処理自体の仕様（ADR-0018の冪等性設計）に従い、本スクリプトはRun Taskの起動・監視のみを担う。

## 12. 運用フロー

### 12.1 初回デプロイ

1. `bootstrap`でstate用S3バケット（`chatbot-invitro-terraform-state-349131272460-us-east-1-an`）を作成（初回のみ、`apply-all`が自動化）。
2. database構成・app構成の`terraform.tfvars`を用意する。
3. `apply-all`を実行する（database構成apply → app構成apply（ゲート閉） → シード実行 → app構成再apply（ゲート開放））。
4. MCP Inspector・`agent_invitro`の手動検証（現行README Phase 6相当）を行う。

### 12.2 アプリのみ更新（日常運用）

- イメージの更新やサービス設定変更のみの場合は`apply-app`のみを実行する。RDS・ネットワークには影響しない。

### 12.3 コスト管理のための一時停止

- 検証を中断してコストを抑えたい場合は`destroy-app`を実行する（RDSは残る）。再開時は`apply-app`のみで復旧できる（再シード不要）。

### 12.4 プロジェクト完全終了時

- `destroy-app`を先に実行し、その後`destroy-database`を実行する（この順序を厳守する。11.5節参照）。

## 13. 移行方針（現行3層構成からの切り替え）

- **現時点でAWS上への実デプロイは行っていないことを確認済み。** そのため、S3上に旧3層構成のstateファイル（`verify-network.tfstate`等）や、対応する実AWSリソースは存在しない。`terraform state mv`等によるstate移行や、既存RDSデータの保全を考慮した切り替え手順は不要である。
- 本再編は、既存の`terraform/`配下（`envs/verify-network`・`envs/verify-database`・`envs/verify`とそのファイル一式）を単純に削除し、8章の新構成としてゼロから作成する方針とする（差分改修は行わない）。`modules/`配下の各モジュール（`network`/`database`/`db-init-task`/`ecr`/`ecs-cluster`/`ecs-service`/`service-discovery`/`mcp-inspector-task`/`cost-alert`）自体はリソース定義を変更する必要がないため、既存の実装をほぼそのまま新しい`terraform/main/database`・`terraform/main/app`から呼び出し先を変更するだけで再利用できる見込みである。
- `bootstrap`（state用S3バケット作成）も、まだ一度も実行されていない前提であれば、新構成の`apply-all`から初回実行すればよく、特別な移行操作は不要。`.env`（`STATE_BUCKET`）の既定値（`chatbot-invitro-terraform-state-349131272460-us-east-1-an`）で新規作成する。

## 14. 受け入れ基準

- `terraform/`配下が、8章のディレクトリ構成（`bootstrap` + `main/database` + `main/app` + `modules/` + `scripts/`）になっていること。
- database構成・app構成のstateが、既定ではS3バケット`chatbot-invitro-terraform-state-349131272460-us-east-1-an`内の`database/state.tfstate`・`app/state.tfstate`にそれぞれ保存され、`terraform_remote_state`によりapp構成→database構成の一方向参照が機能すること。
- バケット名・state keyが`.tf`ファイルやスクリプト本体にハードコードされておらず、`scripts/.env`（`STATE_BUCKET`/`STATE_KEY_DATABASE`/`STATE_KEY_APP`）の値を書き換えるだけで別のバケット名・パスに切り替えられること（9章）。
- 7章の割り当て表通りに、各モジュールがdatabase構成・app構成いずれかに重複なく所属していること。
- `apply-database`/`apply-app`/`apply-all`/`destroy-database`/`destroy-app`/`seed`の6スクリプト（`.ps1`+`.bat`）が用意され、11章の機能要件を満たすこと。
- `destroy-database`実行時にRDS削除保護解除→destroyの2段階手順とタイプ確認が機能し、`destroy-app`ではRDSが残存すること（12.3・12.4節のシナリオで確認）。
- `apply-all`実行後、シード完了（exitCode=0）を経て`knowledge_mcp`が起動すること（現行Phase4→5ゲートと同等の挙動）。
- 既存の`terraform/`配下（旧3層構成）が削除され、8章の新構成に置き換わっていること（13章：state移行は不要であることを確認済み）。

## 15. オープンイシュー

以下のうち、ディレクトリ・stateパスの命名、Bedrock予算アラートの帰属（app構成）、既存AWS環境への移行方式（デプロイ実績なし、移行不要）は2026-08-18時点で確認・確定済み（8章・9章・13章に反映済み）。残るオープンイシューは次のとおり。

1. **ECRモジュールの分割方法**: 現行は`module.ecr`を1回呼び出し5リポジトリをまとめて作成しているが、本書ではdatabase構成（1リポジトリ）・app構成（4リポジトリ）に分けて2回呼び出す前提としている。この分割方針でよいか確認する。
2. **`modules/database`と`main/database`の名称重複**: 8章で触れたとおり、モジュール名（`modules/database`）とTerraform root名（`main/database`）が同名になる。実務上大きな支障はないと考えられるが、分かりやすさを優先して`modules/database`側を`modules/rds`等に改称するかは確認する。
3. **MCP Inspector検証タスク（`modules/mcp-inspector-task`）の帰属**: `sg_verification_task`は`db_hiroba_qa_init`（database構成側処理）とMCP Inspector（アプリ側検証）の両方に共用されているセキュリティグループである。本書はMCP Inspectorをアプリ側の検証という性質からapp構成に割り当てているが、「シードと同じ検証系リソースとしてdatabase構成にまとめたい」という考え方もあり得るため確認する。
4. **destroy-databaseの安全ガード実装レベル**: 11.5節で述べた「app構成が残っている場合の警告・停止」を、スクリプトが自動検出して強制停止するレベルまで実装するか、警告メッセージの表示に留めるかは実装フェーズで確定する。
5. **将来の複数環境対応**: 本書は現行同様「検証環境（verify）のみ」を前提とするが、将来的に本番相当の環境を追加する場合、`terraform/main/`配下に`<env>-database`/`<env>-app`のような形で追加する拡張、または環境ごと`main-<env>/`のような形で分ける拡張のいずれかで対応できる想定である。今回のスコープでは設計のみ触れ、実装は対象外とする。
