# QAデータ・タグ管理UI（front_dev / web_backend 拡張）要件定義書

- 文書番号: REQ-202608060826
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: front_dev（既存デバッグUIの拡張）, web_backend（既存FastAPIアプリの拡張）, Knowledge MCP サーバ（既存、管理系ツールの追加）
- 参照資料: `docs/requirement/202608041002.md`（Knowledge MCP サーバ要件）, `docs/requirement/202608051636.md`（Tag Selector MCP サーバ要件）
- 前提の決定事項: 本書末尾「14. 関連ADR一覧」参照

## 1. 目的

現行の `front_dev` は、チャット応答の動作確認を行うためのデバッグUI（`App.tsx` / `AppStateless.tsx` / `AppEvaluatedMessages.tsx` の3画面）のみを提供しており、QAデータ（質問・回答）やタグの内容・タグ付与状況を一覧で確認する手段、およびそれらを画面から登録・編集する手段が存在しない。現状、QA・タグの内容を確認・変更するには、DBへの直接SQL操作か、Knowledge MCP サーバのMCPツール（`search_knowledge` / `list_tags` / `create_tag` 等）をMCPクライアントから個別に呼び出す方法しかなく、運用担当者が日常的に扱うには不向きである。

本書は、`front_dev` と `web_backend` に、次の機能を追加するための要件を整理したものである。コーディングは対象外とし、要件定義および設計判断（ADR）の整理にとどめる。

1. QAデータの内容・タグ付与状況を一覧して確認できるページ
2. タグおよびタグの階層構造を確認できるページ
3. QAデータの登録・編集機能
4. タグの登録・編集機能

## 2. 背景・参照資料

- `front_dev` は現状、`main.tsx` が `window.location.pathname` を見て3エントリ（`App` / `AppStateless` / `AppEvaluatedMessages`）を切り替えるのみの単純な構成であり、ルーティングライブラリ（React Router 等）は導入されていない（`docs/requirement/202608041002.md` 等の対象外）。
- `web_backend` は現状、FastAPI アプリ（`main.py` / `main_stateless.py`）が `src/db.py` の `DB` クラスを介して `chatbot_db`（pgvector, PostgreSQL）へ直接クエリを発行する構成であり、Knowledge MCP サーバ・Tag Selector MCP サーバとは連携していない（両MCPサーバは独立コンテナとして並行稼働している。README「Knowledge MCP サーバ」節参照）。
- ADR-0005（タグの関連テーブル化）・ADR-0006（タグ管理機能の提供方式）により、`tag` テーブルへの書き込みは Knowledge MCP のMCPツール（`list_tags` / `create_tag` / `rename_tag` / `move_tag` / `delete_tag`）に暫定的に集約する方針が既に決定されている。ただし、これらのツールは MCPクライアントからの利用を前提としており、業務担当者が使えるWeb UIは存在しない。
- QAデータ本体（`qa_original` / `question_altered` / `qa_tag`）の登録・編集を担うツール・APIは、現時点でどのコンポーネントにも存在しない。
- ADR-0008 では、Knowledge MCP 側のタグ管理ツールを `description`（説明文）・`alias`（同義語）の編集にも対応させる拡張が「将来的に必要」「別途スケジューリングする必要がある」将来課題として記載されている（`docs/requirement/202608041002.md` Open Issue #1 とも関連）。本書はこの拡張のうち、管理UIから必要になる範囲を要件として取り込む。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| QA管理UI | 本書で追加する、QAデータの一覧・登録・編集を行う `front_dev` 上のページ群 |
| タグ管理UI | 本書で追加する、タグ階層の確認・登録・編集を行う `front_dev` 上のページ群 |
| BFF（Backend For Frontend） | 本書における `web_backend` の新規APIの位置付け。`front_dev` からのリクエストを受け、Knowledge MCP のMCPツール呼び出しへ変換して結果を返す層 |
| 管理系ツール | Knowledge MCP が提供する、QA・タグの参照・登録・編集用のMCPツール群（既存のタグ管理ツール＋本書で追加するQA管理ツール） |
| タグ階層 | `tag.parent_tag_id` による自己参照で表現される、タグの親子関係（ADR-0005） |

## 4. スコープ

### 4.1 対象範囲（MVP）

**front_dev**

- a. QA一覧ページ: QAデータ（`qa_original`）の内容とタグ付与状況（`qa_tag`）を一覧表示し、キーワード・カテゴリ・タグで絞り込める。
- b. タグ階層ページ: タグ（`tag`）の親子構造をツリー表示し、各タグに紐づくQA件数を確認できる。
- c. QA登録・編集フォーム: 新規QAの登録、既存QAの編集（本文・カテゴリ・タグ紐付けの変更）。
- d. タグ登録・編集UI: 新規タグの作成、名称変更、親タグの変更（再配置）、削除。タグ階層ページに統合する。

**web_backend**

- 上記UIから呼び出す新規REST APIエンドポイント群（`/api/qa/*`, `/api/tags/*`, `/api/categories`）。BFFとしてKnowledge MCP のMCPツールを呼び出し、結果をJSONへ整形して返す（6.4節、ADR-0013）。
- 既存のチャット系エンドポイント（`/ask`, `/ask-sl`, `/session/{id}`, `/evaluate_response`, `/evaluated_messages`）は変更しない。

**Knowledge MCP サーバ**

- QA管理用の新規MCPツール（`list_qa` / `get_qa` / `create_qa` / `update_qa`）の追加（6.5節、ADR-0014）。
- 既存タグ管理ツールの `description` / `tag_alias` 対応拡張（6.6節、ADR-0008 Open Issue対応）。

### 4.2 対象外（将来検討・別プロジェクトスコープ）

- QAデータの削除機能（`question_altered` / `qa_tag` を含む影響範囲の精査、および会話ログ等からの参照有無の確認が必要なため、本フェーズでは見送る）。
- `question_altered`（パラフレーズ）個別行の一覧・編集、およびLLMによるパラフレーズ自動生成のUI化（本フェーズはQA登録時に1件を自動生成するのみ。6.3節・13章 Open Issue参照）。
- タグ・QAデータの一括インポート/エクスポート（CSV等）。
- 認証・権限管理（誰が編集操作を行えるかのアクセス制御。13章 Open Issue、および既存要件定義書 Open Issue #4・#10 と共通の課題として扱う）。
- カテゴリ（`category`）自体の新規作成・編集（本フェーズは既存カテゴリからの選択・参照のみ。13章 Open Issue参照）。
- Tag Selector MCP のタグ知識ベースキャッシュへの即時反映保証（既存のポーリング／`reload_taxonomy` の仕組みに依存し、本フェーズでは変更しない）。
- `front_dev` 全体のルーティング方式変更（既存チャット画面は現状のpathname分岐を維持し、新設する管理画面サブツリーのみ対応する。ADR-0015参照）。

## 5. 全体アーキテクチャ

### 5.1 システム構成（本フェーズ）

                                 │ HTTP (Vite dev proxy)

                 │  新規: /api/qa/*, /api/tags/*,  │
                 │        /api/categories（BFF）    │
                 └──────┬───────────────┬─────────┘
                        │               │
              既存: 直接DBアクセス   新規: MCP over HTTP
              （chat機能のみ、変更なし）      │
                        │               ▼
                        │       ┌───────────────────┐
                        │       │  Knowledge MCP サーバ  │
                        │       │  既存: search_knowledge,│
                        │       │  list_tags 等          │

                        │       │  対応拡張               │

|---|---|

| front_dev（QA/タグ登録編集フォーム） | 入力フォームの提供、バリデーション（必須項目チェック等）、`web_backend` の新規APIの呼び出し |
| web_backend（新規 `/api/*` エンドポイント） | `front_dev` からのHTTPリクエストを受け付け、Knowledge MCP のMCPツール呼び出しへ変換し、レスポンスをJSONへ整形して返す（BFF） |
| Knowledge MCP（既存タグ管理ツール＋新規QA管理ツール） | QA・タグに対する参照・登録・編集の業務ロジック（バリデーション、循環参照防止、embedding計算等）を一元的に実装する |
| データストア | 既存 `chatbot_db`（pgvector）。Knowledge MCP のみが書き込みを行う（`web_backend` の既存chat機能を除く） |

## 6. 機能要件

### 6.1 front_dev: QA一覧ページ

- 一覧表示項目: `id`（guid）, `title`, `question_text`（抜粋）, `answer_text`（抜粋）, `category`, 付与タグ一覧（バッジ表示）, 紐づく `question_altered` 件数。
- 検索・絞り込み: キーワード（`title` / `question_text` / `answer_text` の部分一致）、カテゴリ、タグ（複数選択、AND条件）。
- ページング: 件数が多くなることを想定し、`limit` / `offset` 方式のページングに対応する（詳細な既定値・上限は詳細設計フェーズで確定）。
- 各行から編集フォーム（6.3節）へ遷移するリンク、および新規登録フォームへの遷移ボタンを設ける。
- タグが1件も付与されていないQAを識別できる表示（例: 「タグ未設定」バッジ）を設け、タグ付与状況の確認を容易にする。

### 6.2 front_dev: タグ階層ページ

- Knowledge MCP の `list_tags` ツールが返す木構造をそのままツリー表示（折りたたみ可能）する。
- 各タグに `id` / `name` / `description`（6.6節拡張後） / 紐づくQA件数を表示する。
- 本ページから以下の操作を行える。
  - 新規タグの作成（親タグの指定は任意）
  - タグ名・説明文（`description`）の変更
  - 親タグの変更（再配置。プルダウンによる新親タグ選択方式とする。ドラッグ&ドロップ等の高度なUIは対象外）
  - タグの削除
- 削除不可（子タグが存在する、または `qa_tag` から参照されている）の場合は、その理由をUI上に表示し、削除操作自体を無効化する（Knowledge MCP側の拒否ロジック（ADR-0006）と重複してよいが、UI側でも事前に判定し誤操作を防止する）。

### 6.3 front_dev: QA登録・編集フォーム

- 入力項目: `title`（必須）, `question_text`（必須）, `answer_text`（必須）, `category`（既存カテゴリからの選択。新規カテゴリ作成は対象外）, タグ（複数選択。タグ階層ページと同じタグピッカーコンポーネントを再利用する）。
- 新規作成時の保存処理: `guid` を発行し、`question_text` をそのまま内容とする `question_altered` 行を1件自動生成し、embeddingを計算して保存する（パラフレーズの拡充は本フェーズの対象外。13章 Open Issue参照）。
- 編集時の保存処理:
  - `title` / `answer_text` / `category` / タグ紐付け（`qa_tag`）の変更は、対応するカラム・関連テーブルを更新するのみでよい。
  - `question_text` を変更した場合、新規作成時に自動生成した `question_altered` 行のテキストとembeddingを再計算する。それ以外の（既存データ投入時にLLMで生成された）`question_altered` 行は本フェーズでは編集対象としない（4.2節）。
- バリデーション: 必須項目の入力チェック、タグの重複選択防止。

### 6.4 web_backend: 新規APIエンドポイント（BFF）

`web_backend` に以下のREST APIを新設し、内部でKnowledge MCP のMCPツールを呼び出す（ADR-0013）。パスは既存のチャット系エンドポイント（`/ask` 等）と名前空間を分離するため `/api/` 配下に置く。

| メソッド・パス | 概要 | 対応するKnowledge MCPツール |
|---|---|---|
| `GET /api/qa` | QA一覧取得（キーワード・カテゴリ・タグでの絞り込み、ページング対応） | `list_qa`（新規） |
| `GET /api/qa/{qa_id}` | QA詳細取得（タグ・`question_altered`件数を含む） | `get_qa`（新規） |
| `POST /api/qa` | QA新規登録 | `create_qa`（新規） |
| `PUT /api/qa/{qa_id}` | QA編集 | `update_qa`（新規） |
| `GET /api/tags` | タグ一覧（階層構造）取得 | `list_tags`（既存、6.6節で出力拡張） |
| `POST /api/tags` | タグ新規作成 | `create_tag`（既存、6.6節で入力拡張） |
| `PUT /api/tags/{tag_id}` | タグ名称・説明文・親タグの変更 | `rename_tag` / `move_tag`（既存、6.6節で拡張） |
| `DELETE /api/tags/{tag_id}` | タグ削除 | `delete_tag`（既存） |
| `GET /api/categories` | カテゴリ一覧取得（フォームの選択肢用、参照専用） | `list_categories`（新規、単純な参照ツール） |

- `web_backend` はこれらのエンドポイントの実装において `chatbot_db` へ直接アクセスしない。すべてMCPクライアントとしてKnowledge MCP サーバのMCPエンドポイント（`/mcp`）を呼び出し、そのレスポンスをJSONへ整形して返す（ADR-0013）。
- エラー時、Knowledge MCP 側の業務エラー（`TagError` 等）はHTTP 4xx（例: 409 Conflict）へマッピングし、`front_dev` 側でユーザーに分かる形（例: 「このタグには子タグが存在するため削除できません」）で表示できるようにする。

### 6.5 Knowledge MCP: QA管理ツールの追加（ADR-0014）

既存の `search_knowledge` に加え、以下のMCPツールを新設する。

| ツール | 概要 | 主なパラメータ |
|---|---|---|
| `list_qa` | QA一覧を取得する（キーワード・カテゴリ・タグでの絞り込み、ページング） | `keyword`, `category`, `tag_ids`, `limit`, `offset` |
| `get_qa` | QA1件の詳細を取得する（タグ・`question_altered`件数を含む） | `qa_id`（必須） |
| `create_qa` | QAを新規登録する（`question_altered` 1件を自動生成しembeddingを計算） | `title`, `question_text`, `answer_text`（いずれも必須）, `category_id`（任意）, `tag_ids`（任意） |
| `update_qa` | QAを編集する（`question_text` 変更時は `question_altered` を再計算） | `qa_id`（必須）, `title` / `question_text` / `answer_text` / `category_id` / `tag_ids`（いずれも任意、指定分のみ更新） |
| `list_categories` | カテゴリ一覧を取得する（参照専用） | なし |

- `create_qa` / `update_qa` は、既存 `QARepository` が利用している `embed_fn`（LM Studio embedding API 呼び出し）を再利用し、`question_text` の登録・変更時にベクトルを計算する。
- タグ紐付け（`qa_tag`）の追加・削除は、`create_qa` / `update_qa` の `tag_ids` パラメータで一括指定する方式とする（差分更新ではなく、指定された集合で置き換える）。
- 入力検証: `category_id` / `tag_ids` に存在しないIDが指定された場合はエラーとする（既存 `TagRepository` の存在チェックパターンを踏襲）。

**出力例（`get_qa`）**

```json
{
  "id": "1ca063f6-1e0d-4448-be1c-52caaec81dc6",
  "title": "内訳備考欄の内直接人件費の集計項目は確認できますか。",
  "question_text": "内訳備考欄の内直接人件費の集計項目は確認できますか。",
  "answer_text": "...",
  "category": { "id": 3, "name": "積算システムの操作方法に関するご質問" },
  "tags": [ { "id": 12, "name": "積算システムの操作方法" }, { "id": 3, "name": "積算システム" } ],
  "question_altered_count": 4
}
```

### 6.6 Knowledge MCP: タグ管理ツールの description / alias 対応拡張

ADR-0008で識別された「Knowledge MCP側のタグ管理ツールを `description` / `alias` 編集にも対応させる拡張」を、本フェーズのタグ管理UI（6.2節）から必要になる範囲で実施する。

- `create_tag` / `rename_tag` に、任意パラメータ `description` を追加する。
- 新規ツール `set_tag_description`（説明文の設定・更新）、`add_tag_alias` / `remove_tag_alias`（同義語の追加・削除）を追加する。
- `list_tags` の出力（`TAG_NODE_SCHEMA`）に `description` と `aliases`（配列）を追加する。
- 本拡張は、Tag Selector MCP が読み取り専用で参照する `tag` / `tag_alias` テーブルへの書き込みでもあるため、Tag Selector MCP側の動作（`reload_taxonomy` 実行後に新しい `description` / `alias` が反映されること）に影響がないことを確認する（ADR-0008の前提を維持）。

## 7. データ要件

### 7.1 現行スキーマ（再掲、ADR-0005/0008 適用後）

```sql
qa_original(uuid TEXT PK, title TEXT, question_text TEXT, answer_text TEXT, category_id INTEGER)
question_altered(id SERIAL PK, qa_id TEXT, text TEXT, embedding VECTOR(768))
category(id INTEGER PK, name TEXT)
tag(id SERIAL PK, name TEXT UNIQUE, parent_tag_id INTEGER, description TEXT)
tag_alias(id SERIAL PK, tag_id INTEGER, alias TEXT UNIQUE)
qa_tag(qa_id TEXT, tag_id INTEGER, PRIMARY KEY(qa_id, tag_id))
```

本機能の追加にあたり、既存スキーマへの変更は不要と見込む（6.6節のdescription/alias拡張は既にADR-0008でスキーマ拡張済み）。詳細設計フェーズで、`list_qa` の絞り込み・ページング用インデックス（例: `qa_original.title` への部分一致検索用インデックス）の要否を確認する。

### 7.2 API入出力例（`list_qa`）

```json
// 入力
{ "keyword": "積算", "category": "積算システムの操作方法に関するご質問", "tag_ids": [12], "limit": 20, "offset": 0 }

// 出力
{
  "items": [
    {
      "id": "1ca063f6-1e0d-4448-be1c-52caaec81dc6",
      "title": "内訳備考欄の内直接人件費の集計項目は確認できますか。",
      "category": "積算システムの操作方法に関するご質問",
      "tags": ["積算システムの操作方法", "積算システム"],
      "question_altered_count": 4
    }
  ],
  "total": 1
}
```

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | 一覧系API（`GET /api/qa`, `GET /api/tags`）は目安として1秒以内のレスポンスを目標とする（暫定目標値） |
| 同時実行 | 社内の運用担当者数名程度による同時利用を想定する（既存チャット機能ほどの同時実行数は想定しない） |
| 可用性 | 既存Knowledge MCPと同様、社内利用ツールとして単一インスタンス構成で可とする |
| ログ | QA・タグの登録・編集操作（誰が・いつ・何を変更したか）を記録する要件は、認証・権限管理が未確定（13章）のため、操作内容と時刻のみを対象に暫定対応し、操作者の記録は認証方式確定後に追加検討する |
| 監視 | 既存Knowledge MCPのヘルスチェック機構をそのまま利用する（新規エンドポイント追加は不要） |
| セキュリティ | 書き込み系API（QA・タグの登録編集削除）は、既存要件定義書（202608041002）Open Issue #4・#10 と同様、アクセス制御方式が未確定である。本フェーズでは社内ネットワーク内限定の利用を前提とし、追加の認証は実装しない（13章 Open Issue） |
| 保守性・拡張性 | QA・タグに関する業務ロジック（バリデーション、embedding計算、循環参照防止等）はKnowledge MCP側に一元化し、`web_backend` 側にロジックを重複実装しない（ADR-0013） |

## 9. インフラ・実行環境要件

### 9.1 web_backend ↔ Knowledge MCP 間の接続

- `docker-compose.yml` の `web_backend` サービスに、Knowledge MCP サーバのMCPエンドポイントURL（例: `KNOWLEDGE_MCP_URL=http://knowledge_mcp:8100/mcp`）を環境変数として追加する。
- `web_backend` の `depends_on` に `knowledge_mcp`（`condition: service_healthy`）を追加する。

### 9.2 front_dev（Vite dev server）の設定

- `vite.config.ts` の `proxy` 設定に、新規APIパス `/api` を `web_backend`（`http://app:8000`）へ転送するエントリを追加する。
- 新規追加する管理画面のページパス（例: `/admin/qa`, `/admin/tags`）は `/api` と名前空間が重複しないため、既存 `/evaluated_messages` のような `bypass` によるHTML/非HTML判定は不要とする（ADR-0015）。

### 9.3 環境変数（想定、詳細設計時に確定）

| 変数名 | 説明 |
|---|---|
| KNOWLEDGE_MCP_URL | `web_backend` がMCPクライアントとして接続するKnowledge MCP サーバのエンドポイントURL |

## 10. 既存システムとの関係・影響範囲

- 既存チャット機能（`/ask`, `/ask-sl` 等、`src/db.py` を用いた直接DBアクセス）は変更しない。
- `front_dev` の `main.tsx` に、新設する管理画面（`/admin` 配下）へのパス分岐を追加する（既存の3画面分岐はそのまま維持）。
- Knowledge MCP サーバへのQA管理ツール追加・タグ管理ツール拡張は、既存の `search_knowledge` / `list_tags` 等既存ツールの入出力仕様に変更を加えない（後方互換を維持する）。
- `docker-compose.yml` / `.env.example` の変更が発生するため、README の該当節にも追記が必要になる（実装フェーズで対応）。

## 13. Open Issues（要追加確認事項）

1. **QA・タグの削除機能の要否とcascade方針**: QAデータの削除（`question_altered` / `qa_tag` を含む）は本フェーズの対象外としたが、運用上必要になった場合の削除範囲・確認フローを別途検討する必要がある。
2. **書き込み系API（QA・タグの登録編集削除）のアクセス制御方式**: 既存要件定義書（202608041002）Open Issue #4・#10 と共通の課題。社内ネットワーク限定で十分か、ユーザー単位の認証・権限管理が必要か。
3. **`question_altered`（パラフレーズ）の個別編集・追加生成のUI要否**: 本フェーズはQA登録時の自動1件生成のみに留めたが、既存データ投入時のようなLLMによる複数パラフレーズ生成を管理UIから行いたいという要望が出た場合、別途要件定義が必要。
4. **web_backendのMCPクライアント実装方式**: リクエスト毎にMCPセッションを新規に張るか、コネクションを維持するか等の実装方式は詳細設計フェーズで検討する。
5. **カテゴリ（`category`）自体の登録・編集要否**: 本フェーズは既存カテゴリの参照・選択のみとしたが、カテゴリ自体の追加・変更が必要になった場合、`category_id` を参照する既存データ（`qa_original`）への影響を含めた別途検討が必要。
6. **タグ削除時の `tag_alias` の扱い**: `delete_tag` 実行時、当該タグに紐づく `tag_alias` レコードをどう扱うか（cascade削除か、事前に個別削除を要求するか）を6.6節の拡張実装時に確定する必要がある。
7. **`front_dev` の位置付けの見直し**: `front_dev` は現状「デバッグUI」として位置付けられているが、本機能追加により業務担当者が日常的に利用する管理ツールとしての性格が強まる。将来的にディレクトリ名・位置付け自体の見直し（例: 管理UI専用のフロントエンドへの分離）を検討する余地がある。
