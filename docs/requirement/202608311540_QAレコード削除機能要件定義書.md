# QAレコード削除機能 要件定義書

- 文書番号: REQ-202608311540
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `knowledge_mcp`（新規MCPツール）, `web_backend`（新規API）, `front_dev`（QA一覧ページ・QA編集ページの変更）
- 変更なしのコンポーネント: `qa_original`/`question_altered`/`qa_tag`/`tag`テーブルのスキーマ、既存の`create_qa`/`update_qa`/`import_qa_batch`/`list_qa`/`get_qa`/`list_categories`、既存の`delete_tag`/`delete_question_altered`/`delete_verification_question`、`tag_selector_mcp`、`agent_invitro`、既存の全データエクスポート機能
- 参照資料: `docs/requirement/202608060826_QAタグ管理UI要件定義書.md`、`docs/requirement/202608271750_言い換え質問文（question_altered）管理機能要件定義書.md`（12章 Open Issue #7）、`docs/adr/0014-knowledge-mcp-qa-management-tools.md`、`docs/adr/0064-question-altered-management-via-knowledge-mcp.md`
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照

## 1. 目的

QA一覧ページ（`QaListPage`）およびQA編集ページ（`QaFormPage`）から、QAレコード（`qa_original`）を削除できるようにする。

現状、`qa_original`を削除する手段はシステム全体に存在しない。ADR-0014が追加した`create_qa`/`update_qa`/`list_qa`/`get_qa`/`list_categories`は登録・編集・参照のみを提供し、削除機能を含まない。言い換え質問文（`question_altered`）管理機能の要件定義書（202608271750）は、Open Issue #7として「`delete_question_altered`は主質問文行（`is_primary=true`）を削除できない仕様であるため、既存システム全体で主質問文行の削除手段がない状態が続く。QA自体の削除機能（`delete_qa`）が別途必要かどうかも含め、要望が出た場合に別途要件化する」と明記しており、本書はこの要望に対応するものである。

## 2. 背景・参照資料

- `qa_original`（`uuid` PK, `question_text`, `answer_text`, `title`, `category_id`）は、QA管理UI（要件定義書202608060826、ADR-0013/0014）が対象とする中心的なテーブルである。
- `qa_tag`（`qa_id`, `tag_id`, 複合PK）は`qa_id`に`qa_original.uuid`への**外部キー制約**を持つ（`ON DELETE`句の指定なし＝デフォルトの`NO ACTION`）。そのため、`qa_tag`から参照されている`qa_original`行を先に削除しようとすると外部キー違反になる。
- `question_altered`（`id` PK, `qa_id`, `text`, `embedding`, `is_primary`）は`qa_id`列を持つが、`qa_original.uuid`への**外部キー制約は存在しない**（言い換え質問文管理機能の要件定義書202608271750で確認済み）。そのため、`qa_original`を削除しても`question_altered`側は自動的には削除されず、`qa_id`が存在しない行として残存（孤立）する。
- 既存の削除機能には2通りの設計方針が先例として存在する。
  - `delete_tag`（ADR-0006系）: `qa_tag`から参照されている、または子タグを持つ場合は**削除を拒否**する方式。
  - `delete_question_altered`（ADR-0064）: 対象が`is_primary=false`であることを検証したうえで削除する。参照する外部キーが存在しないため追加の整合性チェックは不要、という設計。
- 検証実行履歴（`verification_run_source`、conversationデータベース）や会話ログ（chatメッセージ）は、QAをデータベースをまたいで参照しているが、クロスデータベースの外部キー制約は設けられていない（ADR-0048で明示済みの既存方針）。そのため、QAを削除しても、これらの履歴・ログ側からの参照を自動的に整理する手段はない。
- 既存の削除系機能（`delete_tag`/`delete_question_altered`/`delete_verification_question`）はいずれも、ブラウザ標準の確認ダイアログ（`window.confirm`）を伴う即時の物理削除であり、論理削除（`is_deleted`等のフラグ）の仕組みはスキーマ上どこにも存在しない。
- 本書は、発注者との確認を経て、次の方針を確認済みである。
  1. **カスケード削除**: `delete_qa`実行時、対象QAに紐づく`qa_tag`行および`question_altered`行（`is_primary=true`の主質問文行を含む、パラフレーズ行も含む全件）を、Knowledge MCP側で自動的に削除する。`delete_tag`の「参照があれば拒否」方式は採用しない（QAの大半にタグが付与される想定のため、拒否方式では実用上ほぼ削除できなくなる）。
  2. **クロスデータベース整合性の告知**: 検証実行履歴・会話ログは削除に伴うカスケードの対象としない（クロスデータベースの外部キーが存在せず、技術的にカスケードできないため）。この制約を、削除確認ダイアログの文言で利用者に明示する。
  3. **削除粒度**: 一覧ページ・編集ページのいずれも、1件単位の単一削除のみを提供する。一覧ページでの複数選択一括削除、CSVインポート経由の一括削除は、いずれも本書のMVPでは対象外とする。
  4. **削除方式**: 既存の全削除機能と同様、確認ダイアログを伴う即時の物理削除（ハードデリート）とする。論理削除フラグ（`is_deleted`等）の新規導入は行わない。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| QA / QAレコード | `qa_original`テーブルの1行。質問・回答本文（`question_text`/`answer_text`）とタイトル・カテゴリを保持する |
| カスケード削除 | 対象QAの`qa_tag`行・`question_altered`行（主質問文行・言い換え行の両方）を、QA本体の削除にあわせて自動的に削除すること |
| 主質問文行 | `question_altered.is_primary = true`の行。`qa_original.question_text`と対応し、通常は`create_qa`/`update_qa`のみが生成・更新する |
| 言い換え行 | `question_altered.is_primary = false`の行。言い換え質問文管理機能（ADR-0064）が対象とする |
| ハードデリート | 論理削除フラグを用いず、DBの行そのものを`DELETE`文で削除する方式。本システムの既存の全削除機能と同一方式 |
| クロスデータベース参照 | `chatbot`データベースの`qa_original`を、別データベース（conversationデータベースの検証実行履歴・会話ログ）から外部キー制約なしに参照している状態（ADR-0048） |

## 4. スコープ

### 4.1 対象範囲（MVP）

- `knowledge_mcp`に、QAを削除する新規MCPツール`delete_qa`を追加する。対象QAに紐づく`qa_tag`行・`question_altered`行（`is_primary`を問わず全件）を同一処理内でカスケード削除したうえで、`qa_original`行を削除する。
- `web_backend`に、`delete_qa`をREST API化する新規エンドポイント`DELETE /api/qa/{qa_id}`を追加する。
- `front_dev`のQA一覧ページ（`QaListPage`）の各行に、削除操作（確認ダイアログを伴う）を追加する。
- `front_dev`のQA編集ページ（`QaFormPage`、編集モードのみ）に、削除ボタン（確認ダイアログを伴う）を追加する。新規作成モードには表示しない。
- 削除確認ダイアログには、（a）タグ設定・言い換え質問文（主質問文行を含む）も同時に削除されること、（b）検証実行履歴・会話ログに残る参照は削除されずそのまま残存し得ること、（c）操作が取り消せないこと、の3点を明示する。

### 4.2 対象外（将来検討・別スコープ）

- **一覧ページでの複数選択一括削除**（チェックボックスによる複数QAのまとめ削除）: 誤操作時に大量のQAが一括で消えるリスクを避けるため、MVPでは対象外とする（ADR-0064のCSV一括削除見送りと同様の判断）。必要になった場合は別途要件化する（12章 Open Issue参照）。
- **CSVインポート経由の削除**（削除フラグ列の追加等）: 対象外。既存のQA一括インポート（`import_qa_batch`、ADR-0053）の対象外とする。
- **論理削除（ソフトデリート）・ゴミ箱・復元機能**: 本システムの既存の削除機能はすべてハードデリートであり、一貫性を保つため本機能でも論理削除フラグは導入しない。
- **検証実行履歴・会話ログ側での「参照先QA削除済み」表示改修**: これらの画面が、削除済みQAへの参照をどう表示するか（例: QAタイトルの代わりに「削除済み」と表示する等）の改修は、本書のスコープに含めない。現状の挙動（参照先が存在しない場合の表示、詳細は各機能の実装依存）のまま変更しない。
- **主質問文行単体の削除（QA本体は残したまま）**: `delete_question_altered`が`is_primary=true`行を削除できない制約（ADR-0064）は本書でも変更しない。主質問文行を削除したい場合は、QA自体を削除する（本書の`delete_qa`を使う）以外の手段は提供しない。
- **認証・アクセス制御の強化**: 既存の管理画面群と同様、ネットワークレベルの制限（社内IPアドレス限定、ADR-0041）のみとし、追加のログイン認証・削除権限の限定は設けない。
- **既存の全データエクスポート・全データインポート機能の変更**: 変更を加えない。

## 5. 全体アーキテクチャ

### 5.1 システム構成（本フェーズ）

```
front_dev（変更: QaListPage に削除操作、QaFormPage に削除ボタン）
        │  DELETE /api/qa/{qa_id}
        ▼
web_backend（変更: qa_controller.py に delete_qa 追加、既存パターンを踏襲したBFF）
        │  MCPツール呼び出し（既存の書き込み経路、ADR-0013を維持）
        ▼
knowledge_mcp（新規ツール: delete_qa。既存 QaManagementRepository を拡張）
        │  トランザクション内で qa_tag → question_altered → qa_original の順に削除
        ▼
chatbot データベース（qa_original / qa_tag / question_altered の該当行を削除）
```

- `tag_selector_mcp`・`agent_invitro`・既存の全データエクスポート・全データインポート機能には変更を加えない。
- 検証実行履歴（conversationデータベースの`verification_run_source`）・会話ログ（chatメッセージ）は、本機能による削除処理の対象に含めない（クロスデータベースであり、外部キー制約もないため、5.1節の削除処理からは意図的に除外する）。

### 5.2 コンポーネント一覧と責務（追加・変更分）

| コンポーネント | 変更内容 |
|---|---|
| `knowledge_mcp`（新規ツール） | `delete_qa`ツールの追加。`QaManagementRepository`に、`qa_tag`・`question_altered`のカスケード削除を含む`delete_qa`メソッドを追加する |
| `web_backend`（変更） | `qa_controller.py`に`delete_qa`関数を追加し、`app.py`に`DELETE /api/qa/{qa_id}`ルートを追加する。既存の`qa_controller.py`のBFFパターン（MCPツール呼び出し＋`log_admin_operation`）をそのまま踏襲する |
| `front_dev`（変更） | `QaListPage.tsx`の各行に削除リンク/ボタンを追加。`QaFormPage.tsx`の編集モードに削除ボタンを追加。`api.ts`に`deleteQa(id)`関数を追加する |

## 6. 機能要件

### 6.1 front_dev: QA一覧ページ（`QaListPage`）の変更

- 各行の操作列（現状「編集」リンクのみ）に、「削除」の操作を追加する。
- クリック時、`window.confirm`による確認ダイアログを表示する（文言は6.6節）。確認された場合のみ`deleteQa(qa.id)`を呼び出す。
- 削除成功後は一覧を再読み込みする。現在のページに表示中の行数が0件になる場合（最終ページの最後の1件を削除した場合等）の挙動（前ページへ戻す等）は、詳細設計フェーズで確定する（12章 Open Issue #1）。
- 削除失敗時（例: 対象QAが既に存在しない）はエラーメッセージを画面に表示し、一覧は変更しない。

### 6.2 front_dev: QA編集ページ（`QaFormPage`）の変更

- 編集モード（`mode === "edit"`）の場合のみ、既存の`QuestionAlteredFormPage`と同様の配置（`admin-form-actions`内、保存ボタンと並べて`admin-btn-danger`スタイル）で「削除」ボタンを追加する。新規作成モードには表示しない。
- クリック時、`window.confirm`による確認ダイアログを表示する（文言は6.6節）。確認された場合のみ`deleteQa(id)`を呼び出す。
- 削除成功後はQA一覧ページ（`/admin/qa`）へ遷移する。
- 削除失敗時はエラーメッセージを画面に表示し、遷移しない。

### 6.3 web_backend: 新規APIエンドポイント（BFF）

| メソッド・パス | 説明 |
|---|---|
| `DELETE /api/qa/{qa_id}` | QAを削除する（`qa_tag`・`question_altered`のカスケード削除を含む）。成功時`204 No Content`。対象が存在しない場合は`delete_qa`ツールが送出する`QaError`が既存のグローバル例外ハンドラにより`409`へマッピングされる |

`qa_controller.py`に、既存の`delete_tag`/`delete_item`（`question_altered_controller.py`）と同一パターンの`delete_qa`関数を追加する。対応するKnowledge MCPツール（`delete_qa`）を呼び出したうえで、`log_admin_operation("delete", "qa", qa_id, {})`を実行し、`chatbot`データベースへの直接アクセスは行わない（ADR-0013の既存方針を維持）。

### 6.4 knowledge_mcp: 新規ツール`delete_qa`

| ツール名 | 説明 |
|---|---|
| `delete_qa` | `qa_id`（必須）を受け取り、対象QAの存在を検証したうえで、`qa_tag`行・`question_altered`行（`is_primary`を問わず全件）・`qa_original`行を1つのトランザクション内で削除する。対象が存在しない場合はエラーを返す |

- `QaManagementRepository`に`delete_qa(qa_id: str) -> None`を追加する。既存の`get_qa`と同様に、まず対象QAの存在を確認し、存在しない場合は`QaError`を送出する。
- 削除順序: `qa_tag`（`qa_original.uuid`への外部キー制約があるため、`qa_original`削除前に削除する必要がある）→ `question_altered`（外部キー制約はないが、孤立行を残さないため同一処理内で削除する）→ `qa_original`、の順に削除する。
- 3つの`DELETE`文は同一トランザクション（既存の`create_qa`/`update_qa`と同様の`with self.db.cursor() as cur:`ブロック）内で実行し、途中で失敗した場合は全体をロールバックする。

### 6.5 削除処理のカスケード範囲

| 対象テーブル | 削除の要否 | 補足 |
|---|---|---|
| `qa_original` | 削除する（本体） | 対象QAの行そのもの |
| `qa_tag` | 削除する（カスケード） | 外部キー制約があるため、`qa_original`削除前に削除が必須 |
| `question_altered` | 削除する（カスケード） | 外部キー制約はないが、孤立行を残さないため削除対象とする。主質問文行（`is_primary=true`）・言い換え行（`is_primary=false`）の区別なく全件削除する |
| `verification_run_source`（conversationデータベース） | 削除しない（対象外） | クロスデータベースであり外部キー制約がないため、技術的にカスケードできない。参照は残存する |
| 会話ログ（chatメッセージ、conversationデータベース） | 削除しない（対象外） | 同上 |
| `category`, `tag` | 削除しない | QAが参照しているだけであり、これらのマスタ自体は削除対象に含めない |

### 6.6 削除確認ダイアログの文言方針

一覧ページ・編集ページのいずれも、`window.confirm`で以下の3点を含む文言を表示する（既存の`delete_question_altered`確認文言のパターンを踏襲し拡張する）。

1. このQAと、紐づくタグ設定・言い換え質問文（主質問文行を含む）が削除されること。
2. 検証実行履歴や会話ログにこのQAへの参照が残っている場合、削除後もそれらの記録は削除されず、参照先が失われた状態のまま残ること。
3. この操作は取り消せないこと。

文言の確定表現は詳細設計フェーズで決定する（12章 Open Issue #2）。

## 7. データ要件

### 7.1 対象テーブル（再掲、スキーマ変更なし）

| テーブル | 列 | 本機能での扱い |
|---|---|---|
| `qa_original` | `uuid`, `title`, `question_text`, `answer_text`, `category_id` | 削除対象本体。スキーマ変更なし |
| `qa_tag` | `qa_id`, `tag_id` | 対象QAに紐づく行をカスケード削除。スキーマ変更なし |
| `question_altered` | `id`, `qa_id`, `text`, `embedding`, `is_primary` | 対象QAに紐づく行（`is_primary`問わず全件）をカスケード削除。スキーマ変更なし |

### 7.2 API入出力例

`DELETE /api/qa/{qa_id}` はリクエストボディを持たず、成功時は`204 No Content`（レスポンスボディなし）を返す。対象QAが存在しない場合は、以下の形式で`409`を返す（既存のグローバル例外ハンドラによる`QaError`のマッピングをそのまま利用する）。

```json
{
  "detail": "qa id=<qa_id> does not exist"
}
```

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 不可逆性 | 論理削除フラグを持たないハードデリートであり、削除後の復元手段は提供しない。確認ダイアログでの事前告知（6.6節）が唯一の抑止策である |
| トランザクション整合性 | `qa_tag`・`question_altered`・`qa_original`の削除は1つのトランザクション内で実行し、部分的な削除（一部テーブルのみ削除された不整合な状態）を残さない |
| クロスデータベース整合性 | 検証実行履歴・会話ログへの影響を自動的に解消する手段は提供しない（技術的にカスケードできないため）。確認ダイアログでの告知にとどめる（既存のADR-0048の方針の範囲内） |
| ログ | 既存の管理系操作ログ（`log_admin_operation`）と同様の方式で、削除の実行を記録する。既存の制限（認証方式未確定のため操作者は記録しない）を踏襲する |
| アクセス制御 | 既存の管理画面群と同様、ネットワークレベルの制限（社内IPアドレス限定、ADR-0041）のみとし、追加の削除権限の限定は設けない |
| パフォーマンス | 削除対象の`question_altered`件数は通常のQA1件あたり数件程度であり、既存の`update_qa`（`question_text`変更時のembedding再計算）と比較して性能上の懸念は小さい |

## 9. インフラ・実行環境要件

追加のインフラ変更は想定しない。既存の`knowledge_mcp`・`web_backend`・`front_dev`のコンテナ構成（ローカルdocker-compose・AWS ECS Fargate）をそのまま利用する。新規の環境変数追加も想定しない。

## 10. 既存システムとの関係・影響範囲

- `qa_original`/`qa_tag`/`question_altered`のスキーマは変更しない。
- 既存の`create_qa`/`update_qa`/`import_qa_batch`/`list_qa`/`get_qa`/`list_categories`（ADR-0014/0053）の実装・シグネチャには変更を加えない。
- 既存の`delete_tag`/`delete_question_altered`/`delete_verification_question`には変更を加えない。独立した削除機能として併存させる。
- `search_knowledge`（ベクトル類似検索）は、削除されたQAに対応する`question_altered`行が存在しなくなることで、自動的に検索対象から除外される。新たな連携実装は不要である。
- 検証実行履歴（`verification_run_source`）・会話ログは、既存のクロスデータベース非外部キー方針（ADR-0048）の範囲内で、削除後も参照が残存し得る。これは本機能が新たに生む問題ではなく、既存の設計方針の延長である。
- `tag_selector_mcp`・`agent_invitro`・既存の全データエクスポート・全データインポート機能には影響しない。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] QA一覧ページの各行から、確認ダイアログを伴ってQAを削除できる。削除後、一覧・検索結果（`search_knowledge`）に表示されなくなる。
- [ ] QA編集ページ（編集モードのみ）から、確認ダイアログを伴ってQAを削除できる。削除成功後、QA一覧ページへ遷移する。
- [ ] 削除確認ダイアログに、タグ・言い換え質問文も削除されること、検証実行履歴・会話ログの参照は残存し得ること、操作が取り消せないことが明示されている。
- [ ] QAを削除すると、そのQAに紐づく`qa_tag`行・`question_altered`行（主質問文行・言い換え行の両方）もあわせて削除される。
- [ ] 存在しないQAに対して削除を実行した場合、エラーが返り、画面にエラーメッセージが表示される。
- [ ] 既存のQA登録・編集・一覧表示・CSV一括インポート、タグ削除、言い換え質問文削除、検証質問削除、全データエクスポート・インポートの動作に影響がないことを確認する。

## 12. Open Issues（要追加確認事項）

1. **一覧ページでのページング調整**: 一覧の最終ページで最後の1件を削除した場合等、削除後にページ位置をどう調整するか（前ページへ戻す、先頭ページへ戻す等）の詳細は、実装フェーズで確定する。
2. **確認ダイアログの文言の最終確定**: 6.6節に示した3点の骨子は確認済みだが、具体的な表現・改行位置等は詳細設計フェーズで確定する。
3. **一括削除の必要性**: 4.2節の通り本書のMVPでは対象外とするが、運用開始後に複数QAをまとめて削除したいという要望が出た場合、誤操作防止策（確認方法の強化等）を含めて別途要件定義・ADRが必要になる。
4. **検証実行履歴・会話ログ側の表示改修の要否**: QA削除後、これらの画面が参照先QAをどう表示するか（現状のまま、または「削除済み」等の表示に改修するか）は、運用開始後の状況を踏まえて別途検討する。
5. **削除操作の監査強化**: 現状、認証方式が未確定のため操作者を記録しない制限がある（既存の`log_admin_operation`と同様）。認証機能導入時にあわせて、削除操作の操作者記録も見直す。
