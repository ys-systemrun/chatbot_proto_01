# 評価済みメッセージページ 列幅ドラッグ変更機能 要件定義書

- 文書番号: REQ-202609141030
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `front_dev`（`EvaluatedMessagesPage.tsx`, `style.css`）
- 変更なしのコンポーネント: `web_backend`, `knowledge_mcp`, `agent_invitro`、DBスキーマ（`conversation`データベース含む）、他の管理画面一覧ページ（`QaListPage.tsx` 等 `admin-table` 系）
- 参照資料: `front_dev/src/feature/evaluated_messages/EvaluatedMessagesPage.tsx`、`front_dev/src/style.css`、`docs/screen_transition/screenshots/02_evaluated_messages.png`
- 前提の決定事項: 本書末尾「12. 関連ADR一覧」参照

## 1. 目的

評価済みメッセージページ（`EvaluatedMessagesPage`）のメッセージ一覧テーブルについて、各列の見出し境界をマウスでドラッグすることで列幅を利用者自身が調整できるようにする。これにより、

1. 「本文」「LLM 入力」列など内容が長い列を必要に応じて広げ、逆に「#」「評価」等の短い列を狭めることで、閲覧時に手動でスクロール・展開操作を行う頻度を減らせるようにする。
2. 調整した列幅をブラウザに保存し、ページの再読み込みや後日の再訪問時にも同じ見やすい列幅を再現できるようにする。

## 2. 背景・現状の課題

### 2.1 現状の実装

`EvaluatedMessagesPage.tsx`は、会話（`EvaluatedConversation`）ごとに`<details>`で開閉可能な「会話カード」を縦に並べて表示し、各カードが独立した`<table className="ev-table">`を持つ。1画面内に会話の件数分（複数〜多数）のテーブルが並ぶ構造である。

列構成は「#」「役割」「評価」「モデル」「本文」「LLM 入力」「登録日時」の7列。列幅は`style.css`のクラス指定（`ev-td-num`: 40px固定、`ev-td-model`: 140px固定、`ev-td-content`: `max-width: 300px`、`ev-td-date`: 130px固定）と、指定のない列（役割・評価・LLM入力）はブラウザの既定（コンテンツ量に応じた自動幅）に委ねられている。`<colgroup>`は存在せず、`table-layout`も既定（auto）である。列幅を利用者が変更する手段は一切ない。

「本文」「LLM 入力」列は、内容が長い場合`ExpandableCell`により「展開」ボタンで全文表示に切り替えられるが、展開しても列幅自体は固定`max-width`の範囲内で折り返されるのみであり、列を横方向に広げて閲覧することはできない。

### 2.2 課題

- 「本文」「LLM 入力」の内容が長文になるケースが多く、固定幅では折り返しが多くなり縦方向に長くなる／確認しづらい。一方で「#」「評価」等はそこまでの幅を必要としない。利用者ごとに見やすい配分は異なるが、現状は固定幅のため調整できない。
- 画面内に会話ごとの個別テーブルが複数存在するため、仮に単純にテーブル単位で列幅を可変にした場合、テーブルごとに列幅がずれてしまい、同じ列見出しであるにもかかわらず視覚的に列が揃わなくなる懸念がある（3章参照）。

### 2.3 既存基盤

- `front_dev`は`react`（18.3系）・`react-router-dom`（6.26系、`/admin`サブツリー限定、ADR-0015）のみに依存を絞った構成であり、`EvaluatedMessagesPage`を含め表形式UIはすべて素の`<table>`要素と`style.css`のクラス指定で実装されている（DataGrid等のUIライブラリは未導入）。
- 本ページのデータ取得元（`GET`系API、`agent_invitro`との連携、`conversation`データベースの配置）はADR-0044・ADR-0045で確定済みであり、本書はこれらに一切変更を加えない、フロントエンドの表示・操作のみに閉じた機能追加である。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| 列幅 | テーブルの各列（#・役割・評価・モデル・本文・LLM入力・登録日時の7列）に割り当てるピクセル単位の幅 |
| ドラッグハンドル | 列見出し（`th`）の右端に配置する、マウスドラッグによる列幅変更の起点となる操作領域 |
| 列幅の同期 | 画面内の複数の会話テーブル（`ConversationCard`ごとの`<table>`）が、同一の列幅配列を共有し、いずれか1箇所での変更が全テーブルに即時反映されること |
| 永続化 | 確定した列幅をブラウザの`localStorage`に保存し、再読み込み・再訪問時に復元すること |
| 既定幅 | 列幅の初期値・フォールバック値。現状のCSS固定値に相当する値を各列ごとに定める（6.4節） |

## 4. スコープ

### 4.1 対象範囲（MVP）

- **評価済みメッセージページ（`EvaluatedMessagesPage`）の`ev-table`のみ**を対象とする（発注者確認済み、13章参照）。
- 7列すべて（#・役割・評価・モデル・本文・LLM入力・登録日時）をドラッグによる幅変更の対象とする。列ごとに最小幅を設ける（6.4節）。最大幅は設けず、合計幅が画面幅を超えた場合は既存の横スクロール（`.ev-table-wrap { overflow-x: auto }`）で対応する。
- 画面内の全会話テーブルは同一の列幅を共有し、いずれか1つのテーブルでの列幅変更が画面内の他の全テーブルへ即時反映される（発注者確認済み、13章参照）。
- 確定した列幅は`localStorage`に保存し、ページの再読み込み・別タブでの再オープン・後日の再訪問時にも直前の列幅を復元する（発注者確認済み、13章参照）。ブラウザ・オリジン単位の保存であり、利用者間・端末間では共有されない。
- ドラッグハンドルのダブルクリックによる単一列のリセット、および画面上の「列幅をリセット」ボタンによる全列一括リセットを提供する（6.5節）。

### 4.2 対象外（将来検討・別スコープ）

- **他の管理一覧ページ（`QaListPage`・`QuestionAlteredListPage`・`TagTreePage`・`VerificationListPage`等、`admin-table`系）への同様機能の展開**: 本書は評価済みメッセージページのみを対象とする。他画面への展開は、要望が出た場合に別途要件化する（11章 Open Issue参照）。
- **列の表示・非表示の切り替え、列の並べ替え（順序変更）**: 本書は列幅の変更のみを対象とし、列構成自体の変更は対象外とする。
- **行（会話・メッセージ）の並べ替え・ソート機能**: 対象外。既存の表示順序をそのまま維持する。
- **列幅設定のサーバー側（DB）永続化、利用者アカウント単位・端末横断での共有**: `localStorage`によるブラウザ単位の保存で要件を満たすと判断し対象外とする（発注者確認済み、13章参照）。
- **タッチ操作（スマートフォン・タブレット）でのドラッグリサイズ対応**: 本ページは社内管理者向けの管理画面であり、PCブラウザでのマウス操作を前提とする既存方針（他の管理画面同様）を踏襲し、タッチ操作固有の対応（タッチイベント・タップ操作でのハンドル操作等）は本書のMVPでは対象外とする。
- **キーボード操作による列幅変更（アクセシビリティ対応）**: 本書のMVPでは対象外（11章 Open Issue参照）。

## 5. 全体アーキテクチャ

### 5.1 方式概要

```
EvaluatedMessagesPage（親コンポーネント、列幅stateを一元管理）
  ├─ マウント時:
  │     localStorage["ev_column_widths_v1"] を読み取り、
  │     形式が正しければ初期列幅state（7要素の数値配列）として採用。
  │     未保存・不正な場合は既定幅（6.4節）にフォールバック。
  │
  ├─ 列幅state（7要素の配列）を各 ConversationCard に props として渡す
  │     （ConversationCard 自身は列幅stateを持たない）
  │
  ├─ onResize(colIndex, newWidth):
  │     列幅stateを更新（全 ConversationCard に即時反映＝同期、4.1節）
  │
  ├─ onResizeEnd() / onDoubleClickReset(colIndex) / 「列幅をリセット」ボタン:
  │     確定した列幅を localStorage["ev_column_widths_v1"] へ保存
  │     （リセット操作の場合は既定幅で上書き保存、または該当キーをクリア）
  │
  └─ ConversationCard（会話ごとの<table>、複数存在）
        ├─ <colgroup> に props で受け取った列幅を反映（<col style={{width}}>）
        ├─ 各 <th> の右端にドラッグハンドルを配置
        │     mousedown → ドラッグ開始（開始X座標・開始幅を記録）
        │     window の mousemove → 差分に応じ onResize(colIndex, clamped幅) 呼び出し
        │     window の mouseup → ドラッグ終了、onResizeEnd() 呼び出し
        │     ダブルクリック → onDoubleClickReset(colIndex) 呼び出し
        └─ 既存の ExpandableCell 等、列幅以外の表示ロジックは変更しない
```

### 5.2 コンポーネント一覧と責務（変更分）

| コンポーネント | 変更内容 |
|---|---|
| `front_dev`（`EvaluatedMessagesPage.tsx`） | 列幅state（7要素配列）の一元管理、`localStorage`からの初期化・保存処理、「列幅をリセット」ボタンの追加、`ConversationCard`への列幅・更新関数のprops引き渡し |
| `front_dev`（`EvaluatedMessagesPage.tsx`内`ConversationCard`） | `<colgroup>`の追加、各`<th>`へのドラッグハンドル追加、ドラッグ中のマウスイベント処理 |
| `front_dev`（`style.css`） | `.ev-table`への`table-layout: fixed`追加、ドラッグハンドル用のスタイル（カーソル`col-resize`、ドラッグ中のハイライト等）追加、幅指定を`<col>`側に一本化するための既存幅指定クラス（`ev-td-num`等）の整理 |
| `front_dev`（`api.ts`、`domain/evaluated/index.ts`） | 変更なし |

## 6. 機能要件

### 6.1 ドラッグ操作

- 各列見出し（`<th>`）の右端に、幅約8pxの操作領域（ドラッグハンドル）を設ける。ハンドル上ではマウスカーソルを`col-resize`に変更する。
- ドラッグハンドル上での`mousedown`によりドラッグを開始する。ドラッグ中は`window`に登録した`mousemove`イベントで、開始位置からの水平方向の移動量を対象列の開始幅に加算し、列幅stateをリアルタイムに更新する（変更は画面内の全会話テーブルに即時反映される、6.2節）。
- ドラッグ中は、対象列の境界線をハイライト表示する等、操作対象が視覚的にわかるフィードバックを設ける。
- ドラッグ中はテキストの誤選択を防止する（`user-select: none`相当の適用）。
- `mouseup`でドラッグを終了し、`mousemove`/`mouseup`のイベントリスナーを解除する。この時点で確定した列幅を`localStorage`へ保存する（6.3節）。

### 6.2 列幅の同期

- 画面内の全ての会話テーブル（`ConversationCard`ごとの`<table>`）は、共通の列幅配列（7要素）を共有する。
- いずれか1つのテーブルでドラッグにより列幅を変更した場合、画面内の他の全ての会話テーブルの対応する列にも、同じ操作中に即時（ドラッグ中のリアルタイム更新として）反映される。
- `<details>`が閉じている（折りたたまれている）会話カードについても、内部で保持している列幅stateの値自体は他カードと同期される。次に開いたときには、他カードで確定済みの列幅がそのまま反映された状態で表示される。

### 6.3 永続化

- 確定した列幅（ドラッグ終了時、およびリセット操作時）は、`localStorage`に`ev_column_widths_v1`のキーでJSON配列（7要素、各要素はpx単位の数値）として保存する。
- ドラッグ中（`mousemove`の都度）は`localStorage`への書き込みを行わない（`mouseup`時にのみ1回書き込む）。
- ページマウント時、`localStorage["ev_column_widths_v1"]`を読み取り、以下の条件をすべて満たす場合のみ初期列幅stateとして採用する: (a) JSON配列としてパース可能、(b) 要素数が7、(c) 全要素が有限の数値であり、かつ対応する列の最小幅（6.4節）以上であること。条件を満たさない場合（未保存、パース失敗、要素数不一致、範囲外の値等）は、既定幅（6.4節）にフォールバックする。
- 本機能は当該ブラウザ・同一オリジンに閉じた保存であり、利用者間・端末間・ブラウザ間で共有されない（4.2節）。

### 6.4 列幅の初期値（既定幅）・最小幅

| # | 列 | 既定幅（px） | 最小幅（px） |
|---|---|---|---|
| 1 | # | 40 | 32 |
| 2 | 役割 | 72 | 48 |
| 3 | 評価 | 56 | 40 |
| 4 | モデル | 140 | 80 |
| 5 | 本文 | 320 | 120 |
| 6 | LLM 入力 | 260 | 120 |
| 7 | 登録日時 | 130 | 100 |

- 上記の既定幅は、現状の固定CSS値（#: 40px、モデル: 140px、登録日時: 130px）を踏襲しつつ、指定のなかった列（役割・評価・LLM入力）・`max-width`指定だった本文列について、現状の見え方に近い妥当な初期値を新たに定める。
- 最大幅の上限は設けない（4.1節）。

### 6.5 リセット機能

- 各列のドラッグハンドルをダブルクリックすると、その列のみを既定幅（6.4節）に戻す。
- 画面上（テーブル一覧の上部）に「列幅をリセット」ボタンを設け、押下すると全7列を既定幅に戻し、`localStorage["ev_column_widths_v1"]`も既定値で上書き保存する（またはキー自体を削除し、次回アクセス時に既定値へフォールバックさせる。実装時にいずれかへ統一する）。

## 7. 非機能要件

| 分類 | 要件 |
|---|---|
| ブラウザ・操作前提 | 社内管理者向けページであり、既存の他管理画面と同様PCブラウザでのマウス操作を前提とする。タッチ操作・キーボード操作でのリサイズは対象外（4.2節） |
| パフォーマンス | ドラッグ中の`localStorage`書き込みは行わず、`mouseup`時にのみ1回書き込む。列幅変更に伴う再レンダリングは、列幅stateを更新した`EvaluatedMessagesPage`配下のテーブル群に限定され、追加のAPIリクエストは発生しない |
| 副作用なし | 本機能はブラウザの表示状態のみに影響し、既存の評価済みメッセージ取得API（`getEvaluatedMessages`）のリクエスト・レスポンス仕様には一切変更を加えない |
| 後方互換性 | `localStorage`に保存値が存在しない利用者・ブラウザ（初回アクセス、保存クリア後等）は、既定幅（6.4節）で従来と同等の見た目から利用を開始できる |
| アクセス制御 | 変更なし。既存の管理画面群と同様、ネットワークレベルの制限（社内IPアドレス限定、ADR-0041）のみとする |

## 8. インフラ・実行環境要件

追加のインフラ変更は想定しない。既存の`front_dev`ビルド・配信構成（ADR-0042）、docker-compose・AWS ECS Fargate構成をそのまま利用する。新規の環境変数・依存パッケージの追加はない（既存の`react` / `react-router-dom`のみで実現し、DataGrid等の新規UIライブラリは導入しない、5章参照）。

## 9. 既存システムとの関係・影響範囲

- `web_backend` / `knowledge_mcp` / `agent_invitro` / DBスキーマ（`conversation`データベース含む）への変更は一切ない。既存の評価済みメッセージ取得APIのリクエスト・レスポンス仕様も変更しない。
- 変更対象は`front_dev`の`EvaluatedMessagesPage.tsx`・`style.css`のみ。
- 他の一覧ページ（`QaListPage.tsx`等）・`api.ts`・`domain/`配下の型定義には変更を加えない。
- `table-layout: fixed`への変更に伴い、既存の`ev-td-content`の`max-width: 300px`等、幅に関わる既存CSS指定は`<col>`側の幅指定に置き換わる（実装時、二重指定によるスタイル競合に注意する必要がある）。

## 10. 受け入れ基準（Definition of Done, MVP）

- [ ] いずれかの列見出しの右端をドラッグすると、マウスの移動量に応じてその列の幅がリアルタイムに変化する。
- [ ] 列幅を変更すると、画面内の他の全ての会話テーブルの対応する列幅も同時に変化する（同期を確認）。
- [ ] 各列を最小幅未満には縮小できないことを確認する。列を大きく広げた場合、テーブル全体が横スクロール可能になり内容が失われないことを確認する。
- [ ] 列幅を変更した状態でページをリロードすると、変更後の列幅が復元される。
- [ ] 列幅を変更した状態で別タブ・後日改めて本ページを開いても、同一ブラウザであれば変更後の列幅が復元される。
- [ ] `localStorage`をクリアした状態、または初回アクセス時は、既定幅（6.4節の表）で表示されることを確認する。
- [ ] 列見出しのドラッグハンドルをダブルクリックすると、その列のみ既定幅に戻ることを確認する。
- [ ] 「列幅をリセット」ボタン押下で、全列が既定幅に戻り、`localStorage`の保存値もリセットされることを確認する（リロード後も既定幅のままであることを確認）。
- [ ] 既存の「展開／折りたたむ」機能（`ExpandableCell`）・会話カードの開閉（`<details>`）・データ取得（読み込み中・エラー・0件表示）の各既存機能に影響がないことを確認する。
- [ ] 保存されている列幅データが不正な形式（例: 要素数が7でない、数値でない値を含む等）の場合でも、画面がエラーにならず既定幅にフォールバックして正しく表示されることを確認する。

## 11. Open Issues（要追加確認事項）

1. **他の一覧ページへの適用**: `QaListPage`等の`admin-table`系ページにも同様の列幅ドラッグ機能を展開するかは本書のMVP対象外。要望が出た場合に別途要件化する。
2. **リセット手段の最終UI**: 6.5節のダブルクリックリセット・「列幅をリセット」ボタンの両方を実装する方針としたが、実装時のユーザビリティ確認により、いずれか一方への簡略化を検討する余地がある。
3. **タッチ操作・キーボード操作への対応**: 4.2節の通り本書のMVPでは対象外とするが、将来的にタブレット等での利用要望が出た場合は別途要件化する。
4. **列構成自体が将来変更された場合の`localStorage`キーのバージョニング**: 列の追加・削除・順序変更が将来発生した場合、保存済みの列幅データ（要素数・意味）と不整合が生じうる。本書はキー名に`_v1`サフィックスを付与する方針とし（ADR-0087参照）、列構成変更時はキーのバージョンを上げることで対応する想定だが、具体的な移行手順は列構成変更が実際に発生した時点で別途定める。
