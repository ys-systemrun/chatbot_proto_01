# AWS環境向けQA・タグ管理UI（ブラウザアクセス）要件定義書

- 文書番号: REQ-202608211014
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `front_dev`（既存QA・タグ管理UIのAWS向けビルド・配信方式）, `web_backend`（既存BFFのAWS実行環境）, `terraform/`（新規ネットワーク・ECSリソース）
- 参照資料: `docs/requirement/202608060826.md`（QAデータ・タグ管理UI要件定義書）, `docs/requirement/202608100910.md`（MCPサーバー・クライアントAWSデプロイ要件定義書）
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照

## 1. 目的

AWS上にデプロイ済みの `chatbot-invitro-rds`（Amazon RDS for PostgreSQL, ADR-0026）に保存されているQAデータ・タグに対して、ブラウザから次の確認・編集操作ができるようにする。

1. QAデータの内容・タグ付与状況を一覧して確認できるページ
2. タグおよびタグの階層構造を確認できるページ
3. QAデータの登録・編集機能
4. タグの登録・編集機能

これらの機能自体は `docs/requirement/202608060826.md`（以下「既存UI要件定義書」）で要件定義済みであり、`front_dev`（`QaListPage` / `TagTreePage` / `QaFormPage` / `TagPicker`）と `web_backend`（`/api/qa/*`, `/api/tags/*`, `/api/categories`）、Knowledge MCPサーバの管理系ツール（`list_qa` / `get_qa` / `create_qa` / `update_qa` / `list_tags` 等）として実装済みである。しかし、これはローカルの `docker-compose` 環境（開発者のPC上）向けの構成であり、AWS上にはまだ配置されていない。

本書は、既存UI要件定義書で定義した機能をそのまま流用し、これをAWS上で稼働させ、社内の利用者がブラウザから到達できるようにするための要件（デプロイ構成・ネットワーク境界・アクセス制御）を整理したものである。コーディングは対象外とし、要件定義および設計判断（ADR）の整理にとどめる。

## 2. 背景・参照資料

- 既存UI要件定義書（202608060826）は、`front_dev` の `vite dev server`（`npm run dev`）と `web_backend` のFastAPIアプリを `docker-compose` 上で並行稼働させ、Viteの開発用プロキシ（`vite.config.ts`）で `/api` を `web_backend` へ転送する構成を前提としている。本番相当のビルド済み静的資産を配信する構成、およびAWS上での実行形態は対象外だった（同書9章）。
- AWS側は、`docs/requirement/202608100910.md`（MCPサーバー・クライアントAWSデプロイ要件定義書）およびADR-0023〜0031, 0036〜0040に基づき、Knowledge MCPサーバ・Tag Selector MCPサーバ・agent_invitro・RDS（`chatbot-invitro-rds`）がECS Fargate／プライベートサブネット上に構築済みである。`web_backend` / `front_dev` はこのAWSデプロイのスコープに含まれておらず、`terraform/main/app/main.tf` にも定義がない。
- ADR-0023は「MCPサーバー・クライアント群はAWS内部限定（VPC内）に配置し、外部公開・オンプレVPN接続は行わない。動作確認はECS Exec／SSMポートフォワーディングで代替する」と決定している。これは「利用者は開発者・運用担当のごく少数であり、AWS CLI等の操作を前提にできる」という状況を前提にした決定である。
- 本件のQA・タグ管理UIは、AWS操作の知識を持たない一般の運用担当スタッフも利用者に含む想定であり、ADR-0023が前提としていた利用者像とは異なる。発注者への確認の結果、次の方針で進めることとした。
  - VPN・専用線は新設しない（コスト・構築工数の観点から見送り）。
  - 利用者はAWS CLI等を使わず、ブラウザのみで到達できるようにする。
  - 到達可能な範囲は社内ネットワークのみに限定する（社内グローバルIPアドレスからのみアクセス可能とする）。
  - 上記のネットワークレベルの制限で十分とし、アプリケーションレベルの追加ログイン認証（Basic認証等）は本フェーズでは実装しない。
- これはADR-0023が定めた「AWS内部限定・外部公開なし」という境界方針そのものを覆すものではなく、QA・タグ管理UI（本書が対象とするコンポーネントのみ）に限り、社内IPアドレスからの到達を許可する例外を新設するものである。Knowledge MCP・Tag Selector MCP・agent_invitro・RDSについては、ADR-0023の方針（VPC内限定、SG参照ベースの到達制御）を変更しない。

| 用語 | 説明 |

| admin_ui サービス（仮称） | 本書で新設する、`web_backend` と `front_dev` の本番ビルド資産を配信するECS Fargateサービス（4.1節）。実際のサービス名は詳細設計フェーズで確定する |

## 4. スコープ

### 4.1 対象範囲（MVP）

- `front_dev` の本番ビルド（`vite build`）資産を、AWS上で配信できる形に構成する（配信方式の決定はADR-0042）。
- `web_backend` をECS Fargate常駐サービスとして稼働させ、既存のKnowledge MCPサーバ（AWSデプロイ済み）をMCPクライアントとして呼び出す構成（既存UI要件定義書6.4節、ADR-0013）をAWS上でも維持する。
- インターネット向けのApplication Load Balancer（ALB）を新設し、そのセキュリティグループで社内IPアドレスからのインバウンドのみを許可する（ADR-0041）。
- 上記ALB配下のECS Fargateタスク自体はプライベートサブネットに配置し、パブリックIPを持たせない（既存のknowledge_mcp等と同様の配置方針）。
- Terraform構成（`terraform/main/app/`）へ、上記を実現するモジュール・リソースを追加する（実装フェーズでの作業。本書は要件定義のみ）。

### 4.2 対象外（将来検討・別スコープ）

- QA・タグ管理UI自体の機能変更・追加（一覧表示項目、絞り込み条件、登録編集フォームの項目等）。既存UI要件定義書（202608060826）のスコープをそのまま踏襲し、本書では変更しない。
- アプリケーションレベルの認証・認可（ユーザー単位のログイン、操作権限の分離）。2章で述べた通り、本フェーズはネットワークレベルの制限（社内IPアドレス限定）のみとし、将来運用担当者の追加や不特定多数の利用が生じた場合に別途ADRで再検討する（既存UI要件定義書13章Open Issue #2と同一の課題として引き継ぐ）。
- HTTPS化のためのドメイン取得・証明書発行の具体的な手順（要否・方法は12章Open Issueとして残し、詳細設計フェーズで確定する）。
- VPN・拠点間専用線の新設（2章の通り見送り）。
- Knowledge MCP・Tag Selector MCP・agent_invitro・RDSのネットワーク境界方針の変更（ADR-0023を維持する）。
- `front_dev` のStorybook（`storybook dev` / `build-storybook`）のAWSデプロイ（開発者のローカル環境でのみ使用する前提を維持し、対象外とする）。
- 管理UIのAWS上での動作を、AWS Client VPN・SSMポートフォワーディング等の代替手段でも利用可能にすること（本フェーズは社内IPアドレス限定のブラウザアクセスのみを対象とし、開発者向けの代替アクセス手段は現行のECS Exec／SSM（ADR-0023）で足りるものとする）。

## 5. 全体アーキテクチャ

### 5.1 システム構成（本フェーズ、追加分のみ抜粋）

```
社内ネットワーク（社内IPアドレスからのみ）
        │  HTTPS/HTTP（ADR-0041, 詳細は8.3節）
        ▼
┌───────────────────────────────┐
│  ALB（新設・インターネット向け, パブリックサブネット）  │
│  SG: 社内IPアドレスのみ許可（ADR-0041）              │
└───────────────┬───────────────────┘
                │
                ▼（プライベートサブネットへ）
┌───────────────────────────────┐
│  admin_ui サービス（ECS Fargate常駐, 新設）             │
│  - web_backend（既存, 変更なし）＋front_dev本番ビルド資産  │
│    を単一コンテナで配信（ADR-0042）                      │
│  - パブリックIPなし。ALBのSGからのみ着信を許可            │
└───────────────┬───────────────────┘
                │ MCP over HTTP（既存, ADR-0013, 変更なし）
                ▼
┌───────────────────────────────┐
│  Knowledge MCP サーバ（既存, AWSデプロイ済み, 変更なし）     │
└───────────────┬───────────────────┘
                ▼
        chatbot-invitro-rds（既存, AWSデプロイ済み, 変更なし）
```

- 既存のKnowledge MCPサーバ・Tag Selector MCPサーバ・agent_invitro・RDSの構成・ネットワーク境界（ADR-0023, 0026, 0036）には変更を加えない。
- 新設する `admin_ui` サービスから Knowledge MCP サーバへの到達性は、既存の `agent_invitro → knowledge_mcp` と同様の方式（セキュリティグループの参照許可）で追加する。
- `admin_ui` サービスから RDS への直接アクセスは行わない（既存UI要件定義書6.4節・ADR-0013の方針を維持し、Knowledge MCP サーバ経由に統一する）。

### 5.2 コンポーネント一覧と責務（追加・変更分）

| コンポーネント | 責務 |
|---|---|
| ALB（新設） | インターネットからのHTTP(S)リクエストの受付、社内IPアドレス以外の遮断（SG）、`admin_ui` サービスへの転送 |
| `admin_ui` サービス（新設, ECS Fargate） | `front_dev` 本番ビルド資産の配信、`web_backend` としての既存 `/api/*` エンドポイントの提供（ロジック自体は既存UI要件定義書の実装をそのまま利用） |
| Knowledge MCP サーバ（既存, 変更なし） | QA・タグの参照・登録・編集の業務ロジック（既存UI要件定義書と同一） |
| chatbot-invitro-rds（既存, 変更なし） | QA・タグのデータストア |

## 6. 機能要件

本書では機能要件の新規追加・変更は行わない。既存UI要件定義書（202608060826）6章の機能要件（QA一覧ページ、タグ階層ページ、QA登録・編集フォーム、タグ登録・編集UI、`web_backend` の `/api/*` エンドポイント、Knowledge MCPのQA/タグ管理ツール）を、そのままAWS上の `admin_ui` サービスが提供する。

## 7. データ要件

既存UI要件定義書7.1節のスキーマ（`qa_original` / `question_altered` / `category` / `tag` / `tag_alias` / `qa_tag`）に変更はない。AWS上では、これらのテーブルは既に `chatbot-invitro-rds` 上に作成済み（`db_hiroba_qa_init` によるマイグレーション・シード、ADR-0016〜0018, 0030）であり、本書のスコープでは追加のスキーマ変更を要しない。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| アクセス制御（ネットワーク） | ALBへのインバウンドは社内IPアドレス（8.1節）からのみ許可する。社内IPアドレス以外からの到達は、ALBのセキュリティグループレベルで拒否する（ADR-0041） |
| アクセス制御（アプリケーション） | 追加のログイン認証は実装しない（2章）。将来、社内IPアドレス以外からの利用や利用者ごとの操作権限分離が必要になった場合は、別途ADRで再検討する |
| 通信の暗号化 | HTTPS化の要否・方法（ドメイン取得・証明書発行）は12章Open Issueとして残す。詳細設計フェーズで確定するまでの暫定として、ALBのHTTPリスナーのみで運用することも許容するが、QA本文等の社内情報が平文で流れる点は運用担当者に明示する |
| 性能 | 既存UI要件定義書8章の目標（一覧系APIは1秒以内、暫定目標値）をAWS環境でも維持する |
| 可用性 | 既存のKnowledge MCP等と同様、社内利用ツールとして単一インスタンス構成（`desired_count=1`）で可とする。ALBを新設する目的はネットワーク境界の制御であり、冗長化のためではない |
| ログ | 既存UI要件定義書8章の方針（操作内容と時刻を記録、操作者の記録は認証方式確定後）を維持する。加えて、ALBのアクセスログ（送信元IPアドレス等）を有効化し、想定外のIPアドレスからのアクセス試行がないかを確認できるようにする |
| コスト | ALB（新設）の稼働費用が発生する（時間課金＋LCU）。VPN・専用線を新設しない前提（2章）でのコスト影響は、ALB単体の費用に限定される。詳細な見積もりは詳細設計フェーズで行う |
| 保守性・拡張性 | `admin_ui` サービスは既存の `web_backend` コード（`/api/*` の実装, ADR-0013）をそのまま利用し、AWS向けの差分はビルド・配信方式（ADR-0042）とインフラ構成（ADR-0041）に限定する |

### 8.1 社内IPアドレスの扱い

- 許可する社内IPアドレス（固定グローバルIPアドレス、または少数のCIDR範囲）の具体的な値は、発注者から別途提供を受ける（12章Open Issue #1）。
- 許可リストは、既存Terraform構成が採用している「`.env` からのTF_VAR_*環境変数エクスポート」方式（ADR-0038）を踏襲し、変数として注入する想定とする（コード上への直書きを避ける）。
- 社内側のグローバルIPアドレスが変動する環境（動的IP等）の場合、都度Terraform変数を更新して `apply` する運用になる。恒常的に変動する場合は、本方式では運用負荷が高くなるため、その場合はAWS Client VPN等への切り替えを別途ADRで検討する（ADR-0041「検討した代替案」参照）。

## 9. インフラ・実行環境要件

### 9.1 新規ネットワークリソース

- パブリックサブネットからインターネットへの到達性（インターネットゲートウェイ経由）が必要になる。既存VPC（ADR-0036, 外部管理・data source参照）にパブリックサブネットおよびインターネットゲートウェイへのルーティングが用意されているかを、実装フェーズで基盤チームに確認する（12章Open Issue #2、ADR-0036と同様の確認プロセス）。
- ALB用セキュリティグループ（社内IPアドレスからの80/443許可）、`admin_ui` タスク用セキュリティグループ（ALBからのコンテナポート許可のみ）を新設する。
- `admin_ui` タスクからKnowledge MCPサーバへの到達性を許可するセキュリティグループルールを、既存の `modules/network` に追加する（既存の `agent_invitro → knowledge_mcp` ルールと同様の形式）。

### 9.2 ECS Fargateサービス

- 既存の `modules/ecs-service`（ADR-0024）を、ALB（ターゲットグループ）への接続に対応させる拡張、またはALB対応の新規モジュールの追加が必要になる（現状の `modules/ecs-service` はService Connectのみに対応し、ALB接続には対応していない）。詳細は実装フェーズで確定する。
- コンテナイメージは、`web_backend` の既存Dockerfileをベースに、`front_dev` の本番ビルド資産（`npm run build` の出力）を含める形に変更する（ADR-0042）。
- 環境変数 `KNOWLEDGE_MCP_URL` は既存のAWSデプロイ済みKnowledge MCPサーバのService Connect名（例: `http://knowledge_mcp:8100/mcp`）を指す形で、既存パターン（`terraform/main/app/main.tf` の他サービスと同様）を踏襲する。

### 9.3 Terraform構成への反映

- `terraform/main/app/main.tf` に、`admin_ui` サービス用のECRリポジトリ・ECS Fargateサービス・ALB関連リソースを追加する。
- 許可する社内IPアドレスのリストを `terraform.tfvars` / `.env`（ADR-0038方式）で管理する変数として追加する。

## 10. 既存システムとの関係・影響範囲

- Knowledge MCP・Tag Selector MCP・agent_invitro・RDSの構成・ネットワーク境界方針（ADR-0023, 0026, 0036）は変更しない。
- 既存UI要件定義書（202608060826）が定義した機能・API・MCPツールの仕様は変更しない。AWS向けの差分はビルド・配信方式とインフラ構成に限定される。
- ローカルの `docker-compose` 環境（開発用）は、本書の対象外として現状のまま維持する。`front_dev` の本番ビルド用Dockerfile追加等が発生する場合、開発用の既存Dockerfile（`npm run dev`）とは別ファイルとして追加し、開発フローに影響を与えない。

## 12. Open Issues（要追加確認事項）

1. **社内IPアドレスの具体的な値・管理方法**: 許可する社内IPアドレス（固定グローバルIPアドレス、またはCIDR範囲）の提供を発注者から受ける必要がある。複数拠点がある場合はその一覧化も必要。
2. **既存VPCのパブリックサブネット・インターネットゲートウェイの有無**: ADR-0036により既存VPCを参照する構成のため、ALB配置に必要なパブリックサブネット・IGWへのルーティングが既存VPC側に用意されているかを基盤チームに確認する必要がある。用意されていない場合、既存VPCへのパブリックサブネット追加、または別途の代替構成（IGWを持つ新規VPCの併設等）を検討する必要がある。
3. **HTTPS化（ドメイン・証明書）の要否**: 社内利用ツールとしてHTTP運用を許容するか、ドメイン取得・ACM証明書発行を行いHTTPS化するかを確定する必要がある。QA内容の機密性の程度も踏まえて判断する。
4. **社内グローバルIPアドレスの変動性**: 動的IPアドレス等で恒常的に変動する場合、8.1節の運用（Terraform変数更新→再apply）では対応しきれない可能性があり、AWS Client VPN等への切り替えを別途検討する必要がある。
5. **ALBのコスト承認**: 8章で述べた追加コスト（ALB稼働費用）について、発注者の予算承認を得る必要がある（既存のBedrockコスト予算アラート、ADR-0040と同様の運用ルールに含めるか要検討）。
6. **将来的な認証・権限管理の要否**: 既存UI要件定義書13章Open Issue #2と同一の課題。社内IPアドレス限定を継続する前提が崩れる場合（社外拠点からの利用要望等）に再検討する。
7. **`front_dev` のディレクトリ・位置付けの見直し**: 既存UI要件定義書13章Open Issue #7と同一の課題。AWS本番稼働の対象になることで、「デバッグUI」という現状の位置付けの見直しが一段と必要性を増す。
