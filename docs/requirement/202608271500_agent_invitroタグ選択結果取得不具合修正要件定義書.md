# agent_invitroタグ選択結果取得不具合修正 要件定義書

- 日付: 2026-08-27
- ステータス: 確定
- 関連調査: `docs/detected_problems/202608270951_チャット情報源検索結果検証ページとの差異調査報告.md`
- 関連ADR: ADR-0063（本書に基づく決定）, ADR-0062, ADR-0057, ADR-0059, ADR-0060, ADR-0021

## 1. 目的

実チャット（`agent_invitro`の`POST /ask-sl`）で、`select_tags`（Tag Selector MCP）の結果が会話タグとして反映されず、情報源検索（`search_knowledge`）が常にタグなし（埋め込み類似度のみ）で実行されてしまう不具合を修正する。これにより、検証ページ（ADR-0060）と同等に「タグを効かせた情報源検索」が実チャットでも成立するようにする。

## 2. 背景・経緯

### 2.1 ADR-0062の適用では事象が解消しなかった

`docs/detected_problems/202608270951_...`（調査報告）とADR-0062は、実チャットの情報源検索が検証ページと食い違う原因を「`agent_invitro/src/tags.py`の`search_with_merged_tags`がタグ別複数回呼び出し＋フォールバック＋最大スコア統合という旧方式（ADR-0057ワークアラウンド）のまま残っていること」と結論づけ、これを検証機能（ADR-0060）と同じ単一`search_knowledge`呼び出し方式へ単純化した（ADR-0062）。

しかし、この変更をAWS環境へデプロイ後も、実チャットは依然として的外れな回答を返し、情報源が正しく取得できていない事象が継続した。

### 2.2 AWS実機ログによる原因の再特定

AWS環境の稼働状況・CloudWatch Logs（`/ecs/agent_invitro`）を直接確認し、以下を確認した。

- **デプロイは正しく反映されている**: `agent_invitro`タスク定義 rev 11 が 2026-08-27 10:20（JST）に登録・ロールアウト完了しており、環境変数から`TAG_SEARCH_FALLBACK_ENABLED`が削除されている（ADR-0062のterraform変更が適用済み）。イメージも同一apply-app実行内で`:latest`が更新され、新タスクが取得している。したがってデプロイ手順・反映漏れの問題ではない。
- **デプロイ後（10:28:03）の実チャット1件の完全トレース**:
  - `POST http://tag_selector_mcp:8200/mcp "HTTP/1.1 200 OK"` … `select_tags`呼び出し自体は成功している（例外ログ`select_tags failed`は出ていない）。
  - `search_with_merged_tags query='…' merged_tags=0 hits=1` … **マージタグが0件**の状態で検索が実行されている。
- **デプロイ前（09:15台）のログも、全リクエストで一貫して`merged_tags=0`** であった。

つまり、実チャットのタグ選択（`select_tags`の結果 → 会話タグ化）は、本機能のリリース以来**一度も機能しておらず、常にタグなしの埋め込み類似度検索のみ**で動作していた。ADR-0062が想定した「タグ別複数回呼び出しと単一呼び出しの差」は、そもそもマージタグが常に空であったため結果に影響しない（ADR-0059により、タグ未指定（`tags=None`）と空配列（`tags=[]`）は同一扱いであり、旧コードのフォールバック1回と新コードの`tags=[]`1回は同じ結果になる）。ADR-0062はレイテンシ削減の副次効果はあるが、報告された事象の是正には寄与していなかった。

## 3. 現状の問題点（原因の特定）

### 3.1 会話タグが常に0件になる直接原因

`agent_invitro`はMCPサーバーへの接続に`langchain-mcp-adapters`（ADR-0021）を用いており、`select_tags`・`search_knowledge`の戻り値は同ライブラリが返す形式で受け取る。`agent_invitro`側はこれを次の2つのアドホックな抽出関数でパースしている。

- `agent_invitro/src/tags.py`の`_extract_selected_tags`（`select_tags`結果 → `selected`配列の取り出し）
- `agent_invitro/src/main/api/server.py`の`_extract_results`（`search_knowledge`結果 → `results`配列の取り出し）

このうち`_extract_selected_tags`は、戻り値が **dict / JSON文字列 / bytes / tuple** の場合しか処理できず、`langchain-mcp-adapters`が返す **「テキストブロックの list」形式**（例: `[{"type":"text","text":"<json>"}]`）に対応していない。list を受け取ると無言で`[]`を返すため、`new_tags`が常に空になり、`compute_conversation_tags`の結果（＝`merged_tags`）も常に0件になる。

一方`_extract_results`には list を処理する分岐が存在するため、検索側は`hits=1`のように非空の値を返す。この**両抽出関数の非対称**が、「タグは0件・検索は一応ヒットあり」という観測結果と一致する。

### 3.2 検索側の抽出も実質的に破綻している可能性

`_extract_results`の list 分岐は、list の要素が「結果dict」または「`results`キーを含むdict」または「JSON文字列」であることを前提にしているが、実際にアダプタが返すテキストブロック（`{"type":"text","text":"<json>"}`）の`text`フィールドをJSONとして解釈する処理がない。このため、検索側も本来の`results`配列を取り出せず、コンテンツブロックそのものを結果として返している疑いが強い（`hits`が観測上つねに1＝テキストブロック1個であることと整合する）。この場合、`_build_context`が生成する参考情報は実質空となり、タグ有無に関わらずLLMへ有効なコンテキストが渡っていないことになる。

### 3.3 動作している検証ページとの対比

検証ページ（`web_backend`）は`langchain-mcp-adapters`を使わず、独自クライアント（`web_backend/src/mcp_client/tag_selector_mcp_client.py`・`knowledge_mcp_client.py`）で`CallToolResult.structuredContent`（＝`{"selected": [...]}` / `{"results": [...]}`）を直接読み取る。このため検証ページはタグ・情報源とも正しく取得できており、実チャットとの差はこの**取得（パース）層の実装差**に起因する。

## 4. スコープ

### 4.1 対象範囲（本書）

- `agent_invitro`のMCPツール戻り値パースを、`langchain-mcp-adapters`が返す全形式（dict / JSON文字列 / bytes / tuple / テキストブロックのlist）に対して頑健に修正する。対象は`_extract_selected_tags`（tags.py）と`_extract_results`（server.py）の両方とする。
- 修正が実際に効いていることをAWS実機で確認できるよう、`select_tags`/`search_knowledge`の戻り値からタグ・情報源が取り出せなかった場合に、原因調査に足る診断ログ（戻り値の型と先頭一部）を出力する。
- 修正後、AWS環境のCloudWatch Logsで`merged_tags>0`（タグが取得できている）かつ`hits`が実際のQA件数を反映することを確認する。

### 4.2 対象外（本書のスコープ外）

- ADR-0062で確定した「単一`search_knowledge`呼び出し方式」自体は維持する（本書では呼び出し回数の方式は変更しない）。
- 継続タグ判定ロジック（ADR-0057 4節、`compute_conversation_tags`／`missed_turns`）は変更しない。
- `tag_selector_mcp`・`knowledge_mcp`（サーバー側）の変更は行わない。両サーバーは`structuredContent`を含む正しいMCPレスポンスを返しており、問題は`agent_invitro`側の受信・パースにある。
- 検証機能（`web_backend`）の変更は行わない。
- `langchain-mcp-adapters`から独自MCPクライアント（検証ページ方式）への全面移行は本書では行わない（8章 Open Issue参照）。
- 実チャットのフロントエンドUIへの情報源表示追加は本書のスコープ外（ADR-0062と同じくOpen Issueに記録）。

## 5. 変更後の仕様

### 5.1 戻り値パースの頑健化

`_extract_selected_tags`・`_extract_results`が共通して依存できる「MCPツール戻り値 → payload（dict）正規化」処理を設け、少なくとも以下の全形式を処理する。

- dict（`structuredContent`相当。例: `{"selected": [...]}` / `{"results": [...]}`）はそのまま採用する。
- `(content, artifact)`タプルは先頭要素を対象にする（従来同様）。
- bytes/bytearray はUTF-8デコードする。
- JSON文字列は`json.loads`でdict化する。
- **テキストブロックのlist**（`[{"type":"text","text":"<json>"}]`等）は、各ブロックの`text`（またはブロック自身がJSON文字列の場合はそのブロック）を`json.loads`し、目的キー（`selected` / `results`）を含むdictを取り出す。
- 上記いずれでも目的キーを取り出せない場合は空配列を返し、かつ5.2の診断ログを出力する。

`_extract_selected_tags`は正規化後payloadから`selected`配列を、`_extract_results`は`results`配列を取り出す。

### 5.2 診断ログ

`select_tags`または`search_knowledge`の戻り値から目的の配列を取り出せなかった場合（結果が空になった場合）、`WARNING`レベルで戻り値の`type`名と先頭一定文字数（機微情報を避けつつ形式が分かる程度、例: 先頭300字）を出力する。これにより、万一想定外の形式が返っても、次回以降のログから実際の形式を確定して追加対応できるようにする。

### 5.3 既存ログの維持

`search_with_merged_tags query=%r merged_tags=%d hits=%d`（server.py）は維持する。本修正の成否は、このログで`merged_tags`が質問に応じて1以上になること、および`hits`が実際のQA件数に一致することで判定できる。

## 6. 非機能要件

- 既存の継続タグ判定・会話要約・単一呼び出し方式（ADR-0062）の挙動に影響を与えないこと。
- `langchain-mcp-adapters`のバージョン差（戻り値が文字列・タプル・list等いずれになっても）に対して頑健であること。

## 7. 受け入れ基準（Definition of Done）

- AWS環境の実チャットで、タグが付与され得る質問に対し、CloudWatch Logsの`search_with_merged_tags`ログで`merged_tags`が1以上になること（＝`select_tags`結果が会話タグへ反映されていること）。
- 同一の質問文・同一タグ集合を検証ページと実チャットに与えたとき、`search_knowledge`から得られる上位件数の情報源（QA）が一致すること（`top_k`差がある場合は小さい方の範囲で一致。ADR-0062の受け入れ基準を継承）。
- 会話の1ターン目から、検証ページと同等の情報源検索結果が得られること。
- `agent_invitro/tests`配下に、テキストブロックのlist形式を含む各戻り値形式に対して`_extract_selected_tags`・`_extract_results`が正しく配列を取り出すユニットテストが追加され、CI上で通ること。

## 8. Open Issues（要追加確認事項）

1. **独自MCPクライアントへの統一**: 本修正はアドホックな抽出関数の頑健化にとどめる。中期的には、`agent_invitro`も検証ページと同じ独自MCPクライアント（`structuredContent`を直接読む方式）へ寄せ、パース層を一本化する選択肢がある。要否・実施時期は別途判断する。
2. **実際の戻り値形式の確定**: 本書は「テキストブロックのlist」を主要因と推定しているが、確定は修正版デプロイ後の診断ログ（5.2）で行う。想定外の形式が判明した場合は追加対応する。
3. **`top_k`・`min_score`の値統一・実チャットUIへの情報源表示**: ADR-0062のOpen Issueを継続（本書のスコープ外）。
4. **リグレッションテストの自動化範囲**: 実チャットとMCP2サーバーを結合した統合テスト（タグが実際に付与されることの検証）まで自動化するかは別途判断する。
