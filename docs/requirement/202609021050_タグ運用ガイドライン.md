# タグ運用ガイドライン

- 文書番号: REQ-202609021050
- 対象プロジェクト: chatbot_invitro
- 位置づけ: システムの仕様・DBスキーマを変更するものではなく、既存のタグ管理機能（ADR-0005・ADR-0006・ADR-0008）を前提に、**タグを作成・運用する担当者向けの運用ルール**を定める文書。技術的な変更を伴う決定はADRとして別途起票する。
- 参照資料: ADR-0005（タグの関連テーブル化）、ADR-0006（タグマスタ管理機能）、ADR-0008（タグ知識ベースの正本・description/alias拡張）、ADR-0058（祖先タグ展開）、ADR-0059（タグ構成類似度スコアリング）

## 1. 背景・課題

タグ付け作業を進める中で、次の課題が確認された。

1. QAの内容によっては、「同じ話題について、状況（対象システム・実行環境等）によって異なる情報にアクセスする必要がある」場合と、「状況によらず共通の情報にアクセスすればよい」場合の両方が存在する。これをタグでどう表現するかが定まっていない。
2. タグをどのような切り口（軸）で整理すべきかが事前に確定できず、運用しながら軸の種類が増え続ける可能性がある。また、同じ語が状況によって軸の役割（枠組みを表すのか、対象そのものを表すのか）を変えることがあり、固定的に分類しきれない。
3. 同じ概念に対して人によって別の名前を付けてしまう（表記ゆれ）、あるいは逆に本来別の概念を同じもの・似たものとして混同してしまう、という認識のズレが実際に発生している（例:「ネットワーク認証」と「ネット認証」）。

これらは、タグの木構造（`tag.parent_tag_id`）や検索ロジック（ADR-0058・ADR-0059）をどう設計するかという技術的な問題ではなく、**タグという統制されたボキャブラリーを複数人で一貫して育てていくための運用上の問題**である。本書は、タグの構造自体には変更を加えず、現行の仕組み（木構造・エイリアス・説明文）をどう使うかの指針を示す。

## 2. 基本方針

1. **タグの分類軸（何を「文脈」、何を「話題」とするか等）を、あらかじめ完全に定義しようとしない。** 軸の数・種類は運用しながら増減しうるものとして扱い、無理に単一の分類体系に押し込めない。
2. **「同じ話題が状況によって異なる答えを持つ」場合は、タグ階層を作り直すのではなく、QAへの複数タグの組み合わせ付けで表現する。**（4章）
3. **タグの新規作成よりも、既存タグ・エイリアスの再利用を優先する。**（5章）
4. **タグの定義を「タグ名」ではなく「説明文（description）」に持たせる。** 名前だけでは表現しきれない前提・区別は必ず説明文に書く。（6章）
5. **構造上の判断に迷う場合は、無理に今すぐ決めず、いったん記録して定期棚卸しで見直す。**（8章）

本書は既存のDBスキーマ・API（`create_tag`/`rename_tag`/`move_tag`/`delete_tag`等）に変更を加えない。将来、本書の運用だけでは対応しきれない技術的課題（例: タグの多親化、タグフォルダ属性の追加等）が具体的に発生した場合は、その時点で個別に要件整理・ADR化を検討する（9章）。

## 3. タグ設計の考え方

### 3.1 「軸」は固定の分類ではなく相対的な役割である

あるタグが「対象を絞り込む枠組み（文脈）」なのか「対象そのもの（話題）」なのかは、タグ単体の性質ではなく、**どの情報とどの情報を区別したいかという場面ごとの関係**で決まる。たとえば「認証」は「維津美V7」という製品に対しては話題（対象そのもの）だが、「ContainerNotFound」というエラーに対しては文脈（起きている状況）になりうる。

したがって、タグを作成する際に「これは文脈タグか話題タグか」を毎回無理に分類する必要はない。判断すべきなのは、「このタグは、どのタグと組み合わさったときに初めて意味が確定するか」という点である。

### 3.2 階層（親子関係）を使うべき場合と、使うべきでない場合

- **使うべき場合**: 対象同士に本当に「広い/狭い」の包含関係がある場合（例: 「認証」の中に「ローカル認証」「ネットワーク認証」という下位区分がある）。この場合は引き続き`create_tag`/`move_tag`で親子関係を設定してよい。
- **使うべきでない場合**: 2つの独立した性質の組み合わせを表現したい場合（例:「認証」×「ローカル/ネットワーク」、「積算」×「対象システム」）。この場合、どちらか一方をもう一方の子にしてしまうと、逆方向の組み合わせ（例: 別のシステムでの「積算」）を表現できなくなる。このようなケースは階層化せず、独立した2つのタグをQA側で組み合わせて付ける（4章）。

迷った場合は、「そのタグの一段上の階層を、そのタグ以外の兄弟タグと入れ替えても意味が通るか」を目安にするとよい。「ローカル認証」を「ネットワーク認証」に置き換えても文の構造として成立する（＝認証の一種として並列である）なら親子関係が妥当。一方、「積算」を「対象システムA」の子にしてしまうと、「対象システムC」における「積算」を表現する場所がなくなる、というような場合は、親子関係ではなく組み合わせで扱うべきサインである。

## 4. 「状況によって異なる情報」を表現する方法（組み合わせタグ付け）

同じ話題が状況によって異なる情報を要する場合、新しい階層構造を作るのではなく、**QAに複数のタグを組み合わせて付与する**ことで表現する。この方法はDBスキーマ・検索ロジックの変更を必要とせず、既存の`qa_tag`（QAとタグの多対多関連）とADR-0059のタグ構成類似度スコアリングでそのまま機能する。

例（「B」という話題が「A」「C」という2つの状況で異なる情報を要する場合）:

| QAの内容 | 付与するタグ |
|---|---|
| AでもCでも共通して言えるBの情報 | `B`のみ |
| Aに固有のBの情報 | `A`と`B`の両方 |
| Cに固有のBの情報 | `C`と`B`の両方 |

利用者が状況（AかCか）を明示せず「Bについて」とだけ質問した場合、検索時に確定しているタグは`B`のみとなる。この場合、`B`のみを持つQA（共通情報）はタグ構成の一致度（Jaccard係数）が最大になり優先的に検索結果に浮上する。逆に、会話の中で既に「A」に関する話であることが分かっていれば（会話タグの継続、ADR-0056/0057）、`A`と`B`の組み合わせを持つQAが優先される。

**ただし、この方法は「共通情報を返す／文脈込みの情報を返す」という検索結果の優先順位付けまでしか解決しない。** 「共通情報では不十分で、AなのかCなのかを利用者に確認する必要がある」という積極的な聞き返しの挙動は、本書の範囲を超える会話フロー上の別機能であり、別途要件定義・ADR化が必要である（9章）。

## 5. 新規タグ作成前の確認手順

タグを新規に作成する前に、担当者は次を確認する。

1. 同じ、または近い意味を持つ既存タグ・エイリアスがないか、タグ管理画面で名称・説明文を確認する。
2. 見つかった既存タグが指している対象と、これから表現したい対象が完全に同一だと判断できる場合 → 新規タグを作らず、既存タグをそのまま使うか、表記ゆれの語を`add_tag_alias`でエイリアスとして追加する。
3. 対象は近いが明確に異なる概念だと判断できる場合（例:「ネットワーク認証」と「ネット認証」が調査の結果、社内LAN認証とインターネット経由のライセンス認証という別概念だったと分かった場合） → 別タグとして作成し、両方の説明文にお互いとの違いを明記する（6.2節のテンプレート参照）。
4. 「同一か別概念か、この場で判断がつかない」場合 → 判断を保留してよい。ただし保留したタグは8章の棚卸し対象リストに記録し、放置しない。

## 6. 説明文（description）の記述ルール

### 6.1 原則

タグ作成・編集時、`description`は**空のままにしない**。名前だけでは伝わらない「このタグが指す範囲」「このタグが指さない範囲」を短くてよいので明文化する。特に、名前が似ている別タグが存在する場合や、将来似た名前のタグが作られる可能性がある場合は必須とする。

### 6.2 テンプレート

```
[このタグが指すもの]: 一文で対象を説明する
[区別すべき紛らわしいタグ]: 似た名前・意味のタグがあれば列挙し、違いを一言で書く
```

例:

```
[このタグが指すもの]: 社内LAN経由でのクライアント認証（オンプレミス環境向け）
[区別すべき紛らわしいタグ]: 「ネット認証」とは異なる。「ネット認証」はインターネット経由のライセンス認証を指す。
```

## 7. 表記ゆれ・概念の混同への対処

- 表記ゆれ（同一概念に複数の名前がある）と判明した場合は、片方を正（残すタグ）、もう片方をエイリアスとして統合する。統合前にどちらか一方のタグにのみQAが紐づいている場合、統合後は残すタグへQAの紐付けを付け替える必要がある（現行の`delete_tag`は`qa_tag`から参照されているタグの削除を拒否するため、削除前に付け替えが必須になる）。
- 概念の混同（別概念なのに同じ／似た名前で運用されていた）と判明した場合は、6章のテンプレートに従って両タグの説明文を書き分け、必要であれば紛らわしくない名前へのリネームも検討する。
- どちらであるかの判断や、上記の統合・リネーム作業は、8章の棚卸しの場でまとめて行うことを基本とし、日々のタグ付け作業の中で個々人が独自に判断して統合・削除しないようにする。

## 8. 定期棚卸し

タグ運用を持続的に健全な状態に保つため、次を定期的に（頻度は運用開始後に実績を見て決定するが、当初は月1回を目安とする）確認する。

- 説明文が空のタグの洗い出しと記入
- 名称が似ている、または5章4.で判断保留にしたタグの一覧確認と、統合／別概念としての明確化の判断
- QAが1件も紐づいていないタグ、または全QAの大部分に紐づいている（絞り込みとして機能していない）タグの洗い出しと要否確認
- 4章の組み合わせタグ付けが実際にどう使われているか（想定通り「共通情報」「A固有」「C固有」のパターンで運用できているか）の確認

## 9. 本書の適用範囲外・別途検討が必要な事項

本書は運用ルールのみを扱い、次の事項は対象外とする。必要になった時点で個別に要件定義・ADR化する。

- タグに複数の親を持たせる、またはタグ名の一意性をnameからidへ変更する等、`tag`テーブルのスキーマ変更を伴う対応
- タグに「文脈」「話題」等のタグフォルダを持たせ、管理画面（`TagTreePage`/`TagPicker`）をタグフォルダ単位の表示に変更する対応
- 検索結果が状況（文脈）によって割れる場合に、利用者へ確認質問を返す会話フローの追加（4章末尾で触れた「聞き返し」機能）
- タグの作成・リネーム・統合・削除を行える担当者の権限・レビュー体制（ADR-0006が「Open Issue」として残したまま未確定の論点。表記ゆれ・概念の混同が実際に発生している状況を踏まえ、レビュー体制の要否を別途検討することを推奨する）
