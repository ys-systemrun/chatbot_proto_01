# AWS環境向けChatbotUI・会話評価機能有効化要件定義書

- 文書番号: REQ-202608240949
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `agent_invitro`（AWS環境限定の常駐HTTPサービス化）, `web_backend`（`admin_ui`, `/ask-sl`の中継化）, `terraform/`（新規ネットワーク・DB・ECSリソース）
- 参照資料: `docs/requirement/202608061621.md`（会話エージェント実験要件定義書）, `docs/requirement/202608100910.md`（MCPサーバー・クライアントAWSデプロイ要件定義書）, `docs/requirement/202608211014.md`（AWS環境向けQA・タグ管理UI要件定義書）, `docs/requirement/_to_delete/202608211542_AWS環境向けChatbotUI・会話評価機能有効化要件定義書.md`（2026-08-21時点の廃案、2章参照）
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照

## 1. 目的

AWS上に既にデプロイ済みのQA・タグ管理UI（`admin_ui`サービス、ADR-0041/0042、要件定義書202608211014）に対し、ローカル`docker-compose`環境では既に機能しているChatbotUI（質問応答、`/ask-sl`）および会話評価（good/bad、`/evaluate_response`, `/evaluated_messages`）の各機能をAWS上でも有効化する。

具体的には、次の構成を実現する。

1. `admin_ui`のバックエンドが、`/ask-sl`にポストされた質問等のデータを使い、`agent_invitro`へHTTPリクエストを送信してチャットの生成を行わせる（`admin_ui`のバックエンドが`agent_invitro`に対するHTTPクライアントとなる）。
2. good/bad評価機構（`/evaluate_response`, `/evaluated_messages`）は、これまでと同様に`admin_ui`のバックエンドが`conversation`データベースへ直接クエリを発行する。

本書はAWS環境専用の要件であり、ローカル`docker-compose`環境の構成（`web_backend`がLM Studioを直接呼ぶ現行実装）には変更を加えない。**`/ask-sl`を実装するソースコード（`web_backend/main/main_stateless.py`）はローカル`web_backend`コンテナとAWS`admin_ui`コンテナの両方で共通であるため、「ローカルではLM Studio、AWSではBedrock（`agent_invitro`経由）」という両立は、コードの置き換えではなく環境変数の有無による条件分岐として実現する**（詳細は6章・9.2節・ADR-0045）。コーディングは対象外とし、要件定義および設計判断（ADR）の整理にとどめる。

## 2. 背景・参照資料

### 2.1 現状（ローカルdocker-compose環境）

- ChatbotUI（`POST /ask-sl`）は、`web_backend`（`main_stateless.py`）が単独で、要約（`SummarizeLLM`）→検索クエリ整形（`FormatQueryToEmbed`）→embedding（`src/embedding.py:get_embedding`）→`chatbot`データベースへの類似QA検索（`DB.search_similar`）→回答生成（`GenerateAnswerLLM`）を行う。いずれもローカルLLM（LM Studio）を直接呼び出す。`/ask-sl`自体は`conversation`データベースへの読み書きを行わない（会話状態はクライアント側で保持し、毎回全履歴を再送するステートレス設計）。
- 会話評価（`POST /evaluate_response`, `GET /evaluated_messages`）は、`web_backend`が`ConversationDB`（`web_backend/src/conversation_db/db.py`）を通じて、独立した`conversation_db`コンテナ（PostgreSQL 16、`db_conversation/init.sql`の`conversation`/`message`テーブル）へ直接読み書きする。
- `agent_invitro`は現状、ChatbotUI・会話評価のいずれにも関与しない。IPython対話シェル専用コンテナ（`sleep infinity`, ADR-0019）であり、常駐HTTPサーバーを持たない。

### 2.2 現状（AWS環境）

- QA・タグ管理UI（`admin_ui`サービス）は既にAWS上にデプロイ済み（ADR-0041/0042, `terraform/main/app/main.tf`）。`web_backend`の実装（`main_stateless.py`）を含む同一コンテナイメージが稼働しているため、`/ask-sl`・`/evaluate_response`・`/evaluated_messages`の各パス自体はALB経由で既に到達可能な状態にある。しかし、これらのエンドポイントが必要とする環境変数（`DATABASE_URL`, `CONVERSATION_DB_URL`, `LMSTUDIO_CHAT_URL`等）はAWS上の`admin_ui`タスクに設定されておらず（空文字fallback、`main_stateless.py`）、呼び出すと実行時エラーになる。
- `agent_invitro`はAWS上でもECS Fargateとして稼働しているが、`container_port = null`・`command = ["sleep","infinity"]`であり、HTTPリクエストを受け付けない（`terraform/main/app/main.tf`）。`LLM_PROVIDER=bedrock`・`BEDROCK_CHAT_MODEL_ID`等は既に設定済みで、Knowledge MCP・Tag Selector MCPへの到達性（セキュリティグループ）も既に確立している。
- AWS上には、QAデータ用のRDSインスタンス（`chatbot-invitro-rds`, ADR-0026, `chatbot`データベース）のみが存在し、`conversation`データベースに相当するリソースは存在しない。

### 2.3 2026-08-21時点の検討経緯（参考）

2026-08-21頃、本件と同種の要件について検討が行われ、要件定義書（`_to_delete/202608211542`）およびADR-0043〜0045（`_to_delete`）が一度作成されたが、実装着手前に取りやめられ、いずれも`_to_delete`ディレクトリへ退避された。検討された方針は次の2案であった。

- 当初案（Rev.1）: `admin_ui`（`web_backend`）にChatbotUI・会話評価機能をそのまま実装し、Bedrockを直接呼ぶ。
- 方針転換後（Rev.2）: `admin_ui`はfrontend層のみを担当し、ChatbotUI・会話評価機能の実処理（QA類似検索、回答生成、要約、評価データの読み書き）を`agent_invitro`に一本化して担わせる。

発注者に確認したところ、これらを取りやめた理由は「当時はAWS環境の構成をよく理解していなかったため一度白紙にしたが、その後調査・検討した結果、今回の要件が最善と判断した」とのことであった。技術的な不整合が原因で取りやめたわけではない。

今回の要望は、Rev.1・Rev.2のいずれとも異なる第3の分担（チャット生成のみ`agent_invitro`に委任し、会話評価はローカル環境と同様`admin_ui`が直接処理する）であり、3章以降で述べる方針を新たな決定として整理する。なお、2026-08-21時点の検討内容のうち、次の2点は技術的な妥当性を保つものとして本書に引き継ぐ。

- `conversation`データベースは新規RDSインスタンスを立てず、既存の`chatbot-invitro-rds`に相乗りさせる（ADR-0044）。
- QA類似検索はKnowledge MCPの`search_knowledge`ツール経由に統一し、`agent_invitro`に`chatbot`データベースへの直接到達性を持たせない（ADR-0043）。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| `admin_ui`サービス | 既存のAWS上ECS Fargateサービス（ADR-0041）。`web_backend`（FastAPI）と`front_dev`の本番ビルド資産を配信する（ADR-0042）。本書ではそのバックエンド（`web_backend`）が`agent_invitro`へのHTTPクライアントとなる |
| `agent_invitro` | LangGraph ReActエージェント（ADR-0019〜0022）。本書でAWS環境限定の常駐HTTPサービスとする（ADR-0043） |
| ChatbotUI | `POST /ask-sl`によるチャット質問応答機能 |
| 会話評価（good/bad） | `POST /evaluate_response`（評価の登録）・`GET /evaluated_messages`（評価済み会話の一覧取得）による、回答へのgood/bad評価機能 |
| `conversation`データベース | 会話履歴・評価データを保存するデータベース（ADR-0044）。AWS上では`chatbot-invitro-rds`上に新設する |

## 4. スコープ

### 4.1 対象範囲（MVP）

- `agent_invitro`をAWS環境限定で常駐HTTPサービス化し、`POST /ask-sl`と同一契約のエンドポイントを実装する（ADR-0043）。
- `admin_ui`（`web_backend`）の`POST /ask-sl`を、`agent_invitro`への薄い中継（リバースプロキシ）に置き換える（ADR-0045）。
- `POST /evaluate_response`・`GET /evaluated_messages`は、`admin_ui`（`web_backend`）が`conversation`データベースへ直接読み書きする実装を維持する（ADR-0045）。
- `conversation`データベースをAWS上の`chatbot-invitro-rds`インスタンス上に新設する（ADR-0044）。
- 上記を実現するTerraform構成（ネットワーク・ECS・DB）の変更を整理する（実装は本書の対象外）。

### 4.2 対象外（将来検討・別スコープ）

- ChatbotUI・会話評価機能自体の仕様変更（質問応答のロジック、評価のUI/UX等）。既存のローカル実装（202608061621, `main_stateless.py`）の仕様をそのまま踏襲する。
- ローカル`docker-compose`環境の構成変更（`agent_invitro`を常駐HTTPサーバー化する等）。本書はAWS環境限定であり、ローカル環境は現状のまま維持する（発注者確認済み）。
- QA・タグ管理UI（`/api/*`）自体の変更。ADR-0013の方針（Knowledge MCP経由）は変更しない。
- 会話データの保持期間・削除ポリシー、個人情報・機密情報の取り扱い（12章Open Issue）。
- 認証・認可の追加、社外公開。既存のADR-0041の方針（社内IPアドレス限定、追加ログイン認証なし）をそのまま踏襲する。
- `agent_invitro`のReActエージェントの精度改善・プロンプト調整そのもの（既存の202608061621のスコープ、および実装フェーズの対象）。

## 6. 機能要件

本書では機能要件（質問応答・評価の仕様そのもの）の新規追加・変更は行わない。既存のローカル実装（202608061621, `main_stateless.py`）の以下の契約をAWS上でも維持する。

- `POST /ask-sl`: `Request{conversation_id, text, messages, summary}` → `Response{conversation_id, messages, summary}`（`Message{order, role, content, input, model, evaluation}`, `Summary{content, summarized_upto}`）
- `POST /evaluate_response`: `EvaluateRequest{conversation_id, messages}` → `EvaluateResponse{conversation_id}`
- `GET /evaluated_messages`: `EvaluatedConversationOut[]`

**6.1 環境ごとのLLM経路の両立（必須要件）**

`/ask-sl`は、実行環境に応じて次の2つの経路のいずれかを使う。両者は同一のソースコード（`web_backend/main/main_stateless.py`）上で、環境変数`AGENT_INVITRO_URL`の設定有無による条件分岐として実装し、コードの置き換え・分岐先のどちらか一方の削除は行わない（ADR-0045決定1）。

| 実行環境 | `AGENT_INVITRO_URL` | 経路 | LLM |
|---|---|---|---|
| ローカル`docker-compose`（`web_backend`コンテナ） | 未設定（既定） | 既存の直接処理（要約→クエリ整形→embedding→`chatbot`データベース類似検索→回答生成）を維持 | LM Studio（変更なし） |
| AWS（`admin_ui`コンテナ） | 設定済み（`http://agent_invitro:8300`等） | `agent_invitro`の`/ask-sl`へ中継（ADR-0043） | Amazon Bedrock（`agent_invitro`側で呼び出し） |

これにより、発注者の要望（ローカルは従来通りLM Studio、AWSはBedrockを使い、両者を両立させる）を満たす。

## 7. データ要件

- `conversation`データベースのスキーマ（`conversation`, `message`テーブル）は、既存の`db_conversation/init.sql`と同一とする（ADR-0044）。追加のスキーマ変更は本書のスコープでは発生しない。
- `chatbot`データベースのスキーマは変更しない。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| アクセス制御（ネットワーク） | `admin_ui_task → agent_invitro`（8300番）、`admin_ui_task → rds`（5432番）の新規到達性を、既存のSG参照ベースの許可方式（ADR-0023）で追加する。`agent_invitro`はALBから到達不可のまま（変更なし） |
| アクセス制御（アプリケーション） | `admin_ui`に注入する資格情報は`conversation`データベース用のみとし、`chatbot`データベース用の資格情報は注入しない（資格情報スコープによる区別、5.1節・ADR-0045） |
| 通信の暗号化 | `admin_ui`⇄`agent_invitro`、`admin_ui`⇄RDSともにAWS内部（VPC内）通信であり、既存のKnowledge MCP等と同様の扱いとする。追加のTLS要件は設けない |
| 性能 | チャット生成が`admin_ui → agent_invitro`の1ホップ増えるため、ALB/`admin_ui`のタイムアウト設定がBedrock応答時間を上回ることを実装フェーズで確認する（12章Open Issue #4） |
| 可用性 | 既存の単一インスタンス構成（`desired_count=1`）を維持する。本書のためにALBを新設する必要はない（既存のALBをそのまま使う） |
| ログ | 既存の方針（操作内容と時刻を記録）を維持する |
| コスト | 追加コストは`conversation`データベース（既存RDSインスタンスへの相乗りのため実質増分なし）のみであり、ALB等の新規リソースは発生しない |
| 保守性・拡張性 | `agent_invitro`の`/ask-sl`実装、`admin_ui`の中継実装は、既存のコード共有せず複製する方針（ADR-0016〜0018）を踏襲する |

## 9. インフラ・実行環境要件

### 9.1 `agent_invitro`（`terraform/main/app/main.tf`の`module "agent_invitro"`）

- `container_port = 8300`を追加。
- `command`引数を`["sleep","infinity"]`から常駐HTTPサーバー起動コマンドへ変更する（具体的なコマンドは実装フェーズで確定）。
- `health_check_command`を追加する（例: `["CMD","curl","-f","http://localhost:8300/health"]`）。
- 既存の`LLM_PROVIDER=bedrock`, `BEDROCK_CHAT_MODEL_ID`, `enable_bedrock=true`, `KNOWLEDGE_MCP_URL`, `TAG_SELECTOR_MCP_URL`は変更しない。

### 9.2 `admin_ui`（`terraform/main/app/main.tf`の`module "admin_ui"`）

- 環境変数`AGENT_INVITRO_URL`（例: `http://agent_invitro:8300`）を追加する。この変数はAWS側の`module "admin_ui"`にのみ設定し、ローカル`docker-compose.yml`の`web_backend`サービスには設定しない（6.1節）。これにより`main_stateless.py`の`/ask-sl`条件分岐が、AWSでは`agent_invitro`経由、ローカルでは既存のLM Studio直接呼び出しを、それぞれ自動的に選択する。
- secrets`CONVERSATION_DB_URL`（ADR-0044の`conversation_db_url_secret_arn`）を追加する。
- `enable_bedrock`は`false`のまま変更しない。

### 9.3 ネットワーク（`terraform/modules/network`）

- `admin_ui_task → agent_invitro`（8300番）のインバウンド許可ルールを追加する（既存の`agent_invitro → knowledge_mcp`と同形式）。
- `admin_ui_task → rds`（5432番）のインバウンド許可ルールを追加する（ADR-0041の限定的な見直し、ADR-0045）。

### 9.4 データベース（`terraform/modules/database`, `db_hiroba_qa_init`）

- `conversation_db_name`変数（既定値`"conversation"`）、`conversation_db_url_secret_arn`出力を追加する。
- `db_hiroba_qa_init`の起動シーケンスに`conversation`データベースの作成（`CREATE DATABASE`、存在チェック付き）、`conversation`/`message`テーブルの冪等DDL適用を追加する（ADR-0044）。

## 10. 既存システムとの関係・影響範囲

- QA・タグ管理UI（`/api/*`、Knowledge MCP経由）は変更しない（ADR-0013）。
- ローカル`docker-compose`環境は変更しない。`main_stateless.py`は`web_backend`（ローカル）と`admin_ui`（AWS）の両方で共有されるが、`AGENT_INVITRO_URL`未設定時（ローカル）は既存のLM Studio直接呼び出し経路がそのまま使われるため、ローカル環境の挙動・依存関係（LM Studio, `chatbot`データベースへの直接クエリ）は変更されない（6.1節）。
- Knowledge MCP・Tag Selector MCP・`chatbot`データベースのネットワーク境界（ADR-0023, 0026, 0036）は変更しない。
- ADR-0019・0025（`agent_invitro`は常駐HTTPサーバー化しない）は、AWS環境限定でADR-0043により見直される。ローカル環境での位置づけは変更しない。
- ADR-0041（`admin_ui`はRDSへ直接アクセスしない）は、`conversation`データベースに限り、ADR-0045により限定的に見直される。`chatbot`データベースへのアクセス経路は変更しない。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] 社内IPアドレスからブラウザで`admin_ui`のChatbotUIページにアクセスし、質問を送信すると、`agent_invitro`経由で生成された回答が表示される。
- [ ] 回答にgood/badの評価を行うと、`conversation`データベース（AWS上の`chatbot-invitro-rds`）に記録される。
- [ ] 評価済み会話の一覧ページ（`/evaluated_messages`）が、AWS上の`conversation`データベースの内容を表示する。
- [ ] `agent_invitro`がALBから到達不可であること（ADR-0023準拠）を確認する。
- [ ] `admin_ui`に注入される資格情報が`conversation`データベース用のみであり、`chatbot`データベース用の資格情報が注入されていないことをコードレビューで確認する。
- [ ] 既存のQA・タグ管理UI（`/api/*`）、Knowledge MCP、Tag Selector MCPの動作に影響がないことを確認する。
- [ ] `main_stateless.py`に`/ask-sl`の条件分岐（`AGENT_INVITRO_URL`有無）を追加した後も、ローカル`docker-compose`環境で`AGENT_INVITRO_URL`が未設定のままChatbotUIが従来通りLM Studio経由で応答し、評価機能も従来通り動作することを確認する（6.1節）。

## 12. Open Issues（要追加確認事項）

1. **QA類似検索の精度**: `search_knowledge`経由（クエリ整形ステップなし、エージェントの推論に委ねる）に切り替えた場合、既存の`FormatQueryToEmbed`による明示的整形と比べて検索精度が損なわれないか、実装フェーズで検証が必要。
2. **回答生成の実装範囲**: `agent_invitro`の回答生成を、単一プロンプト生成（`GenerateAnswerLLMBedrock`相当）に留めるか、既存のReActエージェントのツール呼び出しループ全体を経由させるかは実装フェーズで確定する。
3. **Bedrockチャットモデルの確定**: `BEDROCK_CHAT_MODEL_ID`は`.env.example`上未確定（空）。実装着手前に確定する必要がある。
4. **`admin_ui`→`agent_invitro`のタイムアウト設定**: Bedrock応答時間がALB/`admin_ui`側のタイムアウトを超えないことを実装フェーズで確認する。
5. **会話データの保持期間・削除方針**: 2026-08-21時点で発注者から「MVPでは無期限保存で問題ない」との回答を得ているが、本書で改めて確認することを推奨する。`message.content`/`message.input`に含まれる質問文・LLMプロンプトの機密性・個人情報の取り扱いも含む。
6. **常駐HTTPサーバーの具体的な起動コマンド・フレームワーク**: `agent_invitro`の既存依存関係（`langgraph`, `langchain-mcp-adapters`, `langchain-openai`）にFastAPI等のHTTPサーバーライブラリを追加する必要がある。実装フェーズで確定する。
7. **ECS Execによる対話的検証（ADR-0019/0025の元来の用途）との併存**: 常駐HTTPサーバー化後も、開発者による対話的動作確認（`docker compose exec`相当、AWSではECS Exec）が引き続き可能であることを実装フェーズで確認する。
