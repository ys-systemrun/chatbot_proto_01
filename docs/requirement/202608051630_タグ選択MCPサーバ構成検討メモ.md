RAGシステムでは検索品質が回答品質を大きく左右するため、この責務分離は将来的に非常に拡張しやすい設計です。例えば、「親タグまで広げる」「子タグを含める」「タグAとタグBはAND条件」「タグCは除外する」といった検索ポリシーをTag Selector MCP側で一元的に管理できるようになります。

将来を見据えた構成

以前ご相談されていたRAGシステム全体を考えると、Tag Selector MCPを単独で完結したマイクロサービスとして設計するのが拡張性に優れています。

                    MCP Client
                         │
 ┌───────────────────────┼────────────────────────┐
 │                       │                        │
 ▼                       ▼                        ▼
Tag Selector        Metadata Search        Document Fetch
MCP Server             MCP Server             MCP Server
 │                       │                        │
 ▼                       ▼                        ▼
Taxonomy          Metadata Index          Document Store
Embedding DB       PostgreSQL             S3
LLM                Elasticsearch          OCR

この構成にすると、各MCPサーバーは単一責務になります。

Tag Selector: 質問からタグや検索計画を生成する
Metadata Search: タグや条件に基づいて文書IDを検索する
Document Fetch: 文書本文やチャンクを取得する

それぞれが独立しているため、Tag Selectorだけを新しいLLMやEmbeddingモデルに置き換えたり、Metadata SearchだけをElasticsearchからOpenSearchに変更したりしても、他のコンポーネントへの影響を最小限に抑えられます。

さらに、タグ体系の更新（新規タグ追加・階層変更）と、Embeddingの再生成をCI/CDパイプラインに組み込むことで、タグ知識ベースを継続的に改善しながら運用できるようになります。
