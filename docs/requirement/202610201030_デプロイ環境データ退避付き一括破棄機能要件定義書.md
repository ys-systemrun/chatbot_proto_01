# デプロイ環境データ退避付き一括破棄機能（destroy-all.bat） 要件定義書

- 文書番号: REQ-202610201030
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `db_init`（`src/main.py`・`src/import_data.py`）, `terraform/deploy`（`src/commands.py`・`src/__main__.py`・`src/aws.py`）, `terraform/destroy-all.bat`（新設）, `terraform/export-data.bat`（新設）, `terraform/import-data.bat`（コメントのみ）, `.gitignore`, `terraform/README.md`
- 変更なしのコンポーネント: 既存 `destroy-app`・`destroy-database`・`query`・`seed`・`migrate` コマンドの単独実行時の動作、`import-data` の全消去→上書き処理そのもの（スキーマ版の事前確認のみ追加）、Terraform のリソース定義（ECS タスク定義・IAM・S3 バケット）、`web_backend` の全データエクスポート機能（`GET /api/export`）、各アプリケーション本体
- 参照資料: `docs/adr/0039-terraform-state-two-layer-consolidation.md`, `docs/adr/0040-deploy-orchestration-containerized-python.md`, `docs/adr/0046-chatbot-db-export-readonly-access.md`, `docs/adr/0047-data-export-dump-generation-and-delivery.md`, `docs/adr/0066-full-data-import-batch-automation-and-overwrite.md`, `docs/adr/0075-migration-only-execution-mode.md`, `docs/adr/0083-adhoc-sql-execution-via-query-bat.md`, `docs/adr/0095-verification-env-cost-reduction-single-task-single-az-endpoints.md`, `docs/adr/0097-knowledge-data-versioning-with-dvc-pull-before-build.md`
- 前提の決定事項: 本書末尾「12. 関連ADR一覧」参照（本書に対応するADRは ADR-0103）

## 1. 目的

現状、AWS 上のデプロイ環境を撤去するには、運用者が `destroy-app.bat` → `destroy-database.bat` の順に 2 つのバッチを実行する。`destroy-database` は RDS インスタンスを `skip_final_snapshot=true` で削除し、全データインポート用 S3 バケット（`force_destroy=true`）も同時に削除するため、**実行した時点で RDS 上のデータは AWS 上のどこにも残らない**。

RDS 上には、DVC 管理のシード元データ（ADR-0097）からは再現できないデータが蓄積している。

- 管理 UI から追加・編集した QA・言い換え質問文・タグ・タグエイリアス・トラブルシューティング記事（`knowledge` データベース）
- 会話ログ・評価・リリース記録・検証質問と検証結果（`conversation` データベース）

これらを残すには、破棄の前に運用者が管理 UI の全データエクスポート（`/admin/export`）を手動で実行する必要があるが、手順として強制されておらず、エクスポートを忘れたまま破棄すると復旧手段がない。

本書は、**① デプロイ環境の全データを SQL ファイルとしてローカルへエクスポート → ② `destroy-app` 相当の処理 → ③ `destroy-database` 相当の処理** を、1 回のバッチ実行で、かつ ① の成功を確認してからでなければ ②③ に進まない形で行う、新しいエントリポイント `destroy-all.bat` を新設するための要件を定義する。あわせて、途中で失敗したときに続きから再実行する手段と、退避ファイルから復旧するときにスキーマ版の違いを確認する手段を定める。

## 2. 背景・参照資料

### 2.1 現状の破棄手順（調査結果）

| バッチ | deploy サブコマンド | 内容 | 確認方式 |
|---|---|---|---|
| `destroy-app.bat` | `destroy-app` | app 構成（ECS クラスタ・集約サービス・ALB・ECR 等）を `terraform destroy`。RDS は残る | `'destroy-app'` のタイプ確認 |
| `destroy-database.bat` | `destroy-database` | RDS の削除保護を解除（RDS インスタンスのみ `-target` apply）→ database 構成を `terraform destroy`（`skip_final_snapshot=true`） | `'destroy-database'` のタイプ確認 |

- 破棄順序は app → database（ADR-0039）。`destroy-database` は app 構成の state が残っていると警告するが、処理は止めない。
- 両コマンドとも `--yes` による確認省略は持たない。

### 2.2 既存のデータ取り出し手段

| 手段 | 出力 | 本機能での扱い |
|---|---|---|
| 管理 UI の全データエクスポート（ADR-0046/0047, `GET /api/export?format=sql`） | ブラウザへ ZIP（`knowledge.sql`・`conversation.sql`）を同期ダウンロード | 運用者のブラウザ操作が必要で、バッチから呼べない（ALB へのアクセス経路・認証をバッチに持ち込む必要がある）。流用しない |
| `import-data` の事前自動バックアップ（ADR-0066 §5, `db_init` IMPORT_MODE） | `db_init` の run-task が `TRUNCATE` + `INSERT` 形式の退避 SQL を生成し、import バケットの `rollback/<対象>/<時刻>/` へ保存 | **生成ロジック（`build_backup_sql`）を流用する**。ただし import バケットは `destroy-database` で消えるため、ローカルへの取得が別途必要 |
| `query.bat`（ADR-0083, QUERY_MODE） | 最終文の結果を CloudWatch Logs 経由で画面表示 | 全件ダンプの用途には向かない（ログ行・サイズの制約）。流用しない |

### 2.3 ユーザーの要求（2026-10-20）

- 次の 3 つをすべて行うバッチエントリポイントを作成したい。
  1. 現在デプロイ環境にあるデータを SQL ファイルとしてエクスポートする
  2. `destroy-app.bat` 相当の処理を行う
  3. `destroy-database.bat` 相当の処理を行う

### 2.4 発注者との確認済み方針（2026-10-20 追加確認）

| # | 論点 | 決定 |
|---|---|---|
| 1 | 退避ファイルの保管先 | **運用者の PC（ローカル）のみ**とする。AWS 上の長寿命バケット等への複製は考えない |
| 2 | 途中で失敗したときの再実行 | **続きから再実行できるオプション引数を設ける**（6.4 節） |
| 3 | app 構成が既に無い環境 | 退避できないため、「`destroy-database.bat` を実行するか、`apply-app.bat` を実行してから再実行する」旨のメッセージを表示して処理を終える（6.2 節 F-8） |
| 4 | 復旧時にスキーマ版が異なる場合 | `import-data` 実行時にコンソール上で「そのまま SQL を実行するか／終了するか」を確認する（6.5 節） |
| 5 | 退避ファイル（特に会話ログを含む `conversation.sql`）の保管期間 | **次回のエクスポートで上書きされる形で消える**ようにする。退避ファイルは固定のディレクトリ `terraform/backup/` に置き、`knowledge.sql`・`manifest.json` も含めて毎回まとめて上書きする（PC 上に残るのは常に最新 1 回分）（7 章） |

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| 退避エクスポート | 本機能の ① の処理。両データベースの対象テーブル全行を SQL ファイルとして運用者の PC（リポジトリの `terraform/backup/`）へ保存すること |
| 退避ディレクトリ | 退避エクスポートの成果物を置く固定のディレクトリ `terraform/backup/`。退避のたびに中身を最新 1 回分で上書きする |
| 退避ファイル | 退避ディレクトリ内の SQL ファイル `knowledge.sql`・`conversation.sql` |
| マニフェスト | 退避ディレクトリ内の `manifest.json`。取得日時・環境・ファイルごとのサイズ・SHA-256・テーブルごとの行数・スキーマ版を記録する。データ本体は含まない |
| スキーマ版 | データベースごとの、yoyo で適用済みのマイグレーション ID の集合 |
| 対象テーブル | `db_init/src/import_data.py` の `KNOWLEDGE_TABLES`・`CONVERSATION_TABLES`。全データインポート（ADR-0066）の全消去・再投入の対象と同一の集合 |
| 一括破棄 | 本機能の ①→②→③ を 1 回の実行で行うこと（`destroy-all`） |
| 再開実行 | 一括破棄が ② または ③ で失敗した後、退避を取り直さずに失敗した段から実行し直すこと（`--resume-from`） |

## 4. スコープ

### 4.1 対象範囲

1. `db_init` に退避エクスポート専用の起動モード（`EXPORT_MODE=true`）を追加する。スキーマ版だけを返すマニフェスト限定の実行（`EXPORT_MANIFEST_ONLY=true`）も含む。
2. `terraform/deploy` に `export-data` サブコマンド（退避エクスポートのみ、非破壊）と `destroy-all` サブコマンド（一括破棄、再開実行のオプションを含む）を追加する。
3. `terraform/deploy` の `import-data` に、投入前のスキーマ版の照合と、異なる場合のコンソール確認を追加する。
4. `terraform/destroy-all.bat`・`terraform/export-data.bat` を新設する（ADR-0040 の `.bat` → コンテナ内 Python オーケストレータの実行系を踏襲）。
5. `.gitignore` に `terraform/backup/` を追加する。
6. `terraform/README.md` に、一括破棄・再開実行の手順と、退避ファイルからの復旧手順（`apply-all` → `import-data`）を追記する。

### 4.2 対象外

- 退避ファイルの AWS 上（長寿命バケット等）やローカル PC 以外への保管（2.4 節 #1 で確定）。
- 退避ファイルの暗号化・圧縮。
- 退避ファイルの世代管理（複数回分の保持）。最新 1 回分のみを保持する（2.4 節 #5）。前回分を残したい場合は、運用者が次回の退避の前に別の場所へ手でコピーする。
- スキーマ版が異なる環境へ投入するための SQL の自動変換（照合と確認のみ行い、変換はしない）。
- RDS の最終スナップショット（`skip_final_snapshot=false`）の取得。
- database 構成だけが残っている環境からの退避（一時 ECS クラスタの作成等）。2.4 節 #3 のとおりメッセージを出して終える。
- `destroy-app`・`destroy-database` 単独実行時の動作変更（単独実行には退避を付けない）。

## 5. 全体アーキテクチャ

### 5.1 実行フロー（通常実行）

```
destroy-all.bat
  └ deploy destroy-all
      [0] 前提確認: 両構成の state にリソースがある / ECS クラスタが存在する
            → app 構成が無い場合はメッセージを表示して終了（F-8）
      [0] 実行内容の表示 → 'destroy-all' のタイプ確認（1 回のみ）
      [1] 退避エクスポート
          1-1 集約サービスを停止（desired_count=0, 安定待機）     … 書き込みを止めてから取る
          1-2 db_init を EXPORT_MODE で run-task
                → 両 DB の対象テーブルを SQL 化し import バケットの export/<ts>/ へ保存
                → 各ファイルの SHA-256・行数・スキーマ版を export/<ts>/manifest.json へ保存
          1-3 exitCode=0 を確認
          1-4 export/<ts>/ をローカルの一時ディレクトリ terraform/backup/.incoming/ へダウンロード
          1-5 一時ディレクトリのファイルの SHA-256 をマニフェストと照合
          1-6 照合に成功したら terraform/backup/ の 3 ファイルを一時ディレクトリの内容で置き換える（前回分はここで消える）
          （1-2〜1-6 のいずれかが失敗 → 前回分の退避ファイルはそのまま残し、集約サービスを元の desired_count へ戻して終了。②③ は実行しない）
      [2] destroy-app 相当（タイプ確認なし）
          （失敗 → ここで終了。再開コマンド「--resume-from destroy-app」を表示）
      [3] destroy-database 相当（タイプ確認なし）
          （失敗 → ここで終了。再開コマンド「--resume-from destroy-database」を表示）
      [完了] 退避ディレクトリのパスと復旧手順を表示
```

### 5.2 実行フロー（再開実行）

```
destroy-all.bat --resume-from destroy-app|destroy-database
  └ deploy destroy-all --resume-from ...
      [0] 退避ファイルの再検証（terraform/backup/）: ローカルの SHA-256 をローカルのマニフェストと照合 /
          マニフェストの AWS アカウント・リージョンが現在の .env と一致
      [0] 再開段に応じた前提確認（F-26）
      [0] 退避ファイルの取得日時・行数・実行する段の表示 → 'destroy-all' のタイプ確認
      [2] destroy-app 相当       … --resume-from destroy-app のときのみ
      [3] destroy-database 相当
```

### 5.3 コマンドと実行タスクの対応

| コマンド | 破壊的 | 確認 | 使う ECS タスク | ローカル出力 |
|---|---|---|---|---|
| `export-data`（新設） | いいえ（ただし実行中は集約サービスを停止する） | `y/N`（`--yes` で省略可） | `db_init_task_family`（EXPORT_MODE） | `terraform/backup/`（上書き） |
| `destroy-all`（新設） | はい | `'destroy-all'` のタイプ確認（`--yes` なし） | 同上（再開実行時は使わない） | 同上（再開実行時は出力しない） |
| `import-data`（既存・照合を追加） | はい | 既存のクラスタ名タイプ確認に加え、スキーマ版が異なる場合は `y/N` 確認 | `db_init_task_family`（EXPORT_MANIFEST_ONLY → IMPORT_MODE） | なし |
| `destroy-app`（既存・変更なし） | はい | `'destroy-app'` のタイプ確認 | なし | なし |
| `destroy-database`（既存・変更なし） | はい | `'destroy-database'` のタイプ確認 | なし | なし |

## 6. 機能要件

### 6.1 `db_init` への EXPORT_MODE 追加

| # | 要件 |
|---|---|
| F-1 | `EXPORT_MODE=true`（真偽値判定は `IMPORT_MODE`・`QUERY_MODE` と同じ）で起動したとき、通常のマイグレーション・シードを一切実行せず、退避エクスポートのみを行って終了する。他のモード（`IMPORT_MODE`・`QUERY_MODE`・`MIGRATE_ONLY`）と同時に指定された場合はエラー終了する。 |
| F-2 | `knowledge`・`conversation` の両データベースについて、対象テーブルの全行を SQL 化する。生成ロジックは ADR-0066 の `build_backup_sql`（先頭に `TRUNCATE ... RESTART IDENTITY CASCADE`、続けて親→子順の 500 行単位マルチ行 `INSERT`、`embedding` は pgvector 文字列リテラル）を流用し、形式を揃える。 |
| F-3 | 1 データベースの全テーブルを、1 つの `REPEATABLE READ READ ONLY` トランザクション内で読み出す（テーブル間で同一時点のスナップショットにする）。 |
| F-4 | 各データベースの `public` スキーマに、対象テーブルにも yoyo 管理テーブル（`_yoyo_*`・`yoyo_lock`）にも含まれないテーブルが存在する場合は、エクスポートを失敗させる（対象リストの更新漏れによるデータ欠落を伴う破棄を防ぐ）。 |
| F-5 | 生成した SQL を import バケットの `export/<ts>/knowledge.sql`・`export/<ts>/conversation.sql` へ保存する。`<ts>` は run-task の環境変数 `EXPORT_TIMESTAMP` で受け取る（オーケストレータがどの実行の成果物を取得するかを特定し、マニフェストの取得日時と一致させるため）。 |
| F-6 | `export/<ts>/manifest.json` に、取得日時・データベースごとのファイル名・バイト数・SHA-256・テーブルごとの行数・スキーマ版を保存する。 |
| F-7 | 接続には migrator ロールの接続（IMPORT_MODE と同じ）を用いる。書き込みは行わない。 |
| F-7a | `EXPORT_MANIFEST_ONLY=true` を併せて指定したときは、SQL を生成せず、スキーマ版とテーブルごとの行数だけを記録したマニフェストを `export/<ts>/manifest.json` へ保存する（6.5 節の照合用）。 |

### 6.2 `export-data` サブコマンド

| # | 要件 |
|---|---|
| F-8 | 前提確認: database・app 両構成の state にリソースが存在し、app 構成の `cluster_name` が取得できること。app 構成が無い（state が無い、リソースが空、またはクラスタ名を取得できない）場合は、次の趣旨のメッセージを表示し、何も変更せずに終了する（終了コードは非 0）。<br>「app 構成が存在しないため、データを退避できません（退避用のタスクは app 構成の ECS クラスタで実行します）。データの退避が不要なら `destroy-database.bat` を実行してください。退避が必要なら `apply-app.bat` を実行してから、もう一度このバッチを実行してください。」<br>database 構成が無い場合は、退避・破棄の対象が無い旨を表示して終了する。 |
| F-9 | 実行前に、対象（両 DB）・保存先ディレクトリ・集約サービスを一時停止する旨を表示する。`terraform/backup/` に前回の退避ファイルがある場合は、その取得日時・環境（アカウント・クラスタ名）・行数を示し、「成功すると上書きされて消える」旨を表示する。そのうえで `y/N` 確認を行う（`--yes` で省略可）。 |
| F-10 | 集約サービスを `desired_count=0` にして安定待機してから EXPORT_MODE の run-task を起動し、`exitCode=0` を確認する。CloudWatch Logs のテーブルごとの行数をそのまま画面に表示する。 |
| F-11 | `export/<ts>/` 配下（2 SQL + マニフェスト）を一時ディレクトリ `terraform/backup/.incoming/` へダウンロードし、各 SQL のローカル SHA-256 とマニフェストの値が一致することを確認する。不一致・欠落はエラー終了とし、その場合 `terraform/backup/` の前回分には手を付けない。 |
| F-11a | 照合に成功したら、`terraform/backup/` の `knowledge.sql`・`conversation.sql`・`manifest.json` を一時ディレクトリの内容で置き換え、一時ディレクトリを削除する。3 ファイルは常に同じ回の退避でそろえる（一部だけ新しい状態を残さない）。前回の一時ディレクトリが残っていれば、実行開始時に削除する。 |
| F-12 | ローカルのマニフェストに、実行環境の情報（AWS アカウント ID・リージョン・クラスタ名・実行時の git コミット）を追記する。 |
| F-13 | 成功・失敗にかかわらず、集約サービスを停止前の `desired_count` へ戻して安定待機する（`import-data` の `finally` と同じ扱い）。 |

### 6.3 `destroy-all` サブコマンド（通常実行）

| # | 要件 |
|---|---|
| F-14 | 前提確認は F-8 と同じ（メッセージ中のバッチ名は `destroy-all.bat`）。満たさない場合は ②③ も含めて何も実行せずに終了する（退避なしに破棄へ進む経路を設けない）。 |
| F-15 | 実行前に、退避先（前回の退避ファイルが上書きされる旨を F-9 と同じく含む）・破棄対象（app 構成・database 構成の内容、`destroy-app`・`destroy-database` が表示している警告文と同じ内容）・取り消し不可である旨を表示し、`'destroy-all'` のタイプ確認を **1 回だけ** 行う。`--yes` による省略は設けない。 |
| F-16 | ① 退避エクスポートは F-10〜F-12（F-11a を含む）と同じ処理を行う。ただし、集約サービスの復元（F-13）は **① が失敗した場合のみ** 行う（成功時は直後に破棄するため戻さない）。 |
| F-17 | ① が失敗した場合は ②③ を実行せずにエラー終了する。この場合は何も破棄されておらず、前回の退避ファイルも上書きされていないため、再開オプションなしで再実行すればよい旨を表示する。 |
| F-18 | ② は `cmd_destroy_app` と同じ処理（`app_desired_count=0` で `terraform destroy`）を、タイプ確認なしで行う。失敗した場合は ③ を実行せずにエラー終了し、退避ディレクトリのパスと再開コマンド（`destroy-all.bat --resume-from destroy-app`）を表示する。 |
| F-19 | ③ は `cmd_destroy_database` と同じ処理（RDS インスタンスのみ削除保護解除 → `terraform destroy`）を、タイプ確認なしで行う。失敗した場合は退避ディレクトリのパスと再開コマンド（`destroy-all.bat --resume-from destroy-database`）を表示する。 |
| F-20 | 完了時、退避ディレクトリのパス・各ファイルのサイズと行数・復旧手順（`apply-all` → `import-data --knowledge-sql backup\knowledge.sql --conversation-sql backup\conversation.sql`）と、「退避ファイルは次回の `export-data`・`destroy-all` で上書きされるため、復旧が済むまで退避を実行しないこと」を表示する。 |
| F-21 | 既存の `cmd_destroy_app`・`cmd_destroy_database` は、タイプ確認の有無だけを引数で切り替えられるようにして再利用する。単独実行時の動作（確認文言・処理内容）は変えない。 |

### 6.4 `destroy-all` サブコマンド（再開実行）

| # | 要件 |
|---|---|
| F-22 | オプション `--resume-from {destroy-app,destroy-database}` を受け付ける。指定した段から最後の段までを実行し、① 退避エクスポートは実行しない。 |
| F-23 | 再開の根拠とする退避ファイルは、`terraform/backup/` の現在の内容（直前の退避）とする。ディレクトリを指定するオプションは設けない。 |
| F-24 | 再開実行の前に、退避ディレクトリについて次を確認する。いずれかを満たさない場合は、何も破棄せずにエラー終了する。<br>・`knowledge.sql`・`conversation.sql`・`manifest.json` がそろっている<br>・各 SQL の SHA-256 がマニフェストの値と一致する<br>・マニフェストの AWS アカウント ID・リージョンが現在の `.env` の値と一致する |
| F-25 | 確認画面に、退避ファイルの取得日時・環境（クラスタ名）・テーブルごとの行数・これから実行する段を表示し、`'destroy-all'` のタイプ確認を 1 回行う（`--yes` なし）。退避ファイルが取得されてから破棄までの間に書き込まれたデータは含まれない旨も表示する。 |
| F-26 | 段ごとの前提確認は次のとおりとする。<br>・`--resume-from destroy-app`: app 構成の state にリソースが無ければ、「app 構成は破棄済みです。`--resume-from destroy-database` で再実行してください」と表示して終了する。<br>・`--resume-from destroy-database`: app 構成の state にリソースが残っていれば、「app 構成が残っています。`--resume-from destroy-app` で再実行してください」と表示して終了する。database 構成の state が空なら、破棄済みである旨を表示して正常終了する。 |
| F-27 | 再開実行中に失敗した場合の表示は F-18・F-19 と同じ。再開実行では退避を行わないため、`terraform/backup/` は変更しない。 |

### 6.5 `import-data` へのスキーマ版照合の追加

| # | 要件 |
|---|---|
| F-28 | 投入ダンプ（`--knowledge-sql`・`--conversation-sql`、または既定の `terraform/knowledge.sql`・`terraform/conversation.sql`）と同じディレクトリに `manifest.json` がある場合、そのマニフェストに記録されたスキーマ版を「退避時のスキーマ版」とする。 |
| F-29 | 投入先のスキーマ版は、`db_init` を `EXPORT_MODE` + `EXPORT_MANIFEST_ONLY` で run-task 起動して取得する。この取得は、既存のクラスタ名タイプ確認・S3 アップロード・サービス停止より前に行う。 |
| F-30 | 対象データベースごとに、退避時と投入先のスキーマ版を比較する。一致すれば何も表示せず次へ進む。 |
| F-31 | 一致しない場合は、対象データベース名・退避時にだけ適用されているマイグレーション ID・投入先にだけ適用されているマイグレーション ID を表示し、「スキーマ版が異なります。このまま SQL を実行しますか？（列が合わない場合は投入が失敗し、データは投入前の状態に戻ります）[y/N]」とコンソールで確認する。`y` 以外なら、何も変更せずに終了する（終了コード 0）。 |
| F-32 | マニフェストが無い場合（管理 UI のエクスポートで作ったダンプ等）は、「スキーマ版を確認できません」と表示し、F-31 と同じ `y/N` 確認を行う。 |
| F-33 | F-31・F-32 の確認は `--yes` 等で省略できないものとする（`import-data` は元々確認省略の手段を持たない）。 |

| F-34 | `terraform/destroy-all.bat`・`terraform/export-data.bat` は既存バッチと同じ構成（`cmd /k` による再起動でウィンドウを開いたままにする、`deploy\run.bat` 呼び出し）とし、引数（`%*`）をそのまま渡す。コメント・`echo` は英語で書く（CP932 文字化け回避）。`destroy-all.bat` のコメントに再開オプションの使い方を書く。 |

## 7. 退避ファイル要件

| # | 要件 |
|---|---|
| D-1 | 退避ディレクトリ: `terraform/backup/`（固定）。中身は `knowledge.sql`・`conversation.sql`・`manifest.json` の 3 ファイル。取得日時はファイル名ではなくマニフェストに記録する。 |
| D-2 | SQL の文字コードは UTF-8（BOM なし）、改行は LF。 |
| D-3 | SQL はそのまま `import-data` の投入ダンプとして使える（`TRUNCATE` + `INSERT` の形式は `import-data` が 1 トランザクションで適用でき、シーケンスは `import-data` 側で同期される）。また `psql -f` で直接適用しても退避時点の状態に戻せる。 |
| D-4 | 退避ファイルの保存先は運用者の PC のみとする。`terraform/backup/` は Git 管理外とする。 |
| D-5 | 退避ファイルは次回の退避（`export-data`・`destroy-all` の ①）が成功した時点で、3 ファイルまとめて上書きされる。これにより、会話ログを含む `conversation.sql` は次回の退避までの間だけ PC に残る（2.4 節 #5）。次回の退避が失敗した場合は、前回分をそのまま残す。退避以外のコマンド（`import-data`・再開実行など）は `terraform/backup/` を変更しない。 |
| D-6 | 退避ファイルのうち `conversation.sql` は、会話ログ（利用者の質問文・回答文・評価コメント）を含む。`knowledge.sql` は QA・タグ等のナレッジデータで、会話ログは含まない。`manifest.json` は件数・ハッシュ等のみで、データ本体は含まない。 |

## 8. 非機能要件

| 区分 | 要件 |
|---|---|
| 安全性 | 退避の成功（exitCode=0・ローカル保存・SHA-256 照合）を確認するまで、いかなる破棄処理も開始しない。再開実行では、ローカルの退避ファイルの再検証に成功するまで破棄処理を開始しない。 |
| 安全性 | 破棄に進む確認は `'destroy-all'` のタイプ確認 1 回とし、確認文言で実行する段（退避 → app 破棄 → database 破棄、または再開時はその一部）をすべて明示する。 |
| 整合性 | 退避中は集約サービス（`web_backend`・`knowledge_mcp`・`tag_selector_mcp`・`agent_invitro`）を停止し、退避後〜破棄までの書き込みによるデータ欠落を防ぐ。 |
| 可観測性 | 各段（[0/3]〜[3/3]）の開始・完了を画面に出す。失敗時は、どの段で止まったか・AWS 上に何が残っているか・次に実行すべきコマンド（再開コマンドを含む）を表示する。 |
| 性能 | 現行データ規模で退避エクスポートが 5 分以内に終わること（`wait_task_stopped` の既定タイムアウト 30 分以内）。`db_init` タスクのメモリに SQL 全体を載せる方式（ADR-0066 の退避と同じ）であり、データ量の増加で不足する場合は見直す。 |
| 権限 | 運用者の AWS 認証情報に、import バケットの `s3:GetObject`・`s3:ListBucket` が必要（`import-data` は `PutObject` のみ使用）。`db_init` タスクロールは既に import バケットの `GetObject`/`PutObject`/`ListBucket` を持つため、Terraform の変更は不要。 |
| 機微情報 | `conversation.sql` は会話ログを含む。保管期間は「次回の退避で上書きされるまで」とし、別の場所へのコピーは行わない運用とする（D-5）。 |

## 9. 既存システムとの関係・影響範囲

- `db_init/src/main.py`: 起動モード分岐に `EXPORT_MODE` を 1 つ追加する。`import_data.py` の退避 SQL 生成関数を、ヘッダー文言（ADR-0066 rollback → ADR-0103 export）を引数で切り替えられるようにして共用する。
- `terraform/deploy/src/aws.py`: S3 プレフィックス配下のダウンロード関数を追加する。
- `terraform/deploy/src/commands.py`: `cmd_export_data`・`cmd_destroy_all` を追加し、`cmd_destroy_app`・`cmd_destroy_database` にタイプ確認をスキップする引数を追加する（既定値は現行動作）。`cmd_import_data` に、スキーマ版の取得・照合・確認の処理を追加する（投入処理そのものは変えない）。
- `terraform/deploy/src/__main__.py`: `export-data`（`--yes` あり）・`destroy-all`（`--resume-from`、`--yes` なし）サブコマンドを追加する。
- `import-data` は、照合用の run-task が 1 回増えるため、実行時間が数十秒〜1 分程度延びる。
- Terraform のリソース定義・IAM・ECS タスク定義は変更しない。
- 画面の追加・変更はないため、画面遷移図の更新は不要。

## 10. 受け入れ基準（Definition of Done）

- [ ] `export-data.bat` を実行すると `terraform/backup/` に `knowledge.sql`・`conversation.sql`・`manifest.json` が作られ、マニフェストの行数が各テーブルの `SELECT COUNT(*)` と一致する。
- [ ] `export-data` 実行後、集約サービスが元の `desired_count` で稼働している（成功時・失敗時とも）。
- [ ] `export-data.bat` を 2 回実行すると、`terraform/backup/` には 2 回目の 3 ファイルだけが残り、前回分（`conversation.sql` を含む）は残らない。
- [ ] 2 回目の退避を失敗させた場合（例: 対象外テーブルを作る）、`terraform/backup/` には 1 回目の 3 ファイルがそのまま残る。
- [ ] `destroy-all.bat` を実行し、`'destroy-all'` 以外を入力すると何も変更されずに終了する。
- [ ] `destroy-all.bat` を実行すると、退避 → app 破棄 → database 破棄が順に行われ、終了後に app・database 両構成の state にリソースが残らない。
- [ ] EXPORT_MODE のタスクを意図的に失敗させた場合（例: 対象外テーブルを作る）、app・database のどちらも破棄されず、集約サービスが元の状態に戻る。
- [ ] app 構成を破棄済みの環境で `destroy-all.bat`・`export-data.bat` を実行すると、F-8 のメッセージが表示され、何も変更されずに終了する。
- [ ] ② の失敗を模擬した後、表示された再開コマンド（`--resume-from destroy-app`）で再実行すると、退避を取り直さずに ②③ が完了する。③ の失敗後の `--resume-from destroy-database` も同様に完了する。
- [ ] 再開実行で、退避ファイルを 1 バイト書き換えた場合、またはマニフェストのアカウント ID が `.env` と異なる場合、何も破棄されずにエラー終了する。
- [ ] `--resume-from destroy-database` を app 構成が残っている状態で実行すると、F-26 のメッセージで終了する。
- [ ] `destroy-all` で得た退避ファイルを使い、`apply-all` → `import-data` で再構築した環境のデータ件数が、退避時のマニフェストの行数と一致する（スキーマ版が同じ場合、確認なしで進む）。
- [ ] マイグレーションを 1 つ追加した環境に対して `import-data` を実行すると、差分のマイグレーション ID と `y/N` 確認が表示され、`N` で何も変更されずに終了し、`y` でそのまま投入が実行される。
- [ ] マニフェストの無いダンプで `import-data` を実行すると、「スキーマ版を確認できません」と `y/N` 確認が表示される。
- [ ] `destroy-app.bat`・`destroy-database.bat` の単独実行時の確認文言・動作が変わっていない（回帰確認）。
- [ ] `terraform/backup/` 配下のファイルが `git status` に表示されない。
- [ ] `terraform/deploy/tests` に、`destroy-all` の段の順序と失敗時の停止（① 失敗で ②③ が呼ばれない、② 失敗で ③ が呼ばれない）、再開実行の段の選択と退避ファイル再検証、SHA-256 不一致での停止、`import-data` のスキーマ版比較を確認する単体テストを追加し、通る。
