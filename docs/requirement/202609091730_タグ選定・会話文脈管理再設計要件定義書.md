# タグ選定・会話文脈管理 再設計 要件定義書

- 文書番号: REQ-202609091730
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `tag_selector_mcp`（`RetrievalEngine`・`InferenceEngine`・`SelectTagsUseCase`・`mcp/schemas.py`）, `agent_invitro`（`main/api/server.py`・`tags.py`・新設する言い換えモジュール）, `web_backend`（`main/controllers/chat_controller.py`）, `front_dev`（`StateContainer.tsx`・`domain/stateless/{request,response}.ts`）
- 変更なしのコンポーネント: `knowledge_mcp`（`search_knowledge`のツール契約自体は変更しない）, `tag`/`tag_alias`/`tag_folder`のスキーマ（列追加なし）, `troubleshooting_article`系テーブル
- 参照資料: ADR-0009（タグ選択アルゴリズム）, ADR-0011（タグ知識ベースのキャッシュ方針）, ADR-0043（`agent_invitro`ステートレス方式）, ADR-0056（会話タグのクライアントエコー方式）, ADR-0057（会話タグの検索反映・継続判定）, ADR-0058（祖先タグ展開）, ADR-0059（タグ構成類似度スコアリング）, ADR-0062（タグ検索の単一呼び出し簡素化）, ADR-0076/0078（トラブルシューティング情報源）, `docs/requirement/202609091119_タグエイリアス管理機能要件定義書.md`
- 前提の決定事項: 本書に対応するADRはADR-0084〜ADR-0086（17章参照）。本書は2026-09-09のセッションにおける発注者との協議（`conversation.sql`の実データに基づく不具合再現・アーキテクチャレビューを含む）を踏まえて起票する。

## 1. 目的

チャットボットへの質問「アクセス可能なプロテクトキーが見つかりませんというエラーが出ます。」に対し、本来一意に定まるはずの`ContainerNotFound`タグではなく`認証`/`ローカル認証`/`起動エラー`という不正確なタグが選定される不具合が確認された（2章参照）。この不具合の原因調査を通じて、「タグ」という単一の仕組みに（1）会話文脈の管理、（2）検索のための表記ゆれ正規化、（3）QA・記事間の構造化、という性質の異なる3つの責務が同居しており、これが表記ゆれ正規化の責務（決定論的に効くべきAlias一致が実質的に機能していない）を弱めている、という構造的な問題であることが判明した。

本書は、この3責務を整理し直し、（1）会話文脈の管理は既存の`summary`（会話要約）方式に一本化する、（2）表記ゆれ正規化のうち既知パターンは`tag_alias`による決定論的な確定として扱う、（3）構造化（タグ階層・多重タグ付け）は現状を維持する、という方針のもとで`tag_selector_mcp`・`agent_invitro`を再設計するための要件を定義する。

## 2. 背景・調査結果

### 2.1 不具合の再現と原因

`terraform/conversation.sql`（会話DBダンプ）を確認したところ、以下が確認された。

| 質問文 | 選定されたタグ（score） |
|---|---|
| 「維津美の認証でContainerNotFoundのエラーが出ます。」 | ContainerNotFound(1.0), 認証(0.8) |
| 「維津美の認証でコンテナノットファウンドのエラーが出ます。」 | ContainerNotFound(0.95), 認証(0.9) |
| 「アクセス可能なプロテクトキーが見つかりませんというエラーが出ます。」 | 認証(0.9), ローカル認証(0.7〜0.8), 起動エラー(0.6〜0.7) — **ContainerNotFoundは候補にも挙がらない** |

`data/trouble_shooting.html`を確認すると、「アクセス可能なプロテクトキーが見つかりません」は`troubleshooting_article`テーブルの`error_message`列に格納されている、`ContainerNotFound`という事象に付随する固定のエラー文言そのものであることが分かった（当該記事は`tag=["認証","ネットワーク認証","ContainerNotFound"]`で分類済み）。

`tag_selector_mcp`のコード（`RetrievalEngine`/`InferenceEngine`, ADR-0009）を確認した結果、原因は次の通りと判明した。

1. `RetrievalEngine.find_tags_by_alias_match()`は`tag_alias`テーブルとの部分一致で「確定タグ」を検出する仕組みを持つが、現状の`tag_alias`は`db_hiroba_qa_init/src/seed_description_and_aliases.py`に置かれた暫定的な少数エントリに限られ、当該の固定エラー文言は登録されていない。
2. たとえAlias一致で「確定」しても、`InferenceEngine._build_prompt()`はこれをLLMへの参考情報（「既に同義語辞書との一致により確定しているタグ」という文言）として渡すのみであり、最終的な選定・スコアはLLMの推論任せである。コード上で確定タグを最終結果へ強制採用する仕組みは存在しない。
3. `troubleshooting_article.error_message`という、まさに今回のような固定文言を構造化して保持する列が既に存在するにもかかわらず、`tag_selector_mcp`はこのテーブルを一切参照しない。また`search_knowledge`側（ADR-0078）でも、`error_message`は埋め込み対象テキストから意図的に除外されている。

### 2.2 タグに同居する3つの責務

発注者との協議により、「タグ」という仕組みには性質の異なる3つの責務が同居していることが整理された。

1. **会話文脈の管理**: 「認証がうまくいきません→ネットワーク認証です→XXXという条件です」のような複数ターンにわたる文脈を圧縮して保持する責務。現状は`agent_invitro`の「会話タグ」（ADR-0056/0057、クライアントエコー方式・`missed_turns`による継続判定）が担っているが、同じ`agent_invitro`には`summary`（会話要約）という、同一の設計思想（クライアントエコー方式）に基づく別の状態量が既に存在し、責務が重複している。両者は下流の用途（`summary`→回答生成コンテキスト、会話タグ→`search_knowledge`の`tags`引数）こそ分離されているが、「会話状態を圧縮して持ち回す」という実装パターンの重複、および「静的なタクソノミーの語彙（`tag_id`）を動的なセッション状態の表現に転用している」という設計上のねじれを抱えている。
2. **検索のための正規化（表記ゆれ対応）**: 「測量について」「測量業務について」「そくりょうについて」のような表記ゆれを吸収する責務。embedding（統計的・確率的、`search_knowledge`）と`tag`/`tag_alias`（人間が明示的に登録する決定論的な同義語辞書、本来`RetrievalEngine`が担うべき層）の両方が関与するが、2.1節で述べた通り、決定論的であるべき`tag_alias`側が実質的に機能しておらず、確率的なLLM推論に一元化されてしまっている。
3. **QA・記事間の構造化**: 「`ContainerNotFound`はネットワーク認証の文脈でのみ存在する」というドメイン知識を、タグの親子関係（`tag.parent_tag_id`）と多重タグ付け（`hiroba_qa_tag`/`troubleshooting_article_tag`）で表現する責務。ADR-0058の祖先タグ展開により`search_knowledge`側で実際に活用されており、この責務についてはタグという仕組みが適切に機能している。

本書は、上記のうち1・2の責務の混在を解消することを目的とする。3（構造化）については現状の設計を維持し、変更を加えない。

### 2.3 タグ知識ベースの成熟に伴うADR-0009の前提の陳腐化（参考情報）

ADR-0009（2026-08-05）は「タグ件数は数十件程度」「`parent_tag_id`は全件NULL」という前提のもとEmbedding層・階層探索を見送った。しかし`tags.csv`・`conversation.sql`の実データを確認すると、現在は「維津美V7 › 認証 › ネットワーク認証 › ContainerNotFound」のような多段階層が実際に運用されており、`parent_tag_id`も埋まっている。この前提の変化そのものへの対応（Embedding絞り込み層の追加や、`InferenceEngine`のプロンプトへの階層情報付与等）は本書のスコープ外とし、将来の別途検討事項として15章のOpen Issueに記録する。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| 会話タグ | ADR-0056/0057で導入された、クライアントエコー方式・`missed_turns`継続判定による会話状態としてのタグ集合。本書で廃止する。 |
| 未要約履歴 | `Summary.summarized_upto`より`order`が大きい`messages`。まだ要約に畳み込まれていない直近のメッセージ。 |
| 言い換え質問（`condensed_query`） | 要約・未要約履歴・今回の発話から、LLMにより生成される、単体で意味が通るstandaloneな質問文。 |
| alias一致対象テキスト | `RetrievalEngine`のAlias部分一致判定に使う生テキスト。本書では「今回の発話＋未要約履歴のうちuser発話」と定義する。 |
| 確定タグ | alias一致対象テキストに含まれる`tag_alias.alias`から特定される、`select_tags`が最終結果へ確実に含めるタグ。 |

## 4. スコープ

### 4.1 対象範囲

1. `agent_invitro`に、要約・未要約履歴・今回の発話から言い換え質問（`condensed_query`）を生成するLLM呼び出しを新設する（8章）。
2. `tag_selector_mcp`の`select_tags`ツールに、alias一致専用の入力（alias一致対象テキスト）を受け取れるよう拡張し、確定タグを最終結果へ決定論的に含める（9章）。
3. `agent_invitro`から`tag_selector_mcp`・`knowledge_mcp`への呼び出しを、`condensed_query`とalias一致対象テキストを使う新しいフローへ更新する（8章）。
4. 会話タグ機構（ADR-0056/0057）を廃止し、`Request`/`Response`契約から`tags`フィールドを削除する。会話文脈の管理は`summary`に一本化する（7章）。

### 4.2 対象外

- タグの親子階層（`tag.parent_tag_id`）・多重タグ付けの仕組み自体の変更（2.2節の責務3、現状維持）。
- `tag_selector_mcp`のEmbedding絞り込み層の追加、`InferenceEngine`プロンプトへのタグ階層情報の付与（2.3節、将来の別途検討事項）。
- `troubleshooting_article.error_message`から`tag_alias`を自動導出する仕組み（本書はAlias一致の「確定タグとしての扱い方」を再設計するものであり、Aliasデータそのものの拡充・自動化は別途、タグエイリアス管理機能（REQ-202609091119）の運用、または将来の要件として扱う）。
- 要約済み（圧縮済み）の履歴に含まれていた固定エラー文言をalias一致で拾えるようにすること。この制約は6.3節の通り許容事項として明記する。
- 未要約履歴のうちassistant発話をalias一致対象に含めること（6.2節、user発話のみを対象とする）。

## 5. 全体アーキテクチャ

### 5.1 現状（変更前）

```
agent_invitro（/ask-pipeline）
  ├─ select_tags(query=req.text)                      … 今回の発話のみを見る
  ├─ compute_conversation_tags(new_tags, req.tags)     … missed_turnsによる継続判定
  ├─ search_with_merged_tags(query=req.text, tags=…)   … 今回の発話のみを見る
  └─ generator.generate(context, req.text, summary, history)
```

### 5.2 変更後

```
agent_invitro（/ask-pipeline）
  ├─ 未要約履歴の算出: [m for m in messages if m.order > summary.summarized_upto]
  ├─ alias一致対象テキストの構築: req.text + 未要約履歴のうちrole="user"のcontent
  ├─ condense(summary.content, 未要約履歴, req.text) → condensed_query      … 新設（8章）
  ├─ select_tags(query=condensed_query, alias_match_text=alias一致対象テキスト)  … 拡張（9章）
  │     └─ RetrievalEngine: alias_match_textから確定タグを検出
  │     └─ InferenceEngine: condensed_query＋タグ一覧＋確定タグでLLM推論、確定タグは結果へ強制採用
  ├─ search_knowledge(query=condensed_query, tags=select_tagsの結果)         … 単一呼び出し（ADR-0059/0062は変更なし）
  └─ generator.generate(context, req.text, summary, history)                … 変更なし
```

`Response.tags`（会話タグ）は廃止する。`front_dev`・`web_backend`は`tags`フィールドの送受信を行わなくなる。

## 6. 機能要件

### 6.1 言い換え質問（`condensed_query`）の生成

- 入力: `summary.content`（既存の要約）、未要約履歴（`role`・`content`の列）、`req.text`（今回の発話）。
- 出力: 単体で意味が通る、standaloneな日本語の質問文1件。
- 生成失敗時（LLM呼び出し例外等）は`req.text`をそのまま`condensed_query`として使う（`summarize.py`の既存フォールバック方針を踏襲）。
- 詳細な実装方式（プロンプト・モジュール配置）はADR-0085で定める。

### 6.2 alias一致対象テキストの構築

- `req.text`（今回の発話）＋未要約履歴のうち`role="user"`の`content`を対象とする。`role="assistant"`のメッセージは対象外とする（発注者確認済み）。
- 未要約履歴の`user`メッセージの`content`は、`web_backend`（`chat_controller.py`の`ask()`）・`agent_invitro`（`_ask_impl`）のいずれも、最初のターンから例外なく「参考情報:\n{context}\n\n質問:\n{req.text}」という固定テンプレートで構築されている。素の発話だけが入った`user`メッセージは履歴上に存在しない（12章 Open Issue #1）。`req.text`の値は必ず固定文字列`"質問:\n"`の直後から末尾までに現れるため、alias一致対象テキストの構築時は、各`user`メッセージの`content`から`"質問:\n"`以降の部分文字列を抽出したものを対象とする（`"質問:\n"`が見つからない場合は`content`全文を対象とする、旧形式データ・想定外フォーマットへのフォールバック）。

### 6.3 alias一致の範囲と許容する制約

- 要約済み（`summary.summarized_upto`以下の`order`を持つ）履歴に含まれていた固定エラー文言は、要約によって自由文へ変換されるため、alias一致の対象にならない。この制約は発注者確認済みの許容事項とし、README等の運用ドキュメントに明記する。

### 6.4 確定タグの決定論的採用

- `RetrievalEngine.find_tags_by_alias_match(alias_match_text)`で検出された確定タグは、`InferenceEngine`のLLM推論結果によらず、`select_tags`の最終結果へ必ず含める。スコアは固定値`1.0`とする。
- `confidence_threshold`は確定タグには適用しない（決定論的シグナルのため、閾値によるフィルタの対象外とする）。
- 最終結果は「確定タグ（スコア1.0、`id`昇順）＋確定タグに含まれないLLM選定タグ（スコア降順、`confidence_threshold`適用）」を結合し、`max_tags`件に切り詰める。確定タグの件数が`max_tags`を超える場合は、確定タグを優先し全件を含める（`max_tags`は超過してよい。決定論的シグナルを`max_tags`により恣意的に間引くべきではないため）。
- 詳細な意思決定・代替案検討はADR-0086で定める。

### 6.5 会話タグ機構の廃止

- `front_dev`: `StateContainer.tsx`の`tags` React state、`ConversationTag`型、`Request.tags`/`Response.tags`の送受信を削除する。
- `web_backend`: `chat_controller.py`の`Request`/`Response`Pydanticモデルから`tags`フィールドを削除する。
- `agent_invitro`: `main/api/server.py`の`Request`/`Response`モデルから`tags`フィールドを削除する。`tags.py`の`compute_conversation_tags`/`TagState`/継続判定ロジックを削除し、`search_with_merged_tags`は「その場で得たタグ集合をそのまま渡す」形（実質、5.2節の新フローに置き換え）に整理する。`_extract_selected_tags`/`_mcp_result_to_dicts`（MCP戻り値の正規化ヘルパー、ADR-0063由来）は`select_tags`の呼び出しに引き続き必要なため残す。
- 詳細な意思決定・代替案検討はADR-0084で定める。

## 7. データ・API仕様変更

### 7.1 `select_tags`（`tag_selector_mcp`）入力スキーマの拡張

```
SELECT_TAGS_INPUT_SCHEMA:
  query: string（必須。LLM推論に使う言い換え質問）
  alias_match_text: string（任意。省略時はqueryと同じ値を使う。後方互換のため）
  max_tags: integer（既定3、変更なし）
  confidence_threshold: number（既定0.0、変更なし。確定タグには適用されない点が仕様変更）
```

`alias_match_text`を省略時は`query`にフォールバックすることで、既存の呼び出し元（検証機能等、ADR-0049/0060）への互換性を保つ。

### 7.2 `agent_invitro`/`web_backend`/`front_dev`のRequest/Response契約

`tags`（`ConversationTag`）フィールドを`Request`/`Response`双方から削除する。既存のAWS環境向け中継処理（`web_backend`の`AGENT_INVITRO_URL`設定時のパススルー）も、このフィールドを扱わなくなる。

## 8. 言い換え質問生成の実装方式（概要）

詳細はADR-0085で定めるが、`agent_invitro/src/summarize.py`と同型の構成（Bedrock `converse` API、プロンプト定数を自己完結で保持）を踏襲した新規モジュールを想定する。

## 9. alias確定・確定タグ強制採用の実装方式（概要）

詳細はADR-0086で定めるが、`RetrievalEngine`のインターフェース自体は変更せず（`alias_match_text`を受け取れるよう`retrieve()`の引数を拡張）、`InferenceEngine.infer()`の末尾で確定タグを結果へマージする処理を追加する想定である。

## 10. 非機能要件

| 分類 | 要件 |
|---|---|
| 可用性 | 言い換え質問生成（8章）が失敗しても、`req.text`をフォールバックとして処理を継続する（回答生成自体を失敗させない）。 |
| 一貫性 | `condensed_query`は`select_tags`の`query`と`search_knowledge`の`query`の両方に同一の値を使う。 |
| 後方互換性 | `select_tags`の`alias_match_text`は任意パラメータとし、既存呼び出し元（検証機能等）に変更を強制しない。 |
| 監視 | `select_tags`呼び出し時、確定タグとLLM選定タグの内訳をログへ出力し、確定タグが機能しているかを運用側で確認できるようにする（実装フェーズで詳細確定）。 |

## 11. 影響範囲・既存システムとの関係

- `tag_selector_mcp`: `application/retrieval_engine.py`（`retrieve()`の引数拡張）、`application/inference_engine.py`（確定タグの強制採用ロジック追加）、`application/select_tags.py`、`mcp/schemas.py`・`mcp/tools.py`（入力スキーマ拡張）。
- `agent_invitro`: `main/api/server.py`（`_ask_impl`のフロー変更、`Request`/`Response`モデルから`tags`削除）、`tags.py`（継続判定ロジック削除）、新規モジュール（言い換え質問生成）。
- `web_backend`: `main/controllers/chat_controller.py`（`Request`/`Response`モデルから`tags`削除）。
- `front_dev`: `StateContainer.tsx`・`domain/stateless/{request,response}.ts`（`tags`関連の削除）。
- 影響を受けないコンポーネント: `knowledge_mcp`（`search_knowledge`のツール契約自体は変更しない）、`db_hiroba_qa_init`（スキーマ変更なし）。

## 12. Open Issues（要追加確認事項）

1. **（解消済み）未要約履歴の`user`メッセージに混入するRAGコンテキストの扱い**（6.2節）: `web_backend`（`chat_controller.py`）・`agent_invitro`（`server.py`）の実装を確認した結果、`user`メッセージの`content`は最初のターンから例外なく「参考情報:\n{context}\n\n質問:\n{req.text}」という固定テンプレートで構築されており、素の発話のみが入った`user`メッセージは存在しないことが判明した。`req.text`は固定文字列`"質問:\n"`の直後から末尾までに機械的に現れるため、alias一致対象テキストの構築時はこの部分文字列のみを抽出して使う（6.2節に反映済み）。過去に提示された記事の文言を誤ってAlias一致させるリスクを避けられるため、全文を対象にする案は採用しない。
2. **確定タグの件数が`max_tags`を超える場合の扱い**（6.4節）: 本書では「確定タグは全件含め、`max_tags`を超過してよい」としたが、`search_knowledge`呼び出し件数・レイテンシへの影響を実装フェーズで計測し、必要なら上限を別途設ける。
3. **`troubleshooting_article.error_message`からの`tag_alias`自動導出**（4.2節）: 本書のスコープ外としたが、今回の不具合の再発防止（他の64件の記事についても同様の固定文言が拾えるようにする）には、何らかの形でのAlias拡充が別途必要になる。タグエイリアス管理機能（REQ-202609091119）のUIを使った運用者による手動登録で足りるか、自動導出の仕組みが必要かは、運用開始後の状況を見て別途要件化する。
4. **ADR-0009が置いた前提（タグ件数・階層データなし）の陳腐化**（2.3節）: 本書では扱わないが、`InferenceEngine`のプロンプトへのタグ階層情報付与、Embedding絞り込み層の追加は、タグ件数のさらなる増加に応じて別途検討する。

## 13. 受け入れ基準（Definition of Done）

- [ ] 「アクセス可能なプロテクトキーが見つかりませんというエラーが出ます。」という質問に対し、`select_tags`が`ContainerNotFound`を結果に含める（スコア1.0）。
- [ ] 複数ターンにわたる文脈依存の質問（例:「ネットワーク認証です」の後に「XXXという条件です」）に対し、`condensed_query`が文脈を踏まえたstandaloneな質問文になっていることを確認する。
- [ ] `condensed_query`生成が失敗しても、`/ask-pipeline`全体は500エラーにならず、`req.text`をそのまま使って処理が継続する。
- [ ] `Request`/`Response`契約から`tags`フィールドが削除され、`front_dev`・`web_backend`・`agent_invitro`のいずれにも会話タグ関連のコードが残存しない。
- [ ] `select_tags`に`alias_match_text`を渡さない既存呼び出し元（検証機能）が、変更前と同じ結果を返す（後方互換性の確認）。
