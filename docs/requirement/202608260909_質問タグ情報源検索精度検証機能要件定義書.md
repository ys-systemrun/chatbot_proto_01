# 質問→タグ→情報源 検索精度検証機能 要件定義書

- 文書番号: REQ-202608260909
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `front_dev`（新規管理画面）, `web_backend`（新規API・新規MCPクライアント・新規DBアクセス）, `conversation` データベース（新規テーブル4件）, `db_conversation/init.sql`・`db_hiroba_qa_init`（スキーマ適用先の拡張）
- 利用する既存コンポーネント（変更なし）: `tag_selector_mcp`（`select_tags`ツール）, `knowledge_mcp`（`search_knowledge`ツール）
- 参照資料: `docs/requirement/202608051636.md`（Tag Selector MCPサーバ要件定義書）, `docs/requirement/202608041002.md`（Knowledge MCPサーバ要件定義書）, `docs/requirement/202608240949_AWS環境向けChatbotUI・会話評価機能有効化要件定義書.md`
- 前提の決定事項: 本書末尾「13. 関連ADR一覧」参照

## 1. 目的

RAGベースChatbotが質問に対して適切な情報源（QA等のナレッジ）を検索できているかを、担当者がブラウザから確認・記録できるようにする。具体的には、次の3点を一覧で確認できる管理画面と、その結果をDBに保存する機能を追加する。

1. 検証対象として登録した質問文
2. その質問から `tag_selector_mcp`（`select_tags`）が選択したタグ（最終実行時点の結果）
3. その質問・タグから `knowledge_mcp`（`search_knowledge`）が検索した情報源（最終実行時点の結果）

これにより、タグ選定・情報源検索のどちらの段階に精度上の問題があるかを担当者が切り分けて確認できるようにし、タグのalias整備・description整備（既存のタグ管理UI, ADR-0006/0013）や、将来のタグ選択アルゴリズム・検索アルゴリズムの改善（ADR-0009, ADR-0010）の判断材料を蓄積することを目指す。

## 2. 背景・参照資料

- `tag_selector_mcp`は質問文から関連タグを選択する`select_tags`ツールを提供する（`docs/requirement/202608051636.md`、ADR-0007〜0012）。MVPの選択方式はAlias辞書によるルールベース照合＋ローカルLLM/Bedrockによる一段階選択であり（ADR-0009）、Embedding層・階層探索は未実装である。
- `knowledge_mcp`は質問文とタグ・カテゴリでナレッジベース（QA）を意味検索する`search_knowledge`ツールを提供する（`docs/requirement/202608041002.md`、ADR-0001〜0006）。
- 現在、この「質問→タグ選択→タグ・質問を使った検索」という2段パイプラインを通しで確認する手段は存在しない。近い手段として次の2つがあるが、いずれも本書の要件を満たさない。
  - `web_backend/src/main/evaluate.py`（MRR評価スクリプト）: `DB.search_similar`（`chatbot`データベースへの直接クエリによる類似検索）のみを評価対象とし、タグ選択ステップを経由しない。CLIスクリプトであり、結果はCSV出力のみでDBに保存されず、ブラウザからは確認できない。
  - `agent_invitro`（LangGraph ReActエージェント, ADR-0019〜0022）: `select_tags`・`search_knowledge`の両ツールを呼び出す能力を持つが、どのツールをどの順で・どの引数で呼ぶかはLLMの自律判断に委ねられており（ADR-0022）、「質問→タグ→情報源」という固定順の観測を毎回保証しない。また常時実行結果を記録する仕組みも持たない。
- 既存の管理画面（`front_dev`の`/admin`配下）には、QA一覧・タグ階層（`QaListPage`/`TagTreePage`、ADR-0013〜0015）、会話評価一覧（`EvaluatedMessagesPage`）、全データエクスポート（`ExportPage`、ADR-0046/0047）が存在する。本書が追加する検証機能も、この`/admin`配下の管理画面の1つとして追加する。
- 本書作成にあたり、発注者（ユーザー）に以下4点を確認し、回答を得た。本書はこの回答を前提に要件を定義する。
  1. 検証対象の質問の管理方式 → 「登録済みの質問セットを再実行可能に管理する」（都度入力の単発実行や、既存QAデータの自動流用は行わない）
  2. 検証結果の正誤判定機能の要否 → 「人が目視でタグ・情報源の適切さを判断し、評価を入力する」（正解データとの自動突合（Hit/Rank等）は本フェーズでは実装しない）
  3. 検証実行時に呼び出す処理の範囲 → 「`tag_selector_mcp`→`knowledge_mcp`の2段検索のみ」（`agent_invitro`経由や回答生成は対象外）
  4. 検証結果の保存先 → 「新規の検証専用テーブルを作成し、`web_backend`が直接読み書きする」（`knowledge_mcp`への新規ツール追加は行わない）

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| 検証質問 | 本機能で検証対象として登録する質問文（マスタデータ）。何度でも再実行できる |
| 実行 / 検証実行 | ある検証質問に対して`select_tags`→`search_knowledge`の2段パイプラインを1回動かすこと。実行ごとに結果がDBへ履歴として保存される |
| 選択タグ | ある実行において`select_tags`が返したタグ（`id`/`name`/`score`/`path`）の一覧 |
| 情報源 | ある実行において`search_knowledge`が返した検索結果（`id`/`source_type`/`title`/`content`/`score`/`metadata`）の一覧 |
| 評価 | 担当者が実行結果（選択タグ・情報源）を目視確認し、「適切」「不適切」等を記録する操作。実行単位に記録する（4.1節・7章） |
| 検証機能 / 検証画面 | 本書が追加する管理画面（`/admin/verification`配下）とそのバックエンドAPI・データの総称 |

## 4. スコープ

### 4.1 対象範囲（MVP）

- `front_dev`の`/admin`配下に、検証質問の一覧・登録・編集・削除、および検証実行・実行履歴閲覧・評価入力ができる画面を追加する（6.1節）。
- `web_backend`に、検証質問・検証実行のCRUD API、および検証実行APIを追加する（6.2節）。検証実行APIは、既存の`KnowledgeMcpClient`と同一方式（リクエストごとにMCPセッションを新規に張る）で、新設する`TagSelectorMcpClient`を用いて`tag_selector_mcp`の`select_tags`を呼び出し、続けて既存の`KnowledgeMcpClient`で`knowledge_mcp`の`search_knowledge`を呼び出す（6.3節）。
- 検証質問（マスタ）・検証実行（履歴、タグ・情報源のスナップショットを含む）・評価を保存する新規テーブルを`conversation`データベースに追加する（7章）。`web_backend`が既存の`ConversationDB`同様の直接アクセス方式で読み書きする。
- 一覧画面には、各検証質問について**最終実行（`executed_at`が最も新しい実行）の結果（選択タグ・情報源・評価状態）**を表示する（要望の「最終実行の際の結果」に対応）。過去の実行履歴は検証質問の詳細画面で確認できる。
- 個別の検証質問ごとに「再実行」操作を提供する（一覧からの一括再実行は4.2節で対象外とする）。
- ローカル`docker-compose`環境・AWS環境の両方で動作するようにする（既存の`CONVERSATION_DB_URL`の配線、ADR-0044/0045を踏襲。AWS向けの追加のネットワーク要件は9章参照）。

### 4.2 対象外（将来検討・別スコープ）

- 正解情報源（Ground Truth）の事前登録と、検索結果に正解が含まれるかの自動判定（Hit/Rank、MRR等）。本フェーズは目視評価のみとする（2章 回答2）。将来、既存の`evaluate.py`（MRR評価）との統合・置き換えを検討する場合は別途要件定義する。
- `agent_invitro`（ReActエージェント）経由の検証、および回答生成（LLMによる最終回答文の生成）の検証。本フェーズは`select_tags`→`search_knowledge`の検索部分のみを対象とする（2章 回答3）。
- 一覧からの複数質問一括再実行（バッチ実行）。個別実行のみとし、必要性が高まった場合に別途要件定義する。
- 検証質問のCSV等によるインポート・エクスポート機能（既存の全データエクスポート機能, ADR-0046/0047への新テーブル追加の要否は10章・12章で扱う）。
- タグ・情報源単位の個別評価（本フェーズは実行単位で1つの評価を記録する。7.4節・12章Open Issue参照）。
- `select_tags`・`search_knowledge`のパラメータ（`max_tags`・`confidence_threshold`・`top_k`・`min_score`）を画面から都度変更する機能。本フェーズは`web_backend`側の環境変数による固定値とする（6.3節）。
- 利用者ごとのログイン認証・操作権限分離。既存の管理画面群と同様、本フェーズはネットワークレベルの制限のみとする（既存Open Issue、202608211014 12章 #6と同一の課題として引き継ぐ）。

### 5.1 システム構成（追加分）

```

        ▼
web_backend（新規: verification_controller, TagSelectorMcpClient, VerificationDB）
        │                                   │

        ▼                                   ▼
tag_selector_mcp（既存, 変更なし）      knowledge_mcp（既存, 変更なし）
                                             │
                                             ▼
                                  chatbot データベース（既存, 変更なし）
```

- 検証結果は`conversation`データベースに保存する（ADR-0048）。`chatbot`データベースへの書き込みは発生しない。

## 6. 機能要件

### 6.1 画面（`front_dev`, `/admin/verification`配下）

既存の管理画面ナビ（`AdminLayout`, `admin-nav`）に「検証」リンクを追加し、以下の画面を新設する。既存の`QaListPage`/`QaFormPage`/`TagTreePage`と同様のコンポーネント構成方針（一覧・フォーム・詳細を画面単位で分離）に揃える。

#### 6.1.1 検証質問一覧ページ（`/admin/verification`, `VerificationListPage`）

- 一覧表示項目（1質問1行）:
  - 質問文（長文は省略表示、詳細ページへのリンク）
  - メモ
  - 最終実行日時（未実行の場合は「未実行」と表示）
  - 最終実行の選択タグ（`name`と`score`をバッジ表示。上位数件、詳細は詳細ページで確認）
  - 最終実行の情報源（`title`と`score`を表示。上位数件、詳細は詳細ページで確認）
  - 最終実行の評価状態（「未評価」／「適切」／「不適切」）
  - 最終実行のステータス（成功／エラー。エラー時はエラー内容を詳細ページで確認できるようにする）
- キーワード（質問文・メモ部分一致）による絞り込み、ページングを提供する（既存`QaListPage`と同様の方式）。
- 行内操作: 「再実行」（6.3節のAPIを呼び、一覧を更新）、「詳細」（6.1.3節へ遷移）、「編集」（6.1.2節へ遷移）、「削除」（確認ダイアログの上、削除）。
- 「質問を新規登録」ボタンを画面上部に配置する。

#### 6.1.2 検証質問登録・編集フォーム（`/admin/verification/new`, `/admin/verification/:id/edit`, `VerificationFormPage`）

- 入力項目: 質問文（必須、複数行テキスト）、メモ（任意）。
- 登録・更新後は一覧ページへ遷移する。既存`QaFormPage`と同様、`mode="create"|"edit"`で1コンポーネントを共用する。

#### 6.1.3 検証質問詳細ページ（`/admin/verification/:id`, `VerificationDetailPage`）

- 質問文・メモを表示する。
- 実行履歴を実行日時の降順で一覧表示する。各実行について:
  - 実行日時、ステータス（成功／エラー、エラー時はエラーメッセージ）
  - 選択タグ一覧（`rank`・`name`・`score`・`path`）
  - 情報源一覧（`rank`・`title`・`content`（全文またはプレビュー、6.3.3節）・`score`・`source_type`）
  - 評価欄: 「適切」／「不適切」の選択と、コメント入力欄。保存ボタンで6.3.5節のAPIを呼び出す。すでに評価済みの場合は既存の値を表示し、上書き保存できる。
- 「再実行」ボタンを配置する（一覧ページと同じAPIを呼び出す）。
- 実行履歴が多数になった場合に備え、ページングまたは直近N件＋「もっと見る」の形式で表示する（具体的な件数・方式は実装フェーズで確定する）。

### 6.2 API（`web_backend`, `/api/verification/*`）

既存の`/api/qa*`・`/api/tags*`と同様、`main/app.py`にルートを追加し、レスポンス生成は`controllers/verification_controller.py`に委譲する。

| メソッド・パス | 概要 |
|---|---|
| `GET /api/verification/questions` | 検証質問一覧を返す。各質問に最終実行（タグ・情報源要約・評価状態・ステータス）を含める。`keyword`・`limit`・`offset`に対応 |
| `POST /api/verification/questions` | 検証質問を新規登録する（`question_text`必須、`memo`任意） |
| `GET /api/verification/questions/{id}` | 検証質問の詳細と、全実行履歴（タグ・情報源・評価を含む）を返す |
| `PUT /api/verification/questions/{id}` | 検証質問の`question_text`・`memo`を更新する |
| `DELETE /api/verification/questions/{id}` | 検証質問を削除する（関連する実行履歴も削除される。7.3節） |
| `POST /api/verification/questions/{id}/run` | 検証実行を1回行う（6.3節）。実行結果（新規`verification_run`）を返す |
| `PUT /api/verification/runs/{run_id}/evaluation` | 指定した実行に対する評価（`evaluation`・`comment`）を保存する |

### 6.3 検証実行の処理内容（`POST /api/verification/questions/{id}/run`）

1. 対象の`verification_question`を取得する（存在しなければ404）。
2. `TagSelectorMcpClient`経由で`tag_selector_mcp`の`select_tags`を呼び出す。引数は`query=質問文`、`max_tags`・`confidence_threshold`は`web_backend`の環境変数（`VERIFICATION_MAX_TAGS`・`VERIFICATION_CONFIDENCE_THRESHOLD`、既定値は`tag_selector_mcp`自体の既定値と同じ3・0.0）を使う。
3. 呼び出しに失敗した場合（接続エラー・タイムアウト等）、`status="error"`・エラーメッセージを記録し、`verification_run`を保存して処理を終了する（情報源検索は行わない。6.3.2節）。
4. 呼び出しに成功した場合、返されたタグの`name`一覧を`tags`引数として、既存`KnowledgeMcpClient`経由で`knowledge_mcp`の`search_knowledge`を呼び出す。引数は`query=質問文`、`tags=選択タグのname一覧`、`top_k`・`min_score`は環境変数（`VERIFICATION_TOP_K`・`VERIFICATION_MIN_SCORE`、既定値は`knowledge_mcp`自体の既定値と同じ5・0.0）を使う。`category`は指定しない。
5. `search_knowledge`の呼び出しに失敗した場合、`status="error"`・エラーメッセージを記録し、選択タグは保存するが情報源は空のまま`verification_run`を保存する。
6. 両方成功した場合、`status="success"`として、選択タグ・情報源・使用したパラメータ・各呼び出しのレイテンシを`verification_run`・`verification_run_tag`・`verification_run_source`へ保存する（7章）。
7. 新規に作成された実行結果（評価は未設定）をレスポンスとして返す。

#### 6.3.1 選択タグが0件の場合の扱い

`select_tags`が0件を返した場合（該当するタグが見つからない場合）、`tags=[]`として`search_knowledge`をそのまま呼び出す（タグによる絞り込みなしの検索として扱う）。この場合、検証実行としては「タグが選択されなかった」という結果自体が観測対象であるため、実行は継続し、情報源検索結果もそのまま記録する。ただし`search_knowledge`側が`tags=[]`（空配列）と`tags`未指定（フィルタなし）を同一に扱うかどうかは`knowledge_mcp`の既存実装依存であり、本書では確認していない（12章Open Issue #1）。

#### 6.3.2 エラー時の扱い

- `select_tags`が失敗した場合は情報源検索を行わない（タグが決まらない状態で検索しても、検証の目的（タグ選択の妥当性と検索結果の妥当性を切り分ける）に対して意味のある結果にならないため）。
- 実行のたびに新規の`verification_run`行を作成する（既存実行を上書きしない、7.3節）。エラーであっても履歴として保存する（インフラの一時的な障害等を後から追跡できるようにするため）。

#### 6.3.3 情報源の`content`表示

`search_knowledge`が返す`content`（QA本文相当）は、担当者が情報源の適切さを判断するために必要な情報であるため、原則全文をそのまま保存・表示する。文字数が大きい場合の一覧表示上の省略（詳細ページでの全文表示への展開）はUI側の表示上の配慮とし、DBには全文を保存する。

### 6.4 評価の記録（`PUT /api/verification/runs/{run_id}/evaluation`）

- 対象の`verification_run`が存在しない場合は404。
- `evaluation`（`1`=適切 / `0`=不適切）・`comment`（任意）を受け取り、`evaluated_at`を現在時刻で更新する。
- 評価は実行（`verification_run`）単位に記録する。再実行すると新しい`verification_run`が作られ、評価は未設定の状態から始まる（古い実行の評価は保持されたまま残る）。

## 7. データ要件

### 7.1 配置方針

検証質問・検証実行・タグ・情報源・評価のデータは、`chatbot`データベース（QA・タグのマスタデータ、Knowledge MCP経由でのみ書き込む方針, ADR-0013）ではなく、`conversation`データベース（会話履行・評価データ、`web_backend`が直接読み書きする方針, ADR-0044/0045）に新規テーブルとして追加する。理由・検討した代替案はADR-0048を参照。

### 7.2 テーブル定義

既存の`db_conversation/init.sql`（ローカル）・`db_hiroba_qa_init`の`conversation`データベース向けスキーマ適用処理（AWS, ADR-0044）に、以下4テーブルのDDLを追加する。いずれも既存の`conversation`/`message`テーブルと同様、`CREATE TABLE IF NOT EXISTS`による冪等な定義とする。

```sql
-- 検証対象の質問（マスタ）
CREATE TABLE IF NOT EXISTS verification_question (
    id             SERIAL PRIMARY KEY,
    question_text  TEXT NOT NULL,
    memo           TEXT,
    created_at     TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at     TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 検証実行（1質問について実行するたびに1行追加される履歴）
CREATE TABLE IF NOT EXISTS verification_run (
    id                        SERIAL PRIMARY KEY,
    question_id               INTEGER NOT NULL REFERENCES verification_question(id) ON DELETE CASCADE,
    question_text_snapshot    TEXT NOT NULL,
    executed_at               TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    status                    VARCHAR NOT NULL,      -- 'success' | 'error'
    error_message             TEXT,
    max_tags                  INTEGER,
    confidence_threshold       REAL,
    top_k                     INTEGER,
    min_score                 REAL,
    tag_selector_latency_ms    INTEGER,
    knowledge_mcp_latency_ms   INTEGER,
    evaluation                SMALLINT,              -- 1=適切 / 0=不適切 / NULL=未評価
    evaluation_comment        TEXT,
    evaluated_at              TIMESTAMP WITH TIME ZONE
);

-- 検証実行ごとの選択タグ（select_tags結果のスナップショット）
CREATE TABLE IF NOT EXISTS verification_run_tag (
    id        SERIAL PRIMARY KEY,
    run_id    INTEGER NOT NULL REFERENCES verification_run(id) ON DELETE CASCADE,
    rank_no   INTEGER NOT NULL,
    tag_id    INTEGER,
    tag_name  VARCHAR NOT NULL,
    score     REAL,
    path      TEXT                                    -- select_tags の path をJSON配列文字列で保持
);

-- 検証実行ごとの情報源（search_knowledge結果のスナップショット）
CREATE TABLE IF NOT EXISTS verification_run_source (
    id           SERIAL PRIMARY KEY,
    run_id       INTEGER NOT NULL REFERENCES verification_run(id) ON DELETE CASCADE,
    rank_no      INTEGER NOT NULL,
    source_id    VARCHAR,
    source_type  VARCHAR,
    title        TEXT,
    content      TEXT,
    score        REAL,
    metadata     TEXT                                  -- search_knowledge の metadata をJSON文字列で保持
);
```

### 7.3 データのライフサイクル

- `verification_question`を削除すると、関連する`verification_run`・`verification_run_tag`・`verification_run_source`もすべて削除される（`ON DELETE CASCADE`）。実行履歴も含めて残したい場合は、削除の代わりに論理削除（例: `is_active`列の追加）へ変更する必要があるが、本フェーズでは実装しない（12章Open Issue #2）。
- `verification_run`は実行ごとに新規追加され、更新されない（評価の追記（`evaluation`・`evaluation_comment`・`evaluated_at`列のUPDATE）を除く）。既存の`ConversationDB.upsert`（`message`テーブルへのUPSERT、`evaluation`のみ更新可）と同様、実行結果自体は不変（イミュータブル）に保つ。
- `tag_id`（`verification_run_tag`）・`source_id`（`verification_run_source`）は、`chatbot`データベース側の`tag.id`・`qa_original.uuid`をそのまま値として保持するが、外部キー制約は設定しない（`chatbot`データベースと`conversation`データベースは別データベースであり、PostgreSQLの外部キー制約はデータベースを跨いで設定できないため）。したがって、参照先のタグ・QAが後から削除・変更されても、`verification_run_tag`・`verification_run_source`の内容（実行当時のスナップショット）は変化しない。

### 7.4 評価の粒度

評価（`evaluation`・`evaluation_comment`）は実行（`verification_run`）単位に1つ記録する設計とする。個々の選択タグ・個々の情報源に対して「このタグは不適切」「この情報源は的外れ」のように項目単位で評価する機能は、本フェーズでは設けない（`evaluation_comment`の自由記述で代替する）。項目単位の評価が必要になった場合は、`verification_run_tag`・`verification_run_source`への評価列追加を別途検討する（12章Open Issue #3）。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | 検証実行API（`POST .../run`）は、`select_tags`・`search_knowledge`という既存の2回のMCP呼び出し（いずれもLLM呼び出しを含む）に依存するため、既存の`/ask-sl`と同程度のレイテンシ（数秒〜十数秒程度）を許容する。一覧・詳細の参照系APIは既存の管理画面（QA一覧等）と同様、1秒以内を目標とする（暫定目標値） |
| 一覧の表示範囲 | 一覧画面が表示する「最終実行結果」は`executed_at`が最大の1件のみとし、それ以外の実行履歴はNを問わず詳細画面でのみ参照する（一覧APIのレスポンスサイズを抑える） |
| ログ | 既存の管理系操作ログ（`log_admin_operation`、`qa_controller`・`tag_controller`で使用）と同様の方式で、検証質問の登録・更新・削除、検証実行、評価保存を記録する |
| エラーハンドリング | `select_tags`・`search_knowledge`の失敗は、既存の`KnowledgeMcpError`と同様に業務エラーとして扱わず、実行結果（`status="error"`）としてDBに保存し、画面へは200系レスポンスで返す（実行自体はAPIとして「成功」しており、結果が「エラー」であることを区別する。既存の`KnowledgeMcpError`→409変換は書き込み系の業務エラー用であり、本APIには適用しない） |
| データ量 | MVPでは検証質問数・実行回数の上限は設けない。運用が進み実行履歴が大量になった場合の一覧・詳細のページング方式（6.1.3節）は実装フェーズで確定する |
| 可用性・セキュリティ | 既存の管理画面群と同一のネットワーク境界・アクセス制御（ローカルは`docker-compose`内、AWSは社内IPアドレス限定のALB, ADR-0041）をそのまま利用する。追加のログイン認証は設けない |
| 保守性 | `verification_db`モジュール・`TagSelectorMcpClient`は、既存の`conversation_db`モジュール・`KnowledgeMcpClient`と同一の実装パターン（コンテキストマネージャー、リクエストごとのMCPセッション）に揃える |

## 10. 既存システムとの関係・影響範囲

- `tag_selector_mcp`・`knowledge_mcp`・`chatbot`データベース・`agent_invitro`には変更を加えない。
- `web_backend`の既存API（`/api/ask-sl`・`/api/evaluate_response`・`/api/evaluated_messages`・`/api/qa*`・`/api/tags*`・`/api/export`）には変更を加えない。既存の`ConversationDB`（`message`・`conversation`テーブル）にも変更を加えない。
- 全データエクスポート機能（ADR-0046/0047、`web_backend/src/export/tables.py`の`CONVERSATION_TABLES`）は、現時点では`conversation`/`message`の2テーブルのみを対象としている。本書で追加する4テーブルをエクスポート対象に含めるかどうかは、本書のスコープでは決定せず、12章Open Issue #4として引き継ぐ（含める場合は`tables.py`への追記のみで対応可能であり、大きな構成変更は不要と見込む）。
- `front_dev`の既存画面（チャット・QA管理・タグ管理・評価済みメッセージ・エクスポート）には変更を加えない。管理画面の共通ナビ（`AdminLayout`）に「検証」リンクを追加する点のみが既存UIへの変更である。

## 11. 受け入れ基準（Definition of Done, MVP）

- [ ] `/admin/verification`で検証質問を新規登録できる。
- [ ] 登録した検証質問に対して「再実行」を行うと、`select_tags`→`search_knowledge`の順で処理が行われ、選択タグ・情報源が一覧・詳細画面に反映される。
- [ ] 一覧画面には各検証質問の最終実行結果（タグ・情報源・評価状態）のみが表示され、詳細画面では過去の実行履歴（複数回分）が確認できる。
- [ ] 詳細画面から、ある実行結果に対して「適切」／「不適切」＋コメントを保存できる。再実行後は新しい実行として評価が未設定の状態になる。
- [ ] `select_tags`または`search_knowledge`が失敗した場合でも、画面がエラーで停止せず、実行結果が「エラー」として記録・表示される。
- [ ] 検証質問を削除すると、関連する実行履歴（タグ・情報源・評価を含む）も削除される。
- [ ] ローカル`docker-compose`環境・AWS環境の両方で、本機能が動作する（AWS側は`admin_ui_task → tag_selector_mcp`の到達性が確立していることを含む）。
- [ ] 既存の`tag_selector_mcp`・`knowledge_mcp`・QA・タグ管理UI・会話評価機能・全データエクスポート機能の動作に影響がないことを確認する。

## 12. Open Issues（要追加確認事項）

1. **`tags=[]`と`tags`未指定の扱いの一致確認**: `select_tags`が0件を返した場合に`search_knowledge`へ`tags=[]`を渡した際の挙動（タグ絞り込みなしとして全件から検索されるか、逆に0件になるか）を、`knowledge_mcp`の既存実装（`search_service`・各`repository`の`search`実装）で確認する必要がある（6.3.1節）。挙動によっては、`tags=[]`のときは`tags`引数自体を渡さない（`None`）よう`web_backend`側で分岐する必要がある。
2. **検証質問削除時の実行履歴の扱い**: 本書はCASCADE削除（質問を消すと履行も消える）を採用したが、精度改善の記録として実行履歴を長期的に保持したいという運用ニーズがある場合、論理削除（質問を非表示にするが履行は残す）への変更を検討する必要がある。運用開始後に発注者へ確認する。
3. **タグ・情報源単位の評価粒度**: 現在は実行単位で1つの評価（適切／不適切＋コメント）のみを記録する設計だが、「どのタグが不適切だったか」「どの情報源が的外れだったか」を項目単位で記録したいという要望が運用開始後に出た場合、`verification_run_tag`・`verification_run_source`への評価列追加を別途要件定義する。
4. **全データエクスポート機能への追加要否**: 本書が追加する4テーブルを、既存の全データエクスポート機能（ADR-0046/0047）のダンプ対象に含めるかどうかは未確定。含める場合は`web_backend/src/export/tables.py`の`CONVERSATION_TABLES`への追記で対応できると見込むが、対象に含めるかどうかの判断（検証データの持ち出し要否）を発注者に確認する必要がある。
5. **検証質問の件数・運用ルール**: 何件程度の検証質問を登録・運用する想定か（数件〜数十件程度の想定か、既存QAデータ全件規模を想定するか）によって、一覧・詳細のページング方式、将来のバッチ再実行機能（4.2節で対象外とした機能）の必要性が変わる。運用開始前に発注者へ確認することを推奨する。
6. **利用者ごとのログイン認証・操作権限分離**: 既存の管理画面群と同一の課題（202608211014 12章 #6等）であり、本書独自の課題ではないが、検証結果・評価コメントに担当者名を残したいという要望が今後出た場合は、認証方式の確定と合わせて再検討する。
