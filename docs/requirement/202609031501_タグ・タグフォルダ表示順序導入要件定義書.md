# タグ・タグフォルダ表示順序（display_order）導入 要件定義書

- 文書番号: REQ-202609031501
- 対象プロジェクト: chatbot_invitro
- 対象コンポーネント: `db_hiroba_qa_init`（マイグレーション）、`knowledge_mcp`（`TagRepository`・タグ／タグフォルダ関連MCPツール）、`web_backend`（`tag_controller.py`）、`front_dev`（`TagTreePage.tsx`／`domain/admin/tag.ts`）
- 変更なしのコンポーネント: `search_knowledge`のスコアリングロジック（ADR-0058祖先展開・ADR-0059タグ構成類似度）、`qa_tag`テーブル、`tag_selector_mcp`、タグのis-a階層構造そのもの（`hiroba_tag.parent_tag_id`）、タグフォルダの親子関係構造そのもの（`hiroba_tag_folder.parent_folder_id`、ADR-0073）
- 参照資料: ADR-0074、ADR-0005、ADR-0072、ADR-0073、`docs/requirement/202609030857_タグフォルダ階層化要件定義書.md`

## 1. 目的

`hiroba_tag`（is-a階層）・`hiroba_tag_folder`（分類フォルダ階層、ADR-0073）の兄弟ノードに、管理画面（`TagTreePage.tsx`）で並べ替え可能な表示順序`display_order`を導入する。現状は`id`順（作成順）に固定されている一覧表示を、運用担当者が意味のある順序に並べ替えられるようにする。

## 2. 背景

タグ・タグフォルダの件数が増えるにつれ、`TagTreePage.tsx`上での一覧が作成順のまま固定され、関連するタグ同士をまとめたり、利用頻度の高いタグ・フォルダを上位に置いたりする運用上のニーズに応えられていない。ADR-0074は、この課題に対して、両テーブルへの`display_order`列追加と、「1つ上へ／1つ下へ」ボタンによる隣接ノード入れ替え方式での並べ替えを決定した。本書はこの決定を実装可能な粒度の要件に落とし込む。

## 3. 用語定義

| 用語 | 説明 |
|---|---|
| 兄弟集合 | `hiroba_tag`においては同じ`parent_tag_id`を持つノードの集合、`hiroba_tag_folder`においては同じ`parent_folder_id`を持つノードの集合。ルート直下（親が`NULL`）のノード同士も1つの兄弟集合として扱う。 |
| display_order | 兄弟集合内での表示順序を表す`DOUBLE PRECISION`型の値。値が小さいノードほど先に表示される。兄弟集合をまたいだ比較には意味を持たない。 |
| 中間値挿入 | ノードを兄弟集合内の別の位置へ移動する際、移動先の前後にあるノードの`display_order`の中間値を計算し、移動対象ノード1件のみを更新する方式。 |
| GAP | 新規作成時・末尾追加時に用いる固定の間隔定数（`1000.0`）。 |

## 4. スコープ

### 4.1 対象範囲

- `hiroba_tag`・`hiroba_tag_folder`両テーブルへの`display_order`列追加、および両テーブルの既存データへの初期値一括採番マイグレーション。
- `TagRepository`（`knowledge_mcp`）への`reorder_tag(tag_id, direction)`・`reorder_tag_folder(folder_id, direction)`の新設。
- `list_tags`・`list_tag_folders`の並び順を`display_order`基準（`id`をタイブレーク）へ変更。
- `create_tag`・`create_tag_folder`（`import_tag_batch`によるCSV一括作成を含む）における新規作成時の`display_order`採番（兄弟集合末尾への追加）。
- 既存の`move_tag`・`move_tag_folder`（reparent操作）における、移動後の`display_order`再設定（新しい兄弟集合末尾への追加）。
- 上記に対応するMCPツール定義（`mcp/tools.py`・`mcp/schemas.py`）の改修・新設。
- `web_backend`の`/api/tags/{tag_id}/reorder`・`/api/tag-folders/{folder_id}/reorder`エンドポイントの新設。
- `front_dev`の`TagTreePage.tsx`への「1つ上へ／1つ下へ」ボタンの追加（タグツリー・タグフォルダツリー双方）。

### 4.2 対象外（本書のスコープに含めない）

- ドラッグ&ドロップによる任意位置への並べ替え（ADR-0074決定2）。
- タグ自体のis-a階層構造・タグフォルダの親子関係構造自体への変更（既存のADR-0005・ADR-0073の構造はそのまま）。
- `TagPicker.tsx`のフォルダ別グルーピング表示（`groupTagsByFolder`）内でのタグの並び順制御。フォルダに割り当てられたタグは異なる`parent_tag_id`の兄弟集合をまたぐため、`display_order`だけでは一意な順序を決められない。本書では扱わず、Open Issue とする。
- `search_knowledge`・`QARepository`・ADR-0058/0059のロジック変更（ADR-0072・ADR-0073・ADR-0074の方針により対象外）。
- タグフォルダのCSVインポート/エクスポート（ADR-0072 Open Issue #2の結論待ち）。対応する場合、`display_order`を列に含めるかどうかは別途検討する。
- 兄弟集合単位の`display_order`再採番（メンテナンス操作）の自動化。本書ではOpen Issueとして残す（12章参照）。

## 5. 全体アーキテクチャ

```
front_dev
  └─ TagTreePage.tsx  … タグ／タグフォルダツリーの各ノードに「↑／↓」ボタンを追加（改修）
        │ HTTP: PATCH /api/tags/{tag_id}/reorder（新設）
        │ HTTP: PATCH /api/tag-folders/{folder_id}/reorder（新設）
        ▼
web_backend / tag_controller.py（改修）
        │ MCP: reorder_tag（新設） / reorder_tag_folder（新設）
        │ MCP: list_tags / list_tag_folders（並び順変更） / create_tag / create_tag_folder / move_tag / move_tag_folder（display_order採番ロジック追加）
        ▼
knowledge_mcp / TagRepository（改修）
        ▼
db_hiroba_qa（hiroba_tag・hiroba_tag_folder に display_order 列追加）
```

## 6. 機能要件

### 6.1 データモデル

```sql
ALTER TABLE hiroba_tag
    ADD COLUMN IF NOT EXISTS display_order DOUBLE PRECISION;

ALTER TABLE hiroba_tag_folder
    ADD COLUMN IF NOT EXISTS display_order DOUBLE PRECISION;

-- 既存データへの初期値一括採番（parent_tag_id / parent_folder_id ごとに、
-- 現行の id 順を 1000.0 刻みの display_order に変換する）
WITH ranked AS (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY parent_tag_id ORDER BY id) AS rn
    FROM hiroba_tag
    WHERE display_order IS NULL
)
UPDATE hiroba_tag AS t
SET display_order = ranked.rn * 1000.0
FROM ranked
WHERE t.id = ranked.id;

WITH ranked AS (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY parent_folder_id ORDER BY id) AS rn
    FROM hiroba_tag_folder
    WHERE display_order IS NULL
)
UPDATE hiroba_tag_folder AS t
SET display_order = ranked.rn * 1000.0
FROM ranked
WHERE t.id = ranked.id;

ALTER TABLE hiroba_tag ALTER COLUMN display_order SET NOT NULL;
ALTER TABLE hiroba_tag_folder ALTER COLUMN display_order SET NOT NULL;

CREATE INDEX IF NOT EXISTS idx_hiroba_tag_parent_tag_id_display_order
    ON hiroba_tag (parent_tag_id, display_order);

CREATE INDEX IF NOT EXISTS idx_hiroba_tag_folder_parent_folder_id_display_order
    ON hiroba_tag_folder (parent_folder_id, display_order);
```

- 既存データは、現行の一覧順（`id`順）と体感が変わらないよう、`id`順のまま`display_order`を採番する。
- 移行後は`display_order`を`NOT NULL`とし、以降のINSERT（`create_tag`/`create_tag_folder`）は必ず値を明示的に設定する。

### 6.2 `TagRepository`（`knowledge_mcp`）の改修・新設

- `list_tags(parent_tag_id=None)`: 各階層の兄弟ノードを、`ORDER BY id`から`ORDER BY display_order, id`へ変更する（`id`は同値時のタイブレーク）。ツリー構築後、各ノードの`children`配列もこの順序を反映する。
- `list_tag_folders()`: 同様に`ORDER BY display_order, id`へ変更する。
- `create_tag(...)`: 新規作成時、`parent_tag_id`が同じ兄弟集合内の現在の最大`display_order`に`GAP(1000.0)`を加えた値を採番する。兄弟が存在しない場合は`GAP`そのものを初期値とする。
- `create_tag_folder(...)`: 同様のロジックを`parent_folder_id`単位で適用する。
- `import_tag_batch`（ADR-0053/0061）経由での新規タグ作成も、`create_tag`と同じ採番ロジックを通す。
- `move_tag(tag_id, new_parent_tag_id)`: reparent後、新しい兄弟集合（`new_parent_tag_id`が同じ集合）の末尾に`display_order`を再設定する（既存の循環防止ロジックは変更しない）。
- `move_tag_folder(folder_id, new_parent_folder_id)`（ADR-0073）: 同様に、reparent後に新しい兄弟集合の末尾へ`display_order`を再設定する。
- `reorder_tag(tag_id, direction)`（新設、`direction: "up" | "down"`）:
  - 対象ノードの兄弟集合（同じ`parent_tag_id`、`display_order`順）を取得する。
  - `direction="up"`のとき、対象が兄弟集合の先頭であれば何もしない（No-Op、エラーにしない）。そうでなければ、直前の兄弟をB、Bの直前の兄弟をA（存在しなければ`None`）とし、対象の`display_order`を`A`が存在すれば`(A.display_order + B.display_order) / 2`、存在しなければ`B.display_order / 2`に更新する。
  - `direction="down"`のとき、対象が兄弟集合の末尾であれば何もしない（No-Op）。そうでなければ、直後の兄弟をC、Cの直後の兄弟をD（存在しなければ`None`）とし、対象の`display_order`を`D`が存在すれば`(C.display_order + D.display_order) / 2`、存在しなければ`C.display_order + GAP`に更新する。
  - 更新後のノード（`TagNode`）を返す。
- `reorder_tag_folder(folder_id, direction)`（新設）: 同様のロジックを`parent_folder_id`単位で適用する。

### 6.3 `web_backend`（`tag_controller.py`）

- `PATCH /api/tags/{tag_id}/reorder`（新設）: リクエストボディ`{"direction": "up" | "down"}`を受け取り、`reorder_tag`を呼び出す。
- `PATCH /api/tag-folders/{folder_id}/reorder`（新設）: 同様に`reorder_tag_folder`を呼び出す。
- 既存の`/api/tags`・`/api/tag-folders`（GET）のレスポンスに`display_order`を含める（フロントエンドが境界判定（先頭/末尾）にノードの並び位置を利用できれば必須ではないが、将来のドラッグ&ドロップ拡張やデバッグ用途のため含める）。

### 6.4 `front_dev`

- `domain/admin/tag.ts`の`TagNode`型・`TagFolder`型に`display_order: number`を追加する。
- `TagTreePage.tsx`のタグツリー・タグフォルダツリーの各ノード表示に「↑（1つ上へ）」「↓（1つ下へ）」ボタンを追加する。兄弟集合内で先頭のノードは「↑」を、末尾のノードは「↓」を無効化する。
- ボタン押下時、対応する`PATCH .../reorder`APIを呼び出し、成功後は一覧を再取得（または該当ノードの位置を更新）して表示に反映する。

## 7. データ要件

- `db_hiroba_qa_init`のマイグレーションとして、6.1節のDDL・初期値採番を追加する（既存の番号体系に従い新規マイグレーションファイルを作成、`IF NOT EXISTS`等による冪等性を維持する）。
- 既存の`hiroba_tag`・`hiroba_tag_folder`の`id`・`name`・`parent_tag_id`・`parent_folder_id`・`folder_id`データには変更を加えない。

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| 後方互換性 | タグ・タグフォルダの階層構造（`parent_tag_id`／`parent_folder_id`）・`folder_id`の意味は変更しない。既存の`search_knowledge`検索結果・スコアには影響しない。 |
| 更新コスト | 並べ替え1回の操作につき、更新される行は移動対象ノード1件のみとする（兄弟集合全体の再採番は行わない）。 |
| データ整合性 | 同一`display_order`が偶発的に重複しても一覧表示が破綻しないよう、並び順取得は常に`display_order, id`の複合順とする。 |
| 既知の制約 | `display_order`は浮動小数点のため、同一の2値間で中間値挿入を極端な回数（目安50回超）繰り返した場合、丸め誤差により順序が意図せず入れ替わる可能性が理論上ある。通常の手動操作の範囲では発生しにくいため、本書ではMVPとして許容し、対応が必要になった場合は兄弟集合単位の再採番機能を別途検討する（12章 Open Issue #1）。 |

## 9. インフラ・実行環境要件

- 新規の環境変数・AWSリソースは発生しない。`db_hiroba_qa_init`のマイグレーション実行フロー（ローカル`docker-compose`・AWS双方）に、7章のマイグレーションが追加されるのみ。

## 10. 既存システムとの関係・影響範囲

- `tag_selector_mcp`の`TagMetadataRepository`は`hiroba_tag`を明示的な列指定で読み込んでおり、`display_order`列自体は参照しないため、本書の変更による影響はない。
- `search_knowledge`・`QARepository.search`・`qa_tag`・ADR-0058/0059のロジックには変更を加えない。
- `TagPicker.tsx`の`groupTagsByFolder`によるグルーピング表示順は、本書のスコープでは変更しない（現状の並び順を維持する）。フォルダ内でのタグ表示順を`display_order`で制御する場合の設計は、Open Issue #2として別途検討する。
- `import_tag_batch`/`export_tags`（ADR-0053/0061/0065）は、`display_order`列をCSVの入出力列には含めない。インポートされたタグは常に兄弟集合の末尾に追加される。

## 11. 受け入れ基準（Definition of Done）

- [ ] `TagTreePage`のタグツリーで、あるタグを兄弟内で1つ上／1つ下へ移動できる。
- [ ] `TagTreePage`のタグフォルダツリーで、あるタグフォルダを兄弟内で1つ上／1つ下へ移動できる。
- [ ] 兄弟集合の先頭ノードでは「↑」ボタンが、末尾ノードでは「↓」ボタンが無効化されている。
- [ ] 新規作成したタグ・タグフォルダは、常に兄弟集合の末尾に追加される。
- [ ] 既存のタグ・タグフォルダを別の親へ移動（reparent）すると、移動先の兄弟集合の末尾に追加される。
- [ ] マイグレーション適用後、既存タグ・既存タグフォルダの一覧表示順が、マイグレーション前の`id`順（表示順）と一致する。
- [ ] 並べ替え・新規作成・reparentを行っても、`search_knowledge`の検索結果・スコア（`combined_score`/`tag_similarity`/`embedding_score`）に変化がないことを確認する。

## 12. Open Issues（要追加確認事項）

1. **`display_order`の再採番（メンテナンス操作）**: 浮動小数点の丸め誤差が問題になった場合に備え、兄弟集合単位で`display_order`を等間隔に振り直す再採番操作を用意するかどうか。用意する場合、自動検知（隣接値の差が閾値未満になったら自動実行）と手動実行（メンテナンススクリプト）のどちらの方式にするかも合わせて検討が必要。
2. **`TagPicker.tsx`のフォルダ別グルーピング内でのタグ表示順**: フォルダに割り当てられたタグは異なる`parent_tag_id`の兄弟集合をまたぐため、本書の`display_order`（is-a階層の兄弟内順序）だけでは一意な順序を決められない。フォルダ内表示順を制御したい場合、フォルダ割当自体に別途の順序キーを持たせる（例: タグとフォルダの割当を中間テーブル化し、そこに`display_order`を持たせる）等の拡張が必要になる。現時点でそのニーズが顕在化していないため、本書では対象外とした。
3. **ドラッグ&ドロップへの将来拡張**: ADR-0074は中間値挿入方式を採用しており、将来ドラッグ&ドロップによる任意位置への挿入に拡張する場合もスキーマ変更は不要と見込むが、API契約（`reorder_tag`の`direction`パラメータを、挿入先ノードIDの指定に置き換える等）の見直しが必要になる。本書では対応しない。
4. **タグフォルダのCSVインポート/エクスポート（ADR-0072 Open Issue #2）**: 対応する場合、`display_order`（または相対順序）を列に含めるかどうかは、Open Issue #2の結論と合わせて別途検討する。
